# Other UTXO systems: Bitcoin, BitML/ILLUM and Ergo

Researcher 7; retrieved 2026-10-12. Read-only research against Moriarty commit `84f64b30df53ff0b8ccaf475f57324d3d7c6e594`. Startup status confirms bounded loan/swap capability, unresolved dispatch accounting/binding gaps, and no pending transactions. No downloaded code was executed, dependency installed, or ledger transaction submitted. Claims below distinguish source facts, inspected implementation, and compatibility inference.

## Assessment

Ergo is a credible **public** alternative for a bounded Moriarty state-machine experiment: boxes carry typed state, native assets and guarding scripts, while scripts inspect spending inputs, outputs and read-only data inputs. Its built-in Sigma proving is not evidence of a generic private arithmetic/SNARK backend. Storage rent is an especially important counterexample to naïve history induction: a head box can leave the UTXO set through a protocol rent path without satisfying its normal script. Bitcoin offers useful authorization/compiler techniques, but deployed Taproot and Miniscript do not supply the transaction introspection assumed by ILLUM. These findings do not justify a backend migration or relax Moriarty's Preview execution gate.

Moriarty comparison uses the September 11 amendment in the supplied `MORIARTY-CONTEXT.md` and `LOCAL-ARCHITECTURE.md`: constrained genesis, immutable audited operation keys, fused authorization/transition/effects/intent/invariant relation, same-head consumption, and history induction. Older recursive-per-step descriptions are superseded for this planning assessment. Liability conservation, consumed outcome nonces, gross debit including change, oracle truth, liveness and private handoff remain additional obligations.

**Inference:** Taproot can hide unexercised script branches; that does not hide executed financial state, amounts or liabilities. Miniscript helps analyze spending policies but cannot establish a financial invariant simply because a witness is valid. An HTLC swap demonstrates hash/timelock authorization and coordinated settlement, not an arbitrary persistent debt ledger or private fused relation on vanilla Bitcoin. Pre-signed transaction protocols may implement useful finite financial subsets, but their setup, participant behavior, fees and renegotiation must be explicit.

## Secure compilation evidence

[Renegotiation and recursion in Bitcoin contracts](https://arxiv.org/abs/2003.00296), Bartoletti, Murgia and Zunino, downloaded as `bitml-recursion.pdf` / `.extract.txt`, is arXiv **v2, 2020-04-21** as printed on the PDF. Section 3 and Theorem 1 explain coherent symbolic/Bitcoin executions. Renegotiation compiles a new transaction set and exchanges signatures, with the initialization transaction signed last. Soundness assumes at least one protocol-following honest participant and polynomial computational runs under cryptographic assumptions. Section 5 distinguishes consensual variants executable on standard Bitcoin from a non-consensual recursive call that needs extra mechanisms. This is useful evidence for compiler correspondence and explicit cooperation assumptions, not proof that Moriarty's complete semantics fit Bitcoin.

[Secure compilation of rich smart contracts on poor UTXO blockchains](https://arxiv.org/abs/2305.09545), Bartoletti, Marchesin and Zunino, `illum-paper.pdf` / `.extract.txt`, is arXiv **v3, 2024-04-22** as printed. Sections 3 and 5 define a target extended with state arguments, output-field access, `verscr` and `verrec` covenants. Section 6 Theorem 2 provides a security correspondence under honest translated strategies and polynomial runs; section 7 contains a higher-level prototype including AMM/lending examples. Section 8 explicitly says ILLUM cannot compile to standard Bitcoin transactions. The author repository link `https://github.com/bitbart/illum-lang/` appears in the paper; it was not cloned within the three-repository budget. The theorem is a model-specific secure-compilation result, not universal proof of liability correctness, liveness, privacy or live Bitcoin deployment.

The original 2018 [BitML paper](https://eprint.iacr.org/2018/122.pdf) acquisition returned HTTP403; `bitml-original.receipt.json` and the returned HTML remain preserved. Search metadata identifies Bartoletti/Zunino and CCS2018; no full downloaded original-paper review is claimed. No access-control bypass or repeated retry was attempted.

## Ergo: enabled primitives and their actual guarantees

**Source facts:** [ErgoScript language description](https://docs.ergoplatform.com/dev/scs/sigma/lang-spec/) (`ergo-lang.html`, sections Data Types / Box / Context / Predefined global functions) specifies typed registers, box values/tokens/proposition bytes, collections and transaction context. [Data model](https://docs.ergoplatform.com/dev/data-model/data-model/) (`ergo-data-model.html`, sections 3–4) describes immutable boxes with obligatory R0–R3 and optional R4–R9. [Data inputs](https://docs.ergoplatform.com/dev/protocol/tx/read-only-inputs/) (`ergo-data-inputs.html`, Understanding Data Inputs / Usage) supplies read-only box access. Its statement that this feature is absent from other eUTXO systems is overbroad relative to Cardano reference inputs and is not adopted here.

**Implementation observations:** pinned `sigma-rust/ergotree-ir/src/chain/context.rs:14` exposes `self_box`, outputs, inputs, data inputs, preheader, ten headers and extensions. `ergo-lib/src/wallet/tx_context.rs:106` is a validation entry; `:239` selects the first input's ID as the permitted new token ID. `ergo-lib/src/chain/transaction/ergo_transaction.rs` defines native ERG preservation, weak token preservation and dust/height limits. These are source inspections, not executed validation results or a complete review of the reference node.

**Native issuance:** [Tokens](https://docs.ergoplatform.com/dev/data-model/box/tokens/) (`ergo-tokens.html`, Asset Creation / Limitations) and pinned `ergo-eips/eip-0004.md`, Ergo tokens background, agree that one new token ID can be issued per transaction, derived from its first spent input box ID; existing tokens can be burned. EIP4 is `Proposed`, `Forking: not needed`: its R4/R5/R6 naming/description/decimal metadata is a convention, not ledger-enforced semantic units. The protocol's first-class token facility is distinct from that metadata standard. A thread token needs quantity-one genesis, continuation/burn discipline and liability-preserving terminal rules.

**Sigma versus SNARK:** [Sigma protocols](https://docs.ergoplatform.com/dev/scs/sigma/) (`ergo-sigma.html`, Elementary protocols / Prover and Verifier Workflow) identifies discrete-log and equal-discrete-log proofs composed with AND/OR/threshold. Pinned `sigma-rust/ergotree-ir/src/sigma_protocol/sigma_boolean.rs:110` has the two proof-of-knowledge leaf families; `ergotree-interpreter/src/sigma_protocol/{prover,verifier,fiat_shamir}.rs` are the relevant implementation surfaces. Public script evaluation reduces conditions before proof verification. Nothing inspected establishes a generic native verifier for an arbitrary hidden Moriarty arithmetic transition, contract-property certificate or recursive SNARK. Ring/threshold signer privacy does not imply confidentiality of public registers, outputs, balances or private liability handoff. The [Ergo whitepaper](https://learn.ergoplatform.com/doc/whitepaper/) (`ergo-whitepaper.html`, sections ErgoScript / light verification / storage rent) adds architectural context; historical broad financial claims are not accepted as backend evidence.

## Storage rent is a history and liability obligation

[Rent guide](https://docs.ergoplatform.com/mining/rent/) (`ergo-rent.html`, Key Features / What About Tokens) says aged boxes can pay rent and inadequately funded boxes can expose their assets. Pinned `sigma-rust/ergo-lib/src/chain/transaction/storage_rent.rs:13` sets the period to **1,051,200 blocks**, not a wall-clock deadline. At `:24` an empty proof selects rent checking; `:52` computes serialized-size times the current storage fee factor; `:55` admits a box whose value is at most the rent without further restrictions. Otherwise `:64` preserves all registers except value R0 and creation information R3. The caller `ergo-lib/src/chain/transaction.rs:370` returns successful verification when this route succeeds, before normal script validation.

**Inference:** even a funded rent refresh changes the out-reference and ERG reserve outside Moriarty's ordinary operation relation. An underfunded rent spend can destroy or relocate its thread token and head entirely. Preserved registers do not prove an authorized revision step. Therefore history induction must include protocol rent moves or establish a bounded refresh/funding assumption and a recovery rule; an invariant inside the ordinary script alone cannot eliminate the protocol exception. Fees/rent must be explicit authorized financial effects, and a durable liability record cannot depend solely on an eventually reclaimable head box. `ergo-eips/eip-0039.md` documents monotonic creation-height hardening; the pinned library applies a height rule after block V3, but actual network activation was not independently queried.

## Financial applications and EIP counterevidence

Pinned `sigma-rust/README.md`, Usage Examples, links Oracle Core, Spectrum off-chain services and AgeUSD. This is dependency/ecosystem evidence only; those repositories were not cloned, audited or run. `ergo-eips/eip-0017.md`, Background/Structure, describes actual historical SigmaUSD proxy abuses: fee diversion, early returns and a fake bank box. Its proposal binds user output, fee output and bank NFT. This is particularly relevant to Moriarty: correct user net credit alone can miss protocol liabilities or shared-output allocation. A real state identity and complete effects must be checked by every participating validator.

`ergo-eips/eip-0043.md` describes Reduced Transaction data for offline signing; reduction is not financial settlement. `eip-0044.md` is a proposed arbitrary-data-signing convention with transaction/domain separation and network prefix. Moriarty still needs its own instance/program/head/action/limits/expiry/nonce binding, and an outcome nonce must survive successor heads. All these EIPs remain documentary `Proposed` in the inspected snapshot; implementation or application use does not itself establish universal adoption.

Current [Sigma6 docs](https://docs.ergoplatform.com/dev/protocol/sigma-6/), Activation, report mainnet activation in October2025 and ErgoTree version >=3 for new methods. That page was browser-read only and is not a hashed acquired source. It retains stale/inconsistent `Proposed` and creation/edit metadata, and EIP50 is absent from the pinned `ergoplatform/eips` master snapshot. Treat its activation claim as an official-document assertion requiring exact block/node corroboration before relying on new features. This assessment does not require Sigma6-only primitives.

## Specified-only experiments

1. Select one bounded Moriarty profile and define an Ergo head schema containing program/network/instance/revision, explicit liabilities and consumed outcome nonces. Specify a loan-payment transition that spends exactly one authenticated head and recreates exactly one successor. Demand exact script/token identity and gross input, change, fee, rent and unrelated-token accounting. Negative cases: duplicate successor, counterfeit singleton, wrong creditor, erased residual debt, reused outcome nonce and reference-only head.
2. Make **rent the first discriminator**: specify empty-proof spends just below/at/above the age threshold and just below/at/above the fee threshold, with a head NFT and residual debt. Observe expected protocol acceptance separately from language acceptance. Require a written inductive history statement covering funded rent refresh and underfunded loss before implementation approval.
3. Separately specify a private-field verifier experiment with an exact proof relation, public inputs and target-verifier/cost limits. A successful DLog/ring proof is not this experiment. If no measured compatible arbitrary-transition verifier exists, report public-subset feasibility only.
4. For Bitcoin, compare a finite pre-signed BitML loan/escrow fragment with the same liability model, naming every required participant and timeout exit. Reject any ILLUM lowering that uses unavailable covenants; hypothetical covenant results must be labeled proposed-target results.
