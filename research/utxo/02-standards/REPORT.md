# Cardano eUTXO standards and implementation status

Research date: 2026-10-12 UTC. Researcher 2. Read-only acquisition and analysis; no Cardano or Midnight transaction, build, source execution, or Moriarty modification. Startup read Moriarty AGENTS, development skill and wiki/index; guarded status returned SP01.6 loan-swap-subset with stale admission/accounting inputs and no pending transactions. Comparisons use the September 11 ledger-anchored acceptance amendment in MORIARTY-CONTEXT.md, not the older recursive-per-step interpretation.

**Conclusion — inference:** Cardano has implemented the transaction features needed to express an authenticated, consumed-and-recreated state head: reference inputs, inline datums, reference scripts and collateral return. These establish a plausible backend substrate for the *specified* Moriarty ledger-anchored design, not a correspondence proof or implementation. Ledger support, CIP editorial status, ecosystem adoption, and a particular SDK's tested support are different predicates. Two notable status mismatches are CIP-67 (Proposed while CIP-68 uses its labels) and CIP-109/133 (Proposed while implementation maps their builtins to protocol 11).

## Protocol and transaction semantics

**Source fact:** Official [timeline](https://cardano.org/hardforks/) records Vasil 22 September 2022/PV7, Chang 1 September 2024/PV9, Plomin 29 January 2025/PV10 and van Rossem 18 July 2026/PV11, all later entries remaining Conway. This is documentary activation evidence, not our own node/network observation. Chang documentation identifies V3 introduction but incorrectly/loosely says the first stage completed in August 2024; use timeline date for activation.

**Repository observation:** S03 `plutus-ledger-api/src/PlutusLedgerApi/Common/{Versions,ProtocolVersions}.hs` maps vanRossemPV=11, dijkstraPV=12, V4 introduction to Dijkstra. Batches 1–6 are available to V1/V2/V3 at PV11. Batch6 includes ExpModInteger, DropList, array operations, G1/G2 MSM, and value operations. Batch7 is assigned `futurePV=maxBound`: implemented source names such as MultiIndexArray/Policies/AssetCount/KeepPolicies/DropPolicies are explicitly not approved for a real protocol release. Current master containing V4/Dijkstra code does not establish mainnet V4 activation; no such timeline event was acquired.

**Repository observation:** S02 `eras/conway/impl/cddl/data/conway.cddl:108` body fields are 0 spending-input set, 13 collateral-input set, 16 collateral return, 17 total collateral, **18 reference-input set**. Output map keys are 0 address, 1 value, 2 datum option, 3 script reference. `datum_option=[0,hash32//1,data]`; `script_ref=#6.24(bytes .cbor script)`. Use this CDDL, not early CIP sketches, as the wire-format locator. Transaction inputs identify transaction ID plus output index, so replacing a head creates a new concrete out-reference.

**Repository observation:** S02 `eras/conway/impl/src/Cardano/Ledger/Conway/TxInfo.hs:510` translates spending/reference inputs via `Set.toList`; V3 includes reference inputs, fee, mint, validity interval, required signatories, redeemers, datum map, txid and governance fields. PV11 additionally rejects overlap between spending and reference inputs (`:512`, helper `:825`). Builder should spend the head once and inspect its resolved datum as its spending input; do not also place it in reference inputs to simulate a read/write operation.

**Source fact:** Babbage formal-spec `utxo.tex:23` defines collateral-return identity at index equal to number of normal outputs. `feesOK` requires key-address collateral and ADA-only *consumed difference*, minimum collateral fraction and equality to explicit total collateral when present. `Scripts-No` consumes collateral inputs and inserts collateral return, not normal outputs. Successful `Scripts-Yes` consumes regular spending inputs and inserts regular outputs. The collateral charge is at least the protocol-required amount, not necessarily exactly the rough amount in CIP-40's prose. Non-ADA collateral input assets must survive in the return.

**Repository observation:** S02 Babbage `utxo.tex:194` uses `(serialized output size +160) * coinsPerUTxOByte` for minimum output value. Inline data and reference script storage therefore carry minimum-ADA costs. Current fees additionally account for reference scripts; Conway PDF section 4 gives the fee calculation. Do not assume reference witnesses are free. Actual current fee coefficients, execution budgets and min-UTXO parameters were not queried.

**Repository observation:** S03 `Common/Hash.hs:23` hashes ledger-language tag followed by serialized script with Blake2b-224; V1/V2/V3 tags differ. Reference scripts satisfy a particular script-hash witness, not a mutable code pointer. The datum/programDigest binding and migration allowlist are still application's responsibility.

## Discrepancies and disposition

1. **Status drift:** CIP109/133/101/138/153 remain Proposed although S03 assigns their implemented functions to PV9/PV11. Disposition: preserve editorial status and report implementation activation separately. Combining official PV11 timeline and source mapping supports an activation inference; an exact released-node pin/live verification is still needed for execution acceptance.
2. **Normative-document drift:** Plutus PDF dated 14 September 2026 includes batch6 definitions and references PV11, but chapter 4 tables stop at PV10 and table 4.1 still labels Vasil June 2022. S03 version tables and official timeline are more specific/current on activation. Do not use the PDF's introduction tables alone as a deployment inventory. Its builtin definitions remain useful normative reference; discrepancies are not silently corrected in captures.
3. **Old CIP sketches:** CIP31 sketches reference inputs at field16, whereas deployed CDDL uses18; CIP33 sketches a list-style output and uses coinsPerUTxOWord, whereas the later CDDL supports the map with script_ref and Babbage spec uses coinsPerUTxOByte. Disposition: CIPs establish feature intent/status, pinned CDDL/spec establish serialized representation and rules.
4. **Compatibility evolution:** CIPs31–33's old blanket V1 prohibition must be read alongside Active CIP110's Chang change. That change does not grant V1 visibility into reference inputs or permission to ignore incompatible spent inline data.
5. **Moriarty architecture chronology:** Older wiki/README recursive-per-step mechanics are superseded by the September11 specified ledger-anchored plan. Assessment below applies the amended head-consumption design; recursive/off-ledger import release conditions remain separate open obligations.

## Backend implications and specified experiments

**Inference:** A consumed state UTXO plus unique, tightly controlled state token can anchor `(instanceId,headId,revision,stateCommit,lifecycle,programDigest,netTag)`. Every operation must verify the correct predecessor out-reference/token, program and network, authorization, transition relation, complete effects/fees and exactly the permitted successor head(s). A script address alone cannot identify authentic instance state: anyone can create an output at an address. CIP31 explicitly motivates authenticating data with tokens. Token uniqueness, mint/burn policy, constrained genesis, migration and closure are obligations to implement/prove, not properties supplied by CIP67/68.

**Inference:** Reference inputs can distribute immutable audited operation-key/configuration/certificate data without serializing reads. The referenced output must still exist at validation; replacing it can invalidate prepared transactions. Reference inputs do not run the data provider's spending conditions and cannot enforce payment/access policy by themselves. Main head writes still serialize at that head. This is useful deterministic contention, not automatic parallel updates to a shared loan state.

**Inference:** Ledger double-spend prevention supplies exact-predecessor consumption, but does not by itself establish the fused Moriarty relation or its global consumed-intent-nonce set across heads. A new out-reference or per-head revision cannot prevent the same authorized outcome intent being spent on another valid head. Preserve global authority accounting, full spent-UTXO gross debit, fees in net goals, and residual liabilities through successors.

**Recommendation — specified-only:** Freeze PlutusV3/PLC1.1.0/PV11 semantics plus exact compiler, validator bytes/hash, blueprint schema revision, cost model and network parameters. A Blueprint preamble's version is an application version, not a universal CIP57 version; no universal semver is asserted. Include all artifacts and immutable operation allowlists in programDigest/certificate records. Check ABI one-argument/unit return independently of framework abstractions.

**Recommendation — specified-only:** First transaction harness should verify authentic genesis; accepted loan/swap head consumption and exact successor; competing spends/stale reader rejection; wrong/missing datum, same-address forged state, duplicate state token, wrong purpose, extra/missing effect, swapped index, changed compiler/hash, wrong network and overlapping spending/reference inputs. Exercise phase2 failure separately: normal head/funds remain unspent, collateral charge and collateral return are exact. Test gross authority against full consumed value even with change, fee-adjusted net goal and liability preservation. Add a cross-head reused intent nonce rejection case.

**Recommendation — specified-only:** For optional certificates/imports, evaluate the *complete* target verifier with PV11 BLS/MSM/expMod using real proof/key encodings, malformed-point/subgroup/infinity handling, public-input binding and maximum permitted data/CPU/memory/size. CIP381 exposes opaque G1/G2/Miller-loop results and compressed encodings; it does not imply transcript compatibility with Midnight proofs or recursive verifier feasibility. The amended core path does not need recursive proof per on-ledger step. Public inline datums, redeemers and script execution do not preserve private financial/history guarantees; any privacy-preserving mapping needs a separate design and empirical certificate/commitment evidence.
