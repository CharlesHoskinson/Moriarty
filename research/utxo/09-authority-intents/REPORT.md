## 1. What wallet signatures establish

**Normative source facts.** [CIP-8](https://cips.cardano.org/cip/CIP-8), Active Tools standard, created 2020-09-28, standardizes arbitrary message signing with COSE. [CIP-30](https://cips.cardano.org/cip/CIP-30), Active wallet interface, specifies per-call informative consent for `signTx` and `signData`. `signTx` returns newly produced witnesses; partial signing can produce only the wallet's contribution. `signData` signs COSE `Sig_structure`, with EdDSA/Ed25519, raw address bytes, payment key for payment addresses or staking key for reward addresses. Its payload is un-hashed and external AAD is empty. Script addresses cannot use the base P2PK data-signing path. This does not prescribe an application nonce, cancellation system or financial constraint language. Locators: reused `02-standards/cips/CIP-0030/README.md`, “Full API”, `api.signTx`, `api.signData`; `CIP-0008/README.md`, “Specification / Payload encoding”; local `cip8.html`, `cip30.html` and receipts.

**Implementation observations.** [IOG Cardano JS SDK](https://github.com/input-output-hk/cardano-js-sdk), commit `48019e49c826ea77d81be0e2d2907f94406f5e04`, `packages/key-management/src/cip8/cip30signData.ts:90` creates protected address/key-id/algorithm headers; line127 signs the serialized COSE structure using the requested derivation path. It adds no application domain or nonce. `packages/wallet/src/cip30.ts:384` invokes a data confirmation callback; line420 decodes transactions, requests transaction confirmation and returns newly added signatures. These callbacks establish an integration seam, not proof that a particular wallet UI checks Moriarty semantics. [Emurgo message-signing](https://github.com/Emurgo/message-signing), commit `f76a82442594c8435fb577cb85da3ad594cf1063`, `rust/src/builders.rs:14–61`, implements the builder with empty default AAD and an optional Blake2b224 hash operation. The generic library supports options broader than CIP-30's constrained endpoint.

**Moriarty inference.** A transaction-body witness authorizes one constructed body; a COSE message signature authorizes whatever canonical payload Moriarty defines. The SDK's `packages/key-management/src/InMemoryKeyAgent.ts:145–164` signs `txBody.hash()`, confirming the distinct cryptographic preimage. Neither automatically enforces the other's meaning. Verify COSE structure, algorithm, key-to-address hash, expected credential/role and payload bytes; do not verify Ed25519 over bare application bytes when the wallet signed a COSE structure. A stake-key ownership proof is not payment authority by itself. Include protocol/type/version, network/genesis discriminator, contract/instance, program, signer role, action/constraint schema, expiry and nonce scope in the signed payload. CIP-30 network ID0 does not distinguish Preview from Preprod; `getNetworkId` is not a sufficient domain separator.

## 2. Script signatories and the incomplete on-chain economic view

**Implementation source facts.** Reused [cardano-ledger](https://github.com/IntersectMBO/cardano-ledger), commit `56ddee12ec768b85d14c62da049a33fc05114323`, `eras/conway/impl/src/Cardano/Ledger/Conway/TxInfo.hs:497–543`, constructs V3 context and obtains `txInfoSignatories` from `transTxBodyReqSignerHashes`, not by exposing every witness. Reused [Plutus](https://github.com/IntersectMBO/plutus), commit `0849ed6a3385d17ca7dacc075b29f15999d490e9`, `plutus-ledger-api/src/PlutusLedgerApi/V3/Contexts.hs:436–456`, includes spending/reference inputs, outputs, fee, mint/burn, certificates, withdrawals, validity, required signer hashes, redeemers, datums, ID, votes, proposals and treasury fields. **It has no collateral inputs, total-collateral or collateral-return fields.** `txSignedBy` at line573 searches this signer list. A key witness included only to spend an input does not automatically appear in the list checked by a validator.

**Normative activation.** [CIP-31](https://cips.cardano.org/cip/CIP-31) and [CIP-40](https://cips.cardano.org/cip/CIP-40) are Active Ledger CIPs, implemented with Vasil/Babbage. CIP-31 “Reference inputs” explicitly excludes reference value from balance, does not check referenced spending conditions or require signatures, and does not consume the output. CIP-40 introduces collateral return and an explicit amount at risk. Its motivation describes pre-Babbage pure-ADA/all-consumed restrictions; those are not current blanket rules.

**Counterevidence.** Current ledger `eras/babbage/impl/src/Cardano/Ledger/Babbage/Rules/Utxo.hs:238–310` checks collateral balance, including that non-ADA assets are accounted for in return. CIP-40's explanatory formula should not replace these implementation checks or a pinned era specification. Current wallet CIP-30 documentation deprecates `getCollateral`; dedicated pure-ADA collateral selection is not required as the only construction technique.

**Moriarty inference.** The on-chain checker can enforce normal transaction effects from this context; collateral loss must additionally be bounded by wallet/transaction signing policy, because the failed script cannot enforce its own intended outcome. Record a successful contract transition separately from a phase-two-invalid transaction that loses collateral. The sponsor and recipient of fee/minADA/collateral return must be explicit. Re-sign after any body alteration; obtain fresh resolved input values for policy evaluation. Do not describe ordinary Plutus validation as a ZK proof or preserved private intent/history.

## 3. Replay, role authority and cancellation

**Local amended requirements.** Moriarty `openspec/changes/pcd-ledger-anchored-acceptance/specs/pcd-mandatory-acceptance/spec.md:25–33` defines digest v2. Exact-head mode binds network, contract, entry point, instance, head, revision, commitment, program, action/arguments, caps, observations, certificates and validity; nonce is informational because a correct single-head extension consumes the predecessor. Outcome mode binds constraints, program allowlist, validity and durable per-instance consumed nonce. `PCD-INTEGRATION-2026-09-11.md:237` confirms this distinction. Treat both as specified-only, not an implemented Cardano signature format.

**Reference patterns.** Official [Marlowe data types](https://docs.marlowe.iohk.io/tutorials/concepts/marlowe-data), local `marlowe-roles.extract.txt:90–113`, distinguishes a transaction key signature from spending the role token in the same transaction. A mere reference input containing a role token does not meet this pattern. Reused [Minswap v2](https://github.com/minswap/minswap-dex-v2), commit `c3293ad435792ba502f5a2b1691c6736e5f167e6`, `validators/order_validator.ak`, uses owner-authorized or expiry-triggered cancellation of an order UTXO. `lib/amm_dex_v2/utils.ak:550–590` supports required signature, spent script, withdrawal script or minting-script authorization. Expired cancellation uses finite transaction lower-bound time and downstream output validation. This is an on-chain order-resource pattern, not evidence of a generic signed off-chain permit protocol.

**Moriarty inference and barrier.** A spent order/head prevents that resource's second consumption; it does not prevent reusing an outcome signature on another eligible head. Maintain a consumed-nonce accumulator/registry in authenticated state and preserve it across migration and split/join. Cancellation of an off-chain permit must update authenticated cancellation state or consume the permit resource; deleting an off-chain request does not revoke the signed bytes. Concurrent cancel/fill requires a shared consumed resource and a defined winner. Per-instance nonce consumption only provides per-instance uniqueness. If one signed route may choose among instances but must fill globally once, require a shared global nonce authority or constrain the signed instance set and jointly consumed authority. No collected CIP supplies this global protocol. Transferable role tokens also need explicit mint uniqueness, token return/burn, delegation and instance-scope rules; current possession cannot silently discharge inherited debt.

## 4. Oracle identity, signer validity and data freshness are separate

**Official guidance.** [Cardano Pyth integration](https://developers.cardano.org/docs/developers/curriculum/dapps/oracles/pyth/), local `pyth-official.extract.txt`, “Step1” and warnings, requires the Pyth state reference UTXO and explains that verification does not enforce freshness. Consumers must check update timestamps. Publication date was not verified. The oracle overview and debug-CBOR pages yielded HTTP200 with empty body extracts in this pass; search results are discovery only and not relied upon as retained full evidence.

**Actual implementation.** [Pyth consumer library](https://github.com/pyth-network/pyth-lazer-cardano), commit `217b5917228b17f015719b27dd616a75ad6bd800`, `lib/pyth.ak:45–100` finds the designated state NFT, parses inline datum, finds active withdrawal redeemer and parses messages without a second signature check. `lib/pyth/message.ak:44–60` verifies Ed25519 over payload and requires the whole transaction range inside the trusted signer's range. Raw upstream [`pyth_price.ak`](https://github.com/pyth-network/pyth-crosschain/blob/main/lazer/contracts/cardano/validators/pyth_price.ak), local `pyth-price.txt:16–40`, actually invokes that helper for each withdrawal update and authenticates state and script. API directory records blob `d91b7c5ea3e0b2f5a1dd80115b9fe8bbfd51dabe`; capture SHA256 `e5f18e6d42b6b22d5ab40fee9b71fb626f2f32a5fa7b9848779266e02b90dbf9`. It is a captured file, not a fourth repository snapshot or deployment verification.

**Counterevidence.** `pyth-design.txt`, “State abstraction”, documents an owner NFT that can disable the system by burning state, although governance alone alters meaning. “Zero-withdraw trick” explains why the consumer relies on the validated withdrawal. `pyth-contract-readme.txt` still contains TODO sections. Neither code availability nor official recommendation establishes deployment identity, audit completeness or liveness.

**Moriarty inference.** Bind oracle policy ID/deployment/governance trust, feed/channel, exponent, confidence and absent-value rules; check both signer trust and data age. For an accepted transaction interval `[l,u]` and update time `t`, require the interval to fit the freshness window (for example `t <= l` and `u <= t + maxAge`, with declared clock tolerance). Checking age against the builder's wall clock or against only one convenient point is insufficient. Signatures authenticate the publisher's statement, not market truth, availability or nonselective publication. Reference inputs are observations, never authority consumption or fresh-data proofs.

## 5. Gross funding, net outcome and liabilities

**Local observation.** `experiments/moriarty-language/src/successor/financial-outcome-intent.ts:1–5` identifies itself as an admission checker rather than a signature verifier. `checkOutcomeIntent` counts supplied Transfer/Fee effects and explicitly skips Originate/Accrue/Repay/DueCreated/DueSettled records. This is useful within its stated boundary, but cannot by itself cap newly created liabilities or derive native gross inputs. The corrected swap baseline requires whole 100000-A spent wallet value against authority even for a 10000-A trade with 90000-A change.

**Repository pattern.** Reused [Cardano Loans](https://github.com/fallen-icarus/cardano-loans), commit `66c556bdff4cdf4e8ffb765a22cab6ecd6be8e77`, `aiken/lib/cardano_loans/payment_validation.ak:236–406`, applies epoch interest/penalties, subtracts payment, preserves outstanding balance and counters in the successor, and burns beacons only at full payment. Lines626–636 bind lender address/loan-ID datum and payment value. `accept_validation.ak:218–300` creates explicit outstanding debt and loan-linked outputs. This is an inspected lifecycle pattern, not proof of ACTUS correspondence or a full security audit.

**Funding source facts.** [Marlowe minUTXO](https://docs.marlowe-lang.org/tutorials/concepts/minutxo/), local `marlowe-minutxo.extract.txt`, requires initial minimum deposit and ADA alongside native-token outputs. Its typical2–3ADA comment is an example, not a current protocol constant. Ledger `eras/babbage/impl/src/Cardano/Ledger/Babbage/TxOut.hs:674–701` computes minimum from serialized output size plus160-byte overhead and protocol parameter. Bigger nonce/obligation datums and additional duty outputs alter required funding.

**Adapter requirement, inferred.** Project every spending input's complete multiasset value by authorized actor; separately project normal outputs/change/locked minADA, mint/burn, reward withdrawals, fees and deposit/refund consequences of certificates/proposals/treasury actions. Either account for these target features or explicitly reject them. Preserve unrelated assets. Do not subtract change from gross authority; do subtract all attributed costs from net outcome, without counting the same fee twice. Maintain a separate nominal-liability projection and cap every DueCreated/origination/guarantee exposure even where no value moves immediately. Preserve residual debt and earmarked closure/continuation ADA across partial repayment and migration. Minimum output funding today does not guarantee later fee funding or executor availability.
