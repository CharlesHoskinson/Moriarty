# Cardano reference applications for Moriarty

Retrieved 2026-10-12. Read-only research: 15 primary page capture attempts (14 HTTP 200, Indigo HTTP 404), three shallow repository snapshots, no application builds or executions. The catalogue below contains 12 accessible repository candidates across eight protocol families; two are SDKs and one is a governance library. It does **not** establish 12 complete, recently maintained production applications. Public availability and `isArchived=false` are weaker evidence than ongoing maintenance. The three inspected contracts have immutable/deployed or version-specific histories, so old head dates need interpretation rather than automatic rejection.

Moriarty startup was followed: development skill, guarded status, wiki index and September 11 amendment. Status reported bounded loan/swap capability with dependent dispatch gaps and no pending transactions. This independent research performs no campaign or canonical wiki changes.

## Three strongest pinned teaching snapshots

### 1. Minswap: authenticated genesis, state identity and builder correspondence

Pin `c3293ad435792ba502f5a2b1691c6736e5f167e6`, branch main, commit timestamp 2024-07-10T12:01:34+07:00. Source observed at `validators/authen_minting_policy.ak:19`: genesis consumes a parameterized output reference, requires exactly the prescribed factory/global-setting mint and singleton outputs, then validates datums. This makes the token an authenticated marker, rather than treating any output at a script address as genuine state. The factory and pool minting paths remain part of the identity argument.

`validators/order_validator.ak:29` delegates ApplyOrder to a withdrawal credential; `validators/pool_validator.ak:156` shared batching reads authenticated global settings, checks authorized batcher, unique nonempty input indices and no mint. Off-chain `src/batcher-sample.ts:151` computes input ordering from txid/output index; `:421` constructs reference reads, consumed pool/orders, zero withdrawal, bounded interval, signer and recipient outputs. These are **sample/emulator builders** with dummy reference material, not proof of a production transaction service.

Moriarty inference: use a one-shot authenticated genesis plus checked successor marker for each head, and maintain an explicit transaction projection that corresponds to Core effects. Reference inputs supply settings/read-only observations and cannot consume head authority. Minswap's sample fees/deposits illustrate target funding but do not enforce Moriarty's gross authorized wallet debit policy.

README deployment/audit claims have exact locators `deployed/mainnet/{script,params,references}.json` and `audit-report/{certik,anastasia-labs}/`. The Anastasia PDF was locally passed to pdftotext; it yields only form-feed pages, so its findings/scope were **not** extracted or assessed. Embedded PDFs remain preserved in the snapshot; do not assert all audit issues resolved.

### 2. Sundae: shared batch validation and exact-once allocation

Pin `be33466b7dbe0f8e6c0e0f46ff23737897f45835`, main, 2025-02-26T11:47:57-05:00. `validators/order.ak` has Cancel (multisig/interval authority) and Scoop (withdrawal script requirement) branches. `validators/stake.ak` bridges orders to the authenticated pool output; `validators/pool.ak` validates same payment credential, settings token, authorized scooper and batched effects. Inspecting one order validator without the stake, mint and pool paths would omit the security relation.

`lib/calculation/InputSorting.md` explains the attack in which a malicious redeemer repeats cheap orders and omits expensive ones despite matching the total order count. `lib/calculation/process.ak:331` processes the selected input list; `:392` invokes `check_and_set_unique`. Outputs are traversed and consumed once in order, with a documented zero-output donation corner case. These are direct teaching references for preventing double satisfaction.

Moriarty inference: atomic composition requires an injective allocation or aggregate conservation argument over all participating effects. Input references and output ordinals must be bound, and the compiler must account for ledger ordering rather than trust builder insertion order. The zero-withdrawal pattern is an optimization with a whole-transaction proof obligation; copying the superficial delegation is unsafe. Authorized scoopers create scheduling/censorship assumptions; on-chain validity does not establish eventual execution.

### 3. Cardano-Loans: residual duties, tagged payments and safe recipients

Pin `66c556bdff4cdf4e8ffb765a22cab6ecd6be8e77`, main, 2026-02-15T14:03:57-05:00. `aiken/lib/cardano_loans/data/datums.ak:97` carries active loan principal, outstanding rational balance, epochs, interest, minimum payment, penalties, collateral rules, expiration, lender destination and unique loan ID (derived from offer out-reference). `payment_validation.ak:51` gathers all required successors/payments/burns. `:520` traverses outputs; `:631` checks lender address plus inline `(active_beacon_id,loan_id)` and payment quantity, then advances the output and required-payment lists. One paid output cannot be reused by that traversal for a second obligation.

`aiken/validators/cardano_loans.ak:59` discusses recipient compatibility: required datums can lock payments at arbitrary scripts, so a known proxy is supported with owner staking-credential authorization. This is a concrete limitation on unconstrained composability. `payment_validation.ak:129` also requires all payment loan inputs in the group to share the borrower address; general multi-party batching is not automatically supported.

Moriarty inference: nominal duties must survive successor construction independently of ledger token conservation; enforce rounding/residual balance and terminal default/reclaim disposition. Loan-tagged outputs help attribution but do not implement Moriarty's full authorization, invariant, history, private handoff or property-certificate relation. V2 is explicitly unaudited (`README.md:1519`); its version and semantic changes need independent review before adopting financial formulas.

6. Spectrum paired contracts/backend for executor architecture; Agora only for governance; SDKs only after the validator relation is understood.

Specify a public, two-instance loan repayment fixture for Moriarty's selected financial lifecycle profile. Consume authenticated head outputs, preserve residual duties, output loan-tagged creditor payments, and reconstruct complete gross wallet debit (including returned change), fee/min-ADA funding and collateral consequences. No ledger submission is requested. Positive case: one partial repayment for each instance. Rejection matrix: counterfeit marker; reference-read used as consumption; wrong network/program/head; duplicated head; omitted order; repeated input index; one output offered for two obligations; correct amount to wrong destination; stale nonce across revisions; liability deletion on close/migration; unsupported recipient datum; rounding underpayment; unauthorized fee/whole-wallet input; stale interval/oracle. Add builder-input reordering and retry against spent heads. Measure transaction bytes/exunits and failure outcomes only in a separately authorized implementation pass.

September 11 compatibility: authenticated head spend/recreate supports the **planned ledger-anchored inductive history** direction. It does not discharge deployment audit/property certificates, liability correctness, truthful observations, liveness or private handoff. These applications use public datums/redeemers and ordinary Plutus acceptance; no ZK verifier or preserved Midnight privacy is demonstrated. Recursive/off-ledger certificates remain a distinct feasibility obligation. No CIP activation decision is established here; app README statements that no fork is needed are publisher claims, not a normative standards-status review.
