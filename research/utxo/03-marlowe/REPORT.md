# Marlowe: bounded financial DSL and eUTXO state-machine comparison

Research date: 2026-10-12 UTC. Scope: source inspection and public document acquisition only. No downloaded code, theorem builds, validator benchmarks, ledger transactions or Moriarty experiments were executed. All proposed experiments below are **specified-only**. Research artifacts remain outside the canonical vault.

## Finding

**Inference:** Marlowe is the nearest inspected reference for mapping a bounded financial DSL onto eUTXO: an interpreter validates the consumption of a state-bearing output, computes the next state and payments, and constrains the continuation output. This supports the structural plausibility of Moriarty's September 11 ledger-anchored certified-state-machine plan. It does **not** establish preservation of Moriarty's four mandatory claims, private financial/history guarantees, fused proof relation or target-ledger feasibility. The most useful reusable artifacts are the explicit semantics/ledger boundary, interval conversion, role-payout design, genesis invariants and transaction-safety analysis.

## State, balances and authority mapping

| Aspect | Inspected Marlowe behavior | Moriarty compatibility inference |
|---|---|---|
| State | Datum holds parameters, accounts, choices, bound values, minimum time and residual contract; current minting genesis initializes empty choices/bound values and sorted unique positive accounts. | Head can carry or commit typed state, lifecycle/obligations, revision and program digest. Bind those fields at genesis; semantic maps alone do not identify a legitimate instance. |
| Identity | Current thread token derives from consumed seed and output index. Continuation carries that token; closing burns tokens. | Use unique instance/head identity and immutable authorized program/verifier binding. Consume the exact prior output; prevent substitute heads and replay across instances. |
| Balances | Script value equals internal account totals plus thread token. Transfers between internal accounts differ from external payments. | Constrain actual assets, gross consumed inputs, change, fees and residual duties separately. Marlowe conservation does not imply Moriarty gross-debit authority or fee-inclusive net goals. |
| Roles | Address inputs need payment-key witness; role inputs require spending a corresponding native token. Notify needs no witness. Role payouts lock funds at a payout validator whose datum identifies role currency/name; token holder withdraws. | Transferable bearer roles are an explicit authority choice. They cannot silently replace identity, signature scope, liability ownership or intent-consumed-nonce rules. |
| Time | Ledger range is converted to inclusive POSIX millisecond interval; open endpoints adjust by ±1 ms. Runtime converts slot validity upper bound to the last valid millisecond. | Constrain actual ledger-enforced interval and financial evaluation time, with explicit schedule/calendar/rounding conventions. Host clock/oracle assertion is insufficient. |
| Continuation | A When branch may reference a hash; validator obtains the continuation from transaction datums, then semantic input must match branch hash. | Merkleization is a code-distribution mechanism, not history authentication, proof recursion or secrecy. Preserve availability and hash/encoding agreement. |

## Validator versus runtime

**Repository observation:** On-chain validation runs `computeTransaction` against the spent datum and redeemer. It requires authorized deposits/choices, sufficient payouts, exact next datum/value and zero continuation on Close. It does not construct a transaction or require that each depositor funded the exact declared deposit; authorization plus resultant balances are checked. Current genesis minting checks consumed seed, no own script inputs, account positivity/order, initialization and role-policy admissibility.

**Repository observation:** Runtime `BuildConstraints.hs:529–627` computes slot interval, resolves/merkleizes inputs, invokes the same evaluator, consumes the previous script output, creates next state/payment constraints and burns the thread token on close. `Builders.hs:353–399` loads continuation closure from the store; `Safety.hs:216–293,347–456` uses protocol parameters, minimum UTxO requirements and simulated transaction checks. Safety error types include transaction size/execution cost possibly exceeding protocol limits. [Pinned builder](https://github.com/marlowe-lang/marlowe-cardano/blob/826b5fc5cf6ee77d40936d403301b5a65ec85ab9/marlowe-transactions/src/Language/Marlowe/Runtime/Transaction/BuildConstraints.hs).

**Inference:** A Moriarty backend needs an independently specified transaction projection and asset accounting relation as well as a semantic evaluator. Reusing an evaluator on/off chain reduces drift but cannot prove compiler correctness, complete-effect correspondence, validator identity, or trustworthy indexing. No current runtime deployment was queried.

## Formal proof, lifetime and resource boundaries

**Source fact:** The 2020 paper §§5.1–5.4 proves abstract evaluator termination, state invariants, conservation and timeout/trace bounds. The timeout result means an empty input transaction after the maximum timeout can close a valid funded contract. It does not mean the ledger autonomously refunds without submission, fees or available continuations. [Original paper](https://kar.kent.ac.uk/82483/2/LamelaSeijas2020_Chapter_MarloweImplementingAndAnalysin.pdf).

**Repository observation:** Formal pin `7b5b1e900ec53a8eb18747992bec73470704dfcb` contains `isabelle/Core/AssetsPreservation.thy:746` (valid/positive state and successful transaction imply per-asset conservation), `Timeout.thy:218` (explicit valid-state/time/nonempty hypotheses imply closed/empty result), and `TransactionBound.thy:316` (initial trace bound). No proof build was run. Haskell comments still describe refund ordering differences and absent Isabelle merkleization (`Semantics.hs:576–584,719`). `BlockchainTypes.thy:44` retains endpoint TODO. These are distinct correspondence obligations, not evidence that all proofs are invalid. [Formal repository](https://github.com/marlowe-lang/marlowe/tree/7b5b1e900ec53a8eb18747992bec73470704dfcb).

**Inference:** Finite lifetime and finite computation do not ensure every transaction fits protocol bytes/execution units, that a large Close fits, or that somebody can afford execution. Explicit Moriarty lifetime/work/obligation bounds should stay language properties; protocol parameters and full transaction feasibility are separate dynamic acceptance conditions. Merkleization lowers on-chain representation but does not bound state size, number of payouts, active continuation complexity or continuation-service availability.

**Source fact:** The 2025 Faustus paper proves specified optimizations with weak bisimulation in Isabelle; its conclusion and appendix explicitly leave full guard-disjointing algorithm verification unfinished. This supports a proof technique for observables-preserving compiler transformations, not correctness of current Marlowe validator bytes. [Paper](https://drops.dagstuhl.de/entities/document/10.4230/OASIcs.FMBC.2025.9).

## ACTUS and financial coverage

**Source fact:** Author source `marlowe-formal/papers/actus2021/article.tex:628–690` identifies a real restriction: indefinite ACTUS contracts such as UMP do not directly fit finite Marlowe contracts. Integer fixed-point arithmetic encodes real-valued formulas and must control scaling. Records are represented through integer bindings. §§assurance describe cross-testing Haskell versus Java and SMT analysis, not universal ACTUS conformance.

**Source fact:** Current official tutorial presents PAM terms and generated deposits/payments on a schedule. [ACTUS tutorial](https://docs.marlowe-lang.org/tutorials/concepts/actus-marlowe/). **Inference:** This is reusable evidence for scheduled bounded loan generation. It is insufficient for Moriarty's default, partial repayment, residual liability, allowance, day-count, rounding, intent or complete ACTUS coverage. Timeout-to-Close must not erase an unpaid financial duty merely because assets have been refunded. The current cardano checkout no longer packages `marlowe-actus`; claims of current generator coverage need a separately pinned `actus-core` follow-up.

## Composition concern requiring disposition

**Source fact:** Tweag's March 2023 audit identifies double satisfaction, initial-state invariants, implementation/specification drift and deficient money-preservation proof. Audited pins were formal `c8c67ad6892ec68842461d2e66b02ca87f93f70c` and cardano `523f3d56f22bf992ddb0b0c8a52bb7a5a188f9e9`. Maintainer response in the formal repo says subsequent changes were not re-audited. That audit is independent authoring commissioned by IOG, and excludes individual contracts/off-chain code. [Original audit](https://raw.githubusercontent.com/tweag/tweag-audit-reports/main/Marlowe-2023-03.pdf).

**Repository observation and inference:** The older separated V2 validator `Script.hs:325–355` rejects a second input at the same validator. Current V3 `Scripts.hs:584–589` instead defines `noOthers` by rejecting different validator hashes. Its closing branch permits multiple inputs through token burn counting; payouts are checked per datum as minimum payments. I cannot establish from inspection that two same-hash closing instances with identical payees cannot count the same payout twice. This is **not a reproduced exploit** or a claim about deployed scripts; it is a source-level question that blocks adopting these current validator patterns without a disposition. Genesis/thread-token uniqueness alone does not prove disjoint payment satisfaction.

## Prioritized specified-only experiments

1. **Payment isolation:** Construct two legitimate same-validator heads owing identical payees; close them atomically with one insufficient shared payout and a diverted remainder. Require rejection, then test distinctly tagged/aggregated payments. Also test other-validator composition. Highest priority because head uniqueness is not effect uniqueness.
2. **Genesis/head induction:** Reject forged initial state, duplicate thread mint, stale head, substituted state commitment, missing predecessor consumption, wrong program/network and unauthorized migration. Require liabilities and consumed intent nonce sets to persist across heads.
3. **Full-effect loan/swap projection:** Differentially compare bounded evaluator with exact ledger input/output values, minimum UTxO funding, fees, returned role tokens/change, gross debit caps and residual obligations. Require that 100,000 spent with 90,000 change still consumes 100,000 debit authority.
4. **Time/continuation/resource boundaries:** Test exact timeout endpoints, slot/millisecond conversion, ambiguous intervals, missing/wrong-hash continuations, large refund sets and maximum bounded contracts using current parameters. Report bytes and execution units with safety margin.
5. **Financial/correspondence matrix:** Pin target ACTUS revision and test schedule/day-count/rounding/default/partial-repayment vectors; prove or test each compiler/semantics/ledger boundary separately. Address refund-order and merkleization observations explicitly.

Midnight-specific preservation obligations remain private witnesses/commitments, fused certified acceptance and audited verifier-key identity. The new Moriarty amendment derives history inductively from constrained genesis and same-head accepted steps; recursive certificates are reserved for bounded off-ledger imports. Marlowe's public datum state chain is analogous structure only. It neither supplies privacy nor demonstrates the pending amendment's second independent review, release gates or any Cardano proof verifier budget.
