# Cardano compiler and transaction backend seams for Moriarty

Researcher 4; retrieval 2026-10-12 UTC. Bounded primary-source review, no downloaded code executed, no implementation, compilation or ledger submission. Scope: 1 paper, 12 documentation/release pages, 3 new repository snapshots; two previously acquired standards repositories and the official hard-fork timeline reused read-only. Exact source metadata, hashes and receipts are in `sources.json`. Repository snapshots are not fully audited.

## Assessment

**Compatibility inference:** The strongest first experimental target is **Moriarty bounded Core → generated Aiken validator → Plutus V3/UPLC + CIP-57 blueprint**, paired with **Lucid Evolution for transaction assembly**, followed by an independent inspection of final CBOR and its resolved UTXOs. **Plinth** is a credible second compiler target or independent semantic reference, particularly for a Haskell-oriented assurance workflow. Direct generation of UPLC is a possible later target, but expands the custom compiler and ABI assurance burden. CML/CSL and Mesh are transaction infrastructure, not alternative on-chain acceptance languages.

This recommendation concerns public ledger validation only. It does not establish a target-compatible ZK verifier, private state, private intent, private handoff, off-ledger certificates, compiler correspondence, or Moriarty acceptance. The September 11 planning amendment means the relevant first relation is the fused ledger-anchored step, not mandatory recursive proof verification on every step. That amendment remains specified-only and the sole Midnight Preview execution gate remains unchanged.

## Evidence and maintained targets

1. **Source facts — Aiken.** The official [validator documentation](https://aiken-lang.org/language-tour/validators) describes typed handlers, including `spend` with optional datum, redeemer, consumed output reference and transaction; mint and other purposes have separate handlers. Datum presence must be checked explicitly; creating an output at a script does not run its spending validator. The default fallback rejects. Artifact: `aiken-validators.extract.txt`, “Managing (Optional) Datum” and “Fallback handler”. [Compiling documentation](https://aiken-lang.org/fundamentals/getting-started) describes generated `plutus.json`, `aiken check`, execution costs and benchmarking. Artifact: `aiken-compiling.extract.txt`, “Compiling a project” and “Running tests”. These are tool features, not evidence this study ran them.

   **Repository observations:** Aiken main commit `2a0475328be2fc361251be864b825c936fefb63b`, committed 2026-10-08. Inspected `crates/aiken-project/src/config.rs:35` and `:436`: configuration explicitly rejects non-V3 targets. `crates/aiken-project/src/blueprint/memo_program.rs:13` calls the UPLC generator and converts to De Bruijn form; `blueprint/validator.rs:25` records datum/redeemer/parameters/program/schema. `examples/gift_card/validators/oneshot.ak:12` provides a concrete mint/spend example using consumed out-reference, input address, exact token quantity and purpose rejection. This example is not a complete Moriarty head policy. [Release page](https://github.com/aiken-lang/aiken/releases), `aiken-releases.extract.txt`, latest v1.1.24 dated **2026-09-26**, describes first-class UPLC Value support and V3 conformance coverage. The current [home page](https://aiken-lang.org/), `aiken-home.extract.txt`, lists V4 and first-class zero-knowledge support as ongoing work; do not promote these to implemented privacy.

2. **Source facts — Plinth/Plutus.** [Plinth User Guide](https://plutus.cardano.intersectmbo.org/docs/), `plinth-guide.extract.txt`, identifies Plinth (formerly Plutus Tx) as a Haskell subset compiling to Plutus Core; transaction construction and querying require separate off-chain code. Liu, MacKenzie, Kireev, Peyton Jones, Wadler and Chakravarty, [“Plinth: A Plugin-Powered Language Built on Haskell (Experience Report)”](https://homepages.inf.ed.ac.uk/wadler/papers/plinth/plinth.pdf), Haskell ’25, October 12–18, 2025, DOI 10.1145/3759164.3759347. Artifact: `plinth-paper.pdf` / `plinth-paper.extract.txt`, §§2, 4–6. The compiler passes through GHC Core, PIR, typed Plutus Core and UPLC; UPLC evaluates strictly, unlike ordinary lazy Haskell. The instrumented CEK evaluator accounts CPU/memory. Compiler transformations and repeated evaluation can affect cost. The paper is an author experience report, not an independent Moriarty compiler-correctness proof; historical budget descriptions are not current parameter measurements.

   **Repository observation:** Reused Plutus master `0849ed6a3385d17ca7dacc075b29f15999d490e9` from `../02-standards/plutus`. Inspected `plutus-ledger-api/src/PlutusLedgerApi/V3/Contexts.hs:429–508` (TxInInfo, TxInfo, ScriptContext and findOwnInput), and Common/{Versions,ProtocolVersions}.hs. V3 context provides normal inputs, reference inputs, outputs, fee, mint, validity interval, signatories, redeemers, datums and transaction ID; it does **not** expose collateral inputs/return/total collateral as TxInfo fields. `findOwnInput` resolves the spending out-reference among consumed inputs. Collateral authority cannot simply be added as a public validator check against a nonexistent context field.

3. **Source facts — versions and activation.** [Different Notions of Version](https://plutus.cardano.intersectmbo.org/docs/essential-concepts/versions), `plutus-versions.extract.txt`, distinguishes ledger language, PLC version, protocol version and cost model; importing V3 and selecting a PLC compiler target are different actions. [August 26, 2026 update](https://updates.cardano.intersectmbo.org/2026-08-26-plutus-core/), `plutus-update.extract.txt`, reports package release 1.68.0.0 containing V4 API types but explicitly says V4 remains under development. Reused [official hard-fork timeline](https://cardano.org/hardforks/), `../02-standards/hardforks.extract.txt:1–10`, records **van Rossem, July 18, 2026, PV11.0, Conway**. Plutus source maps vanRossemPV to 11, Dijkstra to 12, V4 to Dijkstra and unreleased batch7 builtins to futurePV. Thus target **V3 + PLC1.1.0 with pinned PV11 semantics** is a reasonable documentary baseline; current repository V4 code is not activation evidence. No node parameters or test network were queried. Documentation describes planned compatibility changes too: pin the actual source table and protocol generation rather than relying on broad version names.

4. **Normative source fact — CIP-57.** [CIP-57](https://github.com/cardano-foundation/CIPs/blob/b4a593c960f2751fef2ddc8df28bec7b22c68eb5/CIP-0057/README.md) is **Active**, created 2022-05-15. Reused artifact: `../02-standards/cips/CIP-0057/README.md`, header, “Document Structure”, “preamble”, “validators”. It defines a JSON Schema blueprint with validator arguments/schema, optional compiled serialized flat script, and script hash required when compiledCode is present; compile-time parameters must be instantiated before final script identity. A blueprint is an ABI/interoperability artifact, not a property certificate or proof of correspondence. Its application version must not be mistaken for a universal CIP schema semver.

## Moriarty correspondence and barriers

**Local repository observations:** Startup skill/status and wiki index were read; no pending transactions were returned. Inspected `experiments/moriarty-language/src/lower-compact.ts:29` restrictions and `openspec/PCD-INTEGRATION-2026-09-11.md` decision/stage graph. Existing Compact lowering explicitly excludes obligation-ledger, authority, proof and settlement acceptance. Neither generation of Aiken nor a successful evaluator result can inherit these missing relations. The amendment supersedes older recursive-per-step prose; imports/certificates and private handoff remain separate release obligations.

**Compatibility inferences:** Consuming a script-controlled live head is a natural counterpart to exact-head read/write. It still needs constrained genesis, unique state token mint/burn discipline, exactly one permitted successor or terminal path, instance/network/program binding, revision and persistent nonce consumption. A minting example or script address is insufficient. A state commitment alone does not make a private transition publicly verifiable.

The adapter must extract **all final consumed wallet value**, not just intended Transfer records. Moriarty’s scoped swap rule charges the whole 100,000-A input even when 90,000 A returns as change. Builder coin selection can therefore invalidate an otherwise valid business intent. Minimum ADA, fees, collateral-loss exposure and unrelated native assets need explicit payer/authority treatment. V3 validators see the successful transaction fee and normal value movement; collateral on invalid transactions requires a separate signed wallet transaction policy and observed outcome record. A validator cannot protect the wallet from its own phase-two failure using checks that never accept.

Integer arithmetic and serialization require profile-specific correspondence: UPLC integers do not automatically preserve Moriarty UInt128 overflow, signedness, FloorDiv, nominal units, rounding or liabilities. Bound redeemer/datum/list sizes and every transaction-wide traversal. State tokens preserve neither oracle truth/freshness, due execution/liveness, nor liabilities on migration. Protocol cost changes require re-evaluation and manifest requalification.

Public datum/redeemer and UPLC acceptance do not preserve Midnight privacy. ZK acceptance needs a separately selected compatible proof system, actual verifier relation/public input binding and measured V3 budgets. Pairing builtins or a compiler roadmap item alone do not establish this.

## Next experiments — specified-only

1. Freeze one atomic profile and reject unsupported constructs. Specify a generated Aiken V3 relation for one loan payment and swap head transition, with exact token policy, successor count, program/network/instance/revision, typed effects, durable outcome nonce and full final transaction projection. Retain source/blueprint/compiler/dependencies/UPLC/hash/PV/cost-model/parameters in the program manifest. Use Plinth as a bounded independent reference for ABI and arithmetic, not an assumed equivalent compiler.
2. Specify differential vectors comparing Moriarty Core evaluation and final UPLC validation: overflow/division/rounding, missing datum, duplicate state token/successor, reference-only predecessor, replay, wrong recipient, hidden extra input, business transfer versus gross input, migration liability erasure, change/min-ADA and fee sponsor. Require the adapter to reject added inputs outside authority after completion.
3. Specify a local evaluator versus pinned node evaluation experiment on identical final CBOR/resolved UTXOs and cost models, including deliberately invalid scripts and collateral outcomes. Report execution units, tx size, fee, min-ADA and collateral independently. No measured budget/throughput claim exists here.
4. Gate private mode separately: select an actual compatible verifier and corrupted-proof controls, quantify public-input/data leakage and verifier cost, then decide whether a private backend is feasible. Do not call the public prototype a privacy-preserving Moriarty backend.
