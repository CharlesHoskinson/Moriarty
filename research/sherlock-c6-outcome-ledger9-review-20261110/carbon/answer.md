### 1. Soundness, completeness, partition invariance, and remaining public leaks

#### 1.1 Soundness and completeness of outcome-only publication

Under M3 (`C = 8`), closing a leaf is a prover choice ([openspec/changes/sherlock-vm-consensus-20261107/design.md:77](file:///home/hoskinson/Projects/Moriarty/openspec/changes/sherlock-vm-consensus-20261107/design.md#L77)). Each leaf allocates physical addresses `base .. base + C - 1`, pads unused rows `len_end - base .. C - 1` with zero tuples (`tag = 0`), refuses reads of zero tuples, and sets `post_d.len = base + C` ([openspec/changes/sherlock-vm-consensus-20261107/design.md:99-105](file:///home/hoskinson/Projects/Moriarty/openspec/changes/sherlock-vm-consensus-20261107/design.md#L99-L105), [qa/gemini-quint/chipleaf-pairrow-m3/verdict.md:40-47](file:///home/hoskinson/Projects/Moriarty/qa/gemini-quint/chipleaf-pairrow-m3/verdict.md#L40-L47)). Consequently, for two runs of the same `(prog_d, input_d)` under different leaf partitions `P_1` and `P_2`, there is a strictly increasing map `f: N -> N` (`a < b <=> f(a) < f(b)`, hence `a == b <=> f(a) == f(b)`) from logical allocation ordinal to physical M3 address.

Outcome-only publication is **sound and complete** across leaf partitions if and only if the following three internal conditions hold alongside hiding `lanes_d` / `mem_root`:

1. **Order- and equality-only handle use (already holds for `RefC`):** Sherlock Machine A has no references ([crates/mori-core/src/sherlock/reference_types.rs:14-24](file:///home/hoskinson/Projects/Moriarty/crates/mori-core/src/sherlock/reference_types.rs#L14-L24)). In C6, `RefC` (`Const(usize) | Data(usize)`) derives only `Clone, Copy, PartialEq, Eq, Debug` ([crates/mori-core/src/sherlock/helper_machine/shared.rs:701-705](file:///home/hoskinson/Projects/Moriarty/crates/mori-core/src/sherlock/helper_machine/shared.rs#L701-L705)), every primitive dereferences before computing, and `BHelperEqual` traverses value structure step-by-step without branching on raw address arithmetic ([crates/mori-core/src/sherlock/helper_machine/families/structural.rs:130-200](file:///home/hoskinson/Projects/Moriarty/crates/mori-core/src/sherlock/helper_machine/families/structural.rs#L130-L200), [research/sherlock-processor-analogy-20261110/experiments-4.md:274-279](file:///home/hoskinson/Projects/Moriarty/research/sherlock-processor-analogy-20261110/experiments-4.md#L274-L279)). Even if pointer-equality short-circuiting were used, `f(a) == f(b) <=> a == b` preserves exact step-for-step equivalence (`RuleIdC` trace and total step count `n_steps`).
2. **Elimination of `start + k` slice arithmetic and dense `fresh == active.*` equalities (REQUIRED CHANGE — completeness blocker):** Outcome-only publication hides addresses at the *end* of the run, but C6 rules also compute addresses *during* the run:
   - Multi-step argument building (`HelperControlC::Append`, [crates/mori-core/src/sherlock/helper_machine/shared.rs:804-812](file:///home/hoskinson/Projects/Moriarty/crates/mori-core/src/sherlock/helper_machine/shared.rs#L804-L812)) and ADT field building (`HelperControlC::Build`, [crates/mori-core/src/sherlock/helper_machine/shared.rs:852-862](file:///home/hoskinson/Projects/Moriarty/crates/mori-core/src/sherlock/helper_machine/shared.rs#L852-L862)) append one element per owner step and enforce `field_start + src_cursor == pre.active().data_fields` ([crates/mori-core/src/sherlock/helper_machine/shared/owner_runtime.rs:2990](file:///home/hoskinson/Projects/Moriarty/crates/mori-core/src/sherlock/helper_machine/shared/owner_runtime.rs#L2990), [crates/mori-core/src/sherlock/helper_machine/shared/owner_runtime/owner_adt_runtime.rs:1585](file:///home/hoskinson/Projects/Moriarty/crates/mori-core/src/sherlock/helper_machine/shared/owner_runtime/owner_adt_runtime.rs#L1585)). Consumers then read `args.start + a_cursor` ([crates/mori-core/src/sherlock/helper_machine/families/structural.rs:637](file:///home/hoskinson/Projects/Moriarty/crates/mori-core/src/sherlock/helper_machine/families/structural.rs#L637)) and `fields.start + k` ([crates/mori-core/src/sherlock/helper_machine/shared/owner_runtime/owner_adt_runtime.rs:1601](file:///home/hoskinson/Projects/Moriarty/crates/mori-core/src/sherlock/helper_machine/shared/owner_runtime/owner_adt_runtime.rs#L1601)).
   - Under M3, whenever a multi-step `Append` or `Build` crosses a leaf boundary (including forced leaf close at slot `S = 16`) with `used < C`, rows `base + used .. base + C - 1` are zero-padded and the next element lands at `base + C != start + k` (and in a single unified `MEM` log, interleaved frame spills `PUSH` also separate slice elements within one leaf). Reading `start + k` then hits a zero-padding row (refused by D3) or a frame cell — breaking **completeness** for honest multi-argument calls and multi-field constructors.
   - Likewise, C6 checks `new_id == pre.img.active.{data, env}` ([crates/mori-core/src/sherlock/helper_machine/shared/owner_runtime.rs:3021-3055](file:///home/hoskinson/Projects/Moriarty/crates/mori-core/src/sherlock/helper_machine/shared/owner_runtime.rs#L3021-L3055)).
   - **Fix:** Store inline child references directly in the `MEM` row for arity `<= 2` (`Leaf`, `Cons`, `Branch`), and represent variadic `Args` (`value_slots`) and ADT `Constructor` field lists as immutable cons-linked cells `(TAG_SLICE, elem_ref, prev_link)` (matching `EnvCellC.previous` at [crates/mori-core/src/sherlock/helper_machine/shared.rs:1057-1061](file:///home/hoskinson/Projects/Moriarty/crates/mori-core/src/sherlock/helper_machine/shared.rs#L1057-L1061) and D7 `fp` at [openspec/changes/sherlock-vm-consensus-20261107/design.md:107](file:///home/hoskinson/Projects/Moriarty/openspec/changes/sherlock-vm-consensus-20261107/design.md#L107)). Replace `new_id == active.*` with `new_addr == running_len`. No rule ever computes `addr + k`.
3. **Prohibition of traps on physical `mem_len` (REQUIRED CHANGE — soundness blocker):** `ExhaustReason` includes `DataNodes`, `DataFields`, and `EnvironmentCells` ([crates/mori-core/src/sherlock/helper_machine/shared.rs:367-378](file:///home/hoskinson/Projects/Moriarty/crates/mori-core/src/sherlock/helper_machine/shared.rs#L367-L378)). Because a malicious prover can close every leaf after 1 step (`steps = 1`), inflating physical `mem_len` by `C = 8` per step even on zero-append steps ([qa/gemini-quint/chipleaf-pairrow-m3/verdict.md:62-66](file:///home/hoskinson/Projects/Moriarty/qa/gemini-quint/chipleaf-pairrow-m3/verdict.md#L62-L66)), **any trap that compares physical `mem_len` against a bound would let a malicious prover turn an honest `Halted(v)` run into a valid proof of `Exhausted(...)`**. All provable `Exhausted` / `Rejected` transitions MUST depend solely on deterministic logical registers (`remaining_fuel`, `frame_count` vs `stack_limit`, or +1-per-allocation logical counters `alloc_*`). Exhausting the physical M3 address tree (`seg >= 2^17` at 17 segment bits, [openspec/changes/sherlock-vm-consensus-20261107/design.md:99](file:///home/hoskinson/Projects/Moriarty/openspec/changes/sherlock-vm-consensus-20261107/design.md#L99), [qa/gemini-quint/chipleaf-pairrow-m3/verdict.md:52](file:///home/hoskinson/Projects/Moriarty/qa/gemini-quint/chipleaf-pairrow-m3/verdict.md#L52)) makes the 131,073rd leaf **unsatisfiable** (prover self-DoS, never a forged outcome).

With fixes (2) and (3), two accepted runs of `(prog_d, input_d)` under any leaf partitions are guaranteed to execute the identical rule sequence, identical `n_steps`, and identical logical result, so a prover **cannot** choose the partition to alter acceptance or published outcome.

### 2. Canonical value encoding, in-circuit computation, and cost

#### 2.1 Precise canonical encoding for every Sherlock value type and outcome

Every runtime or constant Sherlock value in C6 is denoted by `RefC::{Const(usize), Data(usize)}` ([crates/mori-core/src/sherlock/helper_machine/shared.rs:701-705](file:///home/hoskinson/Projects/Moriarty/crates/mori-core/src/sherlock/helper_machine/shared.rs#L701-L705)) over the seven value variants in `ConstantSnapshot` / `DataSnapshot` ([crates/mori-core/src/sherlock/helper_machine/complete_observation.rs:299-358](file:///home/hoskinson/Projects/Moriarty/crates/mori-core/src/sherlock/helper_machine/complete_observation.rs#L299-L358), [crates/mori-core/src/sherlock/helper_machine/c6_phys_data.rs:14-18](file:///home/hoskinson/Projects/Moriarty/crates/mori-core/src/sherlock/helper_machine/c6_phys_data.rs#L14-L18)). ### Detailed analysis

1. **On-chain verification path, transcript, and `k = 20` SRS soundness.**
   In `SherlockRun`, Compact is used only to define on-chain state transitions and generate the `Transcript` public-input template for `acceptRun`; the deployed `ContractOperation` carries the serialized `VerifierKey` of `RunDeciderRelation` (`tools/sherlock-sdk/sherlock-run.compact:3-6`; `crates/mori-recursion/tests/sherlock_keygen_regression.rs:116-120`). At call validation, Ledger 9 runs the `Transcript` VM program to materialize public inputs (`binding_input`, `communication_commitment`, and the `Op` field atoms) and calls `VerifierKey::batch_verify` (`ledger-9.1.0.1:transient-crypto/src/proofs.rs:589-613`) with `TranscriptHash = blake2b_simd::State` (`proofs.rs:65`). Inside the recursion, the node verifies the chip leaf and `RunDeciderRelation` verifies the node using Poseidon transcripts (`CircuitTranscript<PoseidonState<F>>`; `crates/mori-recursion/src/inner.rs:95-103`, `crates/mori-recursion/src/run_decider.rs:222-228`), folding their BLS12-381 KZG commitments and checking the final pairing in circuit against `s_g2` (`run_decider.rs:268-272`). Although `ledger-9.1.0.1` embeds `bls_midnight_2p14` and comments that verifiable circuits do not exceed `2^14` rows (`transient-crypto/src/proofs.rs:105-108,121-128`; `onchain-runtime/src/transcript.rs:80-83`), `ParamsKZG::verifier_params()` extracts only `(s_g2, -g2_prepared, s_g2_prepared)` (`repos/midnightntwrk/midnight-zk` `HEAD:proofs/src/poly/kzg/params.rs:436-444`) and no code path bounds `vk.k()`. Because `bls_midnight_2p20` shares the same ceremony `s_g2`, `k = 20` verifies natively on Ledger 9.1.0.1.

2. **Hand-written chip leaf outside ZKIR.**
   Ledger 9 never sees the leaf or node circuits, proofs, or keys; on chain, `ContractOperation` requires only a `VerifierKey` (`MidnightVK`), and `zk_stdlib::batch_verify` is agnostic to whether a `MidnightVK` originated from ZKIR v3 or a custom `Relation` (`repos/midnightntwrk/midnight-zk` `HEAD:zk_stdlib/src/interface.rs:600-612`). The chip leaf's constraints come from the in-circuit `VerifierGadget` of `midnight-circuits` `7.3.0`, not from Ledger 9: specifically, polynomial rotations in `{-1, 0, +1}`, gate degree compatible with the node verifier, and Poseidon constants matching `midnight-zk-stdlib` `2.4.0`. Layout B pair rows and the M3/Poseidon spike satisfy all three (`openspec/changes/sherlock-vm-consensus-20261107/design.md:109-125`; `research/sherlock-processor-analogy-20261110/experiments-4.md:88`).

3. **Fitting Q1 outcome-only publication into the contract and `k <= 20` decider budget.**
   In Compact `0.28.0` / Ledger 9.1.0.1, `Field` (canonical BLS12-381 scalar), `Uint<8>`, `Uint<64>`, and `Set<Field>` / `Map<Field, ...>` are native state and argument types (`tools/sherlock-sdk/sherlock-run.compact:24-27,40`; `openspec/changes/sherlock-vm-consensus-20261107/design.md:303`). Publishing `outcome_d: Field` (covering `Halted(v_d)`, `Rejected(code)`, `Exhausted(kind)`) removes both the raw carrier digest `fin: Field` and the `Bytes<16>` endianness workaround (`sherlock-run.compact:20-23`; `run_decider.rs:280-282`). However, because `RunDeciderRelation` is already at `929,166` rows (`design.md:122`) against the hard `2^20 = 1,048,576` ceremony SRS ceiling (`bls_midnight_2p20`; `qa/sherlock/manifests/sherlock-run-contract.json:33-38`), **canonical value traversal/hashing must occur inside the leaf/VM before or at halt**, leaving the decider with only a fixed-size Poseidon opening of the terminal state (~0 net row growth).

### Blockers and fixes

No blocker exists in Midnight Ledger 9.1.0.1 itself. The following blockers in Moriarty's current artifacts and client workflow must be resolved:

1. **Contract and decider hard-code `Halted(u128)` and raw `fin_d` (`tools/sherlock-sdk/sherlock-run.compact:23-47`; `crates/mori-recursion/src/run_decider.rs:48-58,279-307`).**
   - *Blocker:* `acceptRun` currently requires `r: Bytes<16>` and `fin: Field`, seals one `(program_d, init_d)` per contract deploy, and `RunDeciderRelation` constrains `fin = Poseidon(SHK_SD, HALTED, result, lanes_d)` with `result < 2^128`. Neither non-`u128` halted values, `Rejected`/`Exhausted` outcomes, nor outcome-only hiding of `lanes_d`/`mem_root` can pass.
   - *Fix:* Update `sherlock-run.compact` to accept and store `outcome_d: Field` (and `outcome_tag: Uint<8>` if exposed separately, plus per-call `prog_d: Field, input_d: Field` for GP-1 universality instead of sealed constructor fields), remove `fin: Field` and `Bytes<16>`, and update `RunDeciderRelation` step 4–5 to open the terminal state's canonical outcome digest without exposing `lanes_d` or `mem_root`.
