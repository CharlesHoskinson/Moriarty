### Surface 1: Counter & Field Arithmetic Overflow / Wraparound

Sherlock circuits operate over the BLS12-381 scalar field $\mathbb{F}_q$ (`midnight_curves::Fq`, aliased as `F` in `crates/mori-chip/src/lib.rs:38-39`), a 255-bit prime field with modulus
$$r = \text{0x73eda753299d7d483339d80809a1d80553bda402fffe5bfeffffffff00000001} \approx 2^{254.857}$$
(`crates/mori-core/src/sherlock/helper_machine/shared/c6_data_canonical.rs:22`).

1. **Intra-run height arithmetic (`ivc.rs`):** In `crates/mori-recursion/src/ivc.rs:78,316,361,363-376`, `constrain_heights` enforces `prev_h < 2^64` (`H_BITS = 64`), `steps - 1 < S_MAX` (`S_MAX = 16`, forcing $1 \le \text{steps} \le 16$ because `0 - 1 = r - 1 >= 16`), and `h = prev_h + steps < 2^64`. Because $(2^{64} - 1) + 16 < 2^{65} \ll r$, field addition in $\mathbb{F}_q$ cannot wrap modulo $r$ before the `< 2^64` range check catches `h >= 2^64`. If the range check on `h` were ever omitted, setting `prev_h = r - 2` and `steps = 2` would yield `h = 0 (mod r)`, re-triggering `is_genesis = is_zero(prev_h)` (`ivc.rs:316,361`) at the *next* fold—which scales `prev_proof` verification constraints by `not_genesis = 0` and erases all prior execution history. Similarly, `steps >= 1` (`SRC-004`, `requirements.md:29`) prevents zero-step stuttering loops.
2. **Exploit E-1 — `GP-4` Diamond DAG Exponential Counter Wraparound (`n_claims` & Cross-Run `total_steps`):**
   `research/sherlock-gp-architecture-20261110/architecture.md:100` specifies `SET = (set_root, n_claims)` where *"n_claims counts occurrences, not distinct claims"* (`n_claims = n_L + n_R` in $\mathbb{F}_q$). `GP-4` (`general-purpose.md:44-50`, `requirements.md:59`) requires DAG aggregation where one proof feeds two consumers. Construct a diamond DAG: let $D_0$ be a 1-claim proof ($n_0 = 1$), and for $i = 0 \dots d-1$ prove $D_{i+1} = \text{JOIN}(D_i, D_i)$ feeding the *same* proof into both child slots:
   - At depth $d = 64$ (**only 64 node proofs**, $\approx 65\text{ min}$ CPU wall time at `61 s`/node), $n_{64} = 2^{64}$, overflowing any 64-bit counter.
   - At depth $d = 255$ (**255 node proofs**, $\approx 4.3\text{ h}$ CPU wall time), $n_{255} = 2^{255} > r$ wraps modulo $r$. By standard double-and-add over $\{D_0, \dots, D_{254}\}$ ($\le 510$ node proofs), a malicious prover can hit $n \equiv 0 \pmod r$ or **any arbitrary residue modulo $r$** from a single valid claim. The exact same attack hits any continuation or batch aggregator that sums `n_steps` across a DAG without per-join `< 2^64` range checks and disjoint-interval enforcement.
   - **Mandatory Defense:** Every integer counter summed in recursion (`h`, `h_hi - h_lo`, `n_claims`, `total_steps`) MUST be range-checked `< 2^64` at every node (`assert_lower_than_fixed(..., 2^64)`), turning depth-64 self-joins into unsatisfiable constraints before field wrap is reachable; and run-segment joins `SEG + SEG -> SEG` MUST enforce contiguous disjoint intervals `[h_lo, h_mid)` and `[h_mid, h_hi)` with strict `0 <= h_lo < h_mid < h_hi < 2^64`, making `JOIN(S_i, S_i)` algebraically unsatisfiable (`h_hi != h_lo`).
3. **Exploit E-2 — Continuation Fuel Refresh Attack:**
   In Sherlock (`design.md:229-231`, `crates/mori-chip/src/rf.rs:238-239`), `input_d = Poseidon(SHK_IN, val_d, fuel_lo, fuel_hi, stack_limit)` initializes `initial_fuel = remaining_fuel = fuel` ($< 2^{128}$) and `consumed_work = 0`; each enabled step decrements `remaining_fuel` by 1 and increments `consumed_work` by 1. If a continuation protocol (`Q2a`/`Q3`) starts run $k+1$ with a fresh `Init` or re-applies `input_d`'s `fuel` instead of carrying `remaining_fuel` and `consumed_work` inside the proved continuation state, a program that must terminate with `Exhausted(Fuel)` at step $500$ under `fuel = 500` can be split into two 300-step runs that halt with `Halted(v)` at step $600$—forging a false outcome for `(prog_d, input_d)`.
4. **Exploit E-3 — Segment Scaling & `ALU` `u128` Address Width Traps:**
   In `crates/mori-chip/src/m3.rs:131`, segment alignment is checked by `8 * acc_in = base` in $\mathbb{F}_q$ where `acc_in` is reconstructed from `TOP` boolean path bits. This prevents modular wraparound **only while $8 \cdot 2^{\text{TOP}} < r$** (`TOP <= 251`). Far stricter is `crates/mori-chip/src/alu.rs:8,111-125`: `ALU` range-checks values and `OP_LT` witnesses to **128 bits** (`11` limbs $\times 12$ bits + `1` limb $\times 8$ bits in `crates/mori-chip/src/range.rs:153-162`, or 11 $\times$ 12-bit limbs = 132 bits with top limb masked). Any memory address or `len` $\ge 2^{128}$ breaks `OP_LT(addr, len)`. Bounding all addresses and lengths strictly below $2^{64}$ (`TOP = 61`, $8 \times 2^{61} = 2^{64} \ll 2^{128} \ll r$) keeps both `8 * acc_in` and `ALU` comparisons strictly integer-exact.

### Surface 2: Malicious Prover Partition Choice (`SRC-023`, `SVM-010`, and Formal Premises)

1. **Exploit E-4 — Prover-Forced $16\times$ Address Starvation under `D3`:**
   Under `D3` (`design.md:96`, `crates/mori-chip/src/m3.rs:23,132`, `crates/mori-chip/src/rfcore.rs:1203`), `post_d.len` is unconditionally set to `base + 8` on leaf close, even if the leaf executed zero appends (`all 8 segment slots = padding`). Meanwhile `SRC-004` / `SRC-014` (`requirements.md:29,39`, `ivc.rs:372`) allow the prover to choose any `steps` $\in [1, 16]$ per leaf. With `TOP = 17` (`m3.rs:38`) and segment `0` reserved (`base = 8` at genesis, `design.md:96`), only $2^{17} - 1 = 131,071$ leaves exist per run (`research/sherlock-c6-outcome-ledger9-review-20261110/review.md:40`).
   - An honest prover packing $S = 16$ steps/leaf proves up to $16 \times 131,071 = 2,097,136$ steps.
   - A malicious prover packing `steps = 1` per leaf exhausts all $131,071$ segments in **$131,071$ pure-ALU steps with zero memory allocations** ($16\times$ earlier), forcing proving refusal on short runs. Worse, if any circuit or host bridge ever encoded physical segment exhaustion as `Exhausted(DataNodes)` or `Exhausted(LogicalCap)`, the malicious prover could choose leaf splits `[1, 1, ...]` vs `[16, 16, ...]` on the **exact same `(prog_d, input_d)`** to flip the on-chain outcome from `Halted(v)` to `Exhausted(...)`, violating both `SVM-010` (`requirements.md:18`) and `SRC-023` (`requirements.md:48`).
2. **Exploit E-5 — Direct Falsification of Lean (`F21`) and Quint (`F20`) Premises by `D3`:**
   `SRC-017` (`requirements.md:42`) rests on two formal artifacts:
   - `clean/fork/Clean/Sherlock/Aggregation.lean:176-214` assumes `Premises.leaf_sound` and `Premises.det`: for every program $p$ and step index $n$, any two valid step chains of length $n$ starting from `init_of p` satisfy $s_1 = s_2$ (lines 199–204), from which `result_unique` (`Aggregation.lean:1136-1150`) proves `fin_1 = fin_2`.
   - `models/sherlock/quint/aggregation.qnt:12-15,89-104` models state digests as `pure def d(p: int, i: int): int = p * 1000 + i`, a deterministic function of `(program, step_index)` alone.
   - **Break:** Under `D3`, run a 16-step zero-allocation program from `base = 8`. Partition $P_1 = [16]$ yields `post_d.len = 16` (`seg 1` filled with 8 zero-padding records); partition $P_2 = [7, 9]$ yields `post_d.len = 24` (`seg 1` and `seg 2` filled with zero-padding records) and a different `mem_root`. Thus $s_1 \ne s_2$ and `post_d(P_1) != post_d(P_2)` at step $h = 16$. The physical `post_d` of `D3` **falsifies `Premises.det` in `Aggregation.lean` and `d(p, i)` in `aggregation.qnt`**! As independently flagged in `qa/gemini-quint/chipleaf-pairrow-m3/verdict.md:41` (`tasks.md:85`), the earlier chip Quint model missed this only because its reference machine was artificially altered to allocate per leaf.
3. **Exploit E-6 — Continuation Split-Point Manipulation under `Q2(a)`:**
   Suppose `Q2(a)` keeps `D3` and tries to chain runs via `GP-2`.
   - If the prover triggers a split by setting a smaller `fuel_1 < fuel` in run 1's `input_d`, then run 1's `input_d^{(1)} = Poseidon(SHK_IN, val_d, fuel_1, ...)` differs from the user's `input_d`, and run 1 legitimately proves `SHK_RUN(prog_d, input_d^{(1)}, Exhausted(Fuel))`—which is a valid terminal claim for a *different* input, not a continuation of `(prog_d, input_d)`.
   - If instead run 1 exports its `D3` physical state at prover-chosen step $h_1$, `mem_root` and `len` at $h_1$ depend on how run 1 partitioned its leaves (`E-5`). Two provers splitting at different heights (or using different intra-run leaf sizes) produce incompatible intermediate commitments and different remaining segment budgets in run 2.
4. **Exploit E-7 — Growing-Depth Merkle Tree Extension & Height-Keyed Address Leaks (`Q2c`):**
   - *Growing-depth Merkle tree:* Suppose memory depth $D$ starts at $4$ and increments to $D+1$ by setting `new_root = H(old_root, EMPTY_SUBTREE_D)` when `len` reaches $2^D$. If internal nodes and leaf/segment roots lack distinct domain tags (`DOM_MEM_NODE` vs `DOM_MEM_SEG`) or if `(D, len)` is omitted from the outer commitment, a dishonest prover can claim depth $D+1$ over a depth-$D$ witness (interpreting two sibling subtrees as double-depth leaves, or attaching fabricated subtrees below depth 0—the exact failure class of OpenVM `CVE-2026-62333` / `GHSA-396x-v8w4-9x82`). Furthermore, variable-depth walks inside a fixed PLONK leaf still require circuit rows sized to `D_MAX` (61 levels for $2^{64}$) plus per-level multiplexer gates to conditionally freeze the root above $D$, costing *more* constraints than a fixed depth-61 tree whose empty right subtrees are precomputed constants `ZERO_HASH[lvl]`.
   - *Height-keyed memory (`addr = (h, subop)`):* Keying memory by step height $h$ embeds execution timing into every pointer: (a) multi-step constructor slices (`XAdtHelperBuildCell` writing 1 field per step across $m$ steps, possibly interleaved with helper evaluation steps) no longer occupy contiguous keys `start + k`, breaking `SI-12`; (b) reading a variable-gap key `(h_i, subop)` requires binary search or non-deterministic index hints; and (c) if continuations ever reset local `h` to `0`, addresses collide across runs, whereas keeping global `h` embeds split/step history into every reference.

### Surface 3: Chaining Replay, Splicing, Cycles & Type Confusion under C6

Under the C6 outcome-only decision (`requirements.md:31-32,47-48`, `design.md:140`), the external run statement is `[prog_d, input_d, outcome_d, n_steps]` and the replay/consumption key is
$$\text{claim\_d} = \text{Poseidon}(\text{SHK\_RUN}, 1, \text{prog\_d}, \text{input\_d}, \text{outcome\_d}),$$
which intentionally omits state digests (`init_d`, `fin_d`, `mem_root`, `len`) and omits `n_steps` (`dissent.md:209-212`).

1. **Exploit E-8 — Value/State Type Confusion at `acceptRun` and `Init`:**
   Suppose `Q3` attempts to pass run $k$'s full VM state to run $k+1$ *through existing `GP-2` `SHK_RUN` claims* (`requirements.md:57`) by encoding the suspended VM state `(regs, mem_root, ...)` as a `sherlock-value/1` ADT/record `v_state`, so run $k$ emits `outcome_d = H(O, 1, 0, vd(v_state))` (`Halted(v_state)`) and run $k+1$ takes `val_d = vd(v_state)` inside `input_d`:
   - **Finality Forgery (Early Halt Spoofing):** Because run $k$'s proof is a valid `SHK_RUN(1, prog_d, orig_input_d, Halted(v_state))` proof, an attacker can submit run $k$ **directly to `SherlockRun.acceptRun` on-chain**, permanently recording `Halted(v_state)` as the final output of `prog_d(orig_input_d)` (and blocking the true final output via `claim_d` or front-running application logic) even though `prog_d` was only halfway through execution!
   - **Genesis Bypass (`Init` Injection):** On the receiving side, if `prog_d` (or the leaf circuit) accepts an `input_d` carrying `v_state` to initialize arbitrary mid-run registers, `fp`, `tp`, and `mem_root`, then **any external caller—without any prior run proof!**—can craft a malicious `v_state*` with `ctl = Publish(forged_val)` and submit a 1-step run starting from `input_d(v_state*)`, bypassing `Init` (`SRC-021`) completely!
   - **Conclusion:** A continuation boundary MUST NEVER emit a `SHK_RUN` claim or encode VM state as a `Halted(v)` `sherlock-value/1` outcome. Continuation checkpoints require a **disjoint domain tag** (`SHK_CONT_V1 != SHK_RUN`) that `acceptRun` and `GP-002` value consumers unconditionally reject.
2. **Exploit E-9 — Segment Dropping, Reordering, Cross-Input Splicing, and `S_A -> S_B -> S_A` State Cycles:**
   Attacking multi-segment chains `(C_0, C_1, ..., C_{m-1})`:
   - **Dropping / Reordering:** If `C_k` omits exact boundary commitments `(pre_canon_d, post_canon_d)` or adjacent height bounds `C_k.h_hi == C_{k+1}.h_lo`, an attacker drops middle segments or permutes segments.
   - **Cross-Input Splicing:** Suppose input $x_1$ and input $x_2$ both reach an identical intermediate VM state $S_{\text{mid}}$ (for example, after canonicalizing an argument) or an attacker splices prefix `[Init(x_1) -> S_mid]` with suffix `[S_mid' -> Halted(y_2)]`. Binding `orig_input_d` immutably across every continuation claim (`C_k.orig_input_d == C_{k+1}.orig_input_d`) AND checking `C_k.post_canon_d == C_{k+1}.pre_canon_d` prevents cross-input splicing unless $S_{\text{mid}}$ is genuinely bit-identical (in which case deterministic continuation from $S_{\text{mid}}$ yields the exact same mathematical outcome $y_1 = y_2$).
   - **State Cycle Pumping (`S_A -> S_B -> S_A`):** If `state_d` omitted monotonic counters and `claim_d` omitted height intervals, a program loop `S_A -> S_B -> S_A` could be replayed $N$ times to pump `n_steps` to any value below $2^{64}$ using only 2 segment proofs! In Sherlock, **three independent strict invariants** prevent cycles when preserved in `canon_state_d`: (i) `consumed_work` increments by $+1$ per enabled step (`rf.rs:239`, `design.md:231`); (ii) `remaining_fuel` decrements by $-1$ per enabled step (`rf.rs:238`, `design.md:230`); and (iii) segment claims bind `[h_lo, h_hi)` with `0 <= h_lo < h_hi < 2^64` and `C_k.h_hi == C_{k+1}.h_lo`. Thus $S_A$ can **never** equal a later reachable state $S_A'$ (`consumed_work(S_A') > consumed_work(S_A)`).

### Surface 4: State Forgery & Non-Canonical Witness Smuggling Between Runs

1. **Exploit E-10 — Total `ALU` Soundness Collapse via Unproved Checkpoint Resume (`StepInv` Bypass):**
   Look at `crates/mori-chip/src/alu.rs:6-9,111-125` and `qa/gemini-quint/chipleaf-final/verdict.md:48,89`:
   > *"Inputs `x` and `y` are NOT range-checked here: the leaf checks values when written and at Init, not when read (`design.md` §2.7.5)."*
   Specifically, for `OP_LT(x, y) -> z` (`alu.rs:116-123`):
   - When `z = 1` (`x < y`), the gate constrains only `x + w + 1 = y (mod r)` and range-checks `w < 2^{128}` (`1` range-checked `w`, `0` range checks on `x` or `y`!).
   - **Concrete Forgery Witness:** Suppose a continuation design allows run $k+1$ to resume from a host-supplied or partially-checked state digest where register `x` was not proved via a valid step chain from `Init`. The attacker sets register `x = r - 1` ($\approx 2^{254.86}$, outside `u128`), `y = 5`, `z = 1`, and `w = 5`:
     $$(r - 1) + 5 + 1 \equiv r + 5 \equiv 5 = y \pmod r, \qquad w = 5 \in [0, 2^{128}).$$
     Every `ALU` and `RANGE` constraint passes! The circuit proves **`r - 1 < 5 == true`** (and similarly wraps `OP_ADD` without triggering overflow traps).
   - **Mandatory Invariant:** `StepInv` (`SVM-002`, `design.md:86`) is **strictly inductive from `Init` (`h_lo == 0`)**. No continuation segment may ever be sealed into `SHK_RUN` unless its `pre_canon_d` is linked by an unbroken chain of verified proofs all the way back to `h_lo == 0` where `Init(prog_d, orig_input_d)` checked all 39 fields and `u128`/`u64` bounds (`SRC-021`).

## Q1: What Should GP-1 Say About Run Length, and What Does "Unbounded" Honestly Mean?

### 1.1 Technical Clarification of $2^{64}$ vs "Unbounded"

1. **What $2^{64}$ actually is:** In `crates/mori-recursion/src/ivc.rs:78,363-376` (`SRC-004`, `requirements.md:29`), $2^{64}$ (`H_BITS = 64`) is the **integer range-check bound on the 64-bit step counter `h`** carried as a single field element in $\mathbb{F}_q$. It exists solely so `h = prev_h + steps` can never wrap modulo the 255-bit prime $r$ (`Surface 1`) and so `n_steps` fits a canonical `u64` on-chain (`SRC-006`, `SRC-007`). **No circuit ever has $2^{64}$ rows.** Every circuit in the key set has fixed size: leaf $k \le 16$ ($\le 65,536$ rows), node $k = 20$ ($\le 1,048,576$ rows), and decider $k = 20$ (`929,166` circuit rows, `design.md:129-131`).
2. **What "unbounded" honestly means in a zkVM:** Physically, no machine can execute $2^{64}$ steps (at 1 ns/step, $2^{64}$ steps is $584.9$ years; at the measured `61 s` CPU fold per 16 steps, $2^{60}$ folds is $2.23 \times 10^9$ years). Honestly stated, **"unbounded capacity under one fixed key set"** means **key-independent scaling**:
   - **Zero key-baked capacity constants:** Neither the proving/verifying keys nor the deployed verifier contract encode a maximum step count, leaf count, program size, input size, call-stack depth, or heap size.
   - **Linear / parallelizable work:** Proving work grows $O(N)$ in the actual step count $N$ by folding fixed-size leaf proofs (sequentially in an IVC chain or in parallel in a `GP-4` binary segment tree), while final proof size and on-chain verification cost remain $O(1)$.
   - **No hidden sub-architectural cliff:** The circuit architecture imposes no tighter ceiling than the 64-bit architectural step and address counters ($< 2^{64}$)—which exceed physical realizability by $>7$ orders of magnitude—so real-world run length is limited **only** by caller-supplied resource policy (`fuel`, `stack_limit` in `input_d`) and external prover time/hardware budgets, never by the key set.

## Q3: Hardened Continuation & Aggregation Protocol under C6

Even with `Q2(d)` removing the $2^{17}$-leaf single-run ceiling up to $2^{64}$ steps, long runs need **both** (1) parallel multi-worker proving of segments within one run (`GP-4`) and (2) cross-session / pause-and-resume continuations when a run is proved across separate host sessions or epochs without ever exposing state digests on-chain (`C6`).

### 3.1 Two-Tier Architecture: Intra-Run `SHK_SEG` PCD vs Cross-Session `SHK_CONT_V1` Checkpoints

1. **Tier 1 (Intra-Run Parallel Segment Folding — `GP-4` `SHK_SEG`):**
   Under `Q2(d)`, the canonical machine state digest `canon_state_d(h)` at step $h$ is **unique and partition-independent**. Any long run $[0, N)$ splits into parallel leaf ranges $[h_0, h_1), [h_1, h_2), \dots, [h_{m-1}, h_m)$ proved concurrently by independent workers, folded in a binary tree (`SEG + SEG -> SEG` checking `L.post_canon_d == R.pre_canon_d`, `L.h_hi == R.h_lo`, `0 <= L.h_lo < L.h_hi < R.h_hi < 2^64`, `L.prog_d == R.prog_d`, `L.orig_input_d == R.orig_input_d`), and sealed once at the root (`SEG -> SHK_RUN`) when `h_lo == 0` and `post.outcome in {Halted, Rejected, Exhausted}` (`architecture.md:97-115`).
2. **Tier 2 (Chain-of-Runs Checkpointed Continuations — Domain-Separated `SHK_CONT_V1`):**
   If a computation is proved as a sequence of separately sealed checkpoint runs $k = 0, 1, \dots, m-1$ (as posed in `Q3`):
   - **Strict Domain Separation (`Exploit E-8` Defense):** A non-terminal run $k < m-1$ (`post.outcome == Running`) MUST NEVER emit a `SHK_RUN` claim and MUST NEVER encode VM state as a `sherlock-value/1` value `vd(v)`. Instead, a checkpoint decider (or internal node accumulator) emits a **continuation claim** under a dedicated tag `DOM_CONT = "SHK_CONT_V1"` ($\ne \text{"SHK\_RUN"}$):
     $$\text{cont\_claim\_d}_k = \text{Poseidon}\bigl(\text{DOM\_CONT}, 1, \text{vk\_id}, \text{prog\_d}, \text{orig\_input\_d}, h_{\text{lo},k}, h_{\text{hi},k}, \text{pre\_canon\_d}_k, \text{post\_canon\_d}_k, \text{deps\_pre\_d}_k, \text{deps\_post\_d}_k\bigr).$$
   - **What `canon_state_d` Commits (Partition-Independent Full Machine State):**
     $$\text{canon\_state\_d} = \text{Poseidon}\bigl(\text{DOM\_STATE\_V1}, \text{regs}_{0..28}, \text{fp\_hash}, \text{tp\_hash}, \bigl\{(\text{root}_a, \text{len}_a, \text{tail\_d}_a)\bigr\}_{a \in \{\text{DATA},\text{FIELDS},\text{ENV},\text{SLOTS}\}}\bigr).$$
     Because `Q2(d)` updates `len_a`, `tail_d_a`, and `root_a` solely on logical appends and hashes `FRAMES`/`TASKS` as canonical chains, `canon_state_d` is **100% independent of internal leaf partitions** (`SRC-023`) and commits `remaining_fuel`, `initial_fuel`, `consumed_work`, `stack_limit`, `frame_count`, `task_count`, `ctl`, `env`, `top`, `task`, `helper`, and `result`. Scratch registers `v0..v2` are constrained to `0` at every leaf/run boundary (`Exploit E-11` closed).
   - **What `input_d` Is Across the Chain (`Exploit E-2`, `E-6`, `E-9` Defense):**
     Every run $k \in \{0, \dots, m-1\}$ carries the **exact, unmodified user `orig_input_d = Poseidon(SHK_IN, vd(x), fuel_lo, fuel_hi, stack_limit)`** (`SRC-021`). Run $k+1$ does **not** fabricate a synthetic `sherlock-value/1` `input_d` for the machine state! Instead:
     - **Epoch $k = 0$ (`h_lo == 0`):** First leaf proves `pre_canon_d_0 == Init(prog_d, orig_input_d)` field-by-field (`SRC-021`), `deps_pre_d_0 == EMPTY_DEPS`, and executes steps $[0, h_1)$, yielding `cont_claim_d_0` with `h_lo = 0, h_hi = h_1 < 2^64`.
     - **Epoch $k + 1$ (`h_lo = h_{k+1} > 0`):** First leaf/node **verifies Epoch $k$'s `SHK_CONT_V1` proof in-circuit** (never trusting host state—closing `Exploit E-10` `ALU` `StepInv` collapse!), enforces:
       1. `prev.vk_id == self.vk_id`, `prev.prog_d == prog_d`, `prev.orig_input_d == orig_input_d`;
       2. `prev.h_lo == 0` (inductive prefix anchor! Epoch $k$ already collapsed $[0, h_{k+1})$ into `[0, h_{k+1})`, so chaining collapses `[0, h_{k+1}) + [h_{k+1}, h_{k+2}) -> [0, h_{k+2})`!), `prev.h_hi == cur.h_lo`, and `0 < cur.h_lo < cur.h_hi < 2^64` (`Exploit E-1`, `E-9` closed);
       3. `prev.post_canon_d == cur.pre_canon_d` (preserving exact `remaining_fuel`, `consumed_work`, stacks, and 4-arena roots—closing `Exploit E-2` fuel refresh and `E-9` state cycles!).
   - **Single On-Chain Proof & Interaction with C6 Outcome-Only Publication (`SRC-006`, `SRC-007`):**
     Only when Epoch $m-1$ reaches a terminal state (`post.outcome in {Halted(v), Rejected(code), Exhausted(kind)}`) over the complete collapsed prefix `[0, N)` (`h_lo == 0`, `h_hi = N < 2^64`) does the **Run Decider** accept (`SRC-006`: `Running` is refused!). The Run Decider opens `post_canon_d` to extract `outcome_d` (`sherlock-value/1`), drops `pre_canon_d`, `post_canon_d`, and all `SHK_CONT_V1` digests inside the witness, and exposes **only the exact four C6 public inputs**:
     $$[\text{prog\_d}, \text{orig\_input\_d}, \text{outcome\_d}, N].$$
     On-chain `SherlockRun.acceptRun` verifies **one** decider proof, computes `claim_d = Poseidon(SHK_RUN, 1, prog_d, orig_input_d, outcome_d)`, checks replay, and stores `(outcome_d, N)`. **Zero state digests, zero `SHK_CONT_V1` claims, and zero continuation split points ever touch the chain or `GP-2` consumer claims**—matching RISC Zero's `ExitCode::SystemSplit` + `SYSTEM_STATE_ZERO_DIGEST` on `Halted(0)` and SP1's `is_complete == 1` gate.
