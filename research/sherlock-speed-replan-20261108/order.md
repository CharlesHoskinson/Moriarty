**Fixed keys.** One key set (leaf over the frozen inventory `R` at the chosen S, node, decider, acceptRun template) serves every committed program and every step count. The linear self-recursive node already has this property: the node key is a constant of itself (`ivc.rs:295-301`), the decider pins `vk_N_repr`, and depth is unbounded. ## 5. Memory safety

Rules, in order of enforcement:

1. **Kernel limit on every heavy process, and on the run.** `run_command` wraps `argv` in `systemd-run --user --scope --collect -q -p MemoryMax=<cap_rss> -p MemorySwapMax=0 -- <argv>` when `cap_rss` is set; `cap_rss` is always set: budget cap, else `DW_DEFAULT_RSS_CAP` (48 GiB), never None and never above 48 GiB. A `--concurrent P` run (E11) first creates a parent scope with `MemoryMax=100G` (owner: "100 GB aggregate") and starts the P children inside it (`systemd-run --user --scope --slice-inherit` or a transient slice), so the aggregate limit is the kernel's, not a poll. Verified on this host: exit 137 at `MemoryMax=64M` for a 300 MB allocation; controllers `cpu memory pids` are delegated to the user slice. The OOM kill is reported as `capExceeded: "rss"` by reading `memory.events` of the scope (`oom_kill` counter) or by exit 137 plus the sampled peak.
2. **Preflight admission.** Add to `preflight.run`: `MemAvailable` from `/proc/meminfo` >= requested cap (per process, or the aggregate cap for a concurrent run) + `DW_MEM_RESERVE_GIB` (20 = 120 - 100); swap used (`SwapTotal - SwapFree`) <= 4 GiB; print both numbers. Without a cap argument (plain `doctorwatson preflight`) use the default cap. Exit 3 on failure, as for disk and load.
3. **Aggregate rule for the concurrent lock class (E11, required).** `queue.acquire_turn` admits a process only while the sum of caps of every admitted heavy and gpu process <= 100 GiB: three 26 GB k20 nodes (78 GB) or four 14 GB k19 nodes (56 GB) fit; a fourth k20 node (104 GB) does not. The lease records the admitted set and the aggregate cap; `runs.jsonl` records `aggregateRssBytes` and `concurrency` beside `maxRssBytes`. The GPU shares the 120 GB, so a `--gpu` process counts its cap in the same sum.
4. **Test commands.** `cargo test` under `heavy` sets `RUST_TEST_THREADS=4` for `mori-backend`, `mori-recursion`, `mori-ledger`; a workspace-wide test run is split per crate, each with its own cap. The 112 GB incident was a 20-thread debug test binary keying C6 consumer circuits.
5. **Unified memory.** The GPU shares the 120 GB; device allocations by a `heavy --gpu` job count against its scope's `MemoryMax` only if they are host-pinned or managed allocations in the process. Open question 4.
6. **Caps for the throughput rows are requirements, not 2x measured** (section 3.2).

## 6. Risks

- The k19 cut may not exist without an arch change; then S carries the target and the node stays 26 GB, which also closes the tree (one prover per host).
- The thread sweep may show the prover saturating 20 cores with a long serial tail; then neither threads nor concurrency help and GPU or S are the only levers.
- Stand-in leaves understate node cost if the universal leaf VK is much wider (more columns -> more in-circuit verifier rows); 5.3 catches this; G-B exists for that reason.
- aarch64 + sm_121 GPU libraries are unproven; the spike is time-boxed.
- A patched midnight-proofs in the production prover is a build-identity change that every manifest (SRC-008) must record; proof bytes must stay identical.
- Seeded caps make the throughput rows fail loudly on the first run; that is intended, but the retry rule then needs `--hypothesis` each time (`heavy.py:253-260`).
- The current A2-A4 rows are retired; the profile harness must not resurrect them as gating rows.
