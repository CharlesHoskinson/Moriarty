An adversary can choose a fabricated carrier state `s_0` (for example, already in a halted configuration with an arbitrary return value and `deps_d = 0`), set `init_d = H(s_0)`, and obtain a valid decider proof (`research/sherlock-recursion-design-review-20261110/review.md:50-65`).     4. *Inline VM processor inside the recursive node `N` (`research/sherlock-gp-architecture-20261110/astra/design-1.md:116-143`):* As measured in `qa/sherlock/decisions/speed-levers.json:28`, two self-verifications plus boundary hashing in `N` already consume `730,243` rows at `k = 20` (`1,048,576` total rows, `64` unusable), leaving only `~318,000` rows before disabled-slot normalization (or `~266,000` rows in `SHKIVC06`). Every node proof pays `61–67 s` for non-native BLS12-381 MSM collapse (`qa/sherlock/decisions/speed-levers.json:66`). Inlining the VM into `N` couples every `S` VM steps to a `65 s` KZG collapse and bloats `N`'s VK with chiplet fixed/lookup commitments (see D4).
    5. *Two-layer design with a different inner proof system (e.g., Goldilocks/BabyBear STARK or Nova/SuperNova folding inside a BLS12-381 halo2 outer verifier):* While RISC Zero and SP1 achieve fast inner proving this way, `midnight-circuits` (`tools/profile/vendor/midnight-circuits-0.8.3/src/lib.rs`) has no FRI/STARK verifier chip and BLS12-381 has no 2-adicity cycle curve in the Midnight stack (`research/sherlock-gp-architecture-20261110/architecture.md:382-385`). Writing and auditing an in-circuit FRI verifier in `midnight-circuits` would take `4–8 weeks` (`ESTIMATE`) and is unnecessary once chiplet-based committed memory brings native BLS12-381 KZG leaves down to `k_U = 17` (`5–9 s` per `16` steps `ESTIMATE`).
  - **Relationship to D4:** Using chiplets and processor registers inside a **separate leaf circuit `U`** (rather than inline inside `N`) is what makes both `U` and `N` fast. Chiplet tables require custom fixed columns, lookup selectors, and permutation columns. In `midnight-circuits` (`tools/profile/vendor/midnight-circuits-0.8.3/src/verifier/msm.rs:491`), every additional fixed or permutation commitment in a verified circuit's VK adds non-native scalar multiplications (~`3,000–4,000` rows each, `research/sherlock-gp-architecture-20261110/architecture.md:117-120`) to its verifier. By isolating the processor registers and chiplets inside `U`, `U` is verified **only once** inside the run-lift `R` (`k = 19` or `k = 20`), whereas the recursive node `N` verifies only `{N, R, F}`—all of which share a minimal `ZkStdLibArch` (`bls12_381 + poseidon` only, `nr_pow2range_cols = 4`, no chiplet tables).

- **risks:**
  - **Custom `Relation` implementation effort:** Writing `U` directly against `midnight-circuits` / `midnight-zk-stdlib` (instead of auto-lowering from ZKIR v3) requires translating the 108 rule transition semantics (currently spread across 63 C6 fragments and 45 unimplemented rules in `crates/mori-backend/src/sherlock_machine/mod.rs:146-326`) into a compact register-microcode table plus 4 chiplets. Mitigation: generate the per-rule register microcode table automatically from the declarative rule spec in `mori-core` (`crates/mori-core/src/sherlock/reference.rs`) so the 108 rules share a single table-driven transition relation rather than 108 bespoke sub-circuits.
  - **Worst-case unique memory/AST openings in one `S = 16` window:** A pathological 16-step slice that touches 16 distinct deep AST nodes and 32 distinct uncached arena cells could exceed the per-leaf Poseidon chiplet budget for `k_U = 17`. Mitigation: include a `noop / flush` continuation tick in `U` so that if a leaf's Poseidon/memory chiplet bus reaches its fixed capacity `B_hash` before 16 owner steps complete, the remaining slots in the leaf pad with `noop` (`state_{i+1} = state_i`) while advancing `h` by the actual number of executed steps `1 <= ds <= 16`.

- **kill_criterion:** Reverse this decision (and fall back to `S = 8` at `k_U = 17` or a two-layer folding/STARK inner proof) if the prototype `U` relation with the 4 chiplets (PROG ROM, Memory/Stack, 128-bit ALU, Poseidon) at `S = 16` exceeds `k_U = 18` (`262,144` rows) in `midnight_zk_stdlib::cost_model` or exceeds `18 s` per leaf proof on a single worker.

- **experiment:** Build a vertical-slice `midnight_zk_stdlib::Relation` prototype of `U` for `S = 16` steps containing the 32-field-element processor register trace, the Memory/Stack permutation chiplet, the PROG ROM lookup chiplet, the 128-bit ALU chiplet, and `PoseidonChip` (supporting the 8 rules exercised by `fact(3)`), and run `midnight_zk_stdlib::cost_model` to measure exact `(k, rows, advice_columns, lookups, permutations)` (`ESTIMATE` 1 day of engineering, < 30 s runtime).

## D3 GP-3/GP-4 wording points

### (i) Node taking at least two prior proofs plus new work (`k=20` vs `k=21`)

- **decision:** Meet the requirement at **`k = 20`** without an owner amendment as the primary path by giving the binary polymorphic node `N` two prior-proof verification slots (`slot_L`, `slot_R`, each accepting a proof from `{N, R, F}` via key-switches over a shared `ZkStdLibArch`) **plus an inline composition and claim-step unit** (run-segment seal `SEG -> SET`, cross-run dependency binding `deps_d`, and 1-step inline claim/continuation dispatch), while lifting raw `S`-step VM leaves `U` into `N`-compatible proofs through the run-lift circuit `R` (`k = 19..20`). In case the owner interprets *"at least two prior proofs plus new work in one node"* (`openspec/changes/sherlock-vm-consensus-20261107/general-purpose.md:54`) as requiring raw VM leaf steps `U` (rather than lift proofs `R`/`F` or inline claim-seal work) to be proved alongside two prior `N` proofs inside a single `k = 20` circuit, provide the explicit **OWNER AMENDMENT** in `requirement_text` below.

- **rationale:**
  - **Why 3 full KZG verifications in one node force `k = 21`:** In `qa/sherlock/decisions/speed-levers.json:28,113` (lever `F22`), a node that verifies two prior `N` proofs plus a third KZG proof (`U`) in the same circuit requires `1,078,147` rows (`k = 21`), exceeding `2^20 = 1,048,576` by `29,571` rows and exceeding the bundled `bls_midnight_2p20` SRS (`crates/mori-recursion/src/ivc.rs:365`).
  - **Why two polymorphic KZG slots `{N, R, F}` + inline claim-composition work fits in `k = 20`:** Two KZG verifications over a shared `ZkStdLibArch` (`bls12_381 + poseidon` only) plus accumulator collapse take `730,243` rows (`qa/sherlock/decisions/speed-levers.json:28`), or `~652,437` rows when disabled-slot normalization is omitted (`research/sherlock-gp-architecture-20261110/architecture.md:107`). Adding key-selection (`vk_sel` over `{vk_N, vk_R, vk_F}`, where each candidate adds only ~`200` conditional-select rows and ~`3,500` rows per fixed/perm commitment in the shared MSM if not pre-selected, `tools/profile/vendor/midnight-circuits-0.8.3/src/verifier/msm.rs:491`) plus the inline PCD join/seal/dependency algebra (`SEG+SEG`, `SEG+SET`, `SET+SET`, `h_lo == 0` seal check, and `deps_d` verification, `~15,000` rows `ESTIMATE`) keeps `N` at **`~760,000–810,000` rows (`k = 20`) `ESTIMATE`**. Because `R` (the run-segment lift that verifies one `U` leaf and checks `deps_d` against an incoming `ClaimSet` proof) and `F` (the foreign proof lift) are themselves valid node-level proofs with the exact same architecture as `N`, a single `N` step can combine a prior `N` proof with a new `R` or `F` proof (chain topology) or two prior `N`/`R`/`F` proofs plus inline seal/dependency work (DAG/tree topology), satisfying every topology in GP-4 (`openspec/changes/sherlock-vm-consensus-20261107/general-purpose.md:45-55`).

- **risks:**
  - **Semantic ambiguity in "new work":** A reviewer could read "two prior proofs plus new work" (`openspec/changes/sherlock-vm-consensus-20261107/general-purpose.md:54`) as requiring raw VM instruction execution inside `N` at the same time `N` folds two prior `N` proofs. Mitigation: surface the exact **OWNER AMENDMENT** below so the owner can confirm that new work enters a binary node either as a lifted leaf/foreign proof (`R` or `F`) in one of the two proof slots or as inline claim-seal/dependency composition work inside `N`.

- **kill_criterion:** Reverse this decision (and generate a `k = 21` SRS to use a 3-slot node `N(N_1, N_2, U)`) if the 2-slot polymorphic node `N` over `{vk_N, vk_R, vk_F}` exceeds `1,048,512` usable rows (`k = 20`) in `midnight_zk_stdlib::cost_model`.

- **experiment:** Add a 3-way conditional VK selector (`{vk_N, vk_R, vk_F}` with matching `ZkStdLibArch`) and the `SEG`/`SET` join/seal constraints to `StepCircuit` in `crates/mori-recursion/src/ivc.rs:456-565` and measure exact row count via `midnight_zk_stdlib::cost_model` (`ESTIMATE` < 2 hours work, < 30 s runtime).

### (ii) Foreign circuits outside the Midnight stdlib configuration

- **decision:** Meet GP-3 for all Midnight-ecosystem circuits (ZKIR v3 / Compact circuits and `midnight-zk-stdlib` `Relation` circuits over BLS12-381 KZG) by admitting **per-VerifierClass adapter circuits `A_c`** in the authenticated key registry, where `class_id = H("SHK:CLASS:v1", arch_bytes, k, exact_pi_count, cs_version, transcript_id, srs_id)` and each admitted foreign key registers `(vk_id, vk_d, class_id, adapter_vk_d)`. For foreign proof systems outside the single-phase `midnight-zk-stdlib` PLONK/KZG configuration (arbitrary multi-phase halo2 `ConstraintSystem<F>`, Groth16, STARKs, or non-BLS12-381 curves), propose an explicit **OWNER AMENDMENT** scoping GP-3's built-in `VerifierChip` path to single-phase BLS12-381 KZG `midnight-zk-stdlib` / ZKIR v3 circuits and allowing any other proof system to enter by registering a custom `midnight-zk-stdlib` verifier `Relation` as its `adapter_vk_d` in the registry.

- **rationale:**
  - **What `VerifierChip` in `midnight-circuits` actually supports:** `midnight_zk_stdlib::VerifierChip` (`tools/profile/vendor/midnight-zk-stdlib-0.8.3/src/verifier.rs:60-115`) and `midnight_circuits::verifier::VerifierGadget` (`tools/profile/vendor/midnight-circuits-0.8.3/src/verifier/mod.rs:78-438`) are parameterized by a compile-time `ZkStdLibArch` (`tools/profile/vendor/midnight-zk-stdlib-0.8.3/src/arch.rs:14-60`), a domain size `k`, and an exact public-input slice `&[AssignedNative<F>]` (`tools/profile/vendor/midnight-circuits-0.8.3/src/verifier/mod.rs:124-156`) where the instance polynomial vanishes over `0..pi.len()`. Furthermore, `assign_vk_as_public_input` (`tools/profile/vendor/midnight-circuits-0.8.3/src/verifier/mod.rs:400-436`) hardcodes `cs.advice_queries.len() + cs.instance_queries.len() + cs.fixed_queries.len() + 7` commitments and a single lookup/permutation phase.
  - **Why a two-level `(class_id, vk_id)` registry solves stdlib/Compact heterogeneity without rebuilding the core:** Different Compact circuits and `midnight-zk-stdlib` relations have different `(arch, k, pi_len)` tuples. However, the output of any `A_c` adapter circuit is a standard `ForeignClaim(vk_id, stmt_d)` plus a folded KZG accumulator (`acc_d`), and every `A_c` circuit itself uses the fixed core architecture (`bls12_381 + poseidon` + transcript chip). Therefore, the core foreign-lift circuit `F` (whose VK is fixed in `{U, R, F, N, C, D}`) verifies `A_c` uniformly using variable-VK verification (`assign_vk`) against `adapter_vk_d` authenticated in `registry_root`, and folds `A_c`'s inner accumulator alongside `A_c`'s own proof accumulator (`research/sherlock-gp-architecture-20261110/fable/design-1.md:198-235`). Adding a new foreign `VerifierClass` requires building and registering a new `A_c` key in `registry_root`, with **zero changes** to the core keys `{U, R, F, N, C, D}`.
  - **Why non-stdlib proof systems need the clarification amendment:** A literal reading of *"any Midnight circuit whose verifying key is registered"* (`openspec/changes/sherlock-vm-consensus-20261110/general-purpose.md:31-32`) is satisfied by `ZkStdLibArch` + ZKIR v3 (since all Midnight Compact/ZKIR circuits compile through `midnight_zk_stdlib`, `repos/midnightntwrk/midnight-ledger/zkir-v3/src/ir_vm.rs:887-935`). To prevent misreading "any Midnight circuit" as arbitrary raw `halo2` or non-KZG proof systems, the **OWNER AMENDMENT** makes the adapter boundary explicit.

- **risks:**
  - **Number of distinct `A_c` keys for Compact contracts:** If every `pi_len` requires a distinct `A_c`, a deployment with many Compact circuits of different public-input lengths needs one `A_c` per `(arch, k, pi_len)`. Mitigation: `A_c` keys live in the extensible Merkle `registry_root` (not in `N`'s fixed VK list), so having 10 or 1,000 `A_c` keys in `registry_root` adds **zero** rows to `F` or `N`.

- **kill_criterion:** Reverse the two-level `(A_c -> F)` design if the foreign lift `F` (verifying one `A_c` proof plus collapsing two KZG accumulators: `A_c`'s proof accumulator and the inner foreign proof's accumulator) exceeds `1,048,512` usable rows (`k = 20`).

- **experiment:** Construct a prototype `A_c` relation for the `k = 13` C6 digest leaf (`crates/mori-backend/src/sherlock_c6_child.rs:840-895`) and a prototype `F` relation that verifies `A_c` with a variable VK and collapses both accumulators, then run `midnight_zk_stdlib::cost_model` on `F` (`ESTIMATE` < 3 hours work, < 30 s runtime).

### (iii) Ledger-format (Blake2b transcript) Compact proofs vs. Poseidon stage 1

- **decision:** Meet GP-3 in full without narrowing the requirement: build an **in-circuit Blake2b-256 Fiat-Shamir transcript gadget and complete byte-parser inside the Compact `VerifierClass` adapter `A_c`** so unmodified ledger-format Compact proofs (`midnight-ledger:proof[v5]`, `midnight-ledger:verifier-key[v7]`) are verified directly. Use Poseidon-transcript re-proving (`PoseidonState<Fr>`) **solely as an M4 stage-1 internal harness test** (`openspec/changes/sherlock-vm-consensus-20261107/tasks.md:107-112`), not as final GP-3 compliance. Provide an optional **OWNER AMENDMENT** only if the owner wishes to phase native `proof[v5]` byte-transcript verification to a post-G-C milestone.

- **rationale:**
  - **Why Poseidon-only does not satisfy GP-3:** Real Midnight ledger and Compact proofs use `Blake2bState` (`Blake2b::with_params(b"", b"", &[64], domain_sep)` in `tools/profile/vendor/midnight-proofs-0.8.3/src/transcript/implementations.rs:29-140`, reading 64-byte challenges reduced via `F::from_bytes_wide` and hashing points in 48-byte compressed G1 form via `C:: Coordinates` / `Write`), wrapped in versioned tagged envelopes (`midnight-ledger:proof[v5]` in `repos/midnightntwrk/midnight-ledger/transient-crypto/src/proofs.rs:58,288-334` and `midnight-ledger:verifier-key[v7]` in `repos/midnightntwrk/midnight-ledger/zkir/src/lib.rs:94`). Meanwhile, `midnight-circuits`'s existing in-circuit verifier uses `PoseidonTranscript` (`tools/profile/vendor/midnight-circuits-0.8.3/src/verifier/transcript_gadget.rs:34-46`). Requiring callers to re-prove a Compact circuit with a Poseidon transcript requires the caller's private witness, which does not exist when composing third-party on-chain or off-chain Compact proofs (`research/sherlock-gp-architecture-20261110/architecture.md:190-208`).
  - **Why Blake2b-in-circuit belongs in `A_c` and fits easily at `k <= 20`:** `midnight-zk-stdlib` already includes `Sha256Chip` and bitwise/byte decomposition chips (`tools/profile/vendor/midnight-zk-stdlib-0.8.3/src/arch.rs:14-35`). Blake2b-512 uses 12 rounds of the `G` mixing function over eight 64-bit words (`XOR`, 64-bit addition mod $2^{64}$, and fixed bit rotations `32, 24, 16, 63`), which costs `~2,500–3,500` rows per 128-byte block (`ESTIMATE`) using standard 8-bit/16-bit lookup tables in `midnight-circuits`. A standard Compact proof (~`3–5 KB`, ~`35–50` transcript Squeezes/Absorptions) requires `~120,000–180,000` rows for the complete Blake2b transcript + compressed G1 decompression witness check ($y^2 = x^3 + 4$ in $\mathbb{F}_p$, sign bit, cofactor/subgroup check via `AssignedBls12_381`) + canonical `< r` scalar bounds (`ESTIMATE`). Combined with the ~`250,000` rows of the deferred KZG evaluation equations (`tools/profile/vendor/midnight-circuits-0.8.3/src/verifier/kzg.rs:60-185`, outputting the inner `Accumulator` as public output of `A_c` without collapsing it inside `A_c`), `A_c` totals **`~400,000–480,000` rows (`k = 19`) `ESTIMATE`**. Because this Blake2b gadget lives inside `A_c` (and not inside `F` or `N`), `N` never pays a single row for Blake2b.

- **risks:**
  - **Incomplete byte parsing / transcript divergence:** As flagged in `research/sherlock-recursion-design-review-20261110/review.md:174-205`, any discrepancy between host `Blake2bState` (`tools/profile/vendor/midnight-proofs-0.8.3/src/transcript/implementations.rs:29-140`) and the in-circuit gadget (such as trailing bytes after `Read` completes, non-canonical field encodings $\ge r$, point-at-infinity flags, or missing `vk_repr_bytes` commitment binding) is a soundness bug. Mitigation: enforce exact byte-length consumption (`cursor == proof_bytes.len()`), canonical `< r` checks on all field reads, on-curve + prime-subgroup checks on all G1 commitments, and differential test `A_c`'s challenge stream bit-for-bit against `midnight_proofs::transcript::Blake2bState` on real `ledger-9.1.0.1` proof vectors.

- **kill_criterion:** Reverse the in-`A_c` Blake2b design (and invoke the staged **OWNER AMENDMENT** to require an off-chain wrapper or `k = 20` split adapter) if the Blake2b transcript + `proof[v5]` parser + deferred KZG verifier in `A_c` exceeds `1,048,512` rows (`k = 20`).

- **experiment:** Implement a 1-block Blake2b-512 compression gadget in `midnight-circuits` using `ZkStdLibArch { bitwise: true, nr_pow2range_cols: 4, .. }` and run `midnight_zk_stdlib::cost_model` to measure exact rows per 128-byte block (`ESTIMATE` < 4 hours work, < 15 s runtime).

### (iv) Fixed tree depth versus expandable storage

- **decision:** Meet GP-1 ("no fixed upper bound on program size, step count, value size, call depth, or helper depth", `openspec/changes/sherlock-vm-consensus-20261107/general-purpose.md:13-14`) without re-keying `U` by using a **64-bit-addressed Sparse / Variable-Active-Depth Merkle Tree (`1 <= d <= 64`) processed by the Poseidon Chiplet in `U`**. Specifically:
  1. Both `prog_root` and `arena_root` commit their active tree depth `d_prog, d_arena in 1..=64` (where $2^d$ covers the current allocated address range, up to $2^{64}$ cells matching GP-1's 64-bit step/height machine word at `crates/mori-recursion/src/ivc.rs:363`).
  2. When `arena_len` grows past $2^{d_{arena}}$, a deterministic in-circuit tree-doubling step updates `(arena_root, d_arena) -> (H("SHK:NODE:v1", arena_root, ZERO_ROOT[d_arena]), d_arena + 1)` in **1 Poseidon compression** (`73` rows), preserving all existing addresses `0..2^{d_arena}-1` untouched.
  3. Inside `U`, the Memory/ROM and Poseidon chiplets verify a Merkle path by running `d` sequential compression cycles on the Poseidon chiplet (`1` cycle per tree level), rather than unrolling a fixed-depth circuit template. Thus, a small program with `< 4,096` cells (`d = 12`) pays only `12` Poseidon chiplet cycles per unique page/cell opening, while a huge program (`d = 32` or `d = 64`) uses more Poseidon chiplet cycles (and if needed, more `S`-step leaves via the `noop / flush` continuation tick from D2) under the **exact same universal verifying key `vk_U`**.
  4. Provide an explicit **OWNER AMENDMENT** in `requirement_text` below only to confirm that the 64-bit address/counter machine word ($< 2^{64}$, matching `h: u64` in `crates/mori-recursion/src/ivc.rs:314`) applies uniformly to step count, memory addresses, and stack depth.

- **rationale:**
  - **Why fixed unrolled Merkle depth is a false dilemma:** Both prior architecture drafts assumed a Merkle path in `U` must be unrolled to a compile-time constant depth `D` (e.g., `D = 20` or `D = 32`), creating a tension between paying `32` hashes per access on tiny programs versus capping storage at $2^{20}$ cells (`research/sherlock-gp-architecture-20261110/architecture.md:209-219`, `research/sherlock-gp-architecture-20261110/architecture.md:575-596`).
  - **How a chiplet state machine eliminates the fixed-depth tax:** Because D2 routes Merkle verifications to the **Poseidon Chiplet** over a permutation/lookup bus, a Merkle opening is just a sequence of `d` chained rows `(level, cur_hash, sibling, dir_bit, next_hash)` in the Poseidon chiplet table where `level` counts down from `d` to `0` and the final row matches `(0, root)`. Combined with root-extension on allocation (`arena_root -> H(arena_root, ZERO_ROOT[d])`), `d` starts small (`d = 10` for `fact(3)`) and grows on demand up to `64` without changing a single gate or commitment in `vk_U`.

- **risks:**
  - **Single-step path cost at extreme depth (`d = 64`):** If a program allocates $2^{40}$ cells, a single arena opening takes `40` Poseidon compressions (`2,920` rows). Mitigation: the Poseidon chiplet budget per leaf `U` (`B_hash` compressions per leaf) is fixed; as `d` grows, the leaf dynamically executes fewer owner steps `1 <= ds <= 16` per leaf via the `noop / flush` continuation tick when `B_hash` fills up, so `vk_U` never changes and even `d = 64` (`4,672` rows/path) easily fits dozens of openings inside `k_U = 17`.

- **kill_criterion:** Reverse variable-active-depth (`1 <= d <= 64`) in favor of a fixed depth `D = 32` if the level-counter chaining constraints in the Poseidon/Merkle chiplet add more than `15` rows per Merkle level on top of the `73`-row Poseidon compression (`tools/profile/vendor/midnight-circuits-0.8.3/src/hash/poseidon/constants.rs:95-114`).

- **experiment:** Write a 100-line test relation in `midnight-zk-stdlib` that verifies a variable-length Merkle path (`1 <= d <= 64`, padded with inactive Poseidon rows up to a chiplet capacity `B_hash = 256`) using `PoseidonChip` and check via `midnight_zk_stdlib::cost_model` that per-compression row cost stays `< 88` rows (`ESTIMATE` < 2 hours work).

## D4 Inline processor versus separate leaf plus lifts

- **decision:** Choose **separate universal leaf `U` plus named lift circuits `R` (run-segment lift) and `F` (foreign-proof lift), binary polymorphic node `N`, closing leaf `C`, and final decider `D` (fixed core key set `{U, R, F, N, C, D}`, plus per-class foreign adapters `A_c` registered in `registry_root`)**, rather than inlining the VM and foreign verifiers into `N`.

- **rationale:**
  - **In-node row budget math rules out inlining at `k = 20`:** At `k = 20` (`1,048,576` rows, `64` unusable), verifying two prior node proofs and collapsing their accumulators in `midnight-circuits` already takes `730,243` rows (`qa/sherlock/decisions/speed-levers.json:28`) or `652,437` rows without disabled-slot normalization (`research/sherlock-gp-architecture-20261110/architecture.md:107`). That leaves at most `318,000–396,000` rows in `N` for everything else. If `N` also inlines the universal VM (`U`), the foreign-proof verifier (`F`), and the Blake2b Compact transcript gadget (`research/sherlock-gp-architecture-20261110/astra/design-1.md:116-165`), all of those sub-circuits must coexist in `N` simultaneously, pushing `N` well past `k = 20` into `k = 21` (`2,097,152` rows, requiring a new SRS and doubling node proving time to `~130 s` `ESTIMATE`).
  - **Self-verification amplification in `midnight-circuits`:** Because `N` verifies two instances of `N` (`crates/mori-recursion/src/ivc.rs:512-545`), any chip added to `N` (such as lookup tables for 128-bit ALU, memory sorting permutations, PROG ROM tables, or Blake2b bitwise tables) adds fixed commitments, lookup commitments, and permutation commitments to `vk_N`. In `midnight_circuits::verifier::msm` (`tools/profile/vendor/midnight-circuits-0.8.3/src/verifier/msm.rs:491`), every extra commitment in `vk_N` adds a non-native scalar multiplication (`~3,000–4,000` rows per commitment × 2 recursive slots = `~6,000–8,000` rows per commitment, `research/sherlock-gp-architecture-20261110/architecture.md:117-120`) inside `N` itself, plus inside `C` and `D` (`crates/mori-recursion/src/run_decider.rs:208-246`). Separating `{U, A_c}` from `N` keeps `vk_N` minimal (`bls12_381 + poseidon` only, `nr_pow2range_cols = 4`).
  - **Decoupling fast leaf proving (`k_U = 17`) from slow KZG accumulator collapse (`k = 20`):** In `SHKIVC06`, `~90%` of the `61–67 s` node step time (`qa/sherlock/decisions/speed-levers.json:66`) is spent on the non-native BLS12-381 MSM accumulator collapse. If the VM runs inline in `N`, every `S` VM steps must pay a `65 s`, `17 GB` `k = 20` proof. With a separate leaf `U` at `k_U = 17`, proving `16` VM steps takes only `5–9 s` and `< 3 GB` RSS (`ESTIMATE`), can be parallelized across `P = 3` workers ahead of the node chain, and allows `R` to lift `U` into the uniform node architecture cleanly.
  - **Where inline logic *does* belong:** While bulk VM execution (`U`) and foreign KZG/Blake2b verification (`A_c`, `F`) must remain separate from `N`, `N` *should* include the tiny (`~15,000`-row `ESTIMATE`) algebraic PCD claim-routing and sealing logic (`SEG + SEG -> SEG`, `SEG -> SET` when `h_lo == 0 && halted == 1`, `SEG + SET -> SEG` discharging a dependency in `deps_d`, and `SET + SET -> SET` unioning verified claim sets). That gives `N` the expressive power of a continuation/claim processor at the PCD level without polluting `vk_N` with VM or Blake2b chips.

- **risks:**
  - **One extra lift proof (`R`) per leaf segment or per run:** Lifting `U` through `R` before entering `N` adds either one `R` proof per `U` leaf (if `R` wraps each `U`) or one `R` proof per sealed run if `N` folds `R` segments. However, because `R` only verifies one `k_U = 17` leaf `U` plus optionally one `N` claim-set proof, `R` is no larger than `N` (`k = 19..20`), and in a tree/chain over `M = 19` leaves (`S = 16`), `R` proofs run in parallel on worker threads or replace the bottom level of `N` nodes, adding at most `1` sequential `k = 20` step (`~65 s`) to the critical path.
  - **Key-switch compatibility across `{N, R, F}` in `N`'s two slots:** `VerifierChip` requires all candidate VKs in a conditional slot to share the exact same `ConstraintSystem` layout (`ZkStdLibArch`, `k`, and commitment counts, `tools/profile/vendor/midnight-circuits-0.8.3/src/verifier/mod.rs:400-436`). Mitigation: compile `N`, `R`, and `F` with the exact same `ZkStdLibArch` (`bls12_381: true, poseidon: true, nr_pow2range_cols: 4`, fixed `k = 20`, and identical public-input count `8`), padding `R` and `F` with dummy advice/fixed gates if needed so their `VerifyingKey` commitment counts and query layouts are identical to `N`.

- **kill_criterion:** Reverse this decision in favor of inlining `U` into `N` only if `midnight-circuits` non-native MSM collapse is optimized to `< 8 s` at `k = 20` **and** `U` + two `N` verifications are shown to fit under `1,000,000` rows (`k = 20`) with identical `vk_N` commitment counts.

- **experiment:** Compile skeleton `N`, `R`, and `F` relations under identical `ZkStdLibArch` (`bls12_381 + poseidon`, `k = 20`, `8` public inputs) and verify in a unit test that their `VerifyingKey` structures have identical commitment counts, query maps, and `cs_degree` so a single `VerifierGadget::verify` call in `N` can switch between `vk_N`, `vk_R`, and `vk_F` using only `select` gates on the assigned VK commitments (`ESTIMATE` < 3 hours work).

# Proposal

## D1 Genesis mechanism

- **decision:** Mechanism (c). The first segment of a run proves a fixed-width initial commitment `Init(prog_d, input_d)` in circuit. `Init` is the digest of a fixed register file plus the canonical empty memory root: control is `Eval` at the program entry, fuel and stack limit come from `input_d`, frame and task links are empty, the outcome is pending, and the memory root is the empty append log. The seal requires the segment to start at height 0. Readers may recompute the same digest. A caller-supplied digest is not the evidence.

- **rationale:** The node currently forces `prev_d == init_d` when the previous height is zero, and `init_d` is a public input (`crates/mori-recursion/src/ivc.rs:498-501`). The contract constructor accepts any nonzero digest (`tools/sherlock-sdk/sherlock-run.compact:29-35`). The Lean pinning theorem takes a carrier state that opens to `initD` as a premise (`clean/fork/Clean/Sherlock/Aggregation.lean:1110-1120`); the circuit does not discharge it. Initialization depends on fuel and stack limit (`crates/mori-core/src/sherlock/reference.rs:14-27`; the qualification config sets both, `crates/mori-backend/src/sherlock_machine/testdata/dispatch/config.json:46-53`). GP-2 requires a later proof to check a consumed claim in circuit (`openspec/changes/sherlock-vm-consensus-20261107/general-purpose.md:22-27`), so the canonical start has to be inside the proof. A lane-by-lane carrier check is the wrong object: genesis prefixes differ by program, 290 lanes for `literal` and 271 for `add`, and carriers are not padded to `Bounds` (`research/sherlock-gp-decisions-council-20261110/BRIEF.md:7`). The image width of the current layout is already a function of the caps (`crates/mori-core/src/sherlock/helper_machine/c6_phys.rs:50-52`: header 48 plus 16 frames of 13 lanes is 256; `c6_phys_helper.rs:66-69` with 8 tasks of 7 lanes is 87 helper lanes). Under committed memory the initial state is a constant-size register file, so the check is one digest, a few empty-root constraints, and one ROM opening of the entry.

- **risks:** The digest must match `Machine::new` for every program, including a program whose entry is not a constant. A hash that Compact cannot recompute forces the contract to pin the field digest rather than recompute it. If `Init` silently omits fuel or the stack limit, two runs of one program under different limits share a start digest.

- **kill_criterion:** `Init` cannot be opened from `prog_d` and `input_d` alone on `literal`, `add`, and the first step of fact(3), or the init constraints need a scan whose row count grows with the program image. Either result reverses this to a dedicated init continuation, and that continuation is itself reversed if one program byte costs more than one node of work.

- **experiment:** Host-only differential, no prover. For `literal`, `add`, and fact(3), build the reference snapshot and the proposed digest from the program root, fuel, and stack limit, and compare openings. Then one `cost_model` of only those constraints. The running full-carrier measurement is evidence about the rejected carrier scan.

## D2 Leaf architecture

- **decision:** A chiplet processor in the node circuit. One fixed register file (control, fuel, outcome, top frame, top task, memory pointers) issues tagged bus requests. Specialised regions of the same circuit serve them: program ROM, append-only memory, a range table for 128-bit limbs, and Poseidon. The bus is one halo2 `lookup_any` argument (set inclusion). LogUp is not the bus. There is no per-rule key and no separate universal leaf. Expected degree is the node degree, k = 20. Expected cost is at most 2^14 rows per owner step (ESTIMATE), which is the ceiling that places 16 owner steps inside the measured headroom. The lookup design aims below that ceiling; a Merkle-opening design without lookups sits near it. Gate G-C is met at S = 16 by about 19 node proofs plus one decider, on the order of half an hour at the measured per-node time even after a full-domain adjustment (ESTIMATE), at k = 20 memory.

- **rationale:** The measured monolithic leaf does not fit any batch size. On commits `5782173bd` and `7fadf00c3`, the dispatch selector alone is k = 22 (2,747,489 rows), `KMachineEvalBinary` is k = 23 (5,116,513), `BHelperMatchArm` is k = 23 (5,670,286), and `KMachineReturnRight` is k = 21 (1,794,327). One dispatch wrapper is about 1.27 million IR instructions on every rule, and 63 fragments total 132,850,191 instructions, with 45 of 108 rules absent (`research/sherlock-gp-decisions-council-20261110/BRIEF.md:9-16`). The leaf prover refuses k above 19 (`crates/mori-backend/src/proving.rs:22`; `sherlock_c6_child.rs:868-880`), and the pinned leaf SRS has degrees 0 through 19 only (`crates/mori-backend/src/parameters.rs:13-16`). So `k_U + log2 S <= 19` has no solution once `k_U >= 23`. The cost sits in the shared facts, which the emitter applies to every carrier lane and to a full program walk (`crates/mori-backend/src/sherlock_machine/c6_dispatch_step.rs:608-647`, frame multiplexer at 622-628, task multiplexer at 712-716). Per-rule keys keep that block: the smallest cited single-rule circuit is already past 2^20. Shrinking the facts inside one ZKIR relation is the same work as the chiplet split, done with worse wiring. A second proof system (an inner STARK or a folding layer, wrapped in KZG) has no verifier in the pinned crates (`research/sherlock-gp-architecture-20261110/architecture.md:55-57`). It stays the fallback if the lookup circuit fails the kill test below.

  The bus matches the machines that already split execution this way. Miden keeps a short main trace and routes hash, bitwise, memory, and kernel-ROM work through a bus into selector-tagged regions of shared columns (https://docs.miden.xyz/miden-vm/design/chiplets/ and https://docs.miden.xyz/0.16/reference/miden-vm/design/chiplets/hasher). The pinned argument that can implement that split is `ConstraintSystem::lookup_any` (`tools/profile/vendor/midnight-proofs-0.8.3/src/plonk/circuit.rs:1889-1900`), whose permutation checks set inclusion (`plonk/lookup.rs:39-67`). The in-circuit verifier assumes one challenge phase (`~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/midnight-circuits-7.3.0/src/verifier/verifier_gadget.rs:16-20`, asserted at 308-310) and does read lookups (538-539). A LogUp bus needs its own challenge, which that gadget will not verify. Set inclusion is sound for a ROM and for write-once rows with a fixed address column. It is unsound for in-place updates. Data, field, environment, and value-slot tables are append-only (`crates/mori-core/src/sherlock/helper_machine/shared/owner_runtime.rs:3513-3564`). Frames and tasks are rewritten and popped in place (`owner_runtime.rs:3566-3588`), so those two stacks are re-encoded as linked write-once entries before they go on the bus. Poseidon is width 3, rate 2, 8 full rounds and 60 partial rounds (`midnight-circuits-7.3.0/src/hash/poseidon/constants/mod.rs:16-26`); the row cost of one permutation is unmeasured.

  Headroom for that processor is measured. Two self-verifications are 730,243 rows and three proof slots are 1,078,147 (`qa/sherlock/decisions/speed-levers.json:26-29`). 2^20 is 1,048,576, so a third proof overflows by 29,571 rows. The existing fit line is 0.95 × 2^20 = 996,147 (`speed-levers.json:68`). Rows left for inline work after two self slots: 996,147 − 730,243 = 265,904. Sixteen steps at 2^14 rows is 262,144 (ESTIMATE), inside that remainder. S = 16 is the value already serialized on the node (`crates/mori-recursion/src/ivc.rs:77`; `qa/sherlock/manifests/node.json:28`).

  Gate G-C is fact(3) at 293 steps and list123 at 303 steps, under 2 hours, 48 GB per process, and 100 GB aggregate (`openspec/changes/sherlock-vm-consensus-20261107/tasks.md:93-98`). At S = 16 that is 19 nodes for fact(3) and 19 for list123. Measured node time is 61.07 s (A16) and 64–67 s (`speed-levers.json:32-35,83-92`), at 16.6–17.6 GB. Nineteen times 67 s is 1,273 s (ESTIMATE). The current node occupies 741,708 of 1,048,576 rows over the C6 digest leaf (`qa/sherlock/manifests/node.json:22`). Scaling that time by 1,048,576 / 741,708 ≈ 1.41 gives about 95 s per full-domain node, 19 × 95 s ≈ 1,805 s, plus the decider at 70.35 s (`speed-levers.json:107`) (ESTIMATE). Base segments are independent proofs under the same key, so the G-A worker count of 3 applies (`speed-levers.json:62`), with the recorded concurrent slowdown 1.69–1.74 (`speed-levers.json:12-16`). A join tree then has logarithmic depth. The total stays under 2 hours. Peak RSS stays in the k = 20 band, measured near 17 GB and ESTIMATE under 48 GB when the domain is full. Three such processes stayed at an aggregate peak of 47.7 GB on the smaller circuit (`speed-levers.json:25,70`).

  Relation to D4: the chiplets are regions of the node circuit. They are the inline processor. A chiplet that was its own proof would need a cross-proof bus, and the pinned verifier has no extra challenge to bind that bus.

- **risks:** Every per-step figure is ESTIMATE. Filling the self-verifier with extra lookup commitments can consume the 265,904-row remainder before any owner step runs. The verifier gadget and `lookup_any` may not compose in one constraint system (one instance column, one phase). The write-once re-encoding of frames and tasks can diverge from `RewriteTop` and `Pop`. Forty-five rules have no fragment, so the processor has to be written from the reference semantics. Idle processor rows are paid on pure joins because the degree is fixed.

- **kill_criterion:** A `cost_model` of the node plus the bus and one owner step exceeds 996,147 rows, or one owner step exceeds 265,904 rows, or the gadget rejects the combined constraint system. Any of those reverses this to a separate chiplet leaf under the existing one-leaf node, which then requires the owner amendment in D3(i). A step above 2^14 rows and at most 265,904 rows keeps the architecture and lowers S. G-C itself fails if the resulting node count times the measured full-domain step exceeds 7,200 s, or one process exceeds 48 GB.

- **experiment:** Three model-only probes, cheapest first. (1) Count the 1.27 million dispatch instructions by source on the fact(3) first step: range checks, program walks, value reads, the two multiplexers. (2) One hand-written circuit with the verifier gadget and a single `lookup_any` into a fixed table, modeled as a node. (3) One owner step of `KMachineReturnRight` over the register file and the bus, modeled for rows. No SRS, no proof.

## D3 GP-3/GP-4 wording points

### (i) Two prior proofs plus new work

- **decision:** The requirement stands, with no amendment. One node circuit verifies two predecessor proofs and, in the same circuit, performs the new work of D2. The work is processor rows, not a third proof.

- **rationale:** GP-4 requires arity at least 2 plus new work, on one key set (`general-purpose.md:42-48`). The three-slot circuit is 1,078,147 rows (`speed-levers.json:27`), which is above 2^20, and the fit rule already closed it against 996,147 (`speed-levers.json:68`). The pinned ceremony file in use is `bls_midnight_2p20` (`qa/sherlock/manifests/node.json:30-34`). Two self slots at 730,243 rows leave 265,904 rows under the fit line, which is where the chiplet work goes. A node may leave the work idle when it only joins, and may leave both slots neutral when it only runs the processor. Both shapes are the same key.

- **risks:** The 265,904-row budget is the whole of GP-4's "new work". A foreign verification that needs a full second verifier gadget does not fit in it in one shot. D3(ii) therefore chunks that work. If the chiplet step misses the kill test in D2, this reading of GP-4 no longer fits on the pinned SRS.

- **kill_criterion:** The combined node model exceeds 2^20 rows once two predecessor verifiers and one useful owner step are both present. That reverses (i) to an owner amendment: new work may enter as a proof in one of the two slots, and a node that holds two prior proofs does so in a separate joining step.

- **experiment:** The same model as D2 probe (2), with the final statement width, canonical neutral slots, and one enabled work step. Record rows against 996,147 and 1,048,576.

### (ii) Circuits outside the Midnight stdlib configuration

- **decision:** The requirement stands, with no amendment. Any PLONK or halo2 circuit on this curve and this KZG setup is admitted by a registry identity. The node proves membership. Verification of a class the current gadget does not implement is inline work, split across nodes when it exceeds one node's work budget. Adapter keys are registry data. The core key set does not gain a key per circuit.

- **rationale:** GP-3 admits a circuit by its verifying key and requires an in-circuit membership proof, with a statement adapter into the common claim (`general-purpose.md:31-38`). The gadget fixes the constraint system and the degree off circuit and puts only `transcript_repr` in the circuit (`architecture.md:32-39`, citing the gadget). It also assumes one instance column and one phase (`verifier_gadget.rs:16-20`). Compact circuits vary by the chips they use and by `optimal_k`. The verifier parameters carry a specific `s_g2` (`tools/profile/vendor/midnight-proofs-0.8.3/src/poly/kzg/params.rs:235-237`), so a key from another setup is a different commitment. The registry identity binds arch, degree, exact public-input count, transcript, and SRS. A class the gadget implements is one inlined verification. A class it does not implement is a verifier program in the work region, authenticated by the registry entry, continued across nodes. That is the path for a circuit outside the stdlib configuration. It does not add a core key, which is what GP-3 forbids when it says the node must not take the foreign key as a constant.

- **risks:** A chunked verifier is unbuilt. At the recorded 3–4 thousand rows per variable base (`architecture.md:48`, citing `research/sherlock-speed-replan-20261108/prover.md:155`), the MSM alone can fill most of the 265,904-row budget (ESTIMATE). Custom gates have to be represented as data the work region can check. A mistake in the registry binding admits a circuit the adapter does not actually verify.

- **kill_criterion:** One foreign verification cannot be split into chunks that the node gadget accepts, or a chunk exceeds 2^20 rows. That reverses the general path to an owner amendment limiting GP-3 to Midnight-stdlib classes until a verifier for the other class exists as registry data of a single accepted class.

- **experiment:** Off circuit, reproduce the pinned verifier's accept/reject on one real Compact proof. Then model one chunk of variable-base MSM plus the membership path, and count distinct `(arch, k, public-input count)` classes in the Compact circuits already in the repo.

### (iii) Ledger-format Blake2b proofs

- **decision:** The requirement stands, with no amendment. The GP-3 artifact is a ledger-format Compact proof: tag, key, and the keyed Blake2b transcript. A Poseidon re-proof of the same constraint system is a development probe. It is a different proof, and it is not the proof the ledger verifies.

- **rationale:** The acceptance text asks for a proof from a Compact contract circuit (`general-purpose.md:38`). On this stack that proof is verified with `TranscriptHash`, which is Blake2b (`repos/midnightntwrk/midnight-ledger/transient-crypto/src/proofs.rs:64`, used at `proofs.rs:575`). The transcript is keyed and prefixed (`tools/profile/vendor/midnight-proofs-0.8.3/src/transcript/implementors.rs:13-24`). The recursive gadget hashes with Poseidon (`midnight-circuits-7.3.0/src/verifier/types.rs:144-149` and `191-196`). The stdlib wrapper `blake2b_256_digest` takes an empty key (`midnight-zk-stdlib-2.4.0/src/external/blake2b.rs:101-108`), so it is not the ledger transcript. Checking ledger bytes means the work region enforces that keyed transcript, the public-input layout, and the point checks the gadget omits. The public-input count is absorbed into the transcript (`verifier_gadget.rs:303-306`), so padding inputs to a cap would verify a different proof.

- **risks:** Blake2b in circuit is bitwise and unmeasured. Enabling the stdlib chip changes the circuit's chip set, which changes the class the node verifies. A divergence of one prefix bit accepts proofs the ledger rejects, or the reverse.

- **kill_criterion:** A model of one keyed Blake2b transcript, with parsing and the point checks, exceeds what continuation nodes can hold under 2^20 rows each, or the challenges differ from `VerifierKey::verify` on a captured ledger proof. Either one keeps the requirement and moves the Blake2b region out of the hot node only if it remains inside the proof; a design that stops at Poseidon would be an owner amendment.

- **experiment:** From a captured Compact proof, recompute the ledger challenges off circuit and compare to the native verifier. Then `cost_model` one compression plus the prefix absorption. No proof.

### (iv) Fixed tree depth versus expandable storage

- **decision:** The requirement stands, with no amendment. One key. Memory is a commitment. A path length is a witness in `1..=64`. An operation whose path does not fit in one node's work budget carries a cursor in the state commitment, and the next node resumes it. Depths 20 and 32 are rejected.

- **rationale:** GP-1 says capacity does not depend on the key, forbids a ladder of capacity keys, and bounds run length by the height field below 2^64 (`general-purpose.md:7-14`). Height is already checked below 2^64 (`crates/mori-recursion/src/ivc.rs:77-79`, `363-375`). An address width of 64 is that same bound applied to space: every program that fits in 2^64 cells uses the same key. A depth fixed at 20 or 32 would make a larger program require another key, which is the ladder GP-1 rules out. The cursor is ordinary inline work, the same continuation mechanism as a long foreign verification. The current whole-carrier hash is what binds capacity to the layout (`crates/mori-backend/src/sherlock_c6_child.rs:551-569`).

- **risks:** A 64-level path is 64 compressions. At an unmeasured Poseidon cost, one path can exceed the 265,904-row budget and must resume. A cursor that is not bound into `pre_d` lets a prover skip the rest of a path. Page-in of cells from an earlier node is the expensive case, and its rate is unmeasured.

- **kill_criterion:** The resumed-path statement can be accepted with the cursor advanced and the memory root unchanged, or a program that fits in the address width needs a second key. Either reverses the memory design. A proposal to cap depth at 20 or 32 would be an owner amendment, and this proposal does not make it.

- **experiment:** One append and one 64-level opening in the bus circuit, modeled for rows, plus a host check that a cursor value outside the path length is rejected by the statement relation. Use fact(3) cell ages to see how often a step reads a cell from an earlier node.

## D4 Inline processor versus separate leaf plus lifts

- **decision:** The inline processor. Core keys are the node N and the decider D. The chiplet bus of D2 is the new work inside N. Separate leaf proofs plus run and foreign lift proofs are rejected on these measurements.

- **rationale:** D2 leaves a processor that fits in the rows after two self slots, and it leaves a third proof slot that does not: 1,078,147 is past 2^20 (`speed-levers.json:27`). A base segment is an N proof with both slots neutral and the processor running, so segment proofs still run in parallel under one key. The G-A record of three concurrent node provers is the relevant contention data (`speed-levers.json:12-16,70`).

- **risks:** Every join pays for a k = 20 circuit even when the processor is idle. The self-verifier now verifies a lookup-heavy circuit, and the commitment count can erase the work budget (D2 risk). A foreign proof that chunks into many nodes makes mixed aggregates slower than a dedicated adapter circuit would. No OWNER AMENDMENT. GP-1 through GP-4 stay as written in `openspec/changes/sherlock-vm-consensus-20261107/general-purpose.md`. The following sentences are the checks for this design.

1. The deployed proving keys SHALL be the node key and the decider key. Neither key SHALL depend on the program, the input, the run length, the memory size, the registry contents, the shape, or the depth.

The bus SHALL be a set-inclusion lookup. The node relation SHALL have one challenge phase. Frames and helper tasks SHALL be stored as linked write-once entries.

When a segment starts at height 0, the processor SHALL prove that the register file and the memory root equal `Init(prog_d, input_d)`, including the entry opened from the program, the fuel and the stack limit from `input_d`, empty links, a pending outcome, and the empty memory root. The decider SHALL require that start. A digest supplied by the caller SHALL NOT by itself establish the initial state.

5. One key SHALL serve every memory size up to an address width of 64. Path length SHALL be a witness. A path that does not finish inside one node's work budget SHALL resume from a cursor carried in the state commitment.

6. The node SHALL admit a PLONK or halo2 circuit on this curve and this KZG setup by membership of a registry identity that binds the arch, the degree, the exact public-input count, the transcript, and the SRS. The node SHALL prove that membership. Verification of a class outside the verifier gadget's configuration SHALL be new work, continued across nodes when it exceeds one node. A claim that ledger proof bytes were checked SHALL enforce the keyed Blake2b transcript, the ledger encodings, and complete parsing.

7. The decided statement SHALL carry the claim-set commitment and a shape commitment that binds slot bits, segment bracketing, and unary nodes. The final proof SHALL be one decider proof, of the same size for every shape and depth.

### (iv) Fixed tree depth versus expandable storage

- **decision:** OWNER AMENDMENT (clarifying). Fixed Merkle depth equal to the machine address width (32 for the data arena and program table; frames and helper tasks as hash chains, which have no depth) meets GP-1. Proposed replacement for the capacity bullet in [general-purpose.md](/home/hoskinson/Projects/Moriarty/openspec/changes/sherlock-vm-consensus-20261107/general-purpose.md:13): "Capacity does not depend on the key. A program whose state does not fit one leaf's registers runs against committed memory: state lives behind a commitment, and each step proves its reads and writes against it. A commitment depth equal to the machine's address width is part of the machine definition, as the 2^64 height bound is; a fixed ladder of capacity keys below that width is not universal." Segmented paging (page-in/page-out per segment) is the optimisation path if paths dominate; fully expandable storage with paths processed across proofs is not adopted.
- **rationale:** GP-1 already accepts one machine-definition bound of this kind: "The run length is bounded only by the height field (below 2^64)" ([general-purpose.md GP-1](/home/hoskinson/Projects/Moriarty/openspec/changes/sherlock-vm-consensus-20261107/general-purpose.md:14)), and heights are range-checked below 2^64 in the node today ([ivc.rs `constrain_heights`](/home/hoskinson/Projects/Moriarty/crates/mori-recursion/src/ivc.rs:363)). Expandable storage needs continuations for path processing across proofs, which is the inline-processor machinery rejected in D4 for the node.

If the owner reads any fixed depth as a narrowing, the cost is the continuation design; the amendment makes that a conscious owner choice.
- **kill_criterion:** If the D2 access census shows cold-path openings at depth 32 exceeding the transition rows on the median step, switch those tables to paged Merkle (page root in registers, page-in/out per segment) before considering expandable storage.
- **experiment:** Rows of one tagged compression, one depth-32 read and one append, in the D2 slice; multiply by the census counts. This is part of experiment 5 of the study ([architecture.md §5](/home/hoskinson/Projects/Moriarty/research/sherlock-gp-architecture-20261110/architecture.md:636)).
