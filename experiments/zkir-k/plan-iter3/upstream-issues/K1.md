Title: from_coordinates on Jubjub accepts any x with the right parity off-circuit, while the circuit pins the exact (x, y)

Affected crate and commit

midnight-ledger, crate zkir-v3 (midnight-zkir-v3 3.0.0), commit 92e8bdd3a97b61b229e38916e1b180de6f448dd5 on ledger-9. The same code is at the head of ledger-9 (0d364eb9, zkir-v3/src/ir_instructions/from_coordinates.rs:42) and in midnightntwrk/midnight-zkir at 2ffe2d17bbb736aec36fb300aeaca679a10d2278 (zkir/src/ir_instructions/from_coordinates.rs:42). The underlying helper is midnight-circuits 7.2.4.

Expected behaviour

`from_coordinates` on two native operands builds the Jubjub point with exactly the coordinates (x, y), or fails if (x, y) is not on the curve. Off-circuit (`preprocess`) and in-circuit should agree on which pairs are accepted, and the value placed in memory should be the pair that was supplied.

Actual behaviour

Off-circuit, `from_coordinates_offcircuit` (zkir-v3/src/ir_instructions/from_coordinates.rs:39-48) computes

    (Native(x), Native(y)) => JubjubExtended::from_xy(x.0, y.0)

`CircuitCurve::from_xy` for `JubjubExtended` (midnight-circuits 7.2.4, src/ecc/curves.rs:109 and 120-138) does not check the curve equation on (x, y). It compresses y together with the low bit of x (`let x_sign = x.to_bytes_le()[0] << 7; bytes[31] |= x_sign;`), decompresses with `JubjubAffine::from_bytes` (midnight-curves 0.3.1, src/jubjub/curve.rs:454 and from_bytes_inner at 478: the sign bit only fixes the parity of the recovered u), and then checks only `point.get_v() == y`. So every x that has the parity of the true x-coordinate yields the true point: x + 2, x + 4, x - 2, and so on, are all accepted, and the value written to memory is the point whose x is the real one, not the x that was supplied.

In circuit, `from_coordinates_incircuit` (from_coordinates.rs:92-104) calls `std_lib.jubjub().point_from_coordinates(layouter, x, y)`, which (midnight-circuits 7.2.4, src/ecc/native/edwards_chip.rs:786-800) assigns the point recovered by the same `from_xy` and then asserts `x == point.x` and `y == point.y`. With a tampered x the assignment succeeds but the equality constraint on x is violated, so the circuit rejects what `preprocess` accepted.

Minimal reproduction

Program (from_coordinates.zkir). The `Point<Jubjub>` input only serves to enable the Jubjub chip (see the separate report on used_chips):

                {"name": "%y", "type": "Scalar<BLS12-381>"},
                {"name": "%enable", "type": "Point<Jubjub>"}],

       {"op": "from_coordinates", "inputs": ["%x", "%y"], "output": "%p"},
       {"op": "into_coordinates", "point": "%p", "outputs": ["%px", "%py"]}]}

Preimage (`ProofPreimage`): `inputs` are the four raw field elements below in decimal, `binding_input` is 42, the three transcripts are empty and there is no communications commitment. The first element is x_G + 2 where (x_G, y_G) is the coordinate pair of the Jubjub subgroup generator; the second is y_G; the last two are (x_G, y_G) for the `%enable` input.

Observed with `IrSource::preprocess`: Ok. Memory holds `%x` = ...689575 (the tampered value) but `%p` and `%px` = ...689573 (the generator's real x). Running the circuit (`keygen` then `prove`, or a MockProver run of `IrSource::circuit`) on this preimage fails the `assert_equal(x, point.x)` constraint of `point_from_coordinates`.

By contrast, with inputs[0] = x_G + 1 (wrong parity) `preprocess` returns an error.

Impact

Consistency between the off-circuit evaluator and the circuit, and the meaning of the instruction. No unsound proof results, because the circuit still pins the exact pair. But `preprocess` accepts a witness that cannot be proved (completeness), and any consumer that trusts `preprocess` as the definition of the instruction (for example a specification derived from it, or a test that only runs `preprocess`) is told that `from_coordinates(x, y)` returns a point whose x may differ from x. The `into_coordinates` output after a "successful" `from_coordinates` need not equal the input coordinates.

Suggested fix

In `from_coordinates_offcircuit`, after `JubjubExtended::from_xy`, check that the recovered point's coordinates equal (x, y) and return the "Cannot build a Jubjub point" error otherwise (equivalently, evaluate the twisted Edwards equation -x^2 + y^2 = 1 + d x^2 y^2 directly). A `from_xy` that checks the equation in midnight-circuits (the FIXME at curves.rs:121-124 already asks for a `from_coords_checked`) would fix both this path and the in-circuit hint. A regression test with (x_G + 2, y_G) should expect an error from `preprocess`.

Found by differential testing against an executable specification.
