Title: used_chips does not enable the Jubjub chip for jubjub_scalar_from_native or native from_coordinates, so key generation panics on programs that preprocess accepts

Affected crate and commit

midnight-ledger, crate zkir-v3 (midnight-zkir-v3 3.0.0), commit 92e8bdd3a97b61b229e38916e1b180de6f448dd5 on ledger-9. Still present at the head of ledger-9 (0d364eb9, zkir-v3/src/ir_vm.rs:1236-1237). The same scanner is in midnightntwrk/midnight-zkir at 2ffe2d17bbb736aec36fb300aeaca679a10d2278 (zkir/src/ir_vm.rs:1461, jubjub predicate at 1485). This extends the earlier report that `from_bytes32` was the only instruction able to reach a chip that `used_chips` had not enabled: `jubjub_scalar_from_native` and `from_coordinates` on two native operands are two more.

Expected behaviour

Every program that `IrSource::load` and `IrSource::preprocess` accept can be synthesised: `keygen_vk` / `keygen` (zkir-v3/src/ir.rs:109-127, via `midnight_zk_stdlib::setup_vk`) and `prove` succeed, or the program is rejected up front with an error.

Actual behaviour

`IrSource::used_chips` (ir_vm.rs:1212-1260) enables the Jubjub chip only when a program input, a `public_input` or a `private_input` has type `Point<Jubjub>` or `Scalar<Jubjub>`, or when the program contains `hash_to_curve` (ir_vm.rs:1236-1237):

    jubjub: involves_types(&[IrType::JubjubPoint, IrType::JubjubScalar])
        || involves_instructions(&|op| matches!(op, I::HashToCurve { .. })),

Two instructions create Jubjub values from natives and need the chip in circuit:

  - `jubjub_scalar_from_native`: the circuit arm (ir_vm.rs:970-977) calls `jubjub_scalar_from_biguint` (ir_instructions/encode.rs:227-240), which ends with `std_lib.jubjub().scalar_from_le_bytes(...)` (encode.rs:239).
  - `from_coordinates` with two native operands: the circuit arm (ir_vm.rs:1104-1108) calls `from_coordinates_incircuit` (ir_instructions/from_coordinates.rs:92-104), whose `(Native, Native)` arm calls `std_lib.jubjub().point_from_coordinates(...)` (from_coordinates.rs:100-103).

`ZkStdLib::jubjub` (midnight-zk-stdlib 2.3.5, src/lib.rs:752-754) is

    self.jubjub_chip.as_ref().expect("ZkStdLibArch must enable jubjub")

so when no Jubjub-typed input and no `hash_to_curve` appear in the program, `preprocess` succeeds and synthesis panics with "ZkStdLibArch must enable jubjub". Any later Jubjub instruction on the produced value (`ec_mul_generator`, `ec_mul`, `into_coordinates`, `encode`, `output`) hits the same missing chip.

Minimal reproduction

Program A (jubjub_scalar_from_native.zkir):

    {"version": {"major": 3, "minor": 0},
     "inputs": [{"name": "%a", "type": "Scalar<BLS12-381>"}],
     "outputs": [], "do_communications_commitment": false,
     "instructions": [
       {"op": "jubjub_scalar_from_native", "native": "%a", "output": "%s"},
       {"op": "ec_mul_generator", "scalar": "%s", "output": "%p"}]}

Preimage: `inputs` = [7], `binding_input` = 42, empty transcripts, no communications commitment. `preprocess` succeeds (`%s` = 7, `%p` = 7 * G). `keygen` panics with "ZkStdLibArch must enable jubjub".

Program B (from_coordinates_native.zkir):

    {"version": {"major": 3, "minor": 0},
     "inputs": [{"name": "%x", "type": "Scalar<BLS12-381>"},
                {"name": "%y", "type": "Scalar<BLS12-381>"}],
     "outputs": [], "do_communications_commitment": false,
     "instructions": [{"op": "from_coordinates", "inputs": ["%x", "%y"], "output": "%p"}]}

Preimage: `inputs` = the generator's coordinates

    inputs[0] = 28336281903124990867587793011069573392383982287722241916350956173377953689573
    inputs[1] = 39385640392217313770878525135509063452020585410343666726093009378539878503883

`binding_input` = 42. `preprocess` succeeds; `keygen` panics with the same message. Adding an unused input of type `Point<Jubjub>` to either program makes key generation succeed, which shows that only the chip gating is at fault.

Impact

Completeness and availability: a well-typed program that the off-circuit evaluator accepts cannot have keys generated, and the failure is a panic during `setup_vk` rather than an error. A compiler that emits `jubjub_scalar_from_native` or native `from_coordinates` without an explicit Jubjub-typed input produces circuits that cannot be proved.

Suggested fix

Enable the chip from the instructions as well as from the input types in `used_chips`:

    jubjub: involves_types(&[IrType::JubjubPoint, IrType::JubjubScalar])
        || involves_instructions(&|op| matches!(op,
               I::HashToCurve { .. } | I::JubjubScalarFromNative { .. } | I::FromCoordinates { .. })),

`FromCoordinates` on foreign operands does not need the Jubjub chip, so enabling it for every `from_coordinates` is conservative but safe (the chip only costs columns). A more precise option is a forward type pass over the instructions, which the crate needs anyway to detect the `from_bytes32` case. Independently, `ZkStdLib::jubjub` could return `Error::Synthesis` instead of panicking, so that a gating bug surfaces as an error from `keygen`.

Found by differential testing against an executable specification.
