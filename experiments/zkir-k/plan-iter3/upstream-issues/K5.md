Title: less_than with bits 253 or 254 passes preprocess but key generation panics (padded bound exceeds MAX_BOUND_IN_BITS)

Affected crate and commit

midnight-ledger, crate zkir-v3 (midnight-zkir-v3 3.0.0), commit 92e8bdd3a97b61b229e38916e1b180de6f448dd5 on ledger-9. Still present at the head of ledger-9 (0d364eb9, zkir-v3/src/ir_vm.rs:966) and in midnightntwrk/midnight-zkir at 2ffe2d17bbb736aec36fb300aeaca679a10d2278 (zkir/src/ir_vm.rs:1131). The chip limit is in midnight-circuits 7.2.4 via midnight-zk-stdlib 2.3.5. Same class as the earlier `reconstitute_field` report, where a bit count accepted by `preprocess` panicked at key generation.

Expected behaviour

The set of `bits` values that `less_than` accepts is the same off-circuit and in-circuit, and a `bits` value outside it is rejected by `IrSource::load` or `preprocess` with an error, never by a panic inside `keygen`.

Actual behaviour

Off-circuit, `resolve_operand_bits` (zkir-v3/src/ir_vm.rs:268-270) rejects only `bits >= FR_BITS` (255):

    if n as usize >= FR_BITS {
        bail!("Excessive bit bound");
    }

In circuit, the `LessThan` arm (ir_vm.rs:959-966) pads the width:

    let bit = std.lower_than(layouter, &a, &b, u32::max(*bits + *bits % 2, 4))?;

`ZkStdLib::lower_than` (midnight-zk-stdlib 2.3.5, src/lib.rs:889-899) calls `native_gadget.bounded_of_element(layouter, n, x)`, and `bounded_of_element` (midnight-circuits 7.2.4, src/field/native/native_gadget.rs:332-344) asserts

    n <= Self::MAX_BOUND_IN_BITS   // MAX_BOUND_IN_BITS = F::NUM_BITS - 2 = 253 (native_gadget.rs:330)

with the message "Cannot bound an element with a bound {} > {} = MAX_BOUND". For `bits` = 253 the padded width is 254; for `bits` = 254 it is 254. Both pass `preprocess` and panic in `setup_vk`. The largest usable value is therefore 252, not 254.

Minimal reproduction

Program (less_than_253.zkir):

    {"version": {"major": 3, "minor": 0},
     "inputs": [{"name": "%a", "type": "Scalar<BLS12-381>"},
                {"name": "%b", "type": "Scalar<BLS12-381>"}],
     "outputs": [], "do_communications_commitment": false,
     "instructions": [{"op": "less_than", "a": "%a", "b": "%b", "bits": 253, "output": "%lt"}]}

Preimage (`ProofPreimage`): `inputs` = [1, 2], `binding_input` = 42, empty transcripts, no communications commitment.

Observed: `preprocess` succeeds with `%lt` = 1. `keygen` (zkir-v3/src/ir.rs:120-127, through `midnight_zk_stdlib::setup_vk`) panics with "Cannot bound an element with a bound 254 > 253 = MAX_BOUND". The same happens with `"bits": 254`; with `"bits": 252` key generation succeeds; with `"bits": 255` `preprocess` returns "Excessive bit bound".

Impact

Completeness and availability. A program that the loader and the off-circuit evaluator accept cannot have keys generated, and the failure is a panic rather than an error. A compiler that emits `less_than` with a 253-bit bound (a natural choice for "any field element below 2^253") produces circuits that cannot be proved.

Suggested fix

Reject the values the chip cannot handle where the other bit bounds are checked. In `resolve_operand_bits`, or specifically for `LessThan` in `preprocess` and in `IrSource::load`'s static checks, require `bits + bits % 2 <= 252`, that is `bits <= 252`:

    I::LessThan { bits, .. } if *bits > 252 => bail!("less_than: bit bound {bits} exceeds the maximum of 252"),

and document the bound on the instruction (ir.rs, `LessThan` doc comment). Alternatively raise the chip limit, but the padding to an even width means 253 can never be supported directly.

Found by differential testing against an executable specification.
