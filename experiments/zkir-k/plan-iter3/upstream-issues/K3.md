Title: decode_offcircuit for Bytes32 uses assert_eq! on caller-supplied raw inputs and panics on a non-canonical element

Affected crate and commit

midnight-ledger, crate zkir-v3 (midnight-zkir-v3 3.0.0), commit 92e8bdd3a97b61b229e38916e1b180de6f448dd5 on ledger-9. Still present at the head of ledger-9 (0d364eb9, zkir-v3/src/ir_instructions/encode.rs:155). Not present in midnightntwrk/midnight-zkir at 2ffe2d17bbb736aec36fb300aeaca679a10d2278, whose `decode_bytes` returns `None` for the same input (see the companion report on the two crates disagreeing).

Expected behaviour

`decode_offcircuit` (zkir-v3/src/ir_instructions/encode.rs:143) is documented to return an error "if the provided raw values cannot be decoded as the given type". A `Bytes<32>` value is two field elements: the low 31 bytes in the first and the high byte in the second. A first element that uses byte 31, or a second element above 255, is not a valid encoding and should produce `Err`.

Actual behaviour

The `Bytes32` arm (encode.rs:150-164) asserts instead of returning `None`:

    let mut bytes = encoded[0].to_bytes_le();
    assert_eq!(bytes[31], 0);                 // encode.rs:155

    let high = encoded[1].to_bytes_le();
    for b in high.iter().skip(1) {
        assert_eq!(*b, 0);                    // encode.rs:159
    }

`decode_offcircuit` is called from `preprocess` on the raw `inputs` of the preimage (ir_vm.rs:192-204, call at line 201) and on the transcripts (`public_input`, `private_input`), so a preimage containing such an element aborts the thread:

    thread 'main' panicked at zkir-v3/src/ir_instructions/encode.rs:155:17:
    assertion `left == right` failed
      left: 1
     right: 0

Minimal reproduction

Program (bytes32_input.zkir):

    {"version": {"major": 3, "minor": 0},
     "inputs": [{"name": "%b", "type": "Bytes<32>"}],
     "outputs": [], "do_communications_commitment": false,
     "instructions": [{"op": "reverse_bytes", "bytes": "%b", "output": "%r"}]}

Preimage (`ProofPreimage`): `inputs` = [2^248, 0] in decimal, that is

    inputs[0] = 452312848583266388373324160190187140051835877600158453279131187530910662656
    inputs[1] = 0

`binding_input` = 42, empty transcripts, no communications commitment. 2^248 is a canonical field element whose little-endian byte 31 is 1.

Observed: `preprocess` panics at encode.rs:155:17 with the message above. With `inputs` = [0, 256] it panics at encode.rs:159:21 instead. Expected: `Err(...)` from `preprocess`.

Impact

Availability. The raw inputs and transcripts of a `ProofPreimage` are caller data; a single malformed element aborts the prover thread instead of yielding a recoverable error. No soundness effect.

Suggested fix

Replace the assertions by early returns of `None` (the arm already returns `Option` and maps `None` to the decode error):

    let mut bytes = encoded[0].to_bytes_le();
    let high = encoded[1].to_bytes_le();
    if bytes[31] != 0 || high[1..].iter().any(|b| *b != 0) {
        None
    } else {
        bytes[31] = high[0];
        Some(IrValue::Bytes32(bytes))
    }

This is what midnight-zkir at 2ffe2d1 does in `decode_bytes` (zkir/src/ir_instructions/encode.rs:144-163). A unit test with [2^248, 0] and with [0, 256] should expect an error.

Found by differential testing against an executable specification.
