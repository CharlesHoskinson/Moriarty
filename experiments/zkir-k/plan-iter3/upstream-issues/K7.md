Title: used_chips does not enable the Jubjub chip for a Jubjub value introduced only by load_constant, so synthesis panics on a program that preprocess accepts

Affected crate and commit

midnightntwrk/midnight-zkir, crate zkir, commit 2ffe2d17bbb736aec36fb300aeaca679a10d2278 (the default branch head at the time of writing). The `load_constant` instruction does not exist in midnight-ledger's zkir-v3 at 92e8bdd3, so this is specific to the standalone crate.

Expected behaviour

Every program that `IrSource::load` and `IrSource::preprocess` accept can be synthesised, or is rejected up front with an error.

Actual behaviour

`used_chips` (zkir/src/ir_vm.rs, `fn used_chips`) decides whether the Jubjub chip is enabled from the declared input types and from the `val_t` of `public_input` and `private_input` instructions only. A `load_constant` with `type` `Point<Jubjub>` or `Scalar<Jubjub>` introduces a Jubjub value without any of those, so the chip stays disabled. In `circuit`, the `LoadConstant` arm calls `assign_constant_incircuit` (zkir/src/ir_instructions/assign_constant.rs), which for `IrValue::JubjubPoint` and `IrValue::JubjubScalar` calls `std_lib.jubjub()`, whose accessor panics: `ZkStdLibArch must enable jubjub` (midnight-zk-stdlib 2.3.5, src/lib.rs:753). The crate's own test `test_constant_proof` does not reach this case because it also has a `private_input` of type `Point<Jubjub>`, which enables the chip.

Minimal reproduction

Program (two instructions, no inputs, no outputs):

{
 "version": {
  "major": 3,
  "minor": 0
 },
 "do_communications_commitment": false,
 "inputs": [],
 "outputs": [],
 "instructions": [
  {
   "op": "load_constant",
   "type": "Point<Jubjub>",
   "encoding": [
    "0xd8b6b11fd5179b86e5e15ff573059744c8666738c1b59d8566a0018c63fbb069",
    "0x26c69cc492e137a38ab29d807387ccd70021ab143c208ed121e97d92cf0c1018"
   ],
   "output": "%p"
  },
  {
   "op": "into_coordinates",
   "point": "%p",
   "outputs": [
    "%x",
    "%y"
   ]
  }
 ]
}

Preimage: no inputs, empty transcripts, binding input 0.

`preprocess` succeeds (memory holds the point and its two coordinates). Building the circuit with the stdlib wrapper (`MidnightCircuit::new` with the preprocessed witness) and running the MockProver panics at synthesis with the message above; `keygen` takes the same path.

Impact

Availability: a well-formed program that the off-circuit path accepts cannot be key-generated or proved. Same class as the earlier report about `jubjub_scalar_from_native` and native `from_coordinates`.

Suggested fix

Extend the `involves_types` scan in `used_chips` to `I::LoadConstant { val_t, .. }`, or enable the chip whenever any instruction's declared type is a Jubjub type. The same scan should be checked for the secp256k1, secp256r1 and curve25519 arms, which use the same predicate.

Found by differential testing against an executable specification.
