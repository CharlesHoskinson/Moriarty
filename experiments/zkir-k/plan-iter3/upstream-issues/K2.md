Title: preprocess panics instead of returning an error when a transcript is shorter than a public_input or private_input needs

Affected crate and commit

midnight-ledger, crate zkir-v3 (midnight-zkir-v3 3.0.0), commit 92e8bdd3a97b61b229e38916e1b180de6f448dd5 on ledger-9. Still present at the head of ledger-9 (0d364eb9, zkir-v3/src/ir_vm.rs:378-380) and in midnightntwrk/midnight-zkir at 2ffe2d17bbb736aec36fb300aeaca679a10d2278 (zkir/src/ir_vm.rs:434-436, panic reported at 435:33).

Expected behaviour

`IrSource::preprocess` (zkir-v3/src/ir_vm.rs:185) returns `Err` for a malformed `ProofPreimage`, as it does for too few raw inputs ("Not enough raw inputs", ir_vm.rs:194-199) and for transcripts that are not fully consumed ("Transcripts not fully consumed", ir_vm.rs:648-660). A preimage whose private or public transcript is shorter than the program reads should be rejected with an error, not abort the process.

Actual behaviour

The `PrivateInput` arm (ir_vm.rs:367-386) slices the transcript before checking its length:

    let w = val_t.encoded_len();
    let raw_outputs = &preimage.private_transcript
        [private_transcript_outputs_idx
            ..private_transcript_outputs_idx + w];

The `PublicInput` arm does the same with `public_transcript_outputs` (ir_vm.rs:348-362). When the transcript is too short the slice indexing panics:

    thread 'main' panicked at zkir-v3/src/ir_vm.rs:379:33:
    range end index 1 out of range for slice of length 0

The length check at ir_vm.rs:648-660 runs only after the instruction loop, so it is never reached.

Minimal reproduction

Program (short_transcript.zkir): an unguarded `private_input` with an empty private transcript.

    {"version": {"major": 3, "minor": 0},
     "inputs": [{"name": "%a", "type": "Scalar<BLS12-381>"}],
     "outputs": [], "do_communications_commitment": false,
     "instructions": [
       {"op": "private_input", "guard": null, "type": "Scalar<BLS12-381>", "output": "%x"},
       {"op": "add", "a": "%a", "b": "%x", "output": "%y"}]}

Preimage (`ProofPreimage`): `inputs` = [1], `binding_input` = 42, `private_transcript` = [], `public_transcript_inputs` = [], `public_transcript_outputs` = [], no communications commitment.

Observed: `preprocess` panics with the message above (exit code 101 in a binary that calls it). Replacing `private_input` by `public_input` and leaving `public_transcript_outputs` empty panics at ir_vm.rs:360. Expected: `Err(...)`.

Impact

Availability. `preprocess` is the entry point that a prover runs on caller-supplied data, so a preimage that is one element short takes down the calling thread (in a wallet or proof server, potentially the whole process) instead of producing a recoverable error. There is no soundness effect: no proof is produced.

Suggested fix

Check the bound before slicing, mirroring the raw-input check at ir_vm.rs:194-199:

    let w = val_t.encoded_len();
    let end = private_transcript_outputs_idx + w;
    if end > preimage.private_transcript.len() {
        bail!("Not enough private transcript entries: needed {} at index {}", w, private_transcript_outputs_idx);
    }
    let raw_outputs = &preimage.private_transcript[private_transcript_outputs_idx..end];

and the same for `public_transcript_outputs` in the `PublicInput` arm (and, if applicable, for `public_transcript_inputs`). Alternatively use `.get(idx..idx + w).ok_or_else(...)`. A unit test with an empty transcript should expect an error.

Found by differential testing against an executable specification.
