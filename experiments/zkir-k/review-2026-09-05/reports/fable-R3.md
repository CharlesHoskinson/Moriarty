# Review R3: constraint checker, chip gating, divergence tests

VERDICT: WARNING — the per-gate relations are mostly the ones `Relation::circuit` enforces, but the checker misclassifies value-level unsatisfiability as synthesis error, reports spurious `violated` verdicts after a witness failure, does not model the communications-commitment constraint at all (so finding 5's actual gap is untestable), and masks a keygen panic in `less_than`; the off-circuit `test_eq` also accepts a type the crate rejects.

## Findings

### 1. major — The communications-commitment constraint is not modelled; `piFixed(1, _)` is unconditionally `holds()`

- K: `semantics/zkir-constraints.k:147` `rule eval(piFixed(_, _), _, _, _) => holds()`; emission at `semantics/zkir-vm.k:116-118`. The file header (`zkir-constraints.k:8`) says `piFixed(i, _)` "pins the binding input and the commitment"; it pins nothing.
- Rust: `ir_vm.rs:1173-1204` builds the in-circuit preimage `[rand] ++ encode_incircuit(memory[input]) ... ++ encode_incircuit(outputs)`, hashes it with `std.poseidon` and `assert_equal`s it to `public_inputs[1]`. `preprocess` (`ir_vm.rs:669-681`) commits the **raw** input stream (`transient_commit` = `transient_hash(opening ++ field_repr)`, `/home/charl/Moriarty/repos/_build/ledger-92e8bdd3/transient-crypto/src/hash.rs:84-88`).
- Why it matters: this is exactly the divergence the review's finding 5 describes (docs review lines 189-201): a non-canonical foreign input makes the raw-stream commitment differ from the canonical re-encoding, so the honest preimage passes `preprocess` and fails the circuit. The K has every ingredient (`encodeValue`, `poseidonHash`, `<outputs>`) and the K witness half checks the raw commitment correctly (`zkir-vm.k:473-476`), but the constraint side cannot observe the gap. Reproduced: program `t9` (one `Base<Secp256k1>` input, `add`, `output`, `do_communications_commitment: true`) with raw limbs of `p+5`: K gen-mode commitment over the raw stream is `38568051874525261413962060539387229545214218749264718088526210633707817698389`, over the canonical re-encoding of the same value it is `49250011375316071074926245919468624206075025600419955865387234020646127538625`; with the raw commitment both K and `zkir-oracle` report `ok` and all four K verdicts hold. Case `f05` in `tools/divergence_tests.py:69-74` uses `comm=False` and checks the `add` gate, so it does not test finding 5.
- Fix: replace `piFixed(1, var("$commitment"))` by `commGate(1)` evaluated as `pi[1] == poseidonHash(ListItem(rand) #encodeAll(inputValues) #encodeAll(outputs))` where `inputValues` are the decoded `<mem>` entries of the declared inputs in order (`ir_vm.rs:1185-1191`) — this needs the opening randomness and `<outputs>` passed to `verdicts`. Then change `f05` to `comm=True` and expect `violated` on the commitment gate. Note `ir_vm.rs:1186` skips an input that is absent from memory (`if let Some`), which the K cannot reach because decoding failure freezes the run.

### 2. major — `#matches` turns value-level unsatisfiability into `synthErr`: `inv` of zero and `bytes32_from_low_high` bounds

- K: `semantics/zkir-constraints.k:136` `rule #matches(vErr(S), _, What) => synthErr(...)` with the comment "the in-circuit op is undefined on these types". But the `vErr`s that reach it are not only type errors: `invV(native(0))` (`semantics/zkir-ops.k:77`, via `#un2` at `zkir-constraints.k:227`) and `#lowHighIC2`'s "low operand uses byte 31" / "high operand is not a byte" (`zkir-constraints.k:346-347`).
- Rust: `inv_incircuit` for Native calls `NativeChip::inv` (`circuits/field/native/native_chip.rs:960-968`): `assign_with_shifted_inverse` then `assert_equal(x, y)` — the relation `x * inv = 1` is unsatisfiable at 0, a constraint failure, not a synthesis error; the foreign `FieldChip::inv` says so explicitly (`circuits/field/foreign/field_chip.rs:996-1000`). `Bytes32FromLowHigh` (`ir_vm.rs:1146-1148`) emits `assert_equal_to_fixed(bytes_low[31], 0)` and `convert(high)` (a byte range constraint, `native_gadget.rs:786-800`), again unsatisfiable, not unbuildable.
- Reproduced: `t3` (`inv %a`, `%a = 0`) gives `synthErr: inv output (a * inv = 1): cannot invert zero of type Native`; `t4` (`bytes32_from_low_high` with `%lo = 2^248`, `%hi = 1`) gives `synthErr: ... low operand uses byte 31`. Both should be `violated`. The gate label even says "(a * inv = 1)" (`zkir-constraints.k:218`) but the outcome contradicts it.
- Why it matters: the divergence tests key on the outcome kind, and `synthErr` is documented (`zkir-constraints.k:16-18`) as "the circuit cannot be built". A reader of the verdict list would conclude that `inv` of zero has no circuit, when the circuit exists and rejects the witness.
- Fix: give the in-circuit evaluators a third result constructor (e.g. `vUnsat(String)`) distinct from `vErr`, mapped to `violated` in `#matches`; or evaluate `inv` as `#and(#nonZero(rd(A)), #matches(...))` and check `BL[31] ==Int 0` / `fitsBits(H, 8)` as `violated` before calling `#lowHighInCircuit`.

### 3. major — Spurious `violated` verdicts and wrong absolute indices for `impact` after a witness failure

Two related defects in the pi bookkeeping the brief asks about.

(a) `semantics/zkir-constraints.k:150` `#piEq(I, _, _, Pi) => violated("public input index ... out of range") requires I >=Int size(Pi)`. When the witness has failed, `<pi>` is frozen (`zkir-vm.k:14-15`), so every impact emitted after the failure whose guard and inputs are still readable is reported as **violated**, not **unknown**. Reproduced: `t1` (`assert %z` with `%z = 0`, then `impact 1 [%a]`) yields `violated: public input index 1 out of range <- piGate(1, imm(1), var("%a"))`. In Rust the impact cell would simply be pushed (`ir_vm.rs:869-881`); nothing about it is violated. Fix: return `unknown("public input vector incomplete: witness stopped")` when `I >= size(Pi)`, or thread `<status>` into `verdicts`.

(b) `semantics/zkir-vm.k:151-159`: `#piGates(size(Pi) +Int D, G, Xs)` is emitted before `#exec`, and `<deadPis>` is incremented only by the rule at line 158, which fires only when `<status>` is already `error`. When the impact **itself** fails (non-boolean guard at `zkir-vm.k:409`, non-native or missing input at `415-418`), neither `<pi>` grows nor `<deadPis>` is incremented, so the next impact reuses the same indices. Reproduced: `t2` (`impact %g [%a]` with `%g = 2`, then `impact 1 [%a]`) emits `piGate(1, var("%g"), var("%a"))` and `piGate(1, imm(1), var("%a"))` — both at index 1; the circuit (`ir_vm.rs:876-880`) would use indices 1 and 2. Fix: add `lenOperands(Xs)` to `<deadPis>` in the `#fail` paths of `#impact`/`#impactPush`/`#impactNatives`, or compute the index from a dedicated `<piIdx>` counter incremented at emission time (the comment at `zkir-vm.k:145-150` already suggests this).

### 4. major — Off-circuit `test_eq` accepts `JubjubScalar == JubjubScalar`; the crate rejects it on both sides

- K: `semantics/zkir-ops.k:103-105` `testEqV(A, B) => vOk(native(bool2Word(A ==K B))) requires sameType(A, B)` — any same-type pair, including `jubjubScalar`. The constraint side is right (`zkir-constraints.k:181` gives `synthErr` for the JubjubScalar pair), so the K reports `ok` off-circuit with a `synthErr` gate, i.e. it reports a finding-7-shaped divergence that does not exist.
- Rust: `ir_instructions/eq.rs:42-66` `test_eq_offcircuit` matches Native, Bytes32, JubjubPoint and the nine foreign types; JubjubScalar falls to `Err("Unsupported test_eq: JubjubScalar == JubjubScalar")`. `test_eq_incircuit` (`eq.rs:86-133`) has the same list.
- Reproduced: `t5` (`test_eq %s %t`, two `Scalar<Jubjub>` inputs 5, 5): K `ok`, `zkir-oracle` `error Unsupported test_eq: JubjubScalar == JubjubScalar`. The differential corpus has no `test_eq` on JubjubScalar, which is why the 314 agreeing comparisons did not catch it (the handmade "every instruction on every type it supports" program presumably follows the doc list, which omits JubjubScalar, `ir.rs:729-741`).
- Fix: `testEqV(jubjubScalar(_), jubjubScalar(_)) => vErr("Unsupported test_eq: JubjubScalar == JubjubScalar")` before the generic rule; add the case to `tools/gen_handmade.py` negatives. (`constrainEqV` and `selectV` are type-generic in Rust too, so they are correct as written.)

### 5. major — `less_than` with `bits` in {253, 254} is accepted by K and by `preprocess` but panics at keygen; the K gate says `holds`

- K: WF accepts `bits < 255` (`semantics/zkir-syntax.k:304-305`; the comment at `zkir-syntax.k:237-238` claims "less_than at most 248", which the rule does not implement). The gate (`zkir-constraints.k:236-239`) checks `#bits(a, #ltBits(N))` with `#ltBits(N) = max(N + N mod 2, 4)` and `#bits` returns `holds` for any `N < 255` when the value fits.
- Rust: `ir_vm.rs:966` `std.lower_than(a, b, max(bits + bits % 2, 4))` → `stdlib/lib.rs:889-899` `bounded_of_element(n)` → `circuits/field/native/native_gadget.rs:338-344` `assert!(n <= MAX_BOUND_IN_BITS)` with `MAX_BOUND_IN_BITS = F::NUM_BITS - 2 = 253` (`native_gadget.rs:330`). For `bits = 253` or `254`, `n = 254` and synthesis panics (`cfg(not(test))`), at keygen as well as at proving. Off-circuit (`ir_vm.rs:454-462`, `resolve_operand_bits` at `ir_vm.rs:268-270`) only rejects `bits >= 255`.
- Reproduced: `t7` (`less_than` with `bits: 253` on inputs 1, 2): K `ok`, all gates `holds`; `zkir-oracle` `ok`. The real prover cannot build this circuit. This is a finding-10-class divergence (source-level robustness, `preprocess` accepts what keygen cannot build) that the review does not list and the K hides.
- Fix: in `#ltBits`/`eval(gate(lessThan ...))` return `synthErr("less_than: bound " ... " exceeds MAX_BOUND_IN_BITS = 253")` when `#ltBits(N) > 253`; decide whether WF should reject `bits > 252` (then fix the comment at `zkir-syntax.k:237`), and add a divergence case. Report upstream as a candidate finding.

### 6. minor — `synthErr` collapses three distinct Rust behaviours, and the vocabulary has no place for the panics the review is about

- K: `zkir-constraints.k:16-19` define `synthErr` as "no arm for these types (Error::Synthesis) or a chip … not initialised".
- Rust: a missing dispatch arm returns `Error::Synthesis` (e.g. `ir_instructions/select.rs:115-119`); a missing chip **panics** (`stdlib/lib.rs:753, 765, 774, 783, 800`); chip-internal bounds are `assert!`s (finding 5 above); the Curve25519 `point_from_coordinates` hint returns `Error::Synthesis("invalid coordinates")` when the values are known (`circuits/ecc/foreign/edwards_chip.rs:1093-1097`) while the Weierstrass hint uses `unwrap_or(identity)` and lets the constraints fail (`weierstrass_chip.rs:930-936`); the Jubjub and Curve25519 hints panic on on-curve-off-subgroup input (`circuits/ecc/native/edwards_chip.rs:792-796`, foreign `edwards_chip.rs:1094`).
- Consequence for the tests: `f11` (`tools/divergence_tests.py:104-109`) is labelled "Finding 11" but finding 11's open half is the witness-hint panic; the K reports `violated`, which is the constraint-level truth and not what the crate does. `t8` (off-curve Curve25519 coordinates) likewise gives `violated` where `circuit()` returns `Err(Synthesis)`. The page (`wiki/zkir/zkir-k-definition.md:38-40`) does not say that panics and chip-internal asserts are outside the model.
- Fix: either add an outcome `panics(String)` used for the known hint/accessor panics (they are decidable from the same values the checker already has), or state in `zkir-constraints.k` and on the wiki page that `synthErr`/`violated` describe the constraint system and that prover-side panics are not modelled.

### 7. minor — Chip gating is exact but the review's premise it encodes is incomplete: `jubjub_scalar_from_native` is a fresh JubjubScalar entry

- K `usedChips` (`zkir-constraints.k:42-66`) matches `used_chips` (`ir_vm.rs:1212-1263`) case by case: input and `PublicInput`/`PrivateInput` types, `HashToCurve` → jubjub + poseidon, `TransientHash` → poseidon, `PersistentHash` → sha2_256, `Keccak256` → keccak_256, commitment → poseidon. Treating a missing chip as `synthErr` is a fair model of the `panic!` in the accessors (the circuit is never built), subject to finding 6.
- Because the K checks the chip per operand value, it already reports what the review's finding 13 (docs review lines 574-577: "FromBytes32 … is the only such fresh entry") misses: `JubjubScalarFromNative` mints a JubjubScalar from a Native and its circuit arm calls `std.jubjub()` (`ir_vm.rs:975` → `ir_instructions/encode.rs:232`), and `EcMulGenerator` then calls `std.jubjub().assign_fixed` (`ir_vm.rs:1068`). Reproduced: `t6` (`jubjub_scalar_from_native %a; ec_mul_generator %s`): K `ok` off-circuit, gates `synthErr: chip not initialised for JubjubScalar`; `zkir-oracle` `ok`. Keygen would panic with "ZkStdLibArch must enable jubjub".
- Fix: add a divergence case (`k03`) and record it as a candidate finding next to K1/K2; tell the review authors that finding 13's "only" is wrong. Nit: `eval(gate(bytes32FromLowHigh ...))` (`zkir-constraints.k:338`) has no `#chipsForValues` on `L` although `into_bytes32_incircuit(low)` uses the foreign chip (`ir_vm.rs:1145`); unobservable today because a foreign `L` implies an earlier gate that already reports the chip.

### 8. minor — Several divergence cases do not test what their notes claim, and the harness accepts vacuous passes

- `f04` (`tools/divergence_tests.py:63-67`): expected outcome `unknown` because `%lt` is absent. The note's claim "the chip would accept the padded 4-bit bound" is never evaluated; `unknown` would also result if the range check were wrong. `f01` (`:140-145`) same shape ("in circuit the sum would wrap mod r" is not checked). Fix: when only the **output** register is missing but the inputs are present, report a distinct outcome (e.g. `satisfiable(expected)`) that carries the value the circuit would force; then `f04` can assert `satisfiable(1)`.
- `f05` tests `add`, not the commitment (finding 1 above). `f02`/`f04` are labelled "Finding 2"/"Finding 4" although the review retired them (docs review lines 66-67, 111-113); only `f01` says "retired" (`:140`). The wiki (`wiki/zkir-k-semantics-plan.md:79`) says "findings 1 to 8 and 10 to 13" without the retirements.
- `tools/divergence_tests.py:184` `outcome = 'holds' if any(gate_sub in g for g in [gate_sub]) else 'holds'` is a tautology: an expected `holds` passes even if the gate was never emitted or the substring is wrong. `:179` matches the substring against violations only, so `f02`/`f03`/`f05` never look at the actual verdict. Fix: return all verdicts from `Runner.run` and look the gate up by constructor, failing if absent.
- `k02` (`:133-138`) accepts any non-zero oracle exit as "panics"; assert on `panicked at zkir-v3/src/ir_vm.rs:379` in stderr (the run shows exactly that). `f10` accepts any `wfError`; assert on the message.
- `evidence/zkir-k-divergence-tests-2026-09-05.txt` records 13 cases and no `k02`; the tool now has 14 (this run: 14/14). The receipt and `wiki/zkir-k-semantics-plan.md:79` ("13 of 13") are stale.

### 9. minor — `eval(gate(_)) => holds() [owise]` makes any unmodelled instruction hold silently

`semantics/zkir-constraints.k:385`. Today every ZKIR instruction and every ZKIR-EXT instruction has a rule (`zkir-ext.k:254-262`), so nothing falls through, but the default should be `unknown("no in-circuit relation for ...")` so that a future instruction cannot pass by omission. Similarly `eval(gate(output(_)))` (`:384`) could check arity and types against `<outTypes>` as `ir_vm.rs:1151-1167` does; today an `output` arity error is only visible through the witness status.

### 10. nit — K1 and K2 are real and correctly attributed; two wording points

- K1 (`tools/divergence_tests.py:125-131`, `wiki/contradictions.md:46`): confirmed. `from_coordinates_offcircuit` (`ir_instructions/from_coordinates.rs:42`) resolves `JubjubExtended::from_xy` to the `CircuitCurve` impl (`circuits/ecc/curves.rs:117-131`), which compresses `(y, x mod 2)` and decompresses — the FIXME there admits it. The test note says "in-circuit (x, y) must lie on the curve"; more precisely, the circuit pins `(x, y)` to the coordinates of the decompressed, cofactor-cleared point.

## Coverage gaps

- No divergence case emits `impact`, so the pi index bookkeeping (finding 3) was untested; no case runs with `do_communications_commitment: true` (finding 1).
- No case for `inv` of zero, `bytes32_from_low_high` with a bad `low`/`high` value, `less_than` with `bits` in 249..254, `constrain_bits`/`reconstitute_field`/`div_mod_power_of_two` at the WF boundary (`bits = 248`, `bits = 254`).
- Chip gating is exercised only through `from_bytes32`; not through `jubjub_scalar_from_native`, nor the hash chips (these cannot fail by construction, worth one positive case).
- `encode` on JubjubScalar (the extra `assert_zero`, `ir_instructions/encode.rs:98-108`) and `encode` on every foreign type have no constraint-side test beyond the differential corpus.
- `from_coordinates` on Jubjub with on-curve-off-subgroup input, and on secp256k1/secp256r1 with off-curve input (the `unwrap_or(identity)` path), are not covered.
- `public_input`/`private_input` gates are tested only on Native. For JubjubScalar the circuit assigns 255 unconstrained-canonicity bits (`circuits/ecc/native/edwards_chip.rs:877-889`, `enforced_canonical: false`) while `decode_offcircuit` demands a canonical 252-bit scalar; the K `#typed` check cannot see this (soundness direction). Not a K completeness defect, but the abstraction hides it and the page should say so.
- The extension surface (`zkir-ext.k`) has no divergence tests at all.

## Questions for the authors

1. Was the commitment constraint left out of the constraint model deliberately (it needs the opening randomness and the output list at verdict time), or is it an oversight? Finding 5 is the review's only confirmed prover-facing completeness gap and it is currently untestable.
2. `zkir-syntax.k:237` says `less_than` is bounded by 248 like `div_mod_power_of_two`; the rule uses 255. Which bound did you intend, and were you aware of `MAX_BOUND_IN_BITS = 253`?
3. Is the `jubjub_scalar_from_native` chip-gating gap known to the arc-zkir authors? Finding 13 asserts `FromBytes32` is the only fresh entry.
4. Should `synthErr` be split so that the review's panic/Error distinction (blast-radius "prover" vs "dev") survives into the verdicts?
5. Is the JubjubScalar input canonicity slack (255 assigned bits, no `< r_J` check in circuit) covered by an Agda side condition, or is it a soundness-direction candidate for the review?
