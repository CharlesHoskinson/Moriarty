# Review R4: K engineering quality, extension surface, tooling and documentation

VERDICT: WARNING — the 92e8bdd3 definition agrees with the crate on everything the harness compares, but ZKIR-EXT diverges from midnight-zkir 2ffe2d1 on `test_eq` over byte strings, ZKIR-VM runs without the static checks it relies on (accepting programs the crate rejects and getting stuck on one shape), the harness reports a stuck configuration as `ok`, the preprocessor is not the serde mirror the wiki says it is, and several wiki claims are not backed by the receipts.

## 1. Findings

### F1 (major) ZKIR-EXT: `test_eq` on byte strings of unequal length errors in K, returns 0 in the crate

- `experiments/zkir-k/semantics/zkir-ext.k:64` — `rule typeOf(bytesV(B)) => bytesT(lengthBytes(B))`; `zkir-ext.k:61` keeps 32-byte strings as `bytes32(_)` with `typeOf` = `bytes32()`.
- `experiments/zkir-k/semantics/zkir-ops.k:104-105` — `testEqV(A, B)` returns `vOk(native(...))` only when `sameType(A, B)`, otherwise `vErr("Unsupported test_eq: ...")`. So `Bytes<2>` vs `Bytes<3>`, and `Bytes<32>` vs `Bytes<3>`, are errors in K.
- Source of truth: `midnight-zkir/zkir/src/ir_instructions/eq.rs:50` at 2ffe2d1, `(Bytes(xs), Bytes(ys)) => Ok(xs == ys)` — the off-circuit `test_eq` matches on the variant, not the length, and returns `false`.
- Verified with the 2ffe2d1 oracle (scratch probe `ext.py`): program `test_eq %a:Bytes<2> %b:Bytes<3>` with inputs `[258, 197121]`: K `status=error "Unsupported test_eq: Bytes == Bytes"`; Rust `status=ok`, `%e = Native 0`. Same for `Bytes<32>` vs `Bytes<3>`.
- Why it matters: any 2ffe2d1 program comparing byte strings of different declared lengths (a Compact `Bytes<n>` equality against a hash output, for instance) has a witness in the crate and none in K. In-circuit the crate does fail synthesis for unequal lengths (`eq.rs:107` guard, `eq.rs:47` fallthrough), so this is also a new off-circuit/in-circuit divergence in the 2ffe2d1 crate itself, in the style of K1/K2, worth reporting upstream (see Q3).
- `constrain_eq` is not affected: `constrain_eq.rs:45` compares `get_type()` (length-indexed), and K's `constrainEqV` does the same; probe `constrain_eq_bytes_2_vs_3` agrees on both sides.
- Fix: in `ZKIR-EXT-VALUES` add rules ahead of the generic one, e.g. `rule testEqV(bytesV(X), bytesV(Y)) => vOk(native(bool2Word(X ==K Y)))`, and the three `bytes32`/`bytesV` mixed cases; keep the gate's `#eqSupported` synthesis error for unequal lengths, which is the crate's in-circuit behaviour.

### F2 (major) ZKIR-VM never runs ZKIR-WF, so the VM relies on preconditions nothing enforces

`experiments/zkir-k/semantics/zkir-vm.k:87` — the `job` rule goes straight to `#loadInputs`; `wf(P)` is only ever called by the separate main module `ZKIR-CHECK` (`zkir-check.k:13`), which `tools/zkir_run.py`, `tools/diff_test.py` and the wiki's "run" never invoke. Four consequences, all verified against the 92e8bdd3 oracle (scratch probe `gap.py`):

1. `div_mod_power_of_two` with `bits` in 249..: `zkir-vm.k:301-305` (comment "bits <= 248 checked statically") computes the quotient and remainder; Rust `ir_vm.rs:399-400` bails "Excessive bit count". Probe `divmod_bits_250`: K `ok`, `%q=0 %r=5`; Rust `error`.
2. `reconstitute_field` with `bits` in 249..254: `zkir-vm.k:310-322` only checks `checkBits(MV, N)` and `checkBits(DV, 255 - N)` and the overflow; Rust `ir_vm.rs:418-419` bails "Excessive bit count" first. Probe `recon_bits_250`: K `ok` with a value in `%o`; Rust `error`.
3. `div_mod_power_of_two` with a number of outputs other than two: the only `#exec` rule is `zkir-vm.k:302` with the pattern `(Q, (R, .Ids))`; with one output no rule matches and the run halts with `<k> #exec(divModPowerOfTwo(var("%a"), 300, "%q", .Ids)) ~> .Instrs ~> #verdicts` and `<status> ok()`; `#verdicts` never runs (`verdicts=0`). Rust: "DivModPowerOfTwo requires exactly 2 outputs" (`ir_vm.rs:396-397`).
4. Reassignment: `zkir-vm.k:185` `#put(X, vOk(V))` does `M[X <- V]` unconditionally, as do `#put2`, `#bindEncoded` and `#divMod`. The header comment `zkir-vm.k:7` ("write-once"), plan decision CLM-0711 (`wiki/zkir-k-semantics-plan.md:123`, "a rule that writes an identifier already present in the map is an error") and `wiki/zkir/zkir-k-definition.md:56` ("rejected by K before the run") describe a design that was not built. The crate also overwrites (`ir_vm.rs:297-623`, plain `memory.insert`), so the witness agrees, but every gate that read the old value is then evaluated against the new one: probe `reassign` (`%b` bound twice) gives `violated` for the `add`, `copy` and `constrain_eq` gates where the crate merely fails the `constrain_eq`; probe `reassign_ext` gives Rust `ok`, K `ok` and a spurious `violated add output`. This is exactly why the spec makes O1 a producer obligation (§8.2), and why the definition should refuse such programs instead of producing meaningless verdicts.

Fix: make the `job` rule `job(P, Pre) => #wfGate(wf(P)) ~> ...` with `#wfGate(wfError(S))` setting `<status> error(S)` and dropping the program, or add the two dynamic bound checks mirroring `ir_vm.rs:396-401` and `418-419`, an `#exec(divModPowerOfTwo(_, _, Os))` error rule for `lenIds(Os) =/=Int 2`, and `requires notBool X in_keys(M)` (with an error rule) on `#put`/`#put2`/`#bindEncoded`.

### F3 (major) The harness reports a stuck configuration as `status: ok`

`experiments/zkir-k/tools/zkir_run.py:278-285` derives the status from `<status>` alone; `k_cell` is captured at line 295 and never inspected by `diff_test.py` or `divergence_tests.py`. In F2(3) the result is `{'status': 'ok', 'memory': {'%a': ...}, 'verdicts': 0}`. `divergence_tests.py:184` then treats the absence of the gate in `violations` as `holds` (the expression `'holds' if any(gate_sub in g for g in [gate_sub]) else 'holds'` is a tautology), so a stuck run can satisfy an expectation of `holds`. Fix: `if out['k_cell'] != '.K': out['status'] = 'stuck'`, and make `divergence_tests.py` require `verdicts > 0` when it expects a gate outcome.

### F4 (major) The preprocessor does not "reject what `IrSource::load` rejects"

`wiki/zkir/zkir-k-definition.md:34` (CLM-0732) and the docstring of `tools/zkir_kast.py:1-14` claim a serde mirror. Verified against `IrSource::load` by feeding the oracle binary (which calls `IrSource::load`, `zkir-oracle/src/main.rs:73`) the same files (scratch probe `serde.py`):

| Case | zkir_kast.py | `IrSource::load` (92e8bdd3) | Source |
|---|---|---|---|
| Unknown field in an instruction (`"comment": ...`) | rejected (`_need`, `zkir_kast.py:163-169`) | accepted; preprocess ok | `ir.rs:357-358` derives `Deserialize` without `deny_unknown_fields` |
| Unknown field in an `inputs` entry | rejected (`zkir_kast.py:331`) | accepted | `ir.rs:168-174` |
| `public_input` without a `guard` key | rejected (`zkir_kast.py:289`) | accepted as `None` (serde `Option` default); preprocess then panics on the empty transcript (K2) | `ir.rs:874-889` |
| Immediate `"0x0x01"` | rejected | accepted as 1 (`const_hex::decode` strips a second prefix) | `ir.rs:225-228` |
| `"minor": 0.0` | accepted (`zkir_kast.py:323`, `0 <= 0.0 <= 0`) | rejected ("invalid type: floating point, expected u8") | `ir.rs:922-925` |
| `Bytes<01>` (ext mode) | accepted (`zkir_kast.py:64-68`, `isdigit()`; also accepts non-ASCII digits) | rejected ("invalid IR type") | 2ffe2d1 `ir_types.rs:176-186` rejects leading zeros |

The three `test_invalid_operand_*` corpus cases and the out-of-range immediates agree. The mismatch stayed invisible because `diff_test.py:147-149` skips format-rejected programs with the comment "rejected before preprocess by both sides" without asking the oracle, and `check_corpus.py` compares only against its own expectation table. In `--ext` mode the same skip silently drops `handmade/native_bytes.zkir` (it uses `reverse_bytes`): the ext receipt has 16 handmade lines where the base one has 18, and the wiki (`zkir-k-definition.md:61`) says "the handmade programs" without the caveat.

Fix: mirror serde (ignore unknown fields, default `guard` to `null`, use `int` type checks for `u8`/`u32`, reuse 2ffe2d1's canonical-string rule for `Bytes<n>`), and run every format-rejected program through the oracle so that loader disagreements are counted as failures.

### F5 (minor) ZKIR-EXT gate: `cond_select` on `Bytes<n>` (n ≠ 32) reported as `holds`

`experiments/zkir-k/semantics/zkir-constraints.k:182` marks only `bytes32 ? bytes32` as a synthesis error; a `bytesV`/`bytesV` pair falls to `#eqSupported(_, _, _) => holds() [owise]` (`:185`). At 2ffe2d1 `select.rs:10-45` (`select_incircuit`) has arms for `Native`, `Bool`, `Byte`, the points and the fields, and `_ => Err(Synthesis(...))` — no `Bytes` arm. Probe `cond_select_bytes3`: both sides `ok` off-circuit, K `violations=[]`. The oracle cannot detect this (it runs only `preprocess`), so it is a modelling gap in the constraint checker. Fix: `rule #eqSupported(vOk(bytesV(_)), vOk(bytesV(_)), "cond_select") => synthErr("Unsupported cond_select: Bytes ? Bytes")` in `ZKIR-EXT`.

### F6 (minor) Overlapping equal-priority function rules (nondeterministic by the K manual) and a vacuous catch-all

The manual (`k/docs/user_manual.md:1739-1746`) states that multiple `[owise]` rules "all have the same priority and thus can apply in any order". `kompile -w all` flags four of them as "Potentially useless rule":

- `zkir-constraints.k:196-197` — `#selBit(_, vOk(A), vOk(B)) ... [owise]` and `#selBit(_, _, _) => vErr("missing") [owise]`.
- `zkir-constraints.k:262` vs `:385` — `eval(gate(divModPowerOfTwo(_, _, _))) => synthErr(...) [owise]` and `eval(gate(_), _, _, _) => holds() [owise]`: for a `div_mod` gate with the wrong arity the two owise rules give `synthErr` and `holds` respectively.
- `zkir-ext.k:190-191` (`#boolFold`) and `zkir-ext.k:202-203` (`#concat`): the `ListItem(V:Value) _` and `ListItem(_) _` owise pairs overlap on every `Value`.

Not flagged by kompile but of the same kind: `zkir-syntax.k:282-285`, the two `#checkArity(divModPowerOfTwo(...))` rules are both priority 50 and both apply when the output count is not two and `bits > 248`; observed result "excessive bit count" whereas the crate reports the output-count error first (`ir_vm.rs:396-401`).

The catch-all `eval(gate(_), _, _, _) => holds() [owise]` at `zkir-constraints.k:385` is a soundness hazard for oracle 2: any instruction without an `eval` rule is vacuously satisfied. Today every base and ext instruction has one, so it is reachable only through the `div_mod` arity case, but a future instruction added to `ZKIR-SYNTAX` without an `eval` rule would report `holds` silently. Fix: delete the catch-all (the function is total without it once `output` and `piFixed` keep explicit rules), add `requires lenIds(Os) =/=Int 2` to the `div_mod` owise rule and drop its `[owise]`, and collapse each owise pair into one rule.

### F7 (minor) Totality declarations and fallback values

`kompile -w all` on `zkir-ext.k` (superset) emits 42 warnings: 8 "Non exhaustive match detected" on `[function, total]` symbols (`zkir-values.k:106 #decForeign`, `zkir-ops.k:199 asNatives`, `:214 #alignedBytes`, `:231 #bffr`, `zkir-hash.k:60 absorbAll`, `:169 #shaOut`, `zkir-ext.k:98 #decChunks`, `:125 #sha512Out`), 27 unused variables (e.g. `zkir-values.k:111` five of seven arguments, `zkir-vm.k:318 O`), 3 unused symbols (`alignments`, `.alignments` at `zkir-syntax.k:78`, and `<zkir>`), plus the 4 useless rules of F6. By inspection the eight functions are total on well-sorted lists (the warning is the checker's list-shape complaint), but `#bffr` is undefined for a negative `Stray` and the `total` attribute is precisely what the Haskell backend uses to assume definedness (manual `:546-552`), so false totality would be a proof-soundness issue, not a runtime one. Several functions are made total by returning a wrong value instead of an error: `#wrapPoint(_, _) => native(0) [owise]` (`zkir-values.k:222`), `#wrapField(X, _) => native(X) [owise]` (`zkir-ops.k:98`), `#svdwSign(_, X, noSqrt()) => pt(X, 0)` (`zkir-hash.k:131`), `#int(_) => -1` (`zkir-constraints.k:142`), `ecMul(C, _, K) => identity(C) requires K <=Int 0` (`zkir-curves.k:124`), `#bindEncoded((_, _), .List) => .K` (`zkir-vm.k:278`). A type confusion upstream of these would surface as a plausible field element rather than a stuck term. Fix: return result sorts (`ValueResult`/`PointResult`) or leave the function partial; compile the definitions with `-w2e` in the toolchain check so the warning list cannot grow silently.

### F8 (minor) `option` alignment segments are parsed by the preprocessor and rejected at run time, while the crate evaluates them

`zkir-ops.k:221` — `#alignedBytes((option(_), _), _, _) => bErr("unsupported: alignment option segment")`. `zkir_kast.py:143-150` builds the `option(...)` term, so such a program passes the static check and fails only when the hash executes. Rust `parse_field_repr` handles options (`base-crypto/src/fab/encoding.rs:267-278`): probe `opt.py`, `persistent_hash` with alignment `[option [[field], [bytes 4]]]` and inputs `[0, 5]` / `[1, 5]`, gives a hash on the Rust side and `error` in K. No corpus program uses an `option` segment or a `compress` atom (grep over `corpus/` and the escrow/swap artifacts), so the gap is untested; it is also unstated in `wiki/zkir/zkir-k-definition.md:29` ("aligned byte layout for the standard hashes"). `compress` atoms fail on both sides with "Inputs did not match alignment" (agrees).

### F9 (minor) Proof readiness on the Haskell backend

Facts established in the scratch directory `r4-haskell` (`kompile --backend haskell`, 22 s, same warnings as LLVM):

- Concrete runs agree with LLVM: `test_minimal_proof.zkir` 2.4 s; `handmade/native_bytes.zkir` (Poseidon, hash-to-curve, SHA, Keccak, curve ops) 10.8 s vs 0.75 s on LLVM, identical status, 34 constraints, 34 verdicts. The List/Map/Set idioms used (`ListItem(X) Rest`, `in_keys`, `M[X]`, `M[X <- V]`, `range`, `size`, `Fs[4] ==K 1`, `<=Set`) behave the same on both backends.
- A claim over one `add` with a symbolic input proves (`r4-spec2.k`, `#Top`, 10.6 s) once every one of the 17 cells is pinned. The same claim with unmentioned cells (`r4-spec.k`) gets stuck at `#bind(L)` because `<strictDecode>` is abstracted to a variable and `decodeStrict(ListItem(A), native(), _Gen32)` cannot pick a rule. The harness and extension state living inside the semantic configuration (`<genMode>`, `<needs>`, `<deadPis>`, `<strictDecode>`, `zkir-vm.k:68-71`) therefore has to be mentioned in every claim.
- A claim over `transient_hash` with a symbolic input (`r4-spec3.k`) does not finish in 7 minutes: kore-exec unfolds `poseidonHash` (all hash functions are `[function, total]` with concrete defining rules and no `[concrete]` guard, `zkir-hash.k:33-80`) and emits repeated `DecidePredicateUnknown` while applying the `modInt` equation of `domains.md:1376`. This confirms the plan's own warning (`zkir-k-semantics-plan.md:156`, CLM-0721) but nothing in the definition implements it.
- What blocks claims: (a) hashes must become uninterpreted for symbolic arguments — mark the defining rules `[concrete]` (manual `:1462-1500`) or split each hash into an abstract symbol plus a concrete-evaluation rule; (b) `modInt`/`^%Int` over symbolic terms needs `simplification` lemmas (`fadd`, `fmul`, `finv` in `zkir-field.k:43-49` are otherwise opaque to the SMT solver); (c) the projections `{M[X]}:>Value` (`zkir-vm.k:164`, `zkir-constraints.k:98`) and `{Fs[4]}:>Int`-style casts generate `#Ceil` side conditions; (d) the `job(P, Pre) => job(P, Pre)` priority-30 rule in `zkir-ext.k:120-121` is a rewrite step that changes only `<strictDecode>` — with a symbolic flag it branches; a configuration variable (`$STRICT`) or an EXT-specific initial configuration would avoid it; (e) the string-dispatched `#bin`/`#un` (`zkir-vm.k:200-226`) add a case split per string literal in symbolic execution.

### F10 (minor) Static checks versus the spec's producer obligations

`ZKIR-WF` (`zkir-syntax.k:216-288`) checks: minor version 0; distinct input names and single assignment (O1); define-before-use (WF4, which the spec makes an invariant P4 rather than a check); immediate range (serde-level, dead for JSON-sourced programs because `zkir_kast.py:88-98` already rejects them); `output` arity and `div_mod_power_of_two` arity (part of WF3); the WF2 bit bounds exactly as O3 states them (`bits < 255` for `constrain_bits`/`less_than`, `bits <= 248` for `div_mod`/`reconstitute`). Differences from §8.2/§5.3 of `docs/zkir-v3-spec.md`:

- O2 (value typing per Appendix B, and no `constrain_eq`/`test_eq` on `JubjubScalar`) is not checked statically; K discovers it at run time (`vErr`) and in the gate (`synthErr`, `zkir-constraints.k:180-181`). This is the obligation P5(b) and statement soundness rest on, so the K checker is strictly weaker than `producer-WT?`.
- WF3's `encode` arity is deferred to run time (`zkir-vm.k:271-272`), the spec lists it as structural.
- Nothing in the K checker is stronger than the spec; the two serde-level checks are outside the spec's list.
- The check exists only as the separate main module `ZKIR-CHECK`; there is no `ZKIR-EXT` check module, so the 2ffe2d1 surface is never statically checked, and `check_corpus.py:33-39` runs neither the handmade positives nor the ext test corpus.

### F11 (minor) What a green test run does and does not establish

- `diff_test.py:98-116` compares status, register variants and encodings, `pis` and `pi_skips` on the compared preimages. It does not compare error messages (only a note; the ext receipt has three message families beyond hex-vs-decimal: "Failed to decode [Fq(...)] as Native", "slice out of bounds: 2..2+3 into Bytes<4>", "nth out of bounds: index 2 into Bytes<2>"), cursors, outputs, or the constraint verdicts (`vnote`, line 176, is printed; `failures` is unaffected). CLM-0729 "all gates hold on every successful run" is true of the receipts (I count 0 `NON-HOLDING` among the 37 and 40 `K=ok Rust=ok` lines) but is not asserted by any tool.
- Only 31 of the 62 base programs and 26 of the 58 ext programs reach a successful witness. The 19 crate tests that never do are the richest ones: `test_secp256k1_proof`, `test_secp256r1_proof`, `test_curve25519_proof`, `test_bytes32_proof`, `test_bytes32_low_high_proof`, `test_coordinates_proof`, `test_reverse_bytes_proof`, the three `*_bytes32_proof`, `*_coordinates_proof`, `*_ec_mul_proof` and `*_point_constrain_eq_fails_on_unequal` programs and `test_jubjub_point_ops` — because `extract_test_inputs.py:12-14` skips preimages with computed values and random inputs fail their assertions. For those the run compares error paths only (up to eight per program). In ext mode `concat`, `slice`, `nth`, `reverse` and `load_constant` never appear in a successful run (`test_bytes_concat_and_nth`, `test_bytes_slice`, `test_constant_proof`, `test_bytes_n_proof` all fail); only `and`, `or`, `xor`, `sha512` and `neg` on `Bool` do.
- Flakiness: seeds are deterministic (`random.Random(f'{seed}:{path.name}')`, `diff_test.py:150`). The oracles are binaries at hard-coded `$HOME` paths built from uncommitted worktree changes (`repos/_build/*/zkir-oracle` untracked; the `ir_vm.rs` patch is the one-line `pub(crate) fn preprocess` → `pub fn preprocess` in both worktrees, verified), so the receipts cannot be regenerated from the repository. A missing or broken oracle fails every comparison loudly except divergence case `k02`, whose expected Rust status is `oracle-failed` (`divergence_tests.py:137`) and which would pass spuriously. `extract_test_inputs.py` rewrites `corpus/ledger9-92e8bdd3-tests/manifest.json` in place. `unit_values.py:168` (`fsqrt 4`) compares the K output with itself; `unit_hash.py:116` ("sha256 bytes(32) alignment vs hashlib") tests the oracle, not K.

### F13 (nit) Idioms

- String dispatch: `#bin(_, _, "add")` etc. (`zkir-vm.k:200-209`, `218-226`, `353-363`; `zkir-constraints.k:199-207`, `224-230`; `#boolGate` in `zkir-ext.k:181-192`) with `[owise] vErr("unknown ... op")` fallbacks turn a misspelled literal into a run-time error; an `Op` sort with constructors would make it a kompile error.
- `symbol(_)` names: instructions reuse JSON `op` names (`assert`, `and`, `or`, `not`, `copy`, `output`), types reuse JSON type keys (`Bool`, `Byte`, `Native`), values take a `V` suffix — consistent and collision-free (kompile would reject duplicates), but `Bool`/`Byte` shadow sort names in pyk-facing code and `ok`/`error`/`unknown`/`holds` are generic enough to clash with a future import.
- `typeName(bytes32()) => "Bytes32"` is not overridden in `ZKIR-EXT` (`zkir-ext.k:70-72`), so 2ffe2d1-mode error texts say `Bytes32` where the crate says `Bytes<32>`; `zkir_run.py:198` patches the variant name on the Python side instead.
- `#immInts((var(_), Es)) => #immInts(Es)` (`zkir-ext.k:229`) silently drops a variable in a `load_constant` encoding (unreachable from JSON, since the preprocessor rejects it, but wrong for hand-built terms). `#concat` (`zkir-ext.k:197-204`) lacks the `MAX_BYTES_LEN` bound the crate enforces (2ffe2d1 `ir_vm.rs`, "Concat result length ... exceeds MAX_BYTES_LEN").
- `<deadPis>` (`zkir-vm.k:145-159`) is an admitted approximation of a public-input index cell.
- `gen_handmade.py:120` — `programs['transcripts'][0]['inputs'] and [('%a', NATIVE)]` is a no-op expression.

## 2. ZKIR-EXT layering: what is sound and what 2ffe2d1 changed that the extension does not model

Sound as built: the priority-30 `job`/`genJob` rules set `<strictDecode>` before the base rule reads it (`zkir-ext.k:120-121`, `zkir-vm.k:87-88`); `negV(boolV(B))` matches `neg.rs:50`; `load_constant` decodes with `decodeStrict(_, _, true)` and the preprocessor mirrors the `constant_encoding` serde (immediates only); the canonical-form check matches `encode.rs:237-248`; `sha2_512` chip gating matches `ir_vm.rs` (`sha2_512: involves_instructions(Sha512)`); `encodedLen(bytesT(N))` matches `div_ceil`; `mkBytes` keeps the invariant that `bytesV` never holds 32 bytes, so `Bytes<32>` values from `concat`/`slice`/`reverse`/hashes are `bytes32(_)` and every base rule applies.

Not modelled or wrong: `test_eq` on byte strings of unequal length (F1); in-circuit `cond_select` on `Bytes<n>` (F5); the `Bytes<n>` canonical type-string rule (F4); `MAX_BYTES_LEN` on `concat` (F13); the 2ffe2d1 error texts for `into_bytes32`/`from_bytes32`/`bytes32_*` on non-32-byte strings ("expected a Bytes<32> value, got Bytes<n>"). The aliasing itself is what produces F1 and F5: with `typeOf` length-indexed for `bytesV` but a distinct `bytes32()` for 32 bytes, "same type" no longer coincides with the crate's `get_type()` equality in exactly the places where the crate does not use `get_type()`.

## 3. Coverage gaps

- Instructions on types never reached by a successful run: `add`/`mul`/`neg`/`inv`/`into_bytes32`/`from_bytes32`/`test_eq`/`constrain_eq`/`cond_select` on the three foreign scalar fields; `cond_select` on `Bytes<32>` and on any base field; `from_bytes32` into scalar types; `into_coordinates` of a Weierstrass identity; `ec_mul` by 0 or by the group order; `test_eq`/`constrain_eq` on `Scalar<Jubjub>` in a program that also succeeds (f07 covers the gate only).
- Ext: `concat`, `slice`, `nth`, `reverse`, `load_constant` never in a successful run; `Bytes<n>` for n ∉ {2, 3, 4, 6, 32, 48} (the `Bytes<1>`, `Bytes<31>`, `Bytes<33>` chunk boundaries are untested); `sha512` over more than one block; `and`/`or`/`xor` with a non-`Bool` input; `load_constant` of a point or foreign-field constant.
- Alignments: `option` segments (F8), `compress` atoms, `bytes` atoms with length 0 or > 31 that is not a multiple of 31 in combination with a `field` atom, empty alignments.
- Error paths not exercised: `Bytes32 decoding assertion failed` through a transcript (only via `unit_values`), `Expected communications commitment` and `Communications commitment mismatch` (the generator always supplies a matching commitment), `Transcripts not fully consumed` with a surplus in each of the three streams separately, `public_input`/`private_input` with a guard that is not boolean, `impact` with a non-native input, `less_than` on non-native operands, `encode` of a value whose length does not match, `reconstitute_field` overflow by exactly one.
- Preimage shapes: transcripts longer than needed (surplus), non-canonical foreign limbs with a high limb above 2^62 (only f05 with a small excess), a `Bytes<32>` transcript element with byte 31 non-zero in the low element, a Jubjub point given as (x, y) with y ∉ curve.
- Static check: no negative case for `less_than`/`reconstitute_field`/`div_mod` bit bounds in `check_corpus.py` (only `constrain_bits`), no ext program ever statically checked (F10).
- Both crates: `test_eq` on unequal-length byte strings as an off-circuit/in-circuit divergence at 2ffe2d1 (F1) is not in the divergence suite.

## 4. Questions for the authors

1. Is `ZKIR-VM` intended to be run only on programs that passed `ZKIR-CHECK`? If so, why is the composition left to the caller, and should the VM be documented as partial on ill-formed programs rather than "write-once"?
2. Are `option` alignment segments in scope? Compact emits them for `Maybe`/enum-typed hash inputs; if they are expected in the escrow/swap artifacts of later compiler versions, the K `persistent_hash`/`keccak256`/`sha512` are incomplete.
3. Is the 2ffe2d1 behaviour of `test_eq` on unequal-length byte strings (off-circuit `false`, in-circuit synthesis error) known to Midnight? It is a new divergence of the K1/K2 kind and would belong in the divergence review and in `contradictions.md` once confirmed.
4. What is the intended contract of the constraint checker for programs that violate O1? Reporting `violated` on a program the crate accepts (probe `reassign_ext`) is defensible only if the definition first states that O1 is a precondition.
5. Was any attempt made to profile `krust kcompile` (for example on `zkir-syntax.k` alone) before concluding "performance of its frontend pipeline"? Without it CLM-0740 is a guess.
6. Should the harness fail on any non-holding gate in a successful run, so that CLM-0729 becomes an asserted property rather than an observation in a text file?
