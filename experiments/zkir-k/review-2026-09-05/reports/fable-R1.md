# Review R1: fields, curves, values, encodings and hashes

VERDICT: APPROVED — every constant, group law, encoding and hash primitive in scope agrees with midnight-curves 0.3.1, midnight-circuits 7.2.4 and the crate at 92e8bdd3 on all inputs I could construct, including adversarial ones; the findings below are modelling-boundary and test-hygiene issues, none of them a wrong value.

## 1. Findings

### F1 (minor) — ZKIR-TEST is kompiled from a stale `zkir-values.k`; the unit receipts do not cover the current source

- `experiments/zkir-k/semantics/zkir-test-kompiled/timestamp` is 2026-09-05 12:12:07; `experiments/zkir-k/semantics/zkir-values.k` was last written 13:00:04 (the ZKIR-EXT milestone added `decodeStrict`, `#canonical` and the `Strict` argument of `decodeInputs`, zkir-values.k:224-251). `zkir-kompiled` and `zkir-ext-kompiled` (13:00:23, 13:00:46) are fresh.
- Consequence: `evidence/zkir-k-unit-values-2026-09-05.txt` and `evidence/zkir-k-unit-hash-2026-09-05.txt` were produced by `tools/unit_values.py:20` / `tools/unit_hash.py:25` against a definition that predates the file they claim to test. `decodeStrict` is absent from that definition (`KeyError: 'decodeStrict: []'` from the same `resolve` helper the tools use). The 41/41 and 18/18 results still hold because none of the tested functions changed, but the receipt cannot be cited for the current `zkir-values.k`, and nothing unit-tests `decodeStrict`/`#canonical` (they are covered only indirectly by the 2ffe2d1 differential run).
- Fix: rekompile `zkir-test.k` (with `--emit-json`) before regenerating the receipts, make `unit_values.py`/`unit_hash.py` refuse to run when any `semantics/*.k` is newer than `zkir-test-kompiled/timestamp`, and add unit checks for `decodeStrict(…, true)` (see section 5 for the cases I ran against a fresh kompile).

### F2 (minor) — Bytes32 decoder: crate panic modelled as a recoverable error, undocumented for the 92e8bdd3 surface

- K: `zkir-values.k:157-161` returns `decErr("Bytes32 decoding assertion failed")` when the low element uses byte 31 (`Lo >= 2^248`) or the high element exceeds one byte.
- Source of truth: `zkir-v3/src/ir_instructions/encode.rs:154-160` (92e8bdd3) does `assert_eq!(bytes[31], 0)` and `assert_eq!(*b, 0)` on the high bytes — a panic, not `Err`. Both conditions are reachable from a well-formed preimage: raw elements are any `Fr < r ≈ 2^254.86`, so `2^248 <= lo < r` is a valid transcript element. At 2ffe2d1 (`midnight-zkir/zkir/src/ir_instructions/encode.rs:143-162`, `decode_bytes`) the same inputs return `None`, i.e. an error, so the K rule is exact for ZKIR-EXT and a deviation for ZKIR.
- Why it matters: a `public_input`/`private_input` of type `Bytes<32>` with transcript `[2^248, 0]` (or `[0, 256]`) crashes the 92e8bdd3 prover while K reports `status` error and continues emitting constraints. The design record documents the analogous K2 (transcript-slice panics, `wiki/zkir/zkir-k-definition.md:63`) but not this case; `tools/divergence_tests.py` has no case for it.
- Fix: record it as K3 next to K2 in `wiki/zkir/zkir-k-definition.md` and add a divergence test that drives the oracle to the panic (the oracle already reports panics for `k02`).

### F3 (minor) — raw preimage elements are never range-checked in K

- K: `decodeValue(ListItem(X), native()) => decOk(native(X))` (zkir-values.k:152) and `decodeInputs` (zkir-values.k:238-247) accept any `Int`; probe results: `decodeValue([r+1], Native) = decOk(native(r+1))`, `decodeValue([-1], Native) = decOk(native(-1))`. `decodeValue([F], JubjubScalar)` likewise accepts `F` in `[r, 2^254)` (zkir-values.k:173-174 checks `fitsBits(F, 254)`, not `F < r`).
- Source of truth: every raw element is an `Fr`; the crate cannot receive a non-canonical one (`transient-crypto/src/curve.rs:346-354` `Fr::from_le_bytes` → `from_repr`, and the oracle's `fr_from_dec`, `zkir-oracle/src/main.rs:52-60`, rejects `>= r` with "not a canonical field element").
- Why it matters: `native(r+1)` and `native(1)` denote the same field element but are distinct K values; arithmetic reduces them (`fadd`, `poseidonHash`), while any rule that compares registers or encodes them without reduction (`encodeValue(native(X)) => ListItem(X)`, zkir-values.k:133; `==K`/`==Int` comparisons in the VM) treats them differently. The differential harness never produces such inputs, so nothing observed it, but any other consumer of the definition (the Agda correspondence, hand-written preimages) can.
- Fix: in `decodeInputs`/`#decodeSlice` (or once in `#preInputs`/`#prePubOut`/`#prePrivate`) require `0 <=Int X andBool X <Int #r` for every raw element and fail with the oracle's message; then `fitsBits(F, 254)` in the JubjubScalar rule becomes redundant but harmless.

### F4 (nit) — `decodeValue` differs from `from_public_input` on wrong-length slices (unreachable through the VM)

- Weierstrass points: `weierstrass_chip.rs:249-252` returns the identity whenever `fields.last() == 1`, *before* checking `fields.len() == 5`; K checks the length first (zkir-values.k:199-200). Probe: `decodeValue([1], Secp256k1Point)` is `decErr` in K, `Some(identity)` in Rust.
- JubjubScalar: `ecc/native/edwards_chip.rs:153-166` accepts 0, 1 or 2 elements (it concatenates their 254-bit decompositions and takes 252 bits); K requires exactly one (zkir-values.k:177).
- Both are unobservable in the VM, which always slices exactly `encodedLen(T)` elements (`zkir-vm.k:400`, `zkir-values.k:246`). Worth a comment so nobody "fixes" the K side in the wrong direction; no code change needed.

### F5 (nit) — kompile warning: unused variable in `#decWPointXY` error rule

- `zkir-values.k:204`: `rule #decWPointXY(X, Y, C, T) => decErr(...) requires X <Int 0 orBool Y <Int 0` — `C` is unused (kompile reports it at that line when the definition is rebuilt). Replace with `_`.

### F6 (nit) — total-function defaults that no caller relies on

- `fpow(_, E, _) => 0 requires E <Int 0` (zkir-field.k:52) and `ecMul(C, _, K) => identity(C) requires K <=Int 0` (zkir-curves.k:124): a negative exponent/scalar silently yields 0 / identity (probe: `ecMul(#secp256k1, G, -1) = inf()`). All callers pass canonical non-negative scalars (`ecMulV` on decoded `*Scalar` values, `#jjScalar` reduces mod `rJ` at zkir-vm.k:232), so this is only a trap for future callers; a comment or `[owise]` error constructor would make the intent explicit.

## 3. Coverage gaps

Not exercised by `tools/unit_values.py`, `tools/unit_hash.py` or the corpus (the items marked "probe" I ran; they should become unit tests):
- `decodeStrict`/`#canonical` on any type (probe: JubjubScalar non-canonical, Secp256k1Base `enc(p)` canonical).
- Foreign-field decode error paths: wrong element count, first element `>= 2^192`, non-zero tail limb (`[5, 2^64]`, `[5, 2^51]` for the 51/5 scalar), wrap-around of values `>= p` (probe).
- secp256r1 encode/decode and secp256r1/curve25519 base/scalar decodes (only secp256k1Base, curve25519Scalar and points are unit-tested); Weierstrass decode with flag 2 (coordinates used, flag ignored), `(0,0)` with flag 0 (probe).
- Bytes32 low element `>= 2^248` (only the high-byte case is unit-tested; probe), and the 92e8bdd3 panic path of F2 in the divergence suite.
- Jubjub decompression corner cases: `(1, 1)` (ZIP 216 `-0`), `(0, -1)` order-2 point, `(0, 1)` identity, `x >= r` (probe); Curve25519 `(0, -1)` and `(0, 1)` (probe).
- Tonelli–Shanks on `k256P`, `p256P`, `2^255-19`; SHA-256/Keccak multi-block and empty messages; SHA-512 empty message and messages of 112–127 bytes (I covered 111, 112, 200 only); `hash_to_curve` with even input lengths and `transient_hash` with 4–5 inputs (probe vs oracle).
- SVDW branch coverage: nothing checks that the twelve `map_to_curve` evaluations compared against the oracle hit all three of `x1`, `x2`, `x3`; a unit test with a `u` known to take each branch would close this.
- `ecMul` edge cases: zero, identity input, `order ± 1`, negative scalar (probe); `ecDouble` with `y = 0` (probe).
- The differential corpus has a single SHA-512 program (`test_sha512_proof.zkir`, a 1-byte message).

## 4. Questions for the authors

1. Is the Bytes32 assert-as-error (F2) an intended, documented deviation for the 92e8bdd3 surface (as K2 is), or should the K definition carry a `panic` status distinct from `error` so that the harness can match the oracle's crash?
2. Is raw-element canonicity (F3) meant to be the harness's responsibility, or should the definition enforce `0 <= x < r` at the preimage boundary so that the Agda correspondence can assume it?
3. `unit_values.py`/`unit_hash.py` run against whichever `zkir-test-kompiled` is present (F1); is there a build step that is supposed to rebuild it, and should the receipts record the definition's timestamp?
