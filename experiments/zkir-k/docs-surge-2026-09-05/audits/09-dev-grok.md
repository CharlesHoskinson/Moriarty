## Findings

### F1 blocking "Modules and representation" / `#canonical` "preserves preceding decoding errors and panics"; "Notes for maintainers" first bullet
Claim: under strict decoding, `#canonical` keeps a preceding `decPanic`, so a malformed two-element `Bytes<32>` encoding stays a panic on the extension surface (the maintainer note calls this a source-level mismatch with Rust `decode_bytes` returning `None`).
Evidence: `zkir-values.k:238` is `rule #canonical(decPanic(_), _, bytes32()) => decErr("Failed to decode as Bytes32")`. Line 239 preserves `decPanic` only when `T =/=K bytes32()`. `decodeValue` still produces that panic at `zkir-values.k:165`, but strict decoding converts it. Ran from the repository root with a one-input `Bytes<32>` program and preimage `[2**248, 0]`: `--ext --checked` printed `"status": "error", "error": "Failed to decode as Bytes32"`; the same files without `--ext` printed `"status": "panic"` and the assertion text from line 165. Rust `encode.rs:144-157` (`decode_bytes`) returns `None` on nonzero high bytes, and `decode_offcircuit` (`encode.rs:230`) turns that into an error, so the conversion at line 238 is the match, not a remaining defect.
Fix: replace the `#canonical` sentence with: "In `zkir-values.k`, `#canonical` keeps a preceding `decErr`; for `bytes32()` it turns `decPanic` into `decErr("Failed to decode as Bytes32")` (the 2ffe2d1 `decode_bytes` path); it keeps `decPanic` for any other type; it accepts `decOk(V)` only when `encodeValue(V) ==K L`." Delete the first maintainer-note bullet, or replace it with: "`zkir-values.k:165` still produces `decPanic` for a malformed two-element `Bytes<32>` encoding; `#canonical` at line 238 maps that to `decErr` when `<strictDecode>` is true. Observed `--ext` status error, not panic. No remaining mismatch with `encode.rs:144`."

### F2 major "Instruction entries", sentence "Extension `eval` rules use `zkir-constraints.k`, `#matches`, to compare the computed value with the output register: equal values hold, unequal values violate, and computation errors become synthesis errors."
Claim: that list is how a developer should read every extension-gate verdict.
Evidence: `#matches(vOk(_), vErr(S), _)` is `unknown(S)` when the output register is absent (`zkir-constraints.k:195`). The `eval` rules at `zkir-ext.k:266-272` (`and`, `or`, `xor`, `concat`, `slice`, `nth`, `reverse`) call no `#need`, so an absent input becomes `vErr` from `resolve`/`rd` and then `synthErr` via `#matches` (`zkir-constraints.k:193`). Reproduced: program `private_input` Bool `%p` then `and [%p] -> %o`, `--ext --checked`, empty private transcript; status panic on the short transcript, verdicts `unknown | register %p is not in the witness | gate(privateInput(...))` and `synthErr | and output: variable not found: Identifier("%p") | gate(andI(...))`. Base gates use `#need` / `#boolean` so an absent register is `unknown` (`zkir-constraints.k:150-152, 178-179`). Only `sha512` follows that convention, through `#needAll` (`zkir-ext.k:274`, which also requires Native; `zkir-constraints.k:449-451`). `load_constant` reads no register. A developer using verdicts to debug a failed run will treat `synthErr` on these seven gates as "the circuit cannot be built" when it can mean "an earlier instruction never wrote the register".
Fix: "Extension `eval` rules use `zkir-constraints.k`, `#matches`: equal values hold, unequal values violate, a computation error (including an absent input register, because `and`/`or`/`xor`/`concat`/`slice`/`nth`/`reverse` call no `#need`) is a synthesis error, and an absent output register is unknown. This differs from the base gates, which report unknown for any absent register (see 08-constraints-and-verdicts.md). The `sha512` gate is the exception: `#needAll` requires every input register to be present and Native, then `#chipNamed("sha2_512")` and `#matches` on `#sha512V`."

### F3 major "Byte-string equality divergence", sentence "The gate rejects the pair: `zkir-constraints.k`, `#eqSupported`, rejects unequal types, and extension rules explicitly reject mixed representations."
Claim: one mechanism (unequal types plus the extension mixed-representation rules) is how the `test_eq` gate rejects unequal-length byte strings, and that this is what a developer will see.
Evidence: `typeOf(bytesV(B))` is `bytesT(lengthBytes(B))` (`zkir-ext.k:65`) and `typeName(bytesT(_))` is `"Bytes"` for every length (`zkir-ext.k:71`). Two `bytesV` values of lengths 3 and 5 are unequal types, so only the inherited rule `zkir-constraints.k:242` matches, with message `Unsupported test_eq: Bytes == Bytes` (length is not in the text). Mixed `bytesV`/`bytes32` matches both that rule (`Unsupported test_eq: Bytes == Bytes32` or the reverse) and `zkir-ext.k:184-185` (`Unsupported test_eq: byte strings of different length`); neither rule has `priority` or `owise`, so the message is not fixed. 13-known-divergences.md:75 and :145 already record a hand run of `Bytes<32>` vs `Bytes<4>` that printed `Unsupported test_eq: Bytes32 == Bytes`, not the extension text. Off-circuit the chapter is right: `eqDispatch(bytesV(_), bytesV(_)) => eqValue()` (`zkir-ext.k:178`) so unequal lengths are false, and mixed representations go to `eqFalse()` (`zkir-ext.k:179-180`); `#testEq` still returns `native(0)`/`native(1)` (`zkir-ops.k:123-124`).
Fix: "For two `bytesV` values of different lengths, the witness is false (`eqDispatch` is `eqValue()`). The gate is a synthesis error because `typeOf` is `bytesT(N)` and `N` differs, so `zkir-constraints.k`, `#eqSupported`, takes the unequal-type arm; `typeName` is `"Bytes"` for every `N`, so the message is `Unsupported test_eq: Bytes == Bytes`. Mixed `bytesV`/`bytes32` is also a synthesis error: the same inherited arm and the two `zkir-ext.k` rules at lines 184-185 all match, with different messages, so the text is not fixed (13-known-divergences.md recorded `Unsupported test_eq: Bytes32 == Bytes`). Equal-length `bytesV` pairs, and `bytes32` pairs, remain eligible for `test_eq`."

### F4 major "Running and testing" (what the three commands print)
Claim: the fenced commands are what a developer types to run and test the extension surface; the only stated result is that the first command prints KORE.
Evidence: `zkir_run.py:381` always prints one JSON object and then returns 0 (`zkir_run.py:382`), including when `"status"` is `error` or `panic` (reproduced in F1). The keys a developer needs are `status`, `error`, `memory` (per-register `variant`/`type`/`encoded`), `verdicts` (a count), `all_verdicts` (triples `[outcome, message, gate]`), and `violations`. The shown `--checked` run of `test_bool_gates.zkir` with `inputs [1,0]` printed `"status": "ok"`, 17 constraints, 17 `holds` verdicts, `"violations": []`. `diff_test.py --ext --only test_bool_gates --no-perturb` (exit 0) printed first `PASS ... run0 K=error Rust=error ... Equality constraint failed` then `PASS ... run1 K=ok Rust=ok`, then `2 comparisons: 1 successful-run agreements, 1 error-run agreements`. That first row is a generated preimage that does not satisfy the program's `constrain_eq` (the program is only an honest witness when `%t` is 1 and `%f` is 0, which is the hand-built preimage in the `zkir_run.py` command, not what `diff_test.py` draws). Without those facts a developer cannot tell a successful run from a failed witness, and will read the first `diff_test.py` line as a problem.
Fix: after the command block, add: "`zkir_kast.py kore` prints one KORE term on stdout. `zkir_run.py` prints JSON and exits 0 even when the VM status is `error` or `panic`; read `status` (and `violations`, which is empty on a holding run). `diff_test.py` prints one `PASS`/`FAIL` line per comparison, then a summary of the form in the receipt. `--only test_bool_gates --no-perturb` still generates preimages: expect an error-run agreement on a random Boolean pair, then a successful-run agreement once both sides accept. The `[1,0]` preimage in the `zkir_run.py` command is the honest pair for that program."

### F5 minor "Running and testing", sentence "`zkir_kast.py --ext` enables parsing; KORE conversion also needs the explicit extension definition above."
Claim: `kore` on an extension program fails unless `--definition` points at `zkir-ext-kompiled`.
Evidence: `zkir_kast.py:377-378` defaults to `semantics/zkir-check-kompiled`, and `zkir-check.k:6-10` imports `ZKIR-EXT-SYNTAX`. Ran `zkir_kast.py kore ... --ext` with no `--definition`: exit 0, same KORE as with `--definition zkir-ext-kompiled`. The same command with `--definition experiments/zkir-k/semantics/zkir-kompiled` raises `KeyError: 'Bool'`. `zkir_kast.py check --ext` (default definition) prints `wfOk`; `check --ext --definition experiments/zkir-k/semantics/zkir-ext-kompiled` prints `unexpected: <generatedTop> ...` because that definition is the VM, not `ZKIR-CHECK`. The shown `kore` command is valid; the necessity claim is not, and copying `--definition zkir-ext-kompiled` onto `check` misleads.
Fix: "`zkir_kast.py --ext` enables parsing. `kore` needs a kompiled definition that contains the extension symbols: the default `zkir-check-kompiled` is enough, and so is `--definition experiments/zkir-k/semantics/zkir-ext-kompiled`. Do not pass the VM definition to `check`; that command's default is `zkir-check-kompiled`. `zkir_run.py --ext` selects `zkir-ext-kompiled` itself (`Runner`)."

### F6 minor "Modules and representation", sentence "The removed instruction also remains in imported K syntax: the JavaScript Object Notation (JSON) boundary enforces its removal."
Claim: only the syntax of `reverse_bytes` is still in ZKIR-EXT; the JSON preprocessor is the whole removal.
Evidence: `ZKIR-EXT` imports `ZKIR-VM` (`zkir-ext.k:161`), so `#exec(reverseBytes(...))` (`zkir-vm.k:263-277`) and `eval(gate(reverseBytes(...)))` (`zkir-constraints.k`, reverseBytes gate) are in the extension definition. A hand-built `reverseBytes` term still runs. Only `tools/zkir_kast.py` `instruction` (`zkir_kast.py:251-253`) rejects JSON `reverse_bytes` when `EXT` is true. The `--ext` receipt's four format rows include `handmade/native_bytes.zkir` with that message.
Fix: "The removed instruction remains in the extension definition with its execution and gate rules (inherited from `ZKIR-VM`). Only the JSON boundary, `tools/zkir_kast.py`, `instruction`, rejects `reverse_bytes` under `--ext`."
