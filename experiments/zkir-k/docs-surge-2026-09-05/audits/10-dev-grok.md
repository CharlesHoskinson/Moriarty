## Findings
### F1 blocking "The command supports only the base surface" / Notes for maintainers first bullet
Claim: `zkir_kast.py check` supports only the base surface because ZKIR-CHECK imports ZKIR-WF alone and `zkir-check-kompiled` has no symbol for `Bool`, `Byte` or the extension instructions, so `check --ext` is unusable (`KeyError: 'Bool'`, exit 1) and the working route is `zkir_run.py --ext --checked`.
Evidence: `experiments/zkir-k/semantics/zkir-check.k` lines 3-10 require `zkir-ext.k` and import `ZKIR-EXT-SYNTAX` (the file comment says this is so `check --ext` uses the same definition). `zkir-check-kompiled/compiled.txt:1013-1014` is `imports ZKIR-WF` then `imports ZKIR-EXT-SYNTAX`; `syntaxDefinition.kore:135` has `symbol'Kywd'{}("Bool")` from `zkir-ext.k`. Ran from the repository root: `uv run --group zkir-k python experiments/zkir-k/tools/zkir_kast.py check --ext experiments/zkir-k/corpus/midnight-zkir-2ffe2d1-tests/test_bool_gates.zkir` printed `wfOk` and exited 0. Without `--ext` the same file printed `format error: unknown IR type 'Bool'` on stderr and exited 2 (preprocessor, not a missing K symbol). `check --ext --definition experiments/zkir-k/semantics/zkir-ext-kompiled` did print `unexpected: <generatedTop> ...` (`configVars.sh` `$PGM` is `Job`), so that half of the maintainer note is true. A developer following the chapter will skip the working `check --ext` path and use a full VM run instead.
Fix: Replace the sentence from "The command supports only the base surface" through "`zkir_run.py --ext --checked`" with: "The command accepts `--ext`. ZKIR-CHECK imports ZKIR-WF and ZKIR-EXT-SYNTAX, and `zkir-check-kompiled` contains the extension symbols, so `check --ext FILE` evaluates `wf` on an extension program (example: `test_bool_gates.zkir` prints `wfOk`). Without `--ext` the preprocessor rejects those files (`format error: unknown IR type 'Bool'`, exit 2). Do not pass `--definition experiments/zkir-k/semantics/zkir-ext-kompiled` to `check`: that definition's `$PGM` is a `Job`, so the `Program` term is left unrewritten and `wf_result` prints `unexpected: <generatedTop> ...`. To execute `checkedJob` on the extension VM, use `zkir_run.py --ext --checked` (06-configuration-and-run-lifecycle.md, 11-tooling-reference.md)." Delete the first Notes-for-maintainers bullet, or keep only the `zkir-ext-kompiled` `$PGM` is `Job` observation.

### F2 major "the VM reports `Unexpected output length of encode instruction`"
Claim: the run-time encode-arity failure string is `Unexpected output length of encode instruction`.
Evidence: `zkir-vm.k:318-319` is `#fail("Unexpected output length of encode instruction: " +String tn(V))` when `size(encodeValue(V)) =/=Int lenIds(Os)`. The in-circuit arm `zkir-constraints.k:359` is `synthErr("Unexpected output length of encode instruction")` without the type suffix. A developer grepping a `job` error for the chapter string will miss the off-circuit report.
Fix: "the VM reports `Unexpected output length of encode instruction: T` (`zkir-vm.k`, `#encode`; `T` is `tn(V)`). The matching gate is `synthErr("Unexpected output length of encode instruction")` (`zkir-constraints.k`)."

### F3 minor "The extension surface adds `reads` and `writes` rules ... and nothing else"
Claim: module ZKIR-EXT-SYNTAX adds only `reads` and `writes` for the extra instructions.
Evidence: `zkir-ext.k:15-52` (module ZKIR-EXT-SYNTAX) also adds `boolT`/`byteT`/`bytesT`, `encodedLen` rules, and the nine instruction constructors. It adds no `#checkArity` rules, so those instructions do take the `owise` arm (`zkir-syntax.k:306`). 09-extension-surface.md already lists the extra syntax.
Fix: "The extension surface adds types, instruction constructors, `encodedLen`, `reads` and `writes` in `zkir-ext.k` (module ZKIR-EXT-SYNTAX). It adds no `#checkArity` rules, so those instructions pass through the `owise` rule (see 09-extension-surface.md)."
