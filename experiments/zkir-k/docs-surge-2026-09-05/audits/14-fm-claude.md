## Findings

### F1 blocking "The extension's `sha512` arm is the model for an instruction-triggered chip:" (Adding a chip, quoted K block, chapter lines 117-120)
Claim: the quoted gate rule is `rule eval(gate(sha512(Al, Xs, O)), M, _, Chips) => #and(#needAll(Xs, M), #and(#chipNamed("sha2_512", Chips), #matches(#sha512V(resolveAll(Xs, M), Al), rdId(O, M), "sha512 output")))`, i.e. the gate recomputes the digest with the off-circuit function `#sha512V`.
Evidence: zkir-ext.k:275 reads `... #matches(#sha512C(resolveAll(Xs, M), Al), rdId(O, M), "sha512 output")))`, and `#sha512C` (zkir-ext.k:276-281) decodes the alignment through `alignedBytesCircuit` (zkir-constraints.k:472-475), which returns `bErr("synthesis: in-circuit decoding of alignment options is not yet implemented")` for any `option` segment and `bErr("synthesis: Cannot decode compressed value from field elements")` for a `compress` atom, whereas `#sha512V` (zkir-ext.k:251-259) uses the off-circuit `alignedBytes` (zkir-ops.k:236-252), which parses options. The relation the chapter states therefore differs from the relation the definition evaluates on every program whose `sha512` alignment contains an option or compress segment (the chapter's version would report `holds` or `violated` where the file reports `synthErr`). The comment at zkir-ext.k:273-274 records the reason ("shares the byte-hash path of persistent_hash and keccak256, `fab_decode_to_bytes`"). The chapter's own gate row says "do not fall through", and the chip section presents this rule as the template to copy.
Fix: replace the quoted rule with the current text of zkir-ext.k:275, and add one sentence after the block: "`#sha512C` differs from the off-circuit `#sha512V` only in decoding the alignment through `alignedBytesCircuit` (zkir-constraints.k), which rejects `option` and `compress` segments at synthesis; a new byte-hash gate must use the circuit decoder, not `alignedBytes`."

### F2 major "A decoder that panics in Rust returns `decPanic`, which `#toValue` turns into `vPanic`." (Adding a type) and "Status `panic(msg)` is reserved for process aborts (short transcripts, the Bytes32 decoder assertions)." (Conventions)
Claim: a `decPanic` always becomes `vPanic` and then status `panic`.
Evidence: zkir-values.k:233 routes every strict decode through `#canonical`, and zkir-values.k:238 `rule #canonical(decPanic(_), _, bytes32()) => decErr("Failed to decode as Bytes32")` turns the Bytes32 assertion into an ordinary error on the extension surface (where `<strictDecode>` is `true`, zkir-ext.k:168-169) and in `load_constant`, which always decodes strictly (zkir-ext.k:244,272 `decodeStrict(#immInts(Es), T, true)`). Only a `decPanic` of another type passes through (zkir-values.k:239). So the same raw element is status `panic` under `zkir-kompiled` and status `error` (class `decode`) under `zkir-ext-kompiled`; docs/13-known-divergences.md:80 records exactly this. A maintainer adding a panicking decoder to a new type has to decide which surface panics, and the chapter gives no rule for it.
Fix: "A decoder that panics in Rust returns `decPanic`; `#toValue` turns it into `vPanic` and `#put` into status `panic`. Under strict decoding (the extension surface, and `load_constant` on any surface) `#canonical` in `zkir-values.k` intercepts `decPanic` for `bytes32()` and returns `decErr("Failed to decode as Bytes32")`, because the 2ffe2d1 decoder returns `None` there; every other type's `decPanic` passes through. A new type whose 2ffe2d1 decoder does not panic needs its own `#canonical` arm." In the conventions paragraph, qualify: "the Bytes32 decoder assertions on the base surface".

### F3 major "Nested function calls evaluate every argument first and hide that order. Instructions that convert between resolves are a chain of `KItem`s." (Conventions, third paragraph)
Claim: sequential resolve-and-convert requires a `KItem` chain; a function cannot give it.
Evidence: the four base hash instructions convert between resolves inside a function: zkir-vm.k:228-235 `resolveNatives((O, Os), M) => #rn(resolve(O, M), Os, M)` and `#rn(vOk(native(X)), Os, M) => #consNative(iOk(X), resolveNatives(Os, M))`, with the error arms at 232-233 and 235 returning without ever resolving `Os`. The recursion sits on the right-hand side of the success arm, so the second operand is resolved only after the first has been resolved and converted, exactly as `preprocess` does, with no `KItem`. The property that matters is where the later `resolve` appears (as a sibling argument of the same application, as in `#bin`, versus on the right-hand side of the arm that has already matched the earlier result), not `KItem` versus function. A reader following the chapter would rewrite `resolveNatives` as a `KItem` chain or believe `#bin` is the only alternative.
Fix: "K evaluates the arguments of a function application before matching its rules, so `#bin(resolve(A, M), resolve(B, M), ...)` resolves both operands before either is inspected. Sequential resolution places the next `resolve` on the right-hand side of the arm that has already matched the previous result: either as a chain of `KItem`s (`#lt`..`#lt4`, `#recon`..`#recon4`, `#impactPush`/`#impactOne`) or as a recursive function whose recursion is only in the success arm (`resolveNatives`/`#rn` for the hash instructions)."

### F4 major "That is the intended report for a forgotten `eval` arm; it must not be turned back into `holds()`." (Pitfalls, catch-all rules) together with "If the instruction is `impact`-like or `output`-like, extend `isSpecialEmit` and emit a dedicated `Constraint` rather than `gate(I)`." (Adding an instruction)
Claim: a forgotten `eval` arm yields the outcome `unsupported`.
Evidence: the only catch-all is zkir-constraints.k:494 `rule eval(gate(I), _, _, _) => unsupported(...) [owise]`, which matches `gate(_)` only. For a new constructor of sort `Constraint` (the dedicated constraint the chapter tells the maintainer to emit), `eval/6` falls through its `[owise]` at zkir-constraints.k:135 to `eval/4`, whose rules are `guardGate` (206), `piGate` (207) and the `gate(...)` arms; there is no rule for any other constructor. `eval/4` is declared `[function, total]` (204) but is not total on that input, so the LLVM interpreter aborts on `#Bottom` while evaluating `verdicts` (zkir-constraints.k:91), i.e. the run does not finish and `zkir_run.py` reports `krun-failed` (tools/zkir_run.py:304-305), not `unsupported`. `verdicts` skips only non-`Constraint` list items (92).
Fix: after the `isSpecialEmit` sentence add: "Every new `Constraint` constructor needs its own `eval` arm (six-ary in `ZKIR-CONSTRAINTS` when it needs outputs or the binding input, otherwise four-ary); the `unsupported` fallback applies to `gate(I)` only, and a `Constraint` with no `eval` arm reaches `#Bottom` inside `verdicts` and aborts the interpreter." In the pitfall, change "for a forgotten `eval` arm" to "for a forgotten `eval` arm of an instruction wrapped in `gate(_)`".

### F5 major "Do not mark a cryptographic function `[simplification]` without a `[concrete]` restriction." (Pitfalls, symbolic unfolding)
Claim: the non-termination comes from simplification rules, and avoiding `[simplification]` (or pairing it with `[concrete]`) prevents it.
Evidence: no rule of zkir-hash.k, zkir-field.k or zkir-ext.k carries `[simplification]` (grep, none). The unfolding recorded in review-2026-09-05/CONSOLIDATED.md:193-197 (item 34) happened with the ordinary defining rules of `poseidonHash`, `absorbAll`, `permute` and `sbox` (zkir-hash.k:33-67), which the Haskell backend applies to symbolic arguments like any function rule. wiki/k-framework/k-best-practices.md:44-46 states that `[concrete]` restricts a rule to fully concrete arguments; that is the attribute a maintainer would put on the defining rules to stop the unfolding, together with a symbolic treatment (an `smtlib` declaration or lemmas, k-best-practices.md:50-53, 175). As written the sentence tells the reader to leave the defining rules unrestricted, which is the state that does not terminate.
Fix: "The defining rules of `poseidonHash`, `absorbAll`, `permute` and `sbox` carry no `[concrete]` restriction, so the Haskell backend unfolds them on symbolic arguments. To prove a claim through a hash, restrict those rules with `[concrete]` and give the function a symbolic treatment (an `smtlib` declaration or `[simplification]` lemmas); none of this is implemented."

### F6 major "Conversions | `zkir-ops.k` | any `as*` helper and the `*V` dispatch arms" and "Chip | `zkir-constraints.k` `chipOfType`" (Adding a type, table)
Claim: the table lists every function a new type must extend.
Evidence: four dispatch functions with an `[owise]` arm that returns a wrong-typed or wrong-kind value instead of an error are missing, and they are exactly the ones a totality convention hides: `#wrapField(X, _) => native(X) [owise]` (zkir-ops.k:98) makes `inv` of a new field type return a `native` value off-circuit; `#wrapPoint(_, _) => native(0) [owise]` (zkir-values.k:227) does the same for a new point type in decoding and `from_coordinates`; `isZeroField(_) => false [owise]` (zkir-constraints.k:292) makes `inv` of zero of a new field type report `synthErr` through `#matches(vErr(...))` (193) instead of `violated` through `#invNonZero` (282), which is the very split the chapter's conventions section uses as its example; `#decField(_, T) => decErr(...) [owise]` (zkir-values.k:198) rejects every decode of a new field type until an arm is added. None of these produce a `vErr`, so the differential harness would report a memory mismatch or a wrong verdict rather than a missing-arm error. The runner side (`type_string`, `encode_value` at tools/zkir_run.py:201,216) and the generator side (`ENCODED_LEN`, `random_encoded`, `small_encoded` at tools/zkir_values.py:98,106,148) exist as the table says.
Fix: add to the conversions row "`#wrapField` and, for field types, `#invField`, `intoBytes32V`, `fromBytes32V`"; add to the base-values row "`#wrapPoint`, `#decField`"; add to the chip row "and `isZeroField`, whose `[owise]` is `false` (without an arm, `inv` of zero is a synthesis error, not a violated gate)". Add one sentence: "Search every `[owise]` arm that returns a typed dummy (`native(X)`, `native(0)`, `false`) before running the harness; those arms do not fail, they return the wrong value."

### F7 major "Name | the crate's `used_chips` string" and "names the crate's `used_chips` actually enables" (Adding a chip)
Claim: the chip names in `<chips>` are strings taken from the crate's `used_chips`.
Evidence: `IrSource::used_chips` returns a `ZkStdLibArch` struct whose fields are booleans (repos/_build/ledger-92e8bdd3/zkir-v3/src/ir_vm.rs:1212-1262: `jubjub`, `poseidon`, `sha2_256`, `sha2_512`, `keccak_256`, `sha3_256`, `blake2b`, `secp256k1`, `p256`, `bls12_381`, `curve25519`, `base64`, `automaton`, plus `nr_pow2range_cols`). There is no string anywhere in that function; the K strings `"jubjub"`, `"p256"`, `"sha2_256"` (zkir-constraints.k:66-84) are the field names of `ZkStdLibArch` chosen for the definition, and the extension's `"sha2_512"` is the field set at repos/_build/midnight-zkir-2ffe2d1/zkir/src/ir_vm.rs:1492. A maintainer told to look for "the crate's `used_chips` string" will not find one, and the fields `sha3_256`, `blake2b`, `bls12_381`, `base64`, `automaton` (all `false` at both pins) are chips the crate can name but the definition does not model.
Fix: "Name | the field of `ZkStdLibArch` that `used_chips` sets to `true` (ir_vm.rs), written as a K string of the same spelling; fields the crate never sets (`sha3_256`, `blake2b`, `bls12_381`, `base64`, `automaton`) have no K name."

### F11 minor "Overlapping arms with different results make execution non-deterministic." (Pitfalls, `[owise]` overlap)
Claim: by listing three fixed instances the paragraph reads as if the definition has no live ones.
Evidence: zkir-constraints.k:258-259 `rule #selBit(_, vOk(A), vOk(B)) => selectV(false, A, B) [owise]` and `rule #selBit(_, _, _) => vErr("missing") [owise]` both match `#selBit(N, vOk(_), vOk(_))` for `N` other than 0 and 1 at the same priority 200 with different results (the `#boolean` outcome placed first in `#and` at 252 masks the value, but `#and` is a function, so `#selBit` is evaluated anyway). zkir-ext.k:184 `#eqSupported(vOk(bytesV(_)), vOk(bytesV(_)), "cond_select") => synthErr("Unsupported cond_select: Bytes ? Bytes")` has no guard and overlaps zkir-constraints.k:242 (`requires notBool sameType(A, B)`, which is true for two `bytesV` of different lengths, message "Unsupported cond_select: Bytes == Bytes") at priority 50; both are `synthErr` and the same error class, so no run detects it. These are not chapter errors, but a maintainer who copies `#selBit` as a template copies the pattern the paragraph warns against.
Fix: either cite `#selBit` and the extension `#eqSupported` arm as the remaining instances to clean up, or replace "keep typed cons arms above a single `[owise]` error" with "exactly one `[owise]` arm per function, and no unguarded extension arm over a guarded base arm".
