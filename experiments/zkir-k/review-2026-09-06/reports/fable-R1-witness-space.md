# R1: the modelled witness space and the soundness statement

VERDICT: WARNING — the modelled witness space over-approximates the circuit's accepted set in the safe direction and no completeness defect was found on the corpus, but the residual list omits foreign-field limb canonicity (the same class of gap the JubjubScalar item names) and the `unconstrained` marker covers only guarded-off inputs while the circuit leaves every transcript input register equally free, so the soundness statement's residual is incomplete as written.

## Findings

### 1. Major — foreign-field limb canonicity is a residual the list does not name and `#canonicity` does not mark

**K code.** `experiments/zkir-k/semantics/zkir-constraints.k:404-406` reports `unconstrained` only for `jubjubScalar()`; every other type falls to `holds()`. The header residual list (`zkir-constraints.k:46-66`) and chapter 08 (`experiments/zkir-k/docs/08-constraints-and-verdicts.md:130-135`) list JubjubScalar canonicity and guarded-off inputs as the only assignment-level gaps. The typing paragraph (`zkir-constraints.k:32-44`, `08-constraints-and-verdicts.md:120`) says the per-type range constraints "hold on every register of a well-typed memory and are not evaluated a second time". My run of the definition on `corpus/handmade/curve_secp256k1.zkir` (five foreign-typed declared inputs) gives five `inputGate` verdicts `holds` and `unconstrained: []`.

**Source of truth.** `FieldChip::assign` (`circuits/field/foreign/field_chip.rs:424-455`) assigns each limb with `assign_lower_than_fixed(xi, 2^log2_bound)` where the bounds come from `well_formed_log2_bounds` (`field_chip.rs:263-277`), chosen so that `m <= base^(nb_limbs-1) * msl_bound < 2m`. The assigned integer `1 + sum base^i x_i` therefore ranges over roughly `[1, 2m)`, and every element below `base^(nb_limbs-1)*msl_bound - m` has a second, non-canonical, well-formed representation. Nothing at assignment proves the value below the modulus; the crate's own comment in `assign_fixed` (`field_chip.rs:474-481`) acknowledges "the non-canonical (but well-formed) form". Downstream, representation leaks: `as_public_input` (`field_chip.rs:500-525`) calls `normalize`, which is a no-op on well-formed inputs (`field_chip.rs:1568-1578`), so `encode_incircuit` (`ledger/ir_instructions/encode.rs:112-130`) and the communications commitment (`ledger/ir_vm.rs:1173-1200`) hash the raw limbs; `assert_equal` (`field_chip.rs:561-580`, used by `constrain_eq_incircuit`) compares limbs after the same conditional normalisation. Arithmetic, `is_zero`/`inv` (`field_chip.rs:694-712, 986-1000`), `is_equal` (`field_chip.rs:637-645`, via `sub` whose bounds force normalisation) and `into_bytes32` (`field_chip.rs:1168-1226`, `enforce_canonical = true`) are value-semantic. Foreign points inherit the gap: `assign_point_unchecked` (`circuits/ecc/foreign/edwards_chip.rs:452-466`) and the Weierstrass `assign_without_subgroup_check` (`circuits/ecc/foreign/weierstrass_chip.rs:945-960`) assign the coordinates through the same `FieldChip::assign`; the on-curve assertions are value-semantic, so a coordinate cell may hold a non-canonical representative that `into_coordinates` then exposes as a register and `encode` hashes.

This is exactly parallel to the JubjubScalar item: `EccChip::assign` (`circuits/ecc/native/edwards_chip.rs:877-889`) assigns 252 bits with `enforced_canonical: false`, and `as_public_input` for scalars (`edwards_chip.rs:1040-1047`) aggregates the raw bits. The K comment at `zkir-constraints.k:394-403` states that gap correctly; the foreign-field gap is the same mechanism in a different chip.

**Why it matters.** The soundness claim says the residual list names every place "where the circuit may accept a witness the model does not describe". A prover who assigns a Secp256k1Scalar declared input as the limbs of `v + m` passes every assignment constraint, every arithmetic gate computes on `v`, but the circuit's `encode` outputs and the commitment differ from `encodeValue(secp256k1Scalar(v))`, so the circuit accepts a witness that the model, which holds only the value `v`, cannot express. No `unconstrained` marker and no residual item tells the reader of `witnessSpace` that six of the eleven typed inputs carry this freedom. The Moriarty compiler-correctness statement will quote `unconstrainedRegs` and the residual list; both are wrong for a program with foreign inputs (all four `curve_*.zkir` handmade programs, and any Compact program using secp256k1 or curve25519 types). The typed `IrValue` interface cannot carry such a witness, so, as for JubjubScalar, the oracle has no column for it; the receipts cannot reveal it.

**Fix.** Extend `#canonicity` (`zkir-constraints.k:404-406`) to `secp256k1Base()`, `secp256k1Scalar()`, `secp256r1Base()`, `secp256r1Scalar()`, `curve25519Base()`, `curve25519Scalar()` with a message of the form `"foreign limb canonicity: the assigned limbs of X are range-checked to the well-formed bounds, not proven below the modulus"`, and to the three foreign point types for their coordinate cells (message naming the coordinates). Add the residual item to the header list and to chapter 08 next to the JubjubScalar item, citing `field_chip.rs:424-455` and `:263-277`, and extend the last paragraph of D5 in `experiments/zkir-k/plan-iter3/circuit-comparison-table.md:241-245` and the "What the crate cannot distinguish" bullet at `:294-297` to say the same of foreign limbs. Add a caveat to projection item (3) (`zkir-constraints.k:28-30`): for the foreign field chip, `assert_equal` is limb equality after conditional normalisation; it coincides with value equality on canonical representations, which is what a typed witness produces.

### 2. Major — the circuit does not read the guard, so a `public_input` / `private_input` register at guard 1 is the same free cell as at guard 0; `unconstrained` marks only the guard-0 case

**K code.** `#guardedOff` (`zkir-constraints.k:387-390`) reports `unconstrained` only when the witness value of the guard is `native(0)`; guard 1 and `noGuard()` give `holds`. The header (`zkir-constraints.k:62-66`) and chapter 08 (`08-constraints-and-verdicts.md:51, 135`) present "Guarded-off inputs" as the residual, and `unconstrainedRegs` (`zkir-constraints.k:185-189`) is documented as "the registers whose assigning relation is unconstrained". The receipt `evidence/zkir-k-circuit-differential-92e8bdd3-2026-09-06c.txt:836` lists as unconstrained only registers whose guard evaluated to 0 (for `transcripts_guard_off.zkir`, `%pp,%ps`; its guard-1 registers `%p1`, `%s1` are not listed).

**Source of truth.** `Relation::circuit` (`ledger/ir_vm.rs:977-1003`) matches `PublicInput { guard: _, val_t, output } | PrivateInput { guard: _, .. }`, reads `preproc.memory.get(output)` and calls `assign_incircuit`; `mem_insert` then compares the cell against the same witness entry it was assigned from (`ir_vm.rs:761-781`), which is a tautology. No `pi_push` and no equality against the transcript exists for either instruction; the transcript is not part of `Preprocessed` (`ir_vm.rs:684-690`). The only difference between guard 0 and guard 1 is off-circuit (`ir_vm.rs:349-389`): `preprocess` stores `IrValue::default` or the decoded transcript slice. `assign_incircuit` (`ledger/ir_instructions/assign.rs:36-142`) constrains only the type, for every one of the thirteen types, so the cell is free beyond its type in every case, public and private, guard 0 and guard 1. The K marker therefore identifies exactly the cells the harness names (D5), which is a strict subset of the circuit's free input cells.

**Why it matters.** The soundness direction of the compiler-correctness statement quantifies over the modelled space. As written, the modelled space already admits any typed value in a guard-1 `public_input` register (the gate is typing only), so the space is not wrong; but the residual list and `unconstrainedRegs` tell the Moriarty specification that the guard-1 registers are pinned, and nothing in `Relation::circuit` pins them. For `public_input` the binding to `public_transcript_outputs` is an obligation of the ledger's transcript re-execution, outside the circuit; for `private_input` there is no binding at all, the register is a prover choice exactly like a declared input. A specification that reads "`public_input` at guard 1 holds the ledger's value" from the K semantics would be assuming a circuit constraint that does not exist.

**Fix.** Decide what `unconstrained` means and make the code and text agree. Either (a) mark every `public_input` / `private_input` register `unconstrained` regardless of guard, with two messages ("guard is 0: witness holds the default" and "transcript value is not pinned in circuit"), and mark declared inputs through `inputGate` the same way, so `unconstrainedRegs` is the list of prover-chosen cells; or (b) keep the marker as "the witness holds a default the circuit does not enforce" and add a residual item "Transcript inputs: the circuit binds no `public_input` or `private_input` register to the transcript; the public transcript is enforced by the ledger, the private transcript by nobody" to the header list, chapter 08 and the plan's compiler-correctness paragraph (`experiments/zkir-k/plan-iter3/PLAN.md:53`). Under either option add a `--inject` column on a guard-1 `public_input` Native register (the current `inject-input` column is restricted to declared inputs, `circuit-comparison-table.md:108`) and predict it with the D3 walk; the oracle will say `A` whenever no consumer reads it, which is the direct test of this finding.

### 3. Minor — a hash input that exceeds its alignment byte width is `synthErr` in K and a constraint failure in the circuit

**K code.** `alignedBytesCircuit` (`zkir-constraints.k:546-556`) reuses `#alignedBytes`, whose byte atoms fail with `bErr("Inputs did not match alignment")` when a field does not fit `8 * stray` bits (`experiments/zkir-k/semantics/zkir-ops.k:319-323`) or 248 bits per chunk (`zkir-ops.k:328-332`). That `bErr` becomes `vErr` in `#std4` (`zkir-constraints.k:554`) and `#matches` maps every `vErr` to `synthErr` (`zkir-constraints.k:245`), which the table translates to a panic (D2).

**Source of truth.** `fab_decode_to_bytes_atom` (`ledger/ir_vm.rs:144-168`) calls `assigned_to_le_bytes(f, Some(k))`; for `k < 32` the native gadget decomposes the cell into `8k` bits with `decompose_fixed_limb_size` (`circuits/field/native/native_gadget.rs:945-960`), a range constraint that a too-large value violates at `verify`, not a synthesis error. Only "too little data" (`ir_vm.rs:134-138, 156-160`) is `Error::Synthesis`.

**Why it matters.** The verdict class is wrong for an existing circuit that rejects. The honest path never shows it (`preprocess` fails first, D9), and the harness's taint walk refuses to decide hash inputs whose alignment the injected value no longer fits (`circuit-comparison-table.md:212-215`), so the receipts cannot contradict K here. The cell is reachable through `--inject` on a Native register consumed by `persistent_hash` or `keccak256`.

**Fix.** Have `bytesFromFieldRepr` (or a circuit-side copy) return a distinct constructor for the range failure, map it to `violated` in `#std4`, keep the "did not match alignment" arity failure as `synthErr`, and teach the walk to predict `C` for that injection.

### 4. Nit — `#unsat` is dead

`zkir-constraints.k:207-210` defines `#unsat(O, _) => O` and nothing uses it (grep over `semantics/*.k`). The prior audit's item 7 was implemented through `#invNonZero` and `#lowHighBounds` instead. Remove it, or use it to carry finding 3.

### 5. Nit — a declared-type mismatch on `inputGate` / `publicInput` / `privateInput` is `violated` in K but `Error::Synthesis` in the crate

`#typed` (`zkir-constraints.k:407-410`) returns `violated`; `assign_incircuit` fails in `convert_values` with `Error::Synthesis` (`ledger/ir_instructions/assign.rs:48-57`), which is a known-witness-dependent synthesis error, the oracle's `S` class that the table says no K row produces (`circuit-comparison-table.md:180-183`). Reachable only under `job` for a program that overwrites an input register with a value of another type (`Relation::circuit` assigns declared inputs from the final witness memory by name, `ledger/ir_vm.rs:712-731`); `checkedJob` rejects such programs. Change the outcome to `synthErr` or document the row.

## Answers to the brief's questions

1. Projection. Every named register is the cell that `mem_insert` or `memory.insert` binds (`ledger/ir_vm.rs:761-781, 1123-1149`), and the K register holds its typed value; for `copy` the "cell" is the operand's cell itself (`ir_vm.rs:866-867`), so value equality is exact. Auxiliary cells are advice the prover chooses, so the existential treatment is a correct over-approximation. Copy wiring is value equality in the native chips (`assert_equal` on coordinates, `circuits/ecc/native/edwards_chip.rs:904-912`) and in the foreign point chips, and is limb equality after conditional normalisation in the foreign field chip (finding 1); on canonical representations the two coincide.
2. Residual list. Missing: foreign-field limb canonicity, including foreign point coordinates (finding 1); the transcript-input binding (finding 2). Present and confirmed: Bytes32 bytes are range-checked at assignment (`native_gadget.rs:565-580`, `assign_less_than_pow2(byte, 8)`); Jubjub points are assigned as a cofactor root then cleared (`edwards_chip.rs:842-856`), foreign Edwards points the same with an on-curve assertion (`circuits/ecc/foreign/edwards_chip.rs:562-576`), Weierstrass points with `assert_is_on_curve` (`weierstrass_chip.rs:945-960`); decomposition hints (`div_mod_power_of_two`, `reconstitute_field`) are canonical decompositions whose outputs are functions of the input (`ledger/ir_vm.rs:1010-1056`), matching the K relations; lookup and hash padding cells are auxiliary.
3. Canonicity. Confirmed as stated: witness-assigned scalars carry `enforced_canonical: false` (`edwards_chip.rs:877-889`) and `value()` reduces the bit string modulo the order (`edwards_chip.rs:121-140`); `jubjub_scalar_from_biguint` (`ledger/ir_instructions/encode.rs:227-240`) is canonical because `div_rem` asserts `r < y` (`circuits/biguint/biguint_gadget.rs:509-528, 896-904`), although the resulting scalar is 256 bits from 32 bytes (`edwards_chip.rs:1362-1380`) with `enforced_canonical: false`, which `encode_incircuit` handles by asserting the second batch zero (`encode.rs:101-110`); `assign_fixed` is canonical (`edwards_chip.rs:891-901`). The base surface has no other JubjubScalar assignment (`from_bytes32_incircuit` has no JubjubScalar arm, `ledger/ir_instructions/from_bytes32.rs:95-140`; `select_incircuit` has none, `select.rs:82-115`); the extension crate adds only the `load_constant` path (`/home/charl/Moriarty/repos/_build/midnight-zkir-2ffe2d1/zkir/src/ir_vm.rs:1141`).
4. Guarded-off inputs. Yes, free in every case and every type; K marks exactly the guard-0 registers, which is a proper subset of the circuit's free input cells (finding 2).
5. Direction of approximation. On every relation I compared, K rejects only what the circuit rejects: `assert` is `assert_non_zero` (`ledger/ir_vm.rs:830-834`); `inv` at zero is unsatisfiable in both chips (`circuits/field/native/native_chip.rs:960-968`, `field_chip.rs:986-1000`); `less_than` bounds both operands to the padded width and its bit is exact (`stdlib/lib.rs:889-899`, `native_gadget.rs:332-345, 416-460`); `reconstitute_field` and `constrain_bits` match `assert_lower_than_fixed` and `assigned_to_le_bits` (`native_gadget.rs:885-915`); `bytes32_from_low_high`, `into_coordinates` of a Weierstrass identity, `from_coordinates` (native `point_from_coordinates` panics on off-curve and on torsion through `into_subgroup`, `edwards_chip.rs:786-800`, `circuits/ecc/curves.rs:60-71`) all reject in both. The receipts show no `ok/violated` or `ok/synthErr` row on the corpus (`evidence/zkir-k-circuit-differential-92e8bdd3-2026-09-06c.txt:835`, `...-ext-2ffe2d1-2026-09-06c.txt:920`). The only misclassification found is finding 3 (rejection in both, wrong class); no witness the circuit accepts and K rejects was found.

## Coverage gaps

- No oracle evidence for finding 1 or for JubjubScalar canonicity: the typed `IrValue` interface cannot carry a non-canonical representative. A malicious-prover harness that bypasses `assign_incircuit` (hand-assigning limbs through `prove_unchecked` and a patched `Relation`) would be needed to observe the cell; absent that, the residual must be stated, not tested.
- `--inject` never targets a `public_input` / `private_input` register at guard 1 (`circuit-comparison-table.md:108-110`); finding 2 has no column.
- The D5 injection is exercised on three Native cells only (`evidence/...-92e8bdd3-2026-09-06c.txt:836`, cells hit `inject-unconstrained: A (D5) x3`); no guard-0 foreign-typed register is injected, and no guard-0 register that a consumer reads is injected on purpose.
- Hash-input overflow of an alignment atom is `undecided` in the walk (finding 3), so no receipt covers the `C` outcome.
- Native `from_coordinates` on an on-curve pair outside the prime-order subgroup (D1c, panic in `into_subgroup`) has no divergence case; `k01` covers parity and `f11` covers Curve25519 under D9.
- The `inputGate` type-mismatch path (finding 5) is reachable only under `job` and has no case.
- Chapter 08 states the `unconstrained` messages but no test asserts that a JubjubScalar declared input reports `unconstrained` on `inputGate` (the corpus shows it only on `test_ec_proof.zkir %s1` and `curve_jubjub.zkir %s`, both `public_input`/`private_input` registers per the receipt lists).

## Questions for the authors

1. How does the Compact compiler or the ledger bind a `public_input` register at guard 1 to the public transcript? If it is through an `impact` push of the same value, the K model could state that convention as a target-contract obligation; if it is only through transcript re-execution, the residual item of finding 2 is the honest statement.
2. Is `unconstrainedRegs` meant to be "cells the circuit leaves to the prover" or "registers whose witness value is a default the circuit does not enforce"? The Moriarty specification needs one of the two meanings; today the code implements the second and the prose suggests the first.
3. Does any Moriarty artifact encode a foreign-field or foreign-point value into the communications commitment or into `encode` outputs? If so, finding 1 is on the critical path of the commitment claim; if not, it can be a stated residual until the foreign surface is used.
