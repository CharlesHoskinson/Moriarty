# R3: the target contract and the static typing

VERDICT: BLOCKED — tier one's central guarantee ("every obligation met or not applicable ⇒ the program keys") is false on two one-instruction programs (a byte hash whose alignment needs more field elements than it is given; `reconstitute_field` with `bits = 0`), the provability sweep is built so that it cannot see either kind of contradiction, and chapter 16 states the two directions of the compiler-correctness theorem with the modelled-space inclusion the other way round from chapter 08.

## Findings

### 1. Blocker — alignment obligations omit the field-count check, so a program the contract passes fails keygen

- Files: `experiments/zkir-k/semantics/zkir-contract.k:160-168` (`defect(align(Op), I, _)`, `#alignDefect`), `experiments/zkir-k/semantics/zkir-static.k:214-231` (`#onlyAtoms`, `#hasCompress`, `alignmentOf`); chapter row `experiments/zkir-k/docs/16-compilation-target-contract.md:19`.
- K says: `alignment.persistent_hash`, `alignment.keccak256` and `alignment.sha512` fail only when the alignment has an `option` segment or a `compress` atom. `#alignDefect` receives the alignment alone; the operand list of the instruction is never consulted.
- Source of truth: `fab_decode_to_bytes_atom` in `/home/charl/Moriarty/repos/_build/ledger-92e8bdd3/zkir-v3/src/ir_vm.rs:133-137` returns `Synthesis("cannot decode field element from no data")` when a `field` atom finds no input left, and `:156-159` returns `Synthesis("cannot decode bytes from to little data")` when a `bytes { length }` atom finds fewer than `length / 31 + (length % 31 != 0)` inputs. Both depend on the instruction alone (the number of operands and the alignment), never on a value; the same code is at midnight-zkir 2ffe2d1 `zkir/src/ir_vm.rs:104+`, which `sha512` also goes through.
- Why it matters: the program `persistent_hash` with alignment `[field, field]` and inputs `["%a"]` (scratchpad `t/t01_align_short_field.zkir`) gets `ok (4 met, 10 n/a)` from `zkir_kast.py contract` and `keygen=panic ... Synthesis("cannot decode field element from no data")` from `zkir-circuit-oracle --keygen`; `keccak256` with alignment `[bytes 40]` and one input (`t02_align_short_bytes.zkir`) gets `ok (4 met, 10 n/a)` and `panic ... "cannot decode bytes from to little data"`. Tiers two and three do reject them (K `Inputs did not match alignment`, oracle `preprocess-error`), so the condition is also preimage-independent off-circuit (`zkir-ops.k:246`), which makes it a well-formedness fact the contract should state, not a witness fact. This contradicts `zkir-contract.k:44-48` and `docs/16:31` ("a program with every obligation met or not applicable keys") and the "0 contradictions" line of `evidence/zkir-k-provability-2026-09-06b.txt`, whose sweep only keys programs already in the corpus.
- Fix: in `ZKIR-STATIC` add `#alignFields(Segments) : Int` = sum over atoms of 1 for `fieldAtom()` and `(N +Int 30) /Int 31` for `bytesAtom(N)` (0 for `compressAtom()`, options already fail); change `#alignDefect` to take the operand list and fail with the Rust text when `lenOperands(Xs) <Int #alignFields(Segs)`. Surplus operands stay accepted (the crate ignores them in both stages). Add `t01`/`t02` to `corpus/handmade-negative/` and to `EXPECTED` in `tools/contract_corpus.py:68` and `NEGATIVE_CONTROLS` in `tools/provability.py:67`; consider the same check in `ZKIR-WF` (`zkir-syntax.k:353-365`), since `preprocess` rejects it for every preimage.

### 2. Major — `reconstitute_field` with `bits = 0` passes tier one, panics keygen and fails every preimage

- Files: `zkir-contract.k:158-159` (`defect(rfWidth(), ...)` requires `N >Int 248`), `zkir-syntax.k:359-360` (`#checkArity(reconstituteField)` same bound), `zkir-vm.k:390` (`checkBits(DV, #frBits -Int N)`).
- K says: any `bits` in `[0, 248]` is well formed and meets `width.reconstitute_field`.
- Source of truth: in circuit, `ir_vm.rs:1036-1040` calls `assert_lower_than_fixed(divisor, 1 << (FR_BITS - bits))`; with `bits = 0` the bound is `2^255`, which reaches `assign_less_than_pow2` in midnight-circuits 7.2.4 `src/field/decomposition/chip.rs:412` and trips `assert!((bit_length as u32) < F::NUM_BITS)`. Off-circuit, `ir_vm.rs:434` resolves the divisor with `Some(FR_BITS - 0) = Some(255)` and `:268` bails `Excessive bit bound` for every value.
- Why it matters: `t/t09_rf_0.zkir` (`reconstitute_field %a %b bits 0`) gets `ok (4 met, 10 n/a)`; `--keygen` gives `panic ... assertion failed: (bit_length as u32) < F::NUM_BITS at .../midnight-circuits-7.2.4/src/field/decomposition/chip.rs:412`. Tier two agrees with the crate on a preimage (`Bit bound failed` / `Excessive bit bound`, `zkir-ops.k:340`), so again only tier one is wrong. The other `bits = 0` cases are fine: `div_mod_power_of_two 0`, `constrain_bits 0`, `less_than 0` all key (`t07`, `t08`, `t10`).
- Fix: reject `bits = 0` (equivalently `#frBits -Int N >=Int #frBits`) in `#checkArity(reconstituteField)` with the Rust text `Excessive bit bound`, and in `defect(rfWidth(), ...)`; add the program as a divergence/negative case. Candidate upstream finding: the crate accepts `bits = 0` at load and rejects it in both stages.

### 3. Major — the "keygen performs exactly these checks" claim is false in the other direction, and the provability method cannot detect it

- Files: `zkir-contract.k:44-49`, `docs/16:31`, `tools/provability.py:67` (`NEGATIVE_CONTROLS`), `:229-235` (a failed contract not in the list is `not keyed`), `evidence/zkir-k-provability-2026-09-06b.txt` (summary line "0 contradictions").
- K/docs say: unknown-witness keygen "performs exactly these checks and no other before it has a witness ... a failed obligation names the instruction whose synthesis fails".
- Source of truth: `width.div_mod_power_of_two` and `width.reconstitute_field` cite `FR_BYTES_STORED * 8` in `ir_vm.rs`, which is the `preprocess` check (`ir_vm.rs:399`, `:418`); the circuit slices a 255-bit decomposition (`:1005-1023`) and bounds with `2^bits` (`:1025-1044`) and accepts up to 255. `width.constrain_bits` cites `assigned_to_le_bits` (`native_gadget.rs:894`, `nb_bits <= 255`) but `preprocess` bails at `n >= 255` (`:268`), and so does `ZKIR-WF` (`zkir-syntax.k:361-362`). The structural `wf` items (reassignment, duplicate input) are `IrSource::load`/`preprocess` facts; `Relation::circuit` uses `HashMap::insert` and checks neither.
- Why it matters: five programs whose contract fails key without error: `t03_divmod_250.zkir` (fails `wf`, `width.div_mod_power_of_two`; keygen `accepted k=9`), `t04_reconst_250.zkir` (`accepted k=9`), `corpus/handmade-negative/excessive_bits.zkir` (`constrain_bits 255`; `accepted k=9`), `reassignment.zkir` (`accepted k=4`), `duplicate_input.zkir` (`accepted k=9`). These are not contract defects (preprocess rejects each for every preimage, so the programs are unprovable), but the sentence in the header and chapter is wrong, and the receipt's "0 contradictions" is by construction: `provability.py` keys only programs whose contract is met plus a hand-picked list, so a "contract fails but keygen accepts" outside the list, or a "contract met but keygen fails" outside the corpus (findings 1 and 2), never appears.
- Fix: give each obligation the stage that enforces it (`keygen`, `preprocess`, `both`; as a fourth field of `obligation` or in the JSON export); rewrite `zkir-contract.k:41-49` and `docs/16:31` as "a program with every keygen-stage obligation met keys; a program with a failed preprocess-stage obligation is rejected on every preimage"; make `provability.py` key every parseable program, expect `accepted` when only preprocess-stage obligations fail and a panic/synthesis error naming the instruction otherwise (today the negative-control check is only `outcome in {panic, synthesis-error}`, `provability.py:87`, `:290`, not the instruction the chapter claims).

### 4. Major — chapter 16 states the soundness direction over an inclusion that chapter 08 states the other way

- Files: `docs/16:53`, `plan-iter3/PLAN.md:53`, `wiki/zkir-k-semantics-plan.md:104` (CLM-0763) versus `docs/08-constraints-and-verdicts.md:128-137`.
- Chapter 16 / PLAN say: "Soundness quantifies over the modelled space, which over-approximates what the real circuit accepts wherever a constraint is unmodelled" — i.e. accepted ⊆ modelled, which is what a compiler-soundness statement needs (every witness the circuit accepts is covered by the source-execution correspondence).
- Chapter 08 says: "any memory in the modelled witness space, with its public-input vector, is accepted by the circuit up to the residual list" — i.e. modelled ⊆ accepted; and its residual list is explicitly two-sided ("may accept a witness the model does not describe, or reject one it does", `:128`). The evidence cited (`--inject` an arbitrary value into an `unconstrained` cell and expect `accepted`, `witness_space` true ↔ `accepted`) tests modelled ⊆ accepted; the accepted ⊆ modelled direction is supported only by the cells of `circuit-comparison-table.md` where a `violated`/`synthErr` verdict must meet a rejection, and by the typing clause of `docs/08:120`, which asserts that the circuit places range, on-curve and cofactor constraints at assignment — a claim about the circuit, not about the typed witness interface, and one that finding f11 and midnight-circuits' `checked_in_subgroup` flag (`ecc/native/edwards_chip.rs:53-65`) show is not uniform across chips.
- Why it matters: a specification of Moriarty that quotes chapter 16 will assume the residual list bounds accepted ⊆ modelled; the residual list was written for the opposite inclusion. The two are not interchangeable: "prover-side panics" and "hash gadget internals" only weaken modelled ⊆ accepted; a chip that accepts an off-subgroup or non-canonical assignment only weakens accepted ⊆ modelled.
- Fix: state both inclusions as separate claims with separate residual lists and separate evidence columns; name the compiler-soundness direction as depending on accepted ⊆ modelled and list exactly which items (JubjubScalar canonicity, guarded-off cells, any chip assignment without a subgroup check) are its residual; mark the typing sentence of `docs/08:120` as an assumption to be checked per chip rather than a consequence of the typed `IrValue`.
- Same paragraph, completeness: the sentence quotes only "status `ok`", "the circuit accepts", "the public inputs"; the triple's second component (outputs) and the skips (finding 5) are missing, and the sentence mixes a claim the definition can prove (`job(P, Pre)` reaches `obs(...)`, `claims/spec-compiled-observable.k`) with a per-preimage test outcome (tier three). Write it as two clauses: a K-level reachability statement, and a circuit-level acceptance assumption discharged by the differential receipts.

### 5. Major — the observable semantics drops `pi_skips`, which the ledger turns into transcript ops

- Files: `zkir-vm.k:551-556` (`obs(Status, List, List)`, `observable`), `docs/16:41-53`; `tools/run_claims.py:61` shows the definition already has a `<skips>` cell.
- K says: `[[P]](pre) = obs(status, encoded outputs, pi)`; the chapter: "The memory, the verdicts and the witness space are the model's evidence for the triple, not part of the observation."
- Source of truth: `Preprocessed.pi_skips` (`ir_vm.rs:74`, filled at `:512-523` for every guarded-off `impact`), returned by `ProofPreimage::prove` (`transient-crypto/src/proofs.rs:762-774`), and consumed by `ledger/src/prove.rs:279-288`, which inserts `Op::Noop { n: skip }` into the transaction's guaranteed and fallible transcripts. The skips therefore change the transaction the source semantics must predict.
- Why it matters: two preimages with the same `(status, outputs, pis)` but different skips produce different transactions; a compiler-correctness statement over `obs` cannot say the transcript is the predicted one, and the `impact` guard, the one place the compiler encodes control flow into the public inputs, is exactly what the skips record.
- Fix: `obs(Status, List, List, List)` with `<skips>` as the fourth component (and in `spec_compiled_observable`); state in the chapter that `pi[0]` (binding input) and `pi[1]` (commitment, when enabled) are in `pis`, that the commitment opening is existentially quantified in any statement, and why the memory is not observable.

### 6. Minor — `width.constrain_bits` can never fail, and its documented bound is the wrong stage

- Fix: with the stage tags of finding 3, make the row read "preprocess: `bits < 255`; circuit: `bits <= 255`" or drop the obligation; keep the reconstitute row with the `bits = 0` case of finding 2.

### 7. Minor — a binding after an unsupported pair is a guess that later obligations report on

- Files: `zkir-static.k:120` (`condSelect`), `:138` (`add`), `:139` (`mul`), `#firstKnown` at `:93-95`.
- `bindOuts` binds the output to the first known operand type even when the two known types differ (an arm the circuit does not have). `circuit.static.dispatch` fails the instruction, but the other walks continue with the guessed type: `add %j %n -> %o ; output %o` with `%j: JubjubPoint`, `%n: Native` and signature `[Native]` fails `circuit.static.dispatch` at instruction 0 and `circuit.static.output` at instruction 1 with "operand has static type JubjubPoint", the guessed half of a pair that never synthesises. The verdict is right, the second message is a guess, which `docs/16:29` says never happens.
- Fix: in the binary arms bind `unknownT()` unless both operand types are known and equal (or `#pairDefect` is empty).

## Coverage gaps

- No corpus program has a byte hash whose alignment consumes more field elements than the instruction supplies (finding 1), on either surface; `sha512` on the extension surface has no short-alignment case.
- No corpus program has `bits = 0` on any of `constrain_bits`, `less_than`, `div_mod_power_of_two`, `reconstitute_field` (finding 2 is the failing one); none has `constrain_bits 254`, `div_mod_power_of_two 248` at the boundary (both key, `t14`, `t12`).
- The provability sweep never keys a program whose contract fails outside the curated list (finding 3), so no receipt exercises a preprocess-stage failure against keygen.
- No test of the "guess" path of finding 7 (a mixed-type binary instruction followed by an `output` of the bound register).
- `do_communications_commitment = true` with non-Native inputs or outputs is not keyed by the sweep (the commitment block encodes every input and output in circuit, `ir_vm.rs:1173-1199`; all `encode_incircuit` arms exist, so no failure is expected, but it is unexercised).
- Programs whose `optimal_k` exceeds the available parameters (`params/bls_midnight_2p{0..16}` present, the receipt says `k=0..17`) or `optimal_k`'s search bound: the contract states no size fact, and `params-unavailable` is silently excluded from contradictions (`provability.py:240`).
- Extension negatives at keygen: `not`/`assert`/`constrain_to_boolean`/`impact` on a `Bool` operand, `nth`/`slice` on a `Byte`, `concat` with a `Native` — each is a K dispatch defect (`zkir-contract.k:288-296`, `zkir-ext.k:429-468`) with no oracle receipt.

## Questions for the authors

1. Should the alignment field count (finding 1) be a `ZKIR-WF` error as well as a contract obligation? `preprocess` rejects it for every preimage, which is the criterion the WF header (`zkir-syntax.k:290-300`) uses.
2. Is a stage tag per obligation (finding 3) acceptable as a fourth field of `obligation`, or should the split be by name (`preprocess.*` / `keygen.*`)? The Moriarty specification will need to know which failures are keygen failures.
3. Is `reconstitute_field bits = 0` worth an upstream report alongside K1–K6? Load accepts it, both stages reject it, and one stage by an assertion.
4. For finding 4: which chips constrain subgroup membership at assignment (`checked_in_subgroup` in `edwards_chip.rs:53-65`)? The typing clause of chapter 08 is the only support for accepted ⊆ modelled on points.
5. Should tier one carry a circuit-size fact (`optimal_k`, or an upper bound on rows) so that a compiler can state provability against a named SRS, or is that deliberately an environment concern?
