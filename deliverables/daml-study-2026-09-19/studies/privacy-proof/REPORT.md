## Explanation: knowledge, authority, and validity are different

Daml's most transferable distinction is between knowing a contract, being entitled to act on it, and proving that a ledger transition conforms to its code. Explicit disclosure supplies authenticated contract data for command interpretation without relaxing the action's authorization. A disclosed price quotation still needs application checks for the expected issuer and asset. Cryptographic authenticity does not establish that the price is current, economically fair, or true of the external world. The example itself leaves enforcement of one active price quotation outside its model. [DP03; [explicit disclosure](https://docs.canton.network/appdev/deep-dives/explicit-contract-disclosure)]

The precise privacy unit is an action tree. A party is an informee according to its role in the node; witnesses also include informees of containing actions. Consequently, someone entitled to a parent action sees its descendants even when they are not a stakeholder of those descendant contracts. A contract observer sees creation and consumption, but does not automatically see every non-consuming exercise or fetch. Contract observers and choice observers are different declarations. For pre/post-consuming choices compiled through a non-consuming outer action and an Archive subaction, a contract observer may see only the archival subaction. [DP01; [detailed ledger model](https://docs.canton.network/overview/reference/ledger-model-detailed)]

This corrects two tempting readings of the introductory pages. “Only stakeholders see contracts” has deliberate divulgence exceptions. “An audit choice returns a summary, so the auditor sees only the summary” is not a privacy theorem: the auditor's action/input visibility and fetched descendants can expose the underlying data. To preserve a private document, design the statement and disclosure relation explicitly; changing the result type alone is insufficient. [DP01, DP05]

A second correction concerns metadata. The [privacy overview](https://docs.canton.network/overview/learn/privacy-model) uses strong no-metadata-leakage language, while its timing-attack section already acknowledges possible inference from activity. The detailed model is more precise: ordinary projections assume a party observes through its participant's Ledger API. Network patterns and some on-wire data can reveal transaction shape and parties beyond that projection. Its shape abstraction includes informees, encoding sizes, and required confirmers, while content remains confidential. This is not a contradiction to resolve by choosing the stronger slogan; confidentiality must name its observation boundary. [DP02]

Participant hosting is another boundary: the hosting validator sees its hosted parties' data. Separation between parties' authorized API views is not secrecy against the operator hosting both parties. Nor is encryption and selective replication the same mechanism as zero-knowledge proof verification. A future Midnight implementation needs its own public-input, witness, error, timing, and continuation leakage model. [DP02, DP13]

Divulgence also differs from reusable access. Immediate divulgence does not automatically entitle a party to use the contract in a later command submission. A non-stakeholder may learn creation without learning later archival. Current documentation therefore requires explicit disclosure for later use where needed. Off-ledger disclosure can avoid broadcasting who else received it; adding observers exposes the stakeholder set to those observers. Neither mechanism erases information previously disclosed. [DP04]

The ledger model divides validity into consistency, conformance, and authorization. Consistency concerns creation/use/consumption order. Conformance concerns the whole action tree required by the code, including all mandatory consequences. Authorization relates required parties to the action's enclosing context. The latter cannot in general be recovered from an isolated subtree. Internal authorization is different from authorization at a projected root. This matters for PCD: a proof that a subtree is internally valid cannot stand in for the authority and provenance supplied by its actual parent. [DP06]

Canton's Virtual Global Ledger guarantee is explicitly relative to honest parties and configured protocol/BFT assumptions. The detailed model describes colluding signatories creating inconsistent spends visible to different honest witnesses. An observer's isolated valid view is not a global anti-equivocation theorem for all issuers. State the honest-signatory and protocol assumptions rather than importing an unconditional global invariant. The interoperability section also labels itself a vision under active development; its cross-ledger examples are not deployment evidence for arbitrary independent-chain atomicity. [DP07, DP14]

## Reference: identity and upgrades

| Identity or compatibility concept | Meaning established in the sources | Consequence for Moriarty |
|---|---|---|
| Package ID | Content-addressed Daml-LF identity | Hash recognition identifies code; it is not a semantic correctness certificate |
| Package name/version | Upgrade lineage and API selection mechanism | Signing a symbolic name alone can leave behavior unresolved |
| Contract ID | Identity of stored immutable contract data; disclosure authentication hashes relevant contents | Old contract identity does not freeze which compatible code version is used |
| Contract key | Stable application lookup attribute; current Canton 3.x permits duplicates | A key is not automatically unique identity or proof that no competing state exists |
| Interface definition | Fixed view/method/choice surface | The implementing methods/view can change under SCU |
| SCU compatibility | Static structural checks plus runtime conversion/metadata/ensure checks | It is not semantic equivalence or continued satisfaction of an earlier intent |
| Package vetting | Participant-side willingness/ability to use packages | It is not a proof theorem or a Moriarty-wide developer admission rule |

Smart Contract Upgrade permits adding optional fields and some constructors, new choices and interface instances, and changing choice bodies/controllers and interface implementation bodies. At runtime, missing added fields become None; dropping populated new fields fails. Signatory/stakeholder metadata is recomputed and constrained, and ensure is re-evaluated. The detailed reference uses signatory/stakeholder equality; redundant observer declarations already covered by signatories can be removed according to the extended guide. These checks preserve specific structural/data properties, not every economic property. [DP08, DP10; [SCU reference](https://docs.canton.network/appdev/deep-dives/smart-contract-upgrading-reference)]

Dispatch must be distinguished by site. A non-interface fetch/exercise inside a choice follows the compiled dependencies. Interface operations and eligible top-level commands can use dynamic package selection. The detailed reference gives a decisive example: the same v1 contract implementing an unchanged interface returns 1 under one implementation preference and 2 under another. A signed condition over an interface result can therefore change meaning unless its allowed implementation/evolution relation is bound. [DP09]

The sources contain different simplifications of default package preference, including “latest uploaded,” selection known to involved participants, and the introductory module's focus on referenced code. We do not turn these into one universal release-independent algorithm. The robust conclusion is the static/dynamic distinction and the need to record explicit target/preference when exact semantics matter. Current source pages also mix historical version guidance; an implementation test must pin actual SDK and Canton versions. [DP09; [SCU guide](https://docs.canton.network/appdev/deep-dives/smart-contract-upgrade)]

Current [contract-key documentation](https://docs.canton.network/appdev/modules/m3-contract-keys) is especially relevant to private-state proofs: multiple active contracts may share a key; lookup prioritizes new contracts in the current transaction, then explicit disclosures in submitted order, then participant-known contracts without a guaranteed order. A lookup returning None can mean nothing is visible, not that nothing exists globally. A proof over a local projection cannot conclude absence of a hidden liability, reservation, or revocation without additional authenticated completeness rules. [DP11]

## Proof and certified-basis reference

The [2023 paper](https://arxiv.org/abs/2303.03749) presents Daml-LF typing and big-step semantics, a separate transaction authorization judgment, compiler structure, CEK runtime interpretation, and ledger integrations with different trust properties. It describes re-typechecking generated and loaded LF and checking authorization before evaluating protected contract logic, partly to prevent error-message leakage. These are concrete assurance mechanisms, but the paper does not establish a machine-checked whole-compiler theorem or a ZKIRv3 proof backend. Formal notation, code hashes, repeatable builds, and runtime validation are distinct from such a theorem. [DP12–DP13]

The paper's first-order serializable boundary keeps ledger arguments/results free of functions, so users cannot inject arbitrary higher-order computation as contract data. Yet Daml-LF remains Turing complete through recursive top-level definitions and non-monotone datatypes. The authors discuss runtime cost control rather than language totality. Moriarty can learn from the explicit code/data boundary without inheriting unrestricted recursion; its supported total/bounded profile must be defined independently. Termination still does not imply financial correctness, bounded practical cost, or eventual completion of a staged business workflow. [DP13]

For the certified-basis agenda, a small set of precise operations with composition judgments is useful inspiration. It does not certify any proposed Moriarty jet. Each optimized primitive needs value, rejection, authority, effect/frame, and cost correspondence under explicit preconditions; ZKIRv3 additionally needs exclusion of invalid satisfying witnesses, not just an honest witness generator. Changed instance behavior illustrates why identical interface types cannot substitute for that certificate. See [SECURITY-PCD.md](SECURITY-PCD.md) for concrete candidate judgments and adversarial traces.

Daml is the language and contract model; Canton supplies participant/runtime/synchronization behavior; Splice and token/dApp standards provide ecosystem-specific interfaces and workflows. None is itself the Midnight backend. Application portability asserted for Daml ledger integrations means integrations implementing its model, not that arbitrary Daml contracts already compile to Midnight or that Canton's privacy topology transfers unchanged. [DP15–DP16]

## Tutorial: a private, staged conditional settlement

This is a conceptual Moriarty design test, not executed Daml or implemented Moriarty code.

1. Buyer signs a request binding asset identity, amount, recipient, fee and liability bounds, required document predicate and attestor, version policy, deadlines, and allowed partial/failure outcomes. A document commitment alone neither reserves funds nor creates a delivery proof.
2. A funding stage consumes scoped spending authority and records escrow/reservations plus residual obligations. No projection-local missing-key result is accepted as proof there are no other reservations.
3. An evidence stage receives the document or an appropriate proof, validates exact subject, issuer, freshness and revocation policy, and exposes only the authorized statement. Possession of the document does not grant seller or buyer spending authority. Future continuations record how an authorized prover can obtain the witness; a private proof is not a data-availability guarantee.
4. A partial settlement stage consumes one permitted allocation and records the delivered amount, fees and remaining duty. Each callback/continuation uses its own bound authority and receipt identity. Repeated proofs cannot spend the same allocation again.
5. If a remote delivery remains unknown when a deadline passes, record unknown outcome and preserve the relevant duties. A compensation/refund stage needs its own justified conditions; it cannot infer nonexecution from timeout or simulate rollback of a completed remote transfer.
6. If an implementation upgrade arrives between funding and settlement, either use the bound old semantics, establish the specifically authorized refinement/migration, or obtain fresh consent. A same-name package and same interface do not suffice. Migration must retain the outstanding duties and permitted recovery paths.
7. Lower each permitted source outcome to the real Midnight phases and pinned ZKIRv3 relation. Guaranteed effects retained after a fallible-stage failure must appear in the public/private effect commitments and continuation obligations.

This accommodates partial transactions, contingent settlement, and NEAR-style asynchronous patterns while keeping Midnight as the execution target. It does not assume one global rollback boundary.

## How to reproduce the claim review

Start with the hashes and line ranges in claims.json and verify the captured bytes against sources.json. Read the complete privacy and detailed ledger-model pages together. Draw the action tree for an audit/fetch example and compute informees, witnesses, and projections before describing what the auditor learns. Then rerun the reasoning with API-only versus network/hosting adversaries.

For upgrades, distinguish contract creation package, choice-body dependency, interface definition, selected implementation, and backend preference. Use the reference's 1-versus-2 example as the minimal semantic-drift counterexample. A later implementation experiment should pin versions and test the old-data/new-code matrix, metadata mismatches, unsupported downgrade, and stale authorization. This study did not run those experiments.

For proof review, inspect paper pages 7, 9, and 11 visually: serializability, authorization formulas, and runtime sequencing are layout-sensitive evidence. Test any proposed PCD induction against missing parent authorization, forged funded base state, replayed resource, changed implementation, private absence, and failure after a retained effect. Record source-supported observation, design inference, executed example, and proved theorem separately.
