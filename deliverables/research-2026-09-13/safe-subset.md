# Targeting Compact: formalise a subset, own the image, or bypass?

**Recommendation.** Define the target as the image of our own lowerer, not as a fragment of Compact. Concretely: write down the grammar of what Core-to-Compact emits (a "Mori-Compact" core), enforce it with a lint pass on every emitted program, and specify the lowering as a translation relation between Core and that image, in the style of the Plutus certifier, so the specification survives changes to the lowerer's heuristics. Attach a semantics to the image only per pinned Compact toolchain version, validated by differential testing against `compactc`, and do not attempt a mechanised semantics of Compact itself. Do not bypass Compact yet: ZKIR is also versioned (v3 arrived with toolchain 0.33) and the 0.31 release notes show the compiler absorbing proof-construction hazards that we would otherwise inherit. The evidence below is unambiguous on one point: every mechanisation of a fragment of someone else's moving language that I could find is now pinned to the standard it started with, and the only formalisations that stayed alive are those whose owners also owned the language (CompCert's intermediate languages, WebAssembly, Plutus Core).

## 1. JSCert, JSRef and the subset lineage

**JSCert** (Bodin, Charguéraud, Filaretti, Gardner, Maffeis, Naudžiūnienė, Schmitt, Smith, "A Trusted Mechanised JavaScript Specification", POPL 2014, https://dl.acm.org/doi/pdf/10.1145/2535838.2535876) mechanised the ES5 core language, excluding most native libraries and parsing. The specification is about 3,000 lines of Coq in a "pretty-big-step" style; the JSRef interpreter is about 2,000 lines, and the proof that JSRef satisfies JSCert is 3,500 lines. Validation was by running JSRef on test262. The paper's own maintenance claim is that because one line of ES5 pseudo-code maps to one or two rules, "if commands need changing, as inevitably they will for future standards, it is relatively straightforward to see which part of JSCert needs changing", and it ends with the hope of a mechanised ES7. The repository (https://github.com/jscert/jscert) tells the rest: 1,616 commits, the last substantive work in December 2016, README updates in 2018-19, and a single 2024 commit relocating a dependency. The README still requires Coq 8.4.6. The project domain jscert.org has lapsed and now serves a casino site. The successor JSExplain (https://github.com/jscert/jsexplain) is marked "not maintained anymore" and points to an Inria GitLab I could not retrieve (bot wall). JSCert never moved past ES5.

**λJS** (Guha, Saftoiu, Krishnamurthi, "The Essence of JavaScript", ECOOP 2010, https://cs.brown.edu/~sk/Publications/Papers/Published/gsk-essence-javascript/paper.pdf) is the model for the "small core plus desugaring" strategy: a three-page core calculus, all of JavaScript except `eval` desugared into it, core and desugaring both mechanised (Coq and Redex). The desugaring was not proven correct. The paper's evidence is a 100-line interpreter run against the Mozilla test suite and compared with SpiderMonkey, V8 and Rhino. JSCert's authors make the point explicitly in a footnote: proving the λJS encoding correct needs a formal semantics of the source first, which did not exist. Repository https://github.com/brownplt/LambdaJS: last real commit June 2013, archived February 2022; its own README says λJS "roughly models ECMAScript 3" and ES5 was "considerably more complex, so we decided to develop it from scratch".

**S5** (Politz, Carroll, Lerner, Pombrio, Krishnamurthi, "A Tested Semantics for Getters, Setters, and Eval in JavaScript", DLS 2012, https://dl.acm.org/doi/pdf/10.1145/2384577.2384579) is that rewrite for ES5: a 500-line OCaml interpreter and a 1,000-line desugarer, again validated by test262 (70% of all ES5 tests, 98% on strict-mode-specific tests) rather than by proof. Repository https://github.com/brownplt/LambdaS5: last commit October 2015, the year ES6 shipped.

**JSIL / JaVerT** (Fragoso Santos, Maksimović, Naudžiūnienė, Wood, Gardner, "JaVerT: JavaScript Verification Toolchain", POPL 2018, https://dl.acm.org/doi/pdf/10.1145/3158138; "JaVerT 2.0", POPL 2019, https://dl.acm.org/doi/pdf/10.1145/3290379) is the most careful subset work. The subset is ES5 Strict, chosen deliberately; JS-2-JSIL compiles it to a goto language whose heap model subsumes JavaScript's so the logic translator's correctness is "straightforward". The compiler itself is validated by passing 8,797 applicable test262 tests, and the paper rejects using S5 as an intermediate because relating two logics through it "would be a difficult task". JaVerT 2.0 states that "additional constructs are likely to be needed to support ES6". The code lives on as Gillian-JS (https://github.com/GillianPlatform/Gillian, active, last commit September 2026) but its README still describes it as "Gillian for ES5 JavaScript". The framework is alive; the JavaScript fragment is frozen at 2009.

**KJS** (Park, Ştefănescu, Roşu, PLDI 2015, https://fsl.cs.illinois.edu/publications/park-stefanescu-rosu-2015-pldi.pdf) took four months for one PhD student and passed all 2,782 core test262 tests; the paper criticises JSCert-style layered semantics as "huge efforts that require maintenance as the language evolves". Its repository (https://github.com/kframework/javascript-semantics) has had no commit since February 2015. It is ES5.1 forever.

## 2. The maintenance verdict

Four independent groups, three proof assistants, one outcome. No formal JavaScript semantics was ever carried across a standard boundary; each was rewritten from scratch or stopped. That happened against a language that changed once in six years. Compact's toolchain moved from 0.31.0 (28 April 2026, language 0.23.0) to 0.34.0 (18 August 2026, language 0.26.0, ZKIR v3): three language versions and a circuit-IR version in sixteen weeks (https://docs.midnight.network/relnotes/compact/toolchain-0.31.0, .../toolchain-0.34.0). Worse for a subset strategy, 0.31 changed "the ZKIR representation of operations in conditional branches" for downcasts and byte conversions without changing syntax: the meaning of programs already inside any plausible subset moved. A formalised Compact fragment would have been wrong the day it was finished. Our own pins (Compact 0.31.1 in use, 0.34.0 recorded and deliberately unused) already show us paying this tax informally.

## 3. Image-of-the-compiler as a design

**CompCert** (Leroy, "Formal verification of a realistic compiler", CACM 2009, https://xavierleroy.org/publi/compcert-CACM.pdf; "A formally verified compiler back-end", JAR 2009, https://xavierleroy.org/publi/compcert-backend.pdf) specifies each of its eight intermediate languages in 300 to 600 lines of Coq versus 1,100 for Clight, and each language is exactly what the preceding pass emits. Cminor is presented as "a stripped-down, typeless variant of C" with a two-type type system; nobody writes it by hand, so it carries no accommodation for humans, and the preservation theorems are stated over source programs, so ill-formed Cminor that the front-end never produces is simply outside the theorem. That is the "only our compiler writes this" property in use, and it is why the per-language specification cost is small (https://github.com/AbsInt/CompCert, active, release 3.18 in September 2026).

**WebAssembly** (Haas, Rossberg, Schuff, Titzer, Gohman, Wagner, Zakai, Bastien, PLDI 2017, https://raw.githubusercontent.com/WebAssembly/spec/main/papers/pldi2017.pdf; CACM version https://cacm.acm.org/research/bringing-the-web-up-to-speed-with-webassembly/) is the industrial case. The designers say it is the first industrial language "designed with a formal semantics from the start", that the type system is "by design, embarrassingly simple", and that pushing structured control flow onto producers made "many algorithms in engines much simpler". The small spec was achievable because the language was a compilation target with no human-ergonomics obligations. Watt ("Mechanising and Verifying the WebAssembly Specification", CPP 2018, https://www.cl.cam.ac.uk/~caw77/papers/mechanising-and-verifying-the-webassembly-specification.pdf) mechanised it in about 700 lines of Isabelle and found that the draft type system was unsound in two places; because he had the spec authors' ear, the spec changed. That is the ownership condition again.

**Racket** defines "fully expanded programs" as a closed grammar of a dozen core forms (https://docs.racket-lang.org/reference/syntax-model.html); the language users write is unbounded, the language the expander emits is fixed. This is the image-of-the-elaborator pattern in a mainstream language, though I found no proof that Racket's expander preserves meaning (Flatt's "Binding as Sets of Scopes", POPL 2016, https://www.cs.utah.edu/plt/publications/popl16-f.pdf, formalises binding, not semantic preservation).

## 4. Certified desugaring

The strongest precedent is close to home. **"Translation Certification for Smart Contracts"** (Krijnen, Chakravarty, Keller, Swierstra, 2022, https://arxiv.org/pdf/2201.04919) certifies the Plutus Tx pipeline from PIR to Plutus Core in Coq by specifying each pass as a purely syntactic translation relation, deliberately non-deterministic where the compiler uses heuristics, so the certifier is "robust in the face of an evolving compiler implementation". The Plutus Core metatheory is mechanised in Agda (https://github.com/IntersectMBO/plutus/tree/master/plutus-metatheory). This is the design I recommend for Core-to-Mori-Compact: relations, not a verified function, so the lowerer can change without the proof restarting. Neither λJS nor S5 nor JaVerT proved their desugaring; all three relied on conformance suites.

## 5. The counterargument

Safe subsets of JavaScript have a poor record even when frozen. **ADsafety** (Politz, Eliopoulos, Guha, Krishnamurthi, USENIX Security 2011, https://www.usenix.org/legacy/events/sec11/tech/full_papers/Politz.pdf) type-checked ADsafe using λJS and found fresh exploits in a 1,800-line runtime that had already been audited. **Caja** (https://github.com/googlearchive/caja) was archived by Google in January 2021 with the note that it "has not been actively maintained or developed to keep up with the latest research" and had accumulated unpatched vulnerabilities. Subsets rot; their guarantees rot faster.

The strongest argument against my recommendation is that an image is only as meaningful as the semantics attached to it, and that semantics is still Compact's. Restricting what we emit shrinks the surface but does not remove the dependency: Compact 0.31 changed the meaning of conditional-branch operations without changing syntax, so a lint pass proving "we are inside the image" would have passed while the circuits changed underneath. The image strategy therefore buys a small, owned specification and a certifiable lowering, but the last link, image to ZKIR, remains trust-by-testing per pinned toolchain version. If that residual is unacceptable, the honest alternative is to bypass Compact and target ZKIR directly, accepting that ZKIR is versioned too and less documented, and that we would take on the proof-failure workarounds the Compact team currently absorbs for us. On present evidence that trade is not yet worth making.
