## Exact TypeScript boundary

The authoritative program is external `.mori` source compiled under an explicit profile. TypeScript provides host tooling and proposed transaction transport; TypeScript callbacks do not define trusted financial semantics. Familiar punctuation confers no JavaScript compatibility: no `number`, coercion, object identity, prototype lookup, mutable closure or implicit `await` semantics enter the admitted program.

If an inert tagged template is later provided, define whether raw template characters or cooked JavaScript strings form the source and commit those exact extracted bytes. Prohibit interpolation; specify escaping of backticks and backslashes and map source offsets back to the enclosing file. Extraction must parse without executing the enclosing module. Calling a tag at runtime is insufficient to establish this property because module imports and surrounding expressions may already have effects. A host must not be able to replace the approved tag with arbitrary behavior and thereby obtain a trusted artifact. The trusted output is the checked source/Core artifact, not the host binding's name or object type.

A future builder may produce bounded declarative AST data only; AST validation remains authoritative even when TypeScript types are bypassed. Embedding is optional integration work and not a prerequisite for the requested first authoring capability.

## Source checks and substantive challenges

**Source fact checked against U02 extraction, §5.3.1–5.3.2, PDF 36–39:** Auction correctness is 7/10 versus 2/10; p≈0.015 concerns participants claiming completion while p≈0.070 concerns overall correct completion. One Obsidian participant refunded the wrong bidder. Casino's four compiling Obsidian solutions all misused `disown`, and no Obsidian solution was fully correct. One Obsidian participant's data were discarded for a compiler bug; task opportunity depended on remaining session time. Thus the atlas is appropriately cautious, but any short summary must preserve compiler maturity and unequal opportunity as limits on comparative Casino performance. The strongest actionable inference is to observe unsafe repair behavior and include recipient correctness, not to derive an effect size or demand more annotations everywhere.

**Source fact checked against U04 extraction, conclusion/future work, PDF 13–14:** static typing favored three tasks and dynamic typing two; the authors explicitly propose later experiments separating annotation effects from checking and studying inference. Consequently the REPORT's evaluation suggestion to compare explicit versus inferred *public* types conflicts with its preferred explicit-boundary policy unless presented as a deliberately separate research question. My first pilot keeps public financial interfaces explicit and varies only local inference. U04 cannot decide that experiment in advance.

**Source fact checked against U05 extraction, §§4.1–4.3, PDF 8–9:** incorrect quiz interpretations were 17.28% versus 6.17%, n=27. Historical course comparison changes access to previous programs and offline compilation. Six non-completers could not get past basic structural compiler errors; those errors were not enhanced. Inference: Moriarty should cover common initial setup and grammar failures as well as impressive domain errors. Selecting diagnostics solely for financial severity can leave first-time authors unable to reach the financial task. This need not become a new editor platform: source locations, a runnable minimal example and concise diagnostic coverage are sufficient initial work.

## Questions and disagreements for the formal/effects panel

1. I favor explicit boundaries and local inference; do you require programmers to write full effect rows or residual-work annotations at every local call? Explain the financial error such repetition prevents. Prefer inferred conservative summaries with declaration-site bounds when equivalent checking is possible.
2. The REPORT's `next.outstanding = ...` example leaves repeated writes and tentative-state reads underspecified. Can we define a small, deterministic update discipline with a clear duplicate-write diagnostic? Do not sell TypeScript familiarity before resolving its most misleading semantic resemblance.
3. Residual duties must be explicit in the language semantics and visible in preparation output. Must authors manually reconstruct every unchanged duty? I oppose this as the default if automatic semantic carry-forward plus explicit authorized discharge is possible; forced boilerplate creates omission and repair pressure. This is a proposed usability tradeoff, not a proof of that design.
4. Which minimum bounded data, schedule and composition facilities are necessary to avoid a loan-only language? Rejecting general handlers must not become a reason to leave pending redemptions, ACTUS lifecycle events or required private composition without an accountable route.
5. Content identity is valuable, but do not require an entire Unison-style database or a five-hash lesson before the first payment. Can default output show name, meaningful change and acceptance stage, with full commitment details available on demand? Signed commitment completeness remains mandatory underneath.

A formative pilot should ask participants to explain and repair a payment, then handle a partial fill with fees and a surviving entitlement without a worked solution. Report incorrect financial completion, abandonment, assistance and confidence separately from elapsed time. Stratify TypeScript, functional-programming and financial experience. All of this remains specified-only; the panel may converge on a proposal while developer-usability superiority remains unestablished.
