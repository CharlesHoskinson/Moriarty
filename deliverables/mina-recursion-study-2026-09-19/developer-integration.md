## Source findings

**D01 — Proof objects and verification have different meanings.** `ProofBase.shouldVerify` starts false. `Proof.verify()` sets it true; `verifyIf(condition)` sets it to that condition. The comments say these methods are meant for circuits and have no verification effect outside them. `toJSON` includes public input/output arrays, maximum proof count and encoded proof. `fromJSON` parses/reconstructs a proof object; it does not invoke cryptographic verification. `ZkProgram` ultimately passes each declared proof's public statement, proof bytes and `shouldVerify` flag to Pickles. An object named Proof or a successful parse is therefore not a validity judgment. [proof.ts:25–68,125–159; zkprogram.ts:935–995]

**D02 — Public statement binding is explicit.** Host `verify` forms a statement from public input and output fields and invokes Pickles with the actual verification-key data. The illustrative recursive program separately calls `earlierProof.verify()` and constrains its public input plus one to the new input; its base case constrains input to zero. The recurrence is application code, not an automatic consequence of recursion. This small example does not authenticate funding, asset identities or financial history. [zkprogram.ts:103–147; examples/zkprogram/recursive-program.ts:3–23]

**D03 — Dynamic key integrity is not key authorization.** DynamicProof supports in-circuit supplied VKs, unlike baked-in Proof keys. Its documentation explicitly assigns key authorization to the application. The implementation reconstructs a circuit VK and asserts its computed hash equals `vk.hash`. This links key data to key identity; it does not establish that the chosen relation is permitted by the user's program. The standalone host verifier explicitly does not check that a VerificationKey object's data and claimed hash agree: it uses `.data`. A separate `VerificationKey.checkValidity()` API checks that consistency. [proof.ts:204–254,269–296; zkprogram.ts:949–970; verification-key.ts:32–44; zkprogram.ts:103–134]

**D04 — Feature compatibility is an independent contract.** DynamicProof declares input/output types, `maxProofsVerified` and feature flags. Flags identify custom gates and runtime tables; undefined is a “maybe” setting with documented proving overhead. Derivation considers all methods and can set differing flags to maybe. Compatible shape does not imply semantic authorization. In the inspected implementation, the side-loaded tag includes child proof count, input/output field counts and feature configuration. [proof.ts:208–254; feature-flags.ts:17–32,67–133; zkprogram.ts:1004–1018]

**D05 — Parent fan-in and child-proof shape are different bounds.** The inspected method compilation rejects more than two proof arguments and recommends a binary tree for larger merges. DynamicProof's `maxProofsVerified` describes the child circuit's own recursive proof shape; it is not the total history length or the number of all ancestors. Binary aggregation needs its own history/accounting relation and cannot erase common-ancestor overlap, multiply budgets or invent a complete branch roster. [proof.ts:218–219; zkprogram.ts:998–1018]

**D06 — Current-state binding is a ledger precondition, not a proof inference.** State.get documents that reading alone does not constrain current on-chain state. `getAndRequireEquals()` combines reading with a node-checked equality precondition. The framework checks unconstrained reads and exposes an explicit danger-zone `requireNothing` escape. In offchain-state settlement the code (1) requests proof verification, (2) binds stored current commitments to proof.publicInput, (3) requires account actionState to match proof.publicOutput.actionState, then (4) sets new commitments. This is a concrete proof-plus-state interface, not a general claim of finality or arbitrary economic correctness. [state.ts:26–73,328–331,422–435; actions/offchain-state.ts:437–450]

**D07 — Production proof mode must be evidence.** `ZkProgram.compile({proofsEnabled:false})` returns an empty verification key. In that mode the prover path evaluates the method and creates a dummy proof, and the program-specific `verify` function immediately resolves true. The default is proving enabled, but a setter can change the mode. This is an explicit testing mechanism, not a demonstrated production bypass. It means a green program.verify result without mode/configuration evidence cannot establish real cryptographic verification. Distinguish this program-specific method from standalone host `verify`. [zkprogram.ts:317,392–430,444–470,547–560,591–594]

**D08 — Cache hits are build artifacts, not certificates.** The cache stores SRS/basis data and step/wrap proving/verifying keys. Filesystem lookup checks a header unique ID and reads data. Header IDs include program/method/index/hash and serialization type; read failures can become cache misses. The cache wrapper itself does not provide authenticated content provenance or prove correspondence to the intended source. This is not evidence that malicious cache bytes can produce accepted invalid proofs; deeper key validation and cryptographic consequences were not audited. [cache.ts:10–24,59–114,124–150,173–211; prover-keys.ts:43–89,124–151]

**D09 — Auxiliary results are outside the ordinary public statement unless constrained through it.** The program exports proof.publicInput/publicOutput and returns auxiliaryOutput separately. The rule stores auxiliary output in a prover-only context, while the returned Pickles statement contains publicOutput and predecessor statements. A field returned next to a proof must not automatically be treated as proved. Bind relevant effect/delivery data into the statement or a constrained commitment with authenticated opening. [zkprogram.ts:497–522,973–995; proof.ts:61–68]

**D10 — A useful source-level counterexample occurs even in an example.** `side-loading/dynamic-keys-merkletree.ts` compares `previous.publicOutput` to current fields and checks the child VK's Merkle inclusion, then calls `proof.verify(vk)` on the child. It does not call `previous.verify()` or `verifyIf()` in the method. Combined with D01's default-false flag, the source does not request recursive verification of that previous proof merely by reading its fields. The key-addition method also explicitly comments that production use needs access control. This is a bounded example-code finding, not an executed exploit or claim about Mina deployments. It motivates a hostile test separating predecessor field consistency from predecessor verification and key-set membership from authority to update that set. [example:77–131]

## Concrete additions to existing ZR requirements

No new backend or theorem prover is recommended. These are refinements to the existing 16 rows, not a seventeenth competing roadmap.

| Existing ZR | Add to required interface or evidence | Discriminating acceptance test |
|---|---|---|
| ZR01/02/05/12/13 | A machine-readable recursive compatibility manifest: statement schema/field count/encoding, child proof shape, allowed feature capabilities, relation/VK identity, version/dependency closure and measured optional-feature cost. Authorization of a compatible relation remains separate. | Compatible heterogeneous proofs succeed; individually mutate feature flags, field count/order, child shape or key authorization. Report the exact incompatible dimension rather than generic success/failure. Measure specific versus general feature support where provided. |
| ZR05/15/16 | Enforce both VK data-to-identifier integrity and identifier-to-signed-policy authorization in every claimed acceptance route, including host verification, imports and caches. Root updates require the applicable evolution authority. | Pair valid proof/key data with a misleading claimed key hash; pair hash-consistent but unauthorized trivial relation; attempt unauthorized key-root insertion. Both distinct mismatches reject. Authorized rotation preserves duties. |
| ZR03/07 | Track whether mandatory predecessor and effect dependencies are actually constrained and cryptographically verified; reading a proof's public fields cannot substitute for verifying it. Base-case guards need their own authenticated genesis obligation. | An invalid predecessor with self-consistent public fields, omitted verify, false guard or unauthenticated base selector fails. A legitimate permitted base with an unused dummy slot remains accepted. |
| ZR03/11/16 | Classify every returned object as statement-bound, witness-only, auxiliary, predicted effect or authenticated actual effect; expose the binding/opening for any auxiliary data used by a consumer. | Alter an auxiliary fee/recipient/output while retaining valid proof bytes: it cannot authorize changed effects unless the accepted statement binds that change. |
| ZR09/12/13 | Distinguish per-node fan-in, child proof shape, total history depth and logical ancestry. Specify a semantics-preserving tree composition when fan-in is decomposed. | Binary-tree versus supported direct join preserves duty/budget results; duplicated ancestry does not multiply spending authority; incomplete branch coverage rejects where completeness is required. |
| ZR10/11 | Require the explicit chain from proved pre-state to authoritative current-state precondition and accepted post-state, including pending-log/action root when relevant. | A valid stale-state proof fails after another accepted state change; fabricated pending-log head fails; mere read or proof verification without currentness does not qualify settlement. |
| ZR01/13/16 | Record and assert real proving/final verification mode at deployment and evidence collection; testing modes must be visibly distinct and unable to qualify production evidence. | A dummy proof accepted by local test mode is rejected by an independently configured real verifier; mode toggles and empty keys cannot yield a final-valid dossier. |
| ZR01/05/16 | Cache artifact manifests with content digests, build/semantic tuple, key purpose and expected identity; verification independent of original cache/prover service. | Cold versus warm builds preserve qualified artifact semantics; corrupted, stale or relabeled cache entries reject or safely rebuild, never certify the wrong program. |

These extend the earlier candidate's broad obligations with concrete developer-facing error surfaces. Native Midnight APIs need not copy o1js names, gate flags, two-parent limit, Pasta/Pickles architecture or cache layout.

## Bounded comparison to the full ZR set

ZR01–03: direct API and statement/compatibility examples inspected. ZR04: only a simple explicit base/step example; no full well-foundedness or financial genesis theorem inspected. ZR05–07: strong developer integration evidence, including dynamic keys, defaults and missing verification risks. ZR08: this study does not inspect Pickles deferred cryptographic finalization, so no conclusion about its complete decider/accumulator implementation. ZR09–10: source shows bounded fan-in and explicit current-state settlement binding; no live race or private financial join reproduced. ZR11: no Moriarty/Midnight compiler correspondence follows. ZR12–13: interfaces expose bounds/feature tradeoffs but no performance experiment was run. ZR14: proofs bind public fields, but witness transfer/confidentiality was not established here. ZR15: key-set example motivates authorization; it is not a general migration theorem. ZR16: serialization, cache and proof-mode evidence are concrete; independent verification was specified, not executed.

The six-month comprehensive Midnight recursion horizon remains the user's planning assumption. Mina's source provides useful requirements and failure cases for that horizon, not evidence of its delivery date or transferable correctness.
