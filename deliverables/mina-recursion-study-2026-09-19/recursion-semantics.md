## Findings from implementation

**M01 — Step/wrap is a partition of obligations, not two independently complete checks.** Pickles Step's `verify_one` enforces `unfinalized.should_finalize = must_verify`, invokes deferred finalization and current verification, and returns `(verified && finalized) || not must_verify`. The caller asserts all returned Booleans. Thus a base/optional branch intentionally has different proof obligations, and the application must constrain when that branch is legitimate. This is actual code behavior, not a finding that Mina permits unauthorized bypass. [E01, E02]

**M02 — Deferred checks include challenge and arithmetic consistency, not just a final group equation.** `step_verifier.ml` checks recomputed xi, challenge-polynomial evaluation b, combined inner product and the PLONK relation. Wrap's finalizer returns the same four classes of checks. Finalization masks are enforced in `wrap_main.ml`. The relevant lesson for Midnight is to specify every deferred item and its consumer; merely listing “final pairing” can obscure earlier scalar/transcript obligations. No claim is made that Midnight uses these same IPA quantities. [E03, E04, E16]

**M03 — Branch, fan-in and domain are bound together.** Wrap obtains a branch index, converts it to one-hot selection, derives the active predecessor mask and selected step domain, then constrains the packed public branch data to those values. It selects the corresponding step key. Step distinguishes self, compiled and side-loaded predecessor keys. The side-loaded API defines width as direct predecessor count, branch as a rule/circuit, and exposes a maximum width type `Nat.N2`; checked key input includes maximum proofs verified, actual wrap domain and key commitments. The documentation also describes Step's at-most-two predecessors. This supports a bounded-two-parent case, not unlimited fan-in or a bound on total history length. [E05, E06, E07]

**M04 — Terminal validity is visibly stronger than one recursive circuit's output.** Pickles external verification checks proof round-vector length, chunk bound, feature/evaluation consistency and domain bound. It separately calls `Ipa.Step.accumulator_check`, prepares statement/key/old-challenge data, and then batch-verifies the wrap proofs. Failure labels are accumulated before returning the result. A consumer skipping the accumulator check would not be following this entry point's acceptance relation. This is source evidence, not a universal soundness proof of that entry point. [E08, E09]

**M05 — Fiat–Shamir context has concrete ordering and type boundaries.** Kimchi absorbs the verifier-index digest, previous challenge commitments and public-input commitment before witness commitments. Later it absorbs the digest from the other sponge and a digest of previous recursion challenges, then computes evaluations for those challenges. A stable field list is insufficient without a specified absorption order, encoding and challenge mapping. Cross-field representation has similar obligations; the Pickles deferred-computation document explicitly discusses equality of integer lifts and public-input commitment binding. This architecture uses Pasta/IPA and does not justify importing its encoding into Midnight's KZG path. [E10, E11, E15]

**M06 — Proof shape is part of the relation interface.** Kimchi `to_batch` requires the number of previous challenges to match the verifier index, checks public-input length, computes chunk size and checks evaluation lengths. Pickles also checks feature flags, domain and opening round count. A heterogeneous relation interface therefore needs more than a VK hash: the canonical relation/version manifest must account for compatible shapes and enabled features. These source checks do not establish arbitrary malformed-deserialization safety beyond the inspected paths. [E08, E12]

**M07 — Empty batches and SRS compatibility need caller-level meaning.** Kimchi returns success on an empty batch. That is mathematically sensible for an empty conjunction, but a Moriarty workflow requiring a parent cannot infer that it has checked one. The batch path selects the first SRS and checks that other indices have equal maximum polynomial size; an adjacent TODO asks whether actual SRS equality should also be checked. This supports requiring explicit parameter identity or a proved compatibility relation, not claiming a demonstrated Mina vulnerability. An upstream invariant may constrain SRS construction outside this inspected range. [E13]

**M08 — Batching soundness depends on randomization and complete equations.** IPA verification accepts an RNG bounded by `RngCore + CryptoRng`, samples separate randomizer bases for proof equations and sg commitment equations, recomputes the challenge polynomial, and checks one combined MSM is zero. It explicitly includes the check that sg commits to the challenge-derived coefficient array. Thus safe batching requires its own soundness/error argument and randomness contract. A KZG implementation can use different equations or a sound Fiat–Shamir batching design; neither this RNG API nor Mina's IPA construction is prescribed for Midnight. [E14]

The candidate already covers final accumulators, zero guards, format lengths and pinned keys. These refinements make those obligations executable and auditable rather than alleging that the current document lacks the high-level requirements. The most important additions are the full deferred-obligation lifecycle, transcript schedule, and parameter/batching security contract. They are semantic/cryptographic correctness requirements. Faster recursion, constant retained size and larger fan-in remain separate performance/capability goals with declared bounds.

## Limits and implications for Moriarty

Pickles is not “verify any proof under any key”: supported statement shapes, features, domains, branches and direct fan-in constrain composition. An application still owns legitimate genesis, authorized key policy, financial intent, complete duties and resource uniqueness. None follows from cryptographic recursion alone. All MC03 real financial recursive steps and MC06 private successor/split/branch/join obligations remain necessary. The approximately six-month Midnight expectation remains a user planning assumption.

This inspection does not establish Mina's complete security theorem, deployment assurance, arbitrary DAG/liveness/privacy properties, or that a cited TODO is exploitable. It does not validate every path in the acquired repositories. A complete transfer requires a native Midnight specification and source/constraint/ledger correspondence, not an assertion that both stacks use recursion. No Mina code reuse or new curve/commitment scheme is recommended.
