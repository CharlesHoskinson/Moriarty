# L2 proposal — U0 target and enforcement

## 1. Goal

U0 should give U1 a versioned semantic contract and a **reverified, compatible released Midnight tuple** on which to test arithmetic and native feasibility. It should give U2 an exact map from each supported stage field to the circuit, authenticated ledger check, or other native boundary that will enforce it. Recording those interfaces is useful; it does not demonstrate signed financial acceptance. The [roadmap](/home/charl/Moriarty/ROADMAP.md:21) assigns native certificates to U1 and the signed source-to-Preview financial path to U2.

## 4. Exit and ownership

I would split U0 into **contract frozen** and **released target qualified**, while retaining one overall U0 dependency gate. U0 must demonstrate the released tuple’s limited compile → real proof → independent verify → verifying-ledger route and a signed-message binding primitive. It need not natively enforce all 84 leaves: many belong to later admitted grammar. U1 owns certified slice arithmetic, adversarial-witness soundness, and measured signature/phase/recursion feasibility. U2 owns the first complete signed financial relation, single-lineage replay/currentness, actual ZKIRv3, native verification, Preview effects and hostile controls ([roadmap](/home/charl/Moriarty/ROADMAP.md:22)). U4 owns full recursive/private handoff and joins; ledger induction cannot close it ([roadmap](/home/charl/Moriarty/ROADMAP.md:34)).

If no released tuple passes U0’s smoke, record **target blocked**. Independent semantic work and provisional U1 probes can continue, but neither U1 native certification nor U2 completion should be inferred from a historical pin.

## 5. Risks and things not to do

Do not equate a passing U0 checker, a generated Compact file, a mock verifier, or a historical Preview fixture with this tuple’s native boundary. Do not bridge incompatible proof formats by relabeling bytes, silently disable proof verification, select a prover-supplied VK, or count outer-proof success before deferred checks. Do not use a host-computed signature Boolean or a partial effects projection as acceptance. Do not turn the March 2027 assumption into a release dependency or reduce MC03/MC06 when current interfaces fail.

## 6. Disagreements

The [U0 roadmap row](/home/charl/Moriarty/ROADMAP.md:21) can be read as satisfied by a matrix of pins and enforcement claims; the current [exit checker](/home/charl/Moriarty/scripts/check_u0_exit_gate.py:324) correctly refuses that conclusion. I recommend making a reproducible **released-tuple smoke** an explicit U0 target gate because U1/U2 otherwise start against mutually incompatible interfaces. Conversely, requiring 84/84 native enforcement in U0 would move U2–U4 implementation into a contract milestone. Keep a field’s **planned locus** separate from its **demonstrated native enforcement**.
