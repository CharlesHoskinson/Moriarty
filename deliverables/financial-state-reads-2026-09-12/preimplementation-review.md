## Design recommendation

Use source profile /3 and a separately versioned financial Core contract /2, sharing the existing machine behind explicit version gates. Preserve /1 and /2 source acceptance, reserved names, signatures, Core /1 constructors and request shape. Do not implement a second interpreter. Source evaluation must continue compiling fresh from primitive source strings; returned mutable elaboration artifacts remain inspection output only.

Six scalar accessors are a coherent small surface:

| Source expression | Result |
| --- | --- |
| `outstanding<Cash>(id)` | `Quantity<Units<Cash,1>,0>` |
| `principal<Cash>(id)` | `Quantity<Units<Cash,1>,0>` |
| `accrued<Cash>(id)` | `Quantity<Units<Cash,1>,0>` |
| `balance<Cash>(party)` | `Amount<Cash>` |
| `allowance_remaining<Cash>(party)` | `Amount<Cash>` |
| `allowance_spent<Cash>(party)` | `Amount<Cash>` |

The identity expression must have type Text; the generic names an already declared unit or asset. A runtime Text argument or local supports named identities without new obligation declarations, record schemas or parser productions for financial state. Reject malformed identities and absent entries; missing is not zero. A valid settled obligation has zero outstanding and remains readable. Obligation reads verify its actual denomination. Balance and allowance lookups select the exact `(party, asset)` pair.

Use dedicated read Core nodes with explicit generic/unit and identity operands. Do not lower to literals, ordinary `ReadPre`, or `ReadObs`. Source text/span alone is not provenance: the financial context must come from kernel validation, separate from caller `Pre`, `Args` and `Obs`. Any public Core /2 entry accepting context text must validate it itself, or consume an internally held context inaccessible to the request; a public object cast or caller claim of validation is insufficient. With no financial context, evaluation of a financial read must reject. Static `check` must work without a context.

All reads observe the same validated pre-action financial state. Emitted operations do not update that read view; one funded kernel call follows expression success. Later action invocations receive the preceding complete `financialPost`. No setters or financial post-state ensures are introduced. Documentation must distinguish ordinary `post` ensures from kernel financial transition validation.

## Ownership, validation and work

Critical observation: `parseOwnedState` currently checks JSON ownership and `work.remaining` shape only. The complete repayment `parseState` runs after expressions in `completeFundedPreparation`. Reusing this shallow helper for reads would allow invalid state to affect guards and arithmetic before validation. Extract/share the kernel's full state admission rather than duplicating its invariants or invoking a dummy repayment.

Recommended order: source transport; compile/typecheck every action; selector validation; own/admit and completely validate financial state; check matched work; validate selected ordinary snapshots; reduce the selected action; bind emitted descriptors and debit expression work on an owned copy; run the funded kernel; publish both posts/effects only after complete success. Preserve static-error-before-selector behavior. Explicitly specify priority where this new profile strengthens state admission: malformed state beats runtime false guards and missing financial lookups. A malformed unselected action still beats all runtime inputs.

Reuse all kernel closed-shape, canonical integer, identity, uniqueness, collection-capacity and invariant checks, including principal + accrued = outstanding, status consistency, allowance arithmetic and work arithmetic. Validate the original work fields before expression debit. Retain primitive string boundaries and per-component byte bounds; never accept mutable external state objects or retain result aliases across calls.

One read costs one expression reduction plus its identity-expression reductions. This is consistent with existing finite node-cost semantics if the maximum 128-entry lookup is explicitly a bounded primitive; use bounded scan or an index built after validation. Static work counts all read/identity nodes, including unselected branches; actual work follows short-circuiting. Admission/index building is bounded validation, not an unreported new expression debit. Do not inflate the bound for extra unselected actions. Successful total debit is E + N, where N is emitted kernel action count; `closureReserve` stays separate and unchanged. Rejections publish neither a tentative debit nor either post.

The three-payment example needs its own work fixture, recommended remaining 256, spent 0, closureReserve 16, with snapshot work matching on every invocation. Preserve the historical 100-work fixture. Pin exact E and final work after the implementation's source example is frozen; a design report cannot honestly give a numeric E for unwritten syntax. Test E and N separately with a minimal read action and exact-budget boundaries.

## Diagnostics and independent test expectations

Recommended existing codes: `TYPE_NAME` for an undeclared generic, `TYPE_MISMATCH` for non-Text identity or mixed-unit arithmetic, `INVALID_IDENTIFIER` for malformed runtime identity, `MISSING_OBLIGATION`, `MISSING_BALANCE`, `MISSING_ALLOWANCE` for absent entries, `NOMINAL_UNIT` for obligation denomination mismatch, and `ARITH_RANGE` when kernel U128 obligation values cannot inhabit signed128 Quantity. A separate `FINANCIAL_CONTEXT_REQUIRED` is appropriate for a new Core evaluator lacking financial context. New runtime expression errors should retain their read-node source span and path; state-admission failures retain kernel input error semantics. Tests should pin selected codes rather than accepting a set of possible failures.

1. **Complete continuation.** Start with principal/outstanding 100, accrued 0, Payer balance/allowance remaining 100, Lender balance 0 and allowance spent 0. `repay(30)` yields debt/balance/allowance remaining 70 and creditor/spent 30. Installment 20 yields 50 and 50. `repay_remaining`, receiving no nominal amount, reads exactly 50 and emits Transfer 50 then Repay 50. Final principal/accrued/outstanding are all 0, status Settled, Payer balance 0, Lender balance 100, allowance remaining 0/spent 100, and ordinary paid is 100. Preserve all other obligation fields and ordered fresh IDs `T1,T2,T3` and `Alloc1,Alloc2,Alloc3`. Verify both exact effects per invocation and work conservation with reserve 16.
2. **Provenance/spoof resistance.** Change ordinary due/paid independently of valid financial debt and assert a source action using only the new read still computes the financial value. Inject an `Obs` or `Pre` key matching an accessor/read name: it must reject the closed snapshot or remain an unrelated ordinary field, never supply the financial read. Alter returned Core/schema/result objects and show the next source call recompiles and owns its inputs. Core /1 rejects new nodes and financial-context request fields.
3. **State validity before reads.** Duplicate obligation IDs or `(party, asset)` rows reject `DUPLICATE`; 129 entries reject `CAPACITY`; inconsistent debt or status reject `INVARIANT`; malformed numbers reject `INVALID_AMOUNT`. Combine each with `requires false` or a missing read identity and require the state-admission diagnostic first. Probe malformed work invariants even if expression debit might appear to repair them.
4. **Lookup semantics.** Exact-case lookup; unknown/empty/65-character/newline/prototype-like IDs; valid identity at positions 1 and 128; two parties with same asset and one party with two assets. Return the selected entry, never first-match-by-unit alone. A declared wrong obligation unit rejects `NOMINAL_UNIT`. An absent asset pair rejects the matching missing-entry code. An undeclared generic fails statically even in an unselected action or branch.
5. **Typed numeric boundaries.** Obligation value `2^127-1` is readable; `2^127` rejects `ARITH_RANGE` for Quantity rather than wrapping or coercing to negative. Use valid matching principal/outstanding fields. Amount balance permits the full kernel U128 domain. Cross-asset Amount arithmetic and cross-unit Quantity arithmetic reject statically. Constructor identities cannot be silently interpreted as dynamic Text literals.
6. **Atomic funding faults.** On valid state, insufficient balance rejects `INSUFFICIENT_BALANCE` at kernel action 0; insufficient allowance rejects `INSUFFICIENT_ALLOWANCE` at 0; Transfer 49 for Repay 50 rejects `INSUFFICIENT_UNALLOCATED` at 1. Fresh IDs isolate these failures from duplicate-ID priority. No failure returns ordinary post, financialPost, effects or successful workRemaining. Reusing the unchanged inputs with corrected funding succeeds. Keep transfer-unit, creditor and payer relationship checks; reads grant no new payment authority.
7. **Evaluation/work.** A false short-circuited branch containing a missing identity does not look it up; typechecking still visits it. Repeated reads before/after an emit see the same pre-state. A successful minimal accessor plus Text literal costs two expression reductions before surrounding statement costs. If E work suffices for expression but leaves less than N, reject `INSUFFICIENT_WORK`; with less than required expression work, reject `WORK_EXHAUSTED`; E+N succeeds exactly. Work mismatch rejects `WORK_MISMATCH`. Extra unselected actions change neither selected output nor debit.
8. **Interfaces and documentation.** Round-trip formatter/idempotence and UTF-8 spans; check/elaborate all actions without state; CLI simulate uses /3 with explicit selector and complete continuation state; rejection stderr/stdout contract holds. README examples must use implemented syntax and explain ordinary snapshots versus validated local kernel state. Preserve unrelated prose. This is local preparation, not proof correspondence or authenticated live ledger settlement.

Recommendation: proceed with this bounded design and the independent tests above. This preimplementation review is not approval of an implementation or replacement for the user's fresh final Astra audit.
