The design has a coherent center: pure bounded computation produces explicit financial effects, signed outcome constraints bound solver freedom, and accepted transitions retain liabilities and history. Its strongest implemented layer is exact arithmetic and local preparation. The main missing layer is a single executable, compositional relation joining the richer source language, financial resources, staged authority, and native acceptance. Existing narrow profiles deliberately reject unsupported behavior; these gaps are not evidence that invalid ledger transitions are currently accepted.

## 1. Product-priority gap: source expressiveness and protected effects are still different layers

**Repository observations.** `experiments/moriarty-language/src/successor/funded-expression-source-v1.ts:207` requires exactly Transfer, Repay, Originate and Accrue operation schemas for source/5 (lines 211–220). `src/successor/financial-agreement-source-compiler.ts:526` invokes that protected binding, and lines 542–547 require transfer asset to equal repayment denomination. Lines 563–607 construct empty vault/enum/variant/observation registries; lines 616–633 elaborate to local Core and a work bound. All `src/` references in this report refer to `experiments/moriarty-language/src/` unless otherwise stated.

The financial expression engine does support a wider vocabulary, including indexed amounts, shares, variants, conditional values, and exact integer conversions (`src/successor/financial-expression-v1.ts:262–290`). Those capabilities do not automatically become source-declarable, executable financial primitives in source/5. Its local evaluate API ends at a prepared envelope (`src/successor/financial-agreement-source-v5.ts:76–96`). The inspected Compact lowerer imports the older frontend (`src/lower-compact.ts:1`) and advertises its restricted arithmetic/effect-operand scope with no authority, proof, or settlement acceptance relation (lines 12–29).

**Inference / design gap.** The permissionless language promise needs an objective primitive-extension/composition boundary, not another application-shaped profile for every financial product. Fixed operation schemas are a legitimate current subset; their restriction must not be mistaken for a general type/effect system. Amount units also need an explicit bridge to dynamic ledger asset identity; equal source identifiers are only one narrow binding policy.

**Smallest discriminating experiment, specified-only.** Have an external developer author a new two-asset conditional-payment program using only proposed supported primitives, with no loan record or privileged host schema. Produce a coverage trace for declaration → typed Core → complete effect relation → ZKIRv3. The first unsupported edge determines the next primitive obligation. This is a capability discriminator, not a request to accept unchecked user-defined effects.

## 2. Outcome authority has not yet joined the richer lifecycle language

**Repository observations.** `src/runtime-types.ts:18–25` defines the implemented bounded-atomic outcome authority with a single program, exact predecessor state hash, principal/nonce, allowed actions, gross debit caps and minimum net credits. It has no partial-fill consumption accumulator, separate liability cap, revocation identifier or signed recovery policy in that schema. `src/evaluate.ts:285` rejects nonempty permitted calls. Lines 289–295 correctly include fees and transfers in gross debits and net credit checks; refunds do not erase gross debit. Lines 298–305 produce one complete candidate and one authority-consumption record. Meanwhile source/5 uses a local lifecycle state with allowances and liability caps, explicitly disclaiming signing/proof/ledger/authenticated time (`src/successor/financial-lifecycle.ts:1–6`, 50–83, 129–138).

**Intent/spec gap.** `docs/MORIARTY-PRODUCT-CONTRACT.md:37–43` requires liability/fee limits, revocation, partial completion, per-phase authority and remedies. The existing single-use atomic intent is not a defect for its profile; it is insufficient to authorize arbitrary solver-selected multi-stage completion while preserving cumulative constraints. Exact state pinning may intentionally be allowed, but cannot be the sole representation for a persistent pending intent.

**Smallest discriminating experiment, specified-only.** Sign one intent once; let two independent solvers propose different valid first fills and continuations. Check the same objective relation accepts either valid route, rejects concurrent double consumption, rejects fees that violate cumulative net goals, and cannot recreate consumed gross allowance via refund. Use the richer financial source program in this experiment, not a second unrelated intent simulator.

## 3. Conditional settlement has requirements but no selected executable resource/stage calculus

**Source facts.** `openspec/changes/partial-and-conditional-transactions/design.md:13–19` names stage occurrences, delegated callback authority, evidence policies, joins, residual duties, refunds and late-delivery races. Lines 27–31 explicitly leave the staged profile unimplemented and the theory choice open. Product contract lines 41–45 distinguish persistent liabilities, affine authority, ledger phase failures, and privacy.

**Repository observations.** The lifecycle action union remains four operations (`src/successor/financial-lifecycle.ts:127`); its state has no condition-policy, continuation, stage-status or evidence-request resource (129–138). Type checking is exact value/schema checking; the generic expression contract explicitly treats Emit as a descriptor rather than financial authority (`spec/successor/static-semantics.md`, STMT section). No claim of general linear/affine checking follows from nominal resource-looking records.

**Recommendation / open question.** Select a small executable state/resource calculus with separate rules for spend authority, persistent duty, and consumed receipt. Do not encode all three as a duplicable value record or indiscriminately forbid discarding all resources. Choose the theory by a distinguishing trace, not by adopting a language wholesale.

**Smallest discriminating experiment, specified-only.** One funded request requiring recipient signature plus fresh document attestation. Execute submission, one evidence arrival, timeout, late second evidence, and cancellation/delivery race. Each step must show custody, consumed authority, fees, outstanding duty, and who may act next. Check outcome availability versus success at a join. This must eventually map to Midnight phase outcomes; a TypeScript atomic rejection is not that mapping.

## 4. Reproduced product gap: bounded evaluation does not yet supply a recovery path

**Experiment observation.** `reserve-repro.mjs` runs only `prepareFinancialLifecycle` for `moriarty-financial-lifecycle/1`. Starting from the checked-in example, it changes ordinary work remaining to 2, leaves closureReserve at 16, and executes Transfer(100) + Originate(100). The result is Prepared, outstanding debt 100, remaining 0, spent 19, reserve 16. A funded, authorized-by-local-allowance Transfer(100) + Repay(100) continuation rejects INSUFFICIENT_WORK. Exact inputs and outputs are retained in `reserve-repro-output.json`. This experiment was executed twice, first inline and then as the saved script; no ledger or source/5 proof path was executed.

**Repository observations.** `src/successor/financial-lifecycle.ts:733–767` only bounds remaining+spent+reserve numerically. Lines 1869–1875 admit cost from ordinary remaining; 1907–1913 spend it. The action union at line 127 contains no close/recovery operation. Searches for closureReserve across current experiment TypeScript/MJS implementations found only parse/validate/copy behavior in the repayment and lifecycle engines, not a consuming recovery path.

**Counterevidence / limitation.** `spec/successor/repayment-kernel.md:147–149` explicitly says reserve is separate and cannot pay ordinary actions; `tests/successor-repayment.test.mjs:1290` encodes that expectation. The observed behavior therefore matches the scoped local specification. It is not an implementation bug relative to that contract, not a deployed funds-loss demonstration, and not proof that every Moriarty workflow is stranded. Reserve may deliberately await a separately specified recovery path. The product-level gap is the absence of that path or an admission argument guaranteeing usable continuation resources. Residual debt is preserved, so safety is not silently replaced by discharge; progress is unavailable through the tested profile.

**Next discriminating experiment, specified-only.** From this exact resulting state, demonstrate a separately authorized closure transition that uses the reserved budget without erasing debt or restoring consumed spending authority; alternatively show admission rejects origination because no such bounded recovery exists. Do not merely let ordinary actions spend the reserve.

## 5. Finite stages and finite-lived instances need an explicit distinction

**Repository observations.** `src/successor/financial-lifecycle.ts:14` sets collection capacity to 128, enforced by parseArray at 503–511. Unique used-transfer, allocation, origination and accrual IDs append forever in this local state: checks/appends at 1499/1523, 1606/1621, 1690/1718 and 1821/1829. Obligations also append at 1717, including eventually settled records. runActions copies full predecessor state at 1877; the four-operation union provides no compaction, accumulator update, or authenticated rollover.

**Inference.** Each current local lineage has at most 128 occurrences per corresponding ID category, potentially fewer due to byte/work bounds. Per-stage finite execution does not itself require a public DeFi service to have such a lifetime cap. The language can intentionally use bounded episodes, but must specify how a successor episode inherits duties, residual authority and replay evidence without replenishing already consumed authority or violating any signed lifetime-work limit. A fresh state cannot silently reset those conditions.

**Smallest discriminating experiment, specified-only.** Reach an ID/category cap with a still-outstanding obligation, then attempt one final repayment. Demonstrate bounded authenticated rollover or document intentional rejection and the required advance recovery capacity. This is separate from proof compression: history proof size alone does not make a full mutable state array smaller.

## Overall recommendation

Keep the current exact arithmetic, immutable pre-state, staged writes, explicit postconditions, gross debit accounting, and separation of token supply from debt. Consolidate their semantics into one public supported-Core acceptance relation before expanding application profiles. The next design review should center on a small conditional two-asset settlement with a surviving duty, two solver alternatives and a recoverable budget boundary. A useful whole-language architecture must explain that example at types, effects, authority, history, resource, and actual ZKIRv3 constraints levels. Static refinement checks should expose definedness and invariant obligations, never label mere type checking or terminating rejection as proof that settlement succeeds.
