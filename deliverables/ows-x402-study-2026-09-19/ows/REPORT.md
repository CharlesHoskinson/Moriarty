# OWS: delegated wallet authority and the federated kernel

OWS is a useful reference for local wallet interoperability and agent-facing signing policy. It is not a proof-carrying intention system or an implemented Midnight adapter. Its most important security boundary is explicit: agent tokens gate the ordinary signing path, but the token also decrypts a stored copy of the full wallet secret. An agent with both token and file access can leave that path. Owner credentials deliberately bypass policies. These facts constrain how OWS could fit into a kernel whose solvers are adversarial.

This study pins `open-wallet-standard/core` at **b3fd7f9b3c2dd200605a2db06726c6a0d4709205** (September 15, 2026 commit; acquired September 19). All 194 tracked files were acquired; 62 documentation/website/ownership files are inventoried. All **15 deployed canonical Markdown documents** match `core/docs` byte for byte. All **12 registered document routes**, both site landing pages, the advertised sitemap, robots files, generated `llms-full.txt`, published skill and installer were captured. There are 46 HTTP capture records, including discovery failures and incidental assets. [Acquisition verification](acquisition-verification.json) states the finite boundary and exceptions; [reading coverage](reading-coverage.json) explicitly distinguishes acquisition from targeted full reading. The installer, wallet commands, signing and transactions were never executed.

## Explanation: what authority the wallet provides

The normative core defines storage, signing, policy, lifecycle, chain and conformance requirements. Agent-access and isolation documents are optional profiles; SDKs, quickstart and implementation guides are non-normative. Hosted custody and service-payment flows are outside the core. A supported profile is a precise claim; general OWS compliance cannot be inferred from file compatibility. The storage introduction's broader wording needs that qualification. **OWS01/OWS24**; exact URLs, local hashes and line ranges are in [claims.json](claims.json) and [references.md](references.md).

An owner passphrase unlocks the wallet directly. An API token instead identifies a key file, checks expiry and wallet scope, evaluates every attached policy with AND semantics, and decrypts only on allow. The inspected `key_ops.rs` and `ops.rs` follow this distinction. Empty policy lists allow; the mechanism supplies the policies actually attached, not an implicit economic safety policy. A token constrained to a wallet is not necessarily constrained to one transaction type, spending budget, chain or counterparty unless applicable policy adds that restriction. **OWS02/OWS07/OWS08**.

API creation decrypts the wallet secret with the owner passphrase, then encrypts a complete secret copy under HKDF-SHA256 of the random token. The reference threat table expressly states that token plus disk access can decrypt by bypassing the OWS process. This is a documented design boundary, not a newly demonstrated exploit. The token is a decryption capability as well as an API credential; it is not a cryptographically attenuated private key. A compromised agent sharing the operating-system principal or address space cannot be assumed to respect the SDK. **OWS03**.

Revocation deletes the key file, so ordinary lookup stops. It cannot erase a copy already retained by an adversary, undo a signature already issued, or revoke a recovered private key at the destination. The quickstart's “immediate” revocation language applies to the managed access path. Owner passphrase changes leave the separately encrypted token copies unaffected. A kernel must distinguish credential lookup revocation, signing-key rotation, destination authorization revocation and cancellation of outstanding actions. **OWS04**.

The current key-isolation profile is same-process hardening and zeroization; it explicitly does not fully mitigate compromised process memory. The future “enclave” is a per-request subprocess. That term must not be promoted into a hardware TEE claim. The quickstart still depicts an isolated signing process, conflicting with the detailed current-state account. Neither process isolation nor hardware attestation, if later added, proves the measured program implements the correct economic policy. **OWS05/OWS06**.

## Reference: policy is narrower than signed intention

| Surface | What the inspected interface establishes | Additional kernel obligation |
|---|---|---|
| Chain allowlist | Requested canonical chain identifier is allowed | Bind actual signed payload semantics to that domain; opaque hashes can describe something else |
| Expiry | Signing-time policy/key timestamp check | Specify treatment of already-issued signatures, pending effects and late settlement |
| Typed-data contract allowlist | EIP-712 verifying contract is allowed when this operation supplies typed data | Restrict operation kinds and the complete message, including spender, value and duties |
| Transaction effects | Cardano-derived per-address asset changes; empty for other current chains | Prove completeness and interpretation of supported effects; absence is not zero loss |
| Executable policy | External process returns an allow/deny JSON result | Establish predicate correctness, bounded costs, trusted inputs and immutable policy semantics |
| Sign-and-send | Broadcast success produces a transaction identifier | Establish execution, chain-specific finality and complete partial-outcome accounting |
| Append-only audit | Implementation appends operation records without raw secrets | Establish authenticated lineage, completeness and recursive compliance if claiming PCD |

Built-in declarative policies cover chain IDs, expiry and typed-data contracts. Spending caps, recipient restrictions, cumulative budgets and simulation require an executable. The typed-data contract rule passes non-typed-data operations; the source also permits an absent typed-data context. A policy author cannot treat that allowlist as a universal restriction on everything the key can sign. **OWS07/OWS08**.

`signHash` signs a raw 32-byte digest without adding a domain separator. The EIP-7702 helper constructs and hashes its selected-chain tuple, while the documented escape route for a wildcard tuple is caller-precomputed `signHash`. Raw-hash access is powerful even when the caller names an allowed chain in the API. A certified kernel must either establish the digest's authorized preimage/semantics or use an explicitly restricted raw-signing capability. The existence of policy evaluation does not establish that a chain-only predicate constrains the digest's economic meaning. **OWS09**.

The policy context makes this distinction visible through `request_type`. Only Cardano currently populates `transaction.effects`; EVM and other chains supply empty effects and raw bytes. Typed data uses its own payload. The documentation describes a concrete migration failure: code that inferred typed-data requests from an empty optional transaction field can change from deny to allow after that field disappears. The result is valid JSON, so fail-closed handling of executable crashes and malformed output does not catch it. This is a strong requirement for typed operations, versioned policy schemas and migration counterexamples. **OWS10/OWS11/OWS13**.

The implementation guide describes `spending.daily_total` as cumulative value signed today, but the inspected context builder calls `noop_spending_context`, which always emits `"0"`. No cumulative spending guarantee follows from this field at the pin. This is a direct documentation/source discrepancy, not a claim that every application using OWS lacks its own accounting. **OWS12**.

## Explanation: partial effects and external evidence

Cardano is especially useful for Moriarty's partial-transaction requirement. Its policy context resolves input and collateral references by fetching source transaction CBOR, checking the requested hash and rejecting missing inputs. That authenticates the referenced byte content under the hash assumption; it does not independently prove chain inclusion, finality or current unspentness. Provider availability and actual ledger validation remain distinct. The documentation describes dependent unconfirmed transactions as blocked through this path when Koios cannot return parent transactions. **OWS14/OWS17**.

Collateral is reported separately as `chain_extra.collateral_effects` because it can be consumed on phase-2 failure rather than the successful transaction path. A successful-path outflow calculation is insufficient. The normative policy example counts collateral, while the non-normative minimal guide omits it. This is a concrete negative witness for a “spending cap” whose predicate does not cover every allowed outcome. It motivates explicit success/failure effect types and residual duties in Moriarty, without importing Cardano's phase semantics into Midnight. **OWS15/OWS16**.

OWS `signAndSend` documents a transaction identifier after broadcast, and expressly leaves per-wallet nonce coordination and request serialization to callers. Its x402 usage-based example likewise puts authorized-versus-settled tracking, session caps and external-ledger reconciliation in the application layer. Neither a signing success nor a retry response proves exactly-once economic delivery. For the user's conditional settlement, destination funding must remain distinct from release after the required combination of signatures, documents, proofs, recipient action and other supported conditions. OWS can provide an authorization signature in such a workflow; it does not implement the whole evidence join, escrow state or recovery theorem. **OWS18/OWS22**.

## Reference: Midnight, NEAR, ZK, MPC and TEE

The pinned registry has no Midnight `ChainType`, and the supported-chain specification has no Midnight profile. Four generic trait/derivation comments mention Midnight's unshielded, shielded and dust roles as motivation for multi-key abstractions. They are useful extension seams, not a Midnight adapter. A real integration still needs precise key roles, network/domain identities, serialization, wallet/prover interfaces, guaranteed/fallible effects, actual ZKIRv3 artifact binding and destination verification. **OWS20**.

The NEAR profile signs raw Ed25519 messages; structured NEP-413 is explicitly a follow-up. Therefore “supports NEAR” does not establish compatibility with the specific NEP-413 Intents payload path reviewed in the NEAR study. That study also separates MPC signature production, solver quotes, native intent authentication and downstream settlement. OWS similarly must not collapse key custody, policy checks, signing and settlement into one guarantee. **OWS19**.

No reviewed OWS profile defines a threshold MPC custody protocol, hardware attestation policy or ZK/PCD compliance relation. Website references to inspiration from sharding or TEE-based products do not establish implementation. The inspected path decrypts local secret material, evaluates ordinary code and returns a signature. Audit logs are not recursive proof-carrying lineage. **OWS21/OWS23**.

For the federated kernel, an OWS adapter should be treated as an optional signer implementation with explicitly declared trust. Solvers remain untrusted proposers. The owner's signed formal intention must bind the admissible effects, and every proof/attestation/MPC signing request must refer to the same stage, artifact, domain and concrete effect. If a destination accepts only a bare signature, compromise of whichever parties can produce that signature remains a bypass of any off-chain proof policy. A TEE implementation would require attestation, freshness and rollback premises; MPC would require threshold and collusion premises; PCD would require sound recursive compliance and actual ledger uniqueness. None is supplied by naming the wallet API “zero-trust.”

## Tutorial: adversarial acceptance exercise

A principal authorizes at most a specified amount to a named destination under a bounded staged policy. An independent solver selects a candidate route. The kernel checks the route and produces proof-bound signing authority for that exact stage. OWS, if used, signs only under the declared custody boundary; the specification must not assume a token holder with recoverable secret access is incapable of signing another payload.

Now mutate the attempt: replace typed-data signing with raw-hash signing; keep the allowed chain label but change the digest's beneficiary; change a policy schema so missing effects look empty; retain a token file before revocation; or report broadcast as final settlement. Each variant must either be rejected by the actual enforcement boundary or recorded as an explicit adversary capability outside the claimed guarantee. A positive witness must still admit a valid independently proposed route and a valid recovery transition. Blanket refusal is not a solution.

The proposed PL refinements and open questions are in [MPLR-candidates.md](MPLR-candidates.md). This track provides documented and source-derived witnesses, not executed wallet tests, cryptographic proofs, a complete security audit or deployment advice. No source, vault or installed skill file was modified.
