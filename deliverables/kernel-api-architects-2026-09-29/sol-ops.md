# Operational protocol for an optional Moriarty DeFi Kernel

**Independent proposal, 2026-09-29.** Author model: GPT-6 Sol cohort; the host did not expose a more precise runtime model identity to this agent. This is a design recommendation, not an implemented or accepted MIL/4 contract. I inspected the scoped [NEAR proposal](../near-kernel-scope-2026-09-29/PROPOSAL.md), [Hyperliquid comparison](../hyperliquid-kernel-comparison-2026-09-29/COMPARISON.md), and [Aeon bridge](../aeon-kernel-experiments-2026-09-29/bridge/RESULT.md), [signing](../aeon-kernel-experiments-2026-09-29/signing/RESULT.md), and [authority](../aeon-kernel-experiments-2026-09-29/authority/REPORT.md) reports. No product code or live transaction was changed.

## Recommendation

Make each external **logical effect** a durable, single-owner workflow. The kernel can coordinate that workflow, but the signed Moriarty authorization and the accepting verifier set its bounds. Persist the intended effect and its exact adapter bytes before any dispatch. Give every send an attempt ID, and keep all attempt IDs attached to one logical effect ID. A response, signature, inclusion, and business effect are different observations. `unknown` remains a live state until evidence resolves the possible effect. This follows the project's proposed kernel boundary; the particular API and state machine below are my recommendation.

The kernel should return two separate products: (1) an append-only operational journal with receipts and unresolved work, and (2) a proposed Moriarty transition whose complete effects and evidence the appropriate verifier can accept. A journal entry cannot itself upgrade an observation into ledger truth. The direct Midnight path does not need this optional coordinator.

### API records and commands

```text
OperationKey = (intentDigest, stageId, logicalLegId, effectKind, settlementDomain)
PinnedLeg = operationKey, adapterId+version+codeDigest, canonicalPayloadDigest,
            authorityDigest, domain+asset IDs, account/recipient, quantity/price/fee caps,
            signer/key epoch, nonce policy, evidence/finality policy, deadline,
            recovery edges, settlement locus
Attempt = attemptId, operationKey, exactBytesDigest, transportId, txId?, nonce?,
          firstSendTime, lastObservation, evidenceRefs
EffectLedger = immutable event IDs, cumulative gross debits, fees, deliveries,
               fills, refunds, remaining entitlement, reservations, residual duties
```

`prepare(plan)` checks the signed authority, financial limits and adapter commitment; `reserve(key, exposure)` durably reserves the shared gross budget and signer nonce. `dispatch(key, attempt)` uses the pinned bytes. `observe(key)` gathers domain facts. `reconcile(key, evidence)` validates provenance, finality and complete effects and proposes an accepted continuation. `cancel(key)` and `recover(key, remedy)` start separately authorized operations. Every command is versioned and returns the current state plus its journal sequence; concurrent updates require compare-and-swap on that sequence. A quote or simulation is advisory. A client may retry a command with the same `OperationKey`, but a changed payload or policy under that key is a conflict, never an implicit amendment.

**Idempotency scope.** Keep a durable Moriarty consumption/nullifier record for an accepted stage and a durable kernel record for its logical effect. External deduplication is an *adapter property* with named scope, key, retention and evidence. Stripe's primary API documentation illustrates the limit: it compares parameters under a key, can prune keys after 24 hours, and returns the first saved result, even a `500`; the result itself does not establish the desired business effect ([Stripe idempotent requests](https://docs.stripe.com/api/idempotent_requests)). Thus neither a client key nor a transport retry implies exactly-once delivery across chains. For a domain with no reliable effect ID or deduplication, a lost acknowledgement leaves `unknown`; automatic new-payload dispatch is forbidden until authoritative reconciliation or an explicit policy for duplicate exposure resolves it.

### State machine and acceptance

| State | Entered by | Next permitted action |
| --- | --- | --- |
| `prepared` | Bound intent, plan, codec and evidence policy | Reserve or abandon without external effect. |
| `reserved` | Durable shared exposure and nonce reservation | Sign or dispatch; expiry releases only after proving no effect was sent. |
| `signed` | Signature over exact bytes and scoped key | Broadcast or retain; no financial effect inferred. |
| `submitted` | Transport accepted exact bytes or tx identity recorded | Observe; no finality inferred. |
| `included` / `enqueued` | Domain inclusion or queue evidence | Observe execution and finality separately. HyperEVM CoreWriter actions can appear as enqueue and later HyperCore execution ([Hyperliquid CoreWriter](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/hyperevm/interacting-with-hypercore)). |
| `active` | Order rests, bridge message awaits delivery, or other continuing domain effect | Accumulate unique effects; retain exposure and residual duties. |
| `finalized` | The policy's named verifier establishes an effect at the specified settlement locus | Import complete effect set; financial completion still depends on the intent. |
| `unknown` | Send may have occurred but evidence is absent, conflicting, stale or insufficient | Reconcile and freeze conflicting remedies/new exposure. |
| `closing` | Authorized cancel, timeout or refund requested | Observe late effects and remedy result; do not call it closed yet. |
| `closed` | Final evidence accounts for all attempts, effects and residual duties | Release only unused reservation; retain consumed gross and history. |

These are operational states, not a monotone claim that every chain offers `finalized`. The event journal is monotone; the derived state may move from apparent inclusion back to `unknown` after a reorg or disputed attestation. Acceptance should bind the exact observed effects, their verifier premise, and the entire committed prefix. A finality policy must say which chain/venue, checkpoint or quorum, depth or consensus commitment, evidence freshness, and reorg response it assumes. A signer receipt or RPC response alone is insufficient. The Aeon signing probe rejected abstract phase substitutions, while a native value falsely declared finalized was accepted, which demonstrates why runtime evidence is still necessary ([local experiment](../aeon-kernel-experiments-2026-09-29/signing/RESULT.md)).

### Specialized operations

**Orders and partial fills.** A resting order is `active`; each fill is a unique economic event with quantity, price, asset, counterparty/venue identity where available, fee and event ID. Deduplicate fills by venue event identity and reconcile against order status and account ledger. `filledQuantity + openQuantity + canceledQuantity` should be accounted for, with venue-specific rounding and status semantics. Cancellation is a request that races with fills: freeze a new replacement order until the old order's final filled amount and terminal status are established or the signed policy explicitly reserves enough for both. Hyperliquid exposes order status lookup by order ID or client ID, separate fill streams with unique trade IDs, and statuses such as open, filled and canceled ([info API](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint), [WebSocket events](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/websocket/subscriptions)). Its cancel error can mean never placed, already canceled **or filled**, so a cancel error cannot prove zero execution ([error responses](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/error-responses)). The client order ID is a correlation key; whether it prevents duplicate placement needs an adapter-specific proof.

**Bridge delivery and refund.** Track source lock/burn, message, destination mint/release, and refund as separate effects under one claim ID. Apply representation ratio, units, fees and rounding to cumulative amounts. Require `delivered + refunded <= authorized entitlement` *and* exclusion of any future destination delivery for refunded units. A source timeout or missing callback is insufficient. IBC's specification is a useful stronger pattern: its timeout checks a destination-side receipt/sequence proof, and explicitly warns that naive timeout logic permits double spend when a relay is delayed ([ICS-004](https://github.com/cosmos/ibc/blob/main/spec/core/ics-004-channel-and-packet-semantics/README.md)). A bridge without comparable nonreceipt/exclusivity evidence remains `unknown` or uses a signed trust premise with that limitation disclosed. The Aeon bridge probe rejects full refund on timeout, unknown status, or merely observed zero delivery; it accepts refund of the remainder only when the input delivery count is complete and authoritative ([local experiment](../aeon-kernel-experiments-2026-09-29/bridge/RESULT.md)). A refund is a new costed transaction, and `refunding` is not `refunded`.

**Signing.** A signer request includes domain chain ID, adapter and codec digest, payload digest, account/derivation path, recipient, value, nonce, key epoch and expiry. Store signed bytes and signed transaction identity before broadcast. A replacement transaction may use a different fee encoding or hash; it is a distinct attempt and must stay linked to the same effect with its own cap accounting. Key rotation cannot erase pending signatures or consumed authority. NEAR Chain Signatures describe obtaining a signature and then constructing/broadcasting the foreign transaction as separate steps ([NEAR Chain Signatures](https://docs.near.org/chain-abstraction/chain-signatures)); Hyperliquid warns that pruning a deregistered agent wallet's nonce state can make old actions replayable after address reuse ([nonce documentation](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/nonces-and-api-wallets)). The kernel must not expose arbitrary-byte signing from a Moriarty intent.

**Oracles.** An observation record contains feed/market ID, domain, publisher or verifier, round/block, value, unit and decimal scale, update time, validity interval, and exact source set. The signed policy chooses acceptable sources and maximum age before execution. The kernel can fetch and cache, but acceptance rechecks the bound round and freshness at its chosen time point. Chainlink says Data Feeds update on heartbeat or deviation and advises consumers to check `updatedAt` for application-specific freshness ([Chainlink Data Feeds](https://docs.chain.link/data-feeds/overview)). A later quote must not silently replace the round that justified an earlier dispatch; replan under a new authorization/reservation if the policy demands a fresher round. Conflicting feeds enter `unknown` or a specified fallback, never an unlogged average.

## Retry, recovery and concurrency rules

1. **Before send:** persist the exact payload, authority check, reservation, nonce lease and journal sequence. Crash recovery can then discover the intended effect without inventing a new one.
2. **After ambiguous send:** query by transaction hash, account nonce, claim ID or order ID and compare domain ledger effects. Rebroadcast identical signed bytes only if the adapter proves that replay is harmless under its nonce/effect semantics. Otherwise hold `unknown`.
3. **After terminal failure evidence:** release unused reservation, keep fees and gross debits actually spent, and permit a new authorized leg only after recording why the old one cannot later execute.
4. **After partial effect:** advance the cumulative effect ledger, retain the unfilled/deliverable remainder and any liabilities, and cap the next leg against both spent and reserved authority.
5. **On cancellation or recovery:** create a new operation with its own authorization, fee cap and evidence; reconcile all late effects before closing the original. Compensation creates a new effect and never erases the old debit.

For concurrent solvers, `reserve` must serialize on the shared authority budget and stage/nullifier, not merely on a solver's local plan. A lost worker lease transfers coordination ownership only; it does not release an externally possible effect. Reconciliation must be idempotent over unique domain event IDs, and reports should expose `observed`, `accepted`, `disputed` and `unresolved` effects separately. The Aeon authority probe accepted an impossible conjunction and gross-cap breach in one encoding, despite rejecting a split check. Therefore its positive result cannot act as kernel admission, signature authorization or settlement evidence ([local experiment](../aeon-kernel-experiments-2026-09-29/authority/REPORT.md)).

## Hostile traces to require in the U5 protocol review

| Trace | Required outcome |
| --- | --- |
| Worker sends an order, crashes before storing the HTTP response, replacement worker sends a new order with a new nonce. | Recover first attempt via venue records; hold `unknown` and reserve both potential exposures until nonexecution or final effect is established. |
| Two solvers each see 60 units free under a 100-unit gross cap and concurrently reserve 60. | One reservation fails at the shared compare-and-swap boundary; no signer call follows for it. |
| GTC order fills 40, cancel request arrives, another 20 fills before cancel commits. | Account for 60 filled; cancellation closes only the remaining quantity. Any replacement size uses the reconciled remainder. |
| Bridge delivers 30 of 100; source timeout fires; relayer delivers another 70 after a full-refund request. | Full refund is rejected or held pending destination nonreceipt/exclusion evidence. Gross debit, destination credits and remedy costs stay visible. |
| MPC signs correct bytes; relayer never broadcasts; operator reports success. | State stays `signed`; no delivered effect or accepted finality transition. |
| Foreign transaction is included, then its block is reorganized before the selected finality point. | Retract the provisional observation into `unknown`; retain authority reservation and reconcile replacement history. |
| Oracle sample has correct feed but stale `updatedAt`, or a fresh round from a different chain. | Reject under signed freshness/domain policy; do not silently substitute a new feed or round. |
| Adapter is upgraded between plan validation and dispatch, or key epoch changes with a pending signed transaction. | Exact codec/payload and key epoch mismatch blocks dispatch; old pending transaction remains tracked and replay authority remains consumed. |
| A cancel API returns `MissingOrder` after an order filled. | Query fills and account effects; do not infer that no order existed. |

## Tradeoffs and unresolved decisions

An append-only journal plus derived state adds storage and reconciliation work, but it preserves evidence when callbacks arrive late or disagree. Holding `unknown` protects against duplicate exposure at the cost of liveness; an owner may explicitly authorize a bounded duplicate-risk remedy, but that risk must consume the same gross budget. Destination proof verification reduces trust in operators and can be expensive or unavailable. A named attestor/quorum profile is operationally easier but is a distinct signed trust assumption. A single generic receipt is easy to integrate but cannot describe venue fills, bridge claims and oracle rounds faithfully; use a common envelope with typed effect payloads.

Before freezing the API, decide: (1) initial custody and signer ownership; (2) first adapter/domain and its actual deduplication, nonce, finality and history retention guarantees; (3) which external observations Midnight can verify and which require a named attestor; (4) whether bridge recovery can obtain authoritative nonreceipt/exclusion evidence; (5) bounded exposure policy when a leg remains `unknown` indefinitely; and (6) whether the first U5 slice requires live foreign settlement or a simulated adapter with explicitly limited acceptance. These are product and trust decisions; none is established by the reviewed documentation or Aeon probes.

## Addendum: lightweight operational framework choice (2026-09-29)

**Repository observation:** the inspected main Python and Node package manifests do not declare PostgreSQL, Temporal, NATS or a queue package. The U5 service runtime and deployment topology are **unverified**. The choices below are conditional recommendations, not claims about the current deployment. License observations refer to the linked upstream repositories/pages as viewed on this date; a selected release and its dependency licenses still need a pinned review.

| Choice | Maintenance, license and complexity | Fit for the first U5 slice |
| --- | --- | --- |
| **PostgreSQL journal, reservations and outbox with a small worker** | One established database and application worker. PostgreSQL's `FOR UPDATE SKIP LOCKED` is documented for queue-like consumers, while its inconsistent view means financial reservations must use explicit transactional row/constraint checks, not queue polling alone ([current SQL documentation](https://www.postgresql.org/docs/current/sql-select.html)). PostgreSQL uses its permissive [PostgreSQL License](https://www.postgresql.org/about/licence/). Schema, backup, migration, worker lease and reconciliation code remain Moriarty's responsibility. | **Preferred base**, if the kernel needs durable coordination among independent solvers. Store authority consumption, reservations, attempts and observations in the same database transaction; external sends remain outside it and require the `unknown` protocol above. |
| **Graphile Worker on PostgreSQL** | Maintained Node/PostgreSQL job runner; upstream describes at-least-once execution and automatic retry, and the repository identifies an [MIT license](https://github.com/graphile/worker) ([official guide](https://worker.graphile.org/docs), [error handling](https://worker.graphile.org/docs/error-handling)). Adds a library and migrations but no second broker. Its job key is queue deduplication, not a permanent financial nullifier. | Add if U5 runs in Node and needs scheduled `observe`/`reconcile` jobs. Configure a send job so retry first reconciles; do not use automatic job retry as permission to repeat a financial call. Node runtime choice is **unverified**. |
| **Temporal self-hosted** | Established durable workflow engine with an [MIT server license](https://github.com/temporalio/temporal/blob/main/LICENSE). Its own [self-hosting guide](https://docs.temporal.io/self-hosted-guide) calls for service deployment, namespaces, monitoring and upgrades; the [service description](https://docs.temporal.io/temporal) includes a server and database. It reduces bespoke workflow scheduling but adds a substantial operated service and workflow versioning discipline. | Reconsider only when long-lived, high-volume workflows and operations staffing justify it. Temporal history cannot prove a foreign payment occurred; adapter evidence and durable Moriarty effect accounting are still required. Actual fit, capacity and run cost are **unmeasured**. |
| **NATS JetStream** | [Apache-2.0 server license](https://github.com/nats-io/nats-server/blob/main/LICENSE); [official reference](https://docs.nats.io/reference/2.12/jetstream) describes persistence, replay and at-least-once delivery. A separate broker adds storage, consumer, replication and upgrade operations. | Optional event distribution after a database journal exists, not the authority or reconciliation store. Throughput need is **unmeasured**; adding it to the first slice would add infrastructure without establishing any missing financial predicate. |

**Selection rule:** start with PostgreSQL and a small worker; use Graphile Worker only for a Node service with enough scheduled jobs to justify a queue library. Keep the journal and external evidence format independent of the job runner so Temporal or JetStream can later carry scheduling or distribution without redefining accepted effects. Before adoption, verify a pinned release, license/dependency inventory, runtime compatibility and actual crash/retry behavior. No framework supplies cross-chain exactly-once execution, finality or refund exclusivity by itself.
