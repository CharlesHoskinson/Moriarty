# Optional DeFi kernel: ABI and semantic contract proposal

**Author role:** independent ABI and semantic-contract architect, assigned GPT-6 Sol cohort. The host did not expose a returned model identifier, so that assignment is not an independently verified runtime identity. **Date:** 2026-09-29. **Status:** recommendation for MIL/4 design review, specified only. No adapter, proof, or chain transaction was executed for this proposal.

## Decision

Freeze a small **semantic ABI** between the Moriarty intent language and an optional execution kernel. The language owns the signed financial relation, per-stage authority, accepted effects, and persistent duties. The kernel offers planning, exact-payload construction, dispatch, observation, and reconciliation. Each domain adapter owns a pinned codec and an evidence extractor. A settlement verifier decides which imported facts satisfy the selected policy. A direct Midnight caller uses the same intent and acceptance judgments without using the kernel.

The existing [NEAR scope proposal](../near-kernel-scope-2026-09-29/PROPOSAL.md) supplies the service operations and direct path. The [Hyperliquid comparison](../hyperliquid-kernel-comparison-2026-09-29/COMPARISON.md) adds native venue and queued action semantics. This proposal specifies the boundary between those pieces; it does not adopt either platform's trust model. The [product contract](../../docs/MORIARTY-PRODUCT-CONTRACT.md) makes managed routing optional, and [MIL/4 M4-C5](../mil4-successor-2026-09-29/DESIGN-MIL4-WORKING.md) still requires scheme, exact bytes, digest, verifier locus, and public inputs before foreign acceptance can be claimed.

## Interface shape

Use a closed tagged union of **capability classes**, each with an explicit authority and evidence profile. Avoid one opaque `execute(bytes)` method. An adapter may implement only the classes it can actually support.

| Capability | Required input | Result and accepted meaning |
| --- | --- | --- |
| `BuildPayload` | authorized leg, adapter manifest digest, venue action parameters | Exact unsigned or pre-signing bytes, decoded field map, payload digest; no external effect. |
| `SignPayload` | signed capability, immutable built payload, signer policy and key epoch | Signature and signed preimage digest; no broadcast or execution claim. |
| `Dispatch` | authorized, signed payload and logical effect ID | Attempt ID and network submission reference, or `UnknownSubmission`; no inclusion claim. |
| `Observe` | domain reference, attempt, pinned extractor and evidence policy | Typed observation with source bytes and provenance, including `Indeterminate`; no automatic language acceptance. |
| `ImportEffect` | observation and verifier result | Accepted per-item effect, fee, finality premise and receipt nullifier, or a typed rejection. |
| `Continue` | authenticated predecessor, cumulative exposure and outstanding duties | New prepared stage or a retained `Unknown`/recovery continuation. |

`BuildPayload` and `Observe` are pure with respect to user assets; `SignPayload` and `Dispatch` cross authority boundaries. The API must not make a successful build, simulation, signature, network acknowledgement, or enclosing transaction into an `ImportEffect`. A HyperEVM CoreWriter enqueue is a queue fact until the Core action executes; a resting HyperCore order is an open order until filled or canceled ([official interaction guide](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/hyperevm/interacting-with-hypercore), [Exchange API](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/exchange-endpoint)).

The signed `IntentEnvelope` should bind: semantic schema ID; program/Core and numeric profile digests; principal and grant; nonce/expiry; domain-qualified asset, units and scale; recipient and settlement locus; permitted action class and adapter manifest digest; target and parameter predicate; gross principal and fee caps; net floor; evidence/finality policy; signer scheme, key epoch and path constraint when applicable; recovery branches and residual duty bounds. A solver may choose a concrete plan only inside that relation. The kernel's `validatePlan` returns a derivation or a named failed predicate, but its answer is never a substitute for the accepting verifier's judgment.

The [earlier SDK specification](../../docs/superpowers/specs/2026-09-11-defi-kernel-sdk-interface-design.md) requires both Moriarty permission and native authority, and observes that a network label in a request is insufficient unless the signed preimage includes it **and** a named native verifier rejects a mismatch. That is the right test for each `SignPayload` class. [EIP-712](https://eips.ethereum.org/EIPS/eip-712) illustrates domain separation with chain and verifying-contract fields; it is an EVM example, not Moriarty's universal wire format. A [CAIP-2 blockchain ID](https://standards.chainagnostic.org/CAIPs/caip-2) can name a domain in records, but the adapter still must show native enforcement of the domain distinction.

## Byte contract and versioning

Freeze **three different artifacts**: (1) the Moriarty signed-envelope encoding, (2) the adapter's native signing preimage and submitted transaction bytes, and (3) the extractor's canonical effect statement. Each carries a schema ID, major/minor version, and domain-separated digest. The signed envelope binds the exact adapter manifest digest, not just a mutable adapter name. The manifest binds chain/network, contract or endpoint, action class, codec version and implementation digest, supported signing domain, field extraction rules, source schema, native success discriminator, finality policy, and verifier locus. Pinning a manifest does not prove its implementation correct; it prevents silent semantic substitution after authorization.

Recommend deterministic CBOR for Moriarty's **new** kernel-facing records because it has binary strings and a published deterministic encoding profile. This is a format proposal, not a claim that existing ZKIRv3 or Midnight bytes already use CBOR. Define a Moriarty-specific profile: definite lengths, integer-only financial amounts, fixed field tags, no floats, duplicate keys rejected, unknown critical tags rejected, and decode-then-re-encode equality before signature acceptance. [RFC 8949 §4.2](https://www.rfc-editor.org/rfc/rfc8949.html#section-4.2) supplies deterministic CBOR rules; its general interchange format permits multiple representations, so naming “CBOR” alone is insufficient. [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785) supplies a JSON alternative but describes constraints on JSON numbers; it is less attractive for large exact financial integers. The choice must be decided with M4-C1/M4-C5 and published test vectors before any signature is authorized.

Use `H("moriarty/kernel/<record-kind>/<major>", length || bytes)` for each commitment, with the actual hash algorithm and byte framing frozen in the profile. Never hash a human-readable preview, parsed object with implicit defaults, or mutable URL. Record both the signing preimage digest and final submitted-byte digest where a native signature is assembled into a transaction. Show the decoded, signed fields to the signer. A changed payload, schema, network, recipient, fee, path, epoch, nonce, or adapter manifest requires a new authorization decision. Minor versions may add only ignorable, nonsigned display metadata. Any field that affects authority, effects, evidence or recovery requires a new major version and new signature. Reject unknown critical versions and tags before value moves; migration produces a new signed artifact and cannot reinterpret an old one.

## Receipt and continuation algebra

Define receipts as immutable, typed **claims about one phase**, with a source, verifier premise and stable identity. An operation may produce several receipts. Suggested phase order is `Prepared`, `Reserved`, `Signed`, `Submitted`, `Included`, `Queued`, `Executed`, `PartiallyFilled`, `Finalized`, `Delivered`, `Recovering`, `Refunded`, and `ClosedWithClaims`. These are not one linear enum: for example `Queued` and `Included` describe different loci, and `Unknown` is a knowledge state that can coexist with a live submitted attempt. Each receipt includes `intentId`, `legId`, `logicalEffectId`, `attemptId`, domain, settlement locus, adapter/extractor manifest digests, payload and submitted-byte digests, native transaction or message ID, observed per-item outcome, actual amounts/fees, source evidence reference, evidence policy and finality status. The fact that an observation is authenticated by a committee remains visible as an attestation premise. The distinction between evidence and an appraisal result in [RFC 9334](https://www.rfc-editor.org/rfc/rfc9334.html) is a useful analogy, though that RFC is about remote attestation rather than chain finality.

`Continuation` is an authenticated snapshot of committed effects, pending attempts, consumed authority, reservations, cumulative gross exposure, net outcome, claim nullifiers and persistent duties. A retry reuses `logicalEffectId` but gets a new `attemptId` only after evidence proves the old attempt cannot execute, or after an explicitly authorized bounded overlap policy reserves for both outcomes. Timeout alone does not prove nonexecution. Import consumes a source-event nullifier across intents and a leg-progress nullifier per attempt. Partial fills retain the open quantity and future fee exposure; refunds retain source and destination accounting so a late delivery cannot be concealed. The prior [SDK interface](../../docs/superpowers/specs/2026-09-11-defi-kernel-sdk-interface-design.md) already specifies per-item success extraction and two distinct nullifier purposes; this ABI makes them first-class record fields.

The kernel may report `Unknown` or `Indeterminate` indefinitely if the selected evidence cannot establish a stronger fact. A direct Midnight path can construct and submit a valid proof-carrying program through its public compiler and ledger interface, import its own actual ledger effect, and advance under the same judgments. Kernel outage, membership and adapter catalog state cannot alter the language's validity or act as universal admission prerequisites ([product contract](../../docs/MORIARTY-PRODUCT-CONTRACT.md)).

## Evidence and dissent

The three [Aeon experiment reports](../aeon-kernel-experiments-2026-09-29/authority/REPORT.md) ([signing](../aeon-kernel-experiments-2026-09-29/signing/RESULT.md), [bridge](../aeon-kernel-experiments-2026-09-29/bridge/RESULT.md)) are useful counterexample probes, not acceptance evidence. Recipient, domain, fee, signing fields and phase-tag substitutions were rejected in selected encodings; the bridge model rejected a full refund based on timeout or an empty observation. The authority probe also **accepted** an impossible combined refinement and `false`. A native Aeon promise for a finalized token was accepted. Thus no Aeon type check should authorize dispatch, import or refund. Its integer stand-ins did not test exact bytes, MPC, finality, bridge delivery or Midnight correspondence.

**Dissent from the broadest service vision:** do not freeze universal identity, gas abstraction, a single grade system, or an all-chain adapter registry as prerequisites of this ABI. Those are optional application promises with distinct trust and availability assumptions. The initial contract should expose sufficient evidence fields to support them later without assigning them to the core language.

**Dissent from a single shared lifecycle enum:** a shared causal receipt envelope is valuable; one total order of phases is false for queued venue actions, bridge legs and direct Midnight settlement. Model phase as typed facts with explicit dependency edges. The public outcome can be a projection that cites those facts.

## Falsifying experiments and open questions

1. **Exact-byte fixture:** two independent encoders and one decoder generate the same envelope and native preimage; mutation of recipient, fee, network, manifest version, nonce and unknown critical tag rejects before signing. If a permitted mutation keeps the digest or is interpreted differently by the signer and verifier, the byte contract fails.
2. **Adapter correspondence:** independently decode submitted bytes and compare the target, value, recipient, fee and native success discriminator with the authorized leg. A successful outer transaction with failed inner action must leave the leg unresolved or failed, not delivered.
3. **Retry and bridge race:** dispatch once, lose acknowledgement, observe a late partial delivery, and request refund plus retry. Show that cumulative delivery plus refund and all live attempts remain within signed bounds, or retain `Unknown`. A timeout-only full refund falsifies the recovery contract.
4. **Direct Midnight:** execute the same supported intent without kernel service availability and compare accepted proof/ledger effects with language judgments. Failure caused solely by the optional service being absent falsifies the product boundary.
5. **Upgrade:** change adapter codec or extractor while an intent is pending. Old receipts must remain interpretable under pinned versions; new code cannot reinterpret or discharge them without a signed migration.

Open decisions: the first native adapter and its actual verifier locus; custody and signer control; hash and envelope codec choice; which external facts can be proved versus attested; whether an overlap retry profile can ever satisfy the gross cap and recovery obligations; and how authenticated continuation state survives rollover. These require concrete implementation and ledger evidence. This proposal makes no deployment, proof, or production-safety claim.

## Framework addendum: lightweight implementation choices

**Recommendation, conditional on the byte-profile decision:** for a TypeScript service prototype, evaluate base [`cborg`](https://github.com/rvagg/cborg) for CBOR encoding/decoding and [`@noble/hashes`](https://github.com/paulmillr/noble-hashes) for the selected digest. `cborg` explicitly targets strict, deterministic CBOR, has an Apache-2.0 license, and published [v6.1.2 on 2026-08-31](https://github.com/rvagg/cborg/releases). Use its base codec, not its `extended` mode, which its own documentation says does not preserve deterministic map ordering. `@noble/hashes` is MIT, documents small modular imports and transparent releases, and its [changelog](https://github.com/paulmillr/noble-hashes/blob/main/CHANGELOG.md) records recent maintenance. The checkout's existing Midnight experiment lockfile already contains several transitive `@noble/hashes` versions; that is a repository observation, not approval of a direct dependency or its exact version. Neither library defines Moriarty's financial types or signature policy. Pin versions and compare independent byte vectors before using either in an authority path.

| Candidate | Fit and burden | License and maintenance evidence | Disposition |
| --- | --- | --- | --- |
| [`cborg`](https://github.com/rvagg/cborg) | Small codec surface; strictness fits exact-byte records. Moriarty still needs a restricted schema and decode/re-encode rule. | [Apache-2.0](https://github.com/rvagg/cborg#license-and-copyright); [August 2026 release](https://github.com/rvagg/cborg/releases). | Preferred prototype codec if CBOR is selected; cross-language and native proof correspondence unverified. |
| [`cbor-x`](https://github.com/kriszyp/cbor-x) | Rich extension and record features increase the profile surface; README describes preferred encodings where feasible, which does not by itself establish Moriarty's exact deterministic profile. | [MIT repository license](https://github.com/kriszyp/cbor-x). Current release cadence and required-mode conformance were **not verified** here. | Alternate only after deterministic cross-implementation vectors. |
| [`@noble/hashes`](https://github.com/paulmillr/noble-hashes) | Modular byte-array hash primitives; still requires a frozen algorithm, framing and domain separation. | [MIT and release process](https://github.com/paulmillr/noble-hashes); [maintained changelog](https://github.com/paulmillr/noble-hashes/blob/main/CHANGELOG.md). | Preferred TypeScript hash candidate; no cryptographic correspondence to Midnight asserted. |
| [`Ajv`](https://github.com/ajv-validator/ajv) | Well-supported JSON/JTD validator for manifests, previews or HTTP records. Its richer JSON Schema surface adds complexity and JSON validation cannot establish signed CBOR/native-byte meaning. | [MIT license](https://github.com/ajv-validator/ajv/blob/master/LICENSE); [2026 release history](https://github.com/ajv-validator/ajv/releases). | Optional service-edge validation only; keep financial and authority checks in the accepting path. |
| [`viem`](https://github.com/wevm/viem) | Supported typed EVM interfaces and EIP-712 helpers, but importing it into the universal ABI would couple all adapters to EVM semantics. | [MIT source license](https://github.com/wevm/viem/blob/main/src/LICENSE); [active releases](https://github.com/wevm/viem/releases). | Use only inside an EVM adapter if one is selected; native preimage and verifier checks remain adapter-specific. |

These are library candidates, not a dependency decision. License compatibility with the final distribution, transitive dependency inventory, package size, maintained security support, and exact codec behavior under the chosen profile still need a pinned-version review. No package was installed or benchmarked for this addendum.
