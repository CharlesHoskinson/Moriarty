# LL04 authority design proposal

**Status: proposed for independent Opus/Astra review.** No implementation, signature, compiler, wallet access or public action ran. This extends [the full ledger contract](ledger-contract-draft.md); every full state field, ordered effect, bound, obligation and historical acceptance limit remains required.

## Selected design

Use an explicit, one-time native maintenance transaction signed by the existing debtor wallet to activate the exact reviewed financial verifier keys. Deploy a fresh lifecycle instance with only deterministic `initialize` enabled. After its exact genesis is finalized, the debtor signs one update that enables `originate`, `accrue`, `repay` and `settle`, removes `initialize`, and replaces maintenance authority with an empty committee whose threshold is one. No financial circuit exists on the initial deployed instance, so possession of a role secret or a host consent flag cannot create debt before activation.

This uses installed ledger-v8 maintenance operations and the existing wallet `signData` callback. It introduces a real setup transaction; it is not an assertion that possession of a maintenance key means assent. The signature approves a precise deployment address and verifier-key update. The debtor signing consumer must show and verify the exact source, profile, roles, terms, cap, complete genesis and permission policy that those bytes authorize.

Origination is funded by the existing lender wallet; repayment and settlement by the existing borrower wallet. Accrual is explicitly permitted to any caller who satisfies the frozen source predicates, eligible time, next period, lifetime cap and work bounds. This permission is in the immutable descriptor approved by the debtor. It grants no spending authority over another wallet; the actual caller funds its own fee.

**Remaining limitation:** Compact `receiveUnshielded` does not name an input owner. The actual provider and independent native-input observer enforce lender/borrower funding identity. This proposal does not establish that an arbitrary alternative client is rejected by the ledger solely for using another payer. That predicate remains open; independent review must not convert this boundary into an unqualified ledger authorization or correspondence claim.

## Exact deployment and signature bindings

The proposed immutable descriptor includes every `wireAndLedgerBindings` field in the JSON. It binds Source5 primitive bytes and Core4/schema/action order; profile, registered bounds and canonicalization; lifecycle/kernel/lowering identities; full generated artifact commitments; exact native role addresses and public keys; Cash domain/issuer mapping; all principal, cap, conversion, allocation and accrual terms; complete financial genesis and ordinary genesis; and the explicit public-accrual policy. Persist the actual full state. A digest supplements the state and cannot replace it with a reduced projection.

For this source, the loan is Loan1, Borrower owes Lender principal100 with cap110, Cash denomination/asset, conversion1/scale0/none, AccrualFirst, rate1/10 floor, period60 and firstPeriodStart1000. Initial balances are Lender100, Borrower10, Other/Token7; allowances100/0,110/0,3/1; no obligations or used identities; work512/17/reserve16; phase0/paid0. Retain exact ordered arrays and numeric encodings. Dynamic source IDs/arguments remain dynamic; D1/O1/A1/P1/R1/P2/R2 are oracle inputs, not a new reduced source language.

Construct the generated genesis descriptor and native bootstrap state before deriving the new deployment address. Use only the `initialize` verifier and maintenance authority `[existingBorrowerUnshieldedVerifyingKey], threshold1, counter0`. The constructor/initialize pair must enforce the precise declared genesis, with initialize callable once and no arbitrary state setter or other operation/version present. Initialize records actual native funding/mint provenance for Lender100/Borrower10 and the unchanged Other row. Any required funding setup remains a real additional action; neither a host balance nor the old20-billion borrower mint suffices.

A new lifecycle preparation path can build a native `ContractState`, copy actual generated constructor `data` and legitimate native balances, install only the bootstrap `ContractOperation`, set the public-key authority, and then form `ContractDeploy`. Do not edit an existing prepared deployment or change its address after freezing it. The current `prepareFinancialDeployment` does not expose this behavior; its old private signing-key flow and deployed instances remain historical. No raw debtor secret is needed: use public key and signing callbacks.

After canonical finalized initialize readback, construct one native `MaintenanceUpdate(contractAddress, orderedUpdates, 0n)` with this exact order:

1. `VerifierKeyRemove("initialize", ContractOperationVersion("v3"))`.
2. `VerifierKeyInsert("originate", v3 exact reviewed originate key)`.
3. `VerifierKeyInsert("accrue", v3 exact reviewed accrue key)`.
4. `VerifierKeyInsert("repay", v3 exact reviewed repay key)`.
5. `VerifierKeyInsert("settle", v3 exact reviewed settle key)`.
6. `ReplaceAuthority(ContractMaintenanceAuthority([], 1, 1n))`.

The borrower consumer verifies all six updates, exact current operation map and full genesis, then calls the existing `unshieldedKeystore.signData(update.dataToSign)` and `update.addSignature(0n, signature)`. Verify against the expected borrower public key before forming `Transaction.fromParts(expectedNetworkId, undefined, undefined, Intent.new(admittedTTL).addMaintenanceUpdate(update))`. This describes use of installed interfaces, not executed code. Submit with the actual guarded provider and pinned SDK `submitTx`. Do not use several separately submitted maintenance helpers: an intermediate unfrozen key map would change the reviewed consent boundary.

Native `dataToSign` contains the maintenance domain, contract address, ordered updates and old counter. The address commits initial native state and nonce; it does not automatically commit arbitrary later state. Genesis/head binding therefore depends on exact immutable genesis committed by deployment and deterministic one-shot initialize. Each financial circuit must require initialized state; originate also requires the exact consented financial genesis/revision0, then each later action consumes the real next revision. A stored expected-head value supplied by a caller is insufficient.

Native maintenance can technically be submitted before initialize: it has no financial-head condition. The approved consumer signs only after finalized initialization. Even a prematurely relayed valid activation must be unable to create debt because all financial circuits assert initialization/genesis; removing initialize early may strand this new instance. Preserve that failure and charges instead of silently recreating it. This limitation is included in the controls.

The native signature has no separate network field. Bind network/genesis/protocol in the deployment descriptor and verified consumer chain context. Retain exact finalized initialize/activation transaction IDs, block references, native operation maps and authority counters in the existing observation flow. Do not invent a self-referential receipt hash inside its own signature or claim that a declaration of networkTag verifies the real chain. A mirrored-chain replay requires an actual native control before claiming cryptographic exclusion.

After activation, only the four exact financial verifier keys may remain, all unsupported operation versions absent, and authority must be empty/threshold1/counter1. Threshold0 would allow unauthorized updates. Financial data, phase, revision0, balances, allowances, work and all source identity histories are unchanged. The native ledger has a separate setup transition; keep it in native history. Do not insert consent into the seven source financial effects.

## Actual caller and funding

Use two existing wallet contexts with separately bound native public identities. The borrower context owns consent signing and borrower-funded repayment/settlement. The lender context owns origination funding. Each immutable provider retains its own payer/account/reservation identity; the current provider cannot switch accounts under one record. Explicitly allocate the lifecycle total across those records under existing accounting instead of resetting a consumed allocation. The selected bounded run may use borrower as the fee payer for deploy, initialize, activation and public accrue, but public-accrual permission is not borrower-only.

The actual source-derived originate calls receive100 Cash/send100 to Borrower with source Transfer/Origination checks; the provider must select and sign lender-owned native inputs, and independent readback must verify them. Repay and settle receive source-computed Cash and send to Lender, with borrower input signatures checked. Retain native input gross caps and change, complete effects and cumulative native DUST fees. A native signature proves authority to consume its own input; it does not by itself cause Compact to assert that its owner is the source Lender/Borrower. The JSON records this as an unresolved arbitrary-caller ledger predicate, not a source success claim.

The independent complete oracle remains the earlier contract: originate principal100/accrued0; accrue100/10; repay30 leaves80/0; settle80 leaves0/0 with settled obligation retained. Lifetime incurred remains110. Work and all ordered financial IDs/effects carry across each actual head without reset. Public permission for accrue cannot override source ensures or allow a second accrual/period.

## Required resource and history delta

The proposed fresh-instance sequence is **deploy → initialize → activate consent → originate → accrue → repay → settle**, seven separate submissions when the six activation updates share one transaction. Any additional asset funding/setup increases this actual count. This is a design count, not an authorized allowance. It cannot fit the inherited closed four-call deploy/initialize/accrue/settle plan without an explicit reviewed amendment.

Record new setup identity, exact plan/schema/stage changes, all actor funding, gross limits, native fees, current deadline and remaining attempts in the existing resource/admission records through the user-required substantive decision process. Preserve the expired September11 window, consumed attempts, historical charges, old loan deployment and private stores. Do not reuse historical unused slack or claim current missing accounting exists. No numerical fee cap, new wallet or execution attempt is authorized by this proposal.

## Disposition for review

The selected activation uses existing native public-key authorization and provides an explicit debtor act binding the exact frozen program. Role secrets, blind maintenance-key possession and bearer tokens were rejected as substitutes. Public bounded accrual is a deliberate permission choice to review, not an inference from the old borrower-secret accrue wrapper.

Review must address the payer-enforcement boundary, immutable-genesis/head assumption, early activation failure and chain replay boundary explicitly. The design does not close LL04.1/LL04.2, authenticate arbitrary lowerings, prove native/Compact correspondence, or waive mandatory SP09/PCD acceptance. LL06 compilation, LL07 Docker results and LL08 Preview settlement retain their original gates.

The JSON preserves the exact original requirement identities, full state inventory, source facts/preimages, interfaces, alternatives and controls. Only these two proposal deliverables were written.
