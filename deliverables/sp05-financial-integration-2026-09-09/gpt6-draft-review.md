## Material next corrections

1. **Bind the original approved call to the balanced recipe before signing.** `providers.mjs:187–199` checks native markers and budgets for the supplied transaction, calls balance, then takes its first semantic snapshot from the returned recipe. A balancer can change the base transaction's recipient, output value, actions or intent structure while staying within gross caps; the later signature/finalization equalities only preserve that changed recipe. This is a remaining R6 obligation explicitly acknowledged by the implementer. The pinned facade balances unshielded effects in place and can add a separate DUST transaction, so naive whole-transaction equality before/after balance is not the repair. Freeze the original approved effects before invoking the wallet, define the allowed funding/change additions, and check original actions, fixed financial outputs, intent associations and permitted additions against the returned recipe before any signature. Add inert same-gross recipient/value/action substitution controls and permitted-change positives.

2. **Make campaign reservations durable across provider reconstruction.** `providers.mjs:132–134,174–178,204–211` keeps all submission, per-asset gross and DUST reservations inside one closure. Constructing another provider with the same limits starts them at zero. The new per-asset representation fixes the old cross-token scalar defect within an instance; it is not persistent campaign accounting. Bind the existing campaign/local state record to its allocation identity, reserve durably before finalization and preserve ambiguous charges across restart. Missing/corrupt state must not mean zero. Add reset/reconstruction and failed-finalization retention controls. This needs the existing state path, not a new orchestration system.

3. **Bind local network and wallet identities before deployment.** `run-local.mjs:25–36` checks only the caller's `network === 'undeployed'` string. The provider accepts syntactically valid endpoints but does not require a network ID; its pinned contracts SDK actually uses global `getNetworkId()`, which the retained wallet restoration code sets from its configuration. Supplying a Preview wallet/provider with the local string is not excluded by this driver. Likewise, arbitrary `roles.firstAddress/secondAddress` are not bound to the wallet funding key; the receipt derives signed input owners but has no role expectation yet. The composition must validate the actual selected network/global SDK configuration/endpoints, wallet-derived funding address and role mapping before the first deploy, with a negative wrong-network and wrong-payer test. Preserve existing identities; do not generate substitutes.

4. **Define and enforce comparator success, rather than merely awaiting it.** `run-local.mjs:42` ignores the return value from `verifyStage`; a comparator returning `false` or a rejected result resolves normally and the next transaction proceeds. The current tests use assertions that throw, which is a possible interface convention but is undocumented and unenforced. Define one explicit success contract for the new comparator and reject every other outcome before appending a stage or submitting the next call. Add a negative returned-failure control as well as a thrown-failure control. The current failure test throws from observation, so it does not exercise the reported comparison-failure branch.

5. **Carry incomplete cleanup/containment into the driver outcome.** `run-local.mjs:61` awaits and discards `providers.cleanup()`; that function expressly returns `containmentComplete:false`, pending-operation count and possibly `walletStopped:false`. A normal-looking driver return therefore omits the very limitation the provider reports. Preserve cleanup and reservation/identifier state in an explicit public operational result or failure record, and do not report bounded execution completed while required containment is unresolved. Outer process containment for uncancellable SDK promises remains required before live execution. Also put provider-owned cleanup around preflight validation where ownership has already transferred; current validations occur before the driver's try/finally.

6. **Finish the actual financial comparator and proven-asset composition.** The driver still takes arbitrary compiledContract, observer, comparator and wallet/role inputs. No loader checks the generated module against a successful real build receipt, and no complete generated-state/effects comparison is supplied by this draft. Implement the already requested original fixture field/provenance comparison without expected-value fallback. Cover initial, intermediate and final obligations, paid/due components, token colors, signed payer, payees, gross movements, fees, reserves, allowances, revisions and remaining work, including extra/missing effects and rollback controls. The receipt's native action projection contains address/entry point, not the complete financial call result; the missing comparator must obtain each required leaf from actual generated state/native observations rather than assuming that a matching action name supplies it. R4 remains pending, not fixed by these 43 tests.
