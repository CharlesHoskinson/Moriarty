**Recommendation: expose a bounded orchestration SDK with three separate authorities: the Moriarty intent, the exact foreign transaction authorization, and the evidence that permits importing its result.**

Use one Midnight instance as the coordinator for the first multichain profile. Foreign legs advance a bounded pending record through `ImportFrom`; they are never represented as Midnight `Step` executions. Keep the four existing effects.

This is a proposed interface, not an implementation or admission claim. The supplied multichain design is explicitly specified-only. [Design specification:4](/home/charl/Moriarty/docs/superpowers/specs/2026-09-11-defi-kernel-multichain-design.md:4)

**Corrections to the starting position**

1. **“The intent’s deltas net to zero across its legs” is wrong as stated.** A user exchanging asset A for asset B has a nonzero delta in each asset. Conservation must include counterparties, reserves, escrow, fee recipients and explicit issuance/burn accounts, separately for each exact asset identity. NEAR’s implementation matches deposits and withdrawals per token and rejects unmatched deltas; its user `TokenDiff` can express `A: -100, B: +200`. Neither establishes conservation by summing unlike assets or only the user’s legs. [TokenDiff:18](/home/charl/protocol-graph/repos/near-intents/contracts/defuse/core/src/intents/token_diff.rs:18), [transfer finalization:265](/home/charl/protocol-graph/repos/near-intents/contracts/defuse/core/src/engine/state/deltas.rs:265)

2. **Salt rotation and invalidation must be distinct operations.** In the inspected NEAR implementation, rotation emits an empty invalidation set; explicit invalidation is a separate DAO/SaltManager operation. Moriarty should define principal-scoped epoch invalidation rather than inherit an unspecified “rotating salt” behavior. [Salt methods:12](/home/charl/protocol-graph/repos/near-intents/contracts/defuse/src/contract/salts.rs:12)

3. **Distinct derivation paths are necessary key isolation, not sufficient network authentication.** The inspected NEAR derivation function consumes predecessor account and a caller-supplied path; it does not impose chain separation. Moriarty must impose that policy itself. [Derivation:10](/home/charl/protocol-graph/repos/near-mpc/crates/near-mpc-crypto-types/src/kdf.rs:10)

4. **“Recovery cannot strand value” needs a funding and custody condition.** A deadline cannot undo an irreversible foreign action. The SDK can guarantee release of local escrow, payment of prefunded compensation, and preservation of residual claims. It cannot guarantee recovery of arbitrary foreign assets.

5. **Foreign network execution costs are missing from the four-plane accounting description.** Preserve the four planes, but make settlement costs domain-specific: Midnight DUST and foreign network charges are separate settlement line items. Neither is orchestration compute.

6. **Several chains do not imply several Midnight predecessors.** A coordinator can import several foreign results serially while retaining predecessor fan-in one. L6 is needed for actual joins of Midnight instances, not merely because a plan mentions three foreign domains.

**3. Exact multichain lifecycle**

Consider a hypothetical, explicitly illustrative plan:

- User pays `100,000,000` atoms of a Midnight asset `M`.
- User must receive at least `60,000,000` atoms of a NEAR asset `N`.
- User must receive at least `39,000,000` atoms of a TRON asset `T`.
- All three example assets use six decimal places.
- Application fee: `100,000` atoms of `M`.
- Orchestration budget: `200,000` atoms of `M`.
- Maximum gross user debit of `M`: `100,300,000` atoms.
- Solver supplies foreign inventory; the user grants no general foreign-account spending authority.
- Priority selections are empty.
- No new user liabilities are permitted.

These symbols do not assert that any particular deployed token has this identity or precision.

**Step 1 — construct `IntentTerms T0`.**

```text
authorization = Outcome
instance = coordinator I
nonce = { principal: U, instance: I, epoch: 7, salt: S7, sequence: 42 }

grossDebitCaps = [
  { account: U_midnight, asset: M, maximum: 100300000 }
]

minimumNetCredits = [
  { account: U_near, asset: N, minimum: 60000000 },
  { account: U_tron, asset: T, minimum: 39000000 }
]

liabilityCaps = []          // no new liability authorized
orchestrationBudget = { asset: M, atoms: 200000 }
partialFillPolicy = NoAutomaticRefill
```

Each foreign leg names `ImportedThreshold{policyHash}`. The policy commits to the exact chain, extractor, finality rule and quorum.

A sample timing choice is:

```text
quote lifetime:                  30,000 ms
stopNewDispatchAt:               t0 + 120,000 ms
evidenceDeadline:                t0 + 600,000 ms
recoverAfter:                    t0 + 660,000 ms
maximumRecoveryTransitions:      2
```

Those are user-selected example budgets, not claims about protocol finality.

**Step 2 — obtain `ResolvedOrder R0`.**

`resolve(program, T0)` publishes the bounded relation, amounts, approved primitives, evidence policies and recovery requirements.

It does not publish wallet secrets, unrestricted signing authority or private witness fields.

**Step 3 — obtain `Plan P0` and `Quote Q0`.**

A solver returns:

```text
P0.legs:
  L0: reserve M on Midnight
  L1: transfer N from solver_near to U_near
  L2: transfer T from solver_tron to U_tron
  L3: finalize Midnight consideration after imports

dependencies:
  L1 <- L0
  L2 <- L0
  L3 <- L1, L2
```

`Q0` binds `H(T0)` and `H(P0)`, itemizes all charges, reserves the maximum metered work and includes a separate DUST estimate.

The flow table includes both sides of every asset movement:

```text
M: user -> escrow -> solver / application / orchestration accounts
N: solver_near -> user_near
T: solver_tron -> user_tron
```

For every exact asset:

```text
sum(all account deltas for that AssetId) = 0
```

No equality between `M`, `N` and `T` is asserted.

Foreign network fees paid by the solver appear as separate flows/charges. They are not subtracted from the user’s promised `N` or `T` credits.

**Step 4 — construct `Intent I0`.**

`prepareIntent(T0, P0, Q0)` binds:

```text
terms
selectedPlanHash = H(P0)
selectedQuoteHash = H(Q0)
claimManifestRoot
displayDigest
```

The commitment order is:

```text
IntentTerms
  -> ResolvedOrder / Plan
  -> Quote
  -> proof-independent ClaimSpec manifest
  -> Intent
  -> intent signatures
  -> instantiated transition claims
  -> transition proof
```

Quote signatures and later proof bytes never enter their own preimages.

**Step 5 — verify and sign.**

```text
verifyPlan(...)          -> Verified<PlanCertificate PC0>
createSigningRequest(...) -> IntentSigningRequest SR0
signIntent(SR0, wallet)   -> SignedIntent SI0
verifyIntent(SI0, ...)    -> Verified<SignedIntent>
```

The display reports the three distinct assets, maximum gross debit, net foreign credit goals, all charges, deadlines, recovery exposure and “threshold-attested foreign results.”

**Step 6 — admit the pending intent on Midnight.**

Prepare a `Step` transition that:

- Reads and writes the current head.
- Consumes nonce `(U, I, 7, S7, 42)`.
- Reserves the user’s consideration and authorized fees.
- Creates the bounded `PendingIntent`.
- Reserves any required compensation.
- Fixes quote allocations and the selected route.

Then:

```text
TransitionCore TC0
 -> ProofRequest PR0 containing SI0
 -> TransactionBundle TB0
 -> Verified<TransactionBundle>
 -> SubmissionRecord SUB0
 -> finalized ledger acceptance
 -> Accepted<PendingIntent PI0>
```

Only after that acceptance may an operator request foreign signatures.

Nonce consumption occurs once at admission. Continuations use `PI0.id` and leg/import nullifiers. They do not consume the same intent nonce again or require the original head to remain current.

**Step 7 — authorize and broadcast foreign legs.**

For each eligible leg:

```text
materializeForeign(PI0, leg, nativeContext) -> ForeignPayload FP
verifyForeignPayload(...)                -> Verified<ForeignPayload>
createForeignSigningRequest(...)         -> SignatureRequest FSR
signForeign(FSR, signer)                  -> SignatureCertificate FSC
assembleForeign(FP, FSC)                  -> Verified<SignedForeignPayload>
broadcastForeign(...)                    -> SubmissionRecord FSUB
```

A dropped acknowledgement causes reconciliation of `FSUB`, not creation of a second transfer.

**Step 8 — import each foreign result.**

```text
collectImport(FSUB, policy) -> ImportCertificate IC
verifyImport(IC, ...)      -> Verified<ImportCertificate>
```

Prepare `ImportFrom` against the **current** Midnight head. Its proof verifies the admitted import relation, records the foreign fact nullifier, and updates the pending leg’s actual cumulative accounting.

Importing L1 does not require L2’s result and does not declare the whole intent settled.

Serial imports retain Midnight predecessor fan-in one.

**Step 9 — final settlement.**

Once all required leg predicates hold:

```text
prepareTransition(Step, SI0, P0, currentState, imports)
 -> final TransitionCore
 -> ProofRequest
 -> TransactionBundle
 -> verified submission
 -> SettlementRecord { status: Succeeded }
```

The final relation checks actual—not projected—gross debits, net credits, fees and liabilities across the admitted execution.

Fee effects credit the application’s accrual account. The application later claims that balance through `claimFees`.

**Failure path**

If L1 succeeds and L2 cannot be proven:

- Keep L1’s imported fact.
- Do not mark the net goals satisfied.
- Stop new dispatch at the signed dispatch cutoff.
- After `recoverAfter`, execute the signed bounded recovery rule.
- Release unused local escrow and pay any specified prefunded compensation.
- Preserve obligations or foreign claims that remain.

Return `Compensated` or `ClosedWithClaims`, never `Succeeded`.

For the first release, I would admit irreversible user-funded foreign routes only where the selected recovery policy has sufficient prefunded compensation or a demonstrated bounded refund path. Otherwise, quote verification rejects the route.

**4. Foreign authorization and result import**

**Authorization requires both Moriarty permission and native authority.**

The `CallPermission` answers:

> What may this intent cause?

The `ForeignAuthorization` answers:

> Which native account may authorize that payload, under which current permission?

Both must hold. Possessing a native key does not enlarge the signed Moriarty relation.

For chain-derived keys, the SDK computes an injective path:

```text
"moriarty/1/"
  + hex(H(canonical(ChainRef)))
  + "/"
  + hex(principalId)
  + "/"
  + decimal(accountIndex)
  + "/"
  + decimal(keyVersion)
```

Developers select `accountIndex`; they cannot supply an arbitrary derivation path. The signing service verifies the same derivation policy.

**Network binding is decoded from the actual signature preimage.**

Hyperliquid demonstrates why a generic network label is inadequate:

- Exchange actions are MessagePack-encoded, augmented with nonce, vault and optional expiry, hashed, and wrapped in an `Agent` message.
- The wrapper uses `source = "a"` or `"b"` and an EIP-712 domain with `chainId = 1337`.
- User-signed actions use a different construction; the code explicitly identifies `hyperliquidChain` as the environment/replay discriminator.

**Import acceptance has a separate checklist enforced by the relation.**

`ImportFrom` must check:

1. The intent names `ImportedThreshold` for this leg.
2. The policy hash is permitted by deployment and exactly matches the intent.
3. The deployed key set and threshold match; signer indices are distinct.
4. The threshold signature verifies over the canonical import statement.
5. Source chain, payload hash, pending ID, intent ID and leg ID all match.
6. The extractor and source schema are the pinned versions.
7. Finality and freshness satisfy the named policy.
8. The extracted account, recipients, amounts, fees and liabilities satisfy the leg predicate.
9. The transaction/event identity has not already discharged another obligation.
10. Partial execution is recorded as partial execution, not success.
11. The current pending state still admits this import or its signed late-evidence recovery path.

Use a source-event nullifier derived from:

```text
H(sourceChain, transactionId, eventOrReceiptId, extractionPolicyHash)
```

and an intent-leg progress key derived from:

```text
H(instance, intentId, legId, attempt)
```

The first prevents reusing the same foreign event as new value. The second prevents duplicate progress.

A `SignatureCertificate` is never accepted in place of an `ImportCertificate`. **5. What the SDK deliberately does not offer**

- **No `signHash`, `sendRawTransaction` or unrestricted `call`.** Such methods bypass the decoded permission and exposure checks.
- **No arbitrary remote execution inside the language.** External execution is orchestration around registered primitives; its result is imported.
- **No cross-chain atomicity promise.** There is a bounded sequence with explicit custody, deadlines, imports and recovery.
- **No “same token” alias across chains.** Conversion or bridging requires an explicit primitive, inventory source and evidence.
- **No automatically reusable partial-fill authority.** V1 uses one admitted intent and bounded leg progress. A second economic fill requires new authorization.
- **No cancellation that erases dispatched work.** Epoch invalidation prevents future admissions. Cancelling an admitted intent follows its recovery rules; it does not revoke already-issued foreign signatures retroactively.
- **No fee amount reconstructed from an ambiguous aggregate.** An adapter must distinguish total, component and additional charges. Missing accounting fields produce unavailable evidence.
- **No sponsor-to-user fallback by surprise.** Capacity exhaustion can use an explicitly authorized priced fallback; sponsor shortfall or budget exhaustion stops further work.
- **No hardcoded resource prices, finality delays or auction latency.** These are versioned quote/policy inputs.
- **No claim that priority buys finality or success.** Priority affects a named ordering service.
- **No unbounded nonce table or watcher.** The profile bounds active nonces, pending intents, imports and recovery work. Expired epochs can be pruned only after their replay window and pending references are closed.
- **No release-time certificate route yet.** Threshold imports are the first supported evidence class; bounded certificate imports remain unavailable.
- **No kernel guarantee for arbitrary foreign staking exits.** The SDK exposes position and withdrawal conditions, not an unconditional liquid balance.

TRON is useful evidence for separating bytes from execution capacity, but its resource system is not a literal specification for Moriarty’s meter. The inspected documentation distinguishes bandwidth and energy, priced TRX fallback, and a deployer subsidy whose uncovered portion can fall to the caller. Moriarty must instead apply its explicit signed payer rules. [Resource units:3](/home/charl/protocol-graph/repos/tron-docs/docs/clients/wallet-cli/typescript/concepts/energy-bandwidth.md:3), [deployer subsidy:15](/home/charl/protocol-graph/repos/tron-docs/docs/clients/wallet-cli/typescript/commands/contract/set-origin-energy-limit.md:15)

**6. The three hardest interface decisions**

| Decision | Options | Choice |
|---|---|---|
| **What does the user sign before native nonces and block references exist?** | Exact foreign bytes for every leg; a broad outcome with unconstrained routing; or a selected bounded plan with adapter-defined materialization. | **Selected bounded plan.** Sign the outcome, route, caps, evidence and materialization rules. Verify every exact foreign payload before requesting its native signature. Economic substitutions require a new intent. |
| **What does timeout mean after partial foreign execution?** | Pretend to roll everything back; wait without bound; or run bounded recovery with explicit compensation and residual claims. | **Bounded recovery.** Require prefunded compensation or a demonstrated refund path for routes marketed as recoverable. Return `Compensated` or `ClosedWithClaims` when original goals were not achieved. |
| **Should developers see a universal chain action or venue-specific types?** | One generic `{chain,to,data,value}` action; separate unrelated SDKs; or shared orchestration records with typed, pinned financial primitives. | **Shared records plus typed primitives.** Keep common authority, budgeting, lifecycle and evidence types. Let adapters own native serialization, permissions, resource units, replay rules and result extraction. |

The remaining uncertainty is empirical rather than a missing API field: none of the inspected sources proves that the proposed adapters match deployed behavior, that the chosen thresholds represent independent operators, or that the new pending/import relations fit admitted resource bounds. Those are release gates. The SDK should return `Unavailable` until they are satisfied, while exposing the exact missing adapter, policy or benchmark digest.
