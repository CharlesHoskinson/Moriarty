# astra-2-10: corrected ECIP verifier count from the actual loop (supersedes astra-2-7 counts)

## Question

Recount the Garaga ECIP verifier cost from the actual code. Check whether the verifier loops over digits or points, whether the per-point work is one or two divisions, how `ep`/`en` relate to the scalar, and what the witness size is. Drop the 124-row break-even unless it is justified. Cite primary code only. Read-only.

## Answer

- **Correction: the verifier loops over basis points, not digits.** `verify_ecip` (`hydra/garaga/hints/ecip.py:147-212`) builds `epns = [positive_negative_multiplicities(neg_3_base_le(s)) for s in scalars]`, one `(ep, en)` pair per point, then `for i, (P, (ep, en)) in enumerate(zip(Bs, epns))` calls `eval_point_challenge_signed` once per point. Digits are summed inside `positive_negative_multiplicities` (`hydra/garaga/hints/neg_3.py`): `ep = Σ_{d_i=+1} (−3)^i`, `en = Σ_{d_i=−1} (−3)^i`. My earlier "107 divisions per scalar" was wrong: the cost is per point, independent of the digit count.
- **Two divisions per point, not one.** `eval_point_challenge_signed` (`ecip.py`, ~245-249) returns `eval_point_challenge(P, ep) + eval_point_challenge(−P, en)`. Each `eval_point_challenge` computes `multiplicity · (xA0 − xP) / (yP − mA0·xP − bA0)` (`ecip.py`, ~234-243), so there is one division for `P` and one for `−P`, computed even when a multiplicity is 0. The in-circuit version agrees: `ECIPCircuits._accumulate_eval_point_challenge_signed_same_point` (`hydra/garaga/precompiled_circuits/ec.py:~192-216`) computes `den_pos`, `den_neg`, and `eval_pos = sign_ep·ep·div(num, den_pos)`, `eval_neg = sign_en·en·div(num, den_neg)`, so 2 `div` gates plus about 4 `mul` gates and a few `add`/`sub`s per point.
- **Skip rule.** `if ep - en == 0: continue` (`ecip.py`, verifier loop) skips the whole point, so points with net zero multiplicity cost nothing. Otherwise it costs the full two-division term.
- **Function-side work is linear in n.** The divisor-sum `sum_dlog` has four coefficient lists whose lengths come from `n_coeffs_from_n_points(n, batched=False)` (`ecip.py:559-566`): `(1+n, 2+n, 2+n, 5+n)`, total `4n + 10` field elements, and `n_points_from_n_coeffs` inverts this (`ecip.py:550-557`). The verifier evaluates these polynomials at `A0` and `A2` (`ec.py` `_eval_function_challenge_dupl`, `_init_function_challenge_dupl`), about 8 multiply-adds per point (4 polynomials × 2 evaluation points).
- **Witness size is 4n + 10 (+2 for Q), not 765.** The `765` figure from astra-2-4 is withdrawn. It was a bit-size guess (381-bit base field, 382-degree polynomial) that does not match the code, which produces `4n+10` coefficients for `n` basis points.
- **`ep`/`en` are per-point field values, not 255-bit digit lists.** The in-circuit ECIP takes `ep, en, sign_ep, sign_en` as inputs per point. The Python hint `scalar_to_base_neg3_le(u128)` (`neg_3.py`) returns `(|sum_p|, |sum_n|, sign(sum_p), sign(sum_n))`, and its comment says the magnitudes "might be larger" than 128 bits. Relation to the scalar: `scalar = sum_p − sum_n` as integers (from the digit definitions). Whether the circuit enforces that identity, and with what range checks, is **not in the captured code**: the top-level ECIP circuit builder that wires `ep, en` to the scalar is absent from the captured files (only the `ECIPCircuits` class is in `ec.py`). I did not find a constraint, so binding is an open item. Do not treat this as verified.
- **Verifier-side soundness check.** `assert LHS == RHS` (`ecip.py` ~206) is the equation. The sanity check `assert Q == ec_group_class.msm(Bs, scalars)` is marked "Sanity check. Not part of the verification" (~209-210), so the equation must bind `Q` to the scalars. Whether that holds depends on the unlocated binding above.
- **Cairo side.** `src/src/universal_ecip.cairo` only dispatches to `ec_ops::msm_g1` (fake-GLV MSM), not to an ECIP verifier. `src/src/ec/ec_ops.cairo` contains MSM code and `hades_permutation` helpers, no ECIP. `src/contracts/universal_ecip/src/lib.cairo` is 46 bytes. The autogenerated Cairo for `ECIPCircuits` is not in the captured tree (`raw/garaga-tree.txt`), so the on-chain ECIP verifier was **not located**. Its absence in this capture is not evidence it does not exist.
- **Hash-to-curve and A0.** As in astra-2-7: `derive_ec_point_from_X` (`ecip.py:38-102`) uses Poseidon252 try-and-increment, and the Python verify samples `A0 = gen_random_point()` when none is given (`ecip.py:177-178`). Fiat-Shamir binding is not in the captured code.
- **Cost per point, derived.** Per basis point: 2 field divisions (`div`) plus about 4 multiplications, plus about 8 multiply-adds for the polynomial evaluations, so about 2 divisions and 12 multiplications. This is independent of the scalar bit-length.
- **Break-even, justified.** Stock per full-width term is at most `39,935 / 3 ≈ 13.3k` rows (`msm_3` fixture, `cost-model.json`; setup-inclusive, so an upper bound on the marginal term cost). The ECIP per-point cost is `2D + 12M` rows, where `D` and `M` are the foreign-field division and multiplication row costs for BLS `Fp`. Break-even: `2D + 12M < ~13.3k`. For a 75% reduction (`≤ 3.3k` per point): `2D + 12M ≤ 3.3k`, so `D` and `M` must each be roughly ≤ 240 rows if equal. The stock foreign ECC `add` (342 rows, `cost-model.json`) contains one slope division and a few multiplications, which suggests `D`, `M` of order tens to low hundreds of rows, but no BLS `Fp` mul or div fixture exists, so this is unmeasured.

## Corrections to earlier reports

- **astra-2-7 is withdrawn in these parts:** the "~107 divisions per full-width scalar" count (wrong: 2 per point), the "~124-row break-even per division" (replaced by the per-point formula above), and "one division per nonzero digit". Its Fiat-Shamir and hash-to-curve findings still stand.
- **astra-2-4 remains withdrawn** for the 765-element witness count (now `4n+10`) and the 7-mult claim (Bulletproofs-only).

## Caveats

- **Binding of `ep`/`en` to the scalar is unverified.** The identity `scalar = sum_p − sum_n` follows from the definitions, but the captured code does not show a constraint that enforces it, nor range checks on the magnitudes. This could dominate the cost if it requires per-digit or per-bit work. It is the first thing to check in the top-level ECIP circuit builder, which is not in the capture.
- **`validate_degrees` was not located** in captured files (`ecip.py` calls it at line 167 but does not define it). It is a degree-bound check the circuit must enforce.
- **Fiat-Shamir binding in Cairo** is not located; Python verify uses random `A0` by default.
- **`D` and `M` (BLS `Fp` foreign division and multiplication row costs)** are not in any captured fixture. The 240/950 thresholds assume equal costs.
- Nothing was built or run. The 2-division count comes from reading the code, not from compiling the circuit; the compiled gate count may differ after optimisation.
