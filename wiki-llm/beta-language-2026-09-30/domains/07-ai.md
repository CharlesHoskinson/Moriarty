# AI coding integrations for Moriarty

**Recommendation AI-R01:** deliver a portable language reference, checked examples, a narrow authoring skill and machine-readable local analysis before building a provider-specific AI extension. Add a bounded local stdio MCP adapter around the same analysis service after its CLI contract works. An assistant supplies a source proposal; the language checker and eventual kernel enforce the accepted relation. This memo proposes integration design. It establishes no model training, IDE activation, MCP interoperability result, certified checker or financial acceptance.

## What assistants need to author the language

**Recommendation AI-R02:** publish one exact, versioned authoring contract. It should identify `.mori`, the source profile, lexical and size bounds, grammar, reserved words, names and financial types, operation signatures, desugaring rules, first-failure order and diagnostic codes. Generate small reference sections and completion metadata from an explicit syntax registry. The registry's authority must be defined before generation; it does not become an independent financial oracle.

Provide complete accepted transfer and repayment source files, their expected Core image, local outcome and source-to-Core origins. Beside each positive example, include a minimal invalid neighbor with the reason it fails. Keep the eight-family mockups required by the user, with construct-level `local`, `specified` and `open` labels. A highlightable example is not automatically an accepted executable program. Assistants should read the exact profile reference and relevant examples rather than interpolate a familiar host language's coercion or runtime rules.

**Repository observation:** the [Source/6 adapter](../../../experiments/moriarty-language/src/successor/mil4-s0-source-v6.ts) accepts source text and returns `SourceRejected`, `CoreRejected` or `PreparedUnqualified`. Successful preparation explicitly lists four unverified bindings: agreement ID, selected program, asset scale and authenticated predecessor. Its [contract](../../../experiments/moriarty-language/spec/successor/financial-agreement-source-v6.md) states that labels and caller Booleans do not establish signature/authentication validity or ledger admission. These are the current language boundary, not a provider integration result.

Complete examples are in the [Source/6 tests](../../../experiments/moriarty-language/tests/mil4-s0-source-v6.test.mjs), whose generators retain the fixed declaration order and full effect vectors.

## One analysis service and structured CLI

**Recommendation AI-R05:** expose `check`, `expand` and `preview` through one service used by CLI, LSP and MCP. Text is the public parsing boundary. An assistant cannot submit an arbitrary AST with claimed types or authenticated properties. Expansion uses strict lowering; recovered editor trees with missing nodes cannot generate an accepted Core term. Completion and hover query the same profile registry, symbols and types; an AI suggestion appears as ordinary editable text and receives the same checker diagnostics.

CLI JSON should contain a schema version, exact language profile, tool version, source digest, request/document identity, status and structured diagnostics. Each diagnostic needs a stable code, phase/judgment, severity, safe message and exact UTF-8 byte range with related origins. Preserve the first failing judgment; any additional advisory diagnostics must not replace the authoritative failure. Source rejection has no published effects. JSON serialization must use decimal strings for large financial integers and closed tagged result forms.

Preview must return a typed local result, complete derived candidate effects, remaining duties where supported, and an explicit premise/qualification record. It should report source checking, local preparation, authentication, proof and ledger commitment independently. A generic `verified: true` conflates those predicates. In the current S0 route, `PreparedUnqualified` stays visible with unverified bindings; provider confidence or successful JSON parsing cannot upgrade it. Unknown profiles and unsupported operations reject with named errors, even if a model knows an attractive syntax for them.

**Recommendation AI-R06:** log compact request identity, profile, duration and diagnostic code by default. Exclude source excerpts, absolute local paths, secrets, raw exceptions and private evidence. Bound error messages and escape terminal/control characters. Source commitments aid exact replay but are not disclosure authorization, signature verification or proof. Detailed debug records remain local and opt-in.

## Bounded read-only MCP

**Discovery-only source fact:** official MCP SDK excerpts expose tool names, JSON input/output schemas and annotations including `readOnlyHint`. The excerpt supports the shape of an adapter, not protocol compliance or enforcement by a host. [MCP tool metadata](https://ts.sdk.modelcontextprotocol.io/v2/api/%40modelcontextprotocol/server/server/mcp.html).

**Recommendation AI-R07:** implement three local tools: `moriarty_check`, `moriarty_expand` and `moriarty_preview`. Each takes an explicitly selected profile and a bounded source string. An optional document ID is a display/correlation label, not a filesystem path. Preview may take a closed scenario object only when its fields and source of authority are specified. A supplied scenario remains untrusted test input. No tool signs, deploys, sends transactions, executes arbitrary shell commands, loads network modules or contacts a model.

Use strict object schemas with required fields, no unknown properties and byte/token/depth/work ceilings. Validate actual UTF-8 byte length after Unicode checking; schema string length alone is insufficient. Bound result bytes and concurrent requests, preserve request IDs and suppress results for stale editor versions. Return typed analysis in `structuredContent` where the pinned protocol/client supports it, with matching concise text for compatibility. Pin and inspect the selected SDK/protocol before implementation; the discovered v2 API is not a selected dependency.

Prefer in-memory source checking in the first server. If a later tool reads files, select workspace roots at server startup, constrain canonical real paths within those roots, reject traversal and symlink escapes, limit extensions and bytes, and bind the inspected bytes in the result. Resolve/read consistency requires care against filesystem races; a prefix string comparison is not confinement. Do not expose a general `read_file`, recursive search or arbitrary tool dispatcher. Protocol roots and read-only hints describe intent; server-side access and effect restrictions enforce the boundary.

The first package should be a local stdio server with no network listener, sampling, remote instructions, credentials, wallet imports or telemetry. Protocol output uses stdout; diagnostics use redacted stderr. Read-only is still a privacy decision because source and responses enter the assistant's context. An installation template must state that an external provider may receive those selected bytes under its own settings; local execution does not prove zero egress by the host. This research authorizes public documentation acquisition only, not private-program submission to hosted assistants.

## Repair loop and acceptance evidence

**Recommendation AI-R08:** the authoring loop selects a source/profile, checks exact bytes, obtains diagnostics, proposes a minimal edit and checks the entire changed document plus its admitted dependencies. Recheck financial constraints and full lowering after every edit. Invalidate prior source commitments, cached checker results and derived artifacts whenever covered bytes change; verify source identity again before displaying or using a result. An assistant's explanation is not an acceptance receipt. Formatting requires rechecking and must state whether exact-source commitments change.

Treat source comments, imported documentation and tool messages as data. They cannot instruct the host to disable checks or authorize broader access. A repair that alters effects, recipients, caps, duties, refinement conditions or policy cannot weaken signed bounds. Preserve finite-work limits and fail with no financial effects. A valid proposal still needs the applicable signature, evidence, proof and ledger checks in the kernel; the authoring adapter has no alternate path around them.

**Specified-only implementation sequence and tests:** first freeze the reference/corpus after the five requested PL reviews; implement shared analysis and CLI JSON; then add neutral packs and inert adapters. Finally add MCP and test a real client spawning the packed local server from a clean directory. Exercise initialization/version negotiation, initialized notification, `tools/list`, schemas, each `tools/call`, malformed/unknown arguments, rejected source, expanded Core, unqualified preview, resource limits, clean shutdown and stdout purity. Compare complete CLI and MCP results for the same exact source, not only success flags.

Include adversarial cap weakening, omitted fees, creditor substitution, fabricated evidence flags, stale document versions and unsupported family operations. Assert zero wallet/network/shell effects and unchanged workspace files through observable process/file/transport boundaries. If bounded file access is added, demonstrate traversal, symlink and race rejection. A real stdio client result establishes interoperability for the pinned server/client/protocol combination; it does not establish Copilot, Claude, Codex or Cursor IDE activation. Each claimed provider integration needs its own observed discovery and invocation with exact versions and selected-source privacy settings.

**Open questions for review:** which beta status vocabulary is shared with editors; whether preview scenarios remain in memory; precise JSON schema/protocol versions; source-byte versus canonical semantic commitments; mandatory dependency rechecking; and whether a dedicated preview panel earns its implementation cost. Unperformed client experiments remain specified only. The recommended initial capability is a developer checking and explaining one supported `.mori` proposal with consistent diagnostics across interfaces, while all financial acceptance predicates retain their existing scope.
