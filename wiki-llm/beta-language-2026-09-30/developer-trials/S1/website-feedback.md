# Website feedback: Moriarty beta tutorial site (from seat S1's first run)

**Hosting:** a static site in a GitHub repo (GitHub Pages). Suggested layout: `docs/` Markdown built with mdBook or Docusaurus/MkDocs; every code block lives as a real file under `examples/` and is run by CI (`mori check`, `mori test`) so the page output cannot drift. Pin the beta version in the page header.

## Landing promise
"Write a payment as explicit, exactly-quantified intent, and see what Core would do with it locally — without signing, sending or proving anything." Put the PreparedUnqualified caveat in the first screen, not the last.

## Navigation / page order
1. Landing + status banner (local only)
2. Prerequisites and install (Node 24+, `npm i @moriarty-lang/beta`, run `./node_modules/.bin/mori` or `npx mori`; say so, because the README's `node dist/cli.js` steps only apply to a source checkout)
3. First five minutes: `init`, `check`, `simulate`, read the result
4. First transfer with fee (walk through the merchant invoice)
5. First repayment (the funded repay path; I did not test it, so the page author must)
6. Model: assets, scale, identities, units
7. Source intent vs untrusted scenario
8. First rejection
9. Bounded project tests
10. Editor and AI setup (LSP, MCP, AGENTS.md)
11. Support matrix
12. What is not proven: authentication, proof, ledger
13. Reference: CLI, diagnostics codes, scenario schema, test schema, API
14. Next steps (SpecifiedOnly families)

## Content that must be stated (missing in shipped docs)
- Scenario and expectation amounts are **atoms**: `125.375 EURC` at scale 3 is `"125375"`. Include a conversion table.
- Source names (`Customer`, `EURC`) versus claimed ids (`Customer7`, `EuroCoinCanonical`); scenario `asset`/`domain` use ids.
- Full scenario schema with every required field; the test-file schema, including the `expect: {status, code}` form for rejections.
- The replay key appears as `inv-2026-0001` in the submitted view and `["Midnight","Customer7","inv-2026-0001"]` in candidate effects.
- Why Source/6 says `TransferLiteralFee`.
- Rejection code table: `S0_AUTH_SCOPE` (allowance < gross), `S0_INTENT_SCOPE` (cap too low / outside valid rounds), plus BETA_* authoring codes.
- Byte-span diagnostics, and how to convert offsets to line/column.

## Example output to show (from S1 run)
Good run: `PreparedUnqualified`; effects Debit Customer7 126625, Credit Merchant42 125375, Credit PlatformFees 1250, UseAllowance 126625, UseReplay, AdvanceHead head-0→head-1; post balances 373375 / 125375 / 1250; allowance remaining 73375.
Rejection: allowance 100000 → `CoreRejected`, `S0_AUTH_SCOPE`, `publishedPost: null`, `publishedEffects: null`, exit 1.
Authoring error: `BETA_ASSET_MISMATCH` "Addition/subtraction require identical numeric types and nominal assets".
Specified-only: `check` exit 0 but `simulate` exit 1 `BETA_PROFILE_UNSUPPORTED`.

## Source intent versus untrusted fixture
Two side-by-side panels: what the signed intent fixes (caps, recipient, fee, validity) and what the scenario merely stipulates (balances, allowance, head). State that a scenario cannot override source and that unknown/duplicate keys are rejected (show BETA_SCENARIO_SCHEMA, BETA_JSON_DUPLICATE).

## Bounded project tests
Show `mori.tests.json` with one accept and one reject, run `mori test .`, and show a deliberate failure (wrong code) so readers see failure. Explain that `test` runs only the cases listed in the file, so keep invalid `.mori` files in a separate folder and reference them by path.

## Editor / AI setup
Split "tested" from "documented". I used MCP only (initialize → initialized → tools/list → tools/call with `source`, `action`, `scenario` strings). Give a 20-line client snippet. LSP/VS Code/Neovim: describe only what the page author has verified.

## Support matrix
Table: LocalS0 (transfer, funded repay) vs SpecifiedOnly (AMM, lending, stablecoin, option, oracle, governance, bridge, staking) with check / inspect / expand / simulate columns.

## Limits
A dedicated page, linked from every page footer: no signature, provider authentication, proof, or ledger commit; four required premises and four unverified bindings; passing tests and matching hashes close none. Note that `fmt` changes source bytes and sourceHash.

## Omit from getting started
The eight SpecifiedOnly examples, the wiki full-language grammar, VS Code packaging, Neovim, API imports, the byte-span map, `min`/`max`. Link them from the reference.

## Tutorial acceptance checklist
- [ ] A fresh Node 24 machine reaches a PreparedUnqualified result using only the installed package, within five minutes.
- [ ] Every command and output on the pages is regenerated by CI.
- [ ] Decimal-to-atom conversion is shown before the first scenario.
- [ ] The first rejection is reproduced and its code explained.
- [ ] The PreparedUnqualified caveat is on the landing page and the first-result page.
- [ ] A reader can write a reject test without guessing the schema.
- [ ] Tested vs untested tools are labeled.
- [ ] No page implies the tool signs, proves or settles.
