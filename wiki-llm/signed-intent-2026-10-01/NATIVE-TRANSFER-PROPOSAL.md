## Delivered predicate

`TransferCircuit` is a nonrecursive PLONK relation over 28 explicitly ordered numerical public fields (`PUBLIC_FIELDS`, version `moriarty-transfer-numerical/1`). It proves the following numerical claims for three distinct account roles; it does not prove the role identities:

- Every public quantity and eight private slack/total values has an actual 128-bit decomposition: sixteen high-to-low bytes, eight boolean bits per byte, zero initial accumulator, base-256 recurrence, final equality to the numeric cell. Thus modular negative values and values >=2^128 cannot satisfy the range relation.
- Amount, fee, gross, gross cap, fee cap and net floor are nonnegative signed127 values; amount is positive using a range-constrained amount-minus-one witness.
- Gross=amount+fee, sender pre=sender post+gross, recipient post=recipient pre+amount, fee recipient post=fee recipient pre+fee. All operands are bounded; integer overflow/underflow cannot be concealed by modular field arithmetic.
- Gross<=gross cap, fee<=fee cap, amount>=net floor, not-before<=round<=not-after, each through a bounded difference and an equality, rather than a host acceptance flag.
- Work remaining decrements by one and spent increments by one. Allowance remaining decrements by gross and spent increments by gross. Separate bounded total witnesses enforce work and allowance totals <=2^128-1; conserved post totals follow from the exact paired deltas.
- Ordered numerical effect fields equal debit gross, recipient credit amount, fee credit fee and allowance gross. The fixture adapter requires exactly the Core5 effect ordering: fee case has six effects; zero-fee case has five and omits a fee-credit line. Its numerical fee effect slot is zero and fee balance unchanged. Work updates are state changes, not invented Core5 effects.

`fixture_public_values` consumes frozen `experiments/midnight-crypto/fixtures/moriarty.json` fee/zero-fee rows from the actual beta -> Source6 -> Core5 export. It checks Core5 Transfer type, exact distinct account/order layout, decimal encoding, allowance and effect order, then projects expected complete numerical pre/post/effects into public instances. This is an **offchain projection test**, not an in-circuit source/compiler hash or semantic correspondence proof. Public instance equality binds these numbers to the selected local proof only. No source/program/policy/account/token/head/nonce/registry digest is computed in this circuit. It has no host `success`/`accepted` input.

The numerical relation does not cover owner signatures, source account ownership, authenticated roots, replay consumption, head advancement, duty/repayment semantics, asset identity, ledger transfer or Preview acceptance. All those scopes remain open. Do not relabel this precursor as a complete signed financial proof.

## Authority and Preview continuation decision

The historical normative-looking docs at `raw/midnight-docs-2026-09-07/markdown/compact/standard-library/exports.md` expose `secp256k1EcdsaVerify(msgHash,sig,pk)` but warn that **msgHash is not constrained to a message**. It cannot authenticate production signed bytes without a circuit-computed compatible message digest.

Actual installed financial compiler0.31.1 (language0.23/runtime0.16) at `/home/charl/.compact/versions/0.31.1/x86_64-unknown-linux-musl/compactc.bin` SHA256 `3054ffa89d7a4dfe24afd31c27ef37e87a95757de0fc24485f335635e26dce57` rejects a minimal `--skip-zk` call with **unbound identifier secp256k1EcdsaVerify**. A typed variant rejects `Secp256k1Point`. External source/probe/error receipts are `G3-ecdsa-{probe,symbol-probe}.compact/.txt`; no proof keys were generated. Therefore the retained docs do not establish this installed builtin. The separate local compiler source checkout `/home/charl/midnight/minokawa-compact` HEAD `c47230cc8c3e743634166d9b84698ac2b238c418`, file `compiler/standard-library.compact` SHA256 `166487c61232e4058f0a5cb1a2a154d5b926a574ba5bc24f5def905c2a938e52`, also has no ECDSA/SHA256/keccak symbols. It is auxiliary local source evidence, **not claimed to be the installed compiler's source pin**. Source mismatch or historic docs for a newer library is an open version contradiction; the actual installed compile refusal is decisive for this specific route today.

Recommendation: continue the existing financial Compact/Preview consumer family, but first resolve a specific deployment-compatible authentication mechanism and source-bound hashing route. Options requiring source/resource review are a supported compiler/gadget version with constrained exact SHA256/signData framing, or native transaction owner authorization with a proven binding from source identity to input owner and selected signed action. Existing native BIP340 input signatures sign ledger `Intent::data_to_sign`, not arbitrary signData frames; offchain Rust ECDSA/BIP340 verification is not a replacement. PersistentHash of a differently serialized typed object does not equal the existing SHA256 signed-byte digest by naming convention.

The existing loan/swap capability hashes and payout addresses do not constitute an owner-key registry. Implement contract-resident registry/key lifecycle, authenticated state origin, atomic head/replay/work/allowance consumption and actual native effect execution together. Preserve the guaranteed/fallible section boundary: fees may survive a failed financial section. Extend the source-derived generator, real `run-local.mjs`/`integrate-preview.mjs` consumer, proven asset manifests and full comparator together. Reusing an existing deployment/wallet requires explicit actual contract address/token colors and retained identity; new deployment-derived colors cannot be presented as preserved existing assets. Real Preview work still needs exact contract/runtime/resource/debit/freshness gates and independent finalized evidence/result audits. No helper flags close these obligations.
