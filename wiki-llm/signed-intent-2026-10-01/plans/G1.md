Account identities are domain-scoped IDs, not cryptographic keys. From/payer must equal signer. For transfer all signer/recipient/feeRecipient IDs must differ, including a zero fee. Repayment creditor is not known from owner intent and remains a bound authenticated obligation property at execution; never copy an unauthenticated scenario creditor into a purported owner authorization. Domain identity applies to every account and asset; all resolved beta entity domains must exactly match it. Do not invent real chain addresses for beta symbolic IDs. Public key possession plus a signer string is not account control.

Minimal route supports only these already supported success-only actions; observations/delegation/recovery/partial outcomes cannot silently enter v1. Product extensibility remains a future separately versioned relation. Asset symbol is display-only and must never replace signed ID/representation/scale.

## Actual hashes without circularity

`sourceSha256` is lowercase SHA256 of exact UTF-8 authoring `.mori` bytes, including whitespace/BOM/newlines, without normalization. Validate source as Unicode scalar text before encoding. Hash is computed by the producer and recomputed by verifier from supplied source bytes; an advertised hash never counts as provenance. Preserve `intent.advertisedSourceHash` and `advertisedPolicyDigest` exactly for Core compatibility, display them as unverified application claims. Do not overwrite them with real hashes or infer certification from their spelling.

`programSha256` is SHA256 of `moriarty-owner-program/1\0 || U32BE(len(P)) || P`, where P is canonical JSON of the following exact scenario-independent projection extracted from actual analyzed beta + Source6Ast: `{authoringProfile,core,sourceProfile,agreementId,actionName,selectedActionId,domain,asset,intent}` using the same values/schema as the signed statement. This is an actual versioned owner-program projection hash, NOT executable/ZKIR artifact hash or compiler correspondence. It includes opaque application claims as source semantics, excludes signature metadata, sourceSha256/programSha256, signedDigest, snapshot, authenticated balance/obligation cells, allowance/replay/work counters, submitted effects/action/postHead, scenarioHash and origins. The actual source hash retains any authoring text not present in the projection. Changing scenario/candidate alone leaves these signed bytes unchanged. If naming this programSha256 risks executable-artifact ambiguity, prefer `ownerProgramSha256` throughout before freeze. Do not later reinterpret the same field as a ZKIR digest.

Source6 generated text is not the original beta source. Verify exact owner projection equality against newly analyzed beta and lowered Source6 from the execution consumer, then separately inspect the candidate through unchanged Core. Source-only input must use a separate authoring profile and real Source6 identity design, not impersonate beta/1. `signedDigest` is absent from signed payload; compute frame SHA256 as a receipt field after framing, or populate an adapter-side optional Core signedDigest only after successful verification if needed. No signed hash includes itself.

## Validation and byte format

All JSON numbers reject, including scale/version numbers: integer fields use canonical ASCII decimal `0|[1-9][0-9]*`; no signs, exponent, leading zero, whitespace. U128 max 2^128-1 (39 digits); money max 2^127-1 (39 digits); scale 0..18 as enforced in beta frontend.ts:309; never widen silently. Use checked conversion and checked arithmetic. Amount >0; validity from<=to; transfer amount+fee checked within S128, gross<=grossCap, fee<=feeCap, amount>=netFloor. Repay amount<=grossCap; feeCap and netFloor must both equal zero, matching Core5:280. Repayment debt discharge is not a token net receipt. State rounds/overpayment/allowance/credit overflow remain Core checks.

ID is ASCII `[A-Za-z][A-Za-z0-9_]{0,63}` to preserve actual beta→Source6 representability. TEXT is nonempty Unicode scalar text, <=1024 UTF-8 bytes, no U+0000..U+001F or U+007F. No Unicode normalization; byte-distinct NFC/NFD strings remain distinct. Reject lone surrogates through Rust parser and explicit TS scalarText. Restrict public keys and hashes to exact lowercase ASCII hex, no prefix; validate curve key by native verifier, not length alone. Signature scheme fixes key width. Signature bytes are envelope fields, not signed payload.

Reuse codec::parse for decoded duplicate-key rejection (including escaped aliases), numbers, trailing input, max input 65536 bytes, depth<=32, nodes<=4096. Reject duplicate identities and unknown fields before canonicalization. Complete verify envelope also <=65536 UTF-8 bytes; derive canonical payload <=65536 and program projection <=65536, check U32 conversion explicitly. Do not parse into generic JS object first: that erases duplicate evidence.

Canonical payload: compact JSON, all fixed closed object keys sorted by UTF-8 byte lexicographic order, arrays retain order; all keys are ASCII. Strings emit direct Unicode scalar UTF-8, quote/backslash escaped, control characters would be schema-invalid. No `/` escaping; serde_json escaping is reference. JS recursively sorted objects can reorder numeric keys; this schema contains no numeric object keys, nevertheless vectors must confirm serializer equivalence. Use a dedicated canonical serializer if any transport profile ever allows arbitrary keys.

Signed bytes: ASCII `moriarty-signed-intent/1` plus NUL, U32BE canonical payload UTF-8 byte length, canonical payload. Framing raw signs these bytes; midnight-sign-data signs ASCII `midnight_signed_message:<frame byte length>:` plus exact complete frame. Mode is itself in signed payload: never retry alternate modes on failure. Do not manually hash before native verify; official APIs define their message hashing. Experimental signatures/domain must fail production verification.

## Rust interfaces / transport

`parse_intent(text: &str) -> Result<SignedIntentV1, IntentError>`; `canonical_intent_message(&SignedIntentV1) -> Result<Vec<u8>, IntentError>`; `owner_program_message(&SignedIntentV1) -> Result<Vec<u8>, IntentError>`; `verify_intent_json(text:&str) -> Result<SignatureReport,IntentError>`. Native Rust cannot verify beta compiler correspondence; source/profile comparison remains a caller obligation. Do not manufacture a `FullyAuthorized` Rust type from a signature alone.

Closed verify envelope `{statement: CLOSED_V1, signatureHex: HEX64}`; scheme/key/framing are solely from statement. Canonicalizer validates the exact schema, not arbitrary JSON. CLI `intent-frame`, `intent-verify` remain separate from experimental `frame`, `verify`. Output `signatureValid`, `profile`, frame digest and explicit `accountAuthorized:null`, `sourceMatched:null`, `transitionValid:null`, `ledgerAccepted:false`. Invalid signature returns exit1, malformed/schema/native-key encoding error exit2. Avoid echoing unbounded request/source/signatures.

Consumer operation `buildSignedIntent(sourceText, actionName, signingConfig)` parses/resolves source and derives all values. `verifySignedIntent(envelope, sourceText, actionName, authorityResolver)` regenerates expected statement, compares complete canonical bytes and actual hashes, then calls pinned Rust native verify. AuthorityResolver must separately verify (domain/network/account,keyRef,scheme,publicKey) at authenticated current authority state with revocation checks. A local explicit map may yield `local-authority-stipulation`, never ledger authority. Then unchanged beta expansion/Source6 lowering/Core5 preparation runs on the supplied scenario; it remains PreparedUnqualified until state/atomic-ledger/proof premises exist.

## Signing display / vectors / risks

Show exact agreement/action, chain/network/domain; asset ID/representation/scale and atoms plus exact decimal scale rendering; signer/from/payer, recipient and fee recipient or obligation ID; amount, fee, gross cap, fee cap, minimum net; nonce/preHead and inclusive round bounds; success-only/empty policies; scheme/keyRef/public-key fingerprint and framing; actual source hash and owner-program projection hash. Label symbolic accounts and advertised claims. Human friendly labels must not substitute for signed fields. Display/render equality against canonical payload is a testable obligation.

Frozen interop vectors: one fee transfer, zero-fee transfer, repayment; expected canonical JSON UTF-8 hex, frame hex, owner projection hex/hash and actual source hash; official generated ephemeral Schnorr and ECDSA signatures for both framing modes. Match Rust and TS independently. Include byte length of astral Unicode text, BMP/NFC/NFD distinctions, quote/backslash, reordered input keys and whitespace stability; changing source whitespace changes sourceHash despite unchanged owner program; changing scenario/post/effects leaves frame identical. Negative matrix: every signed leaf tamper, profile/selected action/scale/domain/network/representation/keyRef/key/scheme/framing swaps, wrong key, experiment-domain signature, duplicate/escaped duplicate, unknown nested fields, surrogate/control/oversize, numeric aliases/range edges, overflow amount+fee, forbidden policy, payer/signer mismatch, transfer aliases, advertised hash discrepancy, actual source mismatch, source action mismatch, alternate candidate within same owner projection.

Open risks: implementation placement remains experiment crate, so production-versioned schema means stable protocol version, not production-qualified ledger acceptance. Current publicKey authorization and source correspondence must be explicit consumer checks; signature result alone does not close either premise. Actual ZKIR executable/circuit/verifier binding is unfinished and cannot be supplied as opaque application hashes. Local fee covers requested transfer fee; ledger guaranteed-phase fees/failure effects are not supported by success-only Core5 and require future signed phase policy. Replay/current revocation/finality remain execution predicates. Reuse official crypto and bounded parser, preserve experimental API/tests and unchanged Core5/Source6 behavior.
