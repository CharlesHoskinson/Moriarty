## 3. The developer's mental model (what the UI must teach)

Five items, always labeled the same way in output and docs:

| Term | What it is | What it is not |
| --- | --- | --- |
| account ID (`signer`, `Owner`) | symbolic ID inside a domain | an address, a key or proof of control |
| keyRef (`key1`) | symbolic label copied from source `key:` | a key; nothing resolves it |
| public key (`--public-key`) | exact key bytes the builder supplies, checked only as a valid curve point | bound to the account or the keyRef by anything here |
| scheme + framing | how the signature is checked (`schnorr_bip340`/`ecdsa_secp256k1_sha256`, `raw`/`midnight-sign-data`) | optional or retried; framing is inside the signed statement |
| signature | the key holder signed those exact frame bytes | owner authority, freshness, acceptance, settlement |

One sentence repeated in every success output and doc page: **A valid signature shows that someone holding this key signed these exact owner terms. It does not show that the key controls the account, that the terms are current or unused, or that anything settled.**

## 4. Command experience

Flags follow the root draft. I add only output design. Both commands: no secret flags, no signing, the verifier binary is explicit configuration.

```text
mori intent FILE --action NAME --scenario FILE --scheme SCHEME --public-key HEX \
    --framing raw|midnight-sign-data --crypto-binary /ABS/BINARY [--json]
mori verify-intent FILE --action NAME --scenario FILE --signature FILE \
    --crypto-binary /ABS/BINARY [--json]
```

**[rec] Default output is a readable review screen; `--json` is the machine form (matches `check`).** Both forms come from the same result object and have identical exit codes. The `intent` review screen prints digests and sizes; exact signable bytes are in `--json` (frame hex can reach 32 KiB, too long to read).

Rules for this screen:
1. One line per statement leaf class; every committed leaf appears. A test enumerates statement leaves and fails when any leaf value is absent from `display.lines` (display-equals-statement obligation, G1's testable display rule).
2. Atoms always appear first and exactly as signed; the scaled decimal is derived, marked "display only", and never appears without scale and asset ID on the same line.
3. `symbol` is shown as a label (`symbol "USD" (label only)`), or `none` for null. It is committed but never identity and never a conversion permission (consistent with GETTING-STARTED).
4. The "claimed" vs "computed" split is mandatory. GETTING-STARTED already warns that `source_hash` is a claim; the screen must not render both under the label "source hash".
5. The display is built from the statement **Rust returned**, after the TS side has compared it to the source-derived statement. A display built from the TS draft would let a TS/Rust divergence show one thing and sign another.

### 4.3 Exit codes

[rec] One rule for both commands: **0** = the requested local operation completed with its documented caveats; **1** = a judgment against the artifact or candidate (mismatch, invalid signature, Core rejection, malformed artifact, formation/authoring error); **2** = no judgment could be made (verifier binary missing, not absolute, timeout, output bound, protocol violation). Exit 2 output must say `signature: NotChecked` and must never print `valid` or `invalid`. This adds exit 2 to a CLI that has only 0/1 today (O1); `GETTING-STARTED.md` "Exit 0 ..." paragraph must state it. Rust's own exit 2 (`IntentRejected`, a malformed artifact) maps to TS status `ArtifactRejected`, exit 1, because the verifier did reach a judgment; only process-level failure maps to 2.

## 5. Result vocabulary (prevent signature-valid ≈ authorized/settled)

Statuses (TS layer, extends G2's list): `OwnerIntentPrepared`, `SignedPreparedUnqualified`, `SignedCoreRejected`, `SignatureRejected`, `StatementMismatch` (new), `ArtifactRejected` (new), `FormationRejected`, `AuthoringRejected`, `Unsupported`, `CryptoUnavailable`.

Rules, each testable:
- No top-level status or `qualification` contains `Valid`, `Verified`, `Authorized`, `Accepted`, `Approved`, `Settled`. (`ledgerAccepted:false` stays as a key, matching Rust's `ledger_accepted:false`.) `qualification` values: `unsigned-owner-intent` and `signature-and-local-stipulation-only`.
- Every verify result carries, in this fixed shape: `sourceMatched` (`true|false|null`), `signature.result` (`ValidForFrame|InvalidForFrame|NotChecked`), `ownerAuthority.status` (`NotChecked` only in this slice, with `reason`), `localPreparation.status` (`PreparedUnqualified|CoreRejected|NotRun`), retained `requiredPremises`/`unverifiedBindings`, `notEstablished` (closed list: `owner-authority`, `key-to-account-binding`, `current-state`, `replay-freshness`, `proof`, `ledger-acceptance`, `settlement`), and `ledgerAccepted:false`.
- `canonical-intent-signature` stays in `requiredPremises` even after `ValidForFrame` (G2's rule), because key-to-account binding is open. The tutorial says why.
- Mismatch precedes signature judgment in reporting: if both fail, show both sections; top-level precedence is `FormationRejected > CryptoUnavailable > ArtifactRejected > StatementMismatch > SignatureRejected > SignedCoreRejected > SignedPreparedUnqualified`. A signature that is valid for a different statement is the most dangerous confusion, so it gets its own name.
- On exit 2 or `NotChecked`, no boolean is ever `false`. Unknown stays `null`/`NotChecked` (root: transport failure is unknown validity).

Diagnostic codes I propose to add to G2's `BETA_CRYPTO_*` set, each with a one-sentence `hint` field from a closed table: `BETA_INTENT_STATEMENT_MISMATCH`, `BETA_INTENT_SOURCE_CHANGED` (only sourceSha256 differs), `BETA_INTENT_SIGNATURE_INVALID`, `BETA_INTENT_ARTIFACT_SCHEMA`, `BETA_INTENT_SCHEME_FRAMING` (unsupported pair), `BETA_INTENT_AMOUNT_FORMAT`. `BETA_CRYPTO_BINARY_UNAVAILABLE` hint: "Build the verifier: `cargo build --release --locked --manifest-path experiments/midnight-crypto/Cargo.toml`, then pass its absolute path with `--crypto-binary`."

## 6. Display safety (escaping, bidi, amounts)

**Dangers [inf from O4, O9]:** (a) bidi override/isolates reorder neighbouring text in a terminal so `"preview‮tset"` can look like a different network; (b) zero-width and variation selectors make two byte-different TEXT values look identical, including `keyRef`, `network`, `representation`, `symbol`, `nonce`, `preHead` and the advertised claims; (c) U+2028/2029/NEL and newlines forge a second "line" in a review screen; (d) ESC sequences can rewrite the screen (blocked by root's control-character rule, but defense in depth is cheap); (e) NFC/NFD and homoglyphs look the same but sign differently; (f) ASCII look-alikes (`l`, `I`, `1`, `O`, `0`) remain even after (a) to (e) are handled.

**Rules (all in `src/intent-display.ts`, pure, no I/O):**
1. `escapeText(s)` returns a double-quoted ASCII-only string. Printable ASCII 0x20..0x7E passes through, except `"` and `\` which are backslash-escaped; every other scalar is `\u{HEX}` (uppercase, no padding beyond needed). This is **escape-by-default**, not a deny-list of "known bidi characters": Unicode format and invisible characters change between versions and a list is incomplete. It matches S1 §6.4 (all non-printable-ASCII escaped) and satisfies the root's requirement to escape control, bidi and line separators.
2. Any `\u{...}` produced adds a warning line `contains non-ASCII text; compare escaped form` and a `warnings` entry. NFC/NFD differences become visible because they escape differently.
3. `asciiJson(value)` is `JSON.stringify` followed by escaping every code unit outside 0x20..0x7E to `\uXXXX`. **Every stdout byte of both new commands, readable and `--json`, must be printable ASCII plus `\n`.** The trial asserts this on every command output. The parsed JSON value is unchanged, so artifacts remain valid for Rust.
4. Hex fields (keys, hashes, signatures) are shown full-length lowercase, never grouped or truncated (copy-paste exactness), with a short fingerprint beside them where a human compares. Truncation (`<8 hex>...`) is only for mismatch hints and always accompanied by the pointer.
5. Amounts: `formatAtoms(atoms, scale)` uses BigInt only and requires the canonical DEC grammar (`0|[1-9][0-9]*`, no sign/space/exponent/separator) or throws `BETA_INTENT_AMOUNT_FORMAT`. Exactly `scale` fractional digits, trailing zeros kept (`10.00` not `10`), left-padded for small values (`5` atoms, scale 2 → `0.05`), scale 0 prints no decimal point, no thousands separators, no locale, no float, no rounding, no symbol-only form. Required vectors: scale 0, 1, 2, atoms < 10^scale, 2^127-1 at scales 0, 2 and 18, `0` at scale 18, leading-zero/`+`/`-`/`1e3` inputs rejected.
6. Round bounds print as plain integers (`rounds 0..10 inclusive`), not formatted as money. Gross cap includes the fee; the line says so in `docs`, not as a derived number in the screen, to avoid a displayed fact that is not a signed field.
7. Display labels are a closed table keyed by statement path. A statement path with no label fails a test, so a later protocol field cannot silently go unshown.

**Residual risk [open]:** the external signer's own UI is outside our control. A wallet that shows only a hex blob gives the user no independent view of the terms; the user relies on this CLI's screen plus comparing `frame sha256` if their signer shows it. The docs state this plainly.

## 7. Programmatic API (DevEx requirements on the root contract)

The root fixes names `prepareOwnerIntent(source, action, scenarioText, signing, crypto)` and `verifyAndPrepare(source, action, scenarioText, signatureText, crypto)` (runner seat owns the implementation). My requirements on their shapes, and what I own:

```ts
// owned by the runner seat; requirements from S3
type Signing = Readonly<{ scheme: 'schnorr_bip340'|'ecdsa_secp256k1_sha256';
                          publicKeyHex: string; framing: 'raw'|'midnight-sign-data' }>;
type OwnerIntentPrepared = Readonly<{
  status: 'OwnerIntentPrepared'; qualification: 'unsigned-owner-intent';
  statement: SignedIntentStatement;                     // as Rust returned it
  frame: { hex: string; sha256: string; byteLength: number };
  signing: { framing: Signing['framing']; messageHex: string; instruction: string };
  display: SigningDisplay;                              // from S3
  unsignedContext: { scenarioSha256: string };          // never part of the display "terms" block
  ledgerAccepted: false }>;
// no property named valid, ok, authorized, accepted, success anywhere in the result types
```

- `framing` is an enum everywhere. Do not expose a boolean `walletPrefix` (G2's draft); root's `framing` already supersedes it.
- A discriminated union on `status`; `verifyAndPrepare` returns the section shape in section 5 for every branch, with `NotChecked` markers rather than omitted fields. Declarations test (extends `distribution.test.mjs` style): a `// @ts-expect-error` on `.valid`, `.ok`, `.authorized` and an exhaustive `switch` over `status` that fails to compile if a status is added without handling.
- Importing the package spawns nothing (G2 rule); `crypto.binaryPath` is the only place a process is chosen.

**Owned by S3 (pure helpers, exported by the runner seat's `index.ts` edit):**

```ts
export type SigningDisplay = Readonly<{ lines: readonly string[]; warnings: readonly string[]; nonAscii: boolean }>;
export function escapeText(value: string): string;                     // section 6 rule 1
export function formatAtoms(atoms: string, scale: number): string;     // rule 5; throws LocalError BETA_INTENT_AMOUNT_FORMAT
export function renderSigningDisplay(statement: SignedIntentStatement): SigningDisplay;
export function renderVerificationDisplay(result: VerificationDisplayInput): readonly string[];
export function asciiJson(value: unknown): string;                     // rule 3
export function assembleSignatureArtifact(statement: SignedIntentStatement, signatureHex: string): string; // optional, see below
```

`assembleSignatureArtifact` returns `{statement, signatureHex}` text through `asciiJson` after checking `^[0-9a-f]{128}$`; it rejects uppercase, `0x`, base64 and a 64-char hash with a message naming the likely mistake ("signature must be 64 bytes as 128 lowercase hex characters; do not pass the hash or base64"). It does not sign and does not normalize. It is optional because the root's artifact is just two fields; the tutorial would otherwise need `jq` or a hand-built JSON snippet. If the root declines the extra export, the tutorial uses a five-line `node` snippet. `SignedIntentStatement` is the runner seat's type; I import it type-only.

## 9. Offline packed CLI developer trial

Goal: a developer outside the checkout, with only a tarball and a copied native binary, runs the entire flow with no network, no cargo and an empty PATH, using ephemeral public fixtures. Test file `packages/moriarty-beta/tests/intent-trial.test.mjs` (new; separate from `distribution.test.mjs` to avoid a merge conflict with the runner seat).

**Preconditions.** `MORI_TRIAL_CRYPTO_BINARY` = absolute path of a locally built release `moriarty-midnight-crypto`. Unset → the test reports **skipped with a named reason**; a skip is not a pass and the acceptance record must show a non-skipped run (rule R8). The fixture source is the data in section 8.2 (public signatures and keys only); no secret or seed field exists anywhere in test inputs.

**Steps and assertions** (all commands: `cwd` = temp dir outside the checkout, `env` = `{PATH:'', HOME: temp}` plus nothing else secret, `shell:false`):
1. `npm pack` the package, then `npm install --prefix TEMP TARBALL --ignore-scripts --no-audit --no-fund --offline`. Assert the tarball lists `SIGNED-INTENT.md` and `examples/signed-intent/*`, and lists **no** binary, `.node`, key, seed or `target/` path.
2. Copy the binary to `TEMP/bin/moriarty-midnight-crypto`, `chmod 0755`, assert SHA-256 equals the original. All later calls use that absolute copy.
3. `mori init TEMP/invoice` and `.../loan --template repay`; assert each source's SHA-256 equals the fixture's `sourceSha256`.
4. `mori intent ... --json` with the fixture public key, scheme and framing. Assert: `statement` deep-equals the shipped artifact's statement; `signing.messageHex` has the expected length and header; `display.lines` contains the exact atoms/scale/chain/network/symbol/claimed-vs-computed lines and the "NOT in this statement" and "decoded bytes" lines; `ledgerAccepted:false`.
5. `mori verify-intent --json` with each shipped artifact. Assert `SignedPreparedUnqualified`, exit 0, `sourceMatched:true`, `signature.result:'ValidForFrame'`, `ownerAuthority.status:'NotChecked'`, `localPreparation.status:'PreparedUnqualified'` and the complete ordered effects/post equal to the independently hand-derived starter expectations already in `starter.ts` (not regenerated), `notEstablished` equals the closed list, `requiredPremises` still contains `canonical-intent-signature`.
6. Frame invariance: change scenario balances and `post_head` → verify still `ValidForFrame` (state is not signed); change the scenario round outside the window → `SignedCoreRejected`, exit 1, `signature.result` still `ValidForFrame`, `publishedEffects:null`.
7. Negative matrix with expected status, exit and first pointer: amount edit in the artifact; one-space source edit (`/statement/sourceSha256`); signature nibble flip; wrong key (other artifact's public key); swapped `signature.framing`; unknown field in the artifact; duplicate key; uppercase signature hex. In each case assert `localPreparation.status:'NotRun'` and no effects.
8. Environment failures: `--crypto-binary` missing path, relative path, non-executable file, → exit 2, `CryptoUnavailable`, `signature.result:'NotChecked'`, hint contains the cargo build line, output contains neither `ValidForFrame` nor `InvalidForFrame`. Tiny executable fixtures for timeout and malformed output are the runner seat's matrix; the trial only checks one (exit-0 child printing "valid") to prove a fake binary cannot create `ValidForFrame`.
9. Display safety: a source whose `network` or `symbol` contains `‮`, `​` and a newline escape. Whatever the schema outcome (rejected or accepted), assert **every stdout byte of every command above is printable ASCII or `\n`**, and when accepted the display contains `\u{202E}` and the warning line.
10. Public API from the installed package with PATH empty: import spawns nothing; `prepareOwnerIntent` then `verifyAndPrepare` against the same copied binary reproduce steps 4-5; declarations compile under `tsc --strict` including the three `@ts-expect-error` lines and the exhaustive status switch.
11. Forbidden-word check: no top-level `status`/`qualification` matches `/Valid|Verified|Authorized|Accepted|Approved|Settled/`, and readable success output contains "Not established".

Offline evidence limits: this proves the flow runs with an empty PATH, no cargo and no checkout reference; it does not prove no network call is possible. If `unshare --net` is available the trial may wrap the commands in it; otherwise record "network isolation unverified". Binary portability is claimed only for the same machine and glibc; no portability claim for other platforms.

## 10. Disagreements and dissent (preserved)

- **D1 TEXT should be printable ASCII (0x20..0x7E) in v1.** G1 and the root allow any Unicode scalar except controls. Every TEXT field (`chain`, `network`, `representation`, `symbol`, `keyRef`, `nonce`, `preHead`, advertised claims) is ASCII in every example and fixture in the repo. An ASCII rule removes bidi, zero-width, NFC/NFD and homoglyph classes at the schema, so display escaping becomes defense in depth rather than the only barrier; a Rust deny list of invisible ranges is incomplete (std has `is_control` for Cc only, not Cf). Cost: the codec's Unicode vectors would move to codec-level tests while the v1 schema tests only ASCII. **My display rules (section 6) hold regardless of the outcome.** Not adopted by root; my vote on the display design does not depend on it.
- **D2 `--scenario` should be optional on `mori intent`.** The owner statement excludes solver state, yet the root draft requires a scenario to produce signing bytes, because the beta bridge lowers Source/6 only from a scenario. That forces a signer to supply unsigned data to get bytes that do not depend on it, and invites reading it as signed. Mitigation if kept: the display's last lines say the scenario is not in the statement, and `scenarioSha256` is kept in `unsignedContext`, never in the terms block. Recommendation for a later iteration: derive the formation check from a minimal conforming internal scenario. Not blocking.
- **D3 Readable default with `--json`.** Root and G2 are silent or JSON-only. A reviewable signing screen is the point of the feature; JSON-only makes the human read a machine blob. Alternative acceptable to me: JSON default with a `--review` flag, provided the display is in the JSON and the tutorial leads with the readable screen.
- **D4 Distinct `StatementMismatch` and `ArtifactRejected` statuses.** G2's list folds statement difference into signature rejection or schema errors. A genuine signature over different terms is the main misread risk and deserves its own name and exit-1 message.
- **D5 `walletPrefix` boolean (G2 text).** The root's `framing` enum already overrides; recorded so the runner seat does not reintroduce a boolean in the API or flags.
- **D6 Exit 2 for "no judgment".** G1/G2 use exit 2 at the Rust level for malformed input. I map Rust `IntentRejected` to TS exit 1 (a judgment) and reserve TS exit 2 for process-level inability to judge. If root prefers exit 2 for malformed artifacts, the status names remain, only the exit table changes.
- **S1 (fixed binary) dissent.** I did not weigh the binary-versus-JSON choice beyond DevEx: JSON gives a reviewable statement and a plain artifact; a fixed binary would remove the reviewable text. If root reverses, section 6 rules and the display table apply to the same field set unchanged; only the artifact schema and the wallet byte instructions change.

## 14. Risks and open questions for the root
