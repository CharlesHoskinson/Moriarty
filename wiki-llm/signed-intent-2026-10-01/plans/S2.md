## 1. What exists today

### Core5 prepare and the Source6 wrapper
- **[obs]** `prepareMil4S0(state, intent, submittedEffects, proposedPostHead, requestedOutcome, localStipulation?)` (`experiments/moriarty-language/src/successor/mil4-s0-core-v5.ts:131`) is pure and non-consuming. It returns `Rejected{judgment,code}` or `PreparedUnqualified{preHead, effects, candidatePost, requiredPremises}`. `requiredPremises` is always `canonical-intent-signature`, `snapshot-to-head`, `head-extension`, `atomic-ledger-compare-and-consume`. Its header says the state, signature and head are not authenticated.
- **[obs]** `localStipulation` (`:211`) only checks that a caller-supplied tuple (intent, state, round, expectedSuccessor, outcome) deep-equals the call arguments. It authenticates nothing and consumes nothing.
- **[obs]** Judgment order is fixed, so the rejection code is order-dependent:
  1. `stage` (shape, S0_STAGE_UNSUPPORTED / S0_STAGE_PREMISE)
  2. `intent` (S0_INTENT_SCOPE: domain/asset equality, validity window against `state.round`, caps, amount, alias)
  3. `effect` (S0_EFFECT_RANGE overdraw/overflow, then S0_EFFECT_MISMATCH vs submitted effects)
  4. `authority` (S0_AUTH_SCOPE: allowance `remaining >= gross`, `workRemaining >= 1`)
  5. `history` (S0_HISTORY_STALE `intent.preHead != state.head`, S0_HISTORY_REPLAY, S0_HISTORY_SUCCESSOR)
  6. `failure` (only TerminalSuccess with no retained effects/duties)
- **[obs]** The stage check is narrow. A transfer state must have exactly 3 ordered balances (signer, recipient, feeRecipient), 1 allowance owned by signer and 0 obligations. A repay state must have exactly 2 balances, 1 obligation and 1 allowance. Any other ledger projection is `S0_STAGE_UNSUPPORTED`. So Core5 prepares one agreement-instance stage state, not an arbitrary account table.
- **[obs]** Replay key is `JSON.stringify([state.domain, signer, nonce])`. The Source6 lowering maps a source `use_replay` nonce to this tuple (`financial-agreement-source-v6-frontend.ts:347`). `consumedReplay` is an unbounded set. Work is a plain decrement of 1. The allowance is consumed by gross (amount+fee), not net.
- **[obs]** `proposedPostHead` is supplied by the caller. Core5 requires only that it is opaque text, differs from `state.head`, and equals `localStipulation.expectedSuccessor` if present. Nothing derives it.
- **[obs]** `prepareSource6S0Unqualified(source)` (`mil4-s0-source-v6.ts:28`) parses and lowers Source6 and calls Core5. It then compares the signed action with the submitted action after the Core `stage` check. The result carries `unverifiedBindings: agreement-id, selected-program, asset-scale, authenticated-predecessor`. It never returns an accepted status.
- **[obs]** Beta bridge (`packages/moriarty-beta/src/bridge.ts`) turns beta text plus a `moriarty-local-scenario/1` into Source6, then calls the wrapper. The scenario carries the whole "authenticated" block (head, predecessor, round, balances, allowance, replay, work, post_head), and Source6 names it `authenticated`. It is stipulated by the caller. `inspect` reports every identity as `authenticated:false` (`index.ts:35`).

### Beta identities (domain/id only)
- **[obs]** Beta `domain` = `{id, chain, network}` (`frontend.ts:305`). `account` = `{domain, id}` only. `asset` = `{domain, id, scale, representation[, symbol]}`. `obligation` = `{domain, id, asset}`. The intent's `key` field is an opaque `keyRef` string. No beta entity holds a public key, scheme, address or wallet reference.
- **[obs]** Core5 sees only the domain `id` (identifier regex) plus the opaque `keyRef`. `chain` and `network` never reach Core. Fixtures use domain `Midnight`, chain `midnight`, network `preview`, accounts `Owner`, `Recipient`, `Fee`, `Payer`, `Creditor`, keyRef `key1`.
- **[inf]** A public key cannot be inferred from a symbolic account ID. Possession of a key that validly signs an intent naming `signer: Owner` proves nothing about control of `Owner`. The existing test `experiments/midnight-crypto/tests/authority.rs` shows this: an attacker key produces a native-valid Schnorr signature over the same message and only the local `LocalBinding` map rejects it.

### Rust ledger surface (official `midnight-ledger` 9f9842eb, local cargo checkout)

- **[obs]** Ledger-native key binding exists for unshielded token ownership: `UserAddress = persistent_hash(schnorr VerifyingKey bytes)` (`coin-structure/src/coin.rs:892`), and `UnshieldedOffer.signatures` sign the `SegIntent`. That path was not run here.
- **[obs]** Pinned `midnight-ledger` depends on `zkir_v2` only (optional, `test-utilities`). A `zkir-v3` directory exists in the checkout but the `ledger` crate does not depend on it at this rev. **[open]** Moriarty targets ZKIRv3; whether this ledger rev accepts v3 contract artifacts is unverified.

## 2. Minimum production authority resolver and context

### What must be authenticated
Tuple `(domainId, chain, network, accountId, keyRef, scheme, publicKey)` plus validity and revocation, as of the evaluation round and the same state version the atomic accept reads.

**[rec]** `AuthorityBinding` (closed, all fields required):
```
{ domain:{id,chain,network}, account, keyRef,
  scheme: 'schnorr_bip340' | 'ecdsa_secp256k1_sha256',
  publicKeyHex,
  validFromRound: U128, validUntilRound: U128,
  revokedFromRound: U128 | null,
  bindingId: TEXT }
```
**[rec]** `AuthorityResolver.resolve(query) -> AuthorityResolution`. `query` = `{domain, account, keyRef, scheme, publicKeyHex, round, stateRef}`. `stateRef` is the head and state digest the caller will use for the atomic accept. Result:
- `Authorized{binding, provenance, registryCommitment}`; `provenance` is `'local-stipulation'` or `'ledger-finalized'` (closed union, a TS brand so a caller can't construct `'ledger-finalized'`).
- `Rejected{code}` with codes `AUTH_NO_BINDING`, `AUTH_KEY_MISMATCH` (any of keyRef/scheme/publicKey differ), `AUTH_DOMAIN_MISMATCH` (domain id, chain or network differ), `AUTH_NOT_YET_VALID`, `AUTH_EXPIRED`, `AUTH_REVOKED`, `AUTH_REGISTRY_UNAVAILABLE`.

Checks the resolver must make, and the consumer must not skip:
1. `domain.chain/network` equals the target ledger (for ledger-native, `LedgerState.network_id`); Core5's domain `id` equals `domain.id`. Without this a signature for `preview` replays on another network.
2. `account` equals the intent's `signer` and, for transfer/repay, `from`/`payer`.
3. `validFromRound <= round <= validUntilRound` and (`revokedFromRound` is null or `round < revokedFromRound`).
4. Binding read at the same state version as the accept. A revocation that commits between prepare and accept must make the accept fail (section 3, rejection R7).
5. Scheme and key width come from the binding and the signed statement, not from the request. A mismatch with G1's statement fields rejects.

**[rec]** Registry source, minimum for a ledger-native route: bindings are committed in the settlement contract's state (or its constructor), and read from a finalized, block-pinned state, with a Merkle/ledger-state proof against a finalized root. `provenance:'ledger-finalized'` is issued only by code that decoded that finalized state (the existing `finalized-financial-state.mjs` already captures block-pinned state for the old kernels, so the pattern exists). **[open]** Who may register or rotate a binding is undecided. Minimum viable: bindings fixed at instance initialization by the deployer-owned capability, no rotation in v1, revocation by a signed revocation transition from the same key or a named revoker key. This needs a design decision before any Preview claim. Alternative: make the account self-certifying (`accountId` includes the key hash, as `UserAddress` does). That changes beta account identity semantics, so it needs an explicit decision and cannot be applied to existing wallet identities.

**[rec]** A local explicit map implementing `AuthorityResolver` is allowed only as `'local-stipulation'`. Its result must flow through to the consumer's output as `qualification:'local-stipulation'` and must never convert to `'ledger-finalized'`. The existing `authority.rs` `LocalBinding` is a precursor; it omits chain, network, account distinct from signer, scheme and `notBefore` on the binding, so it is not the production shape.

## 3. Atomic accept predicate, races and rejections

### Predicate (single atomic section over authoritative state S)
Given: verified owner intent I (signature verified by G1 verifier over the exact canonical bytes; source/owner-program match checked by the consumer), authority resolution A, candidate C from Core5 prepare on a snapshot Σ.

Accept iff all hold, evaluated on S read inside the atomic section:
1. **Snapshot binding.** `digest(S) == digest(Σ)` (full canonical state digest, covering head, round-independent cells, balances, allowances, obligations, replay set, work counters, authority-registry commitment). Head alone is insufficient: Core5 treats head as an opaque predecessor and doesn't prove every other cell is covered by it. **[rec]** Compare both `S.head == I.preHead` and the full digest.
2. **Authority.** A is `Authorized` at `S.round`, for the I's `(domain, chain, network, signer, keyRef, scheme, publicKey)`, and its registry commitment equals S's.
3. **Re-prepare equality.** `prepareMil4S0(S, I.core, C.effects, C.proposedPostHead)` returns `PreparedUnqualified` and its effects and `candidatePost` are canonical-byte-equal to C. This repeats the Core5 checks on S itself (window, caps, balances, allowance, work, head, replay), not on the earlier snapshot.
4. **Head extension.** `successor == deriveHead(S.head, frameDigest, effectsDigest)` for a fixed domain-separated hash. **[rec]** Don't accept a solver-chosen head. G1 excludes the head from the signed statement (only `preHead` is signed), so a deterministic derivation is the only way independent verifiers agree on the next head.
5. **Conservation.** Debits equal credits for the asset (transfer: gross = amount + fee; repay: amount debited = amount credited), no negative balance, `allowance.remaining + allowance.spent` unchanged, `workRemaining + workSpent` unchanged, obligation `principal + accrued == outstanding`, `Settled` iff outstanding 0.
6. **Consumption (single commit).** The commit writes balances, allowance, obligation, replay key, head and work counters in one all-or-nothing step: either S' = `C.candidatePost` or S is unchanged. A failed commit must leave `digest(S)` byte-identical.

Returned status is `LocalCommitted` (local store) or `LedgerCommitted` (only from a ledger-native store with finalized evidence). There is no `Accepted` and no boolean input.

## 4. Reusable consumer

**[rec]** One consumer function, independent of the CLI and the runner:

```
consumeVerifiedOwnerIntent(input: {
  verifiedIntent: VerifiedOwnerIntent,    // branded; only G1's verifier returns it
  preparedCandidate: S0PreparedUnqualified, // from actual Core5 via the Source6 wrapper
  snapshot: AuthenticatedSnapshot,        // branded; only a SnapshotSource returns it
  resolver: AuthorityResolver,
  store: AtomicSettlementStore,
}) -> Promise<ConsumeResult>
```
- `VerifiedOwnerIntent` carries the canonical statement bytes, frame digest, scheme/key from the statement, and G1's `sourceMatched` result. The consumer rejects an intent whose owner-program projection doesn't equal the one derived from the same source that produced `preparedCandidate`.
- `AuthenticatedSnapshot` = `{state:S0State, stateDigest, head, round, registryCommitment, provenance}`. `provenance` is the closed union from section 2. A constructor exists only inside `SnapshotSource` implementations. A test-only `LocalStipulatedSnapshotSource` yields `'local-stipulation'`.
- `AtomicSettlementStore`:
  - `readSnapshot(domain) -> AuthenticatedSnapshot`
  - `compareAndCommit({expect:{stateDigest, head, registryCommitment}, commit:{candidatePost, effects, replayKey, frameDigest, postDigest}}) -> Committed{postDigest} | Conflict{reason}`
- `ConsumeResult` is a closed union: `LocalCommitted | LedgerCommitted | Rejected{layer:'authority'|'atomic'|'core', code}`. `LedgerCommitted` requires a ledger-native store and finalized evidence. Both committed variants carry `qualification` copied from the snapshot provenance. No variant is named `Accepted`.
- No host flags: the consumer accepts no booleans for signature, nonce, freshness or authority. Those come from the verifier, resolver and store objects, never from the caller's data. A test must fail if a boolean field is added to the input.
- No fake authenticated snapshots: the only path from `S0State` plus stipulated scenario to a snapshot is `LocalStipulatedSnapshotSource`, which sets `provenance:'local-stipulation'`. The beta scenario's `authenticated` block remains `stipulated`.

### Test matrix
- Resolver: every tuple member changed alone (domain id, chain, network, account, keyRef, scheme, key); expired; not yet valid; revoked at, before and after the round; registry unavailable; wrong provenance forged by a caller (must not type-check or must be rejected at runtime); a valid native signature by an attacker key (reuse the `authority.rs` scenario).

- Cross-check: run the same five fixtures through Core5 directly and through the consumer; effects and post-state byte-equal.

## 5. Local precursor and ledger-native boundary

**[rec]** Feasible now, with no proving, SRS or network: items in section 4 against `LocalAtomicStore` and `LocalStipulationResolver`. Qualification stays `local-stipulation`, so this closes the Core5 premises `snapshot-to-head` and `head-extension` only for local simulation and closes `canonical-intent-signature` only for G1's native signature check. It does not close `atomic-ledger-compare-and-consume` and does not authenticate authority.

**[rec]** Optional second precursor (specified-only, not run): a Rust test in `experiments/midnight-crypto` that applies a user transaction to `LedgerState` in memory using `ContractDeploy` + `ContractCallPrototype`, with `WellFormedStrictness{proof_verification_mode: CalibratedMock}` behind `mock-verify`. It would show the ledger-native compare-and-consume for a contract state change and PartialSuccess behavior. It needs a compiled settlement contract, test keys and the official test-resolver directory, so it depends on G3's capability results. A calibrated mock is not a real proof and can't count toward Preview acceptance.

**[open]** Whether a Compact circuit can verify a Schnorr/ECDSA signature over Moriarty's frame is not established here. Three routes: (a) in-circuit verification (cost and gadget availability unknown); (b) authority carried by the unshielded transaction signature over `SegIntent` with account = `UserAddress` (self-certifying, but the signed text is the Midnight intent, not the Moriarty owner statement); (c) off-chain signature verification with an on-chain capability binding as today's kernels do (weakest, leaves the signature unauthenticated on chain). This choice determines the production authority model and needs a recorded design decision.

## 6. Barriers and dependency closure before a real Preview financial transaction

Concrete barriers (each observed above unless marked):
1. No authenticated key registry or account-to-key binding exists anywhere; accounts are symbolic. Closure: decided binding source (section 2), registration/revocation rules, finalized-state read.
2. No contract implements Core5's predicate. The existing Compact kernels have revision, program, network and capability-hash checks only; no nonce, allowance, work or signature. Closure: a settlement contract with head, replay set, allowance, work, balances/obligations, compiled to the target ZKIR.
3. No ledger-native proof of the predicate. Native proving, SRS and key material are out of scope here and owned by G3. Closure: real proof and verifier path for that contract. `CalibratedMock` and MockProver do not count.
4. ZKIRv3 vs pinned ledger's `zkir_v2` dependency unresolved. **[open]**
5. Signature route undecided (section 5). **[open]**
6. Core5 stage shape: 3/2 balances, one allowance, at most one obligation. Real Preview contract state must be projected into that shape or Core5 must be extended under a new profile. Extending it is outside this plan.
7. Fees and failure: Core5 is success-only; the ledger can apply the guaranteed section and fail the fallible one. Fees count against net goals and refunds cannot erase gross limits, so a signed phase policy is needed. Closure: an extension profile or an explicit statement that real transactions are success-only and fee-bounded.
8. Snapshot authenticity: the beta scenario's `authenticated` block is stipulated. Closure: snapshot read from finalized, block-pinned ledger state, decoded by the contract's own state layout.
9. Process gates: guarded status shows stale binding inputs, missing current accounting and unavailable resource live state for `loan-swap-subset`. Preview target, account/wallet preservation, both independent result audits (fresh `gpt-6-astra` and `grok-4.6` high, preserved identities) and public transaction ID reporting remain mandatory. No real transaction is justified until these hold.

Dependency closure order: authority binding decision, then signature-route decision, then settlement contract and compile, then proof/keys (G3), then local ledger transaction with real proof, then both audits, then admitted Preview campaign with wallet and account preservation. Steps 1-2 and the local precursor can proceed now without waiting for proving.
