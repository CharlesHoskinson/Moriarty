## Recommendation vote

APPROVE a bounded production owner-intent framing plus external-signature/local-preparation CLI flow, conditional on the root's frozen wire contract and independent audits. Do not call existing experimental frame output production. Rust main.rs currently supports only experimental frame/verify. Core/5 labels the intent moriarty-intent/3 but has no cryptographic codec. ## Observed consumer and identities

packages/moriarty-beta/src/bridge.ts expand() invokes real Source/6 parsing/lowering, and simulate() invokes prepareSource6S0Unqualified(). src/index.ts exports both. cli.ts main is synchronous; add async command branches and async top-level error handling. build.mjs bundles CLI/API with esbuild and emits declarations; package files contain dist, not Rust binaries or Cargo sources. distribution.test.mjs already tests packed CLI with PATH empty and public type imports.

Source entities: domain {id,chain,network}; account {domain,id}; asset {domain,id,scale,representation,symbol?}; obligation {domain,id,asset}. An account has NO address field or key ownership assertion. Its opaque id must not be treated as an authenticated ledger address. Source/6 preserves domain id, asset id/scale, signer id/keyRef, selected action/sourceHash/policyDigest, agreement id and signed action. chain/network/representation are erased by Source/6 and must be recovered from the actual referenced beta entities, not first declarations (the experiment exporter currently selects first domain/asset). Preserve exact claim strings; do not invent network constants, asset conversion or address decoding.

Lowered intent has version/core/sourceProfile/programId/sourceHash/policyDigest/keyRef/domain/asset/signer/nonce/preHead/notBefore/notAfter/grossCap/feeCap/netFloor plus Transfer or Repay fields. Replay is JSON tuple [domain,signer,nonce]. Source selected.sourceHash is a user claim, distinct from SHA256 of authoring bytes. Source/6 hash commits scenario as well as owner terms; exclude source6 hash/state/effects/post/work/balances from solver-independent owner intent. Commit root-selected agreement and domain/asset/account claims through the production schema. Full authoring byte hash may be provenance outside signed payload unless frozen contract explicitly selects it; signing it couples intent to irrelevant source edits.

## Minimal files and APIs

New src/auth.ts; export public functions and types through src/index.ts. No import-time subprocess. cli.ts consumes both functions. Rust production-intent commands depend on frozen protocol worker schema.

```ts
type CryptoConfig = Readonly<{binaryPath:string;timeoutMs?:number}>;
type ExternalSignature = {scheme:'schnorr_bip340'|'ecdsa_secp256k1_sha256';publicKeyHex:string;signatureHex:string;walletPrefix:boolean};
async function prepareOwnerIntent(source:string,action:string,scenarioText:string,crypto:CryptoConfig):Promise<OwnerIntentPreparation>;
async function verifyAndPrepare(source:string,action:string,scenarioText:string,signatureText:string,crypto:CryptoConfig):Promise<SignedLocalPreparation>;
```

prepareOwnerIntent calls expand then parseAndLowerSource6, resolves referenced domain/asset/accounts via analyze source, constructs frozen production owner statement without candidate state, and calls actual Rust `intent-frame` process on its JSON stdin. Output includes portable owner statement, canonical frame hex/hash, exact wallet message hex when selected, domain/account/asset claims, and qualification. Do not implement another host codec; Rust owns canonical bytes. Optional walletPrefix for preparation must be added as an explicit API argument or closed preparation options in root contract; recommended `prepareOwnerIntent(..., crypto, {walletPrefix:false})` to avoid silently defaulting signing mode.

verifyAndPrepare accepts bounded closed signature JSON (exactly scheme/public_key_hex/signature_hex/wallet_prefix), regenerates statement from current source/action/scenario, calls Rust `intent-verify` with the statement and external signature, validates response before deciding anything, then and only on valid signature invokes existing Source/6 local preparation. Signature files contain public material only. No signing command, secret/key file, wallet RPC, network transaction or in-process fallback verifier.

Do not offer a caller-supplied `signatureValid` or certified receipt API. Return Rust response as a readonly observation bound to input statement digest and signature scheme; a host boolean cannot establish authority or ledger acceptance. A changed portable payload must fail signature verification. Current scenario changes may alter local preparation while owner bytes remain stable, which is desired where only unsigned state/candidate fields change.

## Process contract and diagnostics

Use asynchronous `spawn(binaryPath,[command],{shell:false,stdio:['pipe','pipe','pipe']})`; binaryPath must be an absolute explicit developer configuration, never from untrusted statement/signature/source or PATH discovery. CLI `--crypto-binary PATH` and API config are trusted operator selection. Resolve path once. Do not call cargo at runtime or execute a shell. stdin is bounded UTF-8 JSON; end once; do not log signature request. Timeout default 10s, enforce allowed 1..30000 ms. stdout cap 262144 bytes (frame hex needs more than existing 65536 parser cap); stderr cap 8192 bytes. Kill on overflow/timeout, await close, clean timers/listeners, handle stdin EPIPE and process errors once. Limit input to 65536 bytes including envelope; protocol statement may need a smaller bound to fit verify envelope.

Diagnostic closed codes: BETA_CRYPTO_BINARY_REQUIRED, BETA_CRYPTO_BINARY_PATH, BETA_CRYPTO_BINARY_UNAVAILABLE (ENOENT/EACCES), BETA_CRYPTO_TIMEOUT, BETA_CRYPTO_OUTPUT_BOUND, BETA_CRYPTO_PROCESS, BETA_CRYPTO_RESPONSE, BETA_SIGNATURE_SCHEMA. Do not expose raw child stderr as a successful result. Child exit0 + valid schema is necessary; valid=false with exit1 is a signature rejection; malformed exit2 is transport/schema rejection. Any status/exit inconsistency fails closed. Responses need frozen literal protocol/profile/status and exact keys, bounded lowercase hex, expected lengths, digest, echoed scheme/prefix and separate null/false gates. Reject missing/unknown keys, duplicate keys, numbers where strings required, invalid UTF8, extra JSON/trailing records and unsolicited authority claims. Extend parseBoundedJson with an explicit bounded limit option or add a dedicated duplicate-safe bounded response parser; never weaken scenario limits globally.

## Result statuses and mandatory premises

Top-level statuses: OwnerIntentPrepared; SignatureRejected; CryptoUnavailable; FormationRejected/AuthoringRejected/Unsupported; SignedPreparedUnqualified; SignedCoreRejected. Each signed result carries independent coverage:

- signature: VerifiedByRust / Invalid / NotChecked; protocol production version and scheme/prefix.
- domainMapping: SourceClaimsBound / Mismatch / Unverified; signing binds claims, does not establish chain truth.
- accountMapping: Unverified; exact signer/keyRef claims plus supplied public key. No inferred account authority.
- expiry: LocalRoundWithinWindow / LocalRoundOutsideWindow / NotChecked; checked against stipulated scenario round, not chain time.
- replay: LocallyUnused / LocallyConsumed / NotChecked; tuple from lowered intent, never global replay certification.
- state: LocalStipulationOnly; snapshotToHead and headExtension remain Unverified.
- financial: LocallyPrepared / CoreRejected / NotChecked; retain actual Core rejection code and effects/post only as local candidate.
- nativeProof: NotChecked; a native signature verifier is not a native proof.
- ledger: NotSubmitted; ledgerAccepted false.

Keep Core's canonical-intent-signature, snapshot-to-head, head-extension, atomic-ledger-compare-and-consume requiredPremises intact. Put scoped Rust signature evidence next to them; do not remove signature premise while account authority/keyRef mapping remains unverified. Keep Source/6 unverifiedBindings agreement-id, selected-program, asset-scale, authenticated-predecessor verbatim. Signed preparation is always unqualified; public compile/prove/deploy gets no administrative campaign prerequisites.

## CLI and portable offline distribution

`mori intent FILE --action NAME --scenario FILE --crypto-binary ABS_PATH [--wallet-prefix]` emits JSON only with payload/frame suitable for external signing. `mori verify-intent FILE --action NAME --scenario FILE --signature FILE --crypto-binary ABS_PATH` emits signature plus local result statuses. Prefix/scheme reside in closed signature file for verification; no CLI override ambiguity. Both commands use existing bounded file reads and strict unknown/duplicate option rejection. Add help entries, success exit0 only for intent prepared/signed local prepared; invalid/formation/Core exit1; unavailable/process diagnostics exit2. Preserve existing command behavior.

build.mjs should bundle auth imports and declaration output automatically. Do not bundle a platform binary silently or make npm install fetch/build it. Docs provide an explicit separately executed `cargo build --offline --locked --manifest-path experiments/midnight-crypto/Cargo.toml` command and absolute binary selection; offline needs prepopulated pinned dependencies, otherwise diagnose missing cache. A copied production verifier plus npm tarball supports offline use independent of checkout/Cargo/PATH. Existing vscode prepare copies bundled CLI, so no editor command expansion needed to exercise new public CLI. Add README/GETTING-STARTED signed flow and limitations; tests/distribution.test.mjs must run actual copied Rust binary from packed install. No packaging success claim if binary portability is untested.
