## 3. The envelope (closed, versioned, owner-intent only)

[rec] One binary document, `OwnerIntentEnvelope/1`, called C below. It is **solver-portable**: it contains no balance, allowance, work counter, round, replay-set, candidate effect or post-head. It is not W-D2 `/3` and not the experiment frame.

### 3.1 Primitive types

- Header: the 33 ASCII bytes `moriarty-owner-intent-envelope/1` followed by one NUL (length 33 **[measured]**). Different from the experiment header and from W-D2's `moriarty-intent/3\0`, so cross-protocol bytes fail at the first bytes.
- Every field is a one-byte tag followed by its value, in the fixed order below. No optional field, no extension tag, no padding, no trailing byte. Tag order is part of canonicality.
- `id`: u16 big-endian length 1..64, then ASCII `[A-Za-z][A-Za-z0-9_]*` (Source/6 identifier and beta economic-id grammar). Case-sensitive, no normalization.
- `str`: u16 big-endian byte length 1..1024, then UTF-8 of Unicode scalar values only. Reject overlong forms, surrogates (including CESU `ED A0 80`), values above U+10FFFF, truncated sequences, U+0000–U+001F and U+007F (the same set Core's `opaque` rejects). **No Unicode normalization**: NFC and NFD spellings are different strings, different envelopes, different replay keys. Keep Core's permissiveness for the rest (C1, U+2028, bidi controls); signing displays escape them (§6.4).
- `opt_str`: one presence byte (`00` absent, `01` followed by `str`). Absent differs from every present value; empty is not a legal `str`.
- `u128`: 16 bytes big-endian. `s127`: 16 bytes big-endian with the top bit clear (value ≤ 2^127−1). `scale`: one byte 0..18. Fixed width means no redundant integer spellings exist.
- `hash32`: 32 raw bytes. `enum`: one byte from the listed values only.

### 3.3 What the envelope deliberately excludes

- `signedDigest` or any digest of C (self-reference). The digest is derived outside: `intent_digest = SHA-256(C)`, 32 bytes, shown as 64 lowercase hex characters. Nothing carries a caller-supplied digest as evidence; the artifact schema has no such field and rejects it as unknown.
- Snapshot, round, work, allowance, replay set, balances, candidate effects, post-head, scenario hash, proof, signature.
- Creditor on repay (F7).
- Any registry or authority claim. `key_ref` and `public_key` are the owner's claim that this reference denotes this key; checking that against a registry is out of scope and stays `null`.

### 3.4 Binding semantics ([rec] with reasons)

- `public_key` inside C prevents key substitution: re-signing the same intent with another key changes C.
- `chain`, `network`, `asset_representation`, `asset_symbol`, `asset_scale`, `domain_id`, `signer_account` close F1.
- `agreement_id`, `action_id`, `authoring_source_sha256` bind the intent to the exact reviewed program source. A reformatted or commented source gets a different hash, so the intent no longer matches. That is conservative on purpose. A formatter-normalized hash is a possible later variant **[open]**.
- `declared_source_label` and `declared_policy_label` are signed as typed opaque claims. **No code may infer that they are, or match, any hash or that any verification of provenance occurred.** A label that looks like 64 hex characters but differs from `authoring_source_sha256` is not an error and not a mismatch signal; a label equal to the real digest is still only a label.
- `core_version = 05` and `action_id` are nominal discriminators. No semantic hash of Core/5's rules exists, so the envelope does **not** authenticate Core semantics. Say so in the output (`core_semantics_hash: null`).
- Replay identity is the tuple `(domain_id, signer_account, nonce)`. The runner derives Core's replay key with `JSON.stringify([domain, signer, nonce])`, the same function path Core uses. Rust echoes the tuple as an array of three strings and never re-serializes the key.

## 4. Signing conventions and wallet binary encoding

Two conventions over the same C. The artifact names one explicitly; the verifier never guesses and never tries both.

- `raw`: message M = C.
- `wallet_prefixed`: M = ASCII `midnight_signed_message:` + decimal byte length of C (no leading zeros, no padding) + `:` + C.

[rec] Sign C or its prefixed form directly, not a digest of C. C is small, avoids a second hash layer and keeps the experiment's tested pattern. The 32-byte digest variant from the W-D1 note stays an **[open]** item for the later in-circuit binding work and is not adopted here. A signature over `D = SHA-256(C)` (raw or wallet-prefixed) must fail as a negative (§9).

Wallet binary transport: C contains NUL and bytes ≥ 0x80, so it must reach `signData` as `encoding: hex` (lowercase) or base64, both of which the connector decodes to bytes. `encoding: text` would sign different bytes. The runner emits hex only. The verifier artifact accepts only lowercase hex for every byte field, rejects uppercase, mixed case, `0x`, odd length, whitespace and non-hex. The prefix counts decoded bytes, never characters or UTF-16 units.

Extend the existing crate `experiments/midnight-crypto`; keep `frame` and `verify` untouched.

New CLI command `moriarty-midnight-crypto verify-intent`, stdin only, 65,536-byte cap read with `.take(65537)` as today. Request (closed, duplicate keys rejected, unknown/missing rejected, any key order accepted):

```json
{"profile":"moriarty-owner-intent-artifact/1","envelope_hex":"..","convention":"raw|wallet_prefixed","scheme":"schnorr_bip340|ecdsa_secp256k1_sha256","public_key_hex":"..","signature_hex":".."}
```

`scheme` and `public_key_hex` must equal the envelope's `key_scheme`/`public_key` (a wallet reports the key separately; a mismatch is `ARTIFACT_MISMATCH`, not a bad signature). The signature is exactly 64 raw bytes. Decode strictly, re-encode, require byte equality before verifying.

Output (single JSON object plus `\n`, ≤ 8192 bytes, exact key set):

```json
{"status":"SignatureChecked","signature_valid":true,"envelope_valid":true,"intent_digest_sha256":"..","envelope_bytes":379,
 "convention":"raw","scheme":"schnorr_bip340","replay_tuple":["Midnight","Owner","n1"],
 "claims":{ "...decoded fields as strings..." },
 "key_binding_valid":null,"authority_valid":null,"snapshot_membership_valid":null,"transition_valid":null,

```

Exit codes: **0** `signature_valid:true`; **1** verification ran on well-formed input and failed (`status:"SignatureChecked"`, `signature_valid:false`); **2** rejected (`status:"Rejected"`, `code`, `ledger_accepted:false`). For code 2, `signature_valid` is `false` for `SIGNATURE_MALFORMED` and `KEY_MALFORMED` (verification attempted and definitively not valid, per F8) and `null` for every pre-verification code.

Stable codes: envelope `HEADER LENGTH TRUNCATED TRAILING FIELD_TAG OPERATION_TAG LITERAL ID UTF8 CONTROL RANGE VALIDITY SCHEME KEY_LENGTH EMPTY`; artifact `INPUT_LIMIT UTF8_INPUT JSON ARTIFACT_SHAPE HEX ARTIFACT_MISMATCH CONVENTION SIGNATURE_MALFORMED KEY_MALFORMED`. Precedence: input limits → JSON/shape → hex → envelope decode → artifact/envelope consistency → key and signature parse → verify. Within the envelope, check in field order.

ECDSA: rely on the library's observed low-S enforcement (F8) and pin it with a test; if a future pin accepts the twin, the verifier must add its own low-S check before shipping.

- **No new MCP tool** and no MCP change (F6). The published `mori` package ships no Rust binary; `--verifier PATH` is required, and a missing/unrunnable path is `VerifierUnavailable`. There is no JavaScript fallback verifier.

### 6.2 Derivation rules

1. Encode from the beta source and action only. `intent-request` takes no scenario; a scenario is never an input to C.
2. Representability failures return `IntentNotRepresentable` with the cause and never emit a partial envelope: control character in an opaque string, string over 1024 UTF-8 bytes, id outside the grammar, any s127 field above 2^127−1, rounds above 2^128−1, scale above 18, `valid_from > valid_to`, action other than the two S0 actions (`Unsupported` stays `Unsupported`), analysis diagnostics.
3. Financial invalidity is **not** a representability failure. Zero amount, `gross_cap < value+fee`, `fee > fee_cap`, `net_floor > value` and the like encode, sign and verify; Core rejects them separately (§10).
4. `intent-verify` re-derives the expected envelope from source+action+(scheme,key from the artifact) and compares bytes. A mismatch is `IntentSourceMismatch`: `intent_matches_source:false`, signature not reported as valid, exit 1.
5. `declared_*_label` values go through byte-for-byte; no function compares them to any digest.

### 6.3 Verdict composition and exit code

Output carries every §2 field. `status` is `IntentChecked` when the verifier completed with a conforming reply, else `VerifierUnavailable`, `VerifierProtocolError`, `IntentRejected` or `IntentSourceMismatch`. Exit 0 requires `signature_valid === true`, `intent_matches_source === true` and, if `--scenario` was given, `local_core.status === 'PreparedUnqualified'`. Anything else exits 1. A valid signature with a Core rejection prints `signature_valid:true` and a `local_core` rejection with exit 1. Output from `expand`, `simulate`, `inspect`, `check` must stay byte-identical (§11).

`unverifiedBindings` and `requiredPremises` printed by existing commands do not change. The new command adds `signedBindings: ["agreement-id","selected-program","asset-scale","chain","network","asset-representation"]` meaning "committed by the signature bytes", plus `stillUnverified: ["authenticated-predecessor","snapshot-to-head","head-extension","atomic-ledger-compare-and-consume","key-authority","creditor-cell (repay)"]`.

### 6.4 Display

`intent-request` prints a human display of every field from §3.2 with all non-printable-ASCII code points escaped as `\u{...}`, plus `intent_digest_sha256` and the hex of M for each convention. Test: a `key_ref` containing U+202E renders escaped.

### 6.5 Fail-closed transport to the Rust process

`execFile` with a fixed argv (no shell), `stdio` pipes, timeout 10 s, env limited to what the binary needs, request ≤ 65,536 bytes, stdout limit 8192 bytes, stderr limit 8192 bytes (never shown as a verdict). Accept only: exit code in {0,1,2}; stdout is exactly one UTF-8 JSON object plus one `\n`, no BOM; exact expected key set; `exit 0 ⇔ signature_valid true`; `exit 1 ⇔ signature_valid false and status SignatureChecked`; `exit 2 ⇔ status Rejected`; `ledger_accepted === false`; all `null` fields null. Any deviation gives `VerifierProtocolError` with `signature_valid:null`. Never convert an unexpected reply into `false` and never into `true`.

## 9. Signature, binding and transport negatives

Every case below keeps the **original signature** unless it says "re-signed". Run each across both schemes and both conventions unless stated.

**B. Every field is bound.** Generate one structured mutation per leaf of §3.2 for all five fixtures (strings: append a character; ids: swap to another valid id; numerics: +1 or flip a bit; enums: other legal value; opt_str: absent↔present; operation fields individually), re-encode, keep the signature. Expected: `signature_valid:false`, `status:"SignatureChecked"`, exit 1. The test asserts the mutated bytes differ from the original and the count of mutations equals the leaf count in a machine-readable list that the test itself emits (not a hard-coded constant). Named cases that must be present:

- B1 `network` preview→mainnet; B2 `chain` changed; B3 `asset_representation` canonical→wrapped; B4 `asset_symbol` USD→EUR and absent↔present; B5 `asset_scale` 2→3; B6 `asset_id`, `domain_id`, `signer_account` changed (accounts/asset/domain rebinding).
- B7 For B1–B4 also assert (through the runner) that the *Source/6 text* from the two beta sources is identical while the envelopes and digests differ, pinning F1.
- B8 `key_ref`, `nonce`, `pre_head`, `valid_from`, `valid_to`, three caps, each operation field.
- B9 `agreement_id`, `action_id` Transfer↔Repay (with body adjusted to stay well-formed), `authoring_source_sha256`, both declared labels.
- B10 `key_scheme` swapped with a key of the other scheme's length; `public_key` replaced by an attacker key inside C with the original signature (invalid); with the attacker's own fresh signature (valid, and still `authority_valid:null`).

**W. Wallet and convention.**

- W1 Signature made over `raw` M fails when verified as `wallet_prefixed`, and vice versa.
- W2 Prefix with length off by one, doubled prefix, prefix over the UTF-16 length of the hex string, prefix with leading zero, uppercase `MIDNIGHT_...`: all `signature_valid:false`.
- W3 Signature a wallet would produce when `signData` receives the **hex string as text** (message = prefix with length 2·|C| + ASCII hex): fails against `wallet_prefixed` C. Also base64-of-text.
- W4 Signature over `D = SHA-256(C)` (raw and prefixed, 32-byte and 64-char hex forms): fails.
- W5 Prefix length boundaries 99, 100, 999, 1000 and 8192 bytes of C (use synthetic max-size valid envelopes): signature valid at each, wrong digit count invalid.
- W6 `convention` field missing, unknown (`Raw`, `wallet`, `both`), or duplicated: `Rejected`, `CONVENTION`/`ARTIFACT_SHAPE`/`JSON`. The verifier never tries the other convention.

**X. Cross-object separation.**

- X1 Signature of fixture i checked against fixture j's envelope (same key): false.
- X2 Signatures over the experiment owner-intent frame, the experiment complete candidate claim, and the W-D2 `/3` wire (for the same fixture and key) do not verify against C, and a signature over C does not verify against those frames.
- X3 Scheme confusion: ECDSA signature under scheme 01 and Schnorr under scheme 02 (artifact and envelope consistent): `false` or `SIGNATURE_MALFORMED`/`KEY_MALFORMED` per F8, never `true`.
- X4 Wrong key (another fresh key, signature unchanged): `false`. Attacker signs C that names the victim's key: false. Attacker signs C that names the attacker's key: true with every authority field `null`.
- X5 ECDSA high-S twin: `false` (pins F8). Schnorr/ECDSA `s=n`, zero signature, all-`ff` key: `Rejected` with `SIGNATURE_MALFORMED` or `KEY_MALFORMED`, `signature_valid:false`. **T. Rust stdin transport (fail-closed).**

- T1 Truncated JSON, `{}`, `[]`, a bare string, trailing JSON (`{..} {}`), invalid UTF-8, BOM, duplicate key, escaped duplicate (`"scheme"`), unknown key, missing key, numbers where strings belong, `null` fields: exit 2, `status:"Rejected"`.
- T2 Request of exactly 65,536 bytes processed; 65,537 bytes → `INPUT_LIMIT`; envelope hex decoding to 8193 bytes → `LENGTH`; request streamed with an infinite or slow-writer pipe does not buffer beyond the cap.
- T3 Hex: uppercase, mixed case, `0x` prefix, odd length, interior whitespace/newline, non-hex, empty, correct length with one bad nibble: `HEX`. Envelope hex of valid bytes with one trailing zero byte: `TRAILING`.
- T4 `scheme`/`public_key_hex` disagreeing with the envelope: `ARTIFACT_MISMATCH` and `signature_valid:null`.
- T5 Unknown subcommand, no subcommand, extra args: exit 2.

**TS consumer transport.** Using stub executables in a temp directory (always run) plus the real binary (when `MORIARTY_VERIFIER` is set), each of these yields `VerifierProtocolError` or `VerifierUnavailable`, exit 1, `signature_valid:null`, never valid:

**R. Authority, nonce, head (local model only, never in production CLI).**

- R1 A test-only registry like `tests/authority.rs` `LocalBinding`, rebuilt over the decoded envelope: positive at `valid_from` and `valid_to` with unused nonce and matching head; negative for round one before/after, wrong `key_ref`, wrong domain, wrong signer, missing mapping, revoked, expired mapping, wrong key (attacker signature valid, authority false), consumed nonce, stale `pre_head`. **G. Opaque hash and self-reference (provenance).**

- G1 Source with `source_hash: "deadbeef"×8` (64 hex chars) not equal to the real digest: encodes, signs, verifies; no mismatch is raised; output has no field claiming the label was checked.

## 12. Residual risks and open decisions for the root

1. **[open] Header and profile name.** Recommended `moriarty-owner-intent-envelope/1`. Do not call it `/3` until the W-D1/W-D2 decisions are made.
2. **[open] Whole-message signing vs digest signing.** Recommended whole C. Digest signing is a different convention and needs its own vectors.
3. **[open] Exact-bytes program hash.** Recommended; any whitespace or comment change invalidates the intent. A normalized variant needs a formatter-trust argument.
4. **[open] Repay creditor and obligation asset are not signed (F7).** Close later by extending beta source/Source/6 or by binding the obligation cell in the proof relation. Until then `stillUnverified` lists `creditor-cell`.
5. **[open] Rounds as u128, scale ≤ 18.** Recommended because it matches Source/6 and Core exactly and creates no new narrowing. W-D2's u64/38 differ; a later unification must map explicitly.
6. Key authority, revocation, registry, snapshot-to-head provenance, head extension, atomic ledger compare-and-consume, native proof binding of `intent_digest_sha256`, live wallet `signData` interoperability, Preview settlement: all remain open and unchanged by this work. A passing run proves bytes, schema, one native verifier and refusal behavior locally, nothing more.
7. Wallet convention evidence is the pinned connector text plus local ephemeral-key tests (F10). A live wallet vector remains a required later experiment; S1 does not perform it.
8. ECDSA low-S behavior is a property of the pinned library (F8); re-characterize on any pin change.
9. Source/6 `use_replay` and Core's tuple key use string forms specific to this JS implementation (`JSON.stringify`); a different implementation must derive the tuple, not the string. Documented, tested in R3.

## 14. Phasing vote and S1 scope

**Vote: phased implementation is sound**, on four conditions:

1. Phase 0 writes the independent Python reference and the frozen golden vectors **before** the Rust or TS code, from §3 only. A different worker than the implementers must write it; the implementers must not read each other's code.
2. Phase 1 (Rust codec + `verify-intent` + Rust tests) is not "consumed" until Phase 2 passes against the real built binary with zero skips.
3. After the root freezes §3, any field change reruns Phase 0 vectors and all three encoders; no silent schema edits.
4. Existing `frame`/`verify`, `export-fixtures.mjs`, `moriarty.json` and the §11 gates remain as regression throughout.

Phases: **0** vectors/oracle; **1** Rust `intent.rs`, CLI, `intent_*` tests; **2** TS `intent.ts`, CLI commands, stub and real-verifier tests, fixture export; **3** cross-language parity, §9–§11 matrix, gate regression, results note; **4** (separate, later) live-wallet vector, authenticated registry, ledger/proof binding. Phases 0–3 touch no network and no wallet.

**Suggested scope for S1 after the root freezes the schema [rec]:** Phase 0 (reference + vectors + hostile corpus) and Phase 1 test authorship, or Phase 1 implementation if the root assigns a different worker to Phase 0. S1 would not write the TS encoder. Writable paths: the S1 files in §13 only; no edits to existing tests, fixtures, docs or beta sources other than the single `lib.rs`/`main.rs` additions.

## 15. What this contract does not establish

It does not establish wallet interoperability, key ownership, current authority, state authenticity, head extension, atomic consumption, complete effects, UInt128 circuit ranges, proof correspondence, or any ledger or Preview outcome. A green run means: one closed envelope encodes the same bytes three ways, one pinned native verifier accepts only the exact signed bytes under an explicitly named convention, every field change breaks the signature, every malformed or fail-closed transport case refuses, and financially invalid owner actions are still rejected by Core after their signature verifies.
