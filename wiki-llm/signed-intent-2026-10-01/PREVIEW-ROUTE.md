## Hashing is available; exact bytes remain mandatory

Current official library documentation describes persistentHash as SHA256 over Compact values and ECDSA verification as a supplied-digest predicate; the caller must constrain the digest to the intended message and assert signature success. The API takes secp256k1 point/signature values, whereas the frozen runner uses33-byte compressed public keys and64-byte r||s signatures: decoding and point/scalar validity must be specified, not inferred from equal hex strings. [Official standard-library API](https://docs.midnight.network/compact/standard-library/exports#secp256k1ecdsaverify), [persistentHash API](https://docs.midnight.network/compact/standard-library/exports#persistenthash).

Repository source trace establishes a promising exact-byte hashing route rather than absence of SHA256:

- `base-crypto/src/hash.rs::persistent_hash` and `PersistentHashWriter` use SHA256.
- `onchain-runtime-wasm/src/primitives.rs::persistent_hash` hashes `ValueReprAlignedValue.binary_repr`.
- `transient-crypto/src/fab.rs::ValueAtom::binary_repr_unchecked`, `AlignmentAtom::Bytes { length }`, writes raw value bytes plus zeroes to declared byte length. `ValueReprAlignedValue` introduces no extra tag in this path.
- Installed runtime0.16 `dist/built-ins.js::persistentHash` uses type alignment and the native representation.

**Inference:** a `Bytes<N>` value whose declared N equals the exact complete signing message length can reproduce SHA256 of that message, preserving trailing zeroes. A larger padded byte buffer hashes extra zeroes and is wrong. A generic typed struct or field vector can hash different serialization even with the same conceptual terms. This exact runtime/ZKIR comparison is source-derived and has not been exercised as a beta-frame circuit experiment.

The frozen raw signing message is F=`UTF8("moriarty-signed-intent/1\\0") || u32BE(len(canonicalJSON)) || canonicalJSON`; connector framing prepends its exact byte-length prefix. The ECDSA API takes SHA256 of the selected signing message, not a second SHA256 of its hex text, digest text, or an unbound host-computed digest. The native BIP340 route also hashes its message under the inspected pinned Rust API; a future BIP340 circuit must match the actual challenge/tag convention, not reuse Jubjub Schnorr by name.

## Feasible source/compiler alternatives

**Recommended source alternative: specialize the first real beta transfer to the frozen program/selected action and declared account/key mapping.** Generate the canonical owner-frame byte template from the same parsed, checked source that generates its numerical transition. For a source with fixed literal amount/fee/window/nonce and fixed configured signer key, the complete frame is a bounded fixed-length constant; exact SHA256 has a direct Bytes<N> route. Where metadata/key/nonce varies, derive and constrain each byte slot, UTF8/escaping, canonical decimal digits and length, or reject it as unsupported in the declared backend slice. The circuit must prove source-defined fields equal decoded transfer/key/registry fields. Do not introduce a host-supplied digest or success flag. This avoids pretending the first circuit implements all permitted variable-length JSON up to the protocol bound. It still needs genuine signature/registry/state checks.

**Compiler alternative:** inspect a pinned ledger9-compatible toolchain with actual secp ECDSA and exact message hashing, then deliberately regenerate this small contract's source, runtime, ZKIR and keys under the whole compatible stack. Official0.34.0 uses language0.26/runtime0.19 and ledger9; newer0.35 documents caller identity but warns that top-level caller reads can mismatch after wallet balancing. It recommends caller reads only for known contract calls until explicit top-level caller support exists. Thus a newer caller builtin is not an automatic wallet-owner repair. [Official release notes](https://github.com/midnightntwrk/compact/releases).

The official SDK matrix inspected today is dated2026-04-07 and lists Preview ledger8; it does not establish current ledger9 availability. Live read-only deployment/protocol evidence is required before selecting a new stack. [Official compatibility matrix](https://github.com/midnightntwrk/midnight-sdk/blob/main/COMPATIBILITY.md). No upgrade was attempted. The earlier installed0.31.1 probe failure remains controlling for that binary. The auxiliary source checkout c47230cc8c3e743634166d9b84698ac2b238c418 is not the installed compiler source pin.

A **current-stack handwritten secp circuit** is an alternative only if generated native-field limb arithmetic constrains full curve operations/signature verification and matches actual ledger8 ZKIR verifier semantics. No small measured fit/source implementation exists; secp/SHA/registry costs are outside the k10 numerical result. This would require a new reviewed encoding/resource proposal and cannot silently inherit the completed numerical experiment's budget.

A **native ledger input-owner route** can establish authorization of specific spent inputs and a final native call, but has no inspected current contract API tying source signer/keyRef to that input owner for every accepted call. An attacker paying the same amount from their own inputs must not consume the victim's intent nonce/allowance/head. Offchain provider payer checks cannot enforce that universal on-chain condition. `ownPublicKey` concerns shielded coin identity and cannot be silently substituted for a registered unshielded BIP340 owner or ECDSA intent key. A separate final native transaction signature can strengthen the particular transaction's evidence but does not repair missing contract beta-frame authorization.

Do not change the frozen protocol to Jubjub/Poseidon without a separately explicit compatibility/design decision. Do not treat a bearer capability supplied by bootstrap as a wallet signature registry.

## Concrete repair dependency sequence

1. **Source/identity fixture:** freeze exact source, action, statement/frame, public key algorithm/bytes, network genesis, symbolic account->owner/key/address mapping, actual token color, and intended deployment/program/VK identity. Registry bootstrap is an explicit trust event; define genesis authority and owner-controlled rotation/revocation validity rules. The source account domain/id alone is insufficient.
2. **Compatible verifier discriminator:** identify one actual compiled secp verifier and exact Bytes<N> hash route accepted by the selected ledger stack. Test cross-language exact digest, curve/key decoding and wrong-key/invalid-signature/changed-byte refusals with independently defined expected vectors. A source-specialized constant frame still must constrain all corresponding operation fields. No full compiler install/proof retry under the present read-only scope.
3. **Contract acceptance state:** implement contract ledger owner registry/key epoch, head/revision, replay tuple or scoped nonce, work counters/totals, allowance counters/totals, financial balances/duties and actual asset/address map. Contract reads must authenticate the current state at application. A caller-provided Merkle root is not an authenticated head. The circuit atomically checks-and-consumes these states alongside native send/receive and complete ordered effects.
4. **Actual caller integration:** extend the existing `experiments/moriarty-language/src/lower-compact.ts` source-derived mapping and materialization/generator, then custody wrapper, `ledger/{build-proven,proven-assets,prepare-deployment,run-local,integrate-preview,financial-comparison}.mjs` together. These currently admit fixed loan/swap constructors/circuits and amounts, so a beta helper alone has no consumer. Rebuild pinned source manifests and keys whenever source changes. Preserve existing wallet/deployment identities and use actual existing asset colors; redeployment-derived lookalike colors do not preserve assets.
5. **Adversarial acceptance:** attacker-valid key/registry substitution; revoked/expired/rotated key; source/frame/digest mismatch; replay and same-head race; state/finality substitution; gross/fee/net/window/work/allowance overflow; exact omitted/reordered effects; guaranteed/fallible partial success; compare all pre/post state and all native asset movements. A competing stale transaction must not consume another nonce/allowance/head. Invalid financial proof must not become acceptance merely because host verification succeeded.
6. **Preview delivery:** exact current contract/runtime/build/proof/protocol identity, actual resource allocation, per-color gross debit and DUST cap, original wallet address/state identity, submission count/deadline and service/finality readiness. Observe native serialized bytes, matching successful contract call, block-pinned full state/balances and chain-finalized block via `ledger/receipt.mjs::observeFinalizedStage`. This node/indexer observation has an explicit trust boundary; it is not a cryptographic light-client finality proof. Independent full proof/correspondence and result audits must precede acceptance claims. Retain notifications and ambiguity without blind retries.

The first chain target is complete transfer acceptance for the explicitly supported source slice. Repayment follows with full obligation/AccrualFirst state and residual duties. Transfer numerical evidence does not establish repayment, full ACTUS/DeFi support, recursive PCD or mandatory property/intent/transition/history proof coverage.
