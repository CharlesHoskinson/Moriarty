## Minimal strict fee-paying fixture: concrete source-feasible route

The kernel's 10 units of A1 sent to 03 are an application fee. Native transaction fees are DUST; they cannot be paid by relabeling that A1 output, minting an ordinary “fee token” UTXO, zeroing protocol prices, or disabling balancing.

**Source facts:** `L/ledger/src/verify.rs:798–823` debits actual computed protocol fees and credits both dust spend v_fee and registration allow_fee_payment. `dust.rs:1214–1264` calculates generationless fee availability from guaranteed NIGHT inputs owned by the registration key, absent from `dust.generation.night_indices`, and present in the reference UTXO state with creation timestamps. Available dust is the sum of `min(value * night_dust_ratio, elapsed_seconds * value * generation_decay_rate)` with saturating arithmetic. `dust.rs:846–876` checks allowance against that availability under default balancing; `:710–733` verifies the registration signature on parent intent signing data. Application consumes fee dust through `apply_registration:1050–1113`; fee accounting uses actual reference-state UTXOs (`semantics.rs:1143–1208`).

**Recommendation, unexecuted:** use a fresh explicitly authorized development genesis fixture with:

- Exact retained contract state at address 04, correct operation/VK and 10,000 A1 escrow.
- One public development NIGHT signing key, one actual guaranteed NIGHT input owned by it, an honest fixture creation timestamp old enough for sufficient generationless dust, and no existing night-index registration for that input. Preserve current default parameters. This is a declared genesis condition, not fabricated elapsed live history.
- A positive-value matching guaranteed NIGHT return output to the same owner, so NIGHT principal conserves exactly. All ordinary input ownership and spent/absent checks remain active.
- One correctly signed `DustRegistration` for that NIGHT key, `dust_address: Some(...)` using explicit public development dust key material, `allow_fee_payment` sufficient for the actual transaction fee but no greater than proven availability, valid ctime, and `spends: []`. `None` is a deregistration and fails without existing delegation (`dust.rs:1060–1081`). Avoid that trap.
- A1 recipient/fee outputs in the same logical segments as their contract effects, with exact 1000 and 10 amounts. No shielded inputs/outputs/transients.

This can source-feasibly use exactly one contract proof: `DustActions::prove` proves only its spends and clones registrations (`dust.rs:759–776`); signatures are not dust spend proofs. Registration-only dust_actions is nonempty and canonical. `Intent::prove` may visit it without producing any extra proof. Do not call `give_fee_token`: that utility first registers using balancing=false/signatures=false (`test_utilities.rs:333–369`), which does not meet this fixture's strict acceptance requirement.

Record the explicit numerical invariant `native_fees <= F = allow_fee_payment <= generationless_availability`, with positive same-owner NIGHT return, registration Some address and valid creation/block times. Freeze a sufficient allowance after examining actual fee calculation with final transcript/VK/proof sizes. Recheck actual `fees_with_impl`/well_formed computation against availability and allowance on the serialized final transaction. Ledger balancing rejects negative balances, not every positive residual (`verify.rs:1364–1379`); explicitly assert conservation and accounted dust remainder rather than inferring exact balance from acceptance. Do not rely on the application log for unpaid dust as a gate: `semantics.rs:1206–1208` logs that impossible-under-valid-validation condition. Independently assert actual fees are fully funded and consumed under identical parameters/reference state.

No additional proof type is inherently unavoidable for this precise conditional genesis + generationless-registration route. If its prerequisites cannot be met, ordinary DustSpend requires its own real native proof and key material (`dust.rs:520–545`); shielded offers introduce their proof obligations; a contract deposit/mint circuit introduces its own proof. Count every provider invocation and refuse unknown key locations so an unexpected additional proof cannot silently consume the one-proof allocation. No funding mechanism grants new resource authority.
