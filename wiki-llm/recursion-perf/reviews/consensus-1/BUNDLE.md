## What the new sources establish—and do not

**SOURCE:** Nocy's historical pinned `kzg.h` uses thread-local monomial/Lagrange `KzgPointsCache` and a work cache. ## Memory and amortization, including the rest of the prover

**ESTIMATE:** With packed affine G1 size 96 bytes and scalar size 32 bytes, k20 is **96 MiB of bases** and **32 MiB of scalars**. One maximum-size monomial table plus separate Lagrange tables for k20/k17/k13/k12 requires `96+96+12+.75+.375=205.125 MiB`. Precompute factor four gives **820.5 MiB**, factor eight **1,641 MiB**. This assumes identical official SRS, domain conventions and compatible prefix precomputation; padded layouts must replace 96 with measured `sizeof`. Different circuit VKs do not automatically imply different SRS bases, but different Lagrange domains do.

**ESTIMATE:** For ICICLE-style `c=16,p=4,b=8,N=2^20`, `q=ceil(ceil(255/16)/4)=4` bucket modules. Scalars `32Nb=256 MiB`; indices `24qNb=768 MiB`; 144-byte projective buckets `144q2^c b=288 MiB`; all-domain tables above `820.5 MiB`. Conservatively retaining all yields **2,132.5 MiB**, before sorting/allocator/double-buffer overhead. Using 192-byte XYZZ buckets adds **96 MiB**. This is an admission estimate, not a backend allocation promise. The source memory formula is in `raw/s3-commit-msm/helper1-icicle-msm.md`; the implementation's actual chunk estimator is in `open-icicle-cuda-msm.md`.

**ESTIMATE:** WLC threshold six means up to seven stored affine multiples per original base: two k20 tables alone cost `2*7*96=1,344 MiB`, if stored packed affine. Its table is not ICICLE's shifted-base layout: do not combine their parameters or projected savings. At k24 the preceding two-table factor-eight calculation grows `16×` to **24 GiB** before scalar, index, bucket or NTT storage—another reason not to import large A40 contest configurations.

**SOURCE:** Earlier whole-prover memory estimates reach **28.06–28.56 GiB** for an extended-domain proxy, including a 0.75 GiB SRS allowance. Capture: `raw/s3-commit-msm/earlier-astra-proposal.md`. These are earlier estimates, not measurements.

**ESTIMATE:** Raising just that allowance from factor four to eight adds **0.75 GiB**, producing **28.81–29.31 GiB**, while a different batch scratch policy may add more. Admission must use actual `cudaMemGetInfo` and measured concurrent peak, not “32 GB minus the SRS.” Start with a total cap `min(24 GiB, .8*free_device_bytes)` and lower precomputation/batch width when polynomial buffers need the space; 90 GB host RAM is not device residency.

**ESTIMATE:** Precompute break-even is `reuse_count > preparation_time/(unprepared_time−prepared_time)`. Using the historical `25.5−18.1=7.4 ms` only as an illustration, **1 second** preparation takes `ceil(1000/7.4)=136` uses to recover. Moving factor four to eight saves only **0.9 ms** per vendor MSM; a hypothetical extra 1 second then needs **1,112** uses. Measure first-proof latency separately from steady state, and charge preparation once per actual basis table.

## What would change the verdict

**ESTIMATE:** To reach 10× versus Nocy's recorded CPU time requires `1−f+f/s+h ≤ B/10 = .279545`. With `h=0`, the necessary remaining-MSM fractions are **90.06% at s=5**, **80.05% at s=10**, **75.84% at s=20**; even infinitely fast MSM needs **72.05%**. At `f=.6`, the absolute ceiling is `B/.4=6.99×`. A *further* 10× versus the already-GPU baseline is a different target: at `s=20`, it needs `f≥.9/.95=94.74%`.

**OPEN QUESTION:** The verdict upgrades if E1 finds the required critical-path share in the actual P **and D** (and eligible leaves), E2 demonstrates the necessary service speed with official bases and complete correctness, and E3 preserves those gains under whole-prover memory pressure and unchanged ledger-9 verification. Single-kernel timing, batch throughput, changed SDK versions or a parent-only speedup do not meet that condition.

**ESTIMATE:** Downgrade this stage as the route to 10× if the measured unchanged remainder exceeds the budget, if conversion/synchronization erases kernel gains, or if a corrected always-BLST CPU baseline is substantially faster. Retain the best verified MSM adapter as a partial speedup and pass the measured residual budget to witness/NTT/quotient leads. No curve substitution, transcript substitution, new SRS or removal of terminal pairing is proposed.

Consequently the wide k20 suite's “Generate Lookups” 59.63→56.84 s (1.05×) does not refute this specialized construction. The wide circuit has **1,135 columns** and uses an EPYC 7702 / four RTX3090 system; neither result is a Sherlock or 5090 measurement. Sources: `cusnark-permutation.md`, `cusnark.md`.

**SOURCE — ICICLE is supporting evidence for resident arithmetic, not a product-scan number:** The v2 post benchmarks on RTX4080/i9-13900k, includes a simple 8-bit lookup workload with redundant constraints inflating degree, and advertises up to 25× plus vector-operation gains at 2^22. Its lookup-constraint evaluation work overlaps quotient construction. It supplies no directly matching BLS12-381 k20 grand-product timing. The polynomial-inversion-only cuSnark table is nearly flat for lookup generation (57.99→57.92 s), another reason not to infer full-proof benefit from an inverse kernel. Sources: `icicle-halo2-v2.md`, `cusnark-inversion.md`.

**SOURCE — Three independent serial/preprocessing targets exist:** 0.8.3 `permute_expression_pair` calls `sort`, builds `HashMap<F,u32>`, and fills leftover table entries in randomized map order. `commit_product` parallelizes denominator/numerator construction but calls the sequential `ff` batch-inversion iterator and a serial product `scan`. Copy-permutation products similarly use batch inversion and a row loop, with `last_z` carried between column sets. Sources: `midnight-lookup-prover.md`, `ff-batch.md`, `midnight-permutation-prover.md`.

**ESTIMATE — Direct-ID construction suitable for the range table:** Build offsets for the actually loaded tags, with a tuple ID `offset[tag]+value`. Validate the exact raw lookup expressions, including selectors and the disabled `(0,0)` row; do not infer an ID from the theta-compressed field value. Count inputs by ID and emit one block per used ID. At each block head, put one corresponding table entry into S′; fill all remaining positions with unused table entries, retaining their multiplicities and padding. This produces permutations A′ and S′ without requiring numerical field order. For generic lookups, use the existing algorithm or a separately collision-safe generic implementation. The ID metadata is a prover optimization, not a new verifier assumption. Evidence motivating this construction: `midnight-pow2range.md`, `midnight-lookup-prover.md`, `halo2-lookup.md`.

**ESTIMATE — Algebraic reason:** For each group, either `A′[i]=S′[i]` at its head or `A′[i]=A′[i−1]` internally. Thus the existing adjacency equation `(A′−S′)(A′−A′prev)=0` holds, with A′[0]=S′[0]. Exact preservation of both multisets supplies the existing grand-product equality. If distinct raw tuples collide after theta compression, reserving one table entry per raw tuple still satisfies those equations; no inverse map from a compressed value is needed. This reasoning does not justify dropping any opening, boundary, integer range constraint or transcript challenge.

**SOURCE — Executed model, narrowly scoped:** The seven-element-field model passed **567** permutation/adjacency cases (including **162** compression-collision cases), **11,660** nonzero-denominator product cases, three invalid-tuple rejections and **390** block-scan checks including zeros. It explicitly skipped **16,123** exceptional challenge cases for the rational-product test. This is an algebra sanity check, not a security proof, zero-denominator acceptance claim, BLS arithmetic test, or ledger test. ## Integration and acceptance constraints

**SOURCE — Existing kernels are primitives:** sppark has `Multiply`/`prefix_op` and a BLS12-381 scalar field type (`fr_t`, 255-bit modulus); its batch-inversion header is a local sequential forward/backward template that preserves zeros, **not** a ready device-wide inversion kernel. A GPU implementation must organize many such chunks plus carries. The captured source tree is `69440fd55006489431fef54f0ee45f2b67db7c75`; raw Markdown extraction is reference text, not buildable source. No CUDA13/5090 build was performed. Sources: `sppark-tree.md`, `sppark-prefix.md`, `sppark-bls381.md`, `helper2-batch-inversion.md`.

**ESTIMATE — Memory envelope:** One scalar vector at k20 is `2^20×32=32 MiB`. Eight scratch vectors × four lanes = **1 GiB**, plus `4×2^20×4=16 MiB` of u32 counters. This is only a planning envelope: include SRS, PK, MSM buckets, NTT scratch, representation conversion and allocator peaks before admitting a job on the 32 GB GPU. Twenty private CPU histograms cost `20×4 MiB=80 MiB` per lane. Memory and transfers, not only arithmetic throughput, decide whether the GPU route wins.

**ESTIMATE — Preserve ordering and boundaries:** Finish witness commitments before theta; finish the two lookup-permutation commitments before beta/gamma; construct product vectors with z[0]=1, the correct last usable row and fresh blinded suffix; publish commitments to the transcript in the original sequence. Keep challenge-dependent caches proof-local. Copy-permutation column sets inherit `last_z`; independent range lanes do not. Use canonical field conversion to establish correctness before attempting zero-copy layouts. Deterministic table ordering can make the optimized path reproducible, but fixed RNG does **not** imply byte identity against the existing randomized-HashMap baseline. Sources for these obligations: `midnight-lookup-prover.md`, `midnight-permutation-prover.md`, `prior-loki10x.md`.

**ESTIMATE — Acceptance classes:** Arithmetic and permutation-construction changes can target the exact existing VK/SRS and unmodified CPU verifier. Table/layout changes require regenerated keys and verified stock-reader compatibility. LogUp/cq/Lasso change the proof relation/transcript expected by the lookup verifier; sharing PLONK terminology, KZG or BLS12-381 does not make them terminal-compatible. An inner protocol could be checked by an outer stock circuit, but that is a new recursive circuit and terminal key, with a measured wrapper cost and an eventual separately authorized deployment. Keep terminal Blake2b and the official SRS in all candidates. Sources: `prior-loki06.md`, `midnight-kzg-params.md`, `midnight-srs.md`.

## Coset tiles: the concrete extension to the earlier design

**SOURCE — Algebra hooks:** [0.8.3 domain](../../../raw/s5-quotient-ntt/midnight-083-domain.md) sets `n=2^k`, `N=2^extended_k`, `b=N/n`, uses order-three `ZETA`, and caches b vanishing inverses. [0.8.3 evaluation](../../../raw/s5-quotient-ntt/midnight-083-evaluation.md) accesses rotations as `(i+r*b) mod N`. Its numerator includes gates, permutation, lookups and trash. These are pinned 0.8.3 sources, distinct from mutable `main` and from an unverified Fenrir 0.8.2 build identity.

**ESTIMATE — Exact derivation, not a speed measurement:** Write `i=t+b*j`, `0≤t<b`, `0≤j<n`, `ω_n=ω_N^b`, and `s_t=ζω_N^t`. Then

```
A(ζω_N^(t+b*j)) = Σ[l=0..n−1] a_l s_t^l ω_n^(j*l).
(i+r*b) mod N = t + b*((j+r) mod n).
(ζω_N^(t+b*j))^n − 1 = s_t^n − 1.
```

**ESTIMATE — Consequence:** Each tile is a length-n NTT of rescaled coefficients; rotated reads are local wrapped reads, and vanishing division uses one constant per tile. Evaluate the complete ordered constraint accumulator for a tile, scatter `h[i]` into one N-element output, release tile intermediates, then perform the original length-N inverse NTT and inverse ζ scaling. Preserve the existing quotient truncation, splitting, blinding and commitments. This is a scheduling decomposition of the **same N points**, not a reduced evaluation domain. It assumes required argument polynomials already exist at LookupsArgued; it does not parallelize their earlier product construction.

**ESTIMATE — Memory:** With 64 live columns, n=2^20 and 32-byte scalars, full evaluations occupy `64×n×b×32 = 8 GiB (b=4)` or `16 GiB (b=8)`; one tile occupies 2 GiB. Retaining all coefficient inputs adds another 2 GiB; the final output costs 0.125/0.25 GiB, plus real twiddle/workspace/MSM reserves. With **128** live columns at b=8, full evaluations alone are 32 GiB; coefficients+one tile+output instead total `4+4+0.25=8.25 GiB` before reserves. Counts are hypothetical. At 1,135 columns even base coefficients alone are `1135/32=35.47 GiB`: coset tiling alone would still require column liveness or streaming on a 32 GB device.

**ESTIMATE — Arithmetic limit:** Replacing N-point extension by b transforms of n points changes nominal FFT butterfly counts by `log2(N)/log2(n)=22/20=1.10` or `23/20=1.15`, **before** b sets of coefficient scaling, scheduling and final scatter. These are not runtime speedups. Unlike ζ alone, `s_t` generally has no period three; tiles need powers of each shift. The pruned-DIF model in row 6 uses `(N/2)log2(n)+(b−1)n` multiplies versus `(N/2)log2(N)`, so much of the nominal saving may already exist in a pruned implementation.

**SOURCE — Check performed:** [coset-tiles-check.md](../../../raw/s5-quotient-ntt/coset-tiles-check.md) records 9 small BLS12-381 scalar-field cases and 2,744 rotated-value comparisons, exact extended-evaluation and known-quotient reconstruction equality, and wrong-stride negative controls. Reproducer: [check_coset_tiles.py](check_coset_tiles.py). This establishes the tested identities only; it does not validate actual Midnight roots, CUDA arithmetic, a real circuit or ledger acceptance.

## Degree and Pipelonk: two decisions now better constrained

**SOURCE — Degree threshold:** The [pinned constructor](../../../raw/s5-quotient-ntt/midnight-083-domain.md) chooses `N=next_power_of_two(n*(d−1))`; [constraint degree](../../../raw/s5-quotient-ntt/midnight-083-circuit.md) is the maximum of permutation, lookup, trash, gates and configured minimum. Prefer segmentation only where it removes memory pressure or hides measured residual transfers. It is not automatically the best choice for a fitting 32 GB workload. Avoid applying its abstract speedup to the four RTX 3090 cuSnark result or multiplying the two.

# s6-opening: multiopen and KZG opening — wave 1

## Verdict

**ESTIMATE — Prioritize the exact Midnight opening implementation: remove redundant work, then port its reductions, evaluations, division and two MSMs to a resident GPU path.** Keep its transcript schedule and terminal PCS unchanged. Study fflonk only as an inner-layer circuit-size optimization until it proves a reduction in parent/decider cost. There is no measured basis for a 10× end-to-end claim from this stage alone.

**SOURCE — Baseline:** the owner supplies Sherlock A102(k13)+A80(k12)→P(k20)→D(k20), and Fenrir four k17 leaves→N(k20)→D(k20), with ledger-9 accepting PLONK/KZG over BLS12-381, Blake2b and the official SRS. No s6 elapsed time or completed chain timing was supplied. [Raw baseline](../../../raw/s6-opening/task-baseline.md). The earlier study identifies published proofs 0.8.3 for Sherlock and 0.8.2 for recl9; this research fetched both published modules, but did not independently establish the running binaries' dependency/features/local patches. [Earlier study](../../../raw/s6-opening/prior-loki04.md), [0.8.3 source](../../../raw/s6-opening/midnight-kzg-0.8.3.md), [0.8.2 source](../../../raw/s6-opening/midnight-kzg-0.8.2.md).

**ESTIMATE — Ceiling:** normalize the recorded workload to `T=1`; let `q` be the fraction of its actual critical path spent in s6, `r` the s6 acceleration, and `o` added overhead as a fraction of baseline T. Then `S=1/(1-q+q/r+o)`. Even eliminating s6 entirely cannot produce 10× unless `q≥0.90`; at `r=20,o=0.01`, 10× needs `q≥0.91/0.95=95.79%`. This is a necessary coverage condition, not a timing measurement. For parallel children, use critical-path intervals rather than summing their overlapping times.

## What this adds or corrects relative to the earlier study

1. **SOURCE — PR #565 optimizes an existing fflonk implementation; it does not introduce the recorded size reduction.** Its table explicitly says sizes are unchanged by the PR. On one `zswap_output` k14 benchmark, KZG changes 590→415 ms; t=4 changes 924→536 ms. Within the new revision, t=4 is 536/415=1.292× the KZG prover cost, while VK bytes are 2258→578 and proof bytes 4384→3840. CPU model and recursive-circuit results are not specified in that table. [PR565](../../../raw/s6-opening/fflonk-pr565.md). **ESTIMATE:** VK shrink is `1-578/2258=74.40%`, not a 74.40% reduction in recursive proving work. The KZG bundle's `590/415=1.422×` cannot be assigned to opening alone: the PR also changes phase commitments and their representations. [Patch](../../../raw/s6-opening/pr565-files.md).
2. **SOURCE — Midnight's published opening protocol has an extra scalar-message/challenge boundary relative to the captured Axiom SHPLONK implementation.** Midnight writes F, squeezes x3, writes grouped polynomial evaluations, squeezes x4, and writes π. Axiom writes H, squeezes u, and writes its final opening commitment without that intervening evaluation-message round. [Midnight](../../../raw/s6-opening/midnight-kzg-0.8.3.md), [Axiom pinned source](../../../raw/s6-opening/axiom-shplonk.md). **ESTIMATE:** reuse arithmetic kernels, not Axiom's `create_proof` as a protocol replacement.
3. **SOURCE — A baseline-specific dead computation exists:** `multi_open` computes `v=eval_polynomial(final_poly,x3)` solely for `kate_division(final_poly-v,x3)`. `kate_division` produces n−1 outputs from the reversed coefficient iterator, so it never reads coefficient zero. [Opening](../../../raw/s6-opening/midnight-kzg-0.8.3.md), [arithmetic](../../../raw/s6-opening/midnight-arithmetic-0.8.3.md). **ESTIMATE:** call division directly on `final_poly.values` to avoid that evaluation and subtraction; preserve every grouped evaluation written before x4. Proof-byte equality is the deciding check, not this static observation.
4. **SOURCE — A concrete parallel division implementation is available:** Axiom uses an affine-pair Brent–Kung scan, with two n−1 scalar scratch arrays. It explicitly includes `field/alt_bn128.hpp`; this is BN254 code, not a ready BLS12-381 backend. [Scan](../../../raw/s6-opening/axiom-kate-division-header.md), [launcher](../../../raw/s6-opening/axiom-kate-division.md). No new opening-specific speedup was found in these source files.
5. **SOURCE — Fflonk's SRS requirement and challenge change are explicit:** `Fflonk<PCS,LOG2_T_MAX>` loads `k+LOG2_T_MAX`, exposes `max_k−LOG2_T_MAX`, and raises the evaluation challenge to `T_MAX=2^LOG2_T_MAX`. The source tests use `Fflonk<Kzg,2>` for t≤4. [Implementation](../../../raw/s6-opening/midnight-fflonk-pr565.md). **ESTIMATE:** t≤4 at k20 needs degree capacity below 2²², four times the monomial powers of k20. These must come from the same official SRS, not a locally generated replacement. **OPEN QUESTION:** availability, authenticated loading and actual memory cost of that official prefix on this host.

## Protocol boundary and opening schedule

**SOURCE — Published 0.8.2 and 0.8.3 KZG module bodies fetched here are identical.** They group polynomials by point sets and sort those sets by `(cardinality, original index)` for recursive verifier compatibility. The schedule in `multi_open` is:

```text
x1, x2 := existing transcript challenges
q_i := challenge-weighted combination for each ordered point set S_i
F := sum_i x2^i * quotient(q_i / product_{z in S_i}(X-z))
write commit(F)
x3 := challenge (with the configured truncation behavior, if any)
write each q_i(x3), in the existing order
x4 := challenge
G := existing weighted combination of q_i and F
write commit(quotient(G / (X-x3)))
```

**SOURCE:** `raw/s6-opening/midnight-kzg-0.8.3.md`, `raw/s6-opening/midnight-kzg-0.8.2.md`; the omitted remainders above are implicit in polynomial quotient computation. **ESTIMATE:** schedule GPU work around these three host-visible result boundaries: F, evaluation scalars, π. F and π of a single proof cannot be batched into one independent MSM call because π depends on the intervening challenges. Siblings' ready F values can be batched, then siblings' ready π values, without changing any proof. Parent work cannot start from unfinished child proof bytes.

**ESTIMATE — State ownership:** instrument Quotiented→Opened around this exact reduction/opening path; Opened→Proved includes remaining serialization and error propagation. Define the timer boundary explicitly because current application labels may place evaluation writes differently. Do not count earlier quotient construction as a newly accelerated s6 operation, or hide later verification and ledger latency in a narrower timer.

**SOURCE — The Axiom scan realizes** `q_j=a_(j+1)+z*q_(j+1)` using the associative composition `(a,b)∘(c,d)=(a*c,a*d+b)`. [Kernel](../../../raw/s6-opening/axiom-kate-division-header.md). **ESTIMATE:** adapt this recurrence to BLS12-381 and fuse the final polynomial combination into the scan's input reads where profitable. For fflonk's sparse divisor `X^t-x`, the recurrence splits into t residue classes, permitting t shorter independent scans; this is an algebraic design extension, not a measured feature of the captured backend. Ordinary dense vanishing polynomials need a different comparison; one-pass CPU division is not automatically the best GPU algorithm.

## Inner fflonk versus terminal fflonk

**SOURCE — PR575 supplies the recursive verifier trait implementation, merged October 15, 2026; it supplies no row, constraint, k or proving-time benchmark.** PR565 was merged October 14. The original fflonk paper describes a verifier/prover tradeoff and reports roughly tripling prover cost for its construction, unlike the newer Midnight k14 implementation's 1.292× t4 cost. These are different implementations/workloads. [PR575](../../../raw/s6-opening/fflonk-pr575.md), [PR565 metadata](../../../raw/s6-opening/pr565-metadata.md), [paper](../../../raw/s6-opening/fflonk-paper.md).

**ESTIMATE — Break-even for an inner switch:** let L be time spent producing switched proofs, U time spent proving their outer verifier(s), p the measured inner prover multiplier, d the measured fractional outer saving, and K/R amortized extra key/precompute cost per run. Improvement requires `U*d > L*(p−1)+K/R`. Ignoring K, t4 at the published p needs d>7.29% when U=4L, or d>29.16% when U=L. Measure p anew for each actual circuit. Test children-only first, then P/N as an inner proof consumed by D; the latter may shrink D but changes a much more expensive inner prover.

**ESTIMATE — Fixed-k caveat:** fewer verifier commitments may reduce rows without changing k or dominant column/FFT counts. A packing win becomes much more compelling if it actually permits a smaller domain or fewer columns. No row count can be inferred from VK bytes. For illustration, if a fraction a of a parent is verifier work and that portion shrinks by v, row savings are at most a*v; crossing a half-domain boundary needs sufficient initial slack plus those savings, not merely v≈75%.

**ESTIMATE — Terminal policy:** keep D's accepted proof encoding, Blake2b transcript and PCS fixed. A new D circuit for inner fflonk can still emit accepted KZG proofs, but typically needs a new VK and allowed contract registration/redeployment. Ledger-9 protocol acceptance and acceptance by an already-deployed contract VK are separate conditions. If that VK is immutable for this task, restrict the experiment to proof-preserving arithmetic changes. No deployment or ledger transaction was attempted here.

## Memory and batching budget

**ESTIMATE — Scalar storage:** a k20 scalar vector at 32 bytes is `2²⁰*32=32 MiB`. A scan's two scratch vectors are about 64 MiB; input+output+scratch about 128 MiB before F, grouped q_i, polynomial columns or MSM buckets. Four such scan workspaces alone use about 512 MiB; this does not imply four whole k20 proofs fit in 32 GB. [Scratch design source](../../../raw/s6-opening/axiom-kate-division.md).

**ESTIMATE — SRS storage:** assuming 96-byte uncompressed BLS12-381 G1 affine points, k20 bases occupy 96 MiB; fourfold precomputation occupies 384 MiB before overhead. A t4 k20 packing domain may require 2²² powers, or 384 MiB of affine bases before additional transformed bases/caches. Actual device layouts and allocation peaks must be measured. Do not compare compressed 48-byte storage to uncompressed device residency.

**SOURCE — ICICLE supports batch MSM with shared or distinct bases and documents precompute/index/bucket memory tradeoffs.** Its illustrative tuning table uses BLS12-377 on RTX3090 Ti, not BLS12-381 on RTX5090. The k24 table's 232→199 ms uses increased precomputation and memory; it establishes neither a k20 benefit nor suitability of those settings here. [API](../../../raw/s6-opening/ingonyama-msm-api.md). **ESTIMATE:** sweep batch 1/2/4 and precompute 1/2/4 under measured 28 GiB GPU and 80 GiB host high-water targets, leaving headroom within the supplied 32 GB/90 GB host. Treat these as experiment targets subordinate to factory caps. Do not shorten scalars based on an unrelated workload.

- **OPEN QUESTION — E1:** If s6 is under 10% of the chain critical path, even perfect elimination caps the overall gain at `1/.9=1.111×`; route the 10× objective to other stages and retain only cheap improvements here.
- **OPEN QUESTION — E2:** If the exact resident opening pipeline shows ≥4× stage acceleration with proof identity and tolerable memory, implement it; if data copies/challenge waits dominate, broaden residency into adjacent stages rather than extrapolating MSM ratios.
- **OPEN QUESTION — E3:** If inner fflonk crosses k20→k19 (or removes costly columns) and beats `U*d > L*(p−1)+K/R`, it becomes the leading structural option. If rows/k stay unchanged, prioritize arithmetic instead.
- **OPEN QUESTION — Official SRS:** insufficient authenticated degree capacity, or an immutable deployed D VK, can disqualify the fflonk branch while leaving arithmetic changes viable.
- **OPEN QUESTION — Accumulation inventory:** evidence of repeated terminal pairings would promote accumulator batching; evidence of one existing accumulated decision leaves it at 1×.
- **OPEN QUESTION — FK20 workload:** many openings of the same retained polynomial, rather than unrelated child proofs, would justify revisiting amortized preprocessing.

## New conclusions beyond the earlier studies

**ESTIMATE — Terminal placement has sharper thresholds than arity alone.** Using the earlier fitted homogeneous-node model `R(b)=190727+191842b`, the existing pairing adds 316833 rows. With k20 usable capacity 1048569, a binary fused terminal has **891244** rows and **157325** rows of modeled glue headroom. Ternary fusion has **1083086** rows and needs **34517** rows removed, or **4.505% of its verifier**; quaternary fusion needs **226359**, or **23.626%**. This makes a **2×8-tx partition or a slightly improved 3-child terminal** worth testing before attempting a large general recursion rewrite. These sums are estimates: reconfiguration, shared operations, tables and glue can move them.

**ESTIMATE — A flat k21 terminal can be worse despite one fewer proof.** Quaternary fusion gives **1274928** rows and k21. Its domain work is 2 k20 units, equal to N(k20)+D(k20); FFT work is **2.1** rather than 2 units, **5% more**, if widths/degree match. It can still save synthesis or other work, but “delete one layer” is not enough to forecast a latency win. For existing four leaves, a balanced binary tree adds three internal proofs; the table floor prevents rewarding its smaller advice count.

**SOURCE — The table floor and pairing floor are implementation-specific.** Historical node table extent is **1032465** at arities 2–4, while the isolated residue gadget including subgroup checks has **316833** rows. ## Verified and Consumed: what must survive

**SOURCE —** The existing local A3 test verifies a parent with a Poseidon transcript; its circuit produces 28 public lanes including the carried obligation. A4 produces a Blake2b outer proof, verifies it using the ledger verifier, round-trips the key through tagged deserialization, and mutates public lanes/proof bytes. Its installed-key mode explicitly pins the parent VK. [sherlock_parent-local.md](../../../raw/s7-recursion/sherlock_parent-local.md), [sherlock_terminal-local.md](../../../raw/s7-recursion/sherlock_terminal-local.md).

**ESTIMATE — Required preservation contract:**

- **Verified:** distinguish a checked proof with a deferred accumulator from a fully decided statement. Pin child VK/relation, ordered public inputs, transcript domains, canonical encodings and official SRS identity. Host-side success does not discharge a circuit obligation.
- **Consumed:** enforce the transition chain and ordered child coverage exactly once per aggregate. Bind program/context, pre/mid/post state, heights, work/count, instance ID, batch number, ordered trace and communication opening. Carry and combine child accumulators in a node-of-nodes design; checking only each child's outer proof is incomplete.
- **Terminal:** retain ordinary PLONK/KZG over BLS12-381, the Blake2b outer transcript and official SRS under ledger-9's supported architecture. A different relation needs a new registered VK. A custom gate that the stock reader cannot reconstruct is not repaired merely by uploading a VK.
- **Settlement:** bind predecessor state and replay/nullifier or batch-consumption state at the anchor. Proof aggregation order is not the same as ledger replay protection. Direct fusion proves equivalent transition semantics; it must not claim it authenticated particular child proof bytes that were never produced.

## What would change the verdict

1. **OPEN QUESTION —** A complete fused fixed-pair terminal at k15, with equivalent semantics and exact ledger-reader acceptance, measures ≤one tenth of a matched chain including witness, setup policy, proving, serialization and independent verification. That converts the leading estimate into evidence. Failure to fit k16 or an unscaled fraction above 4% would weaken the conservative domain-only 10× case.
2. **OPEN QUESTION —** Actual verifier/table measurements show a repaired fflonk or MSM implementation reduces four-child verifier work by ≥23.626% plus glue, allowing a k20 fused terminal. This would promote rank 3; shrinking VK bytes alone would not.
3. **OPEN QUESTION —** A complete folding bridge, including final commitment openings, primary/secondary state and field conversions, fits the **61.7–125.7 s illustrative wrapper budgets**. This would justify a broader NeutronNova/MicroNova implementation effort. A tiny folding-step benchmark alone would not.
4. **OPEN QUESTION —** Real 16-tx witnesses are unavailable to one prover. That disqualifies witness fusion and FLIP for that deployment, leaving opaque-proof aggregation and implementation acceleration as the relevant comparison.
5. **OPEN QUESTION —** A new matched CPU baseline, measured phase shares, or reliable 5090 kernel integration changes the model. No published GPU, Ethereum-gas, SHA-256-fold or credential-proving ratio has been transferred to Sherlock here.

## Capacity certificate: what 10× actually requires

**ESTIMATE —** For a selected workload and fixed scheduling policy, let C be residual CPU core-seconds per batch, c productive cores, G serialized GPU compute service, Q serialized controller/verification service, P copy-engine service, L the no-queue dependency-path lower bound, F settlement/finality wait, and W the maximum legal number of unfinished batches. If a window slot remains occupied until finalization, the steady interval obeys:

```text
I >= max(C/c, G, Q, P, (L+F)/W, 1/ledger_acceptance_rate)
speedup <= T_reference / I
```

**ESTIMATE —** This is a necessary bound, not an executable schedule. If compute kernels overlap, replace G with a measured effective service bound under that overlap policy; adding overlapping kernel times is invalid. If H2D/D2H use independent engines, bound each separately. Resource demand from rejected work, retransfers, retries and speculative invalidations must be added. The ledger rate is not measured here. If no finite batch window is imposed, F still increases user latency even when it does not limit steady throughput.

**ESTIMATE —** Reusing only the earlier model's *hypothetical* `.25 CPU wall share at two cores`, `.75 GPU share /10`, `.01 serialized control` produces C=808.646 core-s, G=121.297 s, Q=16.173 s and `L=.335×(max(leaves)+N+D)=503.515 s`. With 16 productive cores, W=3 already limits throughput to 9.636×; W≥4 is necessary to cross 10× against historical Fenrir. Add an assumed 300-second finality wait and W≥5 becomes necessary; W=4 caps at 8.051×. None of the phase shares or the 300-second wait is measured. Reproduce these falsifiable bounds with [BOUND_AUDIT.md](BOUND_AUDIT.md).

**ESTIMATE —** If tuned CPU already doubles historical throughput, even infinite buffering leaves the assumed G=121.297 s a ceiling of `1617.292/(2×121.297)=6.667×` against that CPU denominator. A 10× claim then requires GPU service ≤80.865 s, and any serial control, copy or ledger service must also fit. This is why bigger queues cannot rescue insufficient service capacity.

**OPEN QUESTION —** How many batches are truly independent? Distinguish (a) immutable independent statements, (b) descendants whose input state is deterministically known but not finalized, and (c) descendants that require predecessor settlement data. Case (c) can force W=1. For case (b), verify lineage before using outputs and invalidate all descendants on mismatch. Retry losses reduce useful throughput; if an assumed invalidation fraction q=.10 consumes full service, useful rate is only `.9×raw_rate`, so a raw 10× becomes 9×.

## Admission and Queued/Finalized ownership

**ESTIMATE — Proposed policy:** At Queued, store a small immutable job descriptor: workload/relation identity, ordered child identities, public statement digest, expected predecessor state, PK/VK/SRS pins, transcript mode, attempt number and arrival time. Do not materialize an unbounded queue of witnesses. Release a parent only after the required child artifacts pass the pinned independent verifier. Give each proof its own RNG/transcript state. These are correctness requirements for the experiment, not claims that the current code implements them.

**ESTIMATE — Proposed byte accounting:** Maintain separate host and device totals: shared resident keys counted once per distinct shape; each job's retained buffers; temporary next-phase workspace; pinned transfer ring; allocator reserved-but-unused bytes; and safety margin. Begin with one heavy GPU workspace and two 64-MiB pinned buffers. Proposed research ceilings are `min(64 GiB, .8×initial available host RAM)` and `min(24 GiB, .8×initial free VRAM)`, lowered whenever a factory cap is tighter. Reserve enough next-phase space for at least one dependency-ready job to finish and release memory. If that reservation fails, stop admitting witnesses, not completion work. A banker's-style safe-sequence check or one globally reserved completion workspace avoids the deadlock where every paused witness owns memory and none can allocate its next phase.

**SOURCE —** The earlier ~30.7-GB two-proof figure derives from host RSS observations/estimates, not a measured CUDA working set (`raw/s9-orchestration/prior-astra3-review.md`, `prior-verdict.md`). **ESTIMATE —** It says nothing about whether two device proofs fit 32 GB. The prior estimate of two decoded heavy keys is 17.625 GiB (`prior-astra3.md`), already above a decimal-16-GB cap. Factory B7 and wider-host throughput must remain distinct qualification regimes; 90 GB installed RAM does not waive B7.

**SOURCE —** NVIDIA's allocator can retain unused device memory in pools; its default release threshold can discard that cache at synchronization (`raw/s9-orchestration/cuda-async-allocator.md`). **ESTIMATE —** Count reserved and live bytes separately. Do not copy the article's unlimited-retention example into a bounded scheduler. Cross-stream free must wait for every consumer event; keys and buffers cannot be recycled merely because a job was cancelled.

**ESTIMATE — Proposed completion semantics:** A locally verified proof is a durable intermediate result, not a stagenet Finalized result. Record enqueue, admission, proof-ready, locally-verified, submitted, included and finalized timestamps as distinct metadata. For local-only experiments, report “locally verified,” never ledger-finalized. Mark Finalized only after the existing chain's required finality/readback rule passes. Persist verified artifact identity before releasing dependent jobs; deduplicate late retry results by statement/attempt and make ledger submission idempotent under the existing transaction rules. Checkpoint public proof artifacts only; do not publish private witnesses or RNG state.
