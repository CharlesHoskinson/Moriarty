# s4-lookups — wave 1 findings

**ESTIMATE — Verdict:** Prioritize **structured table-index permutation construction, followed by parallel inversion/product scans**. These can preserve the current lookup equations, keys, transcript and official SRS. A large lookup-preparation speedup is credible enough to test; **10× end-to-end is not supported by the available evidence**. Shrinking tables alone cannot reduce the recorded k20 domain. Protocol replacements belong behind a separately validated inner verifier, not in the terminal ledger proof.

**SOURCE — Scope and provenance:** Owned transition: `Committed → LookupsArgued`. Nine leads were investigated in [PLAN.md](PLAN.md). The requested earlier study was found at `../loki/nodes/loki-06-recursive-circuit-cost.md`, not the supplied `10x/` path. Captures: `raw/s4-lookups/prior-loki06.md`, `prior-loki10x.md`, `stage-catalog.md`. All raw paths below are relative to the research root. Recorded timings are historical, not new host measurements. The only executed experiment was the small algebra/row model in [check_models.py](check_models.py); its output is [model-results.json](model-results.json), also captured as `raw/s4-lookups/toy-model-results.md`.

**SOURCE — Version boundary:** The earlier study distinguishes Sherlock/Moriarty proofs 0.8.3 from recl9 proofs 0.8.2 and ledger dependencies. This report directly inspected the public **0.8.3** lookup and permutation code; it does not assert that recl9's pinned implementation is identical. The source catalog also records newer Sherlock A3 times of 316–382 s and A4 about 325 s, alongside the older 882.6 s parent receipt. These are separate runs and must not be mixed into one measured baseline. Sources: `prior-loki06.md`, `prior-loki10x.md`, `stage-catalog.md`.

## What advances the earlier study

**SOURCE — A matching preprocessing precedent, with an important exclusion:** cuSnark's permutation-generation page describes hashing values, counting, prefix-scanning counts, emitting groups, and scanning/scattering leftovers. It reports 39.32 s CPU versus 3.94 s on one RTX4090 at 2^24 rows and one lookup. It explicitly says this implementation was **not used** in the earlier benchmark suite. Consequently the wide k20 suite's “Generate Lookups” 59.63→56.84 s (1.05×) does not refute this specialized construction. The wide circuit has **1,135 columns** and uses an EPYC 7702 / four RTX3090 system; neither result is a Sherlock or 5090 measurement. Sources: `cusnark-permutation.md`, `cusnark.md`.

**SOURCE — ICICLE is supporting evidence for resident arithmetic, not a product-scan number:** The v2 post benchmarks on RTX4080/i9-13900k, includes a simple 8-bit lookup workload with redundant constraints inflating degree, and advertises up to 25× plus vector-operation gains at 2^22. Its lookup-constraint evaluation work overlaps quotient construction. It supplies no directly matching BLS12-381 k20 grand-product timing. The polynomial-inversion-only cuSnark table is nearly flat for lookup generation (57.99→57.92 s), another reason not to infer full-proof benefit from an inverse kernel. Sources: `icicle-halo2-v2.md`, `cusnark-inversion.md`.

**SOURCE — Three independent serial/preprocessing targets exist:** 0.8.3 `permute_expression_pair` calls `sort`, builds `HashMap<F,u32>`, and fills leftover table entries in randomized map order. `commit_product` parallelizes denominator/numerator construction but calls the sequential `ff` batch-inversion iterator and a serial product `scan`. Copy-permutation products similarly use batch inversion and a row loop, with `last_z` carried between column sets. Sources: `midnight-lookup-prover.md`, `ff-batch.md`, `midnight-permutation-prover.md`.

**ESTIMATE — Direct-ID construction suitable for the range table:** Build offsets for the actually loaded tags, with a tuple ID `offset[tag]+value`. Validate the exact raw lookup expressions, including selectors and the disabled `(0,0)` row; do not infer an ID from the theta-compressed field value. Count inputs by ID and emit one block per used ID. At each block head, put one corresponding table entry into S′; fill all remaining positions with unused table entries, retaining their multiplicities and padding. This produces permutations A′ and S′ without requiring numerical field order. For generic lookups, use the existing algorithm or a separately collision-safe generic implementation. The ID metadata is a prover optimization, not a new verifier assumption. Evidence motivating this construction: `midnight-pow2range.md`, `midnight-lookup-prover.md`, `halo2-lookup.md`.

**ESTIMATE — Algebraic reason:** For each group, either `A′[i]=S′[i]` at its head or `A′[i]=A′[i−1]` internally. Thus the existing adjacency equation `(A′−S′)(A′−A′prev)=0` holds, with A′[0]=S′[0]. Exact preservation of both multisets supplies the existing grand-product equality. If distinct raw tuples collide after theta compression, reserving one table entry per raw tuple still satisfies those equations; no inverse map from a compressed value is needed. This reasoning does not justify dropping any opening, boundary, integer range constraint or transcript challenge.

**SOURCE — Executed model, narrowly scoped:** The seven-element-field model passed **567** permutation/adjacency cases (including **162** compression-collision cases), **11,660** nonzero-denominator product cases, three invalid-tuple rejections and **390** block-scan checks including zeros. It explicitly skipped **16,123** exceptional challenge cases for the rational-product test. This is an algebra sanity check, not a security proof, zero-denominator acceptance claim, BLS arithmetic test, or ledger test. Source: `toy-model-results.md`; reproduce with `python3 clusters/s4-lookups/wave-1/check_models.py`.

**SOURCE — Cap 17 is a more informative first candidate than cap 15:** The exact recurrence from the source planner, with four same-tag lanes per row, yields the following local model. Sources: `midnight-limb-planner.md`, `toy-model-results.md`.

| SOURCE — cap | 56-bit decomposition | 64-bit | 128-bit | 255-bit | Bounds 1…255 retaining cap19 row count |
|---|---:|---:|---:|---:|---:|
| 19 | 1 | 1 | 2 | 4 | 255 |
| 17 | 1 | 1 | 2 | 4 | 206 |
| 16 | 1 | 1 | 2 | 5 | 170 |
| 15 | 1 | 2 | 3 | 5 | 143 |

**ESTIMATE — Interpretation:** These are decomposition-row counts, not whole-chip/circuit row counts. In particular, `ceil(255/(4×16))=4` is misleading: four rows of at most four equal-width limbs cannot represent an exact 255-bit bound with cap16 in this planner. A weighted histogram of actual bounds is required. Prefer global tag selection/tie-breaking among equal-row plans, then test caps; do not simply remove unused tags, because the current loader already skips them. Node k20 has only `(1048576−958095)/958095≈9.44%` advice headroom before unusable rows, so extra decomposition rows can make a “smaller-table” design worse.

## Integration and acceptance constraints

**SOURCE — Existing kernels are primitives:** sppark has `Multiply`/`prefix_op` and a BLS12-381 scalar field type (`fr_t`, 255-bit modulus); its batch-inversion header is a local sequential forward/backward template that preserves zeros, **not** a ready device-wide inversion kernel. A GPU implementation must organize many such chunks plus carries. The captured source tree is `69440fd55006489431fef54f0ee45f2b67db7c75`; raw Markdown extraction is reference text, not buildable source. No CUDA13/5090 build was performed. Sources: `sppark-tree.md`, `sppark-prefix.md`, `sppark-bls381.md`, `helper2-batch-inversion.md`.

**ESTIMATE — Memory envelope:** One scalar vector at k20 is `2^20×32=32 MiB`. Eight scratch vectors × four lanes = **1 GiB**, plus `4×2^20×4=16 MiB` of u32 counters. This is only a planning envelope: include SRS, PK, MSM buckets, NTT scratch, representation conversion and allocator peaks before admitting a job on the 32 GB GPU. Twenty private CPU histograms cost `20×4 MiB=80 MiB` per lane. Memory and transfers, not only arithmetic throughput, decide whether the GPU route wins.

**ESTIMATE — Preserve ordering and boundaries:** Finish witness commitments before theta; finish the two lookup-permutation commitments before beta/gamma; construct product vectors with z[0]=1, the correct last usable row and fresh blinded suffix; publish commitments to the transcript in the original sequence. Keep challenge-dependent caches proof-local. Copy-permutation column sets inherit `last_z`; independent range lanes do not. Use canonical field conversion to establish correctness before attempting zero-copy layouts. Deterministic table ordering can make the optimized path reproducible, but fixed RNG does **not** imply byte identity against the existing randomized-HashMap baseline. Sources for these obligations: `midnight-lookup-prover.md`, `midnight-permutation-prover.md`, `prior-loki10x.md`.

**ESTIMATE — Acceptance classes:** Arithmetic and permutation-construction changes can target the exact existing VK/SRS and unmodified CPU verifier. Table/layout changes require regenerated keys and verified stock-reader compatibility. LogUp/cq/Lasso change the proof relation/transcript expected by the lookup verifier; sharing PLONK terminology, KZG or BLS12-381 does not make them terminal-compatible. An inner protocol could be checked by an outer stock circuit, but that is a new recursive circuit and terminal key, with a measured wrapper cost and an eventual separately authorized deployment. Keep terminal Blake2b and the official SRS in all candidates. Sources: `prior-loki06.md`, `midnight-kzg-params.md`, `midnight-srs.md`.

## What would change the verdict

- **OPEN QUESTION —** Does a pinned per-phase profile show enough s4 share to matter? Measure the actual fraction and apply `G(p,g)` before expanding the work. A preparation speedup with <5% chain contribution is a different priority from one removing a dominant serial stage.
- **OPEN QUESTION —** Does indexed grouping deliver ≥2× transfer-inclusive preparation and a repeatable ≥5% whole-proof improvement, with the unchanged CPU/ledger verifier accepting it? That promotes rank 1 from an algebra-backed lead to an implementation candidate.
- **OPEN QUESTION —** Does a 20-core CPU implementation erase most of the GPU advantage at k20? That favors the simpler CPU route; a GPU kernel-only win is insufficient.
- **OPEN QUESTION —** Can a joint change get both actual advice and table extents plus unusable rows below k19, without adding enough columns/lookups/degree to erase the gain or enlarge D? Only that result justifies the smaller-domain performance model.
- **OPEN QUESTION —** Are actual queries sparse relative to the table, and does full cq/LogUp/Lasso verifier/SRS accounting fit the boundary? The cq and GKR PDF fetches returned HTTP403 (`cq-full.md`, `logup-gkr-full.md`); the captured abstracts establish complexity claims but not a complete protocol/SRS audit. Those gaps can change the protocol ranking, not establish acceptance by themselves.
