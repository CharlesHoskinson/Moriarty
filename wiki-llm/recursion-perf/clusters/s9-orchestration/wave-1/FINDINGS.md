# s9-orchestration, wave 1 — scheduling, memory and hardware

**ESTIMATE — Verdict:** A 10× end-to-end result is not established by scheduling evidence. The best next investment is a measured, phase-aware scheduler with a bounded number of unfinished batches and memory reserved for forward progress. It can recover idle CPU/GPU capacity without changing ledger cryptography, but it cannot remove the parent→decider dependency. Distributed leaf proving has a particularly small latency ceiling. Treat 10× sustained throughput as a conditional target requiring faster arithmetic/witness work as well as scheduling.

**SOURCE — Evidence status:** This pass fetched public sources, audited existing records and ran only the arithmetic in [bound_audit.py](bound_audit.py); it ran no prover, GPU benchmark, deployment or settlement. All `raw/...` paths below are relative to the research root, `wiki-llm/recursion-perf/`. SOURCE identifies an observed source statement, not necessarily a measurement on this host. ESTIMATE identifies arithmetic, conditional designs and engineering allowances. OPEN QUESTION identifies a missing measurement or unqualified implementation. [LEADS.md](LEADS.md) records ten concrete research leads.

**SOURCE —** Historical Fenrir's `163.6306+867.2798+586.3817=1617.2920 s` is a sum of proving-stage observations; `LOKI-10X.md` calls it 2.23 batches/hour (`raw/s9-orchestration/prior-astra3.md`, `prior-verdict.md`). **ESTIMATE —** Its arithmetic rate is `3600/1617.292=2.226 batches/hour`, and a 10× reference interval is 161.729 seconds. It is a different workload/version from B3. B3's corresponding 10× *whole-command* endpoints are 92.039–128.753 seconds; neither endpoint can be assigned to Fenrir's GPU phases.

**SOURCE —** The earlier 7.4–9.7× result adjusts a queue model using node/decider whole-invocation averages of 2.69/4.01 cores (`raw/s9-orchestration/prior-astra3-review.md`). Its own caveat says those are not measurements of CPU-phase shares. **ESTIMATE —** Inferring witness CPU demand from those averages is not justified: accelerating a parallel MSM could leave a nearly serial witness, or the reverse. A single CPU fraction also cannot describe repeated CPU↔GPU visits around transcript challenges. The replacement below uses measured service demands and a legal batch window, rather than treating five host slots as sufficient proof of feasibility.

## Capacity certificate: what 10× actually requires

**ESTIMATE —** For a selected workload and fixed scheduling policy, let C be residual CPU core-seconds per batch, c productive cores, G serialized GPU compute service, Q serialized controller/verification service, P copy-engine service, L the no-queue dependency-path lower bound, F settlement/finality wait, and W the maximum legal number of unfinished batches. If a window slot remains occupied until finalization, the steady interval obeys:

```text
I >= max(C/c, G, Q, P, (L+F)/W, 1/ledger_acceptance_rate)
speedup <= T_reference / I
```

**ESTIMATE —** This is a necessary bound, not an executable schedule. If compute kernels overlap, replace G with a measured effective service bound under that overlap policy; adding overlapping kernel times is invalid. If H2D/D2H use independent engines, bound each separately. Resource demand from rejected work, retransfers, retries and speculative invalidations must be added. The ledger rate is not measured here. If no finite batch window is imposed, F still increases user latency even when it does not limit steady throughput.

**ESTIMATE —** Reusing only the earlier model's *hypothetical* `.25 CPU wall share at two cores`, `.75 GPU share /10`, `.01 serialized control` produces C=808.646 core-s, G=121.297 s, Q=16.173 s and `L=.335×(max(leaves)+N+D)=503.515 s`. With 16 productive cores, W=3 already limits throughput to 9.636×; W≥4 is necessary to cross 10× against historical Fenrir. Add an assumed 300-second finality wait and W≥5 becomes necessary; W=4 caps at 8.051×. None of the phase shares or the 300-second wait is measured. Reproduce these falsifiable bounds with [BOUND_AUDIT.md](BOUND_AUDIT.md).

**ESTIMATE —** If tuned CPU already doubles historical throughput, even infinite buffering leaves the assumed G=121.297 s a ceiling of `1617.292/(2×121.297)=6.667×` against that CPU denominator. A 10× claim then requires GPU service ≤80.865 s, and any serial control, copy or ledger service must also fit. This is why bigger queues cannot rescue insufficient service capacity.

**OPEN QUESTION —** How many batches are truly independent? Distinguish (a) immutable independent statements, (b) descendants whose input state is deterministically known but not finalized, and (c) descendants that require predecessor settlement data. Case (c) can force W=1. For case (b), verify lineage before using outputs and invalidate all descendants on mismatch. Retry losses reduce useful throughput; if an assumed invalidation fraction q=.10 consumes full service, useful rate is only `.9×raw_rate`, so a raw 10× becomes 9×.

## Admission and Queued/Finalized ownership

**ESTIMATE — Proposed policy:** At Queued, store a small immutable job descriptor: workload/relation identity, ordered child identities, public statement digest, expected predecessor state, PK/VK/SRS pins, transcript mode, attempt number and arrival time. Do not materialize an unbounded queue of witnesses. Release a parent only after the required child artifacts pass the pinned independent verifier. Give each proof its own RNG/transcript state. These are correctness requirements for the experiment, not claims that the current code implements them.

**ESTIMATE — Proposed byte accounting:** Maintain separate host and device totals: shared resident keys counted once per distinct shape; each job's retained buffers; temporary next-phase workspace; pinned transfer ring; allocator reserved-but-unused bytes; and safety margin. Begin with one heavy GPU workspace and two 64-MiB pinned buffers. Proposed research ceilings are `min(64 GiB, .8×initial available host RAM)` and `min(24 GiB, .8×initial free VRAM)`, lowered whenever a factory cap is tighter. Reserve enough next-phase space for at least one dependency-ready job to finish and release memory. If that reservation fails, stop admitting witnesses, not completion work. A banker's-style safe-sequence check or one globally reserved completion workspace avoids the deadlock where every paused witness owns memory and none can allocate its next phase.

**SOURCE —** The earlier ~30.7-GB two-proof figure derives from host RSS observations/estimates, not a measured CUDA working set (`raw/s9-orchestration/prior-astra3-review.md`, `prior-verdict.md`). **ESTIMATE —** It says nothing about whether two device proofs fit 32 GB. The prior estimate of two decoded heavy keys is 17.625 GiB (`prior-astra3.md`), already above a decimal-16-GB cap. Factory B7 and wider-host throughput must remain distinct qualification regimes; 90 GB installed RAM does not waive B7.

**SOURCE —** NVIDIA's allocator can retain unused device memory in pools; its default release threshold can discard that cache at synchronization (`raw/s9-orchestration/cuda-async-allocator.md`). **ESTIMATE —** Count reserved and live bytes separately. Do not copy the article's unlimited-retention example into a bounded scheduler. Cross-stream free must wait for every consumer event; keys and buffers cannot be recycled merely because a job was cancelled.

**ESTIMATE — Proposed completion semantics:** A locally verified proof is a durable intermediate result, not a stagenet Finalized result. Record enqueue, admission, proof-ready, locally-verified, submitted, included and finalized timestamps as distinct metadata. For local-only experiments, report “locally verified,” never ledger-finalized. Mark Finalized only after the existing chain's required finality/readback rule passes. Persist verified artifact identity before releasing dependent jobs; deduplicate late retry results by statement/attempt and make ledger submission idempotent under the existing transaction rules. Checkpoint public proof artifacts only; do not publish private witnesses or RNG state.

## Why the external results do not establish this speedup

**SOURCE —** [StarPU](https://starpu.gitlabpages.inria.fr/features.html) supports performance-model and locality-aware task placement, transfers, asynchronous tasks and memory reuse (`raw/s9-orchestration/starpu-features.md`). **ESTIMATE —** Borrow those mechanisms, not its cluster-scale claims or an extra mandatory runtime for public Moriarty developers. On one GPU, phase byte peaks and the age of the oldest unfinished batch matter more than simply increasing ready-queue depth.

**SOURCE —** [CUDA graph launch measurements](https://developer.nvidia.com/blog/constant-time-launch-for-straight-line-cuda-graphs-and-other-performance-enhancements/) use a Xeon Silver 4208 and RTX 3060, comparing CUDA 11.8/12.6 straight-line graphs. Repeat-launch CPU overhead approaches 2.5 µs plus roughly 1 ns/node, while first upload still has graph-size cost (`raw/s9-orchestration/cuda-graphs.md`). **ESTIMATE —** Replay only stable arithmetic regions; transcript challenges remain dependencies and each launch needs current buffers/scalars. Launch reductions cannot be multiplied by arithmetic speedups.

**SOURCE —** [Green contexts](https://developer.nvidia.com/blog/control-how-your-gpu-shares-work-with-green-contexts/) expose explicit SM/workqueue partitioning, with Driver API support described from CUDA 12.4 and Runtime API from 13.1 (`raw/s9-orchestration/cuda-green-contexts.md`). Stream priority does not preempt running blocks (`cuda-streams.md`). **OPEN QUESTION —** CUDA “13.x” alone does not prove the installed runtime, driver and WSL path support the needed API or that MSM/NTT bandwidth is isolated. Measure the actual configuration before promising latency isolation.

**SOURCE —** DIZK uses Groth/R1CS and a custom 256-bit Barreto–Naehrig curve; its distributed experiments use ten 32-vCPU/244-GiB EC2 r3.8xlarge machines for up to 128 executors, or twenty for 256. The serial comparator uses a 2-vCPU/15-GiB r3.large (`raw/s9-orchestration/dizk-paper-excerpts.md`). **ESTIMATE —** This is evidence for partitioning techniques, not a same-resource 100× gain for k20 PLONK on one 5090. Network cost at this workload remains unmeasured.

**SOURCE —** zkBridge's abstract reports a Cosmos→Ethereum prototype with proof generation under 20 seconds (`raw/s9-orchestration/zkbridge.md`); that capture does not establish cluster size or a Midnight-compatible wrapper. Boundless's public callback uses `IRiscZeroVerifier`, image identity and receipt claims, while its offer type has lock and request deadlines (`boundless-verifier.md`, `boundless-offer.md`). **ESTIMATE —** Native worker dispatch can copy lifecycle ideas. Neither a market receipt nor an unrelated fast proof replaces the ledger-9 terminal.

## What would change the verdict

1. **OPEN QUESTION —** Does E1 measure a complete matched-workload service vector satisfying every 10× capacity inequality, including unchanged terminal verification and any ledger-rate cap? If G alone exceeds the target, prioritize arithmetic work; if C/c exceeds it, prioritize witness/CPU work; if W is too small, more workers are ineffective.
2. **OPEN QUESTION —** Does E2 sustain ≥10× the *tuned CPU* completed-work rate, with bounded queue depth, unchanged workload/key identities, zero swap/OOM and all stock-verifier checks passing? Report cold/first-batch/p95 latency separately. A 10× result only against the old serial sum does not meet that stronger claim.
3. **OPEN QUESTION —** Does phase-aware memory admission fit the required W and still guarantee forward progress within the applicable cap? OOM recovery, speculative invalidation and cache misses must be in the denominator, not discarded.
4. **OPEN QUESTION —** Does E3 reveal substantial allocation/launch/blocking overhead on this exact backend? If it is below 1%, graph/partition engineering is unlikely to compete with witness/arithmetic improvements.
5. **OPEN QUESTION —** Do the exact resulting native proof family and ordered state effects pass ledger-9 stagenet acceptance/finality? This research pass performed no new acceptance test, so low cryptographic-change risk is not fresh acceptance evidence.
