# s8-decider-settle — wave 2 findings

## Verdict

**ESTIMATE — Build C10 as one authenticated, persistent proving worker plus one kept-synced deployer wallet. Keep the current k20 relation.** This removes repeated preparation and catches the A4 wrong-installed-VK failure before expensive work. It is a sound first engineering target, but the recorded recl9 setup saving is only `634.8 / (634.8 − 46.9) = 1.080×` for a D invocation. Prove-only remains 586.4 s. Removing the recorded 374.910 s wallet sync gives a separate registration counterfactual `435 / (435 − 374.910) = 7.239×`; these ratios must not be multiplied or called a measured settlement speedup.

**SOURCE — The unchanged decider does not fit k19.** Recl9 records 841,682 advice rows and 1,032,209 table rows at k20, with seven unusable rows. The 316,833-row pairing figure belongs to an earlier stand-in D with 832,015 total advice rows. Sources: `raw/s8-decider-settle/w2-private-evidence-summary.md`. **ESTIMATE — Retaining that pairing leaves only 207,448 k19 rows for everything else, versus the stand-in's 515,182-row remainder: a 59.73% reduction in the remainder is needed, before narrower-range overhead.** A redesigned k19 D remains an experiment; it is not a configuration change and needs a new VK.

**SOURCE — This wave adds a source-derived residency model, an authenticated artifact protocol, wallet failure handling, and an OpenSpec draft.** It builds on `clusters/s8-decider-settle/wave-1/FINDINGS.md` and `raw/s8-decider-settle/prior-loki10.md`. The requested Loki `10x/` path is absent; the earlier study exists at `../loki/nodes/loki-10-integration-verification.md`. Existing GPU/backend and pairing ideas are not claimed as new. No proofs, stagenet measurements, deployments or transactions were run. `PLAN.md` records nine concrete leads; `EXPERIMENTS.md` defines the next three experiments.

**SOURCE — Evidence convention:** every abbreviated raw filename below is under `raw/s8-decider-settle/`. `SOURCE` denotes inspected source or historical evidence, never a new timing measurement. **ESTIMATE** includes conditional arithmetic and proposed design choices, not implemented behavior. **OPEN QUESTION** identifies unresolved measurements or compatibility. Private evidence is summarized with exact numbers and checkout hash in `w2-private-evidence-summary.md`; this wave does not reproduce private source text.

## C10 process model and memory budget

**ESTIMATE — Use one Rust proving worker process, one lightweight admission/verification coordinator, one wallet daemon, and the existing qualified wallet proof server.** The worker holds two immutable prepared PK slots: active parent P/node N and terminal D for **one** selected deployment family. Sherlock and Fenrir are separate manifest families; do not assume all four k20 keys fit the two-slot budget. Each request borrows its key; do not deep-clone `MidnightPK` or `ParamsKZG`. A dedicated Rayon pool starts at 16 workers, reserving four host cores for wallet, verification and OS; retain a six-thread benchmark mode and test 10/16/20 before tuning. Run only one large P/N/D proof or key warm-up at a time initially. Separate processes do not make RAM/GPU contention disappear: the wallet proof server shares the global heavy-job admission policy.

**SOURCE — Prepared PK storage differs from the serialized file.** In pinned proofs 0.8.3, `ProvingKey` holds three extended Lagrange polynomials, fixed values/coefficients/cosets, permutation values/coefficients/cosets, the VK and evaluator. `read()` rebuilds transforms and evaluator; the write path omits these derived arrays. Sources: `w2-proofs-plonk.md`, `w2-permutation-keygen.md`, `w2-memory-layout.md`, `stdlib-2.3.5-source.md`. **ESTIMATE — “Cached PK bytes” is therefore not equivalent to “resident prepared PK”; nor is a process's peak RSS the key's allocation size.**

**SOURCE — Archived recl9 N and D each have 27 serialized fixed commitments and 18 permutation commitments.** Both VKs are 2,189 bytes. Their cost metadata reports 45 pre-keygen fixed columns, so multiplying 45 plus 18 as the final key shape would overcount this artifact. Sherlock's P/D source selects the same BLS/Poseidon/four-range-column architecture, but its deployed key objects were not introspected in this wave. Sources: `w2-private-evidence-summary.md`, `local-parent.md`, `local-decider.md`.

**ESTIMATE — Let `N=2^20`, scalar size `s=32 B`, `f=27`, `p=18`, and `e=extended_N/N`.** The dominant prepared arrays per N or D key occupy

`B_PK = s N [(f+p)(2+e)+3e] = 32 MiB × [45(2+e)+3e]`.

**SOURCE — The extension factor is the smallest power of two ≥ `cs.degree()−1` in this pinned implementation** (`w2-domain.md`). **ESTIMATE — At e=4, each key's dominant payload is 8.8125 GiB (9.462 GB); at e=8 it is 14.8125 GiB (15.905 GB), before evaluator, relation, vector capacity and allocator overhead.** These are conditional source-derived sizes, not live-allocation measurements. **OPEN QUESTION — Capture the actual degree/extension and retained allocation of each deployed P and D; until then provision 16 GiB per slot and reject a key that exceeds its reservation.** Same architecture makes the recl9 estimate useful for Sherlock planning, but does not certify its exact resident bytes. The old 12.8 GB PK-stage RSS cannot settle this question.

**SOURCE — `MemoryHigh` throttles/reclaims, whereas `MemoryMax` is the hard limit that can invoke the unit's OOM killer. CPUQuota is relative to one CPU; `1600%` means sixteen CPUs' worth, not 16%.** Source: `w2-systemd-resource.md`. **ESTIMATE — Use cgroup v2 limits if supported, monitor `memory.current`, peak and pressure, and close admission before reaching the soft limit. No automatic worker multiplicity based only on 20 cores. A worker crash cancels its attempt, preserves the journal, and requires re-warm and identity validation. A single worker sacrifices crash isolation between P and D to avoid extra SRS copies and resource pools.**

**SOURCE — Asynchronous CPU/GPU copies need page-locked host memory; mapped host memory has different latency/bandwidth from device memory.** Source: `w2-cuda-memory.md`. **ESTIMATE — Bound the pin pool to 1 GiB within the worker budget; do not page-lock both keys. Fixed-base precomputation must consume an explicit device budget: an illustrative 16 affine entries for each of two 2^20-base sets would already be `2×2^20×16×96=3 GiB`, before any scratch, and is not a claimed implementation.**

**ESTIMATE — Startup warms artifacts serially, validates, then publishes readiness.** For rotation, pause admissions and drain the single active job, retire the old family, then load the new one. Do not briefly retain two complete generations (four PKs) without a separately checked budget. OS service restart, failed CUDA context or corrupt key cache closes readiness; there is no fallback to freshly generated unregistered keys.

## Caller authentication and artifact identity

**SOURCE — A4 explicitly requires terminal VK bytes equal to the installed verifier's original bytes and binds the expected parent key.** Source: `local-terminal-test.md`. **ESTIMATE — Make that invariant part of the service protocol, not a post-hoc log field:**

1. **ESTIMATE — Local transport:** use a filesystem Unix socket in a private directory, restricted owner/group mode, and Linux `SO_PEERCRED` UID/GID allowlist. Map each service account to allowed network/contract/entrypoint and circuit family. Group socket access alone is not authorization. No anonymous TCP listener. For a future remote deployment, require mutually authenticated TLS with an explicit principal→scope map; do not expose the raw proof server. **SOURCE:** kernel credential semantics in `w2-unix-peercred.md`.
2. **ESTIMATE — Owner-approved immutable manifest:** canonical versioned encoding includes relation hash, complete Processed `MidnightVK` hash, optional tagged-envelope hash, parent/child VK hashes, circuit kind, k, architecture, transcript, public-input schema/template hash, official SRS file hash and k, crate/lockfile/features/build identity, network/genesis, contract address/operation, and activation generation. Hash with domain-separated SHA-256; deployment tooling or a read-only root-owned allowlist authenticates the manifest. Merely hashing an attacker-supplied manifest does not authorize it. Keep Blake2b as the proof transcript; artifact hashing is separate.
3. **ESTIMATE — Key load:** checked deserialization, no trailing bytes, trusted manifest comparison, relation and parent pins, and equality between the PK's embedded inner VK and the manifest's decoded inner VK. Also compare outer architecture/k/public-count: hashing only `pk.get_vk()` would omit part of `MidnightVK`. Verify the official SRS pin and fixed G2 identities; never use a newly generated SRS. Warm readiness is per full manifest identity.
4. **ESTIMATE — Request:** require principal, protocol version, manifest hash, `expected_vk_hash` (never optional), network/contract/entrypoint, expected deployment generation, exact public-input encoding/hash, parent artifact hashes, call binding and communication-commitment identity, deadline, and durable idempotency key. The service resolves key IDs itself; clients cannot choose file paths, upload replacement keys, or select arbitrary circuits. Authenticate and compare expected VK against active manifest and loaded key **before queueing, witness intake or proving**. Return `VK_MISMATCH` or `NOT_READY` without fallback.
5. **ESTIMATE — Attempt:** atomically pin one immutable key handle and request digest for the whole proof. Use fresh cryptographic randomness per new attempt; never cache witness/blinding state. Scope idempotency to principal and full request digest. A retry with the same key and digest returns the existing job/result; different digest with the same idempotency key is a conflict. Cryptographic proof reuse is permitted only for that identical request, not a changed transaction binding or public vector.
6. **ESTIMATE — Result:** independent stock ledger-9 verification with proof-verifying features enabled, exact public vector and the allowlisted installed VK, before Decided. Return a signed/authenticated envelope containing job/attempt ID, proof hash, public-input hash, full VK hash, manifest generation, parent hashes, SRS hash, backend/build ID and phase times. The coordinator compares these to the pending request; a signed envelope is not a substitute for cryptographic verification. Do not alter ledger proof serialization to carry service metadata.
7. **ESTIMATE — Submission guard:** wallet rechecks the locally authorized deployment identity and fresh chain/indexer state before signing, using a contract-state snapshot with provenance/height. An upgrade makes the job stale unless the exact old entrypoint VK is still the intended one. If upgrade races with submission, acceptance/rejection and readback decide; a pre-submit check cannot eliminate that race. No auto-rekey or auto-deploy on mismatch.

**ESTIMATE — Keep witness material, wallet secrets, fee recipes, snapshots and communication openings out of metrics, service manifests and this research corpus.** The wallet owns signing keys in its existing protected store. The proving worker receives only the private witness needed for the exact scoped request. Job metadata contains opaque IDs and public artifact hashes. Admission limits request bytes, outstanding jobs and per-principal resource use; a valid caller is not entitled to exhaust RAM.

## Kept-synced deployer wallet and settlement states

**SOURCE — The official Node service guide keeps one `WalletFacade` for the server lifetime and serializes shielded, unshielded and DUST sub-wallets. Its example writes a mode-0600 temporary file and renames it, restores on restart, and saves periodically and on shutdown. The guide says keep snapshots per wallet and network; its filename alone identifies an address and does not enforce the network binding.** Source: `w2-node-wallet.md`. **ESTIMATE — Add explicit network/genesis + derived address + SDK/ledger version + cursor/checkpoint + integrity metadata around each snapshot; keep existing keys and contract private-state store intact. Snapshot, journal and reservation metadata require durable write/fsync ordering, not merely rename. Treat snapshots as private coin inventory, even without signing keys.**

**ESTIMATE — Run one wallet owner per deployer seed/network with an exclusive local lock and a fencing generation for recovery.** Start sync during service startup, before Consumed events. Persist confirmed cursors and pending recipes/transaction hashes, and reconcile them before admitting any new spend after restart. A failed restore falls back to resync only after retaining the recoverable snapshot/journal; do not delete or recreate the wallet. Multiple same-seed wallet daemons are forbidden by deployment policy. A lease alone cannot fence an uncontrolled external signer, so existing external use must be operationally excluded.

**SOURCE — `isSynced`/`waitForSyncedState()` means caught up with the indexer, not that one's submitted transaction has been applied. Building a transaction can lock fee DUST and spent NIGHT UTXOs; available balance must exclude pending locks. Stale restored state can cause InvalidDustSpendProof; same-seed concurrent wallets can cause DustDoubleSpend.** Source: `w2-manage-dust.md`. **ESTIMATE — Readiness requires all relevant sub-wallets healthy, no replay error, indexer freshness against a trusted head, required confirmed application of predecessor spends, and enough unlocked fee inputs. A synced-but-stale indexer is not READY.**

**ESTIMATE — TTL admission inequality:** `expiry − trusted_now > q_p99 + D_p99 + W_p99 + submit_allowance + clock_margin`. **SOURCE — Recorded D alone is 586.4 s; current guide examples use 30 minutes but are not evidence for archived rc.8/ledger-9 configuration** (`w2-private-evidence-summary.md`, `w2-manage-dust.md`). **ESTIMATE — One queued D at that historical duration plus the active D already consumes 1,172.8 s, leaving only 627.2 s of a hypothetical 1,800 s TTL for everything else.** Use the qualified deployment's actual parameters and measured percentiles; six-thread historical means cannot certify deadlines. Preparing independent parent work before forming a fee-bearing transaction can reduce TTL exposure, but cannot precompute a D proof before its required call binding exists.

**SOURCE — DUST estimation distinguishes required fee from declared fee including margins/overhead; a fee-bearing DUST spend needs proof-server work. Current guidance is newer than the archived rc.8 registration and must be version-qualified.** Sources: `w2-manage-dust.md`, `proof-server.md`. **OPEN QUESTION — Exact per-batch proof count, fee unit interpretation, declared/charged amount and expiry behavior for ledger-9 remain unmeasured.** **ESTIMATE — Record fee per finalized logical transaction as actually consumed SPECK divided by settled count; include failed included attempts where charged, report locked-but-unspent inventory separately, and never infer fees from the 6,432-byte proof.**

## Decider-domain arithmetic: k19 decision

**SOURCE — At k20 recl9 reports D advice/table rows `841,682 / 1,032,209`, seven unusable rows, and N `958,095 / 1,032,465`.** `w2-private-evidence-summary.md`. **ESTIMATE — Compare the maximum required height to usable rows, not the sum of advice and table rows.** At k19, retaining seven unusable rows gives `524,288−7=524,281` usable rows; the exact k19 blinding requirement must still be read from its configured circuit.

| Calculation | Result and status |
|---|---|
| k19 budget after historical pairing | **ESTIMATE:** `524,281−316,833=207,448` rows for verifier transcript, fold, collapse and binding. |
| Stand-in remainder | **ESTIMATE:** `832,015−316,833=515,182`; attribution is by subtraction, not measured subphase counters. |
| Required stand-in remainder reduction with pairing unchanged | **ESTIMATE:** `515,182−207,448=307,734`, or `307,734/515,182=59.733%`. |
| Required current recl9 total reduction | **ESTIMATE:** `841,682−524,281=317,401`, or 37.710%; stand-in pairing is not a recl9 measurement. |
| Half-cost pairing, stand-in remainder unchanged | **ESTIMATE:** `515,182+316,833/2=673,598.5` expected rows, still 149,317.5 above k19. Actual rows are integral. |
| Pairing-only route to k19 in stand-in | **ESTIMATE:** allowed pairing `524,281−515,182=9,099` rows, requiring 97.128% reduction, before any other changes. A zero-cost pairing leaves only 9,099 rows headroom. |
| k18 lower bound | **ESTIMATE:** with seven unusable rows capacity is 262,137, so the pairing alone exceeds it by 54,696 rows (17.26% of pairing). |

**SOURCE — The range width is `k−1`, tables load only used tags, and stdlib searches for a fitting k.** Sources: `stdlib-2.3.5-source.md`, `pow2range-7.2.4.md`. **ESTIMATE — It is wrong to call the k20 million-row table an immutable k19 floor. But smaller range width can increase limb/chunk advice rows, so dividing k20 table size by two is not a feasibility proof either.** E2 must measure both with the complete relation; no claim of k19 readiness follows from the 316,833 pairing count.

**SOURCE — D verifies an inner Poseidon proof and binds its accumulator; the final native outer PLONK transcript is Blake2b. The current Sherlock D also checks the communication opening using Poseidon.** Sources: `local-inner.md`, `local-decider.md`, `ledger9-rc6-proofs.md`. **ESTIMATE — There is no separately established in-circuit Blake2b row block to delete. “Pairing plus transcript and binding” includes the full verifier algebra, fixed/variable-base MSM and fold, not just one hash.** Preserving the full Fiat–Shamir statement, subgroup/identity checks, both side scalars and exact call binding is mandatory. The existing residue/constant-G2/normalization work from wave 1 is already in the baseline; do not credit it again.

## What would change the verdict

- **OPEN QUESTION — E1 proves actual deployed key payload/retained RSS and identifies a much larger avoidable A4 setup fraction.** That could raise C10's measured benefit, but cannot turn recl9's separately timed prove-only baseline into setup time.
- **OPEN QUESTION — E2 produces a stock-deserializable k19 D with complete binding, valid range tables, negative-case rejection and a measured latency win.** Promote it only as a changed-VK candidate; it does not replace the currently installed key without an explicitly authorized registration/deployment.
- **OPEN QUESTION — E3 shows synced wallet admission still waits on fee coin ownership or TTL.** Then fee scheduling/readiness, not proof-server kernel speed, is the next bottleneck. A local replay validates failure handling but cannot establish real stagenet latency or fees.
- **ESTIMATE — For a 10× stage claim use a matched timeline:** `speedup=(D+setup+wallet+finality)/(D'+setup'+wallet'+finality')`. If D alone is reduced 10× and positive other terms remain unchanged, end-to-end gain is below 10×. There is no such matched baseline in the supplied observations. **SOURCE:** the recl9 component prove sum is 1,617.4 s, of which D is 586.4 s (`w2-private-evidence-summary.md` and historical wave-1 arithmetic). **ESTIMATE:** deleting D entirely leaves 1,031.0 s, only 1.569× for that serial whole-chain sum; an order-of-magnitude whole-chain result needs other stages too.
