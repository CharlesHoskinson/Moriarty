# s3-commit-msm — wave 1 findings

## Verdict

**ESTIMATE:** Prioritize a **commitment-aware bucket MSM service**, benchmarked against both the exact current BLST dispatch and Nocy's independent per-point multiplication. Keep sppark as the initial reference; evaluate open-ICICLE and WLC as challengers. A conditional 5–20× improvement of the *remaining MSM portion* yields only **1.92–2.33× over Nocy's GPU time, or 5.38–6.50× over its recorded CPU time**, if MSM occupies 60% of the remaining GPU interval: `(12.3/4.4)/(0.4+0.6/s)`, `s=5..20`. These are sensitivity scenarios, not predicted or measured performance. There is **no evidence yet for 10× end-to-end from this stage alone**.

**SOURCE:** The recorded Nocy baseline remains k17 **12.3→4.4 s** and k18 **24.6→8.8 s**, averaged over ten runs against EPYC 7642; neither is Sherlock k20 or this host's 20-core CPU baseline. Capture: `raw/s3-commit-msm/nocy-readme.md`. This research performed source retrieval, code inspection and arithmetic only; no GPU benchmark or proof was run.

**SOURCE:** New evidence beyond the earlier studies: (1) Nocy already caches both GPU base arrays; (2) current sppark `invoke` contains internal synchronization and host collection; (3) open-ICICLE exposes CUDA MSM source and an actual BLS12-381/5090 integration, with an unresolved licensing contradiction and a reported Montgomery/chunking correctness bug; (4) WLC offers a BLS12-381 load-balanced implementation, but its benchmark batches sixteen MSMs and repeats 2,048 random bases. Evidence: `raw/s3-commit-msm/{nocy-kzg,sppark-pippenger,open-icicle-cuda-msm,gnark-cuda-readme,gnark-montgomery-bug,wlc-bench,wlc-util}.md`.

**SOURCE:** The task assigns Witnessed→Committed and preserves PLONK/KZG over BLS12-381, the official SRS and ledger-9's terminal Blake2b transcript. The historical analysis distinguishes intermediate transcripts from the terminal transcript and distinguishes host commitment MSM from the recursive circuit's constrained MSM. The experiments preserve each existing transcript, circuit and key; they do not replace intermediate transcripts with Blake2b.

**ESTIMATE:** Let `B=12.3/4.4=24.6/8.8=2.79545`, `f` be the fraction of *Nocy's remaining GPU wall time on the critical path* replaced by this stage, `s` its acceleration, and `h` new overhead as a fraction of that GPU wall time. Then `G=1/(1-f+f/s+h)` is improvement over the recorded GPU baseline and `B*G` is improvement over its recorded CPU baseline. Do not substitute summed overlapping kernel durations for `f`. For current Sherlock/Fenrir, replace all quantities with measured same-host values. No row below compounds with another without a new residual profile.

**OPEN QUESTION:** No retrieved source establishes `f`, the number of commitments per transcript round, the actual scalar distributions, or current same-host BLST times for A102/A80/P/D or four-leaf/N/D. These are the first experiment's outputs, not inputs we may invent.

## What the new sources establish—and do not

**SOURCE:** Nocy's historical pinned `kzg.h` uses thread-local monomial/Lagrange `KzgPointsCache` and a work cache. Each `kzg_commit_impl` still copies scalars, launches per-point multiplication, repeatedly halves the partial array, copies one result back and calls `cudaStreamSynchronize`. `msm.cuh` forms a 16-entry table per point, runs 64 four-bit windows and reduces independently computed scalar multiples. Captures: `raw/s3-commit-msm/{nocy-kzg,nocy-msm}.md`.

**ESTIMATE:** At `N=2^20`, its halving loop means **20 reduction launches**, in addition to the per-point kernel. A bucket implementation with many launches may still win by removing arithmetic; launch count alone is not the deciding metric. An algorithmic operation-count comparison is suggestive, not a runtime prediction: independent multiplication processes about 256 doublings per point, whereas 16-bit bucket accumulation processes about `ceil(255/16)=16` digit contributions per point plus sorting/reduction.

**SOURCE:** sppark's current `msm_t` can retain bases, but `invoke` allocates temporary storage, copies partial results to the host, synchronizes an internal stream and calls `collect`. Its internal `batch` splits **one MSM** into chunks; it is not an API for multiple commitment outputs. Its sort-grid comment reports tuning on Turing/Ampere and possible 30–40% degradation outside its sweet spot. Capture: `raw/s3-commit-msm/sppark-pippenger.md`.

**ESTIMATE:** Wrapping synchronous `invoke` calls in an outer CUDA stream does not remove those internal waits. A real async adapter must preserve each invocation's scratch and return a pending result, or use lower-level kernels. Blackwell retuning should start with measured sort occupancy/registers and window size, not a new finite-field implementation.

**SOURCE:** The open-ICICLE CUDA source explicitly shares points in a batch and can fall back to sequential MSMs under memory pressure. Its `get_optimal_nof_chunks` returns **four chunks when either points or scalars are on the host even if the job fits**, and one if both are resident, after its minimum-memory check. Capture: `raw/s3-commit-msm/open-icicle-cuda-msm.md`. This is a concrete residency benefit beyond eliminating PCIe bytes.

**SOURCE:** `polytope-labs/gnark-cuda` reports an RTX 5090 / sm_120 BLS12-381 PLONK circuit with **7,097,608 constraints**, approximately **98→13.5 s**, including a device-resident quotient loop. Its adapter includes separate async issue and result-marshaling functions, canonical device inputs and a homogeneous-projective→affine→Jacobian conversion. Captures: `raw/s3-commit-msm/{gnark-cuda-readme,gnark-api}.md`.

**ESTIMATE:** `98/13.5=7.26×` is a whole gnark workload result, not an MSM-only gain and not ledger-9 acceptance. It is evidence for integration feasibility on the right curve/GPU, not evidence that Sherlock will run in 13.5 seconds. No host CPU, SRS, key, transcript or timing equivalence to Sherlock is established by the README.

**SOURCE:** The gnark bug report, found 2026-06-26 on CUDA 12.8.1/5090, reports correct results with canonical inputs but mismatches with Montgomery inputs when memory pressure triggers chunking at `2^23`. Its root-cause explanation is explicitly **suspected**. The workaround explicitly converts inputs once and invokes MSM with both Montgomery flags false. Captures: `raw/s3-commit-msm/{gnark-montgomery-bug,gnark-api}.md`.

**OPEN QUESTION:** Whether the exact candidate revision is still affected, whether k20 can trigger it with concurrent proving buffers, and whether the workaround covers every batch/precompute configuration require differential tests. A successful return code is not a correctness oracle. Compare both paths against BLST, not merely against each other.

**SOURCE:** open-ICICLE's root `LICENSE` is MIT, CUDA MSM source is public, and its scope lists BLS12-381 MSM/NTT/ECNTT. However its README still excludes non-CPU backends from MIT coverage. The attempted `icicle/backend/cuda/LICENSE` URL returns 404. Captures: `raw/s3-commit-msm/{open-icicle-license,open-icicle-readme,open-icicle-cuda-msm,open-icicle-cuda-license}.md`.

**OPEN QUESTION:** Exact redistribution/deployment terms for that revision remain unresolved by these inconsistent documents. The earlier statement that ICICLE's GPU implementation is available only as a closed binary is incomplete for this new repository; the stronger claim that all current GPU code is unambiguously MIT is also unsupported. No maintainer contact was made.

**SOURCE:** WLC's authors describe signed/odd scalar recoding, a threshold-6 power-of-two table for BLS12-381, fourfold bucket-count reduction relative to unsigned windows, balanced partial accumulation and layered bucket reduction. Slides report roughly 2× versus cuZK. The distinct **28.2–85.3%** ablation is explicitly **BLS24-315**, not BLS12-381. Captures: `raw/s3-commit-msm/{wlc-slides-web,wlc-readme,wlc-kernel}.md`.

**SOURCE:** WLC's benchmark initializes its context outside Criterion's timed loop, sets `batches=16`, and generates only `2^11` random bases before repeating them to reach the requested length. The scalar vectors are random. Captures: `raw/s3-commit-msm/{wlc-bench,wlc-util}.md`. Its constant-time variant's README is a claim about that implementation, not a complete side-channel audit.

**ESTIMATE:** Dividing a batch duration by sixteen gives amortized throughput per MSM, not single-request latency. Repeated bases are not official SRS powers and may change exceptional-point and cache behavior; their bias is not quantified. Re-run with actual SRS before ranking WLC above sppark. cuZK's 190 ms k20/V100 measurement is historical context only (`raw/s3-commit-msm/helper2-cuzk.md`); it cannot be divided into another GPU's latency to infer an algorithmic gain.

**SOURCE:** The Yrrid/Matter Labs combined README reports **2.2–2.3 seconds for four 2^26 MSMs**, about **46 GiB** on an A40, with 23-bit windows covering **253 bits** and custom workload-sorted buckets. It attributes an approximately 240 ms combined improvement to field/curve arithmetic (150 ms) and copy/compute overlap (90 ms). Capture: `raw/s3-commit-msm/yrrid-combined.md`.

**ESTIMATE:** Those two contributions sum `150+90=240 ms`; the publication does not show they recur at k20 on Blackwell. At 46 GiB the reported configuration already exceeds this GPU's nominal capacity, and 253-bit recoding cannot simply be copied into BLS12-381's 255-bit scalar path. Borrow sorting/overlap ideas; budget **no transferable speedup** from the contest score.

**SOURCE:** NVIDIA's Blackwell guide distinguishes compatible cubins from forward-compatible PTX and notes JIT cost when native code is absent (`raw/s3-commit-msm/blackwell-compat.md`). The guide's generic examples mention compute capability 10.0; the actual 5090 integration specifies **sm_120** (`gnark-cuda-readme.md`).

**OPEN QUESTION:** Correct architecture selection, current CUDA 13.x compilation, register pressure, sort tuning and graph-capture compatibility still need testing on this host. Neither generic “Blackwell supported” nor FP32/tensor throughput establishes BLS12-381 Montgomery arithmetic performance.

## Memory and amortization, including the rest of the prover

**ESTIMATE:** With packed affine G1 size 96 bytes and scalar size 32 bytes, k20 is **96 MiB of bases** and **32 MiB of scalars**. One maximum-size monomial table plus separate Lagrange tables for k20/k17/k13/k12 requires `96+96+12+.75+.375=205.125 MiB`. Precompute factor four gives **820.5 MiB**, factor eight **1,641 MiB**. This assumes identical official SRS, domain conventions and compatible prefix precomputation; padded layouts must replace 96 with measured `sizeof`. Different circuit VKs do not automatically imply different SRS bases, but different Lagrange domains do.

**ESTIMATE:** For ICICLE-style `c=16,p=4,b=8,N=2^20`, `q=ceil(ceil(255/16)/4)=4` bucket modules. Scalars `32Nb=256 MiB`; indices `24qNb=768 MiB`; 144-byte projective buckets `144q2^c b=288 MiB`; all-domain tables above `820.5 MiB`. Conservatively retaining all yields **2,132.5 MiB**, before sorting/allocator/double-buffer overhead. Using 192-byte XYZZ buckets adds **96 MiB**. This is an admission estimate, not a backend allocation promise. The source memory formula is in `raw/s3-commit-msm/helper1-icicle-msm.md`; the implementation's actual chunk estimator is in `open-icicle-cuda-msm.md`.

**ESTIMATE:** WLC threshold six means up to seven stored affine multiples per original base: two k20 tables alone cost `2*7*96=1,344 MiB`, if stored packed affine. Its table is not ICICLE's shifted-base layout: do not combine their parameters or projected savings. At k24 the preceding two-table factor-eight calculation grows `16×` to **24 GiB** before scalar, index, bucket or NTT storage—another reason not to import large A40 contest configurations.

**SOURCE:** Earlier whole-prover memory estimates reach **28.06–28.56 GiB** for an extended-domain proxy, including a 0.75 GiB SRS allowance. Capture: `raw/s3-commit-msm/earlier-astra-proposal.md`. These are earlier estimates, not measurements.

**ESTIMATE:** Raising just that allowance from factor four to eight adds **0.75 GiB**, producing **28.81–29.31 GiB**, while a different batch scratch policy may add more. Admission must use actual `cudaMemGetInfo` and measured concurrent peak, not “32 GB minus the SRS.” Start with a total cap `min(24 GiB, .8*free_device_bytes)` and lower precomputation/batch width when polynomial buffers need the space; 90 GB host RAM is not device residency.

**ESTIMATE:** Precompute break-even is `reuse_count > preparation_time/(unprepared_time−prepared_time)`. Using the historical `25.5−18.1=7.4 ms` only as an illustration, **1 second** preparation takes `ceil(1000/7.4)=136` uses to recover. Moving factor four to eight saves only **0.9 ms** per vendor MSM; a hypothetical extra 1 second then needs **1,112** uses. Measure first-proof latency separately from steady state, and charge preparation once per actual basis table.

## What would change the verdict

**ESTIMATE:** To reach 10× versus Nocy's recorded CPU time requires `1−f+f/s+h ≤ B/10 = .279545`. With `h=0`, the necessary remaining-MSM fractions are **90.06% at s=5**, **80.05% at s=10**, **75.84% at s=20**; even infinitely fast MSM needs **72.05%**. At `f=.6`, the absolute ceiling is `B/.4=6.99×`. A *further* 10× versus the already-GPU baseline is a different target: at `s=20`, it needs `f≥.9/.95=94.74%`.

**OPEN QUESTION:** The verdict upgrades if E1 finds the required critical-path share in the actual P **and D** (and eligible leaves), E2 demonstrates the necessary service speed with official bases and complete correctness, and E3 preserves those gains under whole-prover memory pressure and unchanged ledger-9 verification. Single-kernel timing, batch throughput, changed SDK versions or a parent-only speedup do not meet that condition.

**ESTIMATE:** Downgrade this stage as the route to 10× if the measured unchanged remainder exceeds the budget, if conversion/synchronization erases kernel gains, or if a corrected always-BLST CPU baseline is substantially faster. Retain the best verified MSM adapter as a partial speedup and pass the measured residual budget to witness/NTT/quotient leads. No curve substitution, transcript substitution, new SRS or removal of terminal pairing is proposed.
