# s6-opening: multiopen and KZG opening — wave 1

## Verdict

**ESTIMATE — Prioritize the exact Midnight opening implementation: remove redundant work, then port its reductions, evaluations, division and two MSMs to a resident GPU path.** Keep its transcript schedule and terminal PCS unchanged. Study fflonk only as an inner-layer circuit-size optimization until it proves a reduction in parent/decider cost. There is no measured basis for a 10× end-to-end claim from this stage alone.

**SOURCE — Baseline:** the owner supplies Sherlock A102(k13)+A80(k12)→P(k20)→D(k20), and Fenrir four k17 leaves→N(k20)→D(k20), with ledger-9 accepting PLONK/KZG over BLS12-381, Blake2b and the official SRS. No s6 elapsed time or completed chain timing was supplied. [Raw baseline](../../../raw/s6-opening/task-baseline.md). The earlier study identifies published proofs 0.8.3 for Sherlock and 0.8.2 for recl9; this research fetched both published modules, but did not independently establish the running binaries' dependency/features/local patches. [Earlier study](../../../raw/s6-opening/prior-loki04.md), [0.8.3 source](../../../raw/s6-opening/midnight-kzg-0.8.3.md), [0.8.2 source](../../../raw/s6-opening/midnight-kzg-0.8.2.md).

**ESTIMATE — Ceiling:** normalize the recorded workload to `T=1`; let `q` be the fraction of its actual critical path spent in s6, `r` the s6 acceleration, and `o` added overhead as a fraction of baseline T. Then `S=1/(1-q+q/r+o)`. Even eliminating s6 entirely cannot produce 10× unless `q≥0.90`; at `r=20,o=0.01`, 10× needs `q≥0.91/0.95=95.79%`. This is a necessary coverage condition, not a timing measurement. For parallel children, use critical-path intervals rather than summing their overlapping times.

## What this adds or corrects relative to the earlier study

1. **SOURCE — PR #565 optimizes an existing fflonk implementation; it does not introduce the recorded size reduction.** Its table explicitly says sizes are unchanged by the PR. On one `zswap_output` k14 benchmark, KZG changes 590→415 ms; t=4 changes 924→536 ms. Within the new revision, t=4 is 536/415=1.292× the KZG prover cost, while VK bytes are 2258→578 and proof bytes 4384→3840. CPU model and recursive-circuit results are not specified in that table. [PR565](../../../raw/s6-opening/fflonk-pr565.md). **ESTIMATE:** VK shrink is `1-578/2258=74.40%`, not a 74.40% reduction in recursive proving work. The KZG bundle's `590/415=1.422×` cannot be assigned to opening alone: the PR also changes phase commitments and their representations. [Patch](../../../raw/s6-opening/pr565-files.md).
2. **SOURCE — Midnight's published opening protocol has an extra scalar-message/challenge boundary relative to the captured Axiom SHPLONK implementation.** Midnight writes F, squeezes x3, writes grouped polynomial evaluations, squeezes x4, and writes π. Axiom writes H, squeezes u, and writes its final opening commitment without that intervening evaluation-message round. [Midnight](../../../raw/s6-opening/midnight-kzg-0.8.3.md), [Axiom pinned source](../../../raw/s6-opening/axiom-shplonk.md). **ESTIMATE:** reuse arithmetic kernels, not Axiom's `create_proof` as a protocol replacement.
3. **SOURCE — A baseline-specific dead computation exists:** `multi_open` computes `v=eval_polynomial(final_poly,x3)` solely for `kate_division(final_poly-v,x3)`. `kate_division` produces n−1 outputs from the reversed coefficient iterator, so it never reads coefficient zero. [Opening](../../../raw/s6-opening/midnight-kzg-0.8.3.md), [arithmetic](../../../raw/s6-opening/midnight-arithmetic-0.8.3.md). **ESTIMATE:** call division directly on `final_poly.values` to avoid that evaluation and subtraction; preserve every grouped evaluation written before x4. Proof-byte equality is the deciding check, not this static observation.
4. **SOURCE — A concrete parallel division implementation is available:** Axiom uses an affine-pair Brent–Kung scan, with two n−1 scalar scratch arrays. It explicitly includes `field/alt_bn128.hpp`; this is BN254 code, not a ready BLS12-381 backend. [Scan](../../../raw/s6-opening/axiom-kate-division-header.md), [launcher](../../../raw/s6-opening/axiom-kate-division.md). No new opening-specific speedup was found in these source files.
5. **SOURCE — Fflonk's SRS requirement and challenge change are explicit:** `Fflonk<PCS,LOG2_T_MAX>` loads `k+LOG2_T_MAX`, exposes `max_k−LOG2_T_MAX`, and raises the evaluation challenge to `T_MAX=2^LOG2_T_MAX`. The source tests use `Fflonk<Kzg,2>` for t≤4. [Implementation](../../../raw/s6-opening/midnight-fflonk-pr565.md). **ESTIMATE:** t≤4 at k20 needs degree capacity below 2²², four times the monomial powers of k20. These must come from the same official SRS, not a locally generated replacement. **OPEN QUESTION:** availability, authenticated loading and actual memory cost of that official prefix on this host.

## Protocol boundary and opening schedule

**SOURCE — Published 0.8.2 and 0.8.3 KZG module bodies fetched here are identical.** They group polynomials by point sets and sort those sets by `(cardinality, original index)` for recursive verifier compatibility. The schedule in `multi_open` is:

```text
x1, x2 := existing transcript challenges
q_i := challenge-weighted combination for each ordered point set S_i
F := sum_i x2^i * quotient(q_i / product_{z in S_i}(X-z))
write commit(F)
x3 := challenge (with the configured truncation behavior, if any)
write each q_i(x3), in the existing order
x4 := challenge
G := existing weighted combination of q_i and F
write commit(quotient(G / (X-x3)))
```

**SOURCE:** `raw/s6-opening/midnight-kzg-0.8.3.md`, `raw/s6-opening/midnight-kzg-0.8.2.md`; the omitted remainders above are implicit in polynomial quotient computation. **ESTIMATE:** schedule GPU work around these three host-visible result boundaries: F, evaluation scalars, π. F and π of a single proof cannot be batched into one independent MSM call because π depends on the intervening challenges. Siblings' ready F values can be batched, then siblings' ready π values, without changing any proof. Parent work cannot start from unfinished child proof bytes.

**ESTIMATE — State ownership:** instrument Quotiented→Opened around this exact reduction/opening path; Opened→Proved includes remaining serialization and error propagation. Define the timer boundary explicitly because current application labels may place evaluation writes differently. Do not count earlier quotient construction as a newly accelerated s6 operation, or hide later verification and ledger latency in a narrower timer.

**SOURCE — The Axiom scan realizes** `q_j=a_(j+1)+z*q_(j+1)` using the associative composition `(a,b)∘(c,d)=(a*c,a*d+b)`. [Kernel](../../../raw/s6-opening/axiom-kate-division-header.md). **ESTIMATE:** adapt this recurrence to BLS12-381 and fuse the final polynomial combination into the scan's input reads where profitable. For fflonk's sparse divisor `X^t-x`, the recurrence splits into t residue classes, permitting t shorter independent scans; this is an algebraic design extension, not a measured feature of the captured backend. Ordinary dense vanishing polynomials need a different comparison; one-pass CPU division is not automatically the best GPU algorithm.

## Inner fflonk versus terminal fflonk

**SOURCE — PR575 supplies the recursive verifier trait implementation, merged October 15, 2026; it supplies no row, constraint, k or proving-time benchmark.** PR565 was merged October 14. The original fflonk paper describes a verifier/prover tradeoff and reports roughly tripling prover cost for its construction, unlike the newer Midnight k14 implementation's 1.292× t4 cost. These are different implementations/workloads. [PR575](../../../raw/s6-opening/fflonk-pr575.md), [PR565 metadata](../../../raw/s6-opening/pr565-metadata.md), [paper](../../../raw/s6-opening/fflonk-paper.md).

**ESTIMATE — Break-even for an inner switch:** let L be time spent producing switched proofs, U time spent proving their outer verifier(s), p the measured inner prover multiplier, d the measured fractional outer saving, and K/R amortized extra key/precompute cost per run. Improvement requires `U*d > L*(p−1)+K/R`. Ignoring K, t4 at the published p needs d>7.29% when U=4L, or d>29.16% when U=L. Measure p anew for each actual circuit. Test children-only first, then P/N as an inner proof consumed by D; the latter may shrink D but changes a much more expensive inner prover.

**ESTIMATE — Fixed-k caveat:** fewer verifier commitments may reduce rows without changing k or dominant column/FFT counts. A packing win becomes much more compelling if it actually permits a smaller domain or fewer columns. No row count can be inferred from VK bytes. For illustration, if a fraction a of a parent is verifier work and that portion shrinks by v, row savings are at most a*v; crossing a half-domain boundary needs sufficient initial slack plus those savings, not merely v≈75%.

**ESTIMATE — Terminal policy:** keep D's accepted proof encoding, Blake2b transcript and PCS fixed. A new D circuit for inner fflonk can still emit accepted KZG proofs, but typically needs a new VK and allowed contract registration/redeployment. Ledger-9 protocol acceptance and acceptance by an already-deployed contract VK are separate conditions. If that VK is immutable for this task, restrict the experiment to proof-preserving arithmetic changes. No deployment or ledger transaction was attempted here.

## Memory and batching budget

**ESTIMATE — Scalar storage:** a k20 scalar vector at 32 bytes is `2²⁰*32=32 MiB`. A scan's two scratch vectors are about 64 MiB; input+output+scratch about 128 MiB before F, grouped q_i, polynomial columns or MSM buckets. Four such scan workspaces alone use about 512 MiB; this does not imply four whole k20 proofs fit in 32 GB. [Scratch design source](../../../raw/s6-opening/axiom-kate-division.md).

**ESTIMATE — SRS storage:** assuming 96-byte uncompressed BLS12-381 G1 affine points, k20 bases occupy 96 MiB; fourfold precomputation occupies 384 MiB before overhead. A t4 k20 packing domain may require 2²² powers, or 384 MiB of affine bases before additional transformed bases/caches. Actual device layouts and allocation peaks must be measured. Do not compare compressed 48-byte storage to uncompressed device residency.

**SOURCE — ICICLE supports batch MSM with shared or distinct bases and documents precompute/index/bucket memory tradeoffs.** Its illustrative tuning table uses BLS12-377 on RTX3090 Ti, not BLS12-381 on RTX5090. The k24 table's 232→199 ms uses increased precomputation and memory; it establishes neither a k20 benefit nor suitability of those settings here. [API](../../../raw/s6-opening/ingonyama-msm-api.md). **ESTIMATE:** sweep batch 1/2/4 and precompute 1/2/4 under measured 28 GiB GPU and 80 GiB host high-water targets, leaving headroom within the supplied 32 GB/90 GB host. Treat these as experiment targets subordinate to factory caps. Do not shorten scalars based on an unrelated workload.

- **OPEN QUESTION — E1:** If s6 is under 10% of the chain critical path, even perfect elimination caps the overall gain at `1/.9=1.111×`; route the 10× objective to other stages and retain only cheap improvements here.
- **OPEN QUESTION — E2:** If the exact resident opening pipeline shows ≥4× stage acceleration with proof identity and tolerable memory, implement it; if data copies/challenge waits dominate, broaden residency into adjacent stages rather than extrapolating MSM ratios.
- **OPEN QUESTION — E3:** If inner fflonk crosses k20→k19 (or removes costly columns) and beats `U*d > L*(p−1)+K/R`, it becomes the leading structural option. If rows/k stay unchanged, prioritize arithmetic instead.
- **OPEN QUESTION — Official SRS:** insufficient authenticated degree capacity, or an immutable deployed D VK, can disqualify the fflonk branch while leaving arithmetic changes viable.
- **OPEN QUESTION — Accumulation inventory:** evidence of repeated terminal pairings would promote accumulator batching; evidence of one existing accumulated decision leaves it at 1×.
- **OPEN QUESTION — FK20 workload:** many openings of the same retained polynomial, rather than unrelated child proofs, would justify revisiting amortized preprocessing.
