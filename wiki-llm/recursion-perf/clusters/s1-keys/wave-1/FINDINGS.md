# s1-keys — wave 1 findings

ESTIMATE — **Keys alone cannot deliver 10× end-to-end on the recorded workloads.** Eliminating Sherlock's repeated 62.3 s PK setup gives `(62.3+882.6)/882.6 = 1.0706×`; a cold-start stream of 16 proofs gives only `16×944.9/(62.3+16×882.6) = 1.0659×`. Keep prepared keys resident because they become essential after other stages accelerate, and first investigate the **0.8.2 large-MSM dispatch cliff** for the 622.8 s cold VK build. A 10× reduction of Queued→KeysReady is a reasonable experimental target, not evidence of a 10× proof or settlement speedup.

SOURCE — Evidence consists of historical local receipts, fresh public-source captures and inspected helper captures. **No prover, keygen, GPU or loading benchmark was run in this wave.** The requested profile path does not exist under `loki/10x`; the study was found under `loki/nodes/` and captured in [prior-profile.md](../../../raw/s1-keys/prior-profile.md). [PLAN.md](PLAN.md) records nine concrete leads. Every source path below is relative to this repository; timings described as recorded are old observations, not measurements on today's host.

## Why the 623-second VK is worth a narrow experiment

SOURCE — The node receipt reports 45 “fixed columns” including 18 permutation commitments, so actual fixed/selector/table count is 27. `build_vk` constructs sigma values from nonzero powers of omega and delta, then commits all 18 sigma columns. `setup_vk` uses the supplied parameter k and calls `keygen_vk_with_k`, bypassing the separate automatic-k entrypoint. The manifest pins proofs 0.8.2 and curves 0.3.1. [recl9-node-keygen-stats.md](../../../raw/s1-keys/recl9-node-keygen-stats.md), [prior-profile.md](../../../raw/s1-keys/prior-profile.md), [midnight082-permutation-keygen.md](../../../raw/s1-keys/midnight082-permutation-keygen.md), [midnight-stdlib-235.md](../../../raw/s1-keys/midnight-stdlib-235.md), [recl9-manifest.md](../../../raw/s1-keys/recl9-manifest.md).

ESTIMATE — Consequently the 18 length-2^20 sigma commitments have 2^20 nonzero terms and cross the 0.8.2 dispatch threshold. Some fixed columns may be sparse enough not to cross; count their nonzeros rather than assuming 45 identical MSMs. This establishes a concrete route into the slow branch; it does **not** establish its fraction of the 622.8 seconds.

ESTIMATE — Even deleting the entire 622.8 s VK interval leaves `959.5−622.8=336.7 s` of that recorded *keygen process*, limiting its acceleration to **2.85×**. Avoiding the already-known repeated cost-model pass is a distinct optimization. The source rules out blaming SRS loading, network fetch or PK coset reconstruction for the VK interval. Synthesis, generic MSM, permutation construction and contention remain candidates.

OPEN QUESTION — Does the original 0.8.2 binary match the current manifest/source and recorded thread environment exactly? The node log says “all” threads, not a controlled 20-core allocation. E1 must record build/lockfile digests, actual worker counts and exclusive phase times before assigning causality. Do not relabel a 0.8.3 Sherlock run as the 0.8.2 recl9 baseline.

## Warm service, artifact identity and residency budget

ESTIMATE — For setup `K`, proving `P`, startup overhead `L`, `B` sequential proofs and negligible hits, cold-per-job time is `B(K+P)`, while a persistent service takes `L+K+BP`. With cache hits `h`, add `(B−1)h`. Throughput improvement from keys alone approaches `(K+P)/(P+h)`; increasing concurrency does not remove proof work. Report queue wait separately from service time.

ESTIMATE — Caching becomes a prerequisite once proof work improves: if only Sherlock proving becomes 10× faster, total speedup is `944.9/(62.3+88.26)=6.276×`; with a fully warm PK it is `944.9/88.26=10.706×`. A **cold** 16-proof stream with 10× proving and one original setup is `944.9/(88.26+62.3/16)=10.254×`, before other overhead. This is cross-stage arithmetic, not a claim that s1 produced those gains.

SOURCE — A single Fenrir batch has four leaves sharing one leaf key, plus N and D. Sherlock has A102, A80, P and D. [recl9-report.md](../../../raw/s1-keys/recl9-report.md), [prior-10x.md](../../../raw/s1-keys/prior-10x.md). OPEN QUESTION — How many distinct active keys and versions enter the actual server? Seven logical keys across both workflows could exceed a five-entry LRU; no observed production thrash is claimed. Separate decoding wrappers can also miss simultaneously unless initialization is coalesced by identity.

ESTIMATE — Define a prepared-key identity from canonical relation/configuration, ordered child VK digests, own VK digest, official SRS identity, k, circuit crate/build/features and prepared-format version. Use a separate device identity including basis, root/order convention, field representation and backend/context. Keep protocol/transcript/domain-separation expectations explicit; terminal Blake2b stays unchanged and inner Poseidon stays unchanged. Revalidate per-proof public statements and child bindings; cache only static work. Queued→KeysReady occurs only after the requested complete identity is available and memory is reserved, not merely after a filename lookup.

SOURCE — The official catalog has separate k12, k13, k17 and k20 extended SRS files. `ParamsKZG::downsize` truncates monomial powers but **recomputes** Lagrange powers with `g_to_lagrange`. `setup_vk` takes k from its SRS. [official-srs-catalog.md](../../../raw/s1-keys/official-srs-catalog.md), [midnight083-kzg-params.md](../../../raw/s1-keys/midnight083-kzg-params.md), [midnight-stdlib-235.md](../../../raw/s1-keys/midnight-stdlib-235.md).

ESTIMATE — Share the k20 monomial prefix with smaller circuits, but never truncate the k20 Lagrange vector to make k17/13/12 parameters. A single “largest SRS” object passed to every `setup_vk` would also promote small children to k20; use explicitly sized views/objects. No SRS trapdoor generation, alternative ceremony or skipped authenticity check is needed.

ESTIMATE — At 96 bytes/affine G1 point, one shared k20 monomial set plus Lagrange sets for k20/17/13/12 uses `96×(2×2^20+2^17+2^13+2^12) = 215,089,152 bytes = 205.125 MiB`, before G2 and bookkeeping. Two projective k20 vectors at 144 bytes/point would be **288 MiB** in host memory. Actual ABI sizes and GPU layouts must be measured. P/N/D can share same-k bases if all SRS/domain identities agree.

ESTIMATE — The prior node geometry gives prepared-key scalar memory `32 MiB×[(27+18)(2+q)+3q]`: **8.8125 GiB at q4**, **14.8125 GiB at q8**. Applying that geometry illustratively to two heavy keys gives **17.625 / 29.625 GiB**, before live trace, quotient and MSM scratch. Thus keep multiple decoded PKs in 90 GB host RAM, but normally admit one heavy GPU working set on the 32 GB card. Use actual free bytes and measured peaks; the assumed geometry does not establish P/D's sizes. Start with a 24 GiB device high-water target as a policy hypothesis, adjust after measurement, and bound host caches by bytes too.

SOURCE — NVIDIA documents that ordinary `mmap` memory is not page-locked, and pinned memory is needed for asynchronous host/device transfers. Stream-ordered allocation uses reusable pools with configurable retention. Linux mmap supplies address-space mappings; neither API promises a decoded Rust object or GPU-resident polynomial. [cuda-memory.md](../../../raw/s1-keys/cuda-memory.md), [cuda-memory-pools.md](../../../raw/s1-keys/cuda-memory-pools.md), [linux-mmap.md](../../../raw/s1-keys/linux-mmap.md).

ESTIMATE — Use a bounded pinned staging ring, not all 90 GB of host RAM. A prepared snapshot must use explicit arrays/offsets and compatibility metadata; mapping a serialized `Vec` or allocator address graph is invalid. Measure first touch and first proof together. For read rate `B_io`, avoided compute `R`, additional snapshot bytes `ΔS`, and validation overhead `V`, the break-even condition is `R > ΔS/B_io + V`. Reusing a resident decoded key usually removes more work than mapping compressed bytes.

## Published benchmarks: useful mechanisms, no transferred ratios

SOURCE — ICICLE's precomputation/batching table is explicitly **BLS12-377 on RTX 3090 Ti**, not BLS12-381 on RTX 5090. It exposes shared bases, device-location flags and a workspace model `max(scalars+indices, scalars+points+buckets)`; its memory estimates are approximate. [h2-icicle-msm-api.md](../../../raw/s1-keys/h2-icicle-msm-api.md). ESTIMATE — Use its API/memory mechanisms as experimental leads only; neither its times nor its recommended maximum precompute factor establishes the best choice with a resident Midnight quotient.

SOURCE — C-KZG's Apple M1 table reports precompute 0/9 as load **1.69/2.82 s**, compute **311.15/169.72 ms**, extra table memory **0/192 MiB**. The feature affects EIP-7594 cell-proof computation/recovery, and the C interface is single-threaded. The README does not identify the exact benchmarked cell function or domain in that table. [h2-ckzg-readme.md](../../../raw/s1-keys/h2-ckzg-readme.md). ESTIMATE — Its own illustrative break-even is `(2.82−1.69)/(.31115−.16972)=7.99`, roughly eight calls. **That is not a Midnight break-even**: cell/FK20-style work, key size, CPU and algorithm differ. It supports measuring amortization rather than assuming precomputation always helps.

## What would change the verdict

- OPEN QUESTION — If E1 shows ≥90% of VK time in one removable bottleneck, a 10× **VK-stage** target becomes credible; finite acceleration requires even more coverage. It still does not create a 10× recorded proof-chain result.
- OPEN QUESTION — If E2 shows repeated cold PK/SRS loading, cache eviction or duplicate initialization contributes far more than the historical 6.6% parent share, recompute the service-level denominator from that measured workload. A pathological cache can have a large fix; the existing records do not prove one.
- OPEN QUESTION — If other stages reach ≤88.26 s parent proving, promote resident keys and miss control to mandatory throughput infrastructure; setup then consumes a large fraction of latency.
- OPEN QUESTION — If E3 reveals >3% of complete job wall time in repeated basis normalization, transfers or allocator stalls, prioritize resident base views and pooled buffers. If it finds only the old 0.8 s file load, deprioritize mmap for speed.
- OPEN QUESTION — If measured q8 PKs plus proof scratch do not fit, prefer host-resident decoded keys with selective device arrays; do not trade working-set eviction for speculative precompute gains.
- OPEN QUESTION — A new smaller relation could reduce keygen and proving together, but the fused-terminal/k19 ideas already belong to prior work and other stages. This wave supplies no new statement-equivalence or redeployment evidence for them.
