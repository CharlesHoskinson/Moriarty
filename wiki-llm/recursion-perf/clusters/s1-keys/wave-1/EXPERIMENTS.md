# s1-keys — first experiments

SOURCE — These are **experiment specifications, not executed benchmarks**. Historical baselines and source locations are in [FINDINGS.md](FINDINGS.md). The research pass only fetched/inspected evidence and checked arithmetic. The source snapshots include the [factory CLI contract](../../../raw/s1-keys/factory-contract.md), [recl9 command implementations](../../../raw/s1-keys/recl9-keygen-caller.md), and [original report commands](../../../raw/s1-keys/recl9-report.md).

ESTIMATE — Run **E1, then E2, then E3**. E1 tests the concrete 0.8.2 regression; E2 establishes the real stream denominator; E3 is conditional on material loading/residency cost. Engineering instructions below describe the instrumentation to add during implementation; there is no already-built `s1-keybench` executable, and this document does not pretend otherwise.

## Common protocol

ESTIMATE — Use these exact recording and comparison rules:

1. Record the binary SHA-256, lockfile digest, proofs/curves/stdlib versions and source revisions, circuit build/features, relation and ordered child-VK digests, own processed VK digest, SRS file hash, k, constraint degree and extended-domain q. Use the actual 20-core/90-GB/32-GB host; record driver/CUDA versions and free device bytes. Do not print environment dumps, witnesses or wallet material.
2. Read the existing official SRS files and keys without changing them. Write result files and any new public key artifacts under `raw/s1-keys/experiments/`; do not overwrite `keys/node4`, `keys/decider`, the SRS, or contract state.
3. Later heavy execution goes through the factory. From the implementation repository root the verified invocation is:
   ```bash
   scripts/doctorwatson heavy --id S1-E1 --budget s1-keygen -- /absolute/path/to/benchmark arguments
   ```
   The benchmark path/arguments must be replaced with the implemented driver or the existing recl9 command below. The wrapper creates its normal factory traces; those writes are outside this research pass's scope, which is why no heavy command was run here. Keep factory preflight/caps and exclusive heavy execution. On failure, record a one-line hypothesis and retry with `--hypothesis`; after two failures of the same kind reduce the test. Do not install a backend as part of these measurements.
4. Use monotonic CPU wall time for the whole interval and CUDA events plus explicit completion at the end of timed GPU work. An asynchronous launch return is not completion. Report wall/CPU time, host peak RSS, device peak used/reserved bytes, page faults, H2D/D2H bytes, cache hits/misses/evictions, initialize count, and GPU fallback/dispatch counts.
5. Run one correctness pair first. If it passes, use three alternating baseline/candidate pairs for timing; no concurrent unrelated proof jobs. Report each sample, median and range, not just the best run. Freeze RNG/thread choices where relevant, but do not require identical whole proofs when lookup iteration is nondeterministic. Require identical deterministic commitments/VK and independent verifier acceptance.
6. Use local unmodified ledger-9 verification for terminal proofs and the existing negative cases. This pass does not authorize stagenet submissions or wallet effects. Full stagenet acceptance remains a later integration measurement; never relabel local acceptance as an on-chain result.

## E1 — Attribute and remove the cold VK dispatch cliff

OPEN QUESTION — Do 0.8.2's >2^19-term generic MSMs explain a material part of the recorded 622.8 s node VK interval?

SOURCE — Entry points are `keygen_node`, stdlib `setup_vk`, proofs `keygen_vk_with_k`, permutation `build_vk`, and `msm_specific`. Captures: [caller](../../../raw/s1-keys/recl9-keygen-caller.md), [stdlib](../../../raw/s1-keys/midnight-stdlib-235.md), [keygen](../../../raw/s1-keys/h1-keygen-rs.md), [permutation](../../../raw/s1-keys/midnight082-permutation-keygen.md), [0.8.2 dispatch](../../../raw/s1-keys/h1-msm082.md), [0.8.3 dispatch](../../../raw/s1-keys/midnight083-msm.md).

ESTIMATE — Exact steps:

1. Preserve the existing 0.8.2 release binary. Build an instrumented 0.8.2 control and a candidate differing **only** in the BLS12-381 dispatch predicate: remove `coeffs.len() <= (2 << 18)` from that branch, keeping zero filtering, curve-type checks and the existing BLST call. Do not replace the whole crate with 0.8.3 and attribute all changes to this one line.
2. Add exclusive spans for `cost_json`; file read/hash/parameter decode; configure/domain; floor-planner synthesis; rational inversion/selector conversion; sigma-vector construction; sigma commitments; fixed commitments; VK serialization. Within each commitment record source column index, input length, nonzero count, selected backend, normalization/conversion and MSM wall time. Log metadata, never scalar values.
3. Use the existing **same** node relation from `batches/batch-1`, `keys/leaf4`, `out/leaves-b1`, arity 4, k20. The existing executable's reproduction interface is:
   ```text
   straw-recl9 keygen-node <recl9>/batches/batch-1 <recl9>/keys/leaf4 <recl9>/out/leaves-b1 <research>/raw/s1-keys/experiments/e1/<variant>/<sample>/node4 20
   ```
   Both roots are absolute paths. Supply explicit `20` for the controlled experiment; separately record the old automatic-k cost because its 335.25 s is outside the 622.8 s VK baseline. Include one default-k control only if reproducing the 959.5 s whole-command baseline. The existing command reads SRS through its established search path; retain the official k20 hash `1cc62978558fdc1e445cd70cfd9a86ec3c2e2151b6d74811232d37faf9133ff1`.
4. Start with `RAYON_NUM_THREADS=4`, one keygen process and the same BLST build in both variants. Record BLST worker count independently; Rayon=4 is not a four-thread total cap. For a total-cap experiment use process affinity over an explicit set of available logical CPUs and record that set. After the correctness pair, compare Rayon 4/10/20 only if CPU utilization or nested-pool contention is still an unresolved concern; tune both variants equally.
5. Require byte-identical processed VK, matching public fixed/sigma polynomial digests, and matching sigma/fixed commitment points. Read the candidate VK through the unchanged reader. Use it for a node proof and complete a D proof under the original terminal VK, then verify with the pinned unmodified ledger-9 verifier. Reject wrong public inputs and a wrong-child-VK fixture through the established checks. A faster VK that changes bytes is a failed experiment.
6. Before repeating full keygens, use the recorded public fixed/sigma vectors inside a small in-process replay mode for the dispatch differential at k20 and nonzero counts `2^19−1`, `2^19`, `2^19+1`, `2^20`. Hold all other data/bases fixed, use official bases, include zero/identity edge cases, and compare exact points. This distinguishes the cutoff from synthesis overhead. Do not run a smaller *recursive relation* with truncated tables as a supposed k19 version of the same circuit.

ESTIMATE — **Deciding measurement:** `ΔVK = median(T_vk_control)−median(T_vk_candidate)` plus exclusive affected-MSM share `f`. Admit the narrow fix if all equality/acceptance checks pass and it reduces measured VK wall time by ≥10% (`≥62.28 s` on the historical scale). This is a planning threshold, not a requirement that today's control equal 622.8 s. Use today's paired control for the final ratio. A 10× VK claim requires measured candidate `≤0.1×control`; predicting it from CPU-count ratios is insufficient.

ESTIMATE — If MSMs account for only 20% of VK, even deleting them gives `1/(1−.2)=1.25×`. If synthesis dominates, shrink to a public keygen-assembly reproducer and prioritize retaining that assembly between VK/PK rather than adding another outer parallel iterator. `fixed.par_iter()` already exists for PK FFT generation.

## E2 — Measure prepared-key reuse, cold decode and concurrent misses

OPEN QUESTION — How much does the native pipeline gain from a persistent decoded-key registry, and is a prepared snapshot worth its extra I/O/memory?

SOURCE — Sherlock's prior setup/prove observation is 62.3/882.6 s; recl9 `prove_node` calls `setup_pk` per invocation. PK read reconstructs derived arrays. The fetched ledger `main` already has a five-entry LRU; deployed behavior must be identified. [prior-10x.md](../../../raw/s1-keys/prior-10x.md), [caller](../../../raw/s1-keys/recl9-keygen-caller.md), [PK reader](../../../raw/s1-keys/midnight083-plonk-mod.md), [cache](../../../raw/s1-keys/ledger-proofs-main-exact.md).

ESTIMATE — Exact steps:

1. Add a driver around the same public APIs used by the native caller: setup/read parameters, setup/read PK, `prove`, and native verification. Keep a single process and immutable `Arc`-owned prepared keys for resident runs. Record spans: queue, lookup/hash, serialized read, decompression, key read, coefficient/coset reconstruction, plan/evaluator, device preparation, prove, verify. Startup time stays inside the cold-stream denominator.
2. Compare four modes on exactly the same relation/VK/SRS and legal fixture sequence: **A** fresh `setup_pk` each job; **B** deserialize an ordinary serialized PK each job; **C** prepare once then retain the decoded key; **D** load the proposed versioned complete prepared snapshot, if implemented. If D is not implemented, report it as untested rather than timing mmap of ordinary bytes as D. Keep A/B serialization format and compression settings in the record.
3. Run `B=1,2,16` sequential requests, first with the Sherlock P key, then with the Fenrir sequence `L,L,L,L,N,D`. Leaf proofs share one key. Use the same fixture identities and fresh proof randomness in baseline/candidate; verify each output. Repeated timing fixtures do not authorize repeated settlement. Record both complete stream time and stage-only time. Use three 16-job pairs only after the short correctness pairs pass.
4. Exercise the key registry without repeated heavy proofs for the cache-policy checks: cycle the seven logical keys `A102,A80,P,D_sherlock,L,N,D_fenrir` for 16 cycles, once with a five-entry policy and once with a byte-budget policy. Record actual unique identities, hit rate and decoded bytes. This synthetic access order tests a failure mode; do not present its miss rate as the application's traffic distribution.
5. On an empty cache, issue two concurrent requests for the same full identity using distinct request wrappers; then two for different identities. The same-identity case must perform exactly **one** decode/initialization, with both requests obtaining the same prepared allocation. The distinct case must not alias. Keep this first test to key initialization, so it does not introduce uncontrolled concurrent k20 proofs. Repeat after eviction and after changing a relation/child VK/SRS/format component.
6. Test process restart separately from warm-page-cache restart. Do not drop the system page cache or claim storage-cold results without a controlled method. For snapshot D, touch every required array and include faults incurred by the first proof. Compare full-array values/digests to a freshly built PK, unchanged VK, and verifier acceptance. Record stored bytes, decoded bytes, first-job time and peak RSS. Test corrupted/truncated snapshot and wrong-format metadata rejection.

ESTIMATE — **Deciding measurements:** for unchanged historical proving, resident C should approach the **1.0706×** Sherlock setup-only ceiling; the 16-job cold-stream ceiling is **1.0659×**, before lookup/startup overhead. A much larger ratio means some other work changed or the measured service has additional cold-path cost; identify it explicitly. To earn a 10× key-stage claim, measured hit latency must be ≤one tenth of paired cold setup, with no repeated reconstruction. Keep the registry if amortized complete-stream time improves and memory remains within the reserved budget. Keep snapshot D only if *first proof included* is faster than B and C's restart path; lazy-fault deferral is not a win.

ESTIMATE — Use actual host memory availability to set a decoded-key budget; start with a 48 GiB cap only as a test policy, leaving room for witnesses, OS, page cache and temporaries. q4/q8 prepared-memory arithmetic in FINDINGS is a sizing hypothesis, not a substitute for RSS measurements. A byte LRU must account for keys still referenced by running jobs after eviction.

## E3 — Separate SRS I/O, prepared bases, device residency and precompute

OPEN QUESTION — Are repeated basis conversions/uploads or workspace allocations large enough to justify device caching or precomputation once E1's CPU baseline is corrected?

SOURCE — The official catalog supplies both bases for each k; `downsize` reconstructs the smaller Lagrange basis. NVIDIA distinguishes mappings from pinned buffers and documents reusable allocation pools. ICICLE exposes precompute/shared-base and workspace controls. [catalog](../../../raw/s1-keys/official-srs-catalog.md), [params](../../../raw/s1-keys/midnight083-kzg-params.md), [memory](../../../raw/s1-keys/cuda-memory.md), [pools](../../../raw/s1-keys/cuda-memory-pools.md), [MSM API](../../../raw/s1-keys/h2-icicle-msm-api.md).

ESTIMATE — Exact steps:

1. Use existing official k12/13/17/20 extended SRS files; verify byte lengths/hashes against the captured catalog once before timed reuse. Separately time file read, hash, checked/trusted decode according to the existing loader contract, affine/Montgomery conversion and device upload. Compare ordinary read and mmap **through the same decoder**. Do not load k25 or regenerate a ceremony for k20 work.
2. With the already installed validated GPU backend, compare three configurations: reload/convert/upload on every request; decoded host bases retained; affine host + device bases retained in one persistent CUDA context. If no validated backend is installed, report the GPU part as unrun and retain the CPU loading measurements; this experiment does not require an installation.
3. Replay the same public E1 fixed/sigma inputs. Request k20 Lagrange and monomial bases and a monomial prefix of length `2^20−1` in the real commitment order. Alternate N and D key identities at k20. Log cache identity, uploaded bytes, normalization count, and exact output points. The prefix must hit the monomial allocation with a shorter view. Separately request k12/13/17 Lagrange bases and require distinct domain-specific entries and exact CPU commitment equality.
4. Retain only immutable public material between jobs. Add bounded pinned staging (start at 64 MiB, then 256 MiB if transfer latency matters), explicit stream dependencies and a persistent allocation pool. Include final synchronization in wall time. Record actual device allocation layout, pool reserved bytes and high-water usage. Begin with one heavy job; do not infer that two fit from SRS size alone.
5. Only after resident factor-1 correctness, sweep precompute factors **1,2,4,8** and commitment batch sizes **1,2,4** supported by the installed backend. Test the actual sparse/dense distributions from keygen, not just random dense scalars. Include table generation once in each cold stream; then measure 1,16,64 repeated uses. Read the backend's documented factor/layout requirements; do not pass ICICLE parameters to a different backend with assumed semantics.
6. Run the winning configuration through one full P or N→D sequence. Measure its peak alongside live PK/quotient buffers. Re-run equality/ledger-9 verification and the same negative fixtures. If a larger precompute table evicts PK arrays, forces CPU fallback, or increases first-job or 16-job wall time, reject it even if the isolated MSM kernel is faster.

ESTIMATE — **Deciding measurements:** promote base residency if whole-job wall time improves ≥3% against the matched corrected-CPU/GPU control and the saving is explained by conversion/transfer/cache counters. File I/O alone was 0.8 s in the historical 959.5 s node keygen, so that observation does not meet the threshold. Precompute is admitted only where measured `m×(t_plain−t_pre) > C_pre` and the complete 16-job sequence improves within the device budget. Report stage/stream ratios separately; no extrapolation from C-KZG's Apple M1 table or ICICLE's BLS12-377/3090 Ti figures.
