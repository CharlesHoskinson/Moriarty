# D-004: One universal key set

- Status: accepted
- Authority: OWNER
- Legacy IDs: hard rule; CPR-003; GP-1

## Context and Problem Statement

Native Compact needs one verifier key per entry. Sherlock must accept every program with the same keys.

## Decision Drivers

- CPR-003 (processor-final).
- GP-001: a new program needs no new key, contract or ceremony.
- odin r10 probe: `n1_pre_hash_equals_universal_n1` true for a05, t02, s01, d04, z02 (LIST.md).

## Considered Options

- One internal-recursive key, one `L` key, one wrap key; per-program keys under `key_root` in `prog_d`.
- A key menu per chip set or per schedule.

## Decision Outcome

One universal key set; one rekey (T25) regenerates it once.

Authority: OWNER. Owner hard rule (LOOP.md line 102).

### Consequences

- Good: One wrap VK on chain for every program.
- Bad: A change to any universal layer is a rekey of everything.

## Confirmation

- outcome: RSL-001, EUI-002, EUI-003, EUF-009. Status: planned unless the cited requirement reads MEASURED.
- conformance: RKY-001, RKY-002, MYC-KEY-001, MYC-KEY-002, MYC-SEAL-015; slice B UKS requirements. Status: planned unless the cited requirement reads MEASURED.

## Pros and Cons of the Options

### One internal-recursive key, one `L` key, one wrap key; per-program keys under `key_root` in `prog_d`

- Good: A program is data.
- Bad: Every app must fit the universal leaf (the 6-or-9 AIR bucket, D-017).

### A key menu per chip set or per schedule

- Good: Less pressure on the leaf verifier.
- Bad: Narrows GP-1; the owner withdrew the schedule menu (D-014) and the KeyBind chain (O10).

### Reconsideration

The owner changes the rule.
