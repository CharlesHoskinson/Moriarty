# Design: program completion contracts

## Inputs and dependencies

Use the source XML as the program authority.
Use the roadmap for dated implementation status.
Use existing accepted package manifests as dependency evidence.

## Architecture

Separate each sprint into a capability specification.
Keep release-gate criteria in a distinct capability.
Refine S02 Candidate A through its eight dedicated changes.
Keep EARS requirements independent from recorded execution status.

## Outputs

Produce source-pinned manifests and recomputed results during each future sprint.
Do not predeclare successful output hashes.

## Trust and failure handling

No stored success flag establishes acceptance.
Missing Council, model checking, or ACTUS evidence blocks the corresponding claim.
An unavailable tool does not establish an architectural counterexample.

## Rollback and semantic scope

Use reviewed revert commits when rollback is required.
Preserve original source receipts.
Do not change Core scope outside an accepted semantic motion.
