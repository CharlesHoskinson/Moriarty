## Decisions

**Supported profile.** Start with the assessment's bounded-atomic source and generated kernel interface. Use a versioned application package for order policies and their custody adapter. Reuse the existing receipt decoder and signed-call work where their target and statement match. Record source bytes, compiler, generated kernel, ZKIRv3, verifier key, contract address, network and accepted ledger rules. Treat compiler output, host inputs, indexers and external observations as untrusted until the consuming check verifies them.

**Acceptance boundary.** The owner signs the complete permitted plan or its constraints. Read current authority, order state and custody from the accepted ledger. Couple authority consumption and transfers in one accepted transition. Bind each receipt to the transaction, block or strict native-local apply, pre-state and post-state. Compare all affected and unchanged accounts, supply, gross debits, fees, net credits, custody, nonces and residual duties against independently frozen expectations. Record network costs even when a refused order moves no order assets. Separate application authorization from the transaction fee payer.

**Trust and failure.** Pin the verifier and describe who can upgrade it, govern feeds, control time or deny inclusion. Reserve an owner exit beyond the execution horizon. Record the compatible source profile and lowering for staged orders. A local Core/2 resume cannot substitute for a funded second-stage transition. The ledger arbitrates competing actions. A client journal can aid restart. A client journal cannot grant the second action. Preserve a failure, refusal, unsupported payer or missing readback with its trace. Keep the corresponding claim open.

**Measurement.** Use `transaction-cost-profiles-1` and its `o1-fill` and `cancel-unfilled` workloads. Publish each setup and operation transaction, per-phase and total resource vectors, actual fee debits and finality rule. Show setup separately and include it in the full per-chain total. Keep prover time and host resources separate. Preserve the fee scenario, units and exclusions of each comparison group. Run scored samples serially. [Pinned operation profile](https://github.com/input-output-hk/SOTA-DeFiFormal-Moriarty/blob/1ced5fe1e0a83d665184bb496bea01bcb9940449/specifications/execution_cost/profiles-1.json)

For the report's Midnight cost mapping, use strict native-local ledger application. Bind the signed transaction, raw apply output, native parameters and before/after states by digest. Reconcile processed DUST events to actual same-time balance debits, including excess payment. A minimum fee or an indexer display cannot establish the paid fee. Unmapped mandatory costs keep a sample unavailable. Public settlement records retain their own finality boundary. [Assessment cost method](https://github.com/input-output-hk/SOTA-DeFiFormal-Moriarty/blob/1ced5fe1e0a83d665184bb496bea01bcb9940449/specifications/execution_cost_measurement.md)

Each sample starts from a fresh fillable order. Record shared setup separately from every order-specific approval, deposit, fill, revocation and withdrawal. Derive phase and chain totals from ordered receipts. Keep rejected probes as diagnostics. For comparison with the original cancellation group, pin its optional `transaction-cost-comparison-1` scenario and satisfy its exclusions. Otherwise use the applicable distinct group. [Cancellation comparison scenario](https://github.com/input-output-hk/SOTA-DeFiFormal-Moriarty/blob/1ced5fe1e0a83d665184bb496bea01bcb9940449/specifications/execution_cost/cancellation-comparison-1.json)
