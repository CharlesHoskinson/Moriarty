# Compact to ZKIR Pipeline

## System Context and Compiler Role

In the Midnight blockchain architecture, smart contracts are authored in Compact, a high-level, domain-specific programming language designed for privacy-preserving, zero-knowledge smart contracts (CLM-0475; SRC-0007 compiler.md:L50-75; source fact; unperformed; high; S5). Compact contracts manage two synchronized domains of state: public on-chain ledger state and private off-chain user witness data (CLM-0475; SRC-0007 compiler.md:L2645-2675; source fact; unperformed; high; S5). To enforce that off-chain state transitions adhere strictly to contract rules without disclosing private data, the contract logic is compiled down into zero-knowledge circuits expressed in the Zero-Knowledge Intermediate Representation (ZKIR) (CLM-0475; SRC-0038 docs/zkir-v3-spec.md:L25-35; source fact; unperformed; high; S5).

The reference compiler for Compact is `compactc`, implemented in Chez Scheme and maintained in repository `LFDT-Minokawa/compact` at pinned commit `11e7ec5abeecb99297c4faa74d30ef9adc7b51f3` (dated 2026-09-01, Source ID SRC-0007) (CLM-0476; SRC-0007 CHANGELOG_compactc.md:L50-60; source fact; unperformed; high; S5). The compiler translates a single Compact source file (`.compact`) into a multi-artifact compilation directory containing (CLM-0476; SRC-0007 compiler/compactc.ss:L25-35; source fact; unperformed; high; S5):
1. **Application-Level TypeScript/JavaScript Bindings:** A TypeScript declaration file (`.d.ts`), a CommonJS/ESM JavaScript module (`.js`), and a debugging source map (`.js.map`) for client applications, wallets, and dApps (CLM-0476; SRC-0007 compiler.md:L2650-2675; source fact; unperformed; high; S5).
2. **Circuit Definitions (ZKIR):** Standalone JSON circuit files (`.zkir`) defining straight-line arithmetic relations for each exported contract circuit (CLM-0476; SRC-0007 compiler/passes.ss:L140-152; source fact; unperformed; high; S5).
3. **Prover and Verifier Keys:** Serialized cryptographic key material (`.prover` and `.verifier`) generated by invoking the `zkir compile-many` CLI tool on the emitted circuit files (CLM-0476; SRC-0007 compiler/passes.ss:L153-168; source fact; unperformed; high; S5).
4. **Contract Info Metadata:** A structured metadata file (`contract-info.json`) recording type signatures, contract declarations, and circuit hashes for cross-contract validation (CLM-0476; SRC-0007 compiler/passes.ss:L145-147; source fact; unperformed; high; S5).

## Nanopass Architecture of `compactc`

The Compact compiler is organized as a series of small, single-responsibility compiler passes built using the Nanopass framework for Chez Scheme (CLM-0477; SRC-0007 compiler.md:L50-90; source fact; unperformed; high; S5). Every pass accepts an abstract syntax tree in a well-defined intermediate language and outputs an equivalent tree in the same or a successor intermediate language (CLM-0477; SRC-0007 compiler.md:L73-82; source fact; unperformed; high; S5).

The primary intermediate languages defined in `compiler/langs.ss` follow this progression:
1. `Lparser`: Preserves complete token-level syntactic structure, comments, and character source offsets directly from the lexer (CLM-0477; SRC-0007 compiler.md:L147-158; source fact; unperformed; high; S5).
2. `Lsrc`: Core source AST where tokens are normalized into semantic bytevectors, symbols, and literals (CLM-0477; SRC-0007 compiler.md:L159-168; source fact; unperformed; high; S5).
3. `Lnoinclude`: AST with all `include` directives recursively resolved and integrated (CLM-0477; SRC-0007 compiler.md:L169-172; source fact; unperformed; high; S5).
4. `Lsingleconst`: Decomposes multi-variable `const` statements into individual variable bindings.
5. `Lnopattern`: Eliminates pattern matching from function arguments, circuit parameters, and variable declarations.
6. `Lhoisted`: Hoists local variable declarations to the top of enclosing blocks.
7. `Lexpr`: Eliminates statements entirely, converting circuit bodies into pure expression trees composed of nested `let*` forms (CLM-0477; SRC-0007 compiler.md:L190-205; source fact; unperformed; high; S5).
8. `Lnoandornot`: Lowers high-level boolean operators (`and`, `or`, `not`) into primitive conditional expressions (`if`).
9. `Lpreexpand`: Incorporates ledger algebraic data type (ADT) definitions.
10. `Lexpanded`: Eliminates modules, imports, exports, and type parameters, unifying names into unique `id` records (CLM-0477; SRC-0007 compiler.md:L219-245; source fact; unperformed; high; S5).
11. `Ltypes`: The strictly typed intermediate language where all parameters, return values, variables, and expressions carry explicit type annotations and pass equivalence checking (CLM-0477; SRC-0007 compiler.md:L246-300; source fact; unperformed; high; S5).
12. `Lflattened`: Emitted by `circuit-passes.ss`; flattens complex expressions, nested calls, and unrolled loops into a flat linear sequence of primitive circuit statements suitable for ZKIR generation (CLM-0477; SRC-0007 compiler.md:L2630-2645; source fact; unperformed; high; S5).

Following `circuit-passes`, the compilation pipeline diverges into two independent backends (CLM-0478; SRC-0007 compiler.md:L117-126; source fact; unperformed; high; S5):
- The TypeScript path: `typescript-passes.ss` generates client-side JavaScript execution code, ABI encoders, and RPC wrappers via `print-typescript`.
- The circuit path: `zkir-passes.ss` or `zkir-v3-passes.ss` lowers `Lflattened` into straight-line ZKIR code via `print-zkir` or `print-zkir-v3`.

## ZKIR Versioning in the Compiler: Default v2 vs Flagged v3

A crucial empirical finding in `LFDT-Minokawa/compact` commit `11e7ec5` is that **the Compact compiler emits ZKIR version 2 by default** (CLM-0479; SRC-0007 compiler/compactc.ss:L50-52; repository observation; inspection; high; S5).

The primary CLI definition in `compiler/compactc.ss` specifies verbatim:

```text
"--feature-zkir-v3 causes the compiler to generate circuits using ZKIR version 3, overriding the default (version 2)."
```

The driver pass in `compiler/passes.ss` reflects this conditional branch (CLM-0479; SRC-0007 compiler/passes.ss:L148-151; repository observation; inspection; high; S5):

```scheme
(with-target-ports
  (map (lambda (sym) (cons sym (format "zkir/~a.zkir" sym)))
       proof-circuit-name*)
  (run-passes (if (feature-zkir-v3) zkir-v3-passes zkir-passes) circuit-ir))
```

Furthermore, when invoking the external circuit compiler CLI, `compactc` selects the binary based on the feature flag:

```scheme
(let ([res (system (format "exec ~a compile-many '~a/zkir' '~a/keys'"
                     (if (feature-zkir-v3) "zkir-v3" "zkir")
                     output-directory-pathname
                     output-directory-pathname))])
  (unless (zero? res)
    (external-errorf "zkir returned a non-zero exit status ~d" res)))
```

### Evolution in `CHANGELOG_compactc.md`

The development history recorded in `CHANGELOG_compactc.md` documents the progressive introduction of ZKIR v3 support (CLM-0480; SRC-0007 CHANGELOG_compactc.md:L50-100; source fact; unperformed; high; S5):
- **Compiler Version `0.25.114` (Language Version `0.17.103`):**
  > "Add a feature flag for ZKIR v3. This is an experimental feature flag which enables a separate circuit backend that generates a new version of ZKIR. We will not yet announce this feature (it won't even work for some time)."
- **Compiler Version `0.25.115`:**
  > "An internal change to duplicate the ZKIR v2 tests to run in ZKIR v3 mode."
- **Compiler Version `0.26.100` (Language Version `0.18.0`):**
  > "A partial refactoring of the (experimental, and not yet announced publicly) ZKIR v3 backend."

This establishes that within the pinned repository state, ZKIR v3 generation remains an opt-in experimental backend activated exclusively via `--feature-zkir-v3` (CLM-0480; SRC-0007 compiler/compactc.ss:L50-52; repository observation; inspection; high; S5).

## Lowering from `Lflattened` to `Lzkir`

The lowering of a circuit from `Lflattened` to ZKIR v3 is executed by `compiler/zkir-v3-passes.ss`, which sequences two sub-passes (CLM-0481; SRC-0007 compiler/zkir-v3-passes.ss:L37-40; repository observation; inspection; high; S5):

```scheme
(define-passes zkir-v3-passes
  (reduce-to-zkir Lzkir)
  (print-zkir-v3  Lzkir))
```

### 1. `reduce-to-zkir.ss`

The `reduce-to-zkir` pass performs the core semantic lowering (CLM-0482; SRC-0007 compiler/zkir-v3-passes/reduce-to-zkir.ss:L18-50; repository observation; inspection; high; S5):
- **SSA Register Generation:** Maps every Compact expression and intermediate value to a uniquely numbered SSA variable name using `(make-temp-id src '<name>)`.
- **Branch Elimination:** Compact `if` expressions are transformed into `cond_select` instructions. Both the then-branch and else-branch are evaluated unconditionally within the circuit, and the boolean condition multiplexes the result:
  ```scheme
  (with-output-language (Lzkir Instruction)
    `(cond_select ,out-var ,test-var ,then-var ,else-var))
  ```
- **Loop Lowering:** Compact loops (`fold` and `map` over fixed-length vectors) are unrolled completely into straight-line sequences of primitive instructions during earlier circuit passes (CLM-0482; SRC-0007 compiler.md:L245-265; source fact; unperformed; high; S5).
- **Alignment Synthesis:** Complex Compact data structures (structs, tuples, enums) are serialized into field elements using ledger alignment descriptors (`AlignmentAtom` sequences) (CLM-0482; SRC-0007 compiler/zkir-v3-passes/reduce-to-zkir.ss:L37-91; repository observation; inspection; high; S5):
  - `afield`: A single native field element.
  - `abytes n`: A byte sequence packed into field elements in chunks of 31 bytes.
  - `acompress`: Compressed representation.
  - `anative <zkir-type>`: Pseudo-alignments translated into explicit `encode` instructions before hashing (CLM-0482; SRC-0007 compiler/zkir-v3-passes/reduce-to-zkir.ss:L46-83; repository observation; inspection; high; S5).

### 2. `print-zkir-v3.ss`

The `print-zkir-v3` pass formats the AST into JSON wire format conforming to the ZKIR v3 specification (CLM-0483; SRC-0007 compiler/zkir-v3-passes/print-zkir-v3.ss:L18-58; repository observation; inspection; high; S5):
- Formats field element immediates into little-endian hex string literals:
  ```scheme
  (define (zkir-field-rep->string fr)
    (if (< fr 0) (put-string sp "-0x") (put-string sp "0x"))
    ... little-endian byte formatting ...)
  ```
- Emits the top-level circuit JSON structure (CLM-0483; SRC-0007 compiler/zkir-v3-passes/print-zkir-v3.ss:L74-78; repository observation; inspection; high; S5):
  ```scheme
  `((version . ((major . 3) (minor . 0)))
    (do_communications_commitment . ,(not (no-communications-commitment)))
    (inputs . ,inputs)
    (outputs . ,outputs)
    (instructions . ,instructions))
  ```
- Maps instructions directly to the authoritative thirty-four ZKIR v3 instructions: `add`, `assert`, `cond_select`, `constrain_bits`, `constrain_eq`, `constrain_to_boolean`, `copy`, `div_mod_power_of_two`, `ec_mul`, `ec_mul_generator`, `encode`, `from_bytes32`, `from_coordinates`, `hash_to_curve`, `impact`, `into_bytes32`, `into_coordinates`, `inv`, `jubjub_scalar_from_native`, `keccak256`, `less_than`, `mul`, `neg`, `not`, `output`, `persistent_hash`, `private_input`, `public_input`, `reconstitute_field`, `reverse_bytes`, `test_eq`, `transient_hash` (CLM-0483; SRC-0007 compiler/zkir-v3-passes/print-zkir-v3.ss:L95-180; repository observation; inspection; high; S5).

Notice that `print-zkir-v3.ss` utilizes `reverse_bytes` (from specification SRC-0038 and extract `92e8bdd3`), rather than `reverse` (from `2ffe2d1`), and does not emit `slice`, `nth`, `concat`, `load_constant`, or `sha512` (CLM-0483; SRC-0007 compiler/zkir-v3-passes/print-zkir-v3.ss:L175-180; repository observation; inspection; high; S5).

### Contrast with ZKIR v2 Artifact (`set.zkir`)

In contrast, the default ZKIR v2 artifact (`set.zkir`) emitted for the same contract circuit has a markedly different schema (CLM-0484; SRC-0007 examples/outputs/tiny.compact/zkir/set.zkir; repository observation; inspection; high; S5):
- Version header: `"version": { "major": 2, "minor": 0 }`.
- Input count: `"num_inputs": 1` (untyped scalar count, rather than typed identifier objects).
- Immediates: Emitted via dedicated `load_imm` instructions rather than inline operand literals.
- Registers: Variables are implicit integer wire indices rather than named alphanumeric registers (`%name`).

## Tooling Contract and Ledger Consumer Integration

Once circuit files are written to `<target-directory>/zkir/`, `compactc` coordinates with the prover infrastructure (CLM-0485; SRC-0007 compiler/passes.ss:L153-175; source fact; unperformed; high; S5).

### 1. Key Generation Step
Unless `--skip-zk` is passed, `compactc` invokes the external ZKIR binary:
```sh
exec zkir compile-many '<target-directory>/zkir' '<target-directory>/keys'
```
This processes each `.zkir` circuit file, computes the optimal constraint degree $k$, runs Setup to derive the prover key (`keys/<name>.prover`) and verifier key (`keys/<name>.verifier`), and serializes them in tagged binary format (CLM-0485; SRC-0006 zkir/src/main.rs:L100-145; repository observation; inspection; high; S5).

### 2. Verifier Key Fingerprinting
The compiler hashes each compiled verifier key (`keys/<name>.verifier`) using SHA-256 (CLM-0485; SRC-0007 compiler/passes.ss:L173-185; source fact; unperformed; high; S5). It embeds this cryptographic digest (`expectedVk`) directly into the generated TypeScript contract binding module:
```typescript
export const expectedVk = "3a8f9b...";
```
At runtime, client applications verify that the verifier key provided by the proving service matches `expectedVk` before accepting proof verification results.

### 3. Ledger Consumer Integration (SRC-0006)

On the consumer side, `midnight-ledger` (repository `midnightntwrk/midnight-ledger` at commit `a8ab82b95b8cb46a9e145bf8696cf40c9ae64cf0`, Source ID SRC-0006) interfaces with ZKIR via the `Zkir` trait in `transient-crypto/src/proofs.rs` (CLM-0486; SRC-0006 transient-crypto/src/proofs.rs:L150-217; repository observation; inspection; high; S5).

```rust
pub trait Zkir: Relation + Any + Send + Sync + Debug {
    fn check(&self, preimage: &ProofPreimage) -> Result<Vec<Option<usize>>, ProvingError>;
    async fn prove(
        &self,
        rng: impl Rng + CryptoRng,
        params: &impl ParamsProverProvider,
        pk: ProverKey<Self>,
        preimage: &ProofPreimage,
    ) -> Result<(Proof, Vec<Fr>, Vec<Option<usize>>), ProvingError>;
    fn k(&self) -> u8;
    async fn keygen_vk(&self, params: &impl ParamsProverProvider) -> Result<VerifierKey, anyhow::Error>;
    async fn keygen(&self, params: &impl ParamsProverProvider) -> Result<(ProverKey<Self>, VerifierKey), anyhow::Error>;
    fn load_ir_from_tagged(reader: impl Read + Seek) -> io::Result<Self>;
    fn load_prover_key_from_tagged(reader: impl Read + Seek) -> io::Result<ProverKey<Self>>;
}
```

The runtime consumer data structure is `ProofPreimage` (CLM-0487; SRC-0006 transient-crypto/src/proofs.rs:L710-730; repository observation; inspection; high; S5):
- `inputs`: Vector of native field elements passed directly to circuit inputs.
- `private_transcript`: Private witness sequence consumed by `private_input`.
- `public_transcript_inputs`: Expected public statement inputs checked by `impact`.
- `public_transcript_outputs`: Public statement return values consumed by `public_input`.
- `binding_input`: Application-level transaction binding element ($\pi[0]$).
- `communications_commitment`: Tuple $(C, \rho)$ binding contract inputs and outputs under Poseidon commit ($\pi[1]$).
- `key_location`: Identifier resolving prover and verifier keys.

During transaction creation:
1. The client executes the contract TypeScript logic, recording public/private transcripts.
2. The client constructs a `ProofPreimage`.
3. The client calls `ProofPreimage::prove::<IrSource>(&rng, &params, &resolver)`.
4. Inside `prove`, `ir.prove` executes `ir.preprocess(preimage)`, derives `pis` and `pi_skips`, compiles the circuit via `Relation::circuit`, and invokes `midnight_zk_stdlib::prove` to produce the SNARK proof.
5. The transaction containing the proof and public inputs is submitted to the Midnight network, where validators verify it against the contract's registered `VerifierKey` using `vk.verify(&PARAMS_VERIFIER, &proof, statement)`.

## Formal Verification and K Semantics Translation Validation

To achieve formal verification across the full compilation chain, the formal semantics of Compact must be related to the formal semantics of ZKIR in the K Framework (CLM-0488; SRC-0038 docs/zkir-v3-spec.md:L800-825; source fact; unperformed; high; S5).

```
+----------------------------------------------------------------------------------------------------+
|                               Translation Validation Architecture                                  |
+----------------------------------------------------------------------------------------------------+
|                                                                                                    |
|    Compact Formal Semantics (Agda Specification / K Semantics)                                     |
|    [[ C ]]_Compact (State_pre, Args) => (State_post, RetVal, Transcripts)                          |
|                                                                                                    |
|                                     |                                                              |
|                                     | Translation Equivalence Theorem                              |
|                                     v                                                              |
|                                                                                                    |
|    ZKIR Formal Semantics (K Framework)                                                             |
|    <k> compactc(C) </k> <transcripts> Transcripts </transcripts>                                   |
|    => <publicInputs> pi </publicInputs> <outputs> RetVal </outputs>                                |
|                                                                                                    |
+----------------------------------------------------------------------------------------------------+
```

### The Translation Validation Predicate

For any Compact circuit $C$, input arguments $A$, and state pre-image $S$, let $\mathcal{M}_{\text{Compact}}(C, S, A)$ denote the high-level evaluation resulting in updated state $S'$, return value $R$, and transcript history $T$ (CLM-0488; SRC-0038 docs/zkir-v3-spec.md:L810-835; source fact; unperformed; high; S5).

Let $\mathcal{Z} = \text{compactc}_{\text{v3}}(C)$ be the emitted ZKIR v3 program. The translation validation property asserts that:
1. **Preprocess Equivalence:** Executing `preprocess` on $\mathcal{Z}$ with preimage constructed from $(S, A, T)$ terminates successfully, yields return value $R$ in $\omega$, and generates public inputs $\pi$ matching the contract's expected on-chain state transition $S \to S'$.
2. **Constraint Completeness:** The witness produced by preprocess satisfies all PLONKish constraints in $\mathcal{Z}$.
3. **Soundness:** Any witness satisfying the constraints of $\mathcal{Z}$ in K corresponds to a valid evaluation under $\mathcal{M}_{\text{Compact}}$.

This formal linkage guarantees that proofs verified on-chain guarantee the behavioral integrity of the original high-level Compact contract code.

For further architectural context and semantics execution rules, refer to [ZKIR Instruction Set](zkir-instruction-set.md), [ZKIR Type System](zkir-type-system.md), and [ZKIR Virtual Machine Semantics](zkir-vm-semantics.md).
