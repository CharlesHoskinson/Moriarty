# Midnight's K Framework tooling: k-rust and k-framework-ts

## Overview and repository identification

The Midnight ecosystem includes two independent, specialized tooling repositories that interact with the K Framework: `k-rust` and `k-framework-ts` (CLM-0500; SRC-0006 k-usage-grep.txt; repository observation; not reproduced; high; S4). Repository `midnightntwrk/k-rust` is pinned at commit `687ccd01e4708c495358c834c3685f297ecc8ac6` dated 2026-09-02T13:00:31-04:00 with the commit message "Add canonical K performance benchmark harness" (CLM-0500; SRC-0006 k-usage-grep.txt; repository observation; not reproduced; high; S4). Repository `midnightntwrk/k-framework-ts` is pinned at commit `120e1dba90adb04f4730f90d8c0c516b30822811` dated 2026-08-14T06:20:23+09:00 with the commit message "chore(deps): add renovate.json" (CLM-0500; SRC-0006 k-usage-grep.txt; repository observation; not reproduced; high; S4). Both repositories are maintained within the Midnight network organization to provide host-independent, embeddable, and high-performance execution, transformation, and verification facilities for K semantics without requiring standard runtime dependencies such as the Java Virtual Machine, GHC Haskell runtimes, or Python execution environments (CLM-0500; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4).

Both codebases are explicitly unofficial reimplementations and disclaim any formal affiliation with Runtime Verification, Inc. (CLM-0501; SRC-0006 k-framework-ts/README.md; source fact; not reproduced; high; S4). Repository `k-framework-ts` carries the author attribution of Sebastien Guillemot and states in its primary documentation:

> "Unofficial. This project is not affiliated with, endorsed by, or supported by Runtime Verification, Inc. or the K Framework maintainers. 'K Framework' is used here only to describe what these packages interoperate with."

Repository `k-rust` is distributed under the BSD 3-Clause License, bundling pinned canonical K Framework builtin sources under their original license terms (CLM-0501; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4). Repository `k-framework-ts` is dual-licensed under the MIT license and the Apache 2.0 license, while carrying third-party BSD 3-Clause notices for all material transcribed from the upstream K Framework and haskell-backend codebases (CLM-0501; SRC-0006 k-framework-ts/README.md; source fact; not reproduced; high; S4).

The purpose of `k-rust` is defined verbatim by its documentation:

```text
"k-rust is a Rust implementation of the K Framework. It parses K definitions and programs, runs the frontend checking and lowering pipeline, emits KORE artifacts, and includes an in-process symbolic backend."
```

The repository is designed to provide an end-to-end native compiler and symbolic execution environment that eliminates the dual JVM and Haskell runtime overhead typical of canonical K distribution workflows (CLM-0502; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4).

The purpose and scope of `k-framework-ts` are defined verbatim in its root documentation:

```text
"TypeScript utilities for working with K Framework artifacts: its serialisation formats, its tool output, and the concepts they encode, directly from TypeScript."
```

The repository focuses on providing TypeScript libraries and CLI utilities for parsing, manipulating, converting, proving, and tracing K definitions and execution terms directly within Node.js and Bun environments without invoking Python-based pyk scripts (CLM-0503; SRC-0006 k-framework-ts/README.md; source fact; not reproduced; high; S4).

The design decisions of `k-framework-ts` are governed by a strict consumer framework structured into five prioritized consumer tiers, designated C1 through C5 (CLM-0504; SRC-0006 k-framework-ts/docs/gap-analysis.md; source fact; not reproduced; high; S4). Tier C1 represents the Panopticon trace and mutation harness, requiring per-run attributable execution traces, deterministic byte-identical outputs, machine-readable JSON Lines records, and high-throughput spawning across mutants (CLM-0504; SRC-0006 k-framework-ts/docs/gap-analysis.md; source fact; not reproduced; high; S4). Tier C2 represents proof-based oracles, supporting specification-driven Starstream symbolic execution, failing proof rendering, diagnosis, resumption, and the derivation of summary lemmas from verified execution graphs (CLM-0504; SRC-0006 k-framework-ts/docs/gap-analysis.md; source fact; not reproduced; high; S4). Tier C3 represents the Lean pipeline, where the `klean` package generates shallow embeddings into Lean 4 for consumption by Nightstream (CLM-0504; SRC-0006 k-framework-ts/docs/gap-analysis.md; source fact; not reproduced; high; S4). Tier C4 explicitly specifies AI agents as the primary operators of the tooling, establishing that machine-readable, deterministic output outranks interactive human user experience, rendering terminal TUIs unnecessary while making idempotent runs and replayable failure artifacts strict requirements (CLM-0504; SRC-0006 k-framework-ts/docs/gap-analysis.md; source fact; not reproduced; high; S4). Tier C5 represents general npm consumers who require correctness and documented fidelity rather than unprincipled feature parity with pyk (CLM-0504; SRC-0006 k-framework-ts/docs/gap-analysis.md; source fact; not reproduced; high; S4).

## Architecture of k-rust

Repository `midnightntwrk/k-rust` is organized as a Cargo workspace containing five distinct crates: `k-rust`, `k-rust-kore`, `k-rust-backend`, `k-rust-napi`, and `k-rust-wasm` (CLM-0505; SRC-0006 k-rust/Cargo.toml; repository observation; not reproduced; high; S4). The workspace uses the Rust 2024 edition and targets a minimum supported Rust version of 1.85 (CLM-0505; SRC-0006 k-rust/crates/k-rust/Cargo.toml; repository observation; not reproduced; high; S4). Crate boundaries are constructed to prevent circular dependencies and to preserve KORE as the clean, host-independent semantic boundary between the frontend and the backend (CLM-0505; SRC-0006 k-rust/docs/backend-port.md; source fact; not reproduced; high; S4). The `k-rust-kore` crate defines host-independent KORE abstract syntax trees, textual parsers, printers, and binary/JSON serialization, remaining independent of frontend data structures (CLM-0505; SRC-0006 k-rust/docs/backend-port.md; source fact; not reproduced; high; S4). The `k-rust-backend` crate implements definition verification, internalization, pattern matching, substitution, builtin evaluation, equation simplification, SMT reasoning via Z3, priority-aware rewriting, and reachability proof search, depending solely on `k-rust-kore` (CLM-0505; SRC-0006 k-rust/docs/backend-port.md; source fact; not reproduced; high; S4). The top-level `k-rust` crate provides the full K frontend compilation pipeline and links `k-rust-backend` directly into the unified native binary named `krust` (CLM-0505; SRC-0006 k-rust/crates/k-rust/Cargo.toml; repository observation; not reproduced; high; S4).

```
+------------------------------------------------------------------+
|                            krust CLI                             |
+------------------------------------------------------------------+
          |                                       |
          v                                       v
+-----------------------+               +--------------------------+
|        k-rust         | ------------> |      k-rust-backend      |
|  (Frontend Compiler)  |               | (In-process Interpreter) |
+-----------------------+               +--------------------------+
          |                                       |
          +-------------------+-------------------+
                              |
                              v
                    +--------------------+
                    |    k-rust-kore     |
                    | (KORE AST & Codec) |
                    +--------------------+
                              ^
            +-----------------+-----------------+
            |                                   |
+-----------------------+           +--------------------------+
|      k-rust-napi      |           |       k-rust-wasm        |
|  (Node-API Bindings)  |           |   (WebAssembly Target)   |
+-----------------------+           +--------------------------+
```

The symbolic backend implemented in `k-rust-backend` is an in-process port of Runtime Verification's Haskell backend (CLM-0506; SRC-0006 k-rust/docs/backend-port.md; source fact; not reproduced; high; S4). In the canonical K ecosystem, symbolic execution relies on a dual-engine architecture where the C++ Booster provides a fast path for unconstrained execution and falls back to the Haskell backend for general symbolic steps (CLM-0506; SRC-0006 k-rust/docs/backend-port.md; source fact; not reproduced; high; S4). The in-process Rust backend combines both fast matching and full fallback capabilities within a single process, avoiding subprocess spawning and socket overhead (CLM-0506; SRC-0006 k-rust/docs/backend-port.md; source fact; not reproduced; high; S4). The LLVM backend remains external to the `krust` binary: invoking `krust kcompile --backend llvm` generates the required KORE definitions and compilation artifacts for consumption by an external LLVM compiler, but does not link or invoke the native LLVM toolchain directly (CLM-0506; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4).

The `k-rust-napi` crate wraps the frontend compiler and in-process backend into a Node-API dynamic library, accompanied by a typed TypeScript facade published under the package name `@midnightntwrk/k-rust` (CLM-0507; SRC-0006 k-rust/crates/k-rust-napi/package.json; repository observation; not reproduced; high; S4). The package allows Node.js hosts to parse programs, compile in-memory definitions across virtual filesystems, and execute symbolic sessions through native function calls with minimal boundary overhead (CLM-0507; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4). Native backend sessions managed via `compileBackend` or `createBackend` expose persistent execution, simplification, implication checking, model extraction, and reachability proving, while caching Z3 preludes per active module (CLM-0507; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4).

The `k-rust-wasm` crate exposes the portable subset of the frontend and backend to WebAssembly and browser environments via `wasm-bindgen`, packaged as `@midnightntwrk/k-rust-wasm` (CLM-0508; SRC-0006 k-rust/crates/k-rust-wasm/package.json; repository observation; not reproduced; high; S4). The WebAssembly package compiles against `wasm32-unknown-unknown` with default features disabled, omitting statically linked Z3, MPFR floating-point folding, and clock-dependent step timeouts (CLM-0508; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4). Parsing and compilation remain synchronous in WebAssembly after asynchronous module initialization (CLM-0508; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4). Concrete execution and inductive proofs operate in-process within WebAssembly, whereas queries that strictly require SMT solving or host clocks fail explicitly with structured diagnostic errors (CLM-0508; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4).

The command-line tool `krust` is built from the `k-rust` crate with the native `cli` feature enabled, which activates statically linked Z3 version 0.20.2 and MPFR support (CLM-0509; SRC-0006 k-rust/Cargo.toml; repository observation; not reproduced; high; S4). Statically linking Z3 eliminates external dynamic library dependencies such as `libz3.dylib` or `libz3.so`, allowing `krust` to perform frontend sort disambiguation and backend SMT satisfiability checks without invoking a standalone `z3` binary (CLM-0509; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4). The CLI exposes subcommands for parsing concrete syntax (`krust kast`), compiling definitions (`krust kcompile`), running concrete programs (`krust krun`), executing KORE patterns directly (`krust kore-exec`), simplifying matching logic patterns (`krust kore-simplify`), checking implications (`krust kore-implies`), finding satisfying models (`krust kore-get-model`), matching disjunctions (`krust kore-match-disjunction`), proving reachability claims (`krust kprove`), and serving the symbolic backend over a TCP socket (`krust kore-rpc`) (CLM-0509; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4).

## Architecture of k-framework-ts

Repository `midnightntwrk/k-framework-ts` is structured as a Bun monorepo comprising 19 distinct packages located under `packages/` (CLM-0510; SRC-0006 k-framework-ts/package.json; repository observation; not reproduced; high; S4). The repository enforces formatting and type-aware linting via `oxfmt` and `oxlint`, and runs all test suites across packages with `bun test` (CLM-0510; SRC-0006 k-framework-ts/README.md; source fact; not reproduced; high; S4). Sixteen packages are public and intended for independent release under the `@kframework-ts` npm scope, while three packages represent private fixture modules that are never published to npm (CLM-0510; SRC-0006 k-framework-ts/README.md; source fact; not reproduced; high; S4).

The core data model and translation packages establish the foundational term algebra and format codecs for K:
1. `packages/kast`: Implements the KAST v4 inner and outer term algebra (`KInner`, `KApply`, `KToken`, `KVariable`, `KSequence`, `KRewrite`, `KAs`, `KSort`, `KLabel`, `KDefinition`), syntactic matching, substitutions, variable extraction, and formatting (CLM-0511; SRC-0006 k-framework-ts/packages/kast/README.md; source fact; not reproduced; high; S4).
2. `packages/kast-json`: Provides a strict reader and validator for KAST JSON versions 3 and 4, decoding AST terms from `krun --output json` and compiled definition envelopes from `kompile --emit-json` (CLM-0511; SRC-0006 k-framework-ts/packages/kast-json/README.md; source fact; not reproduced; high; S4).
3. `packages/kore`: Provides parsers, compact printers, AST definitions, symbol demangling, and index structures for textual KORE and KORE-JSON v1 (CLM-0511; SRC-0006 k-framework-ts/packages/kore/README.md; source fact; not reproduced; high; S4).
4. `packages/konvert`: Bridges KAST frontend terms and KORE backend patterns, providing both a definition-free pure fold and a definition-aware six-stage lowering pipeline that inserts subsort injections and expands sequences (CLM-0511; SRC-0006 k-framework-ts/packages/konvert/README.md; source fact; not reproduced; high; S4).

Higher-level packages model constrained configurations, execution graphs, and automated reachability proof workflows:
1. `packages/cterm`: Implements immutable constrained terms (`CTerm`) pairing a cell configuration with normalized matching logic constraints, syntactic anti-unification, and an asynchronous symbolic adapter (`CTermSymbolic`) connecting to kore-rpc servers (CLM-0512; SRC-0006 k-framework-ts/packages/cterm/README.md; source fact; not reproduced; high; S4).
2. `packages/kcfg`: Models persistent symbolic execution graphs containing nodes, edges, covers, splits, and non-deterministic branches (`NDBranch`), along with graph minimization algorithms and summary lemma module generation (`kcfgToModule`) (CLM-0512; SRC-0006 k-framework-ts/packages/kcfg/README.md; source fact; not reproduced; high; S4).
3. `packages/proof`: Implements all-path reachability proofs (`APRProof`), implies proofs, refutation proofs, proof status derivation, digest-gated resumption, serial and concurrent proof drivers, and terminal node classification (CLM-0512; SRC-0006 k-framework-ts/packages/proof/README.md; source fact; not reproduced; high; S4).

Operational, execution, and verification utilities provide interaction with physical K installations and artifacts:
1. `packages/ktool`: Encapsulates all subprocess spawning in the workspace, managing CLI argument synthesis and execution for `kompile`, `krun`, `kast`, `kprove`, `kore-print`, and native LLVM `interpreter` binaries, as well as warm-JVM `kserver` lifecycle management (CLM-0513; SRC-0006 k-framework-ts/packages/ktool/README.md; source fact; not reproduced; high; S4).
2. `packages/k-parser`: Implements the outer parser for `.k` and literate Markdown files, parsing modules, syntax declarations, and rule bubbles into a `KDefinition` without requiring JVM execution (CLM-0513; SRC-0006 k-framework-ts/packages/k-parser/README.md; source fact; not reproduced; high; S4).
3. `packages/kompiled`: Reads and verifies the internal structure of `*-kompiled/` definition directories, parsing metadata, rule indices (`allRules.txt`), configuration variable scripts, and lazy KORE axioms (CLM-0513; SRC-0006 k-framework-ts/packages/kompiled/README.md; source fact; not reproduced; high; S4).
4. `packages/kore-rpc`: Implements a JSON-RPC 2.0 client over raw TCP sockets for communicating with `kore-rpc` and `kore-rpc-booster` symbolic execution servers (CLM-0513; SRC-0006 k-framework-ts/packages/kore-rpc/README.md; source fact; not reproduced; high; S4).
5. `packages/klean`: Translates compiled KORE definitions into shallow embeddings in Lean 4, generating complete Lake projects with sorts, subsort injections, function definitions, and rewrite relations (CLM-0513; SRC-0006 k-framework-ts/packages/klean/README.md; source fact; not reproduced; high; S4).
6. `packages/kcovr`: Parses `kompile --coverage` hit logs and maps rule execution counts to Cobertura XML coverage reports (CLM-0513; SRC-0006 k-framework-ts/packages/kcovr/README.md; source fact; not reproduced; high; S4).
7. `packages/kfuzz`: Drives property-based fuzzing against semantics using `fast-check` arbitraries evaluated by native LLVM interpreter binaries (CLM-0513; SRC-0006 k-framework-ts/packages/kfuzz/README.md; source fact; not reproduced; high; S4).
8. `packages/prooftrace`: Reads binary proof hint event streams emitted by the LLVM backend (`--llvm-proof-hint-instrumentation`), decoding rewrite ordinals, candidate substitutions, and rejected side conditions into JSON Lines traces (CLM-0513; SRC-0006 k-framework-ts/packages/prooftrace/README.md; source fact; not reproduced; high; S4).
9. `packages/bison`: Analyzes Bison grammar specifications (`parser.y`) by forcing GNU Bison 3.8.2 into one-token IELR mode to formally classify whether a grammar is conflict-free LR(1) (CLM-0513; SRC-0006 k-framework-ts/packages/bison/README.md; source fact; not reproduced; high; S4).

Three private packages vendor external semantics definitions to serve as large-scale test fixtures without publication to npm (CLM-0514; SRC-0006 k-framework-ts/README.md; source fact; not reproduced; high; S4). Package `packages/wasm-fixtures` vendors the KWasm WebAssembly semantics (`runtimeverification/wasm-semantics` at commit `212271b`), containing 1,784 syntax productions, 302 sorts, 2,062 rules, 6 overloads, and 6 cell collections (CLM-0514; SRC-0006 k-framework-ts/packages/wasm-fixtures/README.md; source fact; not reproduced; high; S4). Package `packages/evm-fixtures` vendors the KEVM Ethereum Virtual Machine semantics (`runtimeverification/evm-semantics` version `v1.0.921`), providing 3,797 rules, 58 macro rules, and 264 alias rules for testing macro and alias desugaring (CLM-0514; SRC-0006 k-framework-ts/packages/evm-fixtures/README.md; source fact; not reproduced; high; S4). Package `packages/mir-fixtures` vendors the KMIR Rust Stable MIR semantics (`runtimeverification/mir-semantics` version `release-0.4.226`), providing 31 rules with explicit priorities across six priority values (CLM-0514; SRC-0006 k-framework-ts/packages/mir-fixtures/README.md; source fact; not reproduced; high; S4).

Every public package in `k-framework-ts` enforces independent semantic versioning and explicitly refuses to mirror upstream K release version numbers (CLM-0515; SRC-0006 k-framework-ts/docs/versioning.md; source fact; not reproduced; high; S4). Mirroring K versions was evaluated and rejected because K patch versions do not guarantee format stability, because version mirroring leaves no version space to ship transcription fixes, and because sparse K releases make version matching brittle (CLM-0515; SRC-0006 k-framework-ts/docs/versioning.md; source fact; not reproduced; high; S4). Instead, each package exports a `TRANSCRIBED_FROM` manifest recording the exact file paths, SHA-256 digests, and K releases from which the code was transcribed (CLM-0515; SRC-0006 k-framework-ts/docs/versioning.md; source fact; not reproduced; high; S4). Each package provides an on-demand `check-k <k-release>` command and programmatic API that fetches the corresponding upstream files at the specified K tag, returning exit code 0 if all files match, 1 if any file changed, 3 if a file was moved or refactored away, and 2 if the fetch failed (CLM-0515; SRC-0006 k-framework-ts/docs/versioning.md; source fact; not reproduced; high; S4).

## Supported and unsupported K subset in k-rust

Crate `k-rust` implements the complete outer syntax of the K Framework, supporting both standard `.k` definition files and literate Markdown `.md` files containing fenced K code blocks (CLM-0516; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4). The outer pipeline handles recursive `requires` directives, module imports, syntax declarations, sort synonym declarations, configuration cells, rule declarations, claim specifications, and context bubbles (CLM-0516; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4). Its inner parser is a portable Earley and chart parser that reproduces canonical K scanner winner rules, token layouts, operator priorities, left and right associativities, record productions, user-defined lists, syntactic casts, cell syntax, ambiguity factoring, and sort inference (CLM-0516; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4). In its default native configuration, sort inference for ambiguous or parametric grammar rules is discharged through an embedded Z3 solver instance (CLM-0516; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4).

The lowering pipeline in `k-rust` compiles parsed K definitions into backend KORE definitions through an ordered series of compiler passes (CLM-0517; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4). The pipeline performs import resolution, structural checks, configuration model expansion, subsort injection synthesis, and `ModuleToKORE` translation (CLM-0517; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4). When compiling a definition, `krust kcompile` generates three primary KORE artifacts: `definition.kore` containing the semantic rules and declarations, `syntaxDefinition.kore` containing the concrete syntax signatures, and `macros.kore` containing macro rules and aliases (CLM-0517; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4). The compiler handles ordinary rewrite rules, reachability claims, function equations, `owise` default equations, macro expansions, sort injections, algebraic axioms, no-confusion axioms, and no-junk axioms (CLM-0517; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4).

The in-process symbolic backend supports both concrete program execution and general symbolic rewriting (CLM-0518; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4). Execution supports multiple exploration strategies: all-path exploration, execution to the first branch point via `--execute-to-branch`, first-applicable rewriting via `--strategy any`, and bounded frontier capping via `--breadth` (CLM-0518; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4). State space search supports final states (`--search-final`), all reachable states (`--search-all`), single rewrite steps (`--search-one-step`), and bounded multi-step search (`--search-one-or-more-steps`) (CLM-0518; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4). Pattern matching on associative-commutative (AC) collections supports framing variables over builtin Lists, Sets, and Maps (CLM-0518; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4). The reachability prover (`krust kprove`) handles one-path and all-path reachability claims, trusted claims, circularities, branching semantic rules, depth bounds, and Z3-backed side conditions entirely in process (CLM-0518; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4).

The documentation of `k-rust` explicitly delineates features and components that are outside its current scope or not implemented:

> "The repository is a usable early implementation, not yet a universal drop-in replacement for every K command-line workflow."

The explicit limitations documented in `k-rust/README.md` include:
1. External LLVM backend: "The LLVM backend remains external. `krust kcompile --backend llvm` emits its input but does not invoke LLVM compilation; symbolic execution is handled by the in-process Rust backend." (CLM-0519; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4).
2. Context and freezer label ordering: "Context/freezer labels are semantically equivalent but can differ in numeric suffix assignment from Java when Java's `HashSet` traversal changes encounter order. The exact corpus does not normalize arbitrary user labels." (CLM-0519; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4).
3. Coverage and unsafe transforms: "Coverage instrumentation and the optional unsafe-`anywhere` removal mode are not exposed by the CLI. They are identity stages unless explicitly requested in Java." (CLM-0519; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4).
4. Language server and parser generators: "LSP, `kserver`, and Bison parser generation are outside the current CLI scope." (CLM-0519; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4).
5. Associative-commutative unification limits: "Like the reference backend, AC unification remains conservative when more than one unmatched opaque Set or Map chunk remains after common chunks are cancelled." (CLM-0519; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4).
6. Binary Java serialization: Binary serialized formats such as `compiled.bin`, `cache.bin`, and `haskellDefinition.bin` are neither read nor written by `k-rust`, which uses JSON and textual KORE exclusively (CLM-0519; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4).

When targeting WebAssembly via `k-rust-wasm` or when compiling `k-rust` with `--no-default-features`, an additional set of explicit restrictions applies (CLM-0520; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4). The portable library subset omits the native Z3 SMT solver and MPFR arbitrary-precision floating-point constant folding (CLM-0520; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4). If a definition requires parametric sort inference that crosses into the Z3-dependent boundary, the portable parser returns a structured `Z3InferenceRequired` error rather than guessing an unsound sort (CLM-0520; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4). Because canonical K's standard prelude requires Z3 inference while parsing rules, the WebAssembly build defaults `includePrelude` to false, requiring portable dependencies to be passed explicitly via virtual sources (CLM-0520; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4). Furthermore, clock-dependent step timeouts and SMT model extraction fail explicitly in WebAssembly (CLM-0520; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4).

## Validation against canonical K and differential testing

Repository `k-rust` implements a comprehensive differential validation harness against pinned canonical K Framework artifacts (CLM-0521; SRC-0006 k-rust/scripts/reference-pins.sh; source fact; not reproduced; high; S4). Reference pins are formally defined in `scripts/reference-differential.toml` and verified before test execution by `scripts/reference-pins.sh`:
- Canonical K Framework (`runtimeverification/k`): commit `4a46d1231473b599c699160132fd6e76a5c46406`, corresponding to release `v7.1.337` (CLM-0521; SRC-0006 k-rust/scripts/reference-pins.sh; source fact; not reproduced; high; S4).
- Canonical Haskell backend (`runtimeverification/haskell-backend`): commit `ad54c7a55085b726c4d3c2728242a7e0695b0439`, corresponding to release `release-0.1.155-1-gad54c7a55` (CLM-0521; SRC-0006 k-rust/docs/backend-port.md; source fact; not reproduced; high; S4).
- Upstream `scala-kore` (`runtimeverification/scala-kore`): commit `844214975c`, corresponding to release `v0.3.3` (CLM-0521; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4).
- Reference semantics checkouts: IMP at commit `683a7734`, KWasm at commit `212271bd`, KEVM at commit `5dd05ea7`, KEVM blockchain plugin at commit `651a2db5`, and KMIR at commit `4d793252` (CLM-0521; SRC-0006 k-rust/scripts/reference-differential.toml; source fact; not reproduced; high; S4).

The outer parser in `k-rust` was validated across the entire canonical K repository test suite at the pinned commit (CLM-0522; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4). The parser successfully accepted 1,499 of the 1,504 `.k` files present in upstream K (CLM-0522; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4). ## The Lean 4 export path via klean

Package `@kframework-ts/klean` generates a shallow embedding in the Lean 4 theorem prover from a compiled KORE definition (`definition.kore`) (CLM-0527; SRC-0006 k-framework-ts/packages/klean/README.md; source fact; not reproduced; high; S4). It serves as the TypeScript equivalent of `pyk.klean`, designed to feed verified semantics models into Midnight's Nightstream verification pipeline (CLM-0527; SRC-0006 k-framework-ts/docs/gap-analysis.md; source fact; not reproduced; high; S4). The package does not parse `.k` source files or invoke `kompile`; it consumes verified KORE definitions and generates a complete, buildable Lake project (CLM-0527; SRC-0006 k-framework-ts/packages/klean/README.md; source fact; not reproduced; high; S4).

The package is strictly pinned to Lean version `4.30.0` (using toolchain identifier `leanprover/lean4:v4.30.0`) and canonical K release `v7.1.337` (CLM-0528; SRC-0006 k-framework-ts/packages/klean/README.md; source fact; not reproduced; high; S4). Calling `generateKleanProject` generates a Lake project containing five core Lean modules alongside `lakefile.toml` and `lean-toolchain`:
- `<LibraryName>.lean`: Root entry module importing the rewrite module.
- `<LibraryName>/Prelude.lean`: Upstream hook prelude containing axiomatized and defined collection and arithmetic hooks.
- `<LibraryName>/Sorts.lean`: Lean inductive types corresponding to declared K sorts.
- `<LibraryName>/Inj.lean`: Subsort injection definitions and retrieval functions (`retr`).
- `<LibraryName>/Func.lean`: Lowered K function definitions and axiomatic function declarations.
- `<LibraryName>/Rewrite.lean`: Lowered rewrite relation rules.

Lowering K function rules into Lean requires reconciling a fundamental semantic mismatch: K function rules use matching logic patterns with associative-commutative matching, while Lean function pattern matching is strictly structural (CLM-0529; SRC-0006 k-framework-ts/packages/klean/README.md; source fact; not reproduced; high; S4). Package `klean` resolves this by porting upstream KLean's `Matcher` hierarchy (`src/matchers.ts`), which compiles non-structural pattern shapes into explicit pre-match guards:
- Repeated variables (`f(X, X)`): Compiled into variable renaming followed by equality guards (`match X == _Uniq0 with | true =>`).
- Subsort injections with subsorts (`f(inj{Sub, Super}(P))`): Compiled into projection retrievals (`match (@retr Sub Super) _Pat0 with | some P =>`).
- Collection element matching (`f(ListItem(H) L)` or `f(K |-> V M)`): Compiled into hook splitting operations (`(ListHook E).split` or `(MapHook K V).split`).

Function definitions are ordered by strongly connected components over their call dependencies, emitting mutual recursion blocks when cycles occur (CLM-0529; SRC-0006 k-framework-ts/packages/klean/README.md; source fact; not reproduced; high; S4).

A critical semantic property of `klean` is that its generated rewrite relation is priority-agnostic (CLM-0530; SRC-0006 k-framework-ts/packages/klean/README.md; source fact; not reproduced; high; S4). In canonical K, rules carry numerical priorities that determine execution order (CLM-0530; SRC-0006 k-framework-ts/packages/klean/README.md; source fact; not reproduced; high; S4). The Lean export lowers all rewrites into an unprioritized rewrite relation, which over-approximates K's deterministic transition system (CLM-0530; SRC-0006 k-framework-ts/packages/klean/README.md; source fact; not reproduced; high; S4). A successful proof or elaboration in Lean is therefore sound with respect to reachable states, but does not prove priority-sensitive deterministic semantics (CLM-0530; SRC-0006 k-framework-ts/packages/klean/README.md; source fact; not reproduced; high; S4).

The `klean` package resolves two distinct defects present in upstream `pyk.klean` that caused generated Lean code to fail elaboration (CLM-0531; SRC-0006 k-framework-ts/packages/klean/README.md; source fact; not reproduced; high; S4). First, upstream `pyk.klean` bound collection split leftovers at the raw hook type (such as `List (K × V)`) while the variable expected the collection sort, causing type errors; `klean` introduces `reboxCollection` to map the collection constructor over the `Option` before matching (CLM-0531; SRC-0006 k-framework-ts/packages/klean/README.md; source fact; not reproduced; high; S4). Second, upstream emitted rules where right-hand side expressions referenced variables unbound by the left-hand pattern; `klean` catches these via an `axiomatic-function-equation` diagnostic and axiomatizes the containing function to preserve Lake build validity (CLM-0531; SRC-0006 k-framework-ts/packages/klean/README.md; source fact; not reproduced; high; S4).

## The kore-rpc integration and symbolic tooling

Package `@kframework-ts/kore-rpc` provides an implementation of the JSON-RPC 2.0 protocol spoken by Haskell backend symbolic execution servers (CLM-0532; SRC-0006 k-framework-ts/packages/kore-rpc/README.md; source fact; not reproduced; high; S4). Communication uses persistent, single-flight raw TCP sockets via `tcpTransport`, with newline-delimited JSON framing (CLM-0532; SRC-0006 k-framework-ts/packages/kore-rpc/README.md; source fact; not reproduced; high; S4). Because upstream servers allocate exactly one worker thread per active socket connection, the transport serializes requests internally without pipelining (CLM-0532; SRC-0006 k-framework-ts/packages/kore-rpc/README.md; source fact; not reproduced; high; S4). Concurrent execution requires opening multiple independent TCP connections against a server started with matching GHC runtime worker threads (`GHCRTS=-N<n>`) (CLM-0532; SRC-0006 k-framework-ts/packages/kore-rpc/README.md; source fact; not reproduced; high; S4). The client implements request cancellation by sending a newline-prefixed `cancel` notification over the socket, interrupting long-running symbolic queries without terminating the TCP session (CLM-0532; SRC-0006 k-framework-ts/packages/kore-rpc/README.md; source fact; not reproduced; high; S4).

The client supports the five standardized kore-rpc methods: `execute`, `implies`, `simplify`, `get-model`, and `add-module` (CLM-0533; SRC-0006 k-framework-ts/packages/kore-rpc/README.md; source fact; not reproduced; high; S4). In contrast to pyk, which collapses implication check results into a simple boolean, `@kframework-ts/kore-rpc` preserves the full tri-state status returned by modern backend servers: `valid`, `invalid`, and `indeterminate` (CLM-0533; SRC-0006 k-framework-ts/packages/kore-rpc/README.md; source fact; not reproduced; high; S4). Preserving `indeterminate` is necessary so that higher-level provers can distinguish between an implication that was definitively refuted and one that was abandoned due to SMT timeouts or uninterpreted functions (CLM-0533; SRC-0006 k-framework-ts/packages/kore-rpc/README.md; source fact; not reproduced; high; S4).

The client implementation handles critical behavioral and protocol divergences between legacy `kore-rpc` and modern `kore-rpc-booster` proxy servers (CLM-0534; SRC-0006 k-framework-ts/packages/kore-rpc/README.md; source fact; not reproduced; high; S4). The booster proxy rejects `step-timeout` requests with error code -32003, whereas legacy `kore-rpc` supports them; the proxy returns `reason: "aborted"` when Booster cannot decide a step, whereas legacy `kore-rpc` returns an error code 6 (CLM-0534; SRC-0006 k-framework-ts/packages/kore-rpc/README.md; source fact; not reproduced; high; S4). Most importantly, the booster proxy simplifies states after rewriting and rewrites halt reasons: a `branching` result is converted to `stuck` if all next states simplify to bottom, or continues rewriting silently if only one branch survives (CLM-0534; SRC-0006 k-framework-ts/packages/kore-rpc/README.md; source fact; not reproduced; high; S4). Furthermore, variable substitutions in `get-model` responses are typed at `SortGeneratedTopCell` on Booster, but typed at the configuration state's own root sort on legacy `kore-rpc` (CLM-0534; SRC-0006 k-framework-ts/packages/kore-rpc/README.md; source fact; not reproduced; high; S4).

Repository `k-rust` implements a native, in-process kore-rpc server exposed via `krust kore-rpc <definition.kore> --server-port <port>` (CLM-0535; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4). The Rust server implements the identical JSON-RPC 2.0 wire protocol over raw TCP sockets, supporting `execute`, `simplify`, `implies`, `get-model`, and `add-module` requests (CLM-0535; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4). Added modules are assigned unique `m<sha256>` identifiers and persist in the server session across subsequent connections (CLM-0535; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4). Because `krust kore-rpc` matches the canonical server specification, TypeScript clients written with `@kframework-ts/kore-rpc` or `@kframework-ts/cterm` can connect directly to `krust` as a high-performance backend drop-in replacement (CLM-0535; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4).

For debugging and regression testing, `@kframework-ts/kore-rpc/bugreport` implements session recording compatible with pyk's `BugReport` tar archive format (CLM-0536; SRC-0006 k-framework-ts/packages/kore-rpc/README.md; source fact; not reproduced; high; S4). Recording is implemented as a transport decorator (`recordingTransport`) that captures wire bytes verbatim, bundling `definition.kore`, server version metadata, request envelopes, response envelopes, and execution sequence files into a standard GNU tar archive (CLM-0536; SRC-0006 k-framework-ts/packages/kore-rpc/README.md; source fact; not reproduced; high; S4). Unlike pyk, the TypeScript archive generator forces fixed file modes (0644), fixed timestamps (epoch 0), and zeroed user/group identifiers, ensuring that recorded test sessions are byte-identical and diffable (CLM-0536; SRC-0006 k-framework-ts/packages/kore-rpc/README.md; source fact; not reproduced; high; S4). Recorded sessions can be replayed directly using the canonical `kore-rpc-client run-tarball` executable (CLM-0536; SRC-0006 k-framework-ts/packages/kore-rpc/README.md; source fact; not reproduced; high; S4).

## Execution traces and alternative backend probes

The Panopticon execution trace specification defines ten formal requirements (R1 through R10) for machine-readable execution oracles (CLM-0537; SRC-0006 k-framework-ts/docs/execution-traces.md; source fact; not reproduced; high; S4):
- R1: Caller-owned output location without mutating compiled definition directories.
- R2: One attributable trace per program execution under concurrency.
- R3: Stable rule identity including rule ID, label, source file, line location, and declaring module.
- R4: Concrete variable-to-term substitutions captured on each rule attempt.
- R5: Monotonically ordered rule attempts.
- R6: Deterministic byte-identical trace output for identical inputs.
- R7: Machine-readable, streamable JSON Lines records.
- R8: Client-side or source-side trace filtering without renumbering indices.
- R9: Documented, reproducible runtime overhead and trace size measurements.
- R10: Preservation of trace evidence on parse failures, semantic traps, and runtime aborts.

K exposes three distinct interfaces capable of producing execution traces, each with distinct capabilities and limitations (CLM-0538; SRC-0006 k-framework-ts/docs/execution-traces.md; source fact; not reproduced; high; S4):

| Trace Interface | Ordering | Rule Identity | Variable Substitution | Owning Package |
| :--- | :--- | :--- | :--- | :--- |
| LLVM coverage logs | Monotonic | Full `UNIQUE_ID` | Not available | `@kframework-ts/kcovr` |
| kore-rpc execute logs | Monotonic | Full 64-hex rule ID | Not available (emitted as null) | `@kframework-ts/cterm` |
| LLVM proof hints | Monotonic | Ordinal resolved to rule | Full KAST v4 substitution | `@kframework-ts/prooftrace` |

LLVM coverage logs (`kompile --coverage`) append rule `UNIQUE_ID` hashes to a text file, but capture no variable bindings and require careful process-level isolation of `K_LOG_DIR` to prevent concurrent log clobbering (CLM-0538; SRC-0006 k-framework-ts/docs/execution-traces.md; source fact; not reproduced; high; S4). kore-rpc execution logs return ordered rule IDs during symbolic steps, but current Haskell and Booster servers hardcode substitution fields to null in their JSON responses (CLM-0538; SRC-0006 k-framework-ts/docs/execution-traces.md; source fact; not reproduced; high; S4).

Only the LLVM proof hint stream satisfies the complete execution trace contract including requirement R4 (CLM-0539; SRC-0006 k-framework-ts/packages/prooftrace/README.md; source fact; not reproduced; high; S4). When an LLVM interpreter is built with `--llvm-proof-hint-instrumentation`, running a program with `--proof-output` emits a binary stream of hint events (magic `HINT`, version 13) containing binary KORE 2.0 terms (magic `\x7FKR2`, version 1) (CLM-0539; SRC-0006 k-framework-ts/packages/prooftrace/README.md; source fact; not reproduced; high; S4). Package `@kframework-ts/prooftrace` parses this stream, resolves axiom ordinals against `definition.kore` declaration order, and projects each rewrite step and rejected side-condition attempt into a standardized JSON Lines record carrying full KAST v4 term substitutions (CLM-0539; SRC-0006 k-framework-ts/packages/prooftrace/README.md; source fact; not reproduced; high; S4).

To validate that concrete syntax parsers generated by K are deterministic and unambiguous, package `@kframework-ts/bison` provides formal LR(1) grammar classification (CLM-0540; SRC-0006 k-framework-ts/packages/bison/README.md; source fact; not reproduced; high; S4). Canonical K generates Bison token grammars (`parser.y`) for concrete program parsing, but Bison defaults to LALR(1) and can silently resolve shift/reduce conflicts via precedence declarations (CLM-0540; SRC-0006 k-framework-ts/packages/bison/README.md; source fact; not reproduced; high; S4). The `@kframework-ts/bison` package invokes GNU Bison 3.8.2 in an isolated environment with forced IELR mode (`--force-define=lr.type=ielr`) and inspects the resulting XML automaton (CLM-0540; SRC-0006 k-framework-ts/packages/bison/README.md; source fact; not reproduced; high; S4). It classifies a grammar as `lr1` only if the IELR automaton contains zero unresolved conflicts and zero solved conflicts, proving that parsing is deterministic and that the grammar requires no more than one token of lookahead (CLM-0540; SRC-0006 k-framework-ts/packages/bison/README.md; source fact; not reproduced; high; S4).

## Implications for a ZKIR semantics in K

The state of Midnight's K tooling leads to specific technical inferences regarding how a formal executable semantics of ZKIR in K should be structured, verified, and consumed.

First, any new ZKIR semantics in K must target canonical K Framework version `v7.1.337` (commit `4a46d1231473b599c699160132fd6e76a5c46406`) as its primary normative oracle, while treating `k-rust` compatibility as a downstream execution constraint (CLM-0546; SRC-0006 k-rust/README.md; inference; not reproduced; high; S4). Canonical K v7.1.337 is the exact reference version pinned across `k-rust`, `k-framework-ts`, and all upstream differential manifests (CLM-0546; SRC-0006 k-rust/scripts/reference-pins.sh; source fact; not reproduced; high; S4). Targeting canonical K ensures access to standard LLVM compilation, full Haskell backend reachability proving, and the complete debugging ecosystem (CLM-0546; SRC-0006 k-framework-ts/packages/ktool/README.md; inference; not reproduced; high; S4).

Second, treating `k-rust` as an execution target imposes concrete structural constraints on how the ZKIR semantics is designed (CLM-0547; SRC-0006 k-rust/README.md; inference; not reproduced; high; S4). If the ZKIR semantics is maintained within the subset supported by `k-rust`, Midnight will be able to execute ZKIR programs in-process in Rust applications, in Node.js services via `k-rust-napi`, and in browser environments via `k-rust-wasm` (CLM-0547; SRC-0006 k-rust/README.md; inference; not reproduced; high; S4). This unlocks portable client-side verification of zero-knowledge execution traces without requiring JVM or GHC Haskell installations (CLM-0547; SRC-0006 k-rust/README.md; inference; not reproduced; high; S4).

Third, to remain strictly inside the `k-rust` supported subset and avoid known backend boundaries, the ZKIR semantics must adhere to the following language design rules (CLM-0548; SRC-0006 k-rust/README.md, SRC-0006 k-framework-ts/docs/gap-analysis.md; inference; not reproduced; high; S4):
1. Restrict associative-commutative map and set matching: Avoid rules where more than one unmatched opaque Map or Set chunk variable appears after cancellation of common elements, because both `k-rust-backend` and the canonical Haskell backend reject ambiguous multi-chunk AC unification (CLM-0548; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4).
2. Avoid unsafe `anywhere` rules: Write all transition rules over explicit configuration cells rather than using arbitrary `anywhere` rules, which are not exposed by the `krust` CLI (CLM-0548; SRC-0006 k-rust/README.md; source fact; not reproduced; high; S4).
3. Ensure conflict-free LR(1) syntax: When designing concrete syntax for ZKIR instructions and program blocks, verify that the resulting grammar is strictly conflict-free LR(1) using `@kframework-ts/bison` (CLM-0548; SRC-0006 k-framework-ts/packages/bison/README.md; inference; not reproduced; high; S4). Do not rely on ambiguous GLR parsing or Bison precedence declarations to resolve syntactic ambiguity (CLM-0548; SRC-0006 k-framework-ts/packages/bison/README.md; source fact; not reproduced; high; S4).
4. Use standard user list forms: Declare instruction sequences using non-empty user lists (`NeList{Instruction, ""}`) rather than bare `List` if native Bison generation under `--bison-lists` is desired, as `List` with `--bison-lists` is rejected by K (CLM-0548; SRC-0006 k-framework-ts/packages/k-parser/README.md; source fact; not reproduced; high; S4).
5. Avoid host-clock dependencies and floating-point operations: Ensure that ZKIR execution semantics relies entirely on discrete field arithmetic and integer operations, avoiding float hooks (`FLOAT.round`) that are missing in the Haskell backend and disabled in WebAssembly builds (CLM-0548; SRC-0006 k-rust/scripts/reference-differential.toml; source fact; not reproduced; high; S4).
6. Avoid sort-parametric function rules: Ensure that function equations do not carry unbound sort parameters on their top sort, which triggers the known upstream `GenerateCoverage` compiler crash (CLM-0548; SRC-0006 k-framework-ts/docs/gap-analysis.md; source fact; not reproduced; high; S4).

Fourth, adopting canonical K and maintaining `k-framework-ts` compatibility makes several powerful downstream consumers immediately available for ZKIR (CLM-0549; SRC-0006 k-framework-ts/README.md; inference; not reproduced; high; S4):
1. Formal Lean 4 verification: The `@kframework-ts/klean` generator can compile the ZKIR KORE definition into a shallow embedding in Lean 4, providing an automated bridge to formal inductive proofs of circuit soundness and VM equivalence in Nightstream (CLM-0549; SRC-0006 k-framework-ts/packages/klean/README.md; inference; not reproduced; high; S4).
2. Automated symbolic execution and proof management: Packages `@kframework-ts/cterm`, `@kframework-ts/kcfg`, and `@kframework-ts/proof` can orchestrate symbolic execution, build KCFG execution graphs, and manage reachability proofs over ZKIR execution blocks, interfacing with either `kore-rpc-booster` or `krust kore-rpc` (CLM-0549; SRC-0006 k-framework-ts/packages/proof/README.md; inference; not reproduced; high; S4).
3. Attributable execution tracing: Compiling the ZKIR semantics with LLVM proof hint instrumentation will allow `@kframework-ts/prooftrace` to capture complete, deterministic execution traces with full variable substitutions (CLM-0549; SRC-0006 k-framework-ts/packages/prooftrace/README.md; inference; not reproduced; high; S4). These traces can serve as machine-readable oracles to validate that ZKIR constraint generation accurately reflects operational VM execution steps (CLM-0549; SRC-0006 k-framework-ts/packages/prooftrace/README.md; inference; not reproduced; high; S4).

These architectural considerations demonstrate that building the ZKIR semantics to satisfy both canonical K v7.1.337 and the `k-rust`/`k-framework-ts` toolchain enables a unified verification pipeline spanning interactive prototyping, native Rust execution, WebAssembly client evaluation, and mechanized Lean 4 proof verification.
