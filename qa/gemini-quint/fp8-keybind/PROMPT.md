## The system

A proof chain `app -> leaf -> N1 -> N2 -> N3 (recursive, N3 verifies N2 or N3 proofs) -> L -> L_Fr`. Each of leaf, N1, N2, N3 and L is an OpenVM STARK "verifier sub-circuit" that verifies child proofs. Its cached trace holds the constraint DAG of the child key; the verifying key of a layer does NOT fix that DAG (the cached commitment is per-proof data). A key of a layer is identified by a pair `VkCommit = (cached, pre)`: `cached` = the commitment of its DAG in the parent's cached trace, `pre` = the key's pre-hash.

With the recursion flag `continuations_enabled` on, the proof-shape module of the verifier sub-circuit sends, per child proof `proof_idx` (lane-src/proof_shape_sends_excerpt.rs, lane-src/pvs_sends_excerpt.rs):
- every child public value `(air_idx, pv_idx, value)` on PublicValuesBus (a second copy; the first is consumed inside the verifier);
- every child cached commitment `(air_idx, cached_idx, global_cached_idx, commit)` on CachedCommitBus;
- the child key pre-hash on PreHashBus (once per proof).
These are permutation buses: every send must be matched by exactly one receive with equal message and proof index, or the proof fails. Assume the verifier sub-circuit is sound: the values sent are the true values of the child proof it verified (the child public values, the child's cached commitment, and the pre-hash of the key that the child proof verifies under), and the child proof is valid under a key with that pre-hash whose DAG has that cached commitment. Treat hashes and commitments as injective.

`KeyBind` (AIR 0 of each node layer; last AIR of L) receives these and keeps five slots `app, leaf, n1, n2, n3` (each a VkCommit) plus `flag` and `depth` in its public values. The role of a layer is a constant (Leaf, N1, N2, N3, Root). It is a fork of OpenVM `VerifierPvsAir` (lane-src/upstream_verifier_pvs_air.rs, four slots, flags as selectors) and of the root check in `RootVerifierPvsAir` (lane-src/upstream_root_verifier_pvs_air.rs). Differences: five slots, fixed roles, no deferral, no VM public values, no range check on depth. `Root` (the layer L) pins N2 and N3 as constants and exposes `app, leaf, n1` (48 words) as L public values. Separately, `L_Fr` pins the cached commitment of L (so L verifies only a DAG of the N3 key), and `Root` pins the pre-hash it receives to the N3 pre-hash.

## The property (BIND)

Fix honest keys `A` (app), `Lf` (leaf), `K1` (N1), `K2` (N2), `K3` (N3). Let a "proof" be a tree: each node has a key (any key from a small universe including the honest ones and adversarial keys `X`, `Y` of the same shapes), a set of children, and public values. A proof of a layer key is "accepted" iff the KeyBind constraints of that key's role (adversarial keys may have ANY constraints, i.e. arbitrary public values) hold for every row under the bus semantics above. BIND: whenever L (Root, with pins `K2`, `K3`, and the L_Fr pin that L's own child DAG is `K3`) accepts, the 48 exposed words `(app, leaf, n1)` are exactly `(commit of the app key's DAG in the leaf layer, app pre)`, `(leaf DAG commit in N1, leaf pre)`, `(N1 DAG commit in N2, N1 pre)` of the keys actually used along every path of the tree, and every layer on every path from L down uses the honest key of its position (N3 ... N3, N2, N1, leaf) except that the app key and leaf key and N1 key are whatever the exposed words name (per-program keys). In particular: an adversarial key anywhere at N3/N2 positions is refused; two different app keys in one tree are refused; a tree whose exposed app commit differs from the app actually proven is refused.

## Questions (answer each with evidence)

1. Leaf, N1, N2 roles: is each slot written by exactly one layer (pre-hash half at the layer that verifies that key, cached half checked one layer up against the received cached commitment)? Is every unset slot checked unset by the parent, so that no layer can pre-set a slot above itself?
2. N3 role: do `s2`, `s31`, `s3x` with `dinv` correctly distinguish "child N2", "child N3 at depth 1", "child N3 at depth >= 2"? Can a prover choose a selector that does not match the child (e.g. `s3x` for a depth-1 child, `s31` for a deeper child, `s2` for an N3 child)? Is the absence of a depth range check safe (the depth is set by constraint at every N3 level: 1 over N2, child + 1 over N3)?
3. Mixed rows: with 2 child proofs, can the two rows have different child kinds, depths or slot values and still be accepted? (Each row is checked against the single own public-value vector.)
4. Root: with child flag 3, N2 pinned on every row, N3 pinned when `s3x`, the received cached commitment selected by `s31`/`s3x`, the received pre-hash equal to the N3 pin: is BIND true? Consider a depth-1 N3 child (its n3 slot is unset) and deeper children.
5. The cached commitment is received with `air_idx = CE_AIR_ID = 1`, `cached_idx = 0`, `global_cached_idx = 0`. The Rust driver asserts at keygen that every node key has exactly one AIR with a cached trace, at index 1, and public values only at AIR 0. Under that assumption, can any child cached commitment or child public value go unreceived (which would make the proof fail, a completeness issue) or be received with the wrong meaning (a soundness issue)?
6. Leaf role: the app (W1) has no public values and no cached traces. If an app with public values or cached traces were used, the sends are unmatched and the leaf proof fails. Confirm this fails closed.
7. Compare with upstream `VerifierPvsAir`/`RootVerifierPvsAir` and list every divergence other than the documented ones; say whether each is safe.
8. Completeness: does the honest `trace` (with the driver: a layer passes `child = (commit of child DAG in this layer, child pre-hash)`) satisfy every constraint for the chains leaf -> N1 -> N2 -> N3 (depth 1) -> N3 (depth 2) -> N3 (depth 3) -> L, and for L over depth 1 and depth 2 children?
