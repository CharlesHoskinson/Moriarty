## Tiers and counters

1. **Source evaluation:** check all named source actions; evaluate positive inputs and every source negative. Evidence observed here: two atomic first steps plus one sequential swap are Simulation results; three funded actions are FundedExpressionPrepared; ten source mutations reject GUARD_FAILED with no accepted effects/post. Repeat source evaluation of the same snapshot is allowed and proves no replay prevention.
2. **Compiled UPLC:** compile the relation from source/Core into the selected bounded backend; evaluate actual transaction contexts, exact quantity/datum/signature/validity/allocation mutations and record script hash, source/Core commitment, cost model and exunits. Hard-coded pattern IDs, expected-output flags or host assertions cannot decide acceptance. Backend arguments must be reconstructed from actual context before invoking the relation.
3. **Local real-ledger acceptance:** use an isolated funded local Cardano ledger, authentic state markers, real signed transactions, balancing, fee/min-ADA/collateral handling and ledger receipts. Positive readbacks must agree with source deltas and allocation; same-head writers accept once only. Rejecting UPLC is not equivalent to a phase1 ledger rejection. Phase2 failure can consume collateral, which must be separately expected and authorized. No public-chain financial transaction is permitted by this design.
4. **Privacy/proof correspondence:** unavailable here. A public UPLC success is not Moriarty private settlement. Any later certificate must bind network/program/genesis, actual consumed heads, exact action/outcome authority, source transition, every effect/allocation, retained liabilities and private witness commitments; prove privacy/handoff separately. SB01 consent booleans are not certificates.

## Expressivity disposition and vote

There is **no demonstrated source expressivity gap** for this bounded four-pattern suite when choosing existing atomic/1 for two assets and /5 for funded single-asset orders. Fixed-arity input/output coverage needs no new collection feature. Source /5's protected Transfer has a single declared Amount unit/settlement asset, so it cannot directly serve a general two-asset funded swap; atomic/1 already represents the selected two-asset behavior. Do not add a new profile merely to rename that existing route.

The concrete absent capability is a **backend/context relation**, not yet evidence for new surface syntax: source snapshots and allocation indices are not authenticated Cardano transaction projections, and the current factories do not compile these cases to UPLC. A necessary minimum is source-derived context binding for authentic instance heads, ledger-sorted out-references, native signatories/validity and complete injective effect allocation. If implementing that relation reveals a specific closed-Core constructor deficiency, propose that smallest versioned addition then, with old-profile regression preservation. Do not call a hand-built per-pattern validator general Moriarty support.

I vote B because it tests a falsifiable missing behavior: native acceptance of the source-derived relation and exact rejection of cheap-input reuse, reused payout, and spent pool heads. A (simulator only) cannot answer any of those transaction-context questions. C (full private backend now) expands proof/privacy scope before the public relation and effect binding have been measured. Counter to B: a manually authored Aiken validator can pass all fixture tests while diverging from source; freeze and compare the derivation and commitments, then audit held-out context mutations. B establishes a bounded public backend experiment, not the existing Midnight product's completion or private correspondence.
