## The hash algorithm, source-grounded

- `pallas-traverse/src/hashes.rs:85-89`: `ComputeHash<28> for PlutusScript<VERSION>` is `Hasher::<224>::hash_tagged(&self.0, VERSION as u8)`; for V3 the tag is the single raw byte `0x03`.
- `pallas-crypto/src/hash/hasher.rs:59,73-78`: `Hasher<224>` is Blake2b with a 28-byte digest; `hash_tagged` inputs `&[tag]` then the slice, adding no CBOR encoding (contrast NativeScript `hash_tagged_cbor`, hashes.rs:73-76).
- `pallas-primitives/src/lib.rs:186-196`: `PlutusScript<VERSION>` is a transparent `Bytes`; `PolicyId = Hash<28>`. Aiken `ast.rs:151-187` builds `conway::PlutusScript::<3>(program.to_cbor())` and serializes `compiledCode` as hex of **that same byte slice** with its hash — so the compiledCode slice (2770B, `590acf…`, b9-applied.json:22-23) is the hashed slice.

Hence R2 computes `blake2b-224(0x03 || compiledCode bytes)` via `hashlib.blake2b(..., digest_size=28)`, after a strict guard decoding the compiledCode as exactly one definite CBOR byte string (shortest-form length, exact consumption, no trailing bytes; 2767B inner flat payload). The inner flat payload is **not** hashed and no double-CBOR re-wrap is hashed; the artifact-declared hash `6a4b67e7…59c1` is only a pinned cross-check, and generation fails closed on disagreement. The generated manifest will record claimed, independently recomputed, and classification; Pallas/Aiken SHA-256 pins are audit citations there, not runtime dependencies.
