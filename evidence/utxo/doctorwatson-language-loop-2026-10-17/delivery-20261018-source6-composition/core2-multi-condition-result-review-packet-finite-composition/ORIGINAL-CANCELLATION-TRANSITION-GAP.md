# Pending-frame recovery remains a design prerequisite

At current main588d811dbbd9e88d22d3ebe90b0544672870caa0, public Core/2 load/start/resume does not define a recovery invocation on an existing pending frame. Statement has Await and existing ordinary financial forms, but no source recovery association or alternative suffix (ir.rs:122; parser.rs:333). StageOutcome has Waiting/Complete only (stage/mod.rs:159); public CLI simulate has start/resume routing (simulate.rs:59,177,210). These are source facts, not an executed unsupported-input result or an assessment of security behavior.

MPLR-005 requires distinguishing a refund of still-controlled assets from a new compensating action after committed effects, retaining unrecovered duties (partial-conditional spec:47-56). C0.1 still calls for frozen recovery judgments and C3.2 for cancellation/compensation work (tasks.md:12,27). The original MPLR005 note explicitly leaves concrete syntax and static/dynamic obligations open (:32-34). The inspected Source/6 S0 profile excludes recovery and cannot supply a Core/2 transition by inheritance. Existing Core/1 escrow-recovery actions are source-authored financial transitions, not a public pending-frame cancellation operation. A financial return transfer does not, by itself, define what happens to the prior pending computation. No cancellation success oracle or source implementation is supplied here.

Three concrete ordinary representation choices remain for future consequential design resolution:

1. A source-declared recovery action bound to one pending await, with a new typed public recovery entrypoint. Execute the real designated action against the actual pending boundary/captures; specify its complete report, frame and local-work projection. This is the recommended smallest explicit pending-frame integration slice, provided its missing lifecycle semantics are first adopted. It reuses ordinary statement evaluation but needs an explicit source association and transition contract.
2. Named alternative suffixes at the same await. The source selects delivery versus recovery continuation, and each suffix has its own complete effects/duties/work. This keeps the branch visible in the action but introduces a larger source/IR/plan/report design surface.
3. A separate ordinary user-authored refund/compensation action through existing start. This can demonstrate an explicit forward financial action now, but supplies no recovery transition for the old pending frame and must not be presented as cancellation completion. It is a separate narrower observable predicate, not implementation of the missing pending-frame capability.

Any real recovery choice must specify which source action/suffix is bound, how captures and recovery inputs are passed, which explicit financial statements refund controlled assets versus compensate committed ones, which duties remain, how previous committed prefixes and new logical work are reported, and which output/frame represents the lifecycle transition. Authority, correlation, replay/consumption, recovery races, target/proof and security decisions remain with their designated owner; this note makes none. Do not invent those choices inside tests or an oracle. The original14 staged gaps and all U0-U7/M1-M17/MC/SP/G/full-finance/composition/conditional exits remain open.

The root chose an already-supported multi-condition observation increment for immediate source preparation. Cancellation inputs in cancellation-gap-inputs/ are preserved diagnostic inputs only, deliberately outside the adopted input freeze; their unspecified recovery schedule is not executable or an expected success fixture. This note preserves the actual missing capability rather than relabeling ordinary financial action as its completion.
