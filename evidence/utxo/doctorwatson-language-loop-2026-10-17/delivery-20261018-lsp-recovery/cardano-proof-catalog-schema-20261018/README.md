# Cardano predicate catalog display proposal

This unapplied proposal gives a developer typed metadata and a loader/display example for the retained Cardano catalogue at main commit `74a909d69639df8823a527a4d608a7516ccd69a2`. It changes no repository source or public interface.

`catalogue.ts` describes each row's identity, input description, output description, public statement, profile, target, recorded evidence, assumptions and setup-identity status. `catalogue.schema.proposal.json` describes the metadata JSON shape. `catalogue.view.proposal.json` mechanically projects all **143 versioned rows / 89 source heads**, preserving the original rows. Four retained rows supply a typed `statementSchema`; the other 139 remain prose-only. No missing typed input or output schema is invented.

`example.ts` supplies a concrete loader, exact-version selection and Webs diagram adapter for `MCP-PLN-01@2` and `MCP-PLN-02@2`. Their source-defined statements have **8 and 12 fields**. `two-predicates.expected-display.json` is the expected display data, prepared from those source declarations. Both source statuses remain `experiment-disputed`. The example is about two existing catalog declarations; it does not claim two accepted proofs or deployed predicates.

The source describes P-L0's private input as body bytes B and P-M0's as body bytes/intermediate wires. Both result descriptions are “accept/reject of the relation over the typed statement; no ledger result”. The statement fields include constants and public fields; those source labels and their original ordering are preserved. Snapshot fields remain public-statement declarations rather than a newly inferred output ABI. Values supplied by a user or a proof are absent.

The loader accepts pinned public catalogue text from its caller and parses it for display. Its TypeScript assertion does not validate shape or authenticate provenance. It has no I/O, provider calls, proof verification, setup selection, acceptance policy or ledger action. The JSON Schema describes ordinary metadata shape only; no schema-validator runtime is installed or invoked. Original `binding_constraints` are carried as attributed source declarations; this proposal does not implement or judge them.

The `sourceHead` field is a mechanical projection of explicit `supersedes` references in this one retained source. Every original version remains selectable. Catalogue file SHA-256 is provenance only and is never substituted for `predicate_digest`. Setup class, VK identity, admission, selected profile and target remain null and explicitly owner-dependent; the catalogue's profile names are a vocabulary rather than a selected runtime profile. Original security prose and recorded audit references are preserved without a new judgment of their correctness or sufficiency.

The existing Webs `WebDiagram` reads `scenario.title`, `scenario.strands[].id` and `.label`, with selection and omitted-strand props. The proposal supplies those diagram fields only. The full application also expects claim, statement, authentication, limits, status, effects, dependencies and other scenario fields; no full-App compatibility is asserted. A diagram node's existence, selection or omission is display state and cannot become proof or settlement status.

The retained catalogue, the bounded inventory's **146 CAP candidates / 89 MCP head IDs / 235 pre-dedup review IDs**, and later source addenda remain separate inventories. This proposal does not recover the original42/52 lists, import all CAP predicate bodies, merge catalogue identities, assign circuits or count required setups. The source catalogue's historical status labels are retained at their source revision; later implementation or adoption can supersede a label only through separately scoped owner evidence.

All cryptographic/security interpretation, trusted-setup/key/relation judgments, field-binding and validation rules, evidence authentication and target/ledger qualification remain designated-owner work. This is ordinary developer presentation source, with no new security or trusted-setup conclusion. Normal user access remains permissionless; this proposal introduces no developer admission process.

`SOURCE-MANIFEST.json` pins the six copied public inputs and records read limits. No TypeScript/JavaScript runtime, schema validator, compiler, verifier, model, provider, web, wallet or ledger execution was performed. The loader/display behavior is specified-only and needs an ordinary integration check when such execution is assigned. No hostile tests were created. Only files in this proposal directory were written; all Git operations were read-only.
