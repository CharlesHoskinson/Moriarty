# Completed predecessor → successor: ordinary production contract proposal

Status: UNADOPTED design, source-only. Basis is main `79de664a3d16b5e0456043a530c8f33d723561a2`, never ambient HEAD. All seventy-one complete basis files and original35 MPLR notes are pinned in `SOURCE-PINS.json`. `ORIGINAL-MPLR-001-035.json` contains every original required-behavior paragraph verbatim; the complete notes and canonical EARS remain under `basis/`. No old blocker, oracle, proposal or result is replaced.

**Recommendation:** implement a production-owned `stage::sequence::Sequence` that owns the complete current financial head and every original invocation observation. It starts a successor from its actual completed predecessor through an explicit, typed frame projection; it then lifts the real stage result into the preserved whole frame. Add a public `mori compose` consumer and an adapter in the existing `mori test`; both use this same object. Arbitrary new finite chains of currently supported Core/2 programs use the same implementation. No example registry, test-owned evaluator or application-specific lowering is involved.

This proposes the ordinary local sequential operator. It does not claim full native `Step`, shared-state interleaving, atomic `Join`, asynchronous settlement, persistent authenticated handoff, or full MPLR completion. `OWNER-DEPENDENCIES.md` names the source/admission/identity/error/resource questions reserved to the designated owner. The complete normal-path contract is specified here; those dependent rules must be supplied before integration. Ordinary design adoption requires the existing substantive votes; none has been obtained for this proposal.

## Existing boundary and two concrete approaches

Current `stage::start` accepts a freshly supplied `Scenario`; `StageOutcome::Complete` supplies one segment and work/residual values. No completed-program successor operation exists. `Pair::start` starts both independent members before publication and requires disjoint whole declared domains. `Pair::resume` resumes its original member from that member's continuation. These APIs remain unchanged.

| Approach | Concrete interface connected to existing code | Advantages | Costs and limitation |
| --- | --- | --- | --- |
| A — Stateless completed-prefix transition | Add `start_successor(prefix: CompletePrefix, next: StagedProgram, action, inputs, bindings)` beside `stage::start`. `CompletePrefix` must contain every earlier outcome, whole head, effects and accounting; a single existing `Complete` is insufficient. The new public CLI must carry that full prefix between calls. | A small direct transition interface; convenient when an independently specified persistent predecessor already exists. | Introduces a new externally supplied full-prefix carrier and its admission/reopen/identity contract immediately. Every caller must retain the right predecessor rather than merely a final Snapshot. It still needs the same projection, lifting, accounting and reporting implementation. Reusing a bare `StageOutcome::Complete` silently loses earlier await segments. |
| B — Owned sequence over existing real stage calls, RECOMMENDED | Add `Sequence::plan`, `begin`, `resume`, `next`, `report` in `mori-core::stage::sequence`. The object retains the actual outputs from every call. `next` takes no Snapshot or predecessor supplied by the caller; it starts the next planned program from the owned completed head. | Directly fixes the observed boundary, retains original reports automatically, supports awaiting programs and different program schemas, and gives both public consumers one production path. Existing stage evaluation and local continuations remain authoritative for their own invocations. | Adds an explicit frame adapter and an owned prefix report. Persistent cross-process reopening is a separate owner-defined contract. Output/memory bounds and failure publication need the existing owner decisions; local ownership is not authenticated lineage or ledger uniqueness. |

Choose B. Do not implement A as a second path in this slice. A later persistent handoff may reopen B's full prefix only under its separately specified owner contract; an arbitrary JSON final head is not treated as that operation.

## Generality and execution domain

The input is a finite ordered list of invocation specifications, each selecting one action in any actually loaded Core/2 program, with explicit fresh action inputs, state/duty bindings and the existing optional per-action logical cap. A program may occur more than once. No equality of complete source schemas, distinct exact assets, hard-coded two-program limit or application whitelist is required by this ordinary sequential contract. Real stage admission still applies to each projected view. A local program unsupported by current stage admission does not become supported by this proposal.

All programs may share exact assets, accounts, state keys and duty keys along this serial order. There is at most one active pending action. Another invocation begins only after the previous one completes. There is no interleaving, simultaneous execution or rebasing of a pending continuation. Sequential source order does not create atomic multi-program settlement: the completed P prefix remains a completed prefix when Q later runs. Completion means the selected local program list completed, even when the final residual duty set is positive.

The sequence owns a full `Snapshot` as its global head. Its global state and liability names are explicit keys; every selected program has a local-to-global binding map. The global head may contain unrelated state, other exact assets, unrelated accounts and unrelated liabilities. They stay in the complete report and survive every projection/lift. A name map is not an authorization, commitment, authenticated completeness domain or namespace certificate; those judgments belong to the designated owner.

## Frame projection and lifting

For invocation i let G be the exact current whole head and B_i its declared bindings.

1. The local state view contains each declared program state under its original source name, with its value read from the mapped global key in G. The explicit opening supplies every required value once. A successor never reuses its source initializer to reset a mapped state. Separate local names may refer to one shared global state in successive programs; within one admitted view the mapping shape and type conditions must be satisfied under the eventual owner admission contract.
2. The local balance view contains **all** G balance rows whose exact AssetId is declared by this program, retaining every account, including observers. Asset identity and account strings are not renamed. Other exact-asset rows stay outside. Equal ticker/reference/scale is insufficient to merge assets.
3. The local duty view contains the existing global duty rows selected by the explicit duty binding map, under their original local names. The map also names source duties that are currently absent, so an absent row stays absent until an actual source statement creates it. Other duties stay in the global outside frame, even if they use a selected asset. No present-zero row is changed to absent. Current `stage::decode::canonical_boundary` and source-registry predicates remain in force; this proposal does not create a bypass for incoming duties that the actual stage API would not admit.
4. Inputs come only from the invocation specification. Inputs/lets/events/captures are not inserted into global persistent state. The local `Scenario` passed to the actual `stage::start` is constructed **inside this production adapter** from this projection and the specified inputs, not by the test or CLI caller from a supplied successor scenario.
5. Let F be the complete outside Snapshot omitted by the projection. Lift every original local Step.snapshot and the final boundary by applying the inverse state/duty name map and joining it to F. Balances retain their exact identities. No Step, effect, field, zero row, unselected duty or outside row is sampled or truncated. The current stage rules define the original local effect; this adapter records its global name image separately.
6. When Waiting, retain the exact original continuation. No other program executes before it completes, so the same frame stays outside that continuation on resume. `resume` calls the existing real stage API with that continuation and event. It does not synthesize a continuation from the whole head.
7. `next` starts Q only from the head retained after P's actual complete result. The caller cannot provide Q's balances, liabilities, persistent state, prior effects or prior work. All those components are owned by Sequence. Q receives only its declared fresh inputs and existing selected cap in addition to the internal projection.

Each call records its exact projection, complete outside frame, full original `stage::outcome_report` object, full lifted Step snapshots and actual whole boundary. This makes both the local and global frames observable. A projection is never advertised as a complete global view or evidence of global absence. The nested original outcome and its labels are not rewritten.

## Original history, effects and accounting

The sequence stores every original real invocation outcome once in call order. Each outcome retains its complete segment/Execution/Step/statement/value/snapshot/effect/frame/capture/continuation/residual/work fields. Latest outcomes are references into this table; history is the entire table prefix. Completing an action does not replace its earlier await segments with its final segment.

The global effect table is an ordered list of references to original call/Step/effect positions, each with the exact global name image. Effects follow real invocation order, then original source order. Repeated, zero and self effects stay present. There is no optimization, cancellation, netting, fabricated inverse or removal of previously emitted events. `WIRE-CONTRACT.md` defines exact prefix attachments and table ordering.

For each exact `(asset, account)` at every prefix, report opening/closing balance, transfer debits/credits, fees paid/received, gross debits/credits and signed-direction net change. Gross debit is the sum of Transfer amounts and Fee amounts from that account in the original observed prefix. A later credit or refund does not subtract an earlier debit. A fee received is distinct from a transfer received, and fees paid count in gross debits. Sum across accounts only in the same exact asset; never add identically named denominations from different issuers. Existing zero/self effects remain source effects even when closing minus opening is zero.

For every global liability key/identity, report opening and closing **presence** and amount, all source additions, all explicit discharges, and the original event references. Creation/increase is distinguished from discharge by the attached original Statement, not merely the sign of an Effect::Liability delta. The arithmetic is opening amount + additions − discharges = closing amount, with presence tracked separately. Explicit discharge to zero preserves the original present-zero row. Positive residuals are the complete set of positive global closing liabilities, including outside duties. No external debt, custody or native fee is inferred from these local scalar operations; current Core/2 has no mint/burn primitive, and this design does not silently add one.

## Work and reserve observations

The original local `/2` schedule remains unchanged: statement dispatch/node visits, await entry and guard work, per-action committed prefixes, cap values and every original attempted counter. A successor's local committed counter legitimately begins at zero; its sequence cumulative counters do not reset. For each call record its actual attempted amount and the latest committed amount of the selected action instance. Sum **attempted amounts per call**; sum **latest committed values per action instance**, not every repeated cumulative field. A successful false guard adds its actual attempted work and leaves successful committed work/head/frame/effects unchanged while retaining that original observation.

The proposed allocation fields make an ordinary envelope and a separate closure-reserve amount visible. On a successful ordinary trace with sufficient envelope, available ordinary work = declared ordinary allocation − cumulative attempted work, and the closure-reserve amount remains unchanged. No ordinary transition silently spends that reserve. These are accounting equations for the proposed success trace, not a new cap admission/refusal, funding, metering of adapter overhead, native fee or closure-use policy. The exact global preflight, rejected-call charges, overflow/error handling, and reserve authority are explicitly owner-dependent in `OWNER-DEPENDENCIES.md`. No claim of finite resource adequacy or native lifecycle conservation is made by these observations alone.

## Public path and implementation boundary

Add `crates/mori-core/src/stage/sequence.rs` as the production operation. Reuse actual `stage::load`, `start`, `resume`, `outcome_report` and existing typed IR. Use a small typed frame adapter and prefix-observation builder in that module; do not modify or copy the evaluator. No application-specific branch, new scheduler, external service or test-only success path is introduced.

Add `crates/mori/src/commands/compose.rs`, a `Compose` CLI variant and its ordinary dispatcher arm. `mori compose plan.json --json` loads source/opening/input/event files through existing bounded public readers, constructs the production sequence, follows its explicit start/resume/next operations, and prints the exact run report. It accepts no expected-output files. Keep native/proof/target commands out of this path. The new local feature/profile exposure and resource/error details remain proposed decisions, not current availability.

Add `commands/test/sequence_test.rs` and a distinct `moriarty-tests/sequential-proposed/1` profile. It preloads independent complete expectations, loads the **same** composition plan, and calls the same production operation driver. Expectations cannot supply successor state or history. The adapter compares every complete observation and the full public report/bytes; it never performs projection, financial accumulation or execution itself. Existing `/1`, `/2`, disjoint formats and Pair semantics remain unchanged.

`API-AND-CALLER-TRACE.md` supplies exact normal-path signatures and manifest fields; `WIRE-CONTRACT.md` specifies every new success-report field. `OPENSPEC-DELTA.md` supplies proposed EARS requirements. `EXAMPLES-AND-TESTS.md` supplies full author-worked financial prefixes and the independent-oracle requirement, not fabricated independent goldens.

## Decisions recommended for ordinary votes

SC1: choose owned Sequence over a stateless externally supplied CompletePrefix. SC2: use an explicitly bound whole global Snapshot with lossless local projection/lift, supporting differing schemas and outside frames. SC3: retain original outcome tables and complete global Step/effect prefixes with explicit source attachments. SC4: expose one production compose path reused by the existing test consumer; no expected inputs in production. SC5: preserve full per-asset/per-duty accounting and original local/cumulative-work distinction, with owner-dependent global enforcement/reserve/failure details unresolved. SC6: retain all other operators and native/private/persistent/target/identity contracts as separate requirements; no sequential result substitutes for them.

These recommendations supply one concrete design for adoption. They are not adopted semantics, implementation, execution evidence, independent expected values, security judgments or parent acceptance.
