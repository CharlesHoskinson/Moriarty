# Two-parent local all-of handoff — design proposal

Status: unadopted ordinary design, pinned to main74a909d69639df8823a527a4d608a7516ccd69a2. Nothing in this packet is implementation, admission, an independent oracle or runtime evidence. Independent design and designated-owner review must assess the proposed choices before implementation. Public developer use remains permissionless.

## Selected increment and alternatives

Recommend exactly two independently prepared, first-await Core/2 parents with disjoint complete state/asset/duty domains. Attach their actual typed start receipts to ONE opaque JoinContinuation; resume either parent through the normal stage evaluator; when both normally complete, offer an explicit handoff into one declared successor program/action. The successor starts through the genuine stage::start path. Its subsequent waits/resumes use the genuine stage APIs. This is a local typed API increment with a draft join-source declaration, not a new proof or ledger protocol.

A same-Await conjunction is smaller but does not meet the multi-parent predicate: it evaluates one event tuple against one existing frame and discards false observations. Two ordinary sequential awaits impose one source order. Existing feature-gated Pair accepts two Member starts, resumes a selected member, merges disjoint display state and reports product history; it has no typed parent-to-successor join declaration/handoff or single returned successor control object. This proposal preserves its finite disjoint restriction without claiming Pair is a general join.

Two alternatives remain reviewable: (A) recommended opaque two-parent handoff, retaining full actual start receipts and explicit successor entry; (B) a same-program first-class gather site, which would need separate accumulated-observation semantics and is not the requested independent-parent increment; (C) a shared-domain fork/join, which needs a common-origin/conflict/effect-order design and is substantially larger. This packet selects A only as a proposal. No alternative is adopted by writing this document.

## Exact positive domain

Each parent is a distinct declared module/action with exactly one Await. prepare_parent executes its real stage::start and returns an opaque PendingParent only for the first pending start. That object retains the complete actual start outcome, source Program/StagePlan reference, original Scenario and cap. Its action may commit a financial prefix before waiting. Each parent can be prepared independently; neither preparation starts the other parent. No bare Continuation import is provided: it omits earlier false/rejected attempted work and cannot by itself support a complete imported-attempt counter.

The initial join supports only two disjoint declared state-name sets, exact AssetId sets and duty-name sets. The successor declares exactly the union of those state/asset/duty identities, with ordinary source registration of incoming duty identities. Explicit successor inputs are supplied at attach; they are not guessed from parent captures. Parent captures stay scoped to their own action. The example successor starts with a real pending handoff await after ordinary assertions, so entry produces one genuine successor Continuation without manufacturing an idle site or guard success.

This first API is typed in-process ownership. JoinContinuation has private fields and no public constructor/Default/Deserialize; a complete Serialize-only report/view is exposed. JSON checkpoint decoding, admission/error ordering, arbitrary pre-existing pending-history import and durable single consumption are not supplied by this increment. Do not market an output report as a persistent wire-resume protocol. Those obligations remain open rather than being silently inferred from the typed example.

## Proposed join source and control identity

examples/release-all.join.mori defines the draft source profile moriarty-join-draft/1 with three explicit module imports, two parent labels/action selectors, availability all_observed, success all_complete, frame disjoint_union and one successor selector. load receives the complete source-text map explicitly; it performs no implicit filesystem, registry or network lookup. This source profile/syntax and optional core2-join-draft feature are proposals, unavailable on pinned main. Existing moriarty/2 syntax and its three ordinary example programs are unchanged.

JoinPlan output contains exactly format:moriarty-local-all-of-plan-draft/1, name, module declarations in source order with alias, literal source_key and each complete existing Program and filled StagePlan, the two ordered parent bindings, the successor binding, and the three explicit policy tags. Nested ExprIds keep their original per-module global arenas; no renumbering, flattening or action filtering crosses a module boundary.

ControlIdentity contains exactly format:moriarty-local-all-of-control-draft/1, join_name, the full selected policy tags, ordered parents[{label,module,program_hash,plan_hash,action}], successor{module,program_hash,plan_hash,action}, and caller-supplied instance_tag. Program/plan hashes retain their existing owner-adopted local observational meaning. The join adds no new hash algorithm or source-text hash identity. instance_tag is a display/control label, not an authenticated occurrence, nonce, freshness or uniqueness guarantee. Every JoinContinuation/report retains this entire control value. Security meaning of control identity, decoding/correlation and parent-use rules is not selected here.

## Availability and success are different

Availability is per-parent NotObserved or Observed. It becomes Observed after a normally returned parent resume outcome, including an ordinary false guard; a start alone has not observed that awaited condition. Success is per-parent Pending or Complete, with Complete determined by the genuine StageOutcome::Complete. In this one-await domain a true guard executes the remaining financial suffix and completes that parent. Complete does not mean all its financial liabilities are zero.

The declared all_observed availability predicate is true once both parent slots have observed a normal result; all_complete success is true only once both actual parent computations have completed. Two false observations therefore make results available without making the join ready. This is ordinary local result availability, not authenticated evidence. Rejection/failure/late-result classifications are outside the positive transition table and need their own owner/design work; no hostile tests or negative policy are authored here.

## One continuation and exact transitions

JoinContinuation is one owned control object with phase ParentsPending, ReadyToEnter or SuccessorPending. It retains both full parent records throughout. It does not compress a completed parent into a Bool. The public current frame contains each parent's exact site/captures, complete boundary and outcome phase; completed parent frames are idle while their complete boundaries and zero-valued duty rows remain present. In SuccessorPending the same object additionally retains the genuine successor Continuation and full actual target start history.

| Operation | Core calls | Positive output and exact state change |
| --- | --- | --- |
| prepare_parent(label,scenario,cap) | One real stage::start for that label only | Opaque PendingParent containing the complete actual first Waiting outcome, cap and opening Scenario |
| attach(plan,[left,right],inputs,cap,instance_tag) | None | ParentsPending; keep both original receipts and source-ordered parent slots; no parent re-execution, new Step or financial effect |
| resume_parent while its guard is false | One real stage::resume of that actual pending parent | Its Continuation is unchanged; other parent's entire record/frame is unchanged; join observation history/attempted counters grow, so the entire wrapper is NOT claimed unchanged |
| resume_parent that completes the first parent | One real stage::resume | Retain its complete actual segment/frame/boundary and every residual duty; other parent remains pending; no successor start |
| resume_parent that completes the remaining parent | One real stage::resume | ReadyToEnter; derive the exact disjoint union handoff boundary from both complete parent boundaries; no successor statement or synthetic success event |
| enter on ReadyToEnter | One real stage::start of the declared successor | Build Scenario from the complete union boundary plus explicit successor inputs. Preserve normal source assertions, source-registered duties, normalization and cap behavior. Example returns SuccessorPending with one actual normal successor Continuation |
| resume_successor | One real stage::resume of the actual successor Continuation | SuccessorPending or Complete according to the actual stage outcome; full parent records remain retained |

The view always exposes each parent boundary separately. Its derived union_boundary is the complete disjoint union in existing canonical state/balance/liability row order; it is a local display/input assembly, not an authenticated global predecessor or ledger state. handoff_boundary is absent until ReadyToEnter and is then exactly that union of complete parent boundaries. Successor execution.pre must equal its actual handoff boundary after normal scenario formation; examples include all target-used balance rows so no hidden zero row is needed. Parent/full source snapshots are never replaced by union projections.

No parent effects are rolled back or rerun. Full histories preserve every nested StageSegment/Execution/Step.statement/ExprId/typed value/snapshot/delta and original Step.index. Imported parent prefixes have no asserted common chronological order: they remain two labeled imported histories in declaration order for display only. after_attach history records actual join-call order and producing label. Do not flatten independent prefixes into a fictional global execution. A source-scoped effect view may label the original delta, but never remove or reorder its original per-segment vector. Both arrival orders may reach equal terminal financial frames while retaining different whole histories, each compared independently.

## Financial preservation in the examples

The document parent opens documentDuty for its input amount, also opens retainedDocumentDuty with source literal2, waits on a caller Bool, then transfers its amount and explicitly discharges documentDuty. The recipient parent similarly waits on its independent local Bool and transfers/discharges recipientDuty in a separate exact asset domain. Both are ordinary proposed source examples, not observed executions or independent numerical expectations.

The settlement source declares the exact union asset/state/duty identities. Its unused declare action supplies existing source registration of incoming identities; declaration alone performs no financial action. settle explicitly requires the two primary duties present with amount0, reaches its own real handoff await, then performs a source-written fee/transfer and emit. It never discharges retainedDocumentDuty. Thus the proposed complete checks must retain both primary duty tombstones and the remaining explicit duty across ReadyToEnter, successor waiting and final local completion. It is not a settlement certificate, and all-of does not erase debt merely because parents completed. No mint, burn, accrual, refunds, compensation or shared reserve allocation is introduced.

## Exact measured work without a counter reset

Keep every parent's original cap/profile and current local committed value, including after completion; keep the successor's independent cap/profile/local committed value. Never write a sum of parent work into successor Continuation.logical.committed: existing stage admission expects its own planned prefix. There is no new combined cap or lifetime resource policy in this proposal.

JoinWork contains imported_attempted[2] from the actual first-start receipts, post_attach_attempted[2] from every normal parent resume including false observations, current_committed[2] from the latest actual normal outcomes, successor_attempted, successor_committed, and derived core_attempted_total/core_committed_total. Core attempted total is imported attempts + both post-attach attempt sums + successor attempts. Core committed total is the two latest parent committed values + successor committed value. This is a sum of already measured Core/2 interpretation units, with aggregation tag sum-complete-local-receipts/1-draft, not a new cost profile for actual programs.

Each call reports this_call_core_attempted: the invoked stage meter result, or0 for attach (no Core invocation). enter reports the successor start's actual cost. Pure join orchestration/merge/serialization host cost is explicitly Unmeasured, not certified free or covered by Core units. False observations grow attempted totals without advancing local committed work. All parent start attempts are included exactly once; limiting imports to actual first-start receipts avoids guessing unreported past attempts. Full general history import/resource accounting remains a separate obligation.

## Complete ordinary output and proposed tests

The Serialize-only JoinReport contains exactly format:moriarty-local-all-of-report-draft/1, the existing three qualification labels, phase, full control, full current_frame, availability[2], success[2], availability_satisfied, success_satisfied, union_boundary, handoff_boundary, effective_boundary, residual, caps, work, imported_parent_reports[2] and ordered after_attach records. Each child/target report is the unchanged whole stage::outcome_report projection. Every listed root member is present. handoff_boundary is null until both parents complete and then retains that original handoff snapshot. current_frame.successor is null before enter; thereafter it retains the target frame/boundary, including idle frame after completion. union_boundary always describes the latest two parent boundaries; effective_boundary is successor boundary if started, otherwise union_boundary. residual contains positive duties of effective_boundary, while its zero tombstones remain in the complete boundary. caps contains the two original parent caps and the explicit successor cap. after_attach entries have ordinal, operation, parent (label or null) and core_report (whole actual stage report, or null for attach). Imported start reports remain a two-element source-ordered array. UInt strings and nested existing DTO encodings are unchanged; new enum spellings are snake_case. Full-state/duty/effect fields and empty/null/present conventions must be independently frozen after adoption. New report key order/ASCII/raw-byte contract is NOT inherited from ordinary simulate; proposed join tests compare entire JSON Values, while existing Core/2 output contracts remain separate.

The proposed normal test source calls only the future genuine public join API (which must internally use actual stage APIs), never mocks, a host evaluator or constructed success. It compares a complete JoinPlan including all three Programs/Plans and whole JoinReports to future independent literal files. It covers both-false availability versus success, persistence of one completed parent while the other waits, both true arrival orders, explicit successor entry, final target resume, full frame links and tombstones/residual duties. Expected files are intentionally absent; REQUIRED-ORACLE.json specifies them. No author-generated oracle, executed test, semantic RED, passing result or admission is claimed. The future feature/API does not exist on pinned main; a missing-feature/module compile failure would NOT count as the semantic RED needed before implementation.
