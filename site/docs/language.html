Current formal syntax and semantics

A program first belongs to a particular language profile. Its grammar determines the terms that can be written; its semantics determines the executions and rejections those terms denote.

Implementation reference as recorded on September 19, 2026. The profiles below have distinct scopes. A parsed program, a local evaluation and a native ledger proof are different results; the general correspondence between them remains an obligation.

The definitions are presented together so that a reader can follow the passage from a source expression to its operational meaning. The current local financial-agreement-source/5 profile supports bounded protected financial actions, while the historical repayment projection supplies a narrower reduction system. Neither definition is silently enlarged to cover the future features in the requirements agenda.

Successor source grammar (EBNF)

This is the complete syntax grammar for moriarty-financial-agreement-source/5, reproduced from the canonical EBNF. It admits uninitialized state, record and operation declarations, multiple named actions, six generic financial PRE reads, and six Ensure-only financial POST reads. Protected Originate and Accrue use nested record<Row>{...} constructors and u64(...) literals. The parser, formatter, checker and local funded evaluator support that profile. Historical full grammars remain separate: syntax/0, expression-source/1, financial-expression-source/1, agreement-source/1, agreement-source/2, agreement-source/3 and agreement-source/4. The source contract defines the /5 schema binding, Core /4 constructors, lifecycle kernel evaluation, diagnostics and work rules. The earlier expression-source contract still describes the trusted-schema one-action factory. Complete successor authoring, general K correspondence and Preview settlement through this full language profile remain open; scoped loan and swap results do not establish that complete path.

The grammar uses Extended Backus–Naur Form (EBNF) with ISO/IEC 14977 notation. Production names use letters and digits; they are names in this specification, not Moriarty source keywords.

Notation Meaning
= and ; Define and end a production
, Concatenation: match items in order
| Alternatives: match one choice
[ ... ] Optional: zero or one occurrence
{ ... } Repetition: zero or more occurrences
( ... ) Group an EBNF expression
"..." Literal source text
? ... ? A token or EOF condition defined by the lexical specification
(* ... *) A comment in the grammar specification

Quoted punctuation denotes Moriarty source text. Unquoted punctuation above belongs to EBNF; source comments instead use // or /* ... */.

The lexical specification defines the referenced tokens and their source spans. Identifiers match [A-Za-z][A-Za-z0-9_]*, are case-sensitive, and cannot be keywords. Integers are canonical unsigned decimals (0 or a nonzero digit followed by digits); strings use JSON escapes and must decode to Unicode scalar values. Only ASCII space, tab, CR and LF separate tokens as whitespace. Source comments use // or non-nesting /* ... */; a bare / is not an operator. Input must be valid UTF-8, with no BOM stripping or Unicode normalization.

The expression-source bounds extend the base syntax bounds and apply together: 65,536 source UTF-8 bytes, 64 ASCII characters per identifier, 1,024 decoded UTF-8 bytes per string, 78 digits per integer, 8,192 tokens including EOF, 8,192 AST nodes, nesting depth 64, 256 declarations, 256 statements per action including ensures, 256 action parameters, 128 collection-intrinsic arguments, and 64 ordinary call arguments or effect fields. These parser limits are separate from the atomic execution bounds and from financial runtime limits.

Syntax acceptance does not imply execution. The bounded funded source profile, moriarty-funded-source/0, uses the older moriarty-successor-syntax/0 source header and grammar through a separate preparation API. It supports a typed subset of unit, party, asset and action declarations with explicit Transfer and Repay emissions, producing local Prepared candidates. It rejects state and const declarations, requires, let, next, ensures, projections and operators, although those forms appear in its syntax/0 grammar. Its numeric values are limited to UInt128. The funded example exercises that subset; the separate syntax-only example does not implement a funded payment. Neither parsing nor local preparation establishes authorization, a proof, ledger acceptance or source/Core/K correspondence.

Operational semantics

Executable local semantics and scoped native K evidence exist. Finite matching cases do not establish a general source/Core/K/backend correspondence theorem.

Static judgments describe admissible programs. Small-step rules describe execution. K supplies executable operational definitions; financial properties and cross-layer correspondence remain separate proof obligations. The verification effort targets Midnight’s native proof stack and does not require the Lean theorem prover.

Current lifecycle boundary

The local financial-agreement-source/5 profile binds the scoped Core /4 lifecycle. It checks all actions, selects one, admits financial inputs and snapshots, evaluates the expression prefix once, executes the protected financial actions once, and evaluates the Ensure-only suffix once. PRE reads remain stable throughout the call. POST reads inspect the tentative post-state. Rejection publishes no tentative financial effects or used identifiers.

The protected operations are Transfer, Repay, Originate and Accrue. The work accounting includes expression prefix, kernel actions and suffix. This local protected financial evaluator is distinct from the optional Federated DeFi Kernel. This is a local evaluation contract; local JSON state is not ledger acceptance. See the source /5 contract and language and federation responsibilities.

The September 17 native K run matched 125 expression cases, 104 lifecycle cases and six Unicode probes. These finite results do not close general correspondence or full acceptance of the SP02 authoring and SP03 operational-semantics sprint contracts. Small-step semantics (implemented repayment subset)

This presentation uses Felleisen–Hieb reduction semantics: terms, evaluation contexts, primitive contractions, context closure and terminal answers. Felleisen and Hieb's Revised Report, §2 Definitions 2.1/2.3 and §3.1, supplies the presentation method; its metatheorems are not claims about Moriarty. The downloaded open textbooks and Redex corpus and source-linked practices provide further references.

The K definition implements the provisional moriarty-funded-repayment/0 projection: one Transfer, optionally followed by one Repay; two initial balances, one allowance, one obligation and empty used-ID lists. It supports AccrualFirst, PrincipalFirst and ProRata, with explicit none, floor or ceil conversion rounding. The numeric extension's evidence records its execution and review status. This repayment projection excludes full successor expressions and arbitrary action sequences. Later expression and lifecycle profiles are separate definitions; general correspondence proofs remain open.

The codec admits closed records and canonical UInt128 fields. K checks positive conversion mantissa and scale at most 18 before reaching the stage that computes powers or division. Invalid financial values such as zero mantissa or a huge scale reach K and reject; malformed records and unsupported collection/action shapes stop at the codec. Raw K terms outside this admitted domain are not covered.

Expression small-step semantics (40-constructor Core)

The expression contract and its static semantics define the 40-constructor Core that moriarty-expression-source/1 text elaborates to. Both Core contract documents retain proposal status with scoped independent design approval; the separately versioned expression-source/1 authoring profile is implemented. This document status imposes no registration condition on public programs. The presentation below restates their §E and §S0 as a reduction system in the same explanatory notation as the repayment section. The contract's prose remains authoritative, the runtime is TypeScript rather than K, and no correspondence between the two is proved.

Terms and frames. An action is a statement list followed by an Ensure suffix. is an unentered constructor occurrence and the same occurrence once entered; ranges over values. Every occurrence keeps its original span and node path.

In the generic alternative ranges over the constructor's evaluated operands in listed order; metadata operands are never evaluated. There is no or context: the right operand is reached only by the contractions below.

Entry and context closure. Entering a constructor occurrence costs one unit of work, including statement constructors such as Require, Let and Ensure. An occurrence that cannot be entered rejects without consuming work.

Primitive rules. For other than and , once every evaluated child has returned a value the constructor's rule from the static semantics either yields a value or a rejection code. A rejection discards the entire continuation, staged writes, locals and descriptors; the reported work is the work actually consumed.

Every rejection raised before the first E-ENTER, by admission, schema validation or typing, reports work used 0. A span that is absent, malformed or out of range is reported as the synthetic span with the original node path kept; it is never clamped. An isolated pure expression, evaluated outside an action, ends in rather than a statement result.

Boolean contractions. After the left operand returns, the four contractions fire at zero cost. A skipped right operand is never entered and produces no work or failure. A selected right operand resumes as the original occurrence at child index 1 with its own span; if it is unentered and , E-EXHAUSTED applies to it.
