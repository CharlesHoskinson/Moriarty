# Sherlock stagenet recursive-proof experiment

Status: current user priority and planned feasibility experiment, October 19, 2026. Implementation and measurements remain open. This supplements the full Sherlock goal and its existing requirements.

The immediate outcome is Sherlock deployed to Midnight stagenet and validating a real recursive proof. The largest proof of concept is a deterministic, synthetic Fenrir-derived rollup. Its report must establish what ran, the circuit degree k and actual resource costs, and what the ledger accepted. A successful literal proof is a prerequisite observation and does not establish recursion.

## Concrete integration dependency

These are different source interfaces. Do not feed the current literal SDK proof into the Fenrir child-verifier slot without implementing and validating the appropriate Sherlock integration. The current bridge also keeps its verifier key private. Resolving the actual transcript/key/circuit interface is a concrete source task for the designated owner, not a claim of compatibility or a reason to run another infrastructure loop.

Fenrir's four-transaction leaf directly constrains its synthetic wallet/transaction rules; it does not recursively verify separate wallet user proofs. Recursive verification begins at the node that verifies child leaf proofs, and the decider verifies the node and closes the accumulator. Preserve that exact distinction in the Sherlock adaptation and benchmark.

The generator requires at least eight transactions per batch, while the current recursive stager requires exactly sixteen. Its own generation/replay oracle is an internal consistency check, not the independently authored Sherlock expected-state oracle. Historical reports of deployments or timings are reference evidence, not new Sherlock results. Some older recursion spike material targets ledger 10; it is not the chosen ledger-9 path.

## Measurements

Record each proof layer separately: interpreter step or leaf, recursive parent, fixed-key wrapper when used, and terminal decider. For each, record actual k, 2^k capacity, used and lookup rows when exposed, columns, instance count, proof and key bytes, and the cost-model/library version. A padded domain capacity is not a measured row count; do not guess missing rows. Here k denotes circuit degree, while K names the semantics framework. No automatic k increase or change to existing limits is selected by this plan.

Separate parameter loading, key generation, witness construction, proving and local verification wall/CPU times; record peak RSS, thread counts, hardware, build profile, source/toolchain pins and cold/warm cache state. Persist every failure, timeout and cap; incomplete timings are censored observations. Start with one successful end-to-end sample. Repeat only the selected performance cases needed to measure variability, under the existing actual remaining resources. Do not replay unchanged passing prefixes for administration. Reuse proven history prefixes where the protocol supports it and disclose that reuse.

Count every actual native call, including the reference prover’s automatic negative verifier calls. Fenrir’s `verify_cmd` can print `false` and still return exit zero; require the actual verification predicate, not process status alone. The terminal decider is proved per submission because it binds that transaction’s call inputs. Historical Fenrir runs do not establish fit in the existing literal-proof resource class.

For stagenet record deployment and call transaction bytes, public transaction IDs, fees/DUST, target network identity and ledger/package compatibility, proof/statement hashes, anchor address, blocks, and complete before/after settlement effects. Timestamp proof-ready, submission-start, submission-acknowledged, inclusion-observed and settlement/finality-readback. Report local verification time and submission-to-inclusion/readback latency separately. RPC observations do not isolate validator proof-verification CPU time: label that metric unavailable unless instrumented node evidence actually provides it. Never label network/queue latency as pure cryptographic validation time.

The report compares transaction count, recursive depth and fan-in with k, proof bytes, prover/verifier cost and observed stagenet latency. No throughput or latency target has been supplied; publish measured distributions, sample count and failures rather than inventing a passing performance threshold. Feasibility requires actual Sherlock recursive-proof acceptance and correct settled effects for the explicitly named workload within observed target constraints. A smaller result remains useful under its exact scope.
