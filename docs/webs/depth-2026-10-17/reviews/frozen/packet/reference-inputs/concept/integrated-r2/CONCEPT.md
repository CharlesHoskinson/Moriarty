# Moriarty Webs: concept review candidate

Status: PROPOSED integrated concept, revision r2 with the terminal Opus errata applied. This document selects a coherent product explanation from eight domain studies. It adopts no schema, implementation, security conclusion, deployment permission, or release claim. The canonical public-facing maturity box is in [MESSAGING.md](MESSAGING.md). [CLAIMS-REGISTER.json](CLAIMS-REGISTER.json) records the permitted scope of individual claims.

## The concept and its useful job

**Bring the required proofs to the transition.** [ERR-26]

**Proof-carrying financial workflows for Cardano, with explicit conditions before settlement.**

This is the selected candidate positioning. The first line makes the proposed handoff useful and concrete: an application supplies the evidence a receiving script requires. On the experimental issuance route described by the source, each proof is checked when its claim is issued; the settlement transaction consumes those claims. Proof-at-consumption remains PROPOSED. [Opus ERR-12/ERR-26, V2 source-level reading only] The second explains what that evidence must concern. Amounts, exact assets, recipients, authority, fees, and continuing duties give the proof its financial meaning. Neither line promises a shipped transaction format.

A proposed Web is the script-bound collection of Strands required by the consuming contract for one transition, with all-or-nothing acceptance in a supported profile. This is a PROPOSED acceptance rule, not an implementation claim. Profiles refuse unsupported classes while universal certificates, authenticated history, private handoff, recursion, and bounded multiparent remain required future tracks. [SEC06-P01 PROPOSED, ERR-01] Each Strand is an individual proof with its claim, statement, and binding metadata. A reusable claim specification describes what is asserted and under which premises. Weaving means composing those required proofs under a stated consumer rule. A transaction must still invoke the actual validators and enforce its authorized effects.

The intended developer utility is an explicit handoff between a program, the proofs for a particular action, and the script consuming them. A dapp author can explain what the action requires. An asset issuer can identify which issuance or servicing conditions belong to a policy. A transaction builder can assemble evidence without treating opaque proof bytes as instructions. A wallet can explain what the owner authorizes and what remains owed afterward.

These are design goals, not measured adoption benefits. The concept remains useful if an initial application uses one whole-execution proof. Genuine composition needs separately identified supported relations, matching statements, and an actual required-set consumer. Naming source expressions “fee” and “liability” does not create independent proof producers. [S09 §4; Studies 02 POS-01/POS-02, 05 OPT-06, 08 ECO08-03, all PROPOSED]

## One glossary for this draft

| Term | Selected editorial meaning |
| --- | --- |
| Moriarty | The bounded financial language and its semantics, compiler, proof interfaces, verifier integration, and developer tooling. |
| Moriarty Webs / Web | Working concept name / proposed script-bound collection of required Strands for a specified action or composition. |
| Strand | An individual proof with its claim, statement, and binding metadata. An unproven requirement is not a Strand. |
| weaving | Composition under an explicit acceptance rule. It says nothing by itself about aggregation, recursion, or execution. |
| claim specification | Reusable definition of an assertion, its subject, premises, and intended relation. |
| proof instance | Concrete cryptographic artifact for an identified statement and relation under named assumptions. |
| pattern | Reusable behavior specification or template. A pattern can require multiple claims. |
| proof obligation / financial duty | A required correctness condition / a liability or continuing performance requirement. |
| claim output | Ledger output representing a claim under an identified policy. It is neither the proof nor its validator. |
| settlement | Actual target-ledger acceptance of the authorized effects under the applicable conditions. |

This resolves the studies' broader proof/claim-unit wording for editorial purposes. S01 proposes Strand as one proof. The selected definition keeps the proof essential while allowing the metadata needed to explain it. It introduces no ABI, accepted claim-kind union, or new support. A catalogue entry, arbitrary predicate, reusable pattern, UTxO, or validator is not a Strand. [S01 `/rootVocabularyProposal/Strand`, `/scope`; Study 01 LANG-01/LANG-03, PROPOSED]

Keep three assertions distinct. A concrete execution proof concerns one transition. A universal property certificate would concern every execution in a specified domain. An authenticated ledger claim concerns a fact with a named ledger-authentication path. These meanings cannot substitute for each other. The concept does not establish the latter two as supported Strand kinds. External documents and observations retain their named issuer, predicate, authentication, and freshness assumptions. [S03 “What provable intention means,” “Partial transactions and conditional settlement”; S07 `/limitations/universalPropertyCertificate`; S09 WR06]

## How an application would use a Web

The proposed journey begins with a program and a named target/profile. The application selects an action, obtains relevant predecessor state and observations, and exposes their provenance. It describes the acceptable outcome and authority limits before requesting authorization. The producer supplies proof instances for supported relations and exact statements. The proposed assembly tooling matches those Strands to requirements from the identified consumer policy.

The next artifact is a transaction candidate, not a declaration of settlement. In the reviewed, uncompiled V2 source design, C2 mints one claim per Issue transaction. Claims must exist before settlement. Release and token burn occur inside settlement and require each claimant’s signature. Structurally, n required Strands therefore mean n Issue transactions plus one settlement, excluding one-time genesis and any separate post-expiry reclaim. These are source readings, not measured transaction counts. Batch issuance would require a C2 change. Proof-at-consumption needs a new redeemer and in-settlement pairings, with cost unmeasured. [Opus ERR-04/ERR-25; SEC06-P04 PROPOSED; OPT-07]

At acceptance, actual validators must enforce the relevant evidence and effects. On the reviewed issuance route, the settling validator recomputes each statement from the transaction and spent state and compares it with the digest checked by the claim policy at issuance. It does not perform settlement-time proof verification. Each claim output locks min-ADA until settlement or claimant-signed post-expiry reclaim. Network fees and collateral are funded separately from program-asset fees. [Opus ERR-12/ERR-25, source level only] After submission, an observer distinguishes inclusion, required finality, and complete readback. The application reconciles expected and actual per-asset effects and remaining duties. A timeout leaves observation unknown. It is not proof that no action occurred. [S03 “What provable intention means”; Study 04 USE-06, PROPOSED]

The application handoff would identify source/program, semantics and compiler versions, selected action, claim specifications, statement and proof identities, context provenance, consumer identities, authority, complete expected effects, and evidence stage. This is a PROPOSED information contract. No SDK method or transport schema is asserted to exist. Existing proof exports contain no Plutus Data/CBOR or transaction. [S04 “Proof API boundary”]

## A first reference app that teaches the model

Recommend a proposed **partial invoice explorer** as the first reference app. Its first action is small: inspect one payment, its fee, and the invoice duty that remains. Start with labelled source and fixture data. Add a real proof-to-transaction path only when its dependencies have evidence. This app teaches concepts reused by repayment, allocation, issuance servicing, and partial order execution.

Source-behavior worksheet, not an executed result: S12 open(90,10) funds escrow with 110 CASH and charges the buyer 3 CASH, for buyer gross debit 113. A partial payment of 35 and program-asset fee 2 debit escrow by 37. The seller receives 35, the fee recipient receives 2, and escrow holds 73. Invoice duty becomes 65 and reserve duty stays 10, totaling duties of 75. The source requires non-negative custody, not full backing of liabilities. Network fees, collateral, claim-output min-ADA, and the V2 thread reserve are separate funding items. [S12 actions; Opus ERR-22/ERR-25/ERR-28]

A separate PROPOSED full-backing policy could require funding 112 for one partial, leaving 75 against duties 65 plus 10. Each further partial charges another 2 not reflected in duty amounts, so backing needs an additional rule and funding. S12 contains no extra transfer or reserve-duty-return action. From the 110-funded path, finish pays 65 and leaves cash 8 against reserve duty 10. The reviewed V2 source requires zero balances and duties for Close, so this nonzero reserve duty blocks Close. Discharge or migration needs a program change, not an assumption that finish completes the lifecycle. [S12 actions; Opus ERR-22]

Financial partial progress differs from missing proof evidence. The intended experience allows a specifically authorized partial payment to retain duties while carrying every proof required for that step. An incomplete required-proof set has no authority over thread effects under the PROPOSED all-or-nothing rule. It is not necessarily only off-chain: already-issued claim outputs may exist on-chain, lock value, and remain releasable only by their claimant. Whether the proposed consumer enforces the partial-step distinction remains an Opus-owned validation question. [SEC06-P01/SEC06-P05 PROPOSED; Opus ERR-15]

The next example is conditional reserve allocation through the same claimed pipeline. S13 provides a contrasting arithmetic and multi-asset duty specimen. S13 alone does not authenticate a distinct governance approver. In the reviewed V2 consumer source, action inputs are covered by the required signers’ scenario intents and the statement body. Thus approved=true is consented to by effect-derived signers and, if listed, an advancer. That does not authenticate a separate governance decision unless the governance party is a required signer, advancer, or authenticated input. [S13 actions; SEC06-P05 PROPOSED; Opus ERR-09/ERR-24]

## Five application cases

All five cases are PROPOSED applications. Each needs supported source and relation mappings, genuine owner authorization, actual consumer invocation, and target evidence. They are reference scenarios, not a supported-feature catalogue. [Study 04 USE-01–USE-05]

**1. Batched DEX orders.** A trader specifies exact assets, gross limits, fees, and minimum net receipts. A batcher combines orders with a pool transition and identifies which outputs satisfy each order. For two illustrative 100-A orders, each requiring at least 90 B net, an explanation might allocate 92 B to each owner. Claim specifications cover order execution and pool arithmetic. Allocation over actual outputs belongs to the consuming validator. A proof can attest arithmetic only over values that validator recomputes. The strict illustration gives each order a separate output. A profile may instead choose a consumer-recomputed amount partition that admits coalesced payments, allocates every obligation exactly once, and accounts for any allowance. No input value may count toward two obligations. The reviewed V2 source’s distinct-output rule covers only one S2 script hash, not other versions or scripts. Cross-script/version behavior remains additional work. [SEC06-P05 PROPOSED; Opus ERR-08/ERR-23] Partial fills retain quantity, authority, and duties. Cancellation has its own time conditions. Exact rounding, output-allocation semantics, and contention remain additional dependencies.

**2. Capped issuance and distribution.** An issuer describes its policy, cumulative supply, recipients, and any servicing promises. An illustrative issue of 300 under a cap of 1,000 distributes 180 and 120. The other 700 is unissued capacity, not debt. A redemption promise is a separate financial duty when explicitly defined. A genuine application needs mint/burn semantics, actual mint-policy enforcement, supply-state continuation, and exact recipient outputs. A proof of a claim token does not mint the application asset. Eligibility documents retain their external assumptions. No regulatory-compliance assertion follows.

**3. Loan origination and servicing.** A borrower and lender distinguish disbursed principal, fee, accrual, payment, and closing debt. An illustrative debt 100 plus accrual 5 becomes 105. Payment 35 plus separate fee 2 debits the payer 37 and leaves debt 70. Period and rounding rules must be explicit. A variable-rate extension needs a named observation and freshness rule. Collateral release needs its own policy. Actual payments and the loan continuation must agree with the authorized transition. Invoice arithmetic does not establish this loan application or ACTUS conformance.

**4. Treasury allocation.** Owners authorize a decision with recipients, asset amounts, fee budget, and continuing reserves. S13's `allocate(true,23,7,2)` source arithmetic transfers 14 A and 7 A, charges 2 A, transfers 4 B, and creates duties for 2 A and 6 B. For non-negative custody, that action needs at least 23 A and 4 B. Neither S13 nor the reviewed V2 source requires liabilities to be fully backed. Holding 25 A and 10 B so that 2 A and 6 B remain is a PROPOSED full-backing policy that a consumer would have to enforce. The units input is checked arithmetically and is never itself debited. S13 has no action discharging allocation_reserve, so a nonzero reserve duty blocks Close under the reviewed V2 source. Distinct governance authentication, split/join, and migration remain separate work. [Opus ERR-21/ERR-24] Actual beneficiaries and reserve continuation must be visible. [S13 `action allocate`; Study 04 C4, PROPOSED]

**5. Staged invoice escrow.** Buyer and seller specify funded opening, partial payment, final payment, reserve return, and recovery. Optional delivery evidence identifies issuer, document, predicate, freshness, and dispute assumptions. Submission or reserved funding is distinct from delivery. Unknown delivery cannot become nonexecution merely because a deadline passed. Staged lowering is additional work: the documented experimental compiler does not lower `await`. The first partial-payment app explains this case without claiming to implement the whole flow. [S04 “Supported subset and refusals”; S03 “Partial transactions and conditional settlement”]

Existing source commands remain in a current-experiment guide. Future CLI/SDK surfaces are labelled PROPOSED in [DEVELOPER-EXPERIENCE.md](DEVELOPER-EXPERIENCE.md).

Target guides state actual artifact, proof, consumer, network, and phase boundaries. Do not present a generic deploy command as cross-target support.

The wallet summary should expose action, exact assets, recipients, gross debit, fees, minimum net outcomes, new liabilities, and remaining duties. Details expand to required claims, context provenance, consumer, and artifact identities. This proposes a display, not an installed wallet integration. Unknown network fees remain unknown. A source fee is not an all-in transaction quote. [S03 “What provable intention means”; Studies 07 DX07-P02/P05 and 08 ECO08-04, PROPOSED]

Optional hosted proving, relaying, indexing, and routing services need explicit fees, data handling, availability, and export contracts. They remain optional. Public tooling must remain usable without maintainer approval, campaign records, a program registry, or a mandatory service account. Objective target rules and asset-owner authority still apply. ## Optimization without assumed savings

Prioritize better diagnostics and exact reuse of immutable public preparation artifacts as design candidates. Compare against the ordinary whole-execution path. A cache design needs explicit dependency identities and invalidation rules. Reusing a claim specification or compiler descriptor does not imply reuse of a proof for changed state. Private witness/key caching is outside these proposals. [Study 05 OPT-01/OPT-02, PROPOSED]

Then measure canonical statement-view reuse, transaction-local decoding/indexing, and bounded overlap of genuinely independent jobs. More concurrency can increase aggregate memory and worsen latency. More Strands can duplicate context hashing, range constraints, exports, issuance, and verification. Whole execution may be preferable. Decomposition and validator sharding are separate design dimensions. [Study 05 OPT-03–OPT-07, PROPOSED]

A future comparison must preserve equivalent complete financial behavior and independent expectations. Record developer minutes, isolated stage wall/CPU time, aggregate memory, constraint counts, payload bytes, actual transaction and invocation counts, local VM units, qualified ledger resources, fees, locked value, and latency separately. Report cold/warm conditions, sample sizes, failures, and neutral or losing results. No optimization benefit or onchain cost is claimed from the current local records.

## Later-source readings and their limits

The terminal Opus review A03 read later supplied Aiken/Rust source bodies. This synthesis read A03/A04, not those bodies. All V2 consumer descriptions here are attributed source-level readings of unadopted, uncompiled files. No supplied record pins the S07 binary or S08 compiled C2 wrapper to those exact bytes. The four-piece settle implementation and types/bytes helpers were not supplied to that review. Its claims about four-piece reuse of thread stages rely on S09 and comments, not a complete code trace. [A03 §0; A04 ERR-02/ERR-03/ERR-10]

Opus reports that tag, family, predicate_digest, shape_digest, and body_len are circuit constants. Context fields vk_digest through intents_digest, bytes 112..339 including claimant_vkh, are free booleanized witness bits that are hashed, not interpreted. Body bytes tie to slot wires. Verification binds two public inputs under setup honesty and knowledge soundness. Linking them to statement bytes additionally rests on the in-circuit BLAKE2b gadget, OPEN T3 correspondence, and collision resistance. This does not authenticate those bytes. [ERR-02/ERR-16]

In that V2 source, program_hash and source_hash are visible catalogue fields, covered by catalogue_digest and signed in owner intents. The missing link is an on-chain relation between those fields and predicate/VK digests. The report must call it a CATALOGUE-AUTHOR ASSERTION, with VK-to-matrix OPEN. Exact relation-identity coverage depends on identity.rs, unread by the review. [SEC06-P03 PROPOSED; ERR-13]

The same source includes signed gross/fee/net/liability limits, nonce=seq, duty accrual/discharge chains, an exact custody snapshot for the thread, and zero-duty/zero-balance Close. These do not remove circuit-level NotBound/TouchedOnly limits or establish a general multi-UTxO frame. Web role sets, cross-script allocation, partial-completion rules, key migration, and that general frame remain PROPOSED. [ERR-10]

Reference-input support is wholly PROPOSED in the reviewed supplied Aiken files. A validator would need to read the datum and authenticate its origin. The ledger-unspent-at-application rule is a PREMISE giving presence only, not exclusivity or history. A validity interval neither dates nor authenticates the datum. [SEC06-P06 PROPOSED; ERR-11]

The V2 network byte is catalogue-declared and is not compared with the executing ledger in the reviewed source. Cross-network separation rests on outref uniqueness as a ledger premise, not that byte alone. In the reviewed source, any catalogue account can invoke intent revocation (Revoke), advancing seq and potentially orphaning issued claims; they can remain locked until claimant-chosen expiry. Existing reclaim is after expiry, while early reclaim is PROPOSED. Catalogue VKs are immutable in this source; key migration needs a new action carrying duties. A thread reserve is V2 lovelace, distinct from a program reserve duty. [ERR-06/ERR-07/ERR-14/ERR-28]
