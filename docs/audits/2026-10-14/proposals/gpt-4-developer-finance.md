## Recommended approach and alternatives

Recommend a predicate-led audit organized around public developer journeys, with independent financial and work expectations attached to every transition. Start with the actual installed entry points and follow newly written source through typing, Core, intention, ZKIR, native execution, ledger effects, history and recovery. Record unsupported or unavailable stages as blocked. Supplement two complete journeys with grammar coverage, lifecycle cases and the inherited conformance denominator. This gives understandable developer outcomes while preventing two examples from masquerading as a language-wide result.

The product is a permissionless general language. Fenrir applications are valuable conformance consumers, not the universe of admissible programs (`docs/MORIARTY-PRODUCT-CONTRACT.md:15`). The audit must distinguish a general construct from a library policy and from an external target dependency. Source libraries must use the shared language/compiler path rather than acquire application-specific acceptance shortcuts.

Alternative A is a requirement-first exhaustive review: flatten every U/M/MC/SP/G clause before selecting journeys. It gives stronger omission detection early, but can spend the available review effort reconciling old documents while the public install remains unclear. Retain its obligation register as the recommended approach's completeness backstop, not its sole work order. Alternative B is a developer-first pilot on the smallest runnable profile, expanding only after a successful external journey. It exposes packaging and diagnostics quickly, but may normalize unsupported financial families and defer inherited acceptance indefinitely. Use it only with an unchanged denominator and explicit blocked rows.

## Concrete deliverables and small schemas

Produce `AUDIT-REPORT.md` for developer-visible conclusions, `CAPABILITIES.json` for exact profile support, `OBLIGATIONS.jsonl` for every inherited predicate, `JOURNEYS.jsonl` for stage results, `FINANCE-ORACLES.jsonl` for independently derived expected values, `EVIDENCE.jsonl` for provenance, and `ROADMAP-DELTA.md` for minimal edits. Produce `INSTALL-TRANSCRIPT.md` and two program directories containing original source, scenarios, hand-derived expectations and retained public results. A `LIMITATIONS.md` names uninspected scope and blocked stages. Opus supplies its own separately owned security artifacts; this proposal supplies no security verdict.

Use small records. Capability: `{id, profile, entrypoint, advertised, implemented_scope, qualification, evidence_ids}`. Obligation: `{id, parent_ids, predicate, denominator_member, status, evidence_ids, blocker}`. Journey: `{program_id, stage, profile, input_digest, expected_id, result, evidence_ids, blocker}`. Oracle: `{id, author, derivation, inputs, expected_state, ordered_effects, liabilities, work_profile, expected_work}`. Evidence: `{id, source_commit, artifact_digest, path, line, method, scope, observed_at, limitations}`. Status distinguishes specified, source-inspected, historical-run, current-run, accepted and blocked; accepted requires its actual acceptance authority and predicate. Missing evidence never becomes a pass. Exact counts report denominator membership and qualification, never subjective completion percentages.

## Public installation and end-to-end journeys

Specify a clean external install with no checkout, runtime campaign records or reviewer metadata. First identify the published artifact or explicitly record that no independently installable release has been established. Pin artifact digest, toolchain and executable resolution so the Node and Rust `mori` binaries cannot be confused. Check packaged examples, help, JSON diagnostics, formatter, editor setup and MCP tool descriptions against that exact installation. Exercise Node and Rust separately where both are advertised; packaging success for one gives no result for the other. This proposal specifies those future checks; none ran here.

An independent author should write Program A: a bounded two-asset purchasing agreement with a fixed recipient, maximum gross debit of 11 A including at most 1 A fees, minimum received 20 B, and an explicit permitted partial outcome with a surviving duty. It must be authored from documented constructs, not copied from loan/swap/FeePool fixtures. If the current supported grammar cannot express a required stage, record the first missing construct and stop that lane without silently replacing it with host logic.

Program B should contrast both state and money flow: a finite multi-beneficiary reimbursement agreement whose input costs create liabilities, whose available surplus is allocated with explicit directed rounding, and whose claims remain possible after administrative closure. Choose new identities, amounts and action order independently. Include a nonfinancial counter/state condition so coverage cannot be reduced to recognizing a familiar payment template. Do not assume generic multi-payer native support merely because mapped source-static export exists.

For each program retain source diagnostics and typed representation, source-to-Core field mapping, deterministic reference transitions, canonical intention display, complete expected transfers/fees/reserves/liabilities, per-action work, and generated ZKIR identity. Compare the reference with actual public consumer outputs by field and effect order. Continue the same source identity through native production, independent verification, installation, call and full ledger readback only under separately granted authority. Here every native/SDK/VM/query/prove/verify/keygen/deploy/call stage is blocked by native authority zero; public install, source execution and tests are also specified-only in this review.

Finally trace state/history and normal interruption recovery: pending, partial, unknown, settled and recovered are different outcomes; unfinished duties remain visible across restart. A committed ledger phase may retain fees even when a later phase fails (`docs/MORIARTY-PRODUCT-CONTRACT.md:47`). Compare source, reference and target outcomes for each declared phase rather than expecting universal rollback. No live history, account, clock, nonce or finality is authenticated by this proposal.

## Independent financial and work oracles

Freeze expected results before observing implementation output. An independent financial author should derive small integer cases by hand and use a separately implemented exact-rational calculator for larger vectors. Do not import evaluator arithmetic into the oracle. Preserve base-per-quote units, ceil obligations, floor receipts and protocol-reserve remainder policy, including declared exceptions (`docs/decisions/u0-numeric-profile-decision.md:7`, `:15`). Conversion of quote-per-base references requires a dimensioned conversion, not renaming.

Check conservation per asset, complete recipient distribution, opening plus accrual/creation minus discharge equals closing liability, gross debit including fees, net receipt and persistence of unrelated balances/duties. Ordinary failure conformance includes unsupported operations, missing scenario data, insufficient funds, overflow, work exhaustion, unavailable external observations, interrupted output and unknown settlement status. Expected outcomes must state effects and surviving obligations, not just exit codes. Security-oriented cases and their judgments are handed to Opus.

Work expectations require a separate author to count the documented logical steps/expressions. Keep logical work, target circuit cost, protocol DUST, service fees and external costs in separate fields. The source runtime has a logical charging function (`crates/mori-core/src/runtime.rs:403`); that observation supplies no measured relation to other planes. Metamorphic financial cases should vary allocation order, partition exact payments and change irrelevant state while preserving the intended accounting laws. Their applicability must follow the program's explicit policy.
