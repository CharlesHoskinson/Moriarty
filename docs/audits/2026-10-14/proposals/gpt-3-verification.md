## Recommended audit and two alternatives

Recommend **independent expectation first, boundary-by-boundary conformance QA**. Freeze the admitted profiles and semantic judgments, derive small financial and work expectations independently, then compare each public consumer and reference representation against those expectations. This gives useful evidence about implemented behavior without mistaking CLI/API agreement for independent semantics. The product contract distinguishes reference expressions, logical work and circuit cost, and requires explicit correspondence (`docs/MORIARTY-PRODUCT-CONTRACT.md:25–31`). Security assurance is a separate Opus-owned input to eventual acceptance.

Alternative A is an external developer rehearsal: two fresh authors install the public package and carry independently authored programmes through the complete delivery path. It finds missing commands, packaging friction and scope ambiguity quickly, but a few successful examples provide weak grammar coverage. Alternative B is a primitive-first semantic reconciliation: independently derive arithmetic, rounding and work tables for every primitive before integration. It produces deeper local confidence but can delay discovering broken public consumers. Use the recommendation as the main audit, A as held-out U7 evidence, and B for the primitive basis needed by the initial U1/U2 slice. Reuse existing harnesses rather than creating another framework.

## Financial and work expectations

For every supported arithmetic primitive, independently tabulate tiny integer cases, exact divisibility, nonzero remainder, zero where defined, maximum admitted values and representability boundaries. Each row records input dimensions, base-per-quote orientation, intermediate mathematical result, finite-width rule, obligation/receipt rounding and remainder beneficiary. Compare actual output to this table later through an authorized local lane. Expected values must be calculated before consulting implementation output; disagreements go to a second semantic reviewer and the normative numeric profile.

A financial outcome record includes every balance change and recipient, gross debit, fee, net beneficiary outcome, retained principal/interest or other duty, pool/reserve allocation and conservation equation. Include multi-step sequences so a correct first payment does not conceal a missing residual obligation. Keep fees separate from transferred principal and recovery reservations. Distinguish logical work, target resource estimates, host elapsed time, DUST and reserved recovery work rather than converting one into another without a documented relation.

An independent work oracle walks the source/Core construct list against the versioned schedule. Record each statement/expression contribution, branch taken, rejected-operation charge and excluded preparation cost. Compare literal expected totals to emitted totals; retain the existing cap-boundary checks as a different evidence class. A cap equal to the independently predicted total should preserve successful financial output; a lower permitted cap has the schedule's specified result. These are ordinary metering-conformance checks, not security tests.

Use conditional metamorphic relations: renaming ordinary local variables preserves meaning; reordering irrelevant input-map entries preserves results; adding untouched accounts preserves existing observations; increasing an adequate work cap preserves successful financial output. Payment splitting is equivalent only when fee and rounding rules explicitly permit it. Test the profile's documented zero-fee representation and stable serialization separately. Avoid universal algebraic laws that fail under finite-width arithmetic or per-call fees.
