# Core3 boundary-domain policy decision

Adopted as an abstract policy only on 2026-10-20, from two substantive independent votes: Opus4.8 HIGH and Gemini4ArgonHigh HIGH. Both chose uniform Core3 boundary admission and required qualification of H25. The complete D1/D1A proposal and implementation remain unadopted.

OPERATIVE RULE, UNIFORM FOR /3: For moriarty-core/3, bare stage admission and Sequence projection use the same domain. stage::start for a /3 StagedProgram applies the profile-appropriate canonical_boundary (REG3) for awaiting and non-awaiting actions alike, before evaluation, with attempted 0 on refusal; Sequence project_head applies the same profile-appropriate canonical_boundary at P7 before stage::start in both cases; stage::resume R7 applies the same REG3 rule to the retained continuation boundary. Therefore bare-/3 and Sequence /3 domains coincide and neither depends on await count. For an awaiting /3 action this means the start admission domain equals the resume R7 domain, so any Waiting continuation that is actually emitted has already re-passed the same REG3 canonical_boundary through emit_checked (H25); this is a boundary-domain decode/R7 guard only and is NOT a liveness, progress, completion or guaranteed-ability-to-resume claim, and a non-awaiting /3 action emits no continuation. H25 does not itself decide non-awaiting bare-/3 admission; applying REG3 at non-awaiting bare /3 start is a separate, explicit owner policy choice, adopted here for one-domain-per-invocation serial composition and stated as the owner's choice in RATIONALE. Incoming discharge-only duties with no Statement::Liability anywhere are supported in bare /3 and in Sequence only when declared by a /3 ExternalDutyDecl in REG3; without such declaration they are refused in both domains under the same registry rule. This does not narrow Sequence relative to bare stage::start for /3, because the same narrowing relative to an undeclared-duty reading applies at bare stage.

FOR /2: A Sequence-projected boundary is admissible only if it satisfies BOTH scenario_snapshot AND the profile-appropriate canonical boundary, for awaiting and non-awaiting actions alike; no /2 predicate, message, ordering or hash input is changed. Bare /2 stage admission is unchanged: stage::start applies canonical_boundary only for awaiting /2 actions, preserving bare /2 non-awaiting discharge-only admission. No /1 predicate is changed.

RATIONALE: admission of the same owned head must not depend on successor await count; H25 requires a Waiting continuation to decode and pass R7 or not be emitted; serial composition needs one domain per invocation; the owner chooses the same one domain at bare /3 stage so start, Sequence projection and resume cannot diverge. Alternative rejected: await-dependent admission, because it makes admissibility a function of await count and creates a silent seam in one serial chain. Alternative rejected: extending FrameBindings with caller-supplied (asset,debtor,creditor), because it changes the adopted DTO and treats unauthenticated caller identity as evidence.

COMPATIBILITY: For /1 and /2, no stage predicate is weakened, edited or bypassed (CSQ-016), and bare /2 non-awaiting discharge-only admission is unchanged. No new resource defaults, caps, native authority or counter reset is introduced.

The operative paragraph uses the exact Opus amendment. Gemini agrees with the uniform policy and H25 qualification, and requests additional explicit /2 clarification. Its full amendment is preserved separately; this decision does not claim both reviewers approved identical replacement bytes. Under the unchanged /2 paragraph, Sequence /2 still requires the canonical-boundary predicate for a non-awaiting action, while bare /2 start does not. That /2 domain distinction remains.

The prior Sequence-only choice and its rollback-together condition remain recorded non-operative dissent in the unchanged original proposal. This decision does not adopt the original proposal heading or lines7,9,11,13,15,17: grammar, IR, parser, REG3 construction, load, boundary algorithm and caller data still require their proper review. Neither vote certifies source compliance, financial results or execution eligibility. The three planned financial tests remain unselected and unrun.

Review qualification: one Gemini rationale claim about current scenario_snapshot is not adopted. Current runtime.rs::liability_identities already adds Program.duties for the exact Core3 profile, and scenario_snapshot uses that map. The uniform policy still has two agreeing votes on its abstract domain choice; these votes are not implementation audits. The complete opinions and this qualification are retained.
