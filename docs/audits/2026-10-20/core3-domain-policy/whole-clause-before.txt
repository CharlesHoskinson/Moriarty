D1A Source-authenticated external-duty extension [NEW PROPOSED-UNADOPTED language/IR/profile, not a /2 reinterpretation]: a new profile language "moriarty/3" with semantics "moriarty-core/3" adds exactly one top-level declaration form, parsed only from source text by the new parse_v3 path: duty "<duty-name>" = { asset: <asset-name>, debtor: "<debtor>", creditor: "<creditor>" }; . The IR adds Program.duties: Vec<ExternalDutyDecl>, where ExternalDutyDecl{name:String, asset:String, debtor:String, creditor:String} and asset is the source asset NAME resolved at validation to its declared exact AssetId. The declaration is in the Program value and therefore in the existing canonical program_hash and plan_hash preimages; it is not supplied by a manifest, binding map, Scenario, Snapshot, CLI argument, registry service or caller assertion. For /3 only, the duty registry REG3 is the union of Statement::Liability identities over all actions and all Program.duties entries; two entries for one name with different (AssetId,debtor,creditor) refuse, identical duplicate declarations refuse as duplicate declarations, and a DutyDecl conflicting with a Statement::Liability identity for the same name refuses. validate_v3 applies every validate_v2 rule, replaces the source-derived-identity test for LiabilityPresent/LiabilityAmount reads with REG3 membership, requires every DutyDecl asset to be declared, requires 1..=1024-byte name/debtor/creditor, and imposes no consent, authority or namespace-certificate meaning on the declaration (OD5 remains open). stage loading for /3 is a new load_v3 pipeline parse_v3 -> require_core3 -> validate_v3 -> plan::build -> plan_invariants -> cost::fill -> cost_invariants -> digests, producing the same StagedProgram shape; require_core2 continues to refuse /3 and require_core1/require_core2 behaviour for /1 and /2 is unchanged. decode::canonical_boundary is profile-dispatched only in this sense: for a /2 StagedProgram it uses the existing registry unchanged; for a /3 StagedProgram its registry step uses REG3. The boundary is still checked as written, never re-sorted, with identical state, balance, account-presence, ordering and trace-cell predicates. Admission is therefore identical for awaiting and non-awaiting actions: project_head applies the profile-appropriate canonical_boundary at P7 before stage::start in both cases, and stage::resume R7 applies the same REG3 rule to the retained continuation boundary, so a /3 discharge-only duty that is projected at start remains resumable. A /2 program, or a /3 program without a DutyDecl for the name, still refuses a discharge-only projected duty under U1. Conversion is source re-authoring only: adding a duty declaration creates a /3 source, new program/plan hashes and a fresh stage::load_v3 admission; there is no /2-to-/3 conversion of a StagedProgram, Continuation, Snapshot or wire value, no Deserialize path may invent Program.duties, the frozen v1 wire continues to have no Await and no duty declarations and refuses /3, and a /2 continuation can never be resumed as /3. Caller dataflow is unchanged in shape: duty_bindings remains BTreeMap<String,String> local-name to global-name only and can never carry (asset,debtor,creditor). Rationale: admission of the same owned head must not depend on the successor's await count; a boundary admitted at start for an awaiting action must remain resumable (H25 in S028: a Waiting continuation must decode and pass R7 or it is not emitted); serial composition needs one domain per invocation, not a start-only domain that a later resume would reject. Tradeoff, stated explicitly: this NARROWS the Sequence domain relative to bare stage::start for non-awaiting actions — incoming discharge-only duties with no Statement::Liability anywhere in the program are UNSUPPORTED as projected duties in Sequence (§9), although bare Core/stage admits them. This is a strengthening at the Sequence admission layer only; no existing stage predicate is weakened, edited, or bypassed (CSQ-016). Alternative considered and rejected: await-dependent admission (discharge-only allowed only for non-awaiting actions). It preserves more bare-stage programs but makes Sequence admissibility a function of await count, makes the lifted head's duty set non-uniform across invocations, and lets P complete a discharge that an otherwise-identical awaiting Q could not even project — a silent domain seam inside one serial chain. Alternative also rejected: extend FrameBindings with an explicit (asset,debtor,creditor) identity for discharge-only duties so R7 could be satisfied by construction. FrameBindings is fixed by the adopted ordinary DTO as BTreeMap<String,String> (S049, S050, S096 InvocationSpec{duty_bindings:BTreeMap<String,String>}); inventing an identity carrier changes the adopted success shape and requires fresh ordinary votes, and a caller-supplied duty identity is exactly the kind of unauthenticated identity assertion S048 forbids treating as evidence.
