## Feasibility confirmed

The direction is implementable with existing machinery: (1) the shared scalar evaluator in `runtime.rs:700` charges one per statement plus one per distinct expression node with a fresh cache per statement (`evaluate`, line 387ff.), and `And`/`Or` evaluate both operands (line 447ff.), so successful-segment cost is input-independent; (2) independently recomputed arithmetic matches Opus: E1 start 5, false attempted 2, true 6, committed 11, plan-total 11, two circuits; E2 start 7, false 4, true 8, committed 15; Reserve start 13, true segment 20, committed 33 (never 35 committed — a false resume adds only attempted 2); (3) `Builder::public(expected = Some(wire))` in `mori-backend/src/lib.rs:620` already emits PublicInput, range check, equality and Impact, sufficing for pending post roles; `lower_action` already derives balance keys from the whole action (line 796) and uses the whole-program liability registry (ceiling 16), so full financial frames and the preserved duty registry survive a range-parameterised refactor; (4) the lexer does not keywordise `await`/`when` (`token.rs:keyword`), and the core parser compares token text, so `/1` identifiers named `await`/`when` can stay valid; (5) `intent::canonical` sorts object keys generically, so `digest(Program)`/`digest(StagePlan)` are deterministic for the new variant. No wait circuits, N+1 advance circuits, per-action one pending frame, `advanced:false`/`segment:none`/unchanged `c`, attempted-versus-committed separation, plan-constant costs and total-task-cap preflight are all consistent with this machinery.

## Must-fix before source implementation

**MF1 — Opus §6 byte promise is unresolved.** Opus §6 requires `/1` compile output bytes identical to baseline with no golden regeneration. Revised Sol §Clarifications-1 and the plan (§Constraints) weaken this to no cross-build byte-identity promise. These texts contradict each other; the prompt confirms Opus clarification is still pending, so this is not resolved. Freeze exact scope: backend `/3` `artifact.json`/`.zkir` bytes are plausibly preservable (a `/1` Program serialises unchanged and `lower_action` order can be preserved), but `mori-ledger/src/proving.rs:150` `source_closure()` hashes `mori-core` parser/ir/runtime sources, so every compiler-hash-bearing ledger record necessarily changes. List which byte streams are promised and which are refreshed; do not let the implementer choose.

**MF2 — The implementation plan still contradicts the adopted design.** IMPLEMENTATION-PLAN-SOL.md retains `StageBranch{Start,Wait,Advance}`, `ContinuationPayload` with a caller-carried cumulative counter, `2N+1` circuits (§Shared interfaces, line 56), start/wait/advance tests (Task 2), branch/counter ABI roles (line 78), and "cumulative 35 after false" (line 145). Revised Sol supersedes these, but an implementer following the plan file builds the rejected design. Regenerate or explicitly strike those sections; the only DTOs are Opus §4 (`Continuation`, `StageLogical`, `StageEvent`, `NamedValue`, `ActionPlan`, `AwaitSite`, `CaptureSlot`, `StageOutcome`, `StageRejection`, `Statement::Await{label,binders,guard}`).

**MF3 — Pending-frame boundary representation is undecided.** Revised Sol item 2 leaves this open. `Continuation.boundary: Snapshot` has no pending site/captures; `site`/`captures` in the Continuation duplicate the frame locally, while the `/4` frame is per-action contract state and nothing represents other actions' pending frames. Freeze one reading without touching `/1` Snapshot/Scenario: either Continuation fields are the local frame and circuit roles are their projection (start `pre_site == 0` being locally vacuous must be stated), or an Opus amendment adds a `/2`-only boundary DTO. Multi-action preservation by the future ledger adapter must be written as a premise, not implied.

**MF4 — The `/4` manifest DTO is not frozen.** Opus §5 specifies roles, gates and decoder checks in prose but no `StagedArtifact` struct; the plan's provisional nested `StageCircuit{circuit: CircuitArtifact}` conflicts with a distinct `/4` type. Adding fields to `/3` `CircuitArtifact` (deny_unknown_fields) would break old `/3` decoding. Freeze exact `/4` strings (`moriarty-zkir-artifact/4`, `moriarty-public-abi/4`, `moriarty-zkir-relation/4` per DESIGN-SOL.json), a distinct staged circuit type carrying segment index, entry/exit site, capture layouts in/out, event layout, context hash and frames, a distinct staged Resources type (per-circuit `segment_logical`/`committed_before`, per-action `plan_total`), the exact `/4` context preimage element list and order (the `/3` 18-element `signed_relation::context_hash` stays untouched), whether post-pending wires join the ZKIR Output list or are transcript-only, `replay_steps` meaning per segment, the global circuit filename index across actions/segments, the six-plus-four gates, and envelope byte fixed-point and summed instruction/byte caps. H21 is untestable until this exists.

**MF5 — Zero-await actions and absent cap are undecided.** Revised Sol item 3 leaves both open. Freeze: stage start on a zero-await `/2` action (expect `Complete` with `segment_cost[0]`, `ActionPlan` with `segment_cost.len() == 1`, `committed_before == [0]`); `/4` emission for zero-await and non-await actions in a mixed program (expect exactly one segment 0, entry 0, exit 0, L = 0); `plan_total` definition (`committed_before[N] + segment_cost[N]`, with `committed_before.len() == N+1`); and `StageLogical.cap == None` semantics on start and on resume with CLI `--logical-cap` (R6 only defines the stored-cap case). Use checked arithmetic in plan derivation; bind `CaptureSlot.ordinal` to one meaning (its value feeds `plan_hash`).

**MF6 — Validation must be split, and the silent-consumer inventory is incomplete.** `parser::parse` calls `validate` (parser.rs:147) and `validate` currently rejects any non-`/1` profile (runtime.rs:121). Keep legacy `validate` `/1`-only and add a profile-dispatched validator for parser and stage APIs; otherwise every legacy consumer calling `validate` either rejects `/2` at parse time or silently accepts it. The `/1` branch must explicitly reject any `Statement::Await` in hand-built `/1` IR JSON (Opus §6 allows the code to move to `mori::core::profile`). Adding the variant breaks exhaustive matches that the plan's inventory misses or understates: `mori-backend/src/proving.rs`, `mori-ledger/src/ops.rs` (step-root match), `mori-ledger/src/relation/compiler.rs` (both matches), `mori-ledger/src/signed/mod.rs`, `crates/mori/src/commands/inspect.rs` (`statement_rule`, `expression_constraints`), and `signed_relation.rs` label scan. Wildcard matches are worse: `layout.rs` `admit_bindings_inner` ignores unknown statements, currently shielded only by its prior `validate` call. Every forced arm must be a typed refusal or be proven unreachable behind the `/1` gate; list them all as an integrator checklist. Verify each C7 entry actually calls the `/1` gate before any matching/layout (backend `replay::generate` reaches it only through `compile_mode` via `reconstruct`, and wraps the core error as `mori::backend::program` — pin the accepted error identity in tests).

**MF7 — Resume snapshot validation and file limits cannot reuse existing helpers.** `scenario_snapshot` (runtime.rs:523) sorts balances/liabilities, while R7 requires unsorted input rejected, not re-sorted; its inputs check is replaced by R4. Specify the strict resume validator literally: exact state keys/types, balance-key completeness for the whole action, duplicate rejection, liability identity against the whole-program registry, and the trace-cell formula using whole-action statement and added-liability counts. Separately, `core_io::read_json` caps at 1 MiB via `json::parse` (json.rs:6), contradicting the Opus 4 MiB continuation / 64 KiB event limits; the staged reader needs an explicit size check before parsing plus a duplicate-key-rejecting parse at those limits, without raising `/1` limits.

**MF8 — Segment cost and step shape need an exact pin.** My recomputation confirms the constants only under this mapping: reaching an await charges its single statement charge and stops before the guard; resuming charges that same charge as dispatch, evaluates the guard with a fresh per-statement cache, and emits the entry `Await` step (original ordinal, `Bool(true)`, pre snapshot, no effects) with no second statement charge. `segment_cost` must count distinct reachable nodes per root exactly as `eval_cached` does. The stage evaluator must preflight `committed + segment_cost ≤ cap` with `stage_logical`/attempted 0 (R6) rather than rely on `Meter::charge` mid-run (its code is `mori::core::meter`, Opus §9 item 8); attempted on rejection is the partial charge up to the failing statement (verified: H11 attempted 4, H12 attempted 6). Freeze `Execution.semantics == "moriarty-core/2"` for segments, that a start segment contains prefix steps only (no `Await` step), that a waiting segment excludes its exit `Await` step, and `residual` on the false path (from the unchanged boundary).

**MF9 — The simulate CLI must be restructured without changing `/1` behaviour.** `ActionInput` (crates/mori/src/cli.rs:55) makes `--action` and `--scenario` required, so `--resume`/`--event` cannot coexist with it as-is. Freeze the full argument matrix before implementation: start keeps `simulate FILE --action A --scenario S [--logical-cap C]`; resume is `simulate FILE --resume C --event E [--logical-cap C]`; `--resume` requires `--event` and conflicts with `--trace`, `--target`, authorisation arguments and a scenario, raised as usage errors before any file read; a supplied `--action` on resume must equal `C.action` or fail `stage_site`. Do not change shared `ActionInput` for other commands, and keep `/1` stdout bytes and missing-argument behaviour unchanged.

## Advisory (not blocking this design)

Publish waiting output may exceed the 1 MiB `json::export` cap for large snapshots, as legacy executions already can; document rather than fix here. `inspect` without `--target` will print the new `Await` JSON for `/2`; `inspect --target` is refused through the compile gate, consistent with Revised Sol. Quint modelling, examples/oracle files and test authoring are later implementation work under the separate execution classification. Changing `DESIGN-OPUS.md` §6 requires an Opus clarification record, not a Sol-side edit.

## Disposition

Fix MF1–MF9 in the design documents (MF1 and any DTO change in MF3/MF4 by Opus clarification/amendment) before source implementation; no native acceptance is requested now. After those freezes, the remaining path — shared segment evaluator seeded at the await ordinal, `compile_stages` reusing `Builder`/`lower_action` with whole-action frames, distinct `/4` type with pending roles after the pre-/post-liability positions, native-call and signed paths refusing `/2` — is feasible as specified.
