## 1. Compatibility rule (replaces prior §6, first two bullets)

### 1.1 Exact equality, no exceptions

These must be byte-identical to baseline `fe01bc8b` for the existing corpus:
- `/1` Execution JSON;
- logical-cost/1 values;
- `/1` error code, message, offset and step;
- the `/3` schema/version strings;
- the role layout: names, positions, order, constants and expected bindings;
- the emitted instruction sequence;
- the emitted financial operations.

### 1.2 Attributable regeneration

Only one class of difference is permitted: fields whose value is a deterministic function of `proving::source_closure()`.

**Step A — inspection report (before coding).** The implementer lists, by reading code:
- every JSON path in `artifact.json` whose value depends on the closure;
- every derived field, such as file digests, a manifest digest, or a context hash if its preimage includes the closure;
- whether any `.zkir` byte depends on the closure.

This list is the **whitelist**. It is frozen and reviewed by me.

**Step B — baseline fixtures.** These are generated by building the baseline commit as-is, in a separate worktree. That is an execution step and needs my later classification. Fixtures are never produced by candidate code. A provenance file records:
- the commit;
- the command;
- the toolchain;
- the SHA-256 of each file.

**Step C — comparison test.** Decode the baseline and candidate `artifact.json` with `mori_core::json::parse`. For each whitelisted path, **recompute** the expected value from the candidate closure using the baseline derivation and the baseline's other inputs. Then require full structural equality and canonical byte equality.

Masking alone is forbidden, because a masked field could hide an arbitrary change.

**`.zkir` files:**
- If Step A finds no closure dependency, they must be byte-identical.
- If it does find one, decode both with `IrSource::load`. Require instruction-by-instruction equality, except at immediates that Step A identifies by position as closure-derived. Those immediates must equal the recomputed value.

### 1.3 Snapshots

- An `insta` snapshot or golden with no whitelisted content must not change.
- A snapshot with whitelisted content may change only if the Step C checker, run against the old and new snapshot, passes.
- Each such change gets an entry in `compat-deltas.md`: the file, the path, the old value and the new value.
- `cargo insta accept` or bulk re-blessing is a failure.

No old compiler identity is injected or claimed anywhere.

### 1.4 `/1` Await JSON: the prior delta is withdrawn

My prior §6 allowed `/1` Await JSON to move from a decode failure to `profile`. I now **require zero delta**, for a security reason: `/1` must be *unable to represent* Await, rather than relying on every entry point running a profile check.

There is also a compatibility reason. Adding a variant to a serde enum changes the "unknown variant …, expected one of …" message for **every** unknown `kind`, not only for Await.

**Rule.** Every `/1` decode site uses a frozen wire module, `ir::v1`. That module contains the existing `Program`, `Action` and `Statement` derives moved verbatim, plus infallible `From` conversions into the shared types. This covers:
- `Program` IR JSON;
- any `Execution`/`Step` decode in `replay`.

The implementer enumerates these decode sites (new call-path premise U10). The shared `ir::Statement` gains `Await`; it is used only for serialization and for in-memory `/2`.

**Recorded delta D1:** none. A `/1` JSON statement with `"kind":"Await"`, well-formed or malformed, yields the baseline decode error bytes.

- **Hostile test H23:** byte-compare against fixture errors for three cases: a well-formed Await, a malformed Await, and an unknown kind `"Foo"`.
- **C7 still applies** to in-memory `/2` programs that reach `/1` entry points.

The serialization of non-Await variants must be unchanged, so the existing `program_hash` values do not move. This is tested.

## 2. Pending-frame representation

### 2.1 Legacy Snapshot is not modified

`Snapshot`, `Scenario`, `Execution` and `Step` keep their fields and JSON. Adding a frame to `Snapshot` would change `/1` bytes and would let `/1` inputs carry frames. **Rejected.**

### 2.2 Minimal structures

```rust
#[serde(deny_unknown_fields)]
pub struct PendingFrame { site: u16, captures: Vec<NamedValue> } // site 0 ⇔ captures == []

#[serde(deny_unknown_fields)]
pub struct StageSegment {
    action: String,
    frame_pre: PendingFrame,
    frame_post: PendingFrame,
    execution: Execution, // legacy type, pre/post are legacy Snapshot
}
```

- `StageOutcome::Waiting.segment` and `Complete.segment` become `StageSegment`.
- `Continuation` stays flat as in §4 of my prior report. Its `site` and `captures` fields *are* the executing action's frame, and `boundary` is the legacy Snapshot. A separate `StagedBoundary` type would duplicate this without adding binding, so I do not require one.
- Locally, captures have length `len_k` and no padding. Zero-padding to `L` exists only in `/4` roles.

### 2.3 Frame scope

**Frames of other actions are not included and not represented locally.** Including them would imply that the local tool tracks ledger state, which it does not (P3).

**Locally:**
- A start assumes `frame_pre = {site:0, captures:[]}`. Outputs keep `"consumption":"untracked"`.
- A resume takes `frame_pre` from the continuation.

**In the `/4` relation:**
- Each circuit's pending roles cover only its own action's frame.
- The requirement that other actions' frames are untouched by this transcript is a **ledger write-isolation property**. It is not established.
- The description of the `pending-frame-predecessor-binding` gate is extended to read: "…and isolation: frames of non-executing actions unchanged." Its status stays `unperformed`.
- MPLR-011 is still not claimed.

Actions are independent:
- Action `b` may run while action `a` is pending.
- Interference happens only through shared state, balances and liabilities. This is intended, and H11 pins it.

### 2.4 Actions with zero awaits in a `/2` program

- No frame, so no pending roles.
- `/4` emits exactly one circuit, `s0`, with entry 0 and exit 0, under the `/4` context (C9) with empty capture and event layouts.
- Locally, an invocation without `--resume` returns `Complete`, with `frame_pre = frame_post = {0,[]}` and `committed = plan_total = segment_cost[0]`.
- `--resume` naming such an action fails R3 with `stage_site`.

### 2.5 Cap behavior

- `cap: None` is serialized as JSON `null`, and the field is mandatory.
- **Start with no `--logical-cap`:** the stored cap is `None`. There is no admission check, except that `plan_total` is computed with checked addition at validation; overflow → `bound`.
- **Resume, admission check:** with a CLI cap `c`, admission requires both of these:
  - the stored cap is `None` or `c ≤ stored`;
  - `committed + segment_cost[site] ≤ c`, using checked addition.
- **Resume, output:** the output continuation carries the **stored** cap unchanged. The CLI cap is a check for this invocation only. Stored `None` remains `None`.
- **No CLI cap and stored `Some(s)`:** apply `committed + segment_cost[site] ≤ s`.
- **Any failure →** `stage_logical` with attempted 0.
- **False guard:** attempted is reported; committed and cap are unchanged.
