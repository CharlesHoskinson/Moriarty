# Official K references for bounded repayment

This is a dated reference review for the provisional Moriarty repayment slice, not a semantic freeze or proof result. Nine official documentation pages were captured on 2026-09-09 with installed Scrapling 0.4.15. The live website is not version-pinned to the local K 7.1.337 (`4a46d1231473b599c699160132fd6e76a5c46406`) toolchain. Compile and execute the candidate with that toolchain before claiming compatibility.

| Source fact | Application to this slice (recommendation) |
| --- | --- |
| K `Int` represents arbitrary-precision integers; the `INT` module supplies integer operations. [Integer tutorial](https://kframework.org/k-distribution/k-tutorial/1_basic/06_ints_and_bools/), [builtin domains](https://kframework.org/k-distribution/include/kframework/builtin/domains/) | Encode the source/Core amount bounds explicitly. Reject negative and out-of-range inputs and invalid derived balances before committing state. Do not infer machine-word overflow behavior from K `Int`. |
| Configurations declare cells, initial values and external configuration variables; rules can mention only relevant portions of a configuration. [Configurations](https://kframework.org/k-distribution/k-tutorial/1_basic/15_configurations/) | Make cash, funded transfer state, principal, accrued debt and surviving duty observable. Use whole-state comparisons against the evaluator, including unchanged fields on rejection. Configuration abstraction is not itself a financial invariant. |
| Rewrites describe transitions; the computation cell holds the term being evaluated. [Rewrite rules](https://kframework.org/k-distribution/k-tutorial/1_basic/13_rewrite_rules/), [Basics](https://kframework.org/k-distribution/k-tutorial/1_basic/02_basics/) | Let K compute the payment allocation and resulting debt from the input term. A wrapper should transport terms and decode results, not precompute the expected financial outcome. Keep the executable scope finite and explicit. |
| `requires` restricts applicability. Equal-priority rules have no guaranteed ordering. `owise` is a lower-priority fallback (default priority 200 versus ordinary 50). [Side conditions](https://kframework.org/k-distribution/k-tutorial/1_basic/07_side_conditions/) | Give successful and rejected repayment cases explicit, complete guards. Do not rely on source order for deterministic rejection reasons. An `owise` fallback is useful only with a justified covered domain and clear terminal rejection behavior. |
| `[function]` declares a symbol with at most one value and immediate simplification; `[total]` asserts at least one value for every argument. Soundness of simplification rules and preservation of definedness are the author's responsibility. [Manual, function/total and simplification sections](https://kframework.org/docs/user_manual/) | Use functions for arithmetic and predicates and operational rules for state updates. Add `[total]` only when all argument cases are covered; it is not evidence that the compiler proved totality. Avoid unnecessary partial arithmetic and symbolic simplification lemmas in this concrete slice. |
| LLVM supports concrete execution; Haskell supports more advanced formal reasoning and can also execute concrete terms. Backend selection uses `kompile --backend`. [Backends](https://kframework.org/k-distribution/k-tutorial/1_basic/20_backends/), [Tooling](https://kframework.org/docs/ktools/) | Run the pinned LLVM definition for differential examples. Retain inputs, final configurations, compiler/runtime versions and exit codes. A successful `krun` run is concrete execution evidence; it does not establish a `kprove` theorem, compiler correspondence, PCD or Preview acceptance. |

These recommendations do not determine the financial payment priority or source-language obligations. Those come from the current Moriarty design and funded-repayment reference; K documentation explains how to express them.

## Older-note limitations

The existing `wiki/k-framework/k-best-practices.md` describes the older ZKIR definition. Its lifecycle labels and broad portability language do not establish properties of this repayment definition. In particular, CLM-0806 says that satisfiability of `#Bottom` is generally undecidable. The current manual instead discusses the general problem of proving reachability claims whose right-hand side is `#Bottom`; it says the Haskell backend does not attempt those claims and warns. Keep that distinction. No general statement that every partial function causes an LLVM crash was reproduced here. No archive claim is silently migrated or accepted.
