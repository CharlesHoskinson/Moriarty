# Lookup-oriented dispatch and immutable program images

**Recommendation:** independently rebuild three concepts: immutable decoded program images, explicit scalar-table interfaces, and opcode-class event partitions. Prioritize the concepts by their fit to Sherlock; backend mismatch does not disqualify them. No foreign proof-system port or code reuse is needed.

**Source facts.** The [Jolt paper](https://people.cs.georgetown.edu/jthaler/Jolt-paper.pdf), §3.2 and §7.2, separates code, registers and RAM and explicitly discusses two dispatch arrangements: group executed instructions by opcode, or retain a uniform construction covering every opcode. Its latter arrangement can still perform field work proportional to all constraints. Thus “one executed instruction” does not imply “only one branch costs.” The [Lasso paper](https://people.cs.georgetown.edu/jthaler/Lasso-paper.pdf), §1.1 and §3, describes decomposable tables assembled from smaller tables and a collation expression. More chunks shrink individual tables while increasing query/collation work. These are architectural facts; their reported protocol costs are not Sherlock measurements.

Current Jolt is materially different: its [architecture documentation](https://jolt.a16zcrypto.com/how/architecture/architecture.html) identifies Shout/Twist in place of the paper/v0.1 Lasso/Spice arrangement. At HEAD `8bbb2357890928d8f83b00ca542879077c4d3d28`, `crates/jolt-program/src/preprocess/bytecode.rs:23–65` stores decoded rows, an entry address and a PC mapper, prepends a no-op, and pads to a power of two. Lines108–224 distinguish original instruction addresses from expanded virtual-row positions. `preprocess/ram.rs:40–89` sorts initial bytes and packs little-endian words. `crates/jolt-lookup-tables/src/instructions/riscv/add.rs:7–30` defines lookup operands/index/output separately; its output uses wrapping word arithmetic. Sherlock’s checked UInt128 semantics must be rebuilt independently. [Pinned code](https://github.com/a16z/jolt/tree/8bbb2357890928d8f83b00ca542879077c4d3d28/crates).

SP1 HEAD `02fa30185ecd658174b211d56128b14867ab8e81` provides a useful contrasting organization. `crates/core/machine/src/riscv/mod.rs:98–104` separates program, fetch and decode chips. `program/trusted.rs:25–34,80–130,134–290` separates static PC/instruction columns from execution multiplicities. `alu/add_sub/add.rs:164–171` includes Add from nonempty events unless an explicit shape overrides inclusion. `executor/src/program.rs:35–60` separates decoded instructions, initial memory and preprocessing shape. Memory population is separately located in `machine/src/memory/consistency/trace.rs:9–35`. These concrete partitions support a comparison, not an inference that all other chip costs disappear. [Pinned code](https://github.com/succinctlabs/sp1/tree/02fa30185ecd658174b211d56128b14867ab8e81/crates/core).

**Independent rebuild plan and interfaces.**

1. **P1, optimization02/07, UIREQ-001/004/005/012/013/022/024:** define `prepare(P,capacity)->ProgramImage,LayoutReport`. Image contains bounded expression/function records, ordered child/parameter slices, constants and occurrence IDs. Define `fetch(image,ExprId)` and separate `sourceSiteId` from any expanded implementation-row index. Preparation uses the entire admitted program, never just its observed path; recursive calls remain table references. Preserve first-match lookup behavior unless admission explicitly guarantees unique IDs. Report padding, image bytes and preparation time separately from reference work. Cache by exact program bytes plus representation configuration.
2. **P1 concept; P2 implementation comparison, optimization05, UIREQ-006/023/024/026:** define `ScalarRequest={kind,inputLimbs,outputLimbs,auxiliary}` and `ScalarTableSpec={domain,entry,collate}`. Begin with bounded byte/range tables and a checked-add decomposition, compared against direct limb arithmetic. Rebuild carries, overflow outcome and UInt128 layout for Sherlock. No giant full-domain table or wholesale Jolt arithmetic is proposed. Record table size, query count, collation operations and auxiliary width before choosing chunk size.
3. **P1 interface; P2 comparison, optimization05/07, UIREQ-010/013/023/026:** generate an ordered reference trace plus `ClassEvent={stepId,sourceSiteId,preState,postState,logicalDelta}` partitions for Scalar, FrameReturn, CallBind and DataMatch. Compare universal dispatch, per-program constants and fixed classes through optimization05’s common step API. Keep original order recoverable and pending frames explicit. Partitioning is physical organization; it neither changes fuel nor creates financial boundaries.

**Compatibility and counterargument.** Dense images add indirection and padding; subtables add queries and collation; class partitions add event storage and interface crossings. Direct AST/direct arithmetic/per-program circuits may win. Clean requires separate bounded encoding and step definitions. Its public lookup API is not evidence that the selected Midnight lowering supports these tables; the recorded Circom path has unsupported lookup/interact cases. Required new work is image decoding, CEK-state mapping, UInt128 components, class interfaces and the actual Clean-to-native inventory. Existing private Fenrir is the integration destination; no private content was queried. Both repositories report Apache-2.0; this matters only if actual code reuse is later selected.
