# Sherlock arithmetic: explicit carries before representation changes

Fresh online evidence comprises three project families, including Fiat-Crypto’s 2019 paper. **Source facts — Fiat-Crypto [F].** The paper’s §II-C/III and Figure2 separate mathematical values, limb weights and target word sizes. Current generated `fiat-c/src/p256_32.c` and `p256_64.c` expose `addcarryx`, `subborrowx` and `mulx` primitives. The 64-bit addition primitive computes through `unsigned __int128` and returns low word and carry separately; multiplication returns both halves. These are concrete interface patterns. The surrounding P-256 implementation performs modular Montgomery arithmetic, whereas Sherlock requires checked exact UInt128. Importing that algorithm would change semantics. The README offers MIT, Apache-2.0 or BSD-1-Clause at the user’s choice; GitHub’s automated license classification is NOASSERTION, so retain both observations.

**Source facts — Jasmin [J].** The current x86-64 examples `addcarry.jazz` and `mulx.jazz` explicitly expose carry inputs/outputs and product halves. `#MULX` returns `(hi,lo)` while `#MULX_lo_hi` reverses that order. The expressions manual permits explicit word widths and describes little-endian byte/word conversion. These motivate named result fields and versioned serialization rather than positional tuples. The README identifies compiler code as MIT, with documentation separately CC-BY4.0. Jasmin is a CPU language/compiler; its examples supply no arithmetic-circuit exporter.

**Source facts — HACL*/EverCrypt [H].** `dist/gcc-compatible/internal/Hacl_Bignum_Base.h` provides paired 32/64-bit `mul_wide_add2` routines and equal-length addition/subtraction loops. The former updates a low accumulator word and returns a high word. Its 32-bit version uses a 64-bit temporary; the 64-bit version uses the FStar UInt128 abstraction. The captured GCC header exposes `mul_wide(uint64,uint64)` but ordinary UInt128 `add`, `mul` and their `_mod` variants share native unsigned arithmetic expressions. API names alone therefore do not supply Sherlock’s arithmetic diagnostic. The repository root license is Apache-2.0; the inspected bignum header carries MIT and the UInt128 adapter mentions Apache-2.0/MIT. Preserve file-level notices. The attempted EverCrypt paper URL returned403; no claim depends on its unavailable contents.

**Recommendation P1 — freeze an arithmetic interface.** Define `addCarry_b(a,b,carryIn) → {low,carryOut}`, `subBorrow_b(a,b,borrowIn) → {low,borrowOut}`, and `mulWide_b(a,b) → {low,high}` for b32/64. Keep add/sub carry bits distinct from the whole-word carry of a HACL-style multiply-accumulate helper. State input/output order and little-endian limb order in a `layoutVersion`. Use this interface to describe full intermediate results before the existing checked outcome is selected. A UInt128 product conceptually has up to256 result bits; a low128 result alone cannot describe the requested exact multiplication outcome. These are functional engineering proposals; Opus owns circuit requirements and their assessment.

**Comparison and inference.** Two64-bit words need four elementary schoolbook products; four32-bit words need sixteen; sixteen8-bit words need256. These arithmetic counts exclude carry aggregation, conversions, lookup organization and dispatch. Existing Clean U32 comprises four byte fields and U64 eight: **4×U32 and 2×U64 both occupy sixteen fields**. Two/four packed-field encodings would be additional representations, with new adapters. Wider CPU intermediates and fewer word operations do not predict circuit row reductions. Retain the byte layout as the comparison baseline; give the four32-bit design P1 investigation priority because optimization08 already inventories `Addition32Full`. Give two64-bit and packed layouts P2, conditional on complete primitive/representation inventories.
