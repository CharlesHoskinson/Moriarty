**Representation — source facts.** The [paper §3.3, PDF pages5–6](https://namin.seas.harvard.edu/pubs/icfp-lurk.pdf) uses an eager CEK variant and unfolds only needed content-addressed subterms. Beta’s `src/lem/pointers.rs:15–66,179–190` distinguishes `GPtr{tag,val}`, index variants `Atom/Tuple2/Tuple3/Tuple4/Compact`, and a field-valued `ZPtr`; its comment explicitly delays content addressing during interpretation. `eval.rs:952–975` pops `(variable,value,smaller_env)`; lines1158–1162 package a Let continuation with binder, saved environment, expanded body and continuation. These are actual layouts supporting optimization03/04, rather than evidence that Sherlock should adopt hashes or closures.

**Recommendation P1 — separate storage identity from semantic identity.** Introduce candidate interfaces `NodeRef`, `intern(tag,orderedFields)`, `read(ref)`, `EnvRoot`, `extend(root,binder,value)` and `decodeState`. Retain nominal type identity and the bounded node/frame arrays required by UIREQ-007/009/010/026. Decode repeated references to repeated structural occurrences; arena identity never becomes source equality. Preserve saved complete caller maps, including shadowed locals. Beta’s packed arity-specific records motivate comparing uniform records against per-variant payload pools; they do not settle Sherlock’s capacities, UInt128 limbs or hashing choice. The counterargument is extra indirection and padding: direct trees/full frames remain the baseline, and smaller pools must not introduce earlier capacity outcomes.

**Witness planning — source facts and recommendation P1.** Beta’s [`src/lem/slot.rs:1–106`](https://github.com/lurk-lab/lurk-beta/blob/399c4f361dd6ded8d08d7ab9f37b273984679fe8/src/lem/slot.rs) describes allocating slots for the maximum selected branch demand, then three phases: `Block::count_slots`, interpretation into `Frame`, and synthesis using both. `interpreter.rs:50–112` records input/output pointers, typed hint vectors, bindings and program counter; unused hint slots are `None`. For optimization05/07, propose `plan(stepClass,profile) -> SlotCounts`, `recordStep(pre,site,post) -> StepRecord`, and `materialize(plan,record) -> CandidateRow`. This makes selected-path host computation explicit while retaining fixed bounded row layouts. Slot reuse is a candidate Clean layout technique; the source’s R1CS implementation and its cost claims do not transfer to Midnight. No backend port is proposed.

**Successor dissent — source facts.** Lurk0.5 is not merely Beta with a renamed repository. `core/zstore.rs:93–96,207–217` uses tagged digest arrays and DAG dependency variants; `core/eval_direct.rs:1979–1999` recursively follows environment records. `lair/execute.rs:27–76,410–442,487–525` separates `QueryRecord`, memoized function outputs and explicit caller states. `lair/trace.rs:73–101` generates per-function rows, padding height to a power of two with minimum16. These suggest optimization07’s candidate `QueryCache(programVersion,profile,function,args)` and a separate immutable trace store. **P2 only:** repeated identical calls might reuse physical work, but each source occurrence must retain its original logical frames, depth, work charges and stopping positions. Cached query counts are unsuitable as A’s consumedWork. Query-heavy workloads and metadata overhead can defeat this design.

**Juvix comparison — source facts and recommendation P2.** At its archived pin, `Tree/Language/Value.hs:29–40` stores constructors as `(tag,[Value])`; `Base.hs:27–79` distinguishes argument slots, temporary levels and constructor-field offsets. `Tree/Evaluator.hs:171–184,228–241` evaluates named-call arguments, enters fresh temporaries, selects the first matching constructor tag and optionally saves the scrutinee. `Nockma/Translation/FromTree.hs:161–199,550–578` makes `[code,args,env]` positions and constructor layout selection explicit, including specialized list/maybe/noun representations. Borrow the *schema idea* `ConstructorLayout(typeId,tag,arity,fieldOffsets)` for optimization03 and slot-layout metadata for04; keep generic ADTs beyond A’s concrete lists/trees separately admitted. Juvix’s arbitrary integers, closures, backend conventions and host evaluator provide no UInt128 or fuel correspondence.
