# Sherlock optimization lane 08 — exact UInt128 arithmetic layouts

**Status:** nonsecurity performance/design proposal only; no architecture adoption, execution or measurement. Candidate A SHA-256 `57d830f46fee57c56ed8b854d21f5dd7a695d2977d061b1ef6905eaecd7de30e` verified. Priority P1: compare arithmetic organization and inventoried reuse before selecting packing. UIREQ-024/026 require preserved observations and a Lean/Clean correspondence stage. No private integration content, new security requirement, proof or hostile scenario is supplied.

**Concrete public-source finding.** Clean `U32` has four byte-valued field components and `ProvableType.size=4`; `U64` has eight and size8 [C32,C64]. Consequently four existing U32 words and two existing U64 words both flatten to sixteen field components. Calling these layouts “four fields versus two fields” would misstate the actual APIs. Clean `Addition32Full` returns a low32 result plus carry; `Addition32` returns the low modular result [CA]. They are reuse candidates, not complete Sherlock checkedUInt128 operations. Public Boolean interfaces are separate [CB]. No theorem or compatibility result transfers from these observations.

**Typed interface.** Propose `UInt128Image(layout)` with an explicit layout/version tag and least-significant-word-first ordering. Its mathematical decoding is `Σ word[i]·2^(b*i)` for b32 or64; each word uses the inspected byte decomposition when existing types are reused. A candidate `ScalarRequest={operation,left,right}` returns `UInt128Value` or the existing arithmetic diagnostic; comparison returns a distinct Bool result. Source values remain exact mathematical UInt128, never a field residue. Encoding choice cannot turn checked add/sub/mul into modular or saturating source operations. This defines the functional interface only; circuit acceptance/range/soundness work belongs to Opus.

**Arithmetic organization.** Compare chained word-addition/carry and subtraction/borrow against a packed-wide operation followed by representation conversion. Addition32Full's result/carry interface can help organize the former; its modular low word alone is insufficient to define the whole checked result. For multiplication compare schoolbook word products: four32-bit words give sixteen elementary products, two64-bit words four wider products. This is an algorithmic count, not a row estimate: wider intermediates, carries, conversions and native field/layout details can dominate. Inventory multiplication/subtraction components separately rather than assuming a type declaration supplies them.

**Bool and control.** Keep scalar equality/ordering and Bool negation/results typed separately from UInt128 storage. The public Boolean interface is a possible component, not a replacement for the source conditional rule. Sherlock evaluates its condition then only the selected expression branch. Physical branch organization must preserve that evaluation order, pending frames, defined errors and logical work; evaluating both source branches is a semantic change even if their final scalar values agree.

**Stage and preservation map.** K computes checked arithmetic with mathematical integers and arithmetic error10; Lean must define corresponding exact operations and decoding into semantic values. Clean then needs a separately bounded state/word representation and operation interface, followed by the actual compiler/native correspondence. These are unproved/new tasks; no Midnight exporter or backend compatibility is assumed. The current Quint scalar15 algorithms cannot qualify fullUInt128 arithmetic.
