# Sherlock optimization lane 02 — compact typed program representation

**Status:** proposal only; no architecture adopted, implementation changed, model executed or cost measured. Baseline: Candidate A content-freeze SHA-256 `57d830f46fee57c56ed8b854d21f5dd7a695d2977d061b1ef6905eaecd7de30e`, verified before research. UIREQ-024 governs preservation; UIREQ-026 requires the Lean/Clean stage. All integration into the existing private Fenrir Clean stage remains separately qualified; no private material is used here.

**Recommendation, priority P1:** compare an indexed, predecoded AST against the direct AST before introducing typed bytecode. Keep the current reference semantics unchanged. Give each expression occurrence a stable index and retain explicit CEK frames; code layout changes while evaluation rules remain recognizable. This offers a smaller correspondence surface than immediately changing both representation and evaluation machinery. It is a candidate for evaluation, not a demonstrated speedup.

**Source facts.** OCaml's pinned interpreter distinguishes APPLY, APPTERM and RETURN and explicitly stores/restores program-counter/environment context [O, lines474–638]. This illustrates concrete bytecode call machinery, not Sherlock compatibility or a reason to introduce tail-call optimization here. Michelson gives instructions input/output stack types and requires branch results to have consistent types [M, “Introduction to the type system,” “Meta type variables”]. Its typing specification is separate from a typechecking algorithm. Plutus's versioned CEK source separates constructor values, environments and budget spending [P, `CekValue`, `CekBudgetSpender`]. These motivate alternatives; their numeric semantics, closure machinery and cost units are not imported.

| Representation | Proposed interface | Main tradeoff |
|---|---|---|
| Direct typed AST | Existing recursive expressions plus input function table | Smallest change; variable-size recursive code and helper traversal remain |
| Indexed predecoded AST | ExprId→typed record, ordered operand slices, FunId→parameter/body records | Explicit finite layout; additional representation map and table overhead |
| Typed bytecode | Blocks with stack signatures and CONST/LOCAL/CALL/RETURN/CASE/PRIM operations | Compact linear execution; new lowering, stack layout and step correspondence |

**Concrete indexed interface.** `ProgramImage={expressions, operandIds, functions, parameterIds, constants, sourceOccurrenceMap, bounds}`. An expression record holds kind, result type, immediate/index fields and ordered child slice. Frame records retain their existing semantic tag, saved environment and expression IDs. Function IDs remain program data; different programs use one dispatch definition. No code sharing or constant folding initially: distinct source occurrences remain distinct even when equal. Index widths are chosen from declared capacities, not unchecked truncation.

Let α assign occurrence IDs and `decode(image,id)` recover an expression. The initial functional obligation is `decode(α(P),entry)=P` for the admitted fragment, plus explicit environment/frame translation. Concrete K supports dedicated UInt lists/trees rather than generic nominal declarations; the image must expose that limitation. General ADT tables are future coverage, not obtained by adding a typeId field.

**Rule map.** Literal/variable dispatch keeps the corresponding K value/lookup stage. Let/primitive/constructor records push the same pending-context frames; child slices preserve strict left-to-right order. If/match records select only the same branch and preserve source-ordered cases. Call resolves the same function and binds the same arguments; return restores the same caller. Indexing must preserve existing lookup behavior on its claimed domain; uniquely named admitted function tables permit a direct index, while broader first-match behavior needs its own mapping.

**Preservation predicate.** For admitted `P,input,bounds`, require equality of `Obs(runReference(...))` and `Obs(runImage(...))`: outcome class/reason, structural value, ordered effects with financial boundaries, folded financial state, residual duties, pending/checkpoint meaning and cumulative reference logical work. Preserve suspension and bound/failure position, not just final values. A bytecode instruction may correspond to several reference microsteps; it must retain their work charges and intermediate stopping positions. Existing K helper costs remain unresolved and cannot be declared bounded by predecoding. Changed physical byte-cap admission requires an explicit profile decision. No Await/Commit/Yield policy is selected.

**Required stage mapping.** Retain K as reference; define α/decoding and step/run correspondence in Lean using recursive semantic types and fuel-based runs. Give Clean a separately bounded table/state encoding. Map each dispatch/frame operation to that representation; circuit/native correspondence and exporter compatibility remain open. Current Quint has three algorithm-specific transitions, not a general program loader, so it cannot validate this image by assertion.

**Normal discriminators:** unchanged-rule factorial3=6, list123=6, tree45=9; caller-local fixture12; Bool/let fixture7; mutual even4=true. Compare complete state after each named semantic step, including pending multiplication/right-subtree frames. Later suspension/financial specimens retain existing `/2` prefix obligations and remain unmodeled here.

**Counterargument and gaps.** Predecoding duplicates source metadata, pads records and adds indirect accesses; direct AST may already be cheaper. Bytecode may ultimately reduce dispatch more. Compare code bytes, padding, preprocessing, frame/value bytes, rows, prover/verifier time, memory and DUST separately under the same supported envelope. Every comparison is presently unmeasured; no cost ranking or correspondence result is claimed.
