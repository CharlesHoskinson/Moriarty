GitHub’s merge-queue guidance supports one stable required candidate check that runs on both pull requests and queued merge groups. The same bounded CI DAG should evaluate the candidate GitHub is actually asking to merge; queue checks use the separate `merge_group` trigger. A required check can remain pending when workflow-level path filters skip the run. For dependent jobs, GitHub specifically recommends `always()` with `needs` where the required check must report after an upstream failure. [GitHub Docs, “Troubleshooting required status checks”](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)

**Proposal (repo-native inference):** add a small `.github/workflows/sherlock-ci.yml` caller for `pull_request` and `merge_group`, which invokes one local `workflow_call` file containing the ordinary Sherlock DAG. Name its final required job `sherlock-candidate`; make it depend on all checks required for ordinary code changes and run it with `if: always()`, explicitly failing if any required dependency failed or was cancelled. Keep the required caller/workflow unfiltered by paths; use change-aware conditions only on optional jobs, and ensure the final gate still reports. Start with existing cheap repository-native checks and true independent oracles; put SDK/model/degree/proof work behind the existing applicable environment or trigger because its cost and authority differ. This adds a transparent GitHub Actions graph, not another scheduler or vote system.

**Counterpoint:** always running every check can make a small PR wait on SDK-heavy work. Dependency-aware selection helps, but only if the required gate has an explicit policy for which checks apply and cannot silently pass after a required job was skipped. This source addresses status-reporting mechanics, not Sherlock’s command inventory, SDK costs, or the suitability of any check for mandatory gating.
