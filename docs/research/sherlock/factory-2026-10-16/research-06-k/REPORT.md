# K executable semantics and reachability checks

K defines executable semantics as rewrite rules over structured configurations (“cells”). Its manual describes compiling specs into runnable/testable programs and distinguishes concrete execution (`krun`) from claims checked by `kprove`). The manual documents a fail-closed harness pattern: give the status cell a nonzero default and set it to zero only on success. It also requires reachability claim authors to distinguish `one-path` from `all-path`; the latter quantifies over every path and has materially stronger meaning. These are useful design precedents for Sherlock QA.

**Sherlock adaptation (proposal):** For each bounded circuit transition, store the complete input configuration and independently calculated expected next configuration, including all state, emitted effects, and any trace/prefix data. Execute exactly one step with the K semantics, then compare the complete resulting configuration structurally against the oracle. Require explicit termination/success status and the expected step count; treat a stuck state, timeout, missing output, or incomplete prefix as failure. Keep separate tests for deterministic one-step examples and bounded all-branch reachability where nondeterminism exists. Record mismatch paths so changed or missing cells/effects are visible. This is a proposed factory check, not a claim that K’s own regression harness does all of this.

**Limitation:** The cited manual is explicitly under construction. Its guidance supports a testing pattern, but does not establish that comparing one complete configuration proves the Rust/K/Clean semantics equivalent, nor does a bounded reachability check establish unbounded correctness. Backend-specific behavior also deserves care: the manual warns that backend-specific semantic modules make semantics harder to trust even with testing (lines 347–349).
