## Findings

### A01 — High: an actor view does not define complete authorization evidence

Basis: S01 design lines 119–134 and 226–230. The theorem passes an actor view
to `authorizedAt`, but the prose requires authorization of every hidden effect.
The contract does not define how that view carries authenticated evidence for every effect.

Disposition: keep this freeze obligation open. Define the complete effect
projection, its trace and outcome binding, and its unavailable-evidence result.
Test an extra effect omitted from a display view. A supplied Python payment
tuple cannot establish the completeness of a real transaction or private trace.

### A02 — High: effect comparison grants signing authority

Basis: S01 plan at the base revision, lines 734–736. Its `signing_request_permitted` property
returns the result of a transfer comparison. The checker verifies no signature,
state, domain, nonce, fee ledger, disclosure policy, or assumption evidence.

Experiment observation: executing the plan's example returns signing permission
for a caller-created policy and matching caller-created effects.

Disposition for this increment: retain the local effect verdict and its stable
reasons. Make signing permission false for every local result. State the scope
as an effect comparison, not the full `VerificationCertificate` from the theorem.
Later integration must supply the complete authorization boundary.

### A03 — High: coercion changes untrusted effect payloads

Basis: S01 plan at the base revision, lines 697–704. `from_mapping` converts fields with `str` and `int`.

Experiment observation: the example accepts `True`, `1.9`, and `"1"` as quantity
`1`. It accepts a null source as `"None"` and discards an undeclared field.

Disposition for this increment: reject wrong types and unknown fields. Require
positive integer quantities without coercion. Validate direct construction and
mapping construction. Preserve transfer multiplicity with multiset comparison.

### A04 — High: signing-order requirements conflict

Basis: XML lines 95, 691–695, and 1145–1147. T09 requires local rejection before
signing. The specific requirements distinguish `SignAfterResolve` from
`SignBeforeResolve`. S01 design line 272 uses only the first rejection boundary.

Disposition: label the local experiment `SignAfterResolve`. Keep the second
profile and the unconditional T09 wording as an explicit freeze obligation.
Do not claim rejection before an authorization that already exists.

### A05 — High: the proposed validator can accept altered normative content

Basis: S01 plan gates 03–05, 08–09, and `_validate_manifest`.

Repository observations:

- Gate 03 checks predicate IDs and binding presence, but not that every hard
  predicate enters authorization.
- Gate 05 compares premise IDs, but not their required expressions.
- Gate 08 compares the result with editable expected fields. It does not
  independently require success or reconstruct the canonical swap.
- Gate 09 does not require exactly one appended payment or baseline restoration.
- The manifest checks declared hashes against files. It does not compare the
  prompt and design against independent frozen hash constants.
- The manifest omits the verifier and validator implementation from its output set.
- Empty override dictionaries fall back to disk through `override or load()`.

Disposition: strengthen Task 5 before implementation. Add mutation tests for
each condition, including coordinated file and manifest changes. Check exact
premise expressions, required success, canonical payments, and mutation shape.
Pin executable validation inputs and reject empty overrides explicitly.

### A06 — Medium: terminology coverage is incomplete

Basis: XML terminology inventory at lines 100–151 and W4 at line 712.
The S01 plan derives terms primarily from W4 and W5. The XML additionally
requires distinctions between economic partial completion and several atomicity concepts.

Disposition: include both XML inventories in Task 2. Define distinct meanings
for each atomicity boundary. Do not use unqualified `partial_fill` as an authorization predicate.

### A07 — Medium: completion and evidence instructions need correction

Basis: S01 Tasks 5–7 and the existing graph evidence test.

Repository observations:

- Task 5 asks for a passing report before the package validator has run.
  The validator also consumes that report. A report fixture is not run evidence.
- Task 6 predicts `15 passed`, although the listed tests total 16.
  The baseline currently has 77 tests. Report measured counts.
- Task 6 says the user approved the design. The visible source says
  `approved for planning`. Record the current implementation request without inventing approval history.
- `tests/test_marlowe_graph_evidence.py` runs a script that rewrites the graph
  receipt timestamp. A complete test run is not read-only.

Disposition: generate passing evidence only after its predicates run. Keep
historical receipts immutable. Run the suite in the isolated worktree and
exclude its regenerated graph manifest from implementation commits.
