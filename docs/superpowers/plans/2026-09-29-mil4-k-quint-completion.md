# MIL/4 K and Quint Completion Plan

> **For agentic workers:** Use the repository's guarded task contract for delivery work. Use independent K and Quint reviews at each frozen sprint boundary. This plan schedules work; it does not admit a language profile or start a campaign.

**Goal:** Produce one executable, reviewable K specification for the complete *MIL/4 first-profile language*, with an explicit rule or explicit versioned rejection for every constructor, and use Quint to expose state and concurrency counterexamples before K rules are frozen.

**Architecture:** K owns the exact *MIL/4 Core* selected in Sprint 0: syntax, typing, numeric values, ordered six-judgment admission, diagnostics, and complete financial effects. Existing Core/4 and Source/5 are compatibility inputs, not assumed to represent the new language. Quint owns smaller abstract state machines for budgets, obligations, episode phases, replay, authority, and cross-domain interleavings. A projection maps every admitted K transition to a Quint transition while retaining balances, duties, work, heads, replay and effect identity. Source elaboration, native proof, and Preview settlement have separate evidence gates.

**Tech stack:** MIL/4 source and Core contract selected in Sprint 0; existing Source/5, Core/4 and K as reuse candidates; pinned local K toolchain, Quint CLI, repository TypeScript evaluator and fixture format. Pin exact tool versions and candidate digests at sprint admission.

## Scope and completion rule

“Full K specification” here means the frozen MIL/4 first-profile surface and Core, not every future DeFi product. It includes the shared language constructs in [MIL/2](../../../concepts/intent-language/DESIGN-MIL2.md), [MIL/3](../../../deliverables/mil3-design-draft-2026-09-29/DESIGN-MIL3-DRAFT.md), the eight MIL/4 first profiles, and their explicit later-profile rejection boundary. The constructor register must include version header, types, Φ terms, selected program, holes/refinement, evidence, grants, budgets, effects, duties, stage/episode actions, observations and failure branches. A construct is covered only when it has a K formation rule, executable transition or a named versioned rejection. A family arithmetic projection alone is not coverage.

The final definition must have a single composition root under `experiments/moriarty-language/formal/k/mil4/`. Every admitted constructor must have a complete observation and a positive and otherwise-well-formed hostile trace. The MIL/4 proof register must derive its own claims and domains for determinism, progress-or-defined-rejection, type preservation, finite termination, residual-duty conservation, exact effects, authority/history non-reuse and source/Core/evaluator correspondence. The earlier [SP03 execution record](../../../openspec/sprints/execution/SP03.md) is evidence from a narrower language; its observed results cannot be reused without a MIL/4-specific compatibility result. A proof left open is recorded as open; runnable traces do not relabel it proved. No claim about native financial acceptance follows from this K exit.

### Relation to the earlier SP03 plan

SP03's existing K files, fixtures, execution wrapper and bounded financial traces are candidate components. Sprint 0 assigns each one a disposition: **reuse unchanged with demonstrated semantic equivalence**, **adapt and re-review**, **archive as historical evidence**, or **replace**. The new MIL/4 constructor register, stage relation, profile boundaries and proof register define this plan's exit. A green old SP03 trace does not cover a new MIL/4 constructor, and the old Source/5→Core/4 mapping is not presumed total. If Core/4 cannot represent a required MIL/4 term or duty, Sprint 0 versions a successor Core rather than encoding it in a string or caller Boolean. No old theorem is inherited across a changed state or transition signature.

Quint is a design check, not a second byte codec. Its state retains signed scope and endpoints, gross effect lines, remaining and spent budgets, bound obligation parties, work, replay/nullifiers, selected heads, phase, delivered amount and remaining duty. The projection may abstract away hash bytes only after K verifies the same signed identity and predecessor. For each committed action, require: (1) complete ordered K effects and consumption map to Quint without netting away gross debits, (2) the K successor maps to the Quint successor, and (3) a local rejection retains its first judgment/code with no successor. Accepted signed failures and durable unknown states have their own committed observations. Finite comparisons give bounded trace-correspondence evidence, not a proof of cryptographic or ledger correspondence.

## Next implementation sprint: exact work packet

Sprint 1 is the next technical implementation slice *after* Sprint 0 selects the MIL/4 Core boundary and closes the S0 decision gate. Keep it in the isolated research worktree until the existing guarded delivery slot permits promotion. The S0 packet at `deliverables/mil4-successor-2026-09-29/S0-DECISION-PACKET-WORKING.md` is a candidate subset, not the MIL/4 semantic contract; its W-D0–W-D4 rows remain open.

1. **Freeze the comparison domain.** Record the selected MIL/4 source/Core version, S0 signed bytes, asset and nominal bounds, authenticated predecessor, rejection order and exact observation fields in `semantics-contract.md`, `coverage.tsv` and `decisions.md`. Map each older Source/5/Core/4 field into a named authenticated injection or a version rejection. Do not add AMM division or a foreign receipt to this slice.
2. **Define the shared transition record.** Use fields `pre`, `action`, `signedScope`, `preparedEffects`, `post`, `remainingDuty`, `remainingWork`, `replay`, `preHead`, `postHead`, `phase`, `judgment` and `code`. Each accepted result has all effect lines; each rejected result has no published post or effects. Map the exact existing K and evaluator fields before adding a new wrapper.
3. **Write the Quint state and actions.** `s0.qnt` stores one immutable signed intent before submission. Commit actions compare supplied endpoints and claimed pre-head with that scope, debit the signer-bound owner, credit the obligation's bound creditor, and consume a signed replay ID. Keep ordered gross lines, allowance remaining/spent, validity and work. Represent semantic rejection in a comparison observation with the first K judgment/code and no state successor. Place finite instances and per-action witnesses in a separate module. Treat current-head comparison and replay consumption as atomic.
4. **Complete K preparation and acceptance.** Implement or adapt the current K rules so the same transfer/repay stage derives the complete effect vector, consumes allowance and replay, extends the authenticated head and uses named rejection for every failed six-judgment premise. Keep `m4cNativeQualified` and ledger acceptance as external premises until the specified verifier contract exists; do not turn a caller constructor into proof.
5. **Connect observations.** Define `α` in `projection.md` field by field, including initial states. Compare a ledger-committed K stage to one Quint commit on signed scope, ordered effects, balances, principal/accrued, budgets remaining/spent, replay, head, work and duty. For semantic rejection, compare first judgment/code and no-commit result; Quint need not duplicate lexical errors.
6. **Review the frozen slice.** Use one independent financial/effects review and one formal K/Quint review on the same file digests. The financial reviewer checks complete debits/credits and bounds; the formal reviewer checks reachability, invariants, projection and rejection precedence. Route consequential design choices through the repository's two-vote gate rather than treating sampled Quint runs as adoption.

The future execution record should include the exact `kompile` command and result, `quint typecheck`, sampled `quint run` with nonzero witnesses for both actions, and a K/Core/Quint trace comparison over the finite S0 corpus. `quint run` samples executions; it is not an exhaustive proof. Do not run `quint verify` unless the user separately requests model checking. No command or test in this packet was run while writing this plan.

## Sprint gate and stop rules

- Every sprint starts with a requirement-to-rule map and a finite set of independent expected positive and hostile outcomes. A construct omitted from that map blocks the sprint exit.
- K compilation checks syntax and rule structure only. A successful sampled Quint run checks explored traces only. Neither proves native financial acceptance or ledger finality.
- A counterexample goes into the shared corpus before a rule change. Fix the smallest failing relation; do not rewrite a family name or weaken a guard to silence it.
- Freeze candidate bytes before independent audits. If normative bytes change, obtain fresh full-candidate reviews. Record requested and returned model identities and abstentions.
- Keep research K/Quint work separate from the blocked SP01.6 delivery item. Actual source/Core promotion, guarded campaign actions, native proof and Preview observations use their own existing gates.
- If a verifier, finality premise, numeric target or signed byte contract is unavailable, return a named rejection and carry the exact obligation forward. Do not insert a host Boolean to make the path executable.

## Exit definition

The plan ends when the complete MIL/4 first-profile constructor register, canonical versioned syntax, static judgments, K operational rules, six-judgment admission, effect and duty accounting, failure/recovery relations, and all eight first-profile adapters exist in one executable K definition. Representative multi-step traces project to the Quint models and match the evaluator on the *newly declared* source/Core domain. MIL/4-specific K proof claims have explicit discharged or open results with assumptions; none is inherited from old SP03 by name alone. Later profiles are explicitly rejected. That is a *full working K specification*; adoption, native proof correspondence and Preview financial settlement still require their separate roadmap evidence.
