## 2. Formatter semantics under the new argv

I confirm the prior reviewer's basis for libtest's pretty formatter with `--test-threads=1`, `--show-output` and no `RUST_TEST_NOCAPTURE` (the environment is exactly the declared variables). On success, stdout is:

1. `running 1 test`
2. `test <name> ... ok`. The body's `print!`/`println!`/`eprint!`/`eprintln!` output and panic-hook output are captured per test, so nothing interrupts this line.
3. A `successes:` section containing `---- <name> stdout ----`, the captured text, then the indented name list.
4. `test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in …`

**Checked against the exact `test_membership`:**

- **The `running 1 test` regex matches.** libtest uses the singular form for one test.
- **The result regex yields exactly one tuple, `[(name, "ok")]`.**
  - Section headers start with `----` and the name list is indented, so neither matches `^test `.
  - Op 15's captured `actual_compile_only_artifact=…` and op 16's `complete_step_events_debug_path=…` lines (as described in the prior opinion) also do not start with `test `.
- **The summary regex matches.** The literal `filtered out;` is followed by `finished in`, and the first four groups are `(1,0,0,0)`.
- **`filtered_out` is 0 for both ops.** List ops 08 and 09 each expect exactly one member, so Root's separate `filtered_out == 0` check holds for 15/16.
- **There are no ANSI codes.** stdout is a file, not a TTY, and `--color` defaults to auto. This is the same condition the approved ops 11–14 already rely on.
- **Failure paths fail closed.**
  - A failing body yields `test <name> ... FAILED` plus a `failures:` block containing the captured output, which is printed regardless of `--show-output`.
  - The tuple check rejects that output.
  - A forged `test result: ok…` line inside captured text cannot rescue a failing run, because the tuple check is independent.
- **Diagnostics are retained.**
  - On success, captured output now goes to `stdout.bin` in the `successes:` block, so nothing is lost.
  - Captured `eprintln!` output moves from stderr into that stdout block, so `stderr.bin` will normally be empty on success. No stderr expectation is stated.
  - The two `create_new` Debug event files are written through the environment-variable paths and are unaffected.

**Remaining uncertainty (each is fail-closed and none can produce a false pass):**

- **U1 — direct stdout writes bypass capture.** Libtest capture only intercepts the print macros and panic output. If either body writes with `std::io::stdout().write_all`/`writeln!(io::stdout(), …)`, or through a raw file descriptor, that text would still land on the result line and the op would fail. The prior opinion describes `println!` output, and I did not re-read the bodies.
- **U2 — a captured line could match the result regex.** A captured line of the form `test X ... Y` would add a tuple and fail the op. Nothing like that is described.
- **U3 — the 131072-byte cap.** The summary now follows the captured block, as it did under `--nocapture`, so total stdout volume is essentially unchanged. If the helper's truncation or overflow rule drops the tail, the summary is lost and the op fails. This exposure is not new.
- **U4 — `--show-output` support.** The flag has been stable since Rust 1.39. An unsupported toolchain would reject it as an unknown option.
