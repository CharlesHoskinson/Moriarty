## Scope 2: source correctness of the five Python files

I read all five files in full and traced every runtime path that consume() can take.

### `consume_continuation_window.py`

**Bounds and schedule**
- Guards on `(512, 32, 16, 30)`, `len(windows)==30`, integer index, and `(start,end,bound)==(32+16i, 48+16i, 16)` together pin the schedule.
- A frozen prior is only accepted when `start==32`.

**Dependency chain**
- For index ≥1, the prior checkpoint must have `status==CONTINUE`, the same case, bound 512, and `actual_advancing_records==start`.
- All three row paths must equal the predeclared `expected_*` paths. I checked the template linkage:
  - checkpoint `raw_tape.path` = `@PREVIOUS@-reduce/result.kore`
  - `prefix_wire.path` = `@PREVIOUS@-consume/prefix.actual-wire.json`
  - `next_query.path` = `@WINDOW@-reduce/input.kore` = `window.query`
- Window 0's `next_query_output` equals `windows[1].query`.
- `read_pinned` compares the whole `{path, bytes, sha256}` dict.

**Query identity**
- The query must equal `resume_query(prior_raw, 16)` byte-for-byte. This makes it impossible to substitute a query generated from JSON or from expected data.

**Boundary and join**
- The typed boundary check `_same(prior[-1], new[0])` is type-strict.
- `join_complete_chunks` drops exactly one boundary row. It re-checks Program immutability, the one-event extension per step with `_same`, no state after a terminal, and that a short window is only accepted on a terminal.
- Global `len(events)==ordinal` is checked.

**Status precedence**
- Order is HALT, then OUTSIDE, then BOUND (used==512), then CONTINUE.
- CONTINUE is only reachable when `used==end`, so CONTINUE at index 29 is impossible (it becomes STOP_BOUND). The `index+1` guard is a redundant backstop.

**Persistence and outputs**
- All writes use `xb`. The checkpoint is written last, so a partial failure leaves no checkpoint and nothing downstream can continue.
- `observerCuts` is derived only from actual joined length.
- No expected documents are opened. No process is launched.

### Helper modules (`kore_continuation.py`, `complete_chunk_wire.py`, `complete_k_wire.py`, `nominal_trace_codec.py`)

- They are byte-identical to the preimages, per the attested pins.
- `resume_query` takes the third ngTape argument verbatim after whitespace trim. It wraps only `OBSERVE(…, \dv Int)` around it and checks 5-arity of ngState.
- `application()` correctly treats Kore `'` label quoting as non-delimiting and `"…"` as strings.
- `CompleteKWire` checks that the API declarations match the registry arity. Its decode of Maps keeps duplicate keys, and its list decoding (`_rows`) is iterative.
- API drift between the first-window decode and this decode would surface as a typed-boundary key mismatch. The check is self-detecting.

### Composition argument

The claim that the joined prefix equals one `ngObserve(initial, 512)` holds given these retained premises:
- `ngStep` is a deterministic function of the 5-field state.
- The observer counter is external to the state.
- Cumulative events live inside the state.
- No terminal stutter occurs.
- K's parse of the carried raw final is that state.

The last premise is verified *one window later* by the next typed boundary. The final carried state is never re-queried, so it needs no such check.

**Advisories (non-blocking, no re-review needed unless adopted):**
- **A1** `next_carry` is computed and then discarded. Recording it in stdout or the checkpoint would make each hop self-describing.
- **A2** The consumer does not pin-check `contract`, `api`, `syntax` or its own imports. This relies on Root (see M2).
- **A3** There is no byte check `raw_parts[0] == carried final`. The typed check plus the next-window boundary cover this semantically, so it is optional hardening.
- **A4** `first-case.complete-observed-wire.json` is written for STOP_BOUND and STOP_OUTSIDE_MODEL as well. The wire carries no status, so any later consumer must read `checkpoint.status` alongside it.
- **A5** The whole prefix is re-validated and re-serialized each window. This costs O(n²) per window and O(n³) overall. It is acceptable at the expected scale (see Scope 3).
- **A6** `application()` assumes Kore comments contain no top-level `,`/`(`/`)`. This holds for the observed `/* InternalMap: */`, `/* Inj: */` and `/* concrete element: */`.
- **A7** `PrintedTermParser.term` recursion depth grows about one frame per cumulative event. That stays under the default limit of 1000 to roughly n≈900 but is untested beyond n=32.
- **A8** `complete_states` uses `==`, which conflates `True` and `1`. `join_complete_chunks` re-checks with `_same`, so this is closed.

### Prospective risk: completion is not established

This is my structural analysis, not an observation.

**Raw Kore grows about quadratically per state.** Kore pretty-printing indents each successive `ngEvent` cons cell by +4 spaces. This is visible in the seed, where cells sit at indents 8→132 and their content lines inherit that indent. A raw ngState with *n* events therefore carries Θ(n²) indentation bytes.

The data agrees: state 16 is 228 KB and state 32 is 493 KB, a ratio of 2.16, which is superlinear. A window tape holds about 18 such states.

Illustrative fit, assuming about 70 KB of fixed size: size(n) ≈ 70K + 6.6K·n + 206·n² bytes.

| Window start S | Estimated tape |
|---|---|
| ≈64 | ~29 MB |
| ≈104 | ~54 MB |
| ≈120 | ~69 MB |
| ≈248 | ~260 MB |
| ≳350 | above FSIZE 512 MiB (→ SIGXFSZ) |

**Reduce wall time.** If kore-exec time scales roughly with tape bytes (observed ≈0.3–0.45 s/MB), the 30 s wall is reached somewhere around S≈110–160. The host was already loaded during the passed run: load average ≈13 and CPU PSI "some" ≈53–70%. That adds inflation, and there is no RSS cap on Haskell-backend memory.

**Consumer.** The indented JSON prefix grows as ≈ N·8 KB + N²·1.5 KB. That is about 30 MB at N≈140 and should be fine. Much larger N would strain the pure-Python indented encoder and the O(N²) `_same` pass.

**Where the program likely terminates.** A coarse reading of the supplied Program suggests termination in roughly the 120–150 advancing-record range. This is non-binding. It is not an oracle or a golden, and it must not enter scheduling or comparison. That range overlaps the estimated wall-time risk zone.

**Consequence.** Every failure mode above (timeout-kill, SIGXFSZ, consumer exception) is a clean fail-closed stop under the contract:
- evidence is preserved;
- no checkpoint is written for the failed window;
- the suffix stays UNRUN;
- there is no retry.

That is why I judge the proposal *eligible*. But a timeout ends this selection without any termination claim. Any remedy, such as resuming from the last CONTINUE checkpoint with smaller windows, changes the hard-coded `16`/`32+16i` schedule. That would be a new source and contract requiring fresh review, not an in-flight adjustment.
