## Item 1: assessment

**The refusal diagnosis is correct.**
- `source_binding` calls `pin_schema(p)` for each `m['head_files']` entry.
- `exact(p,'path sha256','pin')` rejects the extra `bytes` key, which produces exactly `schema keys: pin`.
- The guard never checks a head-file byte count; it checks only the SHA via `check_pin`. Dropping `bytes` therefore loses no guard-enforced integrity, and SHA-256 binds content and size anyway.

**The equivalence is enforced in code, not only asserted by the proof file.**
- Both the issuer and the preflight assert `after==dict(before,head_files=[{path,sha256}…])`.
- This is exact equality over all top-level keys, including the full `files` map, `root`, `head` and `excluded_directories`. It also preserves head-file order and forbids extra keys.
- Both inputs are hash-pinned, so the relation is a durable property of the two hashes. A later TOCTOU cannot break it.
- Arithmetic cross-check: 7444184 − 7444090 = 94. With `indent=2, sort_keys` at depth 3, each removed `      "bytes": N,\n` line is 6 + 9 + digits + 2 bytes. That gives 19 + 19 + 18 + 19 + 19 = 94, which matches. This is consistency only, not verification of content.

**The review identity is handled truthfully.**
- The security and nonsecurity receipts keep `source_manifest_sha256` = `1632a29a…`. The issuer asserts this in `observed_review` and in the receipt loop, and the preflight asserts it again.
- Guard `consent` requires only HEX format plus pair agreement for these receipts. It never tied them to `c['source_manifest']`, so this change introduces no regression.
- The consumed manifest `1e042df3…` is bound transitively, through `config_inputs`, into the Root and tier receipts.
- The link between 1632 and 1e042 lives only in the issuer/preflight assertions and Root's adoption record, never in the guard. That is the stated design, and it is acceptable.

**Every refusal comes before the first write.**
- The adoption-file check and the prephase-raw check both run before the first `put` (`ROOT-CURRENT-STAT-CUT-DIFF.json`). So does the `UNISSUED` `old_home_stats` path assert.
- In the current state, the issuer therefore refuses with no writes.
- Post-write asserts still exist, as before: tier templates, the token scan, and the `argv` checks. A failure there leaves a partial `future-actual-03` that must be preserved, and any retry needs a new namespace.

**The counters are correct and counted once.**

  - P = 739509969

### Non-blocking hardening (optional, not required for APPROVE)

- **H-a.** The preflight takes `original_review_manifest`, `consumed_manifest` and `proof` from `ROOT-ACTUAL-ADMISSION.json`, and it does not pin that file itself. Adding literal asserts would remove that reliance:
  - `compat['original_review_manifest']['sha256']=='1632a29a…'`
  - `compat['consumed_manifest']['sha256']=='1e042df3…'`
  - `compat['proof']['sha256']=='d638adda…'`
- **H-b.** The preflight checks `subject['cargo_lock_sha256']==actual['Cargo.lock']` but not the guard's `LOCK` constant (`3fbc2453…`). Items 2 and 3 cover this through the real guard. A literal check would catch a mismatch earlier.
- **H-c.** The issuer hard-codes `whole_wall_debit_ceil: 5`. It could instead derive this as `ceil(steps[-1]['elapsedSeconds'])` from the pinned raw file. This assumes `RAW-POST-TERMINAL-CGROUPS.json` is the record containing `steps`, which the matching 2783-byte size suggests.
- **H-d.** `source=c['source_manifest']['sha256']` is now unused dead code. It is harmless.
