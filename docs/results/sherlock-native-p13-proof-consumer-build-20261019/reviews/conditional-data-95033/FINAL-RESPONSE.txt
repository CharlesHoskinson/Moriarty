## 1. Why 281/281 under 300 fits (from the supplied bodies)

**Timer ordering**
- `consent`, `supervisor_envelope` and `enforce_post_p11_historical_debits(at_start=True)` all run before `setitimer(ITIMER_REAL, total_wall_seconds)`.
- So the whole-job timer fires at outer-relative time T_pre + 281, where T_pre is the time from the start of the outer cap to the `setitimer` call.
- At 300/300, the outer SIGKILL would always win. With 281, the in-process refusal path is reachable whenever T_pre < 19 s.

**F wall is redundant**
- In `launch`, `start=time.monotonic()` is taken after `setitimer` and after the pre-launch checks.
- So F wall 281 can never expire before the whole-job timer. The total timer is the effective cap.
- Setting both to 281 is consistent and only needs the ≤ relation. It changes no logic.

**Phase CPU**
- `debited_group_init` sets `prior_cpu = debit_state['effective_phases_usec_at_start']` for phase F.
- `launch(..., retained_audit=False)` does not overwrite it.
- With an F cap of 1,140,026,337 and an effective prior of 840,026,337, the fresh allowance is 300,000,000 µs. A larger prior shrinks it, which is safe.

**Stderr**
- `counts` is shared across all three F variants.
- In the main loop, `need(counts<=cap)` runs before `log.write`. In the drain path, `take` clamps writes to the cap.
- So the on-disk F stderr is at most 2,097,152 bytes. The helper's historical-prefix check only refuses after capture.
- Worst-case Root debit: 79,686 + 2,097,152 = **2,176,838 < 16,777,216**. Correct.

**Arithmetic**

## 2. Honest limitations (existing, unchanged by the amendment)

1. **The 19 s is not a guaranteed cleanup window.** Real cleanup headroom is 19 s − T_pre − launcher latency. The cleanup path after SIGALRM is:
   - `group.kill`
   - `proc.wait(timeout=5)`
   - `group.close` (body not supplied, duration unbounded as far as I can see)
   - the `TERMINAL_FAILURE` receipt

   Nothing in the supplied code bounds that total under 19 s. If it overruns, the outer SIGKILL lands mid-cleanup: no receipt, and the leaf may be unclosed.
2. **A `TimeoutExpired` from `proc.wait(timeout=5)` replaces the `Refusal`.** It also skips the rest of the inner `finally`. The outer `finally` (`group.close`) and the receipt attempt still run.
3. **The drain path can outlast the alarm.** If SIGALRM lands before the listener handoff, the drain loop is bounded by `start`+281, not by the alarm. It can therefore run past the alarm by up to the gap between `setitimer` and `start`. In practice it ends at EOF after `group.kill`.
4. **The whole-job timer also covers post-compile work.** That includes post-compile verification, `enforce_post_p11_historical_debits(at_start=False)` and the result receipt. A compile that succeeds late can still end in refusal, which is fail-closed.
5. **`RLIMIT_CPU` with soft == hard ends in SIGKILL with no Python cleanup.** The limit is inherited per process by bwrap, cargo and rustc. A child that hits it exits nonzero, which leads to a clean refusal. The supervisor hitting it means no receipt.
6. **The phase CPU limit is a polled `Group.check`** (body not supplied), checked about every 50 ms. Unless `quotas` installs a kernel cap, the actual figure can overshoot 300e6 by up to poll interval × CPUs. If the supervisor is SIGKILLed, an orphaned leaf could keep consuming CPU. So 300e6 is a planning bound, not a ledger value.

All of these fail closed with respect to native output acceptance. They only weaken receipt and cleanup completeness, which the conditions below address.
