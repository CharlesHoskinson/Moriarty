## 1. Retained family API — sound, with the stated authority boundary

`C6PushFamilyParams` in `c6_push_step.rs` has private fields `cfg`, `admission_bounds`, `limits`, `binding`, `expected_ctx`, `caps`, and `geometry`. Its only constructor, `new`, derives every cached value itself:

- `binding` via `C6MetaConfigBinding::from_host_config(admission_bounds, &cfg, limits)`, i.e. the reviewed META constructor over the separately retained admission `BoundsC` and the complete `cfg.layout`;
- caps/geometry via `geometry_from_config`, which runs `cfg.state_context(&limits)` → `C6StateContext::from_parts` → `effective_for_extended_domain(cfg.ext)` → `C6StateCaps::from_parts`/`C6PhysCaps::from_parts`, then `C6PaddedCarrierGeometry::checked_new` against `limits.max_state_lanes`;
- `expected_ctx` as the immediate `encode_context(cfg.ext, cfg.budgets)`, with a decode roundtrip check.

Public access is read-only: `cfg()` returns a reference to an owned config with no mutable path through this type, `admission_bounds()`/`limits()`/`expected_ctx()`/`caps()`/`geometry()` return copies, and `meta_binding()` returns a clone of a binding whose own fields are private and whose constructors are `pub(crate)` validated constructors. There is no field-literal, decoded-witness-config, host-bool, or assertion-type route to manufacture an inconsistent binding/caps/geometry/cache combination. The selected relation parameters are therefore internally consistent by construction.

`validate_geometry` recomputes caps/geometry from the retained cfg/limits through the same Core chain and refuses a supplied geometry that differs. `emit_c6_push_step_block` calls it immediately after the scope and `LANE_BITS` checks and **before** any length checks, canonical blocks, or emission, so geometry mismatch is an ungated host derivation refusal, not a `debug_assert` and not a circuit result. The builder takes the family rather than loose geometry/meta-limits and derives geometry from `source_params.geometry()`, so the normal builder path cannot independently raise caps while parent DATA/frame code uses different caps. The low-level `C6PushStepInputs` still exposes `geometry`, but the emitter validates it against the family before use; inside emission, parent frame/DATA code uses the validated `g.caps`, while PROG/CTX uses `inputs.source_params.caps()`, and validation makes those the same caps.

The manual `PartialEq`/`Eq` is correct: it compares `cfg`, `admission_bounds`, `limits`, `expected_ctx`, `caps`, `geometry`, and the binding through the existing crate-visible `admission_bounds()`/`layout()`/`limits()` getters. That is sufficient because the binding’s derived arrays (`admission_values`, `layout_values`, `capacity_values`, `layout_variable_expected`, `layout_total_lanes`) are deterministic functions of exactly those three retained inputs and the binding has no other constructors. The Witness’s public `PartialEq`/`Eq` is therefore preserved, not silently dropped: `C6PushStepWitness` still derives `PartialEq, Eq`, now satisfiable because the family implements them manually. `C6PushStepInputs`/`C6PushStepCircuit` remain `Clone, Debug` only, as before; no trait was removed there.

Semantics that must not be blurred: a family copied from a witness — notably through the test helper `circuit_for(w.source_params().clone())` — is self-selected by that witness’s producer. It proves the circuit enforces *that* family; it does not prove the family is the verifier’s family. `witness_from_host_pair` honestly builds the family from the caller-supplied `cfg`, the caller-supplied `limits`, and `pre.admission.bounds`; `witness_from_owner_step` inherits exactly that through `witness_from_host_pair` after one actual recorder step. A future native consumer must still independently select or reconstruct the expected family/spec, compare the reconstructed circuit/IR and lengths/offset/mode/scope against it, and only then use ledger keys. That is future P1 work, explicitly absent here, and its absence does not invalidate this source relation.
