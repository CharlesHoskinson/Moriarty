## 2. Parser change

**Lexer.**
- The new alternatives only start at `~` or `.`. Any string the original tokenized contains neither character, so on every input the original accepted, tokenization is identical.
- `\.K` needs `K` immediately after the dot, so `. K` fails tokenization.
- `.Kjunk` tokenizes as `.K` followed by `junk`, which the exact-tail check then rejects.
- The whole stripped text is still tokenized before parsing, so stray `<`, `~` or `.` anywhere still fails.

**Parser boundaries.**
- **Value position:** `~>` or `.K` is neither an integer nor in `ARITIES`, so it raises "unevaluated/unknown constructor".
- **Inside an open constructor:** `~>` hits "expected comma or closing parenthesis".
- **The only new acceptance:** `need_value` is false, the stack is empty and a top-level value has been produced, and the remaining tokens are exactly `["~>", ".K"]`. After `break`, the unchanged post-checks still require an empty stack, `not need_value` and a `Term` root, so a bare integer root such as `17 ~> .K` is still rejected.

**Accepted language.** The new language is the original accepted set plus each original-accepted complete tree followed by exactly `~> .K`, with insignificant whitespace (zero or more). The returned `Term` is the unchanged full tree. There is no search, split, truncation, last-term selection or fill.

**Semantics.** `T ~> .K` is `kseq(T, dotk)`, which is exactly the shape `frame` built. Requiring the exact unit tail means "no residual K items". Any unreduced `lcFinish`, `#And` or `<generatedTop>` still rejects.

**Wrapper.** Only one outer `<k>…</k>` is stripped, as before. `<k>T</k> ~> .K` and multiple wrappers both fail tokenization at `<`.

**Consistency with Root's observation.** The reported failure was at offset 37872 of a 37890-byte file. Had a `<generatedTop>` prefix been present, it would have failed at offset 0. The tail beyond the tilde is still unseen by me. If it is anything other than exactly `~> .K`, new06 fails closed; it cannot falsely pass.
