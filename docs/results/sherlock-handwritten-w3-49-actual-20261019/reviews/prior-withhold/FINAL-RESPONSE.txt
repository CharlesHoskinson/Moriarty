## 3. Mandatory findings

**F1 — Blocking: unread emitter in the call closure of 22 operations.**
`space_read_any_kind` in W3-06 and in W3-10 calls `emit_enabled_fetch_block`, whose body is absent. Affected operations:

| Ops | Tests | Path to the unread body |
|---|---|---|
| 01–08 | Add arithmetic | Includes 08 via `emit_public_b_scalar_arithmetic_add` |
| 34–37, 40–43 | Add chains | Stage 1 uses Add arithmetic |
| 44–46 | Sub chains | Stage 1 uses Sub arithmetic |
| 47–49 | Sub `three_tests` | Sub arithmetic directly |

Consequences:

- **Effects.** The effects class `HOST_EMITTER_EVALUATOR_OR_CONSTRUCTOR_CHECK` for these 22 rests on code nobody has reviewed here.
- **Interpreter compatibility.** The interpreters in W3-07, W3-09 and W3-12 reject any instruction outside their match arms (no `DivModPowerOfTwo`, no `PublicInput`, and so on). Whether the fetch block emits only supported instructions is unknown.
- **Assertion relevance.** Op 42 asserts that `%ns_s1_arith.const_fetch.temp.0` and `.data_fetch.temp.0` are emitted names. That depends on naming inside `enabled_fetch.rs`.

To lift: supply the complete `enabled_fetch.rs`, plus anything it calls, for a fresh review.

**F2 — `ConstructionError` definition unread.**
Ops 07, 16, 38 and 42 compare `Err(…Fetch(ConstructionError::…))` with `assert_eq!`. That relies on `ConstructionError`'s `PartialEq`, whose impl is unread. For ops 16 and 38 in the reduced set, this is precondition P8.

**F3 — `test_membership` cannot be reused verbatim with these operation dicts.**
The helper reads `op['expected']['exactTest']`, but every frozen op uses the key `expectedMembership`. Called as-is, it raises `KeyError`. Root must declare the exact adapter, for example `dict(op, expected=op['expectedMembership'])`. Also, `test_membership` does not check that `filtered_out == N-1`; that comparison is extra glue Root must state.

**F4 — Stale, contradictory fields in `EXACT-49-OPERATIONS.json`.**

- `"ELF": {"path": null, … "PENDING_ACTUAL_NEW_W3_BUILD_OUTPUT…"}` contradicts the 49 argv, which already name `execution-copy-01/mori_backend-W3-3a2f695515330e5a`.
- `actualListOperation` uses `/PENDING_NEW_W3_ELF/…` with `--list --format terse`. That differs from `EXACT-LIST-OPERATION.json` (plain `--list`).

Root must record that `EXACT-LIST-OPERATION.json` and `ACTUAL-ELF-AND-EXECUTION-COPY-BINDING.json` are authoritative, and that the embedded stanza is never executed.

**F5 — No existing primitive parses `--list` output, and the list may overflow its stream cap.**

- The helper has no list parser. Root must state the exact predicate. Count only `^(\S+): test$` entries and require each of the 49 names to appear exactly once among them. Read the summary line `^(\d+) tests?, (\d+) benchmarks?$`.
- Define N as tests plus benchmarks. libtest's `filtered out` counts both, so N−1 is only right with that definition.
- Each list line is up to about 140 bytes. If the crate has roughly 900 or more tests, `--list` stdout exceeds 131072 bytes. The capture then records a cap overflow and fail-stops before any test runs.
- That would be a controller outcome, not a test failure. It consumes the attempt, and a different list operation would need fresh review (no cap raise is allowed).

**F6 — The acceptance predicate is spread across prose; the helper's `main` is forbidden.**
Exit 0, no `controller_failure`, `full_stream_retained` on both streams, membership with N−1, and the post-checks were enforced only in the forbidden `main`. Before selection, Root must write down the exact per-operation predicate and the fail-stop rule as a composition of existing functions.

**F7 — Resource counters are not bound.**
Only raw debits are supplied, for example `phases` at `usage_usec 96917530` and the ledger root at `116543574`. No remaining allowance is given. Worst-case child consumption:

| Selection | Wall (s) | CPU (s) |

| Reduced 28 operations | ≈280 | ≈224 |

Neither cgroup placement nor whether these debits count against an applicable counter is stated. I am not inventing a limit. Root must bind it (P4).

**F8 — Teardown still pending.**
The raw receipt shows `pids.current 0` in all three cgroups, but `memory.current` is about 4.06 GB in `phases` and the binding says "teardown: Root next". The ordering is unresolved (P3).

**F9 — ELF-to-source linkage is asserted, not reviewed.**
I cannot confirm the ELF was built from exactly these 13 bodies. Op-00 membership only partly corroborates it.

**F10 — Timeout risk is not a safety issue but would consume the attempt.**

- The binary is a `target/debug` (unoptimized) build.
- The interpreters in W3-02 and W3-04 decode each immediate by looping `Fr::from(candidate)` over 0..=1024.
- Chain tests evaluate large instruction streams several times. Op 42 emits about 30 chains; op 43 evaluates 4 chains and round-trips JSON.
- Under 8 s CPU and 10 s wall, a kill is possible. Under fail-stop it ends the campaign without saying anything about the source. A stack overflow in a debug test thread is similar (process abort). I do not predict either outcome.

**F11 — Effects classification is slightly understated for op 29.**
Besides `IrSource::load`, op 29 directly calls `serde_json::from_value::<Operand>` on both the accepting and the rejecting path. It is still in-memory SDK serde only, with no I/O. In my read scope no selected test performs file, network, environment or subprocess I/O.

**F12 — Assertion relevance (not soundness).**

- **Interpreter semantics differ from the SDK.** The interpreters use host u128 values with no `Fr` wrap. `ConstrainBits`/`LessThan` with 128 bits are unchecked, and immediates outside 0..=1024 cause rejection. A pass shows only that the emitted stream accepts or rejects under these host semantics.
- **Some assertions only pin layout.** Op 13 pins instruction indices 142 and 144 and temporaries `.68`/`.70`. Ops 30 and 41–42 pin first-failure ordering and names. These are emitter-layout and token assertions.
- **Expected values are authored, not independent.** Some come from host `checked_add`/`checked_sub`, the rest are literal. No independent oracle exists for this union.

**F13 — Stale documentation (non-blocking for execution).**

- W3-10's module docs say the Add-specialized completion, return-right and P1 emitters "do not consume this block".
- W3-11 says return-right "rejects every enabled Sub state".
- Both are contradicted by W3-05 (`emit_k_machine_return_right_sub_block`) and W3-01 (`emit_b_sub_to_publication_chain`), which now consume these carriers. This should be corrected before any source adoption.

Within the read scope I found no source defect that blocks the 27-operation subset.
