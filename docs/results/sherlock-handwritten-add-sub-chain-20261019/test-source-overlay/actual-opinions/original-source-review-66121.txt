## Mandatory security issue

Each negative checks only:

> `err.contains("ConstrainEq failed")`

The harness formats every failed equality as `step {index}: ConstrainEq failed ({va} != {vb})`. Therefore:

- Forging `%sb.s1.h.st.u128.0` to `19` shows that some equality rejects it, but does not prove that the Sub arithmetic staged-difference check is the first or specific rejecting relation.
- Forging `%sb.s3.ctrl.pec` from `10` to `11` shows inconsistency somewhere in the return-right/primitive/P1 chain. It does not isolate the intended typed handoff, especially because `11` remains a domain-valid primitive error code.
- Forging `%sb.s5.out.rej` from `11` to `10` shows some equality rejects the final state. Source tracing limits `s5` consumption to P1, but the assertion itself still does not encode the P1 guard, expected pair, or first failure.

The positive baseline is evaluated before each mutation, and each mutation changes one lane, so these are meaningful generic non-vacuity witnesses. They are **not** exact guard-isolation witnesses.

**Mandatory correction before approving the claimed security isolation:** pin each negative to its actual exact first-failure values/step or another assertion that uniquely identifies the intended relation. The correct exact strings must be established from the real emitted instruction order, not guessed in this review. Until then, the supportable claim is only “a single-lane forged witness is rejected by some `ConstrainEq`.”
