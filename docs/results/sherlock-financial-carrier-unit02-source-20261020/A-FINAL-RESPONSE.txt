## 1. Source-design faithfulness

The sealed checked-construction design chosen by the owner is actually implemented:

- `FinBoundSource` has private fields and is produced only by `bind_fin_source`.
- `FinSnapshot` has private fields, stores a clone of its producing `FinBoundSource`, and is produced only by `FinSnapshot::from_core` or mutated through checked operations.
- `FinAdmittedExtras` has private fields. `FinAdmittedExtras::new` calls `validate_fin_plan`, then checks exact action count, order, and name identity against the bound source.
- The parent change is exactly `pub mod fin_carrier;` to `pub(crate) mod fin_carrier;`.

`bind_fin_source` now checks profile identity, strictly sorted view names, `name_rows`, `name_bytes`, state/asset capacities, initial-state type consistency, state/state, asset/asset, and state/asset duplicate declarations, duplicate asset identities, and resolves program, state, asset, and action names. Duplicate actions are also refused.

Structural source identity is correctly limited to carried names, state bindings, asset bindings, action bindings, and capacities. The code does not prove full `ProgramView`, expression, occurrence, cryptographic, admission, or V8 identity, and it does not claim such proof in its operative checks.

Canonical balance order is coherent. `FinSnapshot::from_core` sorts by actual `AssetId`, then account; `check_fin_snapshot` enforces that same strict order; `to_core` emits the stored order. `uc05_multi_asset_balance_liability_core_roundtrip` discriminates declaration order `zeta(row 0), alpha(row 1)` from Core `AssetId` order `alpha, zeta`.

## 2. Security and refusal completeness

No reachable forged-vector counterexample remains in safe production code outside the module:

- Read-only getters return shared slices or references. They do not expose mutable snapshot, source, or extras fields.
- Cloning preserves previously checked values; it does not create a new construction path.
- Every consumer — `to_core`, `apply_set_state`, `apply_liability_add`, and `apply_transfer` — first calls `check_fin_snapshot`.
- `check_fin_snapshot` checks stored-source equality, state length and types, supplied balance/liability capacities, asset-row ranges, strict balance order by `(AssetId, account)`, and strict liability-name order.
- A supplied alternative source cannot raise capacities for an existing snapshot. Capacities are part of `FinBoundSource` structural equality, so a differently capped source produces `SourceMismatch`.

Failure atomicity is sound:

- `apply_set_state` performs source, shape, row, and type checks before its single assignment.
- `apply_liability_add` checks asset range, existing-row position and identity, and `checked_add` before assignment. New-row insertion occurs only after existence, sorted-position, and capacity checks.
- `apply_transfer` resolves both positions, computes `checked_sub` and, for distinct rows, `checked_add` before either assignment. The later `if let Some(get_mut)` writes are unreachable as `None` because both indices came from `position` on the same unchanged vector and were already dereferenced through `get`. Self-transfer checks sufficiency, performs no net write, and still returns the transfer effect.
- `from_core` mutates no caller state and returns no partial snapshot on truncated/extra states, type mismatch, unknown assets, duplicates, or capacity excess.

The owner prose saying “no direct index remains” is not literally correct. Direct indexing remains in `FinSnapshot::from_core` sorting/duplicate checks and in `check_fin_snapshot` balance windows. It is nevertheless provably in range on current paths:

- In `from_core`, each row came from `asset_row_of`, which returns the `row` assigned by `bind_fin_source` as the binding’s enumeration index; the source is sealed.
- In `check_fin_snapshot`, explicit balance and liability asset-range checks precede the balance-window indexing.

That is a prose inaccuracy, not a reachable code defect. No mandatory code correction follows from it.
