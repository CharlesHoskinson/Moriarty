## Findings to fix before merge

**1. The loop insertion swallows the original priority text (structural).** `implementation-loop.md` adds a `###` heading directly under `## Current priority`. Everything after it, up to `## Entry and next actual implementation`, now renders as part of "Dated recovery correction". That includes the October 19 user instruction, the "Select work in this order" route and the 2026-10-17 provenance paragraph. In the TOC and in rendered structure, the user's original instruction appears to be content of the correction.
- **Fix:** keep it insertion-only, but place the block after those paragraphs, immediately before `## Entry and next actual implementation`. Alternatively, insert a `### October 19 instruction (original cut)` heading after the correction block.

**2. The verify-only prerequisite's status is not stated, so the supersession is ambiguous.** The old loop route and the experiment's step 1 both begin with "saved-bundle independent verify-only". The corrections say:
- the timeout has no verdict and must not be requeued unchanged;
- the experiment's order "records the original planning cut";
- the next path is complete-cohort → review/checks → C4 child compile.

Neither entry says whether step 1 is still an open prerequisite. A reader could take "original planning cut" plus the new next path as dropping it. The experiment sentence "This is separate from recursion and target acceptance" makes this worse, because its antecedent is unclear.
- **Fix:** add one sentence to both entries: "The saved-bundle verify-only prerequisite remains unsatisfied. Any consumption of its result needs a changed, separately eligible operation. Only the immediate next actionable step changes; the stage order and every acceptance requirement remain."

**3. The status record is not pinned or discoverable.**
- `DESIGN-011-STATUS-AND-PROVENANCE.md` has no path, byte count or SHA-256 in the change proof or in the AUTHORSHIP object. AUTHORSHIP names it by filename only.
- The verbatim README append and the note do not link to it. A reader of the note therefore sees stale statements with no visible pointer to the correction:
  - "push pending";
  - "fresh reviews are ready but not launched";
  - "unadopted and unexecuted";
  - "historical cached build".
- **Fix:**
  - Add the status record's preimage (absent) and afterimage pins to the change proof, and ideally a `status_sha256` to AUTHORSHIP.
  - Add a separate, clearly Sol-attributed README line after the verbatim append that links the status record. Do not edit the author's words.

"Privately" could read as unreviewable or unpublished, which conflicts with "applicable fresh review/checks". Use "separately frozen" consistently. The experiment entry says "frozen" and the DW addendum says "complete immutable", so the four entries also disagree with each other.

5. **"That finite uncharged window" (loop).** The K result covers two compiled windows. Use "windows" or "that finite uncharged profile", which is the DW addendum's wording.

6. **H1–H6/G1 versus one-Camino.** The status corrects "fresh reviews … not launched" by citing the one-Camino approval and method passes. It never says that the note's "owner H1–H6/G1 proposal" is that same candidate. If it is, say so explicitly, so that the note's "unadopted and unexecuted" is visibly superseded. Here "executed" covers only the ordinary methods, not cache reconstitution or native runs. If it is not the same candidate, the status needs to give that proposal's current state.
