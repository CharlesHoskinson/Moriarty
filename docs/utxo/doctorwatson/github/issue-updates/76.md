## Problem
`crates/mori-core` holds a second language frontend for Core (`language "moriarty/1";` and the staged `"moriarty/2"`): its own parser (`src/parser.rs`), IR (`src/ir.rs`), checker (`runtime::validate`, `stage/validate.rs`) and evaluator. It reuses only `mori-lexer`, not `mori-ast`, `mori-parser`, `mori-checker` or `mori-diagnostics`. `RUST_GUIDELINES.md` only covers `moriarty-beta/1`, so none of its frontend rules were applied:
- Tokens are copied into `Vec<Tok { text: String, .. }>` and the parser matches token text, not tags.
- The IR stores owned `String`s in array-of-structs nodes; `ExprId` is a bare `u16` alias, not a newtype.
- Two-token operators aren't checked for adjacency: `a = = b` parses as `a == b` and `a < = b` as `a <= b`. `not =` means "not equal".
- Errors are `mori_core::Error { code: String, message, offset, step }` with no spans, labels or help.

`mori check` also accepts `moriarty/1` and `moriarty/2` files (`crates/mori/src/commands/check.rs`), and `mori init` scaffolds `moriarty/1`. Neither is listed under *Intentional differences*. Sherlock's draft frontend (`moriarty-sherlock-draft/1`, `crates/mori-core/src/sherlock/draft_source.rs`) is a third grammar.

## Suggested fix
- **Option A (recommended):** parse Core with `mori-parser` into the struct-of-arrays `mori-ast` as a profile, check it with `mori-checker`, and lower the checked tables to the existing `mori_core::Program` IR, so `mori-backend` and `mori-ledger` don't change at first.
- **Option B:** keep Core separate, but give it its own crates that follow the same rules (lexer reuse, SoA AST with `u16` handles, a separate check phase, `MoriDiagnostic`), and add a Core section to `RUST_GUIDELINES.md`.

Either way, record the outcome in `RUST_GUIDELINES.md` and open issues for the chosen path.

## Needs input
This is a maintainer decision:
1. Is Core a profile of the beta pipeline or a separate language with its own crates?
2. Should `mori check` and `mori init` handle Core? If so, record it under *Intentional differences*.
3. Should `= =`, `< =` and `not =` stay accepted? Rejecting them breaks programs that parse today.
4. Should the Sherlock draft grammar converge with Core or beta, or stay separate?
