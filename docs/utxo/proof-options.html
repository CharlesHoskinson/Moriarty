    Why a proof does not authenticate its own root
    A Groth16 proof checks a relation against public inputs. If a prover supplies the root, the root is just another public input until the consumer ties it to an accepted source. Historical inclusion under a root is not proof that an output is still unspent, or that the set is complete.
    Batching or aggregation is not recursion
    Verifying several proofs together, or aggregating them, does not show that one proof checked another inside its relation, and does not link state from one step to the next.
    Same-transaction shards and ExUnits
    Several script inputs can compose atomically in one transaction when every required script accepts. They share that transaction's execution budget, so splitting work inside one transaction does not add total ExUnits.

      A proof checks a relation. An anchor gives the relation something to trust.

      How to read the labels

      ESTABLISHED means a cited source establishes it for the stated scope.

      ASSUMED means the consumer must supply, derive or trust it. Nothing on this page verifies a proof.

      How a proof becomes a UTxO transition

      An output only validates when another transaction spends it. There are no automatic triggers. A receipt UTxO is data that waits; a consumer transaction must spend it and run a validator that checks it.
