
## YOUR LENS: P3 — compilation, proving and AI ergonomics

You own the question of whether this can be built, proved, and driven by a machine.

- **Canonical form and the digest.** §8 requires a canonical encoding with bounded depth and node count, hashed to a digest that is a public input and authenticated in-circuit. Is that achievable for a recursive predicate tree? What is the actual cost shape — estimate it against ZKIRv3's 34 instructions and 13 types (see `wiki/zkir/zkir-instruction-set.md` and `docs/MORIARTY-BACKEND-REQUIREMENTS.md`). The design admits a tension and proposes a fallback: commitment to the tree plus in-circuit evaluation of only the effect-binding clauses. Is that fallback sound, and does it preserve the design's honesty claims?
- **What must be in-circuit versus checked by the ledger versus host-advisory.** For each MIL/1 construct — escrow release, refund, footprint disjointness, monotonicity, conservation, evidence class, authority kind, replay — say where it must be enforced and why. The controlling rule is that a host-computed Boolean is never sufficient. Which constructs does that rule make expensive, and is any of them unaffordable?
- **Compile-time checks the design assumes.** It requires: `release ∧ refund` unsatisfiable; `release ∨ refund ∨ after(deadline)` valid; escrow exit reachability; footprint disjointness; hole polarity. Are these decidable for Φ as specified, and at what complexity? Name the decision procedure. If any needs an SMT solver, say so plainly — the project has an explicit position that adding a solver to the trusted computing base is a cost, and a compile-time-only use may or may not escape it.
- **The Episode.** A bounded DAG of stages with joins, compensation and cumulative budgets. How does it compile? Is an Episode a single proof, a proof per stage with a linking relation, or a recursive certificate — and how does that interact with the fact that Midnight per-transaction recursive verification is not assumed available and full recursion is a March 2027 planning assumption? Does the Episode force U4 work into U2?
- **Bounded execution.** Every stage terminates in checked bounds. Does Φ evaluation, footprint computation and escrow exhaustiveness checking fit a bounded stage? What is the worst case for a realistic intent?
- **AI ergonomics, concretely.** §11 lists ten properties. Which of them actually hold given the rest of the design, and which are aspirations? Focus on: counterexample-carrying rejection (what exactly is returned, and is a minimal unsatisfiable core computable here?), the distinct outcome vocabulary, declared per-clause cost (computable statically, or does it depend on runtime data?), and residue (does a residue field weaken the acceptance relation — can a program hide a real effect in residue?).
- **Implementability at U0.** The design places Φ, types, footprints, authority kinds and canonical form in U0 as the signed-intent syntax task. Is that a realistic U0 scope, or is it three milestones of work? If it is too big, what is the minimum subset that must be frozen at U0 so the rest can arrive without a breaking change — and what exactly breaks if it is deferred?

Estimate numbers where you can, and say when a number is an estimate rather than a measurement.
